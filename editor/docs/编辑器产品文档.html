1. 概述

1.1 目的

本文档定义 GF 内容编辑器（下文简称"编辑器"）的产品方案：它是什么、给谁用、解决什么问题、界面长什么样、每个功能怎么操作、系统怎么反馈。文档面向数值策划、系统策划、关卡策划、文案/本地化、程序、美术六类读者，作为后续实现立项、UI 详细设计、开发排期的唯一依据。本文档不涉及具体实现技术栈的最终拍板（第 16 章"技术选型建议"明确标注为实现层面的建议，不是架构结论），也不新增任何架构原语（技能效果类型、光环效果类型、职能标志位等的新增仍走 12_扩展与变更流程.md 的 ADR 审批）。

1.2 定位

GF 内容编辑器（Game Foundation Editor，简称 GF 编辑器；命名来自框架包名前缀 com.gamefoundation）是一个 Windows 桌面程序，用来编辑基于本框架（architecture/ 文档集）立项的任意一款 <game> 的全部内容数据。

一句话说清它做什么：游戏世界里能被策划改动的一切——人物与生物、职业与天赋、属性、技能、光环、触发器、施法修正、物品（含新增装备）、套装、词缀、槽位与品质定义、掉落与爆率、经验与等级曲线、任务、对话（菜单与剧情树）、遭遇与关卡、刷新表、区域触发、难度档位、成就、货币与商人、阵营与反应矩阵、目标选择链、AI 行为外壳与优先级表、外形映射与动画集与装备外观、特效与音效定义、飘字/镜头/界面布局/外壳菜单等表现层配置、本地化文本——全部是 04_数据与内容管线.md 第 1.1 节总索引里登记的60 余张结构化数据表里的行，编辑器就是编辑这些表的通用工具。

理论基础是 ADR-0004 拍下的"数据即内容"：游戏世界一切具体内容都是结构化文本表里的行，运行时只认 id 与字段，不认具体内容。这句话反过来定义了编辑器的能力边界：

编辑器 = 对所有表的通用编辑能力 + 对高频域的专项编辑器 + 与运行时完全一致的校验 + 数值预览/模拟。

编辑器只编辑内容，不新增原语：新增一种效果类型（如给 skill.def.effects 加一种新的原语）、新增一种光环效果类型、新增一种职能标志位，都属于"改变运行时代码能理解的词汇表"，必须先过 ADR 审批并由程序落地代码，编辑器本身不提供"发明新原语"的入口；编辑器能做的是列出已经登记的原语供策划选择、组合、填参数——这与"数据即内容"的边界完全一致：内容作者只管往表里加行，不碰运行时代码。

1.3 面向用户

角色 典型诉求
数值策划 调技能伤害系数、属性成长曲线、物品预算、经验曲线，需要立刻看到结算结果，不想自己心算三段式聚合
系统策划 设计新机制对应的内容组合（新装备、新光环、新触发器），需要看到"这条数据会影响哪些既有内容"
关卡策划 配掉落表、遭遇/波次/阶段、刷新点、区域触发，需要在地图上直接摆放坐标而不是心算 Vec2
文案/本地化 补齐/核对多语言文本，需要一张能看清"哪些 key 缺哪个语言"的矩阵，不想在几十个 JSON 文件里翻找
程序 升级框架版本后要跑迁移、跑全量校验，需要确认"编辑器里看到的红线 = 运行时/门禁会报的错"
美术 核对外形映射（display.map 等）里引用的资源是否存在、纸娃娃层是否齐全，不想手动比对文件名

单机单用户使用场景：编辑器不做账号体系、不做多人实时协作，文件落地即 JSON（见 data/README.md 的信封与主键规则），协作方式是团队各自用编辑器改自己负责的表，再靠 git 提交、review、合并（见第 12 章"版本控制与协作"）。

1.4 典型用户故事

以下六个场景覆盖编辑器最核心的价值主张，后续各章的功能设计均以能完整走通这六个场景为验收基准。

故事 1：数值策划改一条技能伤害并立刻看结算预览。 数值策划打开"技能/状态/触发编辑器"，在技能列表里选中 skill.sample_strike，在效果卡片里把 school_damage 的 coefficient 从 1.0 改成 1.2；右侧"结算预览"面板已经选好了施法者模板 creature.sample_hero 与目标模板 creature.sample_beast，数值改动的瞬间（字段失焦或按 Enter）预览面板重新跑一次确定性模拟，命中表、护甲减免、最终伤害与期望 DPS 立即刷新，策划不需要保存、不需要打开游戏、不需要心算三段式聚合。

故事 2：系统策划新增一件装备并自动生成外形/文本行。 系统策划在"物品编辑器"点"新增物品"，向导依次选槽位（item.slot_definition 下拉）、品质（item.quality_definition 下拉）、物品等级、输入显示名；系统自动生成 item.<name> 形式的 id、l10n.item.<name>.name 文本键并写入默认语言正文、在 display.map 里创建一行外形占位（display.<name>，等待美术核对具体资源）；向导第三步进入属性分配，实时显示"预算消耗 / 预算上限"进度条；完成后自动跑一次字段级 + 表级校验，0 错误时向导关闭并把新记录带到检视区。

故事 3：关卡策划配掉落表并模拟 1 万次。 关卡策划在"掉落与爆率编辑器"给 loot.sample_beast 加一个 weighted_pick_one 分组，塞入三件候选物品，各自设权重；右侧"模拟面板"输入次数 10000、种子 12345，点"运行模拟"，几秒内输出每件物品的出现次数、实际概率（与权重归一化后的理论概率对比）、平均获得数量、按物品预算估算的期望价值，策划据此判断"稀有件出现频率是否符合设计目标"。

故事 4：文案补齐缺失文本键。 文案打开"本地化编辑器"，矩阵视图按"缺失单元格"排序，看到 l10n.quest.deliver_letter.description 在 zh-CN 有正文但 en-US 缺失（高亮黄色）；文案双击该单元格直接填入译文，保存后该行的缺失标记消失，问题面板里对应的一条"文本键存在"警告随之清除。

故事 5：程序升级框架版本后跑迁移与全量校验。 程序把工程的框架快照路径从 dist/0.2.0/ 改指到 dist/0.3.0/，重新打开工程时状态栏提示"框架版本 0.3.0，检测到 2 张表 schema_version 落后"；程序在"校验、诊断与引用分析"面板点"执行迁移"，预览迁移前后字段差异（如新增字段的默认值）后确认执行，迁移完成后触发一次全量校验，报告 0 错误后程序提交这批因迁移产生的文件改动。

故事 6：美术核对外形映射资源是否存在。 美术打开"外形与表现编辑器"，筛选"资源缺失"，看到 display.map.sample_new_monster 一行的 sprite_set_id 在工程 assets/ 目录下找不到对应文件，黄色感叹号标注；美术确认是资源还没导出，先在编辑器里记下待办，等 ComfyUI 出图与 import_assets.py 跑完后重新扫描，该行的黄标自动消失。

1.5 与现有工具链的关系（先给结论，细节见第 3 章）

编辑器不是另起一套数据规范或校验规则，而是仓库既有工具链（data/README.md、toolchain/validate_data.py、toolchain/validator、toolchain/import_assets.py）之上的图形化前端：数据文件组织、信封、主键规则、多根合并、字段级/引用级校验规则、外形映射生成方式，编辑器全部复用，不重复定义、不产生第二套语义。第 3 章"总体方案"给出编辑器如何在实现层面直接复用这些既有能力。

2. 术语与范围

2.1 术语表（详版见附录 E）

术语 含义
工程 编辑器打开的一个游戏数据编辑单元，对应某个 <game> 仓库的 data/<game>/ 数据根 + 其锁定的框架快照 dist/<version>/
工作区 工程在编辑器本地的偏好与状态存档（<game>/.gfeditor/workspace.json），非数据本身
数据根 一批同构织入的数据文件目录，编辑器按"多根合并"规则同时加载框架根（data/_framework/）与游戏根（data/<game>/），见 04 第 4 节
层（框架层/游戏层） 数据根的归属：框架层数据（随 dist/<version>/data/_framework/ 交付）默认只读，游戏层数据（data/<game>/）可编辑；框架层记录可通过"覆盖到游戏层"生成可编辑副本（见第 6.4 节）
表 / 域 / 记录 / 字段 表 = 一个 .json 文件对应的一组同构记录；域 = 表名第一段（如 skill、item）；记录 = 表里的一行；字段 = 记录里的一个键值对
引用 某字段的值是另一条记录的 id，由 FieldKind.Reference 或 DataRegistry.declareReference 声明，编辑器据此做引用完整性检查与"跳转到目标记录"
文本键 l10n.text 表的 key，格式 l10n.<来源域>.<来源记录name>.<字段名>，由 FieldKind.TextKey 字段承载
Expr 全架构统一的条件/表达式语言，见 04 第 6 节
校验报告 一次校验（字段级/表级/全量）产出的问题列表，含错误与警告两级
变更集 编辑器一次会话内累积的未保存改动集合，是撤销栈与"保存哪些表"判断的基础
原语 效果类型、光环效果类型、职能标志位等运行时代码认识的固定词汇表条目，新增须走 ADR
时间模型 found.time_model 声明的连续（continuous，单位秒）或离散（discrete，单位回合）模式，决定编辑器里时间字段显示"秒"还是"回合"

2.2 范围内

  • 编辑 data/<game>/ 下全部内容表的记录（增删改、克隆、重命名 id、跨层覆盖）。
  • 与运行时完全一致的校验（复用 DataRegistry 与全部 IValidationRule）。
  • 高频域的专项编辑体验（技能/物品/生物/掉落/经验/任务对话/世界遭遇/本地化/外形表现）。
  • 脱离引擎的数值预览与确定性模拟（结算预览、掉落模拟、经验估算、简易战斗回放）。
  • 批量编辑、查找替换、CSV 导入导出。
  • 与 git 的只读感知（状态显示、diff 预览、提交前自动校验提示），不内置完整 git 客户端。
  • 与游戏可执行文件/Unity 工程的联调（一键运行、保存触发热重载、日志反查）。

2.3 范围外（明确不做）

不做的事 原因
不编辑引擎场景资源本身（精灵图、模型、音频文件的二进制编辑） 属于美术/引擎工具职责，编辑器只管理"逻辑 id → 资源引用"的映射行，资源本身由 import_assets.py 或引擎编辑器产出
不做代码编辑 编辑器编辑的是数据表，不是 C#/脚本源码；script 效果原语与 found.hook 钩子的具体实现在代码里，编辑器只填钩子 id
不新增原语 见 1.2 节；新增效果类型/光环类型/职能标志位需过 ADR 并由程序实现
不做多人实时协作（无锁机制、无云端会话） 单机单用户工具，协作靠 git，见第 12 章
不做在线服务（无账号、无云同步、无遥测上报） 见第 15.4 节"安全"：编辑器不联网、不上传
不做完整的 git 客户端（不做分支管理、不做交互式 rebase） 复杂 git 操作交给专业 git 工具，编辑器只做"内容改动"视角需要的最小 git 感知

3.2 数据流

打开工程
  → 探测数据根（框架快照 data/_framework/ + 游戏根 data/<game>/）
  → DataRegistry.loadAll(多根) —— 按主键合并、按 schema_version 检查、跑迁移
  → 内存记录集（DataRecord 集合，按表分组）
  → 用户编辑（网格/表单/源码三视图任一）
  → 字段级即时校验（编辑动作发生时，FieldKind 对应的单字段规则）
  → 保存（该记录所属表文件整份格式化写回：稳定字段顺序、2 空格缩进、LF、无 BOM）
  → 表级校验（该表全部记录的 IValidationRule）
  → （用户手动触发或提交前）全量校验 —— 等价 toolchain/validate_data.py 两道校验，可选 --strict
  → git（编辑器展示状态与 diff，用户在编辑器内或外部 git 工具提交）

3.3 核心技术主张（编辑器实现层面的选型建议，非架构结论）

本节标注的四点是"编辑器如何实现"层面的建议，供第 16 章"技术选型建议"进一步展开评估，不是架构文档的结论，不影响 architecture/ 的任何既有拍板。

编辑器进程内直接引用框架的六个核心类库（Core.Foundation → Core.Numbers → Core.Rules → Core.Carriers → Core.Gameplay → Presentation.Common，由 build.ps1 编译出的 Release DLL，目标框架 .NET Standard 2.1）与桩适配层（Adapters.Stub，纯 .NET 实现），而不是自己重新描述表结构、重新实现校验、重新实现结算算法。这样做换来四个"零重复"：

  1. 表结构零重复：核心库的 TableSchema/FieldSchema（core/foundation/data_registry/contracts/）已经登记了每张表的字段名、FieldKind（Bool/Int/Number/String/Id/IdList/Reference/TextKey/Expr/Enum/Vec2/Object/Array，见 FieldKind.cs）、Required、EnumValues、ReferenceTable/ReferenceDomain、Description（见 FieldSchema.cs）、当前 CurrentSchemaVersion 与 Migrations 迁移链（见 TableSchema.cs）。编辑器读取这些声明自动生成网格列与表单控件（见第 6.2 节控件映射表），新表/新字段只要在核心库登记，编辑器零改动即可编辑——不需要为每张新表单独写一份 UI 代码。
  2. 校验规则零重复：编辑器直接调用 DataRegistry.LoadAll/Validate/Reload 与全部已注册的 IValidationRule，做到"编辑器里看到的红线 = 运行时/门禁会报的错"这一硬承诺；不存在"编辑器说没问题，但 validate_data.py 报错"的割裂体验。
  3. 数值预览与模拟零重复：确定性固定步长模拟（拍板决策 3）本身可以脱离引擎运行，编辑器借桩适配层（Adapters.Stub）跑结算管线（06 第 4.1 节）、掉落抽取（08 第 1 节）、经验曲线换算等"数值沙盘"（第 10 章），预览结果与游戏内真实运行结果保证一致，因为走的是同一份规则层代码。
  4. 版本对齐：编辑器随框架 dist/<version>/ 同版本发布，或自身声明兼容的框架版本范围；打开工程时核对游戏工程 Packages/manifest.json 里 file: 锁定的框架快照版本，版本不匹配时提示但不阻断打开（只读模式下仍可查看）。

3.4 与既有工具链的复用关系一览

既有工具/文档 编辑器如何复用
data/README.md 文件组织（data/<game>/<domain>/<table>.json）、信封（table/schema_version/rows）、主键规则（内容表 id、登记表 key、l10n.text 复合键）、编码格式（UTF-8 无 BOM、2 空格、LF）全部照搬，保存动作严格产出符合此约定的文件
toolchain/validate_data.py 编辑器"手动全量校验"命令等价调用它的两道校验（骨架级 + toolchain/validator），支持传等价的 --strict
toolchain/validator（.NET） 编辑器进程内直接引用同一套 DataRegistry + IValidationRule 实现（而非再拉起子进程），字段级/表级校验走同一套代码路径；全量校验可选择"进程内跑"或"拉起子进程跑，日志汇入输出面板"两种模式（后者用于跟门禁行为完全对齐地复核）
toolchain/import_assets.py 编辑器"外形与表现编辑器"提供调用入口（见第 7.9 节），把出图产物生成 display.map/display.equip_visual 行，编辑器本身不重复实现资产扫描逻辑
04 第 4 节多根加载与合并规则 编辑器打开工程即按此规则加载框架根 + 游戏根，override/final 字段在记录操作里可视化呈现（见第 6.4 节）
04 §4 DataRegistry.reload(domain) 编辑器保存文件后，若联调面板检测到游戏侧以开发期构建运行，转发一次 reload 请求触发热重载（见第 13 章）

4. 工程与工作区

4.1 新建/打开工程向导

编辑器首次启动或点"新建/打开工程"时弹出向导：

  1. 选游戏仓库根：文件选择器选中某个 <game> 仓库的根目录（例如用户本地的游戏仓库路径）。
  2. 自动探测数据根：编辑器在所选根目录下查找 data/<game>/（<game> 段名由该仓库自己决定，编辑器不关心具体拼写），探测到即列为"游戏层数据根";若找不到，提示用户手动指定路径或改为"仅浏览框架层"的只读模式。
  3. 自动探测框架快照：读取该仓库 Unity 工程 Packages/manifest.json 里 com.gamefoundation.adapter.unity/com.gamefoundation.game-template 的 file: 依赖路径，解析出所指向的 dist/<version>/ 目录，从中读取 dist/<version>/data/_framework/ 作为框架层数据根、读取内嵌的核心 DLL 供编辑器加载；若 manifest.json 不存在或依赖路径解析失败，弹出手动选择框架快照目录的对话框。
  4. 显示框架版本与编辑器兼容性：向导最后一步展示"检测到框架版本 0.3.0，本编辑器兼容 0.2.x ~ 0.3.x"一类结论；版本超出兼容范围时给出黄色警告但允许继续（只读优先，写操作前二次确认）。
  5. 确认后进入主界面，状态栏立即显示工程名与框架版本（见第 5.7 节）。

4.2 最近工程

主界面欢迎页与"文件"菜单下列出最近打开的工程（路径 + 上次打开时间 + 框架版本），点击直接按 4.1 节流程重新加载；工程路径不存在时该项标灰并提示"未找到，是否移除记录"。

4.3 工程文件 .gfeditor/workspace.json

工程首次打开成功后，编辑器在游戏仓库 <game>/.gfeditor/workspace.json 写入/更新一份工作区文件，记录：

字段 说明
dataRoots 已探测/手动指定的数据根路径列表（框架层 + 游戏层）
frameworkSnapshotPath 当前锁定的 dist/<version>/ 路径
defaultLocale 默认语言，用于文本键校验与内联编辑默认显示语言
preferences 编辑器偏好（布局、主题、最近打开的标签页等，纯 UI 状态）
lastValidationSummary 上次全量校验的时间与结果摘要，供打开工程时快速展示"距上次校验已过 N 天"

是否入库的建议（默认方案，可调整）：workspace.json 里 dataRoots/frameworkSnapshotPath/defaultLocale 属于"团队共享的工程配置"，建议入库（多人打开工程时行为一致）；preferences（布局、最近标签等纯个人偏好）与自动保存草稿目录（见第 15.2 节 .gfeditor/autosave/）不建议入库，建议在游戏仓库 .gitignore 里为 .gfeditor/autosave/ 与 .gfeditor/*.local.json 加忽略规则；编辑器首次写入 workspace.json 时如检测到仓库尚无对应 .gitignore 规则，弹出一次性提示询问是否代为写入。

6. 通用表编辑器（Schema 驱动）

6.4 撤销/重做

跨记录、跨表的事务式撤销栈：一次原子编辑（改一个字段值、执行一次批量替换、执行一次重命名 id 级联更新）作为一个撤销单元；Ctrl+Z/Ctrl+Y 在整个工程范围内撤销/重做，不限定在当前打开的标签；保存动作不清空撤销栈（保存只是把当前内存状态落盘，撤销栈仍保留保存前后的完整历史，允许"保存后又想撤销回保存前的状态"）。撤销栈上限为可配置的操作步数（默认 500 步，见第 14.1 节设置项），超出上限从最早的操作开始丢弃。

6.5 保存

  • 按表文件写回：一次保存动作只重写该记录所属的表文件（data/<game>/<domain>/<table>.json），不触碰其它未改动的表文件。
  • 稳定字段顺序：按 TableSchema.Fields 声明的顺序输出字段；核心库尚未登记但文件里已存在的未知字段，保留在已知字段之后、按原文件中的相对顺序追加，不丢弃。
  • 格式：2 空格缩进、LF 行尾、UTF-8 无 BOM，与 data/README.md "编码与格式"一节要求一致，保证 git diff 最小（只有真正改动的字段产生 diff 行）。
  • 外部修改检测：编辑器对已打开工程的数据根文件保持文件系统监视；若磁盘文件在编辑器外被修改（如另一进程的脚本改了 JSON，或 git 切换分支），弹出提示"检测到外部修改"，提供"重新加载（丢弃编辑器内改动）"与"对比差异后决定"两个选项，避免静默覆盖。

7. 专项编辑器

9.3 覆盖诊断

多根合并产生的 override: true/final: true 行为（见 04 第 4 节 2026-09-06 修订）不是错误，而是一类信息级诊断，单独列在问题面板的"覆盖诊断"分类下：

  • 某记录被后层 override: true 覆盖：显示"框架层原始版本 vs 游戏层覆盖版本"的并排字段差异对比。
  • 某记录声明 final: true 且被后层尝试覆盖：显示为阻断错误（04 定义为仍判定阻断），提示"该记录禁止被覆盖，请改用其它 id 新增而非覆盖同名记录"。
  • 单根场景（该表本次未跨根合并）出现 override/final 字段为真值：显示为警告"该字段仅在跨根同主键重叠时生效，当前单根场景下已被忽略"，对应 04 第 4 节该行为定义。

9.4 引用图（引用了谁 / 被谁引用）

  • 检视区"引用面板"（第 5.5 节）对当前选中记录展示两个列表：引用了谁（本记录全部 Reference/Id（识别为引用字面量）/Expr 中 id 字面量指向的目标，逐条可点击跳转）与被谁引用（反向索引，扫描全部已加载记录中指向本记录的引用字段，逐条可点击跳转）。
  • 删除影响分析对话框（第 6.3 节"删除"操作触发）：复用同一份反向索引，列出"被谁引用"的完整清单，按所属表分组，用户可展开查看具体字段路径。
  • 孤儿视图：本地化编辑器（7.8）与通用表编辑器筛选行（"孤儿"复选框，第 5.3 节）共用同一份反向索引数据源，展示"没有被任何已知入口引用"的记录（对应 04 第 5 节"孤儿记录检测"，警告级，不阻断，便于清理）。

9.5 schema 迁移

打开工程时若检测到某表记录的 schema_version 低于核心库 TableSchema.CurrentSchemaVersion，状态栏与问题面板同时提示"N 张表待迁移"；用户在"校验"菜单点"执行迁移"，弹出预览对话框逐表展示迁移前后的字段差异（新增字段的默认值、被拆分/合并的字段），确认后按 TableSchema.Migrations 声明的迁移链顺序执行（04 第 3 节"迁移链只增不减"），执行完成后记录的 schema_version 写为当前版本、migrated_from 记为原始版本号，随后自动触发一次全量校验确认迁移未引入新问题。

12. 版本控制与协作

12.1 git 状态显示

底部面板区"git 变更"子面板（第 5.6 节）列出当前工程数据根内相对 git HEAD 的文件级改动（新增/修改/删除三色图标），实时随保存动作刷新；状态栏（第 5.7 节）显示当前分支名与脏文件计数。

12.2 变更文件列表与 diff 预览

点击"git 变更"面板中的任一文件，右侧弹出并排 diff 预览（旧内容 | 新内容，逐行高亮增删），diff 渲染基于文本行比较（因为保存动作保证稳定字段顺序，diff 天然聚焦在真正改动的字段行，见第 6.5 节）；面板提供"暂存该文件"/"撤销该文件改动（还原为 HEAD 版本）"两个操作，其余 git 操作（提交、拉取、推送、分支管理）引导用户使用外部专业 git 工具或命令行完成，编辑器不重复实现完整 git 客户端（第 2.3 节范围外声明）。

12.3 提交前自动校验

对应仓库既有 .githooks/pre-commit 的快速门禁思想：编辑器"校验"菜单提供"提交前检查"命令，一键跑一次全量校验（等价 validate_data.py 两道校验）并汇总结果；若配置了自动模式（第 14.1 节设置项），编辑器检测到用户即将通过其内置的"暂存"操作提交时会先自动跑一次该检查，报错时弹出确认框"仍有 N 个错误，是否继续提交"，默认按钮为"取消"。

12.4 冲突时的记录级合并辅助

当 git 报告某数据表文件存在合并冲突（例如 pull 时与远端改动冲突）时，编辑器提供"记录级合并"辅助视图：读取冲突文件的双方版本（--ours/--theirs，经外部 git 命令获取原始文本），按主键对比出"仅本地改""仅远端改""双方都改"三类记录，双方都改的记录并排展示字段级差异，用户逐条选择"用本地"/"用远端"/"手动编辑合并"，全部记录确认后拼装出合并结果并写回文件，供用户在 git 里标记该文件为已解决冲突；此辅助视图不自动执行 git 命令本身（add/commit 等），只负责生成正确的合并后文件内容。

13. 运行联调

13.1 配置游戏可执行文件/Unity 工程路径

"运行"菜单"配置联调目标"：选择该游戏的 Unity 工程路径（用于一键在编辑器内启动 Unity 编辑器打开该工程）或独立版可执行文件路径（用于一键启动打包后的游戏）；两者均可配置，互不冲突（开发阶段常用 Unity 工程内运行，验收阶段用独立版可执行文件运行）。

13.2 一键运行

"运行"菜单"运行▶"（或工具栏按钮）按已配置的目标启动：若目标是 Unity 工程，拉起本机 Unity Editor 以命令行参数打开该工程并进入 Play 模式（需要该工程已同步过最新的 data/<game>/，编辑器保存动作已保证这一点）；若目标是独立版可执行文件，直接启动该进程；启动日志汇入"输出"面板。

13.3 保存触发热重载

保存动作完成后，若联调面板检测到目标游戏进程正以开发期构建运行（编辑器与目标进程之间通过本地约定的开发期热重载通道通信，具体传输机制留给实现阶段按 04 §4 DataRegistry.reload(domain) 与落地计划"数据加载"一节"编辑器内构建监听 JSON 文件变化触发重载并发 data.load_completed"的既有设计落地，默认方案，可调整），编辑器发出一次针对该表所属 domain 的 reload 请求；成功回执后"输出"面板打印"已触发 <domain> 热重载"。

前提与限制（必须在界面上明确提示，避免用户误判"为什么没生效"）：

  • 仅对开发期构建有效，发布构建默认关闭热重载通道（对应落地计划"编辑器内构建...仅限编辑器内构建"）。
  • 结构性改动（新增字段、改变字段类型、schema_version 提升）仍需要重启游戏进程才能生效，热重载只对"同结构下的数值/内容变化"生效；编辑器保存后若判断本次改动可能涉及结构变化（如触发了迁移），主动提示"本次改动建议重启联调目标"而不是尝试热重载。

13.4 从游戏日志反查编辑器记录

联调运行时，编辑器订阅目标进程输出的日志流（若目标提供，默认约定读取标准输出/标准错误或指定日志文件路径，具体接入方式属实现细节）；日志文本中出现符合 id 格式（^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$）的片段时，"输出"面板对该片段做超链接高亮，点击直接在编辑器内跳转打开对应记录，便于"游戏里报了个奇怪的 skill.xxx 找不到"这类问题的快速定位。

战斗回放导出目录 <工程>/.gfeditor/exports/ 数值沙盘导出文本落地目录
网格虚拟化行高 28px 影响大表滚动的渲染密度，性能与信息密度的折中项

14.2 插件机制

编辑器提供四类扩展点，供后续按需扩展而不改动编辑器核心：

扩展点 用途 约束
专项编辑器插件 为某张/某组表提供更定制的界面（类似第 7 章九个专项编辑器的编写方式） 必须通过核心库 DataRegistry 读写记录，不允许绕过其校验直接操作文件
字段控件插件 为特定 FieldKind 或特定字段（按表名+字段名匹配）提供自定义控件渲染 控件只做展示与编辑交互，字段值的读写仍经统一的记录模型 API
沙盘插件 新增一种数值预览/模拟面板（第 10 章之外的自定义沙盘） 必须使用桩适配层跑逻辑，不允许沙盘内直接读写磁盘数据文件
导入器插件 新增一种批量导入格式（CSV 之外，如 Excel、专有格式） 导入结果必须经过与手工编辑相同的字段级/表级校验，不允许跳过校验直接写盘

插件目录：<编辑器安装目录>/plugins/<插件名>/，每个插件是独立目录，含清单文件（声明插件类型、兼容的编辑器版本范围、入口）与实现文件；编辑器启动时扫描该目录加载。不允许绕过核心库校验是插件机制的硬约束（对应第 1.2 节"编辑器只编辑内容，不新增原语"的产品定位，插件也不例外）。

14.3 schema 变化自动适配的原则

核心库新增一张表或给已有表新增字段时，编辑器不需要跟着改代码即可继续工作：新表自动出现在导航区"按层/域/表"树中（归入通用表编辑器）；已有表新增字段自动出现在表单视图的对应分组末尾与网格视图的新增列（默认显示，用户可手动隐藏）。只有当某张表需要专属的可视化（画布、卡片、图表）时才需要更新对应专项编辑器或走插件机制补一个专项编辑器插件；这是"零改动可编辑新表"（第 3.3 节主张 1）与"专项体验需要额外投入"之间的边界。

16. 技术选型建议

本章标注为实现层面的建议，非架构结论，可在实现立项时另出评估文档拍板，不影响 architecture/ 目录下任何既有结论。

16.1 桌面壳：WPF 与 Avalonia 对比

维度 WPF（.NET 8） Avalonia（.NET 8）
平台范围 仅 Windows 跨平台（本产品只需 Windows，此项非决定因素）
与核心 DLL（.NET Standard 2.1）互操作 原生，无额外适配层 原生，无额外适配层
生态成熟度（数据网格、代码高亮控件） 成熟（第三方控件库选择多，社区历史悠久） 逐步成熟（部分控件需自行封装或用较新的第三方库）
主题/深浅色支持 需要自行搭建资源字典体系 内置 Fluent 主题与浅深色切换支持较完善
团队现有经验（假设） Windows 桌面团队通常更熟悉 需要一定学习曲线
建议 首选（默认方案，可调整）：本产品明确只需 Windows，WPF 生态里的数据网格/代码编辑控件选型更直接，减少自研控件的工作量 若未来有跨平台需求（当前无）可重新评估

16.2 理由与备选（Web 壳 + 本地服务）对比

维度 桌面壳（WPF/Avalonia）直接引用核心 DLL Web 壳（本地 HTTP 服务 + 浏览器/内嵌 WebView 前端）
与核心库集成方式 进程内直接引用，无序列化开销 核心库跑在本地服务进程，前端通过 HTTP/WebSocket 调用，需要额外设计 API 协议与序列化
启动性能 更快（无需起服务进程 + 浏览器渲染进程） 较慢（两个进程 + WebView 启动开销）
离线可靠性（第 15.5 节"不联网"要求下的自洽性） 天然离线，无端口占用/防火墙提示等困扰 本地服务仍可能触发系统防火墙首次提示，用户体验有干扰
UI 生态（图表、代码高亮控件） 需要选型桌面端专属控件库 可直接复用成熟的 Web 前端生态（图表库、代码编辑器组件更丰富）
结论 选桌面壳：第 15.5 节离线要求与启动性能优先级更高，UI 生态差距可通过桌面端成熟的第三方控件库弥补 仅在未来若需要"团队远程协作查看只读快照"一类场景时才重新评估 Web 壳路线

16.3 图表、代码编辑控件、文件监视、git 调用方式（默认方案，可调整）

能力 建议方案
图表（成长曲线、经验曲线、结算预览条形图） 桌面端成熟图表库（如 OxyPlot 一类开源图表库），满足折线/柱状/进度条即可，不需要复杂交互式图表
代码/JSON 高亮编辑控件（源码视图、Expr 编辑器） 桌面端成熟的代码编辑控件（如 AvalonEdit 一类），自行扩展语法高亮规则以支持 Expr 语法与 JSON

git 调用方式 拉起本机已安装的 git 命令行工具（子进程），解析其文本输出得到状态/diff；不内嵌完整 git 实现库，保持与用户本机 git 配置（凭据、hooks）行为一致

16.4 与 toolchain/validator 共享注册逻辑的方式

toolchain/validator（.NET）的 Program.cs 并不自己枚举各层的表与规则，而是直接调用核心库已经存在的级联注册目录：core/rules/assembly/RulesSchemaCatalog（注册 L0 内置 + L1 五模块 + L2 四模块的 TableSchema/IValidationRule）→ core/carriers/assembly/CarriersSchemaCatalog（级联 RulesSchemaCatalog 后再补 L3）→ core/gameplay/assembly/GameplaySchemaCatalog（级联后再补 L4）→ presentation/assembly/PresentationSchemaCatalog（级联后再补 L5）；toolchain/validator/Program.cs 实际调用的正是最外层的 PresentationSchemaCatalog.RegisterAll，一次性注册齐全部 L0～L5 模块。编辑器建议直接引用与 toolchain/validator 相同的注册入口——core/rules/assembly/RulesSchemaCatalog 等各层 assembly 注册目录（编辑器按需覆盖到哪一层，就引用哪一层级联到底的目录，通常是最外层的 PresentationSchemaCatalog）——从而保证"编辑器已知的表清单与校验规则"与"门禁用的校验器已知的表清单与校验规则"永远是同一份代码产出的同一份注册结果，不需要人工保持两处同步。若后续把 toolchain/validator Program.cs 里"调用汇总注册入口 + 设置 FailOnUnknownTable/Strictness 等选项"这一小段本身也抽成一个核心库内、专供 toolchain/validator 与编辑器两个消费方共用的更薄的汇总入口更佳（默认方案，可调整：是否需要再抽这一层、抽到哪个程序集，留待实现阶段与 toolchain/validator 的实际代码结构对齐决定），本节结论不影响 architecture/ 的任何既有拍板。
