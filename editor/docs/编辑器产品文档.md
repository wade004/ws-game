## 1. 概述

### 1.1 目的

本文档定义 **GF 内容编辑器**（下文简称"编辑器"）的产品方案：它是什么、给谁用、解决什么问题、界面长什么样、每个功能怎么操作、系统怎么反馈。文档面向数值策划、系统策划、关卡策划、文案/本地化、程序、美术六类读者，作为后续实现立项、UI 详细设计、开发排期的唯一依据。本文档不涉及具体实现技术栈的最终拍板（第 16 章"技术选型建议"明确标注为实现层面的建议，不是架构结论），也不新增任何架构原语（技能效果类型、光环效果类型、职能标志位等的新增仍走 [12_扩展与变更流程.md](../../architecture/12_扩展与变更流程.md) 的 ADR 审批）。

### 1.2 定位

**GF 内容编辑器**（Game Foundation Editor，简称 GF 编辑器；命名来自框架包名前缀 `com.gamefoundation`）是一个 **Windows 桌面程序**，用来编辑基于本框架（`architecture/` 文档集）立项的任意一款 `<game>` 的**全部内容数据**。

一句话说清它做什么：游戏世界里能被策划改动的一切——人物与生物、职业与天赋、属性、技能、光环、触发器、施法修正、物品（含新增装备）、套装、词缀、槽位与品质定义、掉落与爆率、经验与等级曲线、任务、对话（菜单与剧情树）、遭遇与关卡、刷新表、区域触发、难度档位、成就、货币与商人、阵营与反应矩阵、目标选择链、AI 行为外壳与优先级表、外形映射与动画集与装备外观、特效与音效定义、飘字/镜头/界面布局/外壳菜单等表现层配置、本地化文本——全部是 [04_数据与内容管线.md](../../architecture/04_数据与内容管线.md) 第 1.1 节总索引里登记的**60 余张结构化数据表**里的行，编辑器就是编辑这些表的通用工具。

理论基础是 ADR-0004 拍下的"数据即内容"：游戏世界一切具体内容都是结构化文本表里的行，运行时只认 id 与字段，不认具体内容。这句话反过来定义了编辑器的能力边界：

> **编辑器 = 对所有表的通用编辑能力 + 对高频域的专项编辑器 + 与运行时完全一致的校验 + 数值预览/模拟。**

编辑器**只编辑内容，不新增原语**：新增一种效果类型（如给 `skill.def.effects` 加一种新的原语）、新增一种光环效果类型、新增一种职能标志位，都属于"改变运行时代码能理解的词汇表"，必须先过 ADR 审批并由程序落地代码，编辑器本身不提供"发明新原语"的入口；编辑器能做的是**列出已经登记的原语供策划选择、组合、填参数**——这与"数据即内容"的边界完全一致：内容作者只管往表里加行，不碰运行时代码。

### 1.3 面向用户

| 角色 | 典型诉求 |
|---|---|
| 数值策划 | 调技能伤害系数、属性成长曲线、物品预算、经验曲线，需要立刻看到结算结果，不想自己心算三段式聚合 |
| 系统策划 | 设计新机制对应的内容组合（新装备、新光环、新触发器），需要看到"这条数据会影响哪些既有内容" |
| 关卡策划 | 配掉落表、遭遇/波次/阶段、刷新点、区域触发，需要在地图上直接摆放坐标而不是心算 Vec2 |
| 文案/本地化 | 补齐/核对多语言文本，需要一张能看清"哪些 key 缺哪个语言"的矩阵，不想在几十个 JSON 文件里翻找 |
| 程序 | 升级框架版本后要跑迁移、跑全量校验，需要确认"编辑器里看到的红线 = 运行时/门禁会报的错" |
| 美术 | 核对外形映射（`display.map` 等）里引用的资源是否存在、纸娃娃层是否齐全，不想手动比对文件名 |

单机单用户使用场景：编辑器不做账号体系、不做多人实时协作，文件落地即 JSON（见 [data/README.md](../../data/README.md) 的信封与主键规则），协作方式是团队各自用编辑器改自己负责的表，再靠 git 提交、review、合并（见第 12 章"版本控制与协作"）。

### 1.4 典型用户故事

以下六个场景覆盖编辑器最核心的价值主张，后续各章的功能设计均以能完整走通这六个场景为验收基准。

**故事 1：数值策划改一条技能伤害并立刻看结算预览。**
数值策划打开"技能/状态/触发编辑器"，在技能列表里选中 `skill.sample_strike`，在效果卡片里把 `school_damage` 的 `coefficient` 从 `1.0` 改成 `1.2`；右侧"结算预览"面板已经选好了施法者模板 `creature.sample_hero` 与目标模板 `creature.sample_beast`，数值改动的瞬间（字段失焦或按 Enter）预览面板重新跑一次确定性模拟，命中表、护甲减免、最终伤害与期望 DPS 立即刷新，策划不需要保存、不需要打开游戏、不需要心算三段式聚合。

**故事 2：系统策划新增一件装备并自动生成外形/文本行。**
系统策划在"物品编辑器"点"新增物品"，向导依次选槽位（`item.slot_definition` 下拉）、品质（`item.quality_definition` 下拉）、物品等级、输入显示名；系统自动生成 `item.<name>` 形式的 id、`l10n.item.<name>.name` 文本键并写入默认语言正文、在 `display.map` 里创建一行外形占位（`display.<name>`，等待美术核对具体资源）；向导第三步进入属性分配，实时显示"预算消耗 / 预算上限"进度条；完成后自动跑一次字段级 + 表级校验，0 错误时向导关闭并把新记录带到检视区。

**故事 3：关卡策划配掉落表并模拟 1 万次。**
关卡策划在"掉落与爆率编辑器"给 `loot.sample_beast` 加一个 `weighted_pick_one` 分组，塞入三件候选物品，各自设权重；右侧"模拟面板"输入次数 10000、种子 `12345`，点"运行模拟"，几秒内输出每件物品的出现次数、实际概率（与权重归一化后的理论概率对比）、平均获得数量、按物品预算估算的期望价值，策划据此判断"稀有件出现频率是否符合设计目标"。

**故事 4：文案补齐缺失文本键。**
文案打开"本地化编辑器"，矩阵视图按"缺失单元格"排序，看到 `l10n.quest.deliver_letter.description` 在 `zh-CN` 有正文但 `en-US` 缺失（高亮黄色）；文案双击该单元格直接填入译文，保存后该行的缺失标记消失，问题面板里对应的一条"文本键存在"警告随之清除。

**故事 5：程序升级框架版本后跑迁移与全量校验。**
程序把工程的框架快照路径从 `dist/0.2.0/` 改指到 `dist/0.3.0/`，重新打开工程时状态栏提示"框架版本 0.3.0，检测到 2 张表 `schema_version` 落后"；程序在"校验、诊断与引用分析"面板点"执行迁移"，预览迁移前后字段差异（如新增字段的默认值）后确认执行，迁移完成后触发一次全量校验，报告 0 错误后程序提交这批因迁移产生的文件改动。

**故事 6：美术核对外形映射资源是否存在。**
美术打开"外形与表现编辑器"，筛选"资源缺失"，看到 `display.map.sample_new_monster` 一行的 `sprite_set_id` 在工程 `assets/` 目录下找不到对应文件，黄色感叹号标注；美术确认是资源还没导出，先在编辑器里记下待办，等 ComfyUI 出图与 `import_assets.py` 跑完后重新扫描，该行的黄标自动消失。

### 1.5 与现有工具链的关系（先给结论，细节见第 3 章）

编辑器不是另起一套数据规范或校验规则，而是仓库既有工具链（`data/README.md`、`toolchain/validate_data.py`、`toolchain/validator`、`toolchain/import_assets.py`）之上的图形化前端：数据文件组织、信封、主键规则、多根合并、字段级/引用级校验规则、外形映射生成方式，编辑器全部复用，不重复定义、不产生第二套语义。第 3 章"总体方案"给出编辑器如何在实现层面直接复用这些既有能力。

## 2. 术语与范围

### 2.1 术语表（详版见附录 E）

| 术语 | 含义 |
|---|---|
| 工程 | 编辑器打开的一个游戏数据编辑单元，对应某个 `<game>` 仓库的 `data/<game>/` 数据根 + 其锁定的框架快照 `dist/<version>/` |
| 工作区 | 工程在编辑器本地的偏好与状态存档（`<game>/.gfeditor/workspace.json`），非数据本身 |
| 数据根 | 一批同构织入的数据文件目录，编辑器按"多根合并"规则同时加载框架根（`data/_framework/`）与游戏根（`data/<game>/`），见 [04 第 4 节](../../architecture/04_数据与内容管线.md#4-dataregistry-接口) |
| 层（框架层/游戏层） | 数据根的归属：框架层数据（随 `dist/<version>/data/_framework/` 交付）默认只读，游戏层数据（`data/<game>/`）可编辑；框架层记录可通过"覆盖到游戏层"生成可编辑副本（见第 6.4 节） |
| 表 / 域 / 记录 / 字段 | 表 = 一个 `.json` 文件对应的一组同构记录；域 = 表名第一段（如 `skill`、`item`）；记录 = 表里的一行；字段 = 记录里的一个键值对 |
| 引用 | 某字段的值是另一条记录的 id，由 `FieldKind.Reference` 或 `DataRegistry.declareReference` 声明，编辑器据此做引用完整性检查与"跳转到目标记录" |
| 文本键 | `l10n.text` 表的 `key`，格式 `l10n.<来源域>.<来源记录name>.<字段名>`，由 `FieldKind.TextKey` 字段承载 |
| Expr | 全架构统一的条件/表达式语言，见 [04 第 6 节](../../architecture/04_数据与内容管线.md#6-expr-条件表达式语言) |
| 校验报告 | 一次校验（字段级/表级/全量）产出的问题列表，含错误与警告两级 |
| 变更集 | 编辑器一次会话内累积的未保存改动集合，是撤销栈与"保存哪些表"判断的基础 |
| 原语 | 效果类型、光环效果类型、职能标志位等运行时代码认识的固定词汇表条目，新增须走 ADR |
| 时间模型 | `found.time_model` 声明的连续（`continuous`，单位秒）或离散（`discrete`，单位回合）模式，决定编辑器里时间字段显示"秒"还是"回合" |

### 2.2 范围内

- 编辑 `data/<game>/` 下全部内容表的记录（增删改、克隆、重命名 id、跨层覆盖）。
- 与运行时完全一致的校验（复用 `DataRegistry` 与全部 `IValidationRule`）。
- 高频域的专项编辑体验（技能/物品/生物/掉落/经验/任务对话/世界遭遇/本地化/外形表现）。
- 脱离引擎的数值预览与确定性模拟（结算预览、掉落模拟、经验估算、简易战斗回放）。
- 批量编辑、查找替换、CSV 导入导出。
- 与 git 的只读感知（状态显示、diff 预览、提交前自动校验提示），不内置完整 git 客户端。
- 与游戏可执行文件/Unity 工程的联调（一键运行、保存触发热重载、日志反查）。

### 2.3 范围外（明确不做）

| 不做的事 | 原因 |
|---|---|
| 不编辑引擎场景资源本身（精灵图、模型、音频文件的二进制编辑） | 属于美术/引擎工具职责，编辑器只管理"逻辑 id → 资源引用"的映射行，资源本身由 `import_assets.py` 或引擎编辑器产出 |
| 不做代码编辑 | 编辑器编辑的是数据表，不是 C#/脚本源码；`script` 效果原语与 `found.hook` 钩子的具体实现在代码里，编辑器只填钩子 id |
| 不新增原语 | 见 1.2 节；新增效果类型/光环类型/职能标志位需过 ADR 并由程序实现 |
| 不做多人实时协作（无锁机制、无云端会话） | 单机单用户工具，协作靠 git，见第 12 章 |
| 不做在线服务（无账号、无云同步、无遥测上报） | 见第 15.4 节"安全"：编辑器不联网、不上传 |
| 不做完整的 git 客户端（不做分支管理、不做交互式 rebase） | 复杂 git 操作交给专业 git 工具，编辑器只做"内容改动"视角需要的最小 git 感知 |

## 3. 总体方案

### 3.1 架构图

```
                                +-----------------------------------+
                                |            编辑器壳（UI）           |
                                |  菜单/工具栏/命令面板/主题/DPI/布局   |
                                +-----------------+-------------------+
                                                  |
                                +-----------------v-------------------+
                                |            编辑核心                  |
                                |  工作区管理 / 文档模型 / 撤销栈       |
                                |  变更集 / 字段级即时校验调度          |
                                |  控件工厂（FieldKind → 控件）        |
                                +-----------------+-------------------+
                                                  |
              +-----------------------------------+-----------------------------------+
              |                                   |                                   |
+-------------v-------------+     +---------------v---------------+     +-------------v--------------+
|      框架核心库（DLL）      |     |         外部工具（子进程）        |     |        文件系统 / git       |
| DataRegistry（加载/查询/    |     | toolchain/validate_data.py     |     | data/<game>/**/*.json      |
|   校验/多根合并/迁移）       |     | toolchain/validator（.NET）    |     | .gfeditor/workspace.json   |
| TableSchema/FieldSchema     |     | toolchain/import_assets.py     |     | 本地 git 仓库（状态/diff）  |
| Expr 解析器                 |     | 游戏可执行文件 / Unity 工程     |     |                             |
| 全部 IValidationRule        |     |  (运行联调，第 13 章)           |     |                             |
| 桩适配层（数值沙盘用）       |     +---------------------------------+     +-----------------------------+
+------------------------------+
```

编辑器壳只负责界面呈现与交互；一切"表长什么样""这个字段该怎么校验""结算怎么算"的权威判断都下沉到框架核心库与外部工具，编辑器不重复实现。

### 3.2 数据流

```
打开工程
  → 探测数据根（框架快照 data/_framework/ + 游戏根 data/<game>/）
  → DataRegistry.loadAll(多根) —— 按主键合并、按 schema_version 检查、跑迁移
  → 内存记录集（DataRecord 集合，按表分组）
  → 用户编辑（网格/表单/源码三视图任一）
  → 字段级即时校验（编辑动作发生时，FieldKind 对应的单字段规则）
  → 保存（该记录所属表文件整份格式化写回：稳定字段顺序、2 空格缩进、LF、无 BOM）
  → 表级校验（该表全部记录的 IValidationRule）
  → （用户手动触发或提交前）全量校验 —— 等价 toolchain/validate_data.py 两道校验，可选 --strict
  → git（编辑器展示状态与 diff，用户在编辑器内或外部 git 工具提交）
```

### 3.3 核心技术主张（编辑器实现层面的选型建议，非架构结论）

> 本节标注的四点是"编辑器如何实现"层面的建议，供第 16 章"技术选型建议"进一步展开评估，不是架构文档的结论，不影响 `architecture/` 的任何既有拍板。

编辑器进程内**直接引用框架的六个核心类库**（`Core.Foundation` → `Core.Numbers` → `Core.Rules` → `Core.Carriers` → `Core.Gameplay` → `Presentation.Common`，由 `build.ps1` 编译出的 Release DLL，目标框架 `.NET Standard 2.1`）与桩适配层（`Adapters.Stub`，纯 .NET 实现），而不是自己重新描述表结构、重新实现校验、重新实现结算算法。这样做换来四个"零重复"：

1. **表结构零重复**：核心库的 `TableSchema`/`FieldSchema`（`core/foundation/data_registry/contracts/`）已经登记了每张表的字段名、`FieldKind`（`Bool`/`Int`/`Number`/`String`/`Id`/`IdList`/`Reference`/`TextKey`/`Expr`/`Enum`/`Vec2`/`Object`/`Array`，见 `FieldKind.cs`）、`Required`、`EnumValues`、`ReferenceTable`/`ReferenceDomain`、`Description`（见 `FieldSchema.cs`）、当前 `CurrentSchemaVersion` 与 `Migrations` 迁移链（见 `TableSchema.cs`）。编辑器读取这些声明**自动生成**网格列与表单控件（见第 6.2 节控件映射表），新表/新字段只要在核心库登记，编辑器零改动即可编辑——不需要为每张新表单独写一份 UI 代码。
2. **校验规则零重复**：编辑器直接调用 `DataRegistry.LoadAll`/`Validate`/`Reload` 与全部已注册的 `IValidationRule`，做到"编辑器里看到的红线 = 运行时/门禁会报的错"这一硬承诺；不存在"编辑器说没问题，但 `validate_data.py` 报错"的割裂体验。
3. **数值预览与模拟零重复**：确定性固定步长模拟（拍板决策 3）本身可以脱离引擎运行，编辑器借桩适配层（`Adapters.Stub`）跑结算管线（06 第 4.1 节）、掉落抽取（08 第 1 节）、经验曲线换算等"数值沙盘"（第 10 章），预览结果与游戏内真实运行结果保证一致，因为走的是同一份规则层代码。
4. **版本对齐**：编辑器随框架 `dist/<version>/` 同版本发布，或自身声明兼容的框架版本范围；打开工程时核对游戏工程 `Packages/manifest.json` 里 `file:` 锁定的框架快照版本，版本不匹配时提示但不阻断打开（只读模式下仍可查看）。

### 3.4 与既有工具链的复用关系一览

| 既有工具/文档 | 编辑器如何复用 |
|---|---|
| [data/README.md](../../data/README.md) | 文件组织（`data/<game>/<domain>/<table>.json`）、信封（`table`/`schema_version`/`rows`）、主键规则（内容表 `id`、登记表 `key`、`l10n.text` 复合键）、编码格式（UTF-8 无 BOM、2 空格、LF）全部照搬，保存动作严格产出符合此约定的文件 |
| `toolchain/validate_data.py` | 编辑器"手动全量校验"命令等价调用它的两道校验（骨架级 + `toolchain/validator`），支持传等价的 `--strict` |
| `toolchain/validator`（.NET） | 编辑器进程内直接引用同一套 `DataRegistry` + `IValidationRule` 实现（而非再拉起子进程），字段级/表级校验走同一套代码路径；全量校验可选择"进程内跑"或"拉起子进程跑，日志汇入输出面板"两种模式（后者用于跟门禁行为完全对齐地复核） |
| `toolchain/import_assets.py` | 编辑器"外形与表现编辑器"提供调用入口（见第 7.9 节），把出图产物生成 `display.map`/`display.equip_visual` 行，编辑器本身不重复实现资产扫描逻辑 |
| 04 第 4 节多根加载与合并规则 | 编辑器打开工程即按此规则加载框架根 + 游戏根，`override`/`final` 字段在记录操作里可视化呈现（见第 6.4 节） |
| 04 §4 `DataRegistry.reload(domain)` | 编辑器保存文件后，若联调面板检测到游戏侧以开发期构建运行，转发一次 reload 请求触发热重载（见第 13 章） |

## 4. 工程与工作区

### 4.1 新建/打开工程向导

编辑器首次启动或点"新建/打开工程"时弹出向导：

1. **选游戏仓库根**：文件选择器选中某个 `<game>` 仓库的根目录（例如用户本地的游戏仓库路径）。
2. **自动探测数据根**：编辑器在所选根目录下查找 `data/<game>/`（`<game>` 段名由该仓库自己决定，编辑器不关心具体拼写），探测到即列为"游戏层数据根";若找不到，提示用户手动指定路径或改为"仅浏览框架层"的只读模式。
3. **自动探测框架快照**：读取该仓库 Unity 工程 `Packages/manifest.json` 里 `com.gamefoundation.adapter.unity`/`com.gamefoundation.game-template` 的 `file:` 依赖路径，解析出所指向的 `dist/<version>/` 目录，从中读取 `dist/<version>/data/_framework/` 作为框架层数据根、读取内嵌的核心 DLL 供编辑器加载；若 `manifest.json` 不存在或依赖路径解析失败，弹出手动选择框架快照目录的对话框。
4. **显示框架版本与编辑器兼容性**：向导最后一步展示"检测到框架版本 `0.3.0`，本编辑器兼容 `0.2.x ~ 0.3.x`"一类结论；版本超出兼容范围时给出黄色警告但允许继续（只读优先，写操作前二次确认）。
5. 确认后进入主界面，状态栏立即显示工程名与框架版本（见第 5.7 节）。

### 4.2 最近工程

主界面欢迎页与"文件"菜单下列出最近打开的工程（路径 + 上次打开时间 + 框架版本），点击直接按 4.1 节流程重新加载；工程路径不存在时该项标灰并提示"未找到，是否移除记录"。

### 4.3 工程文件 `.gfeditor/workspace.json`

工程首次打开成功后，编辑器在游戏仓库 `<game>/.gfeditor/workspace.json` 写入/更新一份工作区文件，记录：

| 字段 | 说明 |
|---|---|
| `dataRoots` | 已探测/手动指定的数据根路径列表（框架层 + 游戏层） |
| `frameworkSnapshotPath` | 当前锁定的 `dist/<version>/` 路径 |
| `defaultLocale` | 默认语言，用于文本键校验与内联编辑默认显示语言 |
| `preferences` | 编辑器偏好（布局、主题、最近打开的标签页等，纯 UI 状态） |
| `lastValidationSummary` | 上次全量校验的时间与结果摘要，供打开工程时快速展示"距上次校验已过 N 天" |

**是否入库的建议（默认方案，可调整）**：`workspace.json` 里 `dataRoots`/`frameworkSnapshotPath`/`defaultLocale` 属于"团队共享的工程配置"，建议入库（多人打开工程时行为一致）；`preferences`（布局、最近标签等纯个人偏好）与自动保存草稿目录（见第 15.2 节 `.gfeditor/autosave/`）不建议入库，建议在游戏仓库 `.gitignore` 里为 `.gfeditor/autosave/` 与 `.gfeditor/*.local.json` 加忽略规则；编辑器首次写入 `workspace.json` 时如检测到仓库尚无对应 `.gitignore` 规则，弹出一次性提示询问是否代为写入。

## 6. 通用表编辑器（Schema 驱动）

通用表编辑器是编辑器的地基：任何一张登记在 `TableSchema` 里的表，不需要任何专项定制即可用它编辑；第 7 章的专项编辑器都是在通用表编辑器基础上叠加的"更好用的皮肤 + 专属校验/预览"，专项编辑器覆盖不到的表（第 7.10 节）直接落回通用表编辑器。

### 6.1 三视图同步

一条记录或一整张表在文档区可以三种视图打开，三者对同一份内存记录集读写，切换视图不丢失未保存的编辑，字段级校验状态三视图共享。

```
+----------------------------------------------------------------------------------+
| [网格视图] [表单视图] [源码视图]                              记录: skill.sample_burn |
+----------------------------------------------------------------------------------+
| 网格视图（整表）：                                                                  |
|  id 冻结列 | school | kind | range | cast_time | cost | ... （可排序/筛选/分组/隐藏列）|
|  多选后可批量改字段（见第11章）；行内编辑，Tab/Enter 移动焦点                          |
+----------------------------------------------------------------------------------+
| 表单视图（单条记录，按 schema 顺序分组）：                                            |
|  [基础] id / school / kind / range                                                |
|  [引用] target_shape_ref                                                          |
|  [数值] cast_time / cooldown_duration / cost                                       |
|  [表现] （该表若有 display 相关字段则归入本组）                                        |
|  [高级] tags / interrupt_flags / action_cost                                       |
|  必填字段星标(*)，字段旁 (?) 悬停显示 FieldSchema.Description                          |
+----------------------------------------------------------------------------------+
| 源码视图（该记录或整表 JSON，语法高亮）：                                             |
|  {                                                                                 |
|    "id": "skill.sample_burn",                                                     |
|    "school": "school.fire",                                                       |
|    ...                                                                            |
|  }                                                                                 |
|  保存时若 JSON 解析失败 → 进入"修复模式"（红色边框 + 错误行号提示），不覆盖磁盘文件      |
+----------------------------------------------------------------------------------+
```

- **网格视图**：列 = 字段，虚拟化渲染（保证 5 万行级表滚动流畅，见第 15.1 节性能指标）；冻结主键列（`id`/`key`）；支持列排序、按字段值筛选、按枚举字段分组折叠、隐藏/显示列（列头右键菜单）；行内编辑（双击进入编辑态，控件按第 6.2 节映射表渲染）；支持多选（`Shift`/`Ctrl` 点选，或框选）。
- **表单视图**：按 `TableSchema.Fields` 的登记顺序分组展示（基础/引用/数值/表现/高级五个语义分组，具体某字段归入哪组由字段命名与 `FieldKind` 启发式判断，见附录 B 控件映射表最后一列的"分组建议"；未来若核心库补充字段分组元数据，编辑器优先读取显式声明）；必填字段（`FieldSchema.Required == true`）显示红色星标；每个字段标签旁的 `(?)` 图标悬停显示 `FieldSchema.Description`。
- **源码视图**：可查看/编辑单条记录或整张表的原始 JSON，语法高亮（键名/字符串/数字/布尔各自配色）；保存时先做 JSON 语法解析，解析失败不覆盖磁盘文件、进入"修复模式"（编辑区红框 + 错误所在行号与列号提示），修复通过后才允许写盘。

### 6.2 字段类型 → 控件映射表

| `FieldKind` | 渲染控件 | 交互细节 |
|---|---|---|
| `Bool` | 开关（Toggle） | 点击切换，无需二次确认 |
| `Int` / `Number` | 数字输入框 | 支持步进按钮与拖拽微调；识别为"时间字段"（`cast_time`/`channel_time`/`cooldown_duration`/光环 `duration`/`interval`/`internal_cooldown` 等，见 04 第 3.1 节清单）时，输入框带单位后缀（"秒"或"回合"，取决于该记录所属作用域的 `found.time_model.mode`），离散模式下拒绝输入小数（失焦时四舍五入并提示"离散模式下时间字段必须为整数"） |
| `String` | 单行文本框 | 无格式限制的自由文本（如 `sprite_set_id` 一类资源引用字符串） |
| `Enum` | 下拉选择框 | 选项列表 = `FieldSchema.EnumValues`；不允许手输不在列表内的值 |
| `Id` | Id 输入框 | 自动补全 `domain` 前缀（按所属表的 domain 段，见 04 第 2.2 节）；实时按正则 `^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$` 校验格式；主键字段额外做同表唯一性检查，冲突时输入框标红并提示已存在的记录 |
| `IdList` | 标签编辑器（Chips） | 每个 id 显示为一个可删除的标签；输入区支持按域筛选的自动补全下拉 |
| `Reference` | 引用选择器 | 点击弹出搜索浮层，可搜索 `ReferenceTable`/`ReferenceDomain` 声明的目标表/域内记录，列表显示"显示名 + id + 缩略图"；`Ctrl+点击`已填值直接跳转到目标记录；悬停已填值显示目标记录的预览卡（名称/关键字段摘要）；目标缺失时输入框标红并提供"创建目标记录"按钮（跳转到对应新增流程，见第 8 章） |
| `TextKey` | 本地化内联编辑框 | 直接显示/编辑默认语言（`workspace.json.defaultLocale`）正文；首次填入非空文本时按规则 `l10n.<来源域>.<来源记录id去掉domain前缀>.<字段名>` 自动生成 key 并写入 `l10n.text`；其余已登记语言若该 key 缺失，框下方显示"缺失 N 种语言"提示，点击展开逐语言小输入框 |
| `Expr` | 表达式编辑器 | 语法高亮（关键字/分组名/字符串/数字/括号配色）；输入 `group.` 后弹出该分组下已知 `key` 的自动补全列表（九个分组：`self`/`target`/`event`/`world`/`quest`/`player`/`combat`/`enemies`/`time`，见 04 第 6.2 节）；括号自动匹配高亮；失焦时按 04 第 6.1 节 BNF 做实时解析，语法错误处标红下划线并在状态提示条给出错误位置；点分标识符若域名段与九个分组同名但未登记为 `group.key`，标黄"疑似引用拼写错误"警告（对应 04 第 5 节该项校验）；识别为合法内容 id 字面量的片段可点击跳转到目标记录 |
| `Vec2` | 双数字框（x/y） | 相邻两个数字框；若该记录所属专项编辑器提供地图画布（第 7.7 节），双数字框与画布上的点位联动：拖拽画布上的点等价于改这两个数字 |
| `Object` | 结构化子表单 / JSON 子编辑 | 若该字段结构已在模块登记（如技能 `effects`、掉落 `groups`、任务 `objectives`、对话 `nodes` 等，均在第 7 章专项编辑器中定制为卡片/子表格），渲染对应的定制子表单；未登记定制的 `Object` 字段退化为一段内嵌的 JSON 子编辑器（同源码视图的编辑体验，但只作用于该字段） |
| `Array` | 结构化子表格 / JSON 子编辑 | 同 `Object`，已登记的模块结构渲染为可增删排序的子表格（如效果列表卡片可拖拽排序），未登记的退化为 JSON 子编辑 |

### 6.3 记录操作

| 操作 | 用户怎么做 | 系统反馈 |
|---|---|---|
| 新增 | 网格视图工具栏"新增"按钮，或右键"在此表新增记录" | 生成新记录，主键按"表 domain 前缀 + 用户输入名字段"规则自动生成 id 建议值（可编辑），其余字段按 `FieldSchema` 声明的类型给出合理默认值（`Bool→false`、`Number→0`、`Enum→` 第一个枚举值等，模板可由专项编辑器覆盖为更贴合语义的默认值，见第 8 章新增内容向导）；新记录自动打开表单视图供继续填写 |
| 克隆 | 选中记录右键"克隆" | 弹出对话框要求输入新 id，默认建议 `<原id>_copy`；若原记录存在被同类结构引用的关联行（如物品的 `display_ref`），提供"级联克隆关联行"复选框（默认不勾选），勾选后连带克隆并重新绑定引用 |
| 删除 | 选中记录右键"删除"或按 `Delete` | 先弹出"影响分析"对话框（见第 9.3 节引用图）列出"哪些记录引用了本记录"，若存在引用则默认按钮为"取消"，需用户显式点击"仍然删除"二次确认；确认后记录从内存集移除并标记该表为脏 |
| 重命名 id | 选中记录右键"重命名 id" | 弹出对话框输入新 id，系统扫描全部表中的引用字段、`Expr` 中的 id 字面量、`l10n.text` 的 key 前缀，生成一份"改动清单"预览（哪些表哪些字段会被级联更新），用户确认后统一执行并标记全部受影响表为脏 |
| 移动到另一层 | 框架层只读记录右键"覆盖到游戏层" | 在游戏层数据根生成一份内容相同、带 `override: true` 的副本记录，覆盖诊断面板新增一条"该记录已被游戏层覆盖"的信息级提示（非错误）；若原框架层记录声明 `final: true`，菜单项显示为禁用并附锁形图标提示"该记录不可覆盖" |

### 6.4 撤销/重做

跨记录、跨表的**事务式撤销栈**：一次原子编辑（改一个字段值、执行一次批量替换、执行一次重命名 id 级联更新）作为一个撤销单元；`Ctrl+Z`/`Ctrl+Y` 在整个工程范围内撤销/重做，不限定在当前打开的标签；**保存动作不清空撤销栈**（保存只是把当前内存状态落盘，撤销栈仍保留保存前后的完整历史，允许"保存后又想撤销回保存前的状态"）。撤销栈上限为可配置的操作步数（默认 500 步，见第 14.1 节设置项），超出上限从最早的操作开始丢弃。

### 6.5 保存

- 按表文件写回：一次保存动作只重写该记录所属的表文件（`data/<game>/<domain>/<table>.json`），不触碰其它未改动的表文件。
- 稳定字段顺序：按 `TableSchema.Fields` 声明的顺序输出字段；核心库尚未登记但文件里已存在的未知字段，保留在已知字段之后、按原文件中的相对顺序追加，不丢弃。
- 格式：2 空格缩进、LF 行尾、UTF-8 无 BOM，与 [data/README.md](../../data/README.md) "编码与格式"一节要求一致，保证 git diff 最小（只有真正改动的字段产生 diff 行）。
- 外部修改检测：编辑器对已打开工程的数据根文件保持文件系统监视；若磁盘文件在编辑器外被修改（如另一进程的脚本改了 JSON，或 git 切换分支），弹出提示"检测到外部修改"，提供"重新加载（丢弃编辑器内改动）"与"对比差异后决定"两个选项，避免静默覆盖。

## 7. 专项编辑器

专项编辑器是通用表编辑器之上，针对高频域定制的更好用的界面：更贴合语义的布局、专属的可视化控件（画布、卡片、图表）、更聚焦的专属校验与预览。每个专项编辑器覆盖固定的一组表，不覆盖到的表仍可从导航区"按层/域/表"进入通用表编辑器直接编辑。

### 7.1 人物与生物编辑器

**目的**：编辑生物模板与其依赖的职业/种族/天赋/资源类型/属性/阵营定义，让策划一次看清"一只生物由哪些表拼成"。

**交互流程**：

1. 左侧列表选中一只生物，中央区域按上图分块展示；每块都是对通用表单视图的重新编排，字段控件仍按第 6.2 节映射表渲染，只是布局更贴合"策划心里怎么想一只生物"的顺序。
2. 属性面板的"等级 1..N 成长预览"：读取 `stat_growth_ref` 指向的成长曲线（与 `prog.level_curve` 同类结构）与 `tier` 对应的分档倍率，逐级算出 `base_stats` 之外每级的最终属性值，渲染为表格 + 折线图；纯预览，不产生任何写盘副作用。

4. AI 绑定、掉落绑定两处的下拉本质是 `Reference` 控件；"打开"按钮跳转到对应记录（AI 优先级表落回通用表编辑器，掉落表跳到 7.4 节掉落编辑器）。
5. **职业编辑（`arch.class`）**：主属性引用（`Reference` 到 `stat.definition`）、资源类型引用（`Reference` 到 `arch.power_type`，可多选）、技能书（`Reference` 到 `skill.book`）、天赋树引用（`Reference` 到 `arch.talent_tree`）四个字段按同样的分块表单呈现；点击天赋树引用旁"打开"进入下方的天赋树画布。
6. **天赋树画布**：节点（每个节点 = 一条天赋，绑定一个被动光环或 `override_skill`/`spell_mod` 效果，见 06 第 3.5、5 节）以卡片形式摆放在画布上，前置关系画连线；拖拽节点改变位置（纯展示布局，不影响数据语义）；拖拽节点边缘到另一节点建立/删除前置连线；系统在每次连线改动后运行成环检测（DFS 沿前置边遍历），检测到环时该连线显示红色警示线并在问题面板报"循环引用检测"错误，阻止保存。
7. **反应矩阵（`fac.reaction_matrix`）**：二维网格呈现，行/列均为 `fac.faction` 记录，单元格是枚举下拉（敌对/中立/友好）；对角线单元格（阵营对自身）灰化不可编辑，恒为"友好"。

**专属校验/预览**：属性成长预览、天赋树成环检测（对应 04 第 5 节"循环引用检测"）、反应矩阵对称性提示（若 A 对 B 是敌对但 B 对 A 未设为敌对，出信息级提示，不阻断，因为设计上允许单向敌意）。

6. **触发器编辑**（`skill.proc_def`）：`trigger_event` 下拉数据源来自 `found.event_catalog`（框架层只读登记表）；`condition` 是 `Expr` 编辑器；`proc_chance` 数字框限定 `0~1`；`internal_cooldown` 按时间模型显示单位。
7. **施法修正**（`skill.spell_mod_def`）：`targetDimension`（枚举下拉：`cast_time`/`cost`/`cooldown`/`crit_chance`/`effect_value`/`charges`）、`op`（`flat`/`pct`）、`value`、`affects`（技能过滤器：按学派/标签/具体技能 id 三种过滤方式的组合表单）。
8. **右侧结算预览**：下拉选施法者模板与目标模板（数据源为 `creature.template`），点"运行结算预览"调用桩适配层跑一次确定性结算（06 第 4.1 节固定管线：判定 → 基础值 → 暴击 → 施法者乘区 → 减免 → 目标乘区 → 免疫吸收 → 落地 → 后置），分步展示每一步的中间值与最终伤害/治疗量，并给出"期望 DPS"（若 `cast_time` > 0，按读条时间折算）。字段改动后预览自动标记为"已过期"（半透明 + "结果可能已过期，重新运行"提示），不做静默自动重算（避免频繁改字段时预览抖动）。

**专属校验/预览**：效果数上限进度提示、叠加类别冲突高亮、结算预览分步展示。

4. 遭遇/关卡以下方标签页承载（非画布内容，因为遭遇定义本身不含坐标语义，`units` 里的 `position` 字段除外——该字段可选中后跳转画布定位）：`units` 列表（引用 `spawn.table` 条目或直接内联 `creature.template` + 坐标，二选一见 08 第 8 节）、`waves`（触发条件 `Expr` + 生成引用列表）、`phases`（`enterCondition` Expr + `aiRotationOverride` 映射表 + `onEnterHook`）、`victory_condition`/`defeat_condition`（均为 `Expr` 编辑器）、`combat_mode_override`/`initiative_override`（离散/连续覆盖，仅在需要偏离场景默认时序时填写）。
5. **关卡**（`encounter.level`）：`mapRef` 引用选择器、`encounterSequence` 为可排序的有序引用列表、`entryDifficultyOptions` 为 `diff.tier` 多选。

**专属校验/预览**：地图画布上的坐标合法性直观核对（点位是否落在地图边界内，若地图有边界声明）、遭遇阶段切换的 `aiRotationOverride` 引用完整性。

### 7.8 本地化编辑器

**目的**：以矩阵视图集中管理全部语言的文本，让文案一眼看清缺口。

**覆盖的表**：`l10n.text`、`l10n.locale`。

**界面布局线框**：

```
+----------------------------------------------------------------------------------------+
| 筛选：来源域[skill▾] 缺失[✓] 孤儿[ ]              [导出CSV] [导入CSV]                     |
+----------------------------------------------------------------------------------------+
| key                              | zh-CN(默认)      | en-US            | ja-JP           |
+-----------------------------------+------------------+------------------+-----------------+
| l10n.skill.sample_burn.name      | 灼烧              | Burn             | ⚠ 缺失(双击填入) |
| l10n.item.sample_blade.name      | 铁剑              | Iron Blade       | 鉄の剣           |
| l10n.quest.deliver_letter.title  | 护送商队           | ⚠ 缺失(双击填入)  | 護送商隊         |
+-----------------------------------+------------------+------------------+-----------------+
| 占位符一致性: l10n.item.sample_blade.desc 中 {level} 在 en-US 缺失该占位符  [跳转]         |
+----------------------------------------------------------------------------------------+
```

**交互流程**：

1. 矩阵：行 = `key`（按来源域可折叠分组），列 = `l10n.locale` 中登记的各语言；单元格显示该语言正文，缺失单元格黄色背景 + `⚠` 标记。
2. 双击缺失单元格直接进入行内编辑，输入译文回车保存，保存后该单元格黄标消失，问题面板对应"文本键存在"警告随之清除。
3. 筛选栏：按来源域（key 前缀第二段）筛选、"仅显示有缺失的行"开关、"孤儿 key"开关（不被任何记录字段引用到的 key，见 04 第 5 节"孤儿记录检测"思想在文本键上的应用）。
4. **CSV/表格导入导出**：导出时选定语言列与来源域范围，产出便于外包翻译的 CSV（列头 = key + 各语言列）；导入时先弹出预览表格标出"新增行/覆盖行/无变化行"三类差异，用户确认后写入，不静默覆盖已有译文。
5. **占位符 `{var}` 一致性检查**：对同一 key 的多语言正文提取 `{xxx}` 占位符集合，若某语言缺少默认语言存在的占位符（或多出未知占位符），在矩阵下方问题条列出，点击跳转定位单元格。

**专属校验/预览**：缺失矩阵高亮、孤儿 key 提示、占位符一致性检查。

### 7.9 外形与表现编辑器

**目的**：管理逻辑 id 到外形资源的映射，核对资源是否真实存在，串联 `import_assets.py` 出图产物。

**覆盖的表**：`display.map`、`display.anim_set`、`display.equip_visual`、`display.weapon_style`、`vfx.def`、`sfx.def`、`feedback.binding`、`feedback.floating_text_style`、`camera_profile`、`ui_layout_definition`、`shell_menu_definition`。

**界面布局线框**：

```
+----------------------------------------------------------------------------------------+
| 外形映射列表(左,筛选:资源缺失/category) |  中央：kind切换表单                | 右：预览      |
+------------------------------------------+---------------------------------------+---------------+
| ▸ display.map.sample_beast               | kind: (●)sprite ( )model              | [缩略图]       |
| ⚠ display.map.sample_new_monster         | ── sprite 组 (灰化: model 组) ──       | icon_id 预览   |
|                                            | sprite_set_id:[sprite.creature.wolf_.]| sfx 试听按钮   |
|                                            | direction_count:[8▾]                  |               |
|                                            | mirror_pairs:[+]  anchor_points:[+]    |               |
|                                            | paperdoll_layers:[+]                  |               |
|                                            | icon_id:[icon.creature.wolf_grey]      |               |
|                                            +---------------------------------------+               |
|                                            | 反查: 该逻辑id还没有display行 → [一键补建N条]           |
|                                            | [调用 import_assets.py] 输出日志:...  |
+------------------------------------------+---------------------------------------+---------------+
```

**交互流程**：

1. 列表按 `category`（`skill`|`aura`|`item`|`creature`|`gobj`|`projectile`）与"资源缺失"筛选；缺失（工程 `assets/` 目录下找不到 `sprite_set_id`/`icon_id`/`model_ref` 等对应文件）的行前缀黄色感叹号。
2. `kind` 单选切换 `sprite`/`model` 两组专属字段（07 表现层 7.1 节字段表），未选中的一组整体灰化只读，对应 04 第 5 节"外形类型字段组完整"校验项在此以界面禁用的方式提前预防，而不是等保存后报错。
3. **资源引用存在性检查**：编辑器在打开工程时扫描一次工程 `assets/` 目录建立文件名索引，每个引用字段（`sprite_set_id`/`icon_id`/`model_ref`/`sfx_id` 等）失焦时对照索引查找，找不到则该字段标黄，右侧检视区预览面板显示"资源缺失"占位图。
4. 预览：精灵/图标类字段显示缩略图（读取匹配到的实际图片文件）；`sfx_id` 提供"试听"按钮（本地播放对应音频文件，无音频输出设备时按钮置灰并提示）。
5. **"外形映射存在"反查**（对应 04 第 5 节同名校验项）：扫描全部表中标记为需要外形映射的逻辑 id 集合（技能/光环/物品/生物/物件），列出"还没有 `display.map` 行"的清单，提供"一键补建"批量生成占位行（`kind` 留待用户选择，其余字段留空）。
6. **调用 `import_assets.py`**：面板提供"选择出图产物目录"按钮，点击后作为子进程调用 `toolchain/import_assets.py`，标准输出/错误实时汇入本面板下方日志区（同时也汇入主界面"输出"面板，见第 5.6 节），执行完成后自动刷新一次资源存在性索引与相关 `display.map`/`display.equip_visual` 记录（对应 ADR-0014"外形表行由工具生成而非手填"）。
7. 其余表（`display.anim_set`/`display.equip_visual`/`display.weapon_style`/`vfx.def`/`sfx.def`/`feedback.binding`/`feedback.floating_text_style`/`camera_profile`/`ui_layout_definition`/`shell_menu_definition`）在本编辑器内以标签页形式提供紧凑表单，字段渲染沿用第 6.2 节映射表，不单独定制画布。

**专属校验/预览**：资源存在性检查、外形映射存在反查、外形类型字段组完整的界面级预防、`import_assets.py` 调用与日志。

| 新对话 | ①选类型（gossip 菜单或剧情树）②gossip：添加选项与动作／剧情树：在画布上添加节点与分支③（可选）挂接演出钩子（`found.hook` 引用）④文本 | `l10n.text`（对话文本）；（若涉及演出）登记引用 `found.hook`（不新建钩子本身，钩子的代码实现属于程序职责） | 引用完整性（动作指向的技能/任务/传送点存在）、表达式可解析（显隐条件）、文本键存在、循环引用检测（对话树分支） |
| 新成就 | ①基础字段（名称）②添加达成条件（六种 `Criterion.type` 任选，`observeEvent` 下拉自 `found.event_catalog`）③（可选）奖励④外形（图标）⑤文本 | （可选）`display.map` 一行（成就图标）；`l10n.text`（名称键） | 引用完整性（观察事件已登记）、文本键存在 |

每类向导的最后一步统一执行"字段级 + 表级"校验（不做全量校验，避免向导响应变慢），0 错误时向导关闭；有错误时向导停留并列出问题供当场修正，用户也可选择"忽略并稍后处理"关闭向导（问题会保留在问题面板）。

## 9. 校验、诊断与引用分析

### 9.1 三个校验时机

| 时机 | 触发条件 | 范围 | 反馈方式 |
|---|---|---|---|
| 编辑即字段级 | 字段失焦、下拉选择变更、卡片参数改动 | 仅该字段（格式、枚举、引用格式、Expr 语法等不依赖同表其它记录的检查） | 字段旁即时标红/标黄下划线，悬停显示错误文本 |
| 保存即表级 | 保存该表文件时 | 该表全部记录的 `IValidationRule`（预算超标、叠加类别冲突、效果数上限等需要跨记录/跨表核对的规则） | 问题面板增量刷新该表相关问题；保存本身不因表级警告而失败，但表级错误会在问题面板高亮且状态栏错误数增加 |
| 手动/提交前全量 | 用户点"校验"菜单"全量校验"，或提交前钩子触发 | 全部已加载数据根，等价 `toolchain/validate_data.py` 两道校验，可选 `--strict`（警告也阻断） | 弹出/刷新完整校验报告，问题面板全量重建，状态栏错误/警告数刷新为全量结果 |

### 9.2 问题面板设计

问题面板（第 5.6 节底部面板区）列表每行结构：`[级别图标] 所属表.记录id: 检查项名称 — 说明文本 [跳转]`；支持按"所属表"/"问题类型"（对应 04 第 5 节 14 项检查项名称）/"来源"（字段级/表级/全量）三维筛选与组合排序；双击任意一行跳转到对应记录的对应字段并高亮闪烁一次。

### 9.3 覆盖诊断

多根合并产生的 `override: true`/`final: true` 行为（见 04 第 4 节 2026-09-06 修订）不是错误，而是一类**信息级诊断**，单独列在问题面板的"覆盖诊断"分类下：

- 某记录被后层 `override: true` 覆盖：显示"框架层原始版本 vs 游戏层覆盖版本"的并排字段差异对比。
- 某记录声明 `final: true` 且被后层尝试覆盖：显示为阻断错误（04 定义为仍判定阻断），提示"该记录禁止被覆盖，请改用其它 id 新增而非覆盖同名记录"。
- 单根场景（该表本次未跨根合并）出现 `override`/`final` 字段为真值：显示为警告"该字段仅在跨根同主键重叠时生效，当前单根场景下已被忽略"，对应 04 第 4 节该行为定义。

### 9.4 引用图（引用了谁 / 被谁引用）

- 检视区"引用面板"（第 5.5 节）对当前选中记录展示两个列表：**引用了谁**（本记录全部 `Reference`/`Id`（识别为引用字面量）/`Expr` 中 id 字面量指向的目标，逐条可点击跳转）与**被谁引用**（反向索引，扫描全部已加载记录中指向本记录的引用字段，逐条可点击跳转）。
- **删除影响分析对话框**（第 6.3 节"删除"操作触发）：复用同一份反向索引，列出"被谁引用"的完整清单，按所属表分组，用户可展开查看具体字段路径。
- **孤儿视图**：本地化编辑器（7.8）与通用表编辑器筛选行（"孤儿"复选框，第 5.3 节）共用同一份反向索引数据源，展示"没有被任何已知入口引用"的记录（对应 04 第 5 节"孤儿记录检测"，警告级，不阻断，便于清理）。

### 9.5 schema 迁移

打开工程时若检测到某表记录的 `schema_version` 低于核心库 `TableSchema.CurrentSchemaVersion`，状态栏与问题面板同时提示"N 张表待迁移"；用户在"校验"菜单点"执行迁移"，弹出预览对话框逐表展示迁移前后的字段差异（新增字段的默认值、被拆分/合并的字段），确认后按 `TableSchema.Migrations` 声明的迁移链顺序执行（04 第 3 节"迁移链只增不减"），执行完成后记录的 `schema_version` 写为当前版本、`migrated_from` 记为原始版本号，随后自动触发一次全量校验确认迁移未引入新问题。

## 10. 数值沙盘（预览与模拟）

数值沙盘全部基于框架核心库 + 桩适配层（`Adapters.Stub`）运行，不依赖引擎、不依赖网络；种子可复现（同种子同输入必然同输出，对应确定性拍板决策 3），是编辑器区别于"纯表格编辑工具"的核心差异化能力。沙盘以独立标签页形式在文档区打开（"工具"菜单"数值沙盘"或各专项编辑器内的快捷入口）。

|---|---|---|---|

| 经验估算 | 等级曲线、经验来源假设 | 达到目标等级所需击杀数/时长估算 | 见第 7.5 节 |
| 生物属性成长 | 生物模板、成长曲线、tier 分档倍率 | 等级 1..N 属性表格与折线图 | 见第 7.1 节 |
| 简易战斗回放（可选） | 两个生物模板、时长（N 秒或 N 回合）、种子 | 战斗日志（逐条 Combat Log 风格事件文本）与胜率统计（多次重复跑取胜率，若跑多次） | 06 第 8 节事件词汇表、结算管线 |

## 12. 版本控制与协作

### 12.1 git 状态显示

底部面板区"git 变更"子面板（第 5.6 节）列出当前工程数据根内相对 git `HEAD` 的文件级改动（新增/修改/删除三色图标），实时随保存动作刷新；状态栏（第 5.7 节）显示当前分支名与脏文件计数。

### 12.2 变更文件列表与 diff 预览

点击"git 变更"面板中的任一文件，右侧弹出并排 diff 预览（旧内容 | 新内容，逐行高亮增删），diff 渲染基于文本行比较（因为保存动作保证稳定字段顺序，diff 天然聚焦在真正改动的字段行，见第 6.5 节）；面板提供"暂存该文件"/"撤销该文件改动（还原为 `HEAD` 版本）"两个操作，其余 git 操作（提交、拉取、推送、分支管理）引导用户使用外部专业 git 工具或命令行完成，编辑器不重复实现完整 git 客户端（第 2.3 节范围外声明）。

### 12.3 提交前自动校验

对应仓库既有 `.githooks/pre-commit` 的快速门禁思想：编辑器"校验"菜单提供"提交前检查"命令，一键跑一次全量校验（等价 `validate_data.py` 两道校验）并汇总结果；若配置了自动模式（第 14.1 节设置项），编辑器检测到用户即将通过其内置的"暂存"操作提交时会先自动跑一次该检查，报错时弹出确认框"仍有 N 个错误，是否继续提交"，默认按钮为"取消"。

### 12.4 冲突时的记录级合并辅助

当 git 报告某数据表文件存在合并冲突（例如 pull 时与远端改动冲突）时，编辑器提供"记录级合并"辅助视图：读取冲突文件的双方版本（`--ours`/`--theirs`，经外部 git 命令获取原始文本），按主键对比出"仅本地改""仅远端改""双方都改"三类记录，双方都改的记录并排展示字段级差异，用户逐条选择"用本地"/"用远端"/"手动编辑合并"，全部记录确认后拼装出合并结果并写回文件，供用户在 git 里标记该文件为已解决冲突；此辅助视图不自动执行 git 命令本身（`add`/`commit` 等），只负责生成正确的合并后文件内容。

## 13. 运行联调

### 13.1 配置游戏可执行文件/Unity 工程路径

"运行"菜单"配置联调目标"：选择该游戏的 Unity 工程路径（用于一键在编辑器内启动 Unity 编辑器打开该工程）或独立版可执行文件路径（用于一键启动打包后的游戏）；两者均可配置，互不冲突（开发阶段常用 Unity 工程内运行，验收阶段用独立版可执行文件运行）。

### 13.2 一键运行

"运行"菜单"运行▶"（或工具栏按钮）按已配置的目标启动：若目标是 Unity 工程，拉起本机 Unity Editor 以命令行参数打开该工程并进入 Play 模式（需要该工程已同步过最新的 `data/<game>/`，编辑器保存动作已保证这一点）；若目标是独立版可执行文件，直接启动该进程；启动日志汇入"输出"面板。

### 13.3 保存触发热重载

保存动作完成后，若联调面板检测到目标游戏进程正以**开发期构建**运行（编辑器与目标进程之间通过本地约定的开发期热重载通道通信，具体传输机制留给实现阶段按 [04 §4](../../architecture/04_数据与内容管线.md#4-dataregistry-接口) `DataRegistry.reload(domain)` 与落地计划"数据加载"一节"编辑器内构建监听 JSON 文件变化触发重载并发 `data.load_completed`"的既有设计落地，默认方案，可调整），编辑器发出一次针对该表所属 domain 的 reload 请求；成功回执后"输出"面板打印"已触发 `<domain>` 热重载"。

**前提与限制（必须在界面上明确提示，避免用户误判"为什么没生效"）**：

- 仅对开发期构建有效，发布构建默认关闭热重载通道（对应落地计划"编辑器内构建...仅限编辑器内构建"）。
- 结构性改动（新增字段、改变字段类型、`schema_version` 提升）仍需要重启游戏进程才能生效，热重载只对"同结构下的数值/内容变化"生效；编辑器保存后若判断本次改动可能涉及结构变化（如触发了迁移），主动提示"本次改动建议重启联调目标"而不是尝试热重载。

### 13.4 从游戏日志反查编辑器记录

联调运行时，编辑器订阅目标进程输出的日志流（若目标提供，默认约定读取标准输出/标准错误或指定日志文件路径，具体接入方式属实现细节）；日志文本中出现符合 id 格式（`^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$`）的片段时，"输出"面板对该片段做超链接高亮，点击直接在编辑器内跳转打开对应记录，便于"游戏里报了个奇怪的 `skill.xxx` 找不到"这类问题的快速定位。

### 14.1 设置项清单

| 设置项 | 默认值 | 说明 |
|---|---|---|
| 主题 | 跟随系统 | 浅色/深色/跟随系统 |
| 默认语言（`defaultLocale`） | 首次打开工程时按检测到的系统语言建议，可改 | 决定 `TextKey` 内联编辑默认显示的语言列 |

| 提交前自动校验 | 开启 | 见第 12.3 节 |

### 14.2 插件机制

编辑器提供四类扩展点，供后续按需扩展而不改动编辑器核心：

| 扩展点 | 用途 | 约束 |
|---|---|---|
| 专项编辑器插件 | 为某张/某组表提供更定制的界面（类似第 7 章九个专项编辑器的编写方式） | 必须通过核心库 `DataRegistry` 读写记录，不允许绕过其校验直接操作文件 |
| 字段控件插件 | 为特定 `FieldKind` 或特定字段（按表名+字段名匹配）提供自定义控件渲染 | 控件只做展示与编辑交互，字段值的读写仍经统一的记录模型 API |
| 沙盘插件 | 新增一种数值预览/模拟面板（第 10 章之外的自定义沙盘） | 必须使用桩适配层跑逻辑，不允许沙盘内直接读写磁盘数据文件 |
| 导入器插件 | 新增一种批量导入格式（CSV 之外，如 Excel、专有格式） | 导入结果必须经过与手工编辑相同的字段级/表级校验，不允许跳过校验直接写盘 |

插件目录：`<编辑器安装目录>/plugins/<插件名>/`，每个插件是独立目录，含清单文件（声明插件类型、兼容的编辑器版本范围、入口）与实现文件；编辑器启动时扫描该目录加载。**不允许绕过核心库校验**是插件机制的硬约束（对应第 1.2 节"编辑器只编辑内容，不新增原语"的产品定位，插件也不例外）。

### 14.3 schema 变化自动适配的原则

核心库新增一张表或给已有表新增字段时，编辑器不需要跟着改代码即可继续工作：新表自动出现在导航区"按层/域/表"树中（归入通用表编辑器）；已有表新增字段自动出现在表单视图的对应分组末尾与网格视图的新增列（默认显示，用户可手动隐藏）。只有当某张表需要**专属**的可视化（画布、卡片、图表）时才需要更新对应专项编辑器或走插件机制补一个专项编辑器插件；这是"零改动可编辑新表"（第 3.3 节主张 1）与"专项体验需要额外投入"之间的边界。

## 15. 非功能需求

### 15.1 性能指标

| 场景 | 目标 |
|---|---|
| 冷启动到主界面可交互 | ≤ 3 秒（不含首次打开工程的数据加载） |
| 打开工程（框架层+游戏层两根合并加载） | 中等规模数据集（约 60 张表、单表数千行以内）≤ 5 秒 |
| 5 万行 `l10n.text` 网格滚动 | 虚拟化渲染，滚动帧率不低于 30fps，无明显掉帧卡顿 |
| 保存单张表（数千行内） | ≤ 1 秒 |
| 全量校验（中等规模数据集） | ≤ 10 秒（进程内跑；拉子进程跑对齐 `validate_data.py` 实际耗时，不额外设上限） |

### 15.2 可靠性

**崩溃恢复**：编辑器按第 14.1 节设置的间隔（默认 120 秒）自动把当前未保存的变更集快照写入 `<game>/.gfeditor/autosave/`（不覆盖用户的正式保存文件）；异常退出后再次启动时检测到该目录存在快照，提示"检测到上次异常退出遗留的自动保存草稿，是否恢复"，用户可选择恢复、丢弃或先对比差异；正常退出（用户主动关闭且已无未保存改动，或已确认放弃改动）时清空该次会话对应的草稿文件。

### 15.3 可用性

- 键盘优先：全部高频操作有快捷键（见附录 A），网格视图/表单视图之间的字段导航支持 `Tab`/`Shift+Tab`/方向键。
- 无鼠标可完成主要流程：新增记录、填字段、保存、触发校验、切换标签均可纯键盘完成（命令面板 `Ctrl+K` 是无鼠标操作的核心入口）。
- 屏幕阅读器基本支持：控件具备可读的名称/角色/值（Name/Role/Value）语义标注，满足基本的辅助技术识别需求（不要求达到完整无障碍认证等级，作为基础可用性底线）。

### 15.4 兼容性

- 操作系统：Windows 10/11 x64。
- 分辨率：1080p 至 4K，含 125%/150%/200% 等常见 DPI 缩放档位（见第 5.8 节）。
- 最小窗口尺寸 `1280×800`（见第 5.8 节）。

### 15.5 安全

编辑器**不联网、不上传**任何数据（不含遥测、不含自动检查更新的默认开启项——若未来加入检查更新功能，须默认关闭并需用户显式开启）；全部数据读写限定在用户显式打开的工程目录、`.gfeditor/` 子目录与用户显式指定的导入导出路径内。

## 16. 技术选型建议

> 本章标注为**实现层面的建议，非架构结论**，可在实现立项时另出评估文档拍板，不影响 `architecture/` 目录下任何既有结论。

### 16.1 桌面壳：WPF 与 Avalonia 对比

| 维度 | WPF（.NET 8） | Avalonia（.NET 8） |
|---|---|---|
| 平台范围 | 仅 Windows | 跨平台（本产品只需 Windows，此项非决定因素） |
| 与核心 DLL（.NET Standard 2.1）互操作 | 原生，无额外适配层 | 原生，无额外适配层 |
| 生态成熟度（数据网格、代码高亮控件） | 成熟（第三方控件库选择多，社区历史悠久） | 逐步成熟（部分控件需自行封装或用较新的第三方库） |
| 主题/深浅色支持 | 需要自行搭建资源字典体系 | 内置 Fluent 主题与浅深色切换支持较完善 |
| 团队现有经验（假设） | Windows 桌面团队通常更熟悉 | 需要一定学习曲线 |
| **建议** | **首选**（默认方案，可调整）：本产品明确只需 Windows，WPF 生态里的数据网格/代码编辑控件选型更直接，减少自研控件的工作量 | 若未来有跨平台需求（当前无）可重新评估 |

### 16.2 理由与备选（Web 壳 + 本地服务）对比

| 维度 | 桌面壳（WPF/Avalonia）直接引用核心 DLL | Web 壳（本地 HTTP 服务 + 浏览器/内嵌 WebView 前端） |
|---|---|---|
| 与核心库集成方式 | 进程内直接引用，无序列化开销 | 核心库跑在本地服务进程，前端通过 HTTP/WebSocket 调用，需要额外设计 API 协议与序列化 |
| 启动性能 | 更快（无需起服务进程 + 浏览器渲染进程） | 较慢（两个进程 + WebView 启动开销） |
| 离线可靠性（第 15.5 节"不联网"要求下的自洽性） | 天然离线，无端口占用/防火墙提示等困扰 | 本地服务仍可能触发系统防火墙首次提示，用户体验有干扰 |
| UI 生态（图表、代码高亮控件） | 需要选型桌面端专属控件库 | 可直接复用成熟的 Web 前端生态（图表库、代码编辑器组件更丰富） |
| **结论** | **选桌面壳**：第 15.5 节离线要求与启动性能优先级更高，UI 生态差距可通过桌面端成熟的第三方控件库弥补 | 仅在未来若需要"团队远程协作查看只读快照"一类场景时才重新评估 Web 壳路线 |

### 16.3 图表、代码编辑控件、文件监视、git 调用方式（默认方案，可调整）

| 能力 | 建议方案 |
|---|---|
| 图表（成长曲线、经验曲线、结算预览条形图） | 桌面端成熟图表库（如 OxyPlot 一类开源图表库），满足折线/柱状/进度条即可，不需要复杂交互式图表 |
| 代码/JSON 高亮编辑控件（源码视图、Expr 编辑器） | 桌面端成熟的代码编辑控件（如 AvalonEdit 一类），自行扩展语法高亮规则以支持 Expr 语法与 JSON |
| 文件监视（外部修改检测、资源存在性扫描） | 操作系统原生文件系统监视 API（.NET `FileSystemWatcher` 一类），叠加去抖动处理避免同一次外部改动触发多次刷新 |
| git 调用方式 | 拉起本机已安装的 `git` 命令行工具（子进程），解析其文本输出得到状态/diff；不内嵌完整 git 实现库，保持与用户本机 git 配置（凭据、hooks）行为一致 |

### 16.4 与 `toolchain/validator` 共享注册逻辑的方式

`toolchain/validator`（.NET）的 `Program.cs` 并不自己枚举各层的表与规则，而是直接调用核心库已经存在的级联注册目录：`core/rules/assembly/RulesSchemaCatalog`（注册 L0 内置 + L1 五模块 + L2 四模块的 `TableSchema`/`IValidationRule`）→ `core/carriers/assembly/CarriersSchemaCatalog`（级联 `RulesSchemaCatalog` 后再补 L3）→ `core/gameplay/assembly/GameplaySchemaCatalog`（级联后再补 L4）→ `presentation/assembly/PresentationSchemaCatalog`（级联后再补 L5）；`toolchain/validator/Program.cs` 实际调用的正是最外层的 `PresentationSchemaCatalog.RegisterAll`，一次性注册齐全部 L0～L5 模块。编辑器建议直接引用与 `toolchain/validator` 相同的注册入口——`core/rules/assembly/RulesSchemaCatalog` 等各层 assembly 注册目录（编辑器按需覆盖到哪一层，就引用哪一层级联到底的目录，通常是最外层的 `PresentationSchemaCatalog`）——从而保证"编辑器已知的表清单与校验规则"与"门禁用的校验器已知的表清单与校验规则"永远是同一份代码产出的同一份注册结果，不需要人工保持两处同步。若后续把 `toolchain/validator` `Program.cs` 里"调用汇总注册入口 + 设置 `FailOnUnknownTable`/`Strictness` 等选项"这一小段本身也抽成一个核心库内、专供 `toolchain/validator` 与编辑器两个消费方共用的更薄的汇总入口更佳（默认方案，可调整：是否需要再抽这一层、抽到哪个程序集，留待实现阶段与 `toolchain/validator` 的实际代码结构对齐决定），本节结论不影响 `architecture/` 的任何既有拍板。

## 17. 里程碑与验收标准

验收统一使用仓库自带的 `data/_sample/` 作为验收数据集（框架仓库自测用示例数据，不代表任何真实游戏内容，见 `data/README.md`）；每条验收条目要求"用编辑器完成动作后，跑 `python toolchain/validate_data.py` 或编辑器内等价的全量校验，得到预期结果"，保证验收标准是可机器判定的，不是主观描述。

| 里程碑 | 范围 | 验收条目（示例） |
|---|---|---|
| M1 | 工程与工作区（第 4 章）+ 通用表编辑器（第 6 章）+ 校验（第 9 章前两个时机） | 1. 打开 `data/_sample` 工程成功加载全部表且行数与源文件一致；2. 用编辑器新增一条 `stat.definition` 记录并保存，`validate_data.py --data-root data/_sample` 结果为 0 错误；3. 手工改坏一个 `Reference` 字段指向不存在的 id，字段级校验能在不保存的情况下即时标红 |
| M2 | 技能/物品/生物/掉落/经验五个专项编辑器（第 7.1～7.5 节） | 1. 用"物品编辑器"新增物品向导新增一件装备（含外形与文本自动生成），保存后全量校验 0 错误；2. 用"掉落与爆率编辑器"对 `loot.sample_beast` 跑 10000 次模拟并得到与权重归一化理论概率误差在合理统计范围内的结果；3. 用"技能/状态/触发编辑器"改 `skill.sample_strike` 的 `coefficient` 后结算预览面板数值随之变化 |
| M3 | 新增内容向导（第 8 章）+ 引用分析（第 9.4 节）+ 批量与导入导出（第 11 章）+ 本地化编辑器（第 7.8 节） | 1. 走完"新任务"向导后自动挂接的 `dialog.gossip_menu` 动作项存在且引用完整性校验通过；2. 删除一条被引用的记录时能弹出正确的影响分析清单；3. 本地化编辑器导出 CSV 后再导入同一份文件（未改动）得到"无变化"计数等于总行数 |
| M4 | 数值沙盘（第 10 章）+ 任务/对话画布、世界/遭遇画布（第 7.6、7.7 节）+ 热重载（第 13.3 节） | 1. 战斗回放沙盘对同一对模板、同一种子跑两次得到完全一致的战斗日志；2. 剧情树画布能正确检出人为造出的一个环并阻止保存；3. 联调面板检测到开发期构建运行时，保存一条技能数值改动后游戏侧在数秒内可观察到新数值生效（不需重启进程） |
| M5 | 插件机制（第 14.2 节）+ 打磨 + 性能（第 15.1 节） | 1. 按插件清单接口实现一个最小示例字段控件插件，编辑器能正确加载并渲染；2. 5 万行 `l10n.text` 网格滚动帧率不低于 30fps 的性能指标现场实测通过；3. 全部第 15 章非功能需求逐项现场核对通过 |
