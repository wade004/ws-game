## 1. 概述

### 1.1 目的

本文档定义 **GF 内容编辑器**（下文简称"编辑器"）的产品方案：它是什么、给谁用、解决什么问题、由哪几层构成、界面长什么样、每个功能怎么操作、系统怎么反馈。文档面向数值策划、系统策划、关卡策划、文案/本地化、程序、美术六类读者，作为后续实现立项、UI 详细设计、开发排期的唯一依据。本文档不涉及具体实现技术栈的最终拍板（第 9 章"技术选型建议"明确标注为实现层面的建议，不是架构结论），也不新增任何架构原语（技能效果类型、光环效果类型、职能标志位等的新增仍走 [12_扩展与变更流程.md](../../architecture/12_扩展与变更流程.md) 的 ADR 审批）。

### 1.2 定位

**GF 内容编辑器**（Game Foundation Editor，简称 GF 编辑器；命名来自框架包名前缀 `com.gamefoundation`）用来编辑基于本框架（`architecture/` 文档集）立项的任意一款 `<game>` 的**全部内容数据**：人物与生物、职业与天赋、属性、技能、光环、触发器、施法修正、物品（含新增装备）、套装、词缀、槽位与品质定义、掉落与爆率、经验与等级曲线、任务、对话（菜单与剧情树）、遭遇与关卡、刷新表、区域触发、难度档位、成就、货币与商人、阵营与反应矩阵、目标选择链、AI 行为外壳与优先级表、外形映射与动画集与装备外观、特效与音效定义、飘字/镜头/界面布局/外壳菜单等表现层配置、本地化文本——全部是 [04_数据与内容管线.md](../../architecture/04_数据与内容管线.md) 第 1.1 节总索引里登记的**60 余张结构化数据表**里的行，编辑器就是编辑这些表的通用工具。

**一句话说清定位（三层结构，本文档主线，详见第 3 章）**：编辑器不是随框架发布的单一产品，而是拆成三层各自独立演进的东西——**ws-game（框架）只保证"编辑器需要的契约与交付物"，不承载编辑器代码**；**编辑器项目是一个独立仓库、独立语义化版本的消费方**，产出编辑器基础套件（类库）与编辑器模板（最小可运行工程），按版本号锁定框架版本；**每款游戏的编辑器实例放在该游戏自己的仓库**（复制编辑器模板改名），随游戏版本发布。这是用户 2026-09-09 的拍板："一个游戏一个编辑器，编辑器跟随具体游戏走，不跟随框架走"，对应提议中的 [ADR-0018](../../architecture/adr/0018-编辑器随游戏走与框架为此提供的交付物.md)：ws-game 提供无头适配层与校验装配入口等契约面，编辑器项目消费这些契约面产出通用能力，游戏项目只写游戏专属薄层。

理论基础是 ADR-0004 拍下的"数据即内容"：游戏世界一切具体内容都是结构化文本表里的行，运行时只认 id 与字段，不认具体内容。这句话反过来定义了编辑器的能力边界：

> **编辑器 = 对所有表的通用编辑能力 + 对高频域的专项编辑器 + 与运行时完全一致的校验 + 数值预览/模拟。**

编辑器**只编辑内容，不新增原语**：新增一种效果类型（如给 `skill.def.effects` 加一种新的原语）、新增一种光环效果类型、新增一种职能标志位，都属于"改变运行时代码能理解的词汇表"，必须先过 ADR 审批并由程序落地代码，编辑器本身不提供"发明新原语"的入口；编辑器能做的是**列出已经登记的原语供策划选择、组合、填参数**——这与"数据即内容"的边界完全一致：内容作者只管往表里加行，不碰运行时代码。

### 1.3 面向用户

| 角色 | 典型诉求 |
|---|---|
| 数值策划 | 调技能伤害系数、属性成长曲线、物品预算、经验曲线，需要立刻看到结算结果，不想自己心算三段式聚合 |
| 系统策划 | 设计新机制对应的内容组合（新装备、新光环、新触发器），需要看到"这条数据会影响哪些既有内容" |
| 关卡策划 | 配掉落表、遭遇/波次/阶段、刷新点、区域触发，需要在地图上直接摆放坐标而不是心算 Vec2 |
| 文案/本地化 | 补齐/核对多语言文本，需要一张能看清"哪些 key 缺哪个语言"的矩阵，不想在几十个 JSON 文件里翻找 |
| 程序 | 升级框架版本或编辑器项目版本后要跑迁移、跑全量校验，需要确认"编辑器里看到的红线 = 运行时/门禁会报的错" |
| 美术 | 核对外形映射（`display.map` 等）里引用的资源是否存在、纸娃娃层是否齐全，不想手动比对文件名 |

单机单用户使用场景：编辑器不做账号体系、不做多人实时协作，文件落地即 JSON（见 [data/README.md](../../data/README.md) 的信封与主键规则），协作方式是团队各自用编辑器改自己负责的表，再靠 git 提交、review、合并（见第 5.10 节"版本控制与协作"）。

### 1.4 典型用户故事

以下六个场景覆盖编辑器最核心的价值主张，后续各章的功能设计均以能完整走通这六个场景为验收基准。

**故事 1：数值策划改一条技能伤害并立刻看结算预览。**
数值策划打开"技能/状态/触发编辑器"，在技能列表里选中 `skill.sample_strike`，在效果卡片里把 `school_damage` 的 `coefficient` 从 `1.0` 改成 `1.2`；右侧"结算预览"面板已经选好了施法者模板 `creature.sample_hero` 与目标模板 `creature.sample_beast`，数值改动的瞬间（字段失焦或按 Enter）预览面板重新跑一次确定性模拟，命中表、护甲减免、最终伤害与期望 DPS 立即刷新，策划不需要保存、不需要打开游戏、不需要心算三段式聚合。

**故事 2：系统策划新增一件装备并自动生成外形/文本行。**
系统策划在"物品编辑器"点"新增物品"，向导依次选槽位（`item.slot_definition` 下拉）、品质（`item.quality_definition` 下拉）、物品等级、输入显示名；系统自动生成 `item.<name>` 形式的 id、`l10n.item.<name>.name` 文本键并写入默认语言正文、在 `display.map` 里创建一行外形占位（`display.<name>`，等待美术核对具体资源）；向导第三步进入属性分配，实时显示"预算消耗 / 预算上限"进度条；完成后自动跑一次字段级 + 表级校验，0 错误时向导关闭并把新记录带到检视区。

**故事 3：关卡策划配掉落表并模拟 1 万次。**
关卡策划在"掉落与爆率编辑器"给 `loot.sample_beast` 加一个 `weighted_pick_one` 分组，塞入三件候选物品，各自设权重；右侧"模拟面板"输入次数 10000、种子 `12345`，点"运行模拟"，几秒内输出每件物品的出现次数、实际概率（与权重归一化后的理论概率对比）、平均获得数量、按物品预算估算的期望价值，策划据此判断"稀有件出现频率是否符合设计目标"。

**故事 4：文案补齐缺失文本键。**
文案打开"本地化编辑器"，矩阵视图按"缺失单元格"排序，看到 `l10n.quest.deliver_letter.description` 在 `zh-CN` 有正文但 `en-US` 缺失（高亮黄色）；文案双击该单元格直接填入译文，保存后该行的缺失标记消失，问题面板里对应的一条"文本键存在"警告随之清除。

**故事 5：程序升级框架版本后同步升级编辑器项目版本，跑迁移与全量校验。**
程序在游戏仓库根跑 `toolchain/get_framework.ps1 -Version 1.13.0 -Target packages`（或私服通道 `-FromRegistry`）把框架从 `1.12.0` 升级到 `1.13.0`，`ws-game.lock` 随之更新（见第 3.3 节"版本与兼容矩阵"）；程序确认编辑器项目已发布的兼容矩阵（第 6.6 节）覆盖框架 `1.13.0`（同 MAJOR 段内即视为兼容），按第 7.2 节"锁定版本"把 `<game>/editor/` 里编辑器实例锁定的编辑器项目版本同步升级到对应的新版本；重新打开编辑器时读取新的 `ws-game.lock` 与编辑器项目版本锁定记录，因框架 MAJOR 段未变（均为 `1`）判定兼容，仅在状态栏与问题面板提示"框架版本 `1.12.0 → 1.13.0`（MINOR 升级），检测到 2 张表 `schema_version` 落后，建议查阅框架 `CHANGELOG.md` 对应区间的"编辑器相关契约"标注条目"；程序在"校验、诊断与引用分析"面板点"执行迁移"，编辑器先展示该版本区间 `CHANGELOG.md` 条目中标注的迁移说明摘要（若有），再预览迁移前后字段差异（如新增字段的默认值），确认执行后触发一次全量校验，报告 0 错误后程序提交这批因迁移产生的文件改动，并按第 7.6 节"升级流程"记录本次升级。若框架升级跨越 MAJOR 段（例如 `1.x` → `2.0.0`），编辑器直接拒绝打开工程并提示"框架 MAJOR 版本超出当前编辑器项目版本的兼容矩阵，请先升级编辑器项目版本"，不进入迁移流程（见第 3.3 节"版本与兼容矩阵"、第 5.2.1 节向导第 4 步）。

**故事 6：美术核对外形映射资源是否存在。**
美术打开"外形与表现编辑器"，筛选"资源缺失"；黄标数据源不是编辑器自建的目录扫描，而是编辑器调用 `toolchain/import_assets.py check --dataset <game>`（验收数据集场景下为 `--dataset _sample`，见第 10 章）子进程解析回来的问题清单——看到 `display.map.sample_new_monster` 一行的 `sprite_set_id` 被 `check` 判定为对应目录缺失，黄色感叹号标注；美术确认是资源还没导出，先在编辑器里记下待办，等 ComfyUI 出图、`import_assets.py sprite` 一类子命令跑完写入精灵资源与 `display.map` 行后，在编辑器里点"重新扫描"（本质是再跑一次 `import_assets.py check`），该行的黄标自动消失。

### 1.5 与现有工具链的关系（先给结论，细节见第 4、5 章）

编辑器不是另起一套数据规范或校验规则，而是仓库既有工具链（`data/README.md`、`toolchain/validate_data.py`、`toolchain/validator`、`toolchain/import_assets.py`）之上的图形化前端：数据文件组织、信封、主键规则、多根合并、字段级/引用级校验规则、外形映射生成方式，编辑器全部复用，不重复定义、不产生第二套语义。第 4 章给出 ws-game（框架）一侧为此固定承诺的契约面，第 5.1 节给出编辑器基础套件如何在实现层面直接复用这些既有能力。

### 2.2 范围内

- 编辑 `data/<game>/` 下全部内容表的记录（增删改、克隆、重命名 id、跨层覆盖）。
- 与运行时完全一致的校验（复用 `DataRegistry` 与全部 `IValidationRule`，经第 4.4 节"校验装配入口"）。
- 高频域的专项编辑体验（技能/物品/生物/掉落/经验/任务对话/世界遭遇/本地化/外形表现）。
- 脱离引擎的数值预览与确定性模拟（结算预览、掉落模拟、经验估算、简易战斗回放），经第 4.3 节"无头适配层"。
- 批量编辑、查找替换、CSV 导入导出。
- 与 git 的只读感知（状态显示、diff 预览、提交前自动校验提示），不内置完整 git 客户端。
- 与游戏可执行文件/Unity 工程的联调（一键运行、保存触发热重载、日志反查）。
- 游戏侧通过五类扩展点（第 6.1 节）接入游戏专属能力，不改动基础套件源码。

### 2.3 范围外（明确不做）

| 不做的事 | 原因 |
|---|---|
| 不编辑引擎场景资源本身（精灵图、模型、音频文件的二进制编辑） | 属于美术/引擎工具职责，编辑器只管理"逻辑 id → 资源引用"的映射行，资源本身由 `import_assets.py` 或引擎编辑器产出 |
| 不做代码编辑 | 编辑器编辑的是数据表，不是 C#/脚本源码；`script` 效果原语与 `found.hook` 钩子的具体实现在代码里，编辑器只填钩子 id |
| 不新增原语 | 见 1.2 节；新增效果类型/光环类型/职能标志位需过 ADR 并由程序实现 |
| 不做多人实时协作（无锁机制、无云端会话） | 单机单用户工具，协作靠 git，见第 5.10 节 |
| 不做在线服务（无账号、无云同步、无遥测上报） | 见第 8.5 节"安全"：编辑器不联网、不上传 |
| 不做完整的 git 客户端（不做分支管理、不做交互式 rebase） | 复杂 git 操作交给专业 git 工具，编辑器只做"内容改动"视角需要的最小 git 感知 |
| **框架仓库不承载编辑器代码**（新增，v2） | 用户拍板"编辑器跟游戏走，不跟框架走"；ws-game 只提供第 4 章列出的契约与交付物，编辑器基础套件、模板、每款游戏的编辑器实例均不进本仓库，见第 3 章 |

## 3. 三层结构与职责划分

本章是全文档的主线：编辑器不是一个随框架发布的单一产品，而是三层各自独立演进、依赖方向单向的消费方结构。第 4～7 章分别展开每一层的具体交付物与操作步骤，本章先给出整体骨架。

### 3.1 三层定义与依赖方向图

1. **ws-game（框架，本仓库）**：不承载编辑器代码，只保证"编辑器需要的契约与交付物"（第 4 章）。框架仓库是被依赖方，任何消费方不进入框架仓库（[落地方案与分阶段计划.md](../../architecture/落地计划/落地方案与分阶段计划.md) 第 3.5 节既有原则），编辑器不是这条原则的例外。
2. **编辑器项目（独立仓库，独立语义化版本）**：产出编辑器基础套件（类库，第 5 章）与编辑器模板（最小可运行工程，第 6.4 节）。按版本号经既有通道（`toolchain/get_framework.ps1` zip 通道或私服通道）锁定框架版本，只引用框架的发布产物，不引用框架源码；兼容性按框架 MAJOR 段声明（第 3.3 节）。
3. **每个游戏项目**：复制编辑器模板到 `<game>/editor/` 改名 `Editor.<Game>`，与该游戏的工程共用同一份 `ws-game.lock`（因此编辑器实例与游戏运行时使用的框架版本由构造保证一致），另锁定编辑器项目的版本；随游戏版本发布（第 7 章）。游戏专属的编辑面板、校验规则接入、沙盘预设、配置均只放在这一层。

依赖方向单向，用 ASCII 图表示（本图为新增的依赖方向图，不计入第 5.3.1 节起的 UI 线框图统计）：

```
+---------------------------+
|   游戏项目 <game>          |
|   <game>/editor/           |
|   (Editor.<Game>)          |
|   - 游戏专属插件/配置       |
|   - 复制自编辑器模板        |
+-------------+---------------+
              | 依赖（锁定编辑器项目版本 + 共用 ws-game.lock）
              v
+---------------------------+
|   编辑器项目（独立仓库）     |
|   - 基础套件（类库）        |
|   - 编辑器模板              |
|   - 五类扩展点契约          |
+-------------+---------------+
              | 依赖（按版本号锁定框架，经 zip/私服通道）
              v
+---------------------------+
|   ws-game（框架，本仓库）   |
|   - 契约面（第 4.1 节）     |
|   - 无头适配层、校验装配入口 |
|   - 不含任何编辑器代码       |
+---------------------------+
```

依赖只能从上到下：框架不知道编辑器项目的存在，编辑器项目不知道任何具体游戏的存在，游戏项目可以看见并消费编辑器项目与框架的发布产物。这与框架对"游戏"的既有消费方模型完全同构（新游戏 = 引擎适配层 + 薄游戏层 + 数据）。

### 3.2 职责表

| 层 | 放在哪 | 内容 | 版本 | 依赖 |
|---|---|---|---|---|
| ws-game（框架） | 本仓库 | 核心类库六个程序集、Unity 适配层、`toolchain`、无头适配层（`Adapters.Stub`）、校验装配入口、`TableSchema`/`FieldSchema`（含 [ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md) 子结构）、Expr 解析器、`DataRegistry` | 框架语义化版本（当前 1.12.0），随 `build.ps1 -Release` 发布 | 无（被依赖方） |
| 编辑器项目 | 独立仓库 | 基础套件（类库，第 5 章通用能力全部）、编辑器模板（第 6.4 节）、五类扩展点契约（第 6.1 节） | 编辑器项目自己的语义化版本，随编辑器项目自己的发布流程发布 | 按版本号锁定框架发布产物（zip 或私服通道），不引用框架源码 |
| 游戏项目 | 该游戏自己的仓库 `<game>/editor/` | 编辑器实例（复制编辑器模板改名 `Editor.<Game>`）、`editor.config.json`、游戏专属插件（校验规则接入、专属表单、专属向导、沙盘预设、品牌） | 随该游戏自己的版本发布（编辑器实例不单独发版） | 共用游戏工程的 `ws-game.lock`（框架版本）+ 另锁定编辑器项目版本 |

### 3.3 版本与兼容矩阵

- **框架 MAJOR.MINOR ↔ 编辑器项目版本**：编辑器项目声明"兼容框架 MAJOR = N 的全部版本"（与 v1.1 旧版"编辑器兼容框架 MAJOR 相同的全部版本"同一口径，只是主体从"编辑器"换成"编辑器项目"）；编辑器项目每次发布在自己的变更记录里注明所测试过的框架 MINOR 区间（第 6.6 节"兼容矩阵测试"要求至少覆盖当前框架 MAJOR 内两个 MINOR）。框架 MAJOR 升级（如 1.x → 2.0.0）视为破坏编辑器项目所依赖的契约面，编辑器项目需要发布对应的新 MAJOR 版本才能兼容，二者 MAJOR 段不要求数值相等，只要求编辑器项目自己的兼容声明表里能查到对应框架 MAJOR 的支持记录。
- **编辑器项目版本 ↔ 游戏**：游戏在 `<game>/editor/` 的锁定记录（第 7.2 节）里写死一个具体的编辑器项目版本号（如 `1.3.0`），与该游戏当前锁定的框架版本号（`ws-game.lock` 的 `version` 字段）相互独立，但编辑器实例首次打开工程时校验两者是否落在编辑器项目声明的兼容矩阵内，不在矩阵内则拒绝打开并提示"当前锁定的编辑器项目版本 `X.Y.Z` 未声明兼容框架版本 `A.B.C`，请升级编辑器项目版本或降级/升级框架版本"。
- **两个锁文件**：游戏仓库根 `ws-game.lock`（框架版本，与游戏工程共用，不属于编辑器专有）与 `<game>/editor/editor.lock`（编辑器项目版本 + 来源通道，格式与 `ws-game.lock` 同构：`version`/`source.channel`/`source.git_commit` 或注册表来源字段，见第 7.2 节）。两者都入库，团队打开工程时行为一致。
- **升级顺序**（对应用户故事 5）：先升级框架版本（`ws-game.lock` 更新）→ 核对编辑器项目已发布版本的兼容矩阵是否覆盖新框架版本 → 升级 `editor.lock` 锁定的编辑器项目版本 → 打开编辑器实例执行迁移与全量校验（第 5.7.5 节）。三步顺序不能颠倒：若先升编辑器项目版本、框架版本未跟上，编辑器实例可能读到自己不认识的新字段（表现为"未知字段保留但不渲染定制控件"，不阻断，但体验降级）。

### 3.4 三方工作项清单

三层各自的工作项，按"先做哪些能解锁后续"排列，供实现立项时拆分任务与排期参考。

**ws-game（框架）六项**：

1. **复合字段子结构 schema 登记**（前置，最大工作量）：按 [ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md) 首批范围（`skill.def.effects` 19 种原语、`skill.aura_def.effects` 10 种、`skill.proc_def`/`skill.spell_mod_def` 复合字段、`loot.table.groups`、`quest.def` 目标与奖励、`dialog.*` 节点与动作、`encounter.def` 单位/波次/阶段、`spawn.table` 条目、`area.trigger_def.params`、`gobj.lock.requirement`、`display.map`/`display.anim_set` 复合字段）给 `FieldSchema` 补 `fields`/`item`/`variants` 子结构登记，登记与校验同源（第 4.2 节）。

## 4. ws-game 侧：编辑器依赖的契约与交付物

本章是 ws-game（框架）一侧对编辑器项目的全部承诺；**框架对编辑器只承诺契约，不承诺实现**（[ADR-0018](../../architecture/adr/0018-编辑器随游戏走与框架为此提供的交付物.md) 决策 4）——编辑器项目消费的是下列固定的契约面，框架内部如何实现这些契约面允许自由演进，只要契约签名不破坏兼容。

### 4.1 契约面清单

编辑器依赖的框架面固定为以下七项，逐项变更在 `CHANGELOG.md` 里单独标注"编辑器相关契约"（第 4.7 节），破坏兼容时框架升 MAJOR：

| 契约面 | 现状（`core/foundation/data_registry/contracts/`） | 对编辑器的意义 |
|---|---|---|
| `TableSchema`/`FieldSchema`（含 [ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md) 子结构、[ADR-0021](../../architecture/adr/0021-字段登记表纳入数值范围约束.md) 数值范围、[ADR-0022](../../architecture/adr/0022-登记表补充导航与编辑元数据.md) 归属/分组/时间/IdList 引用元数据、[ADR-0024](../../architecture/adr/0024-字段登记表纳入动态键映射形态.md) 动态键映射、消费方反馈第 28/29 条 IdList/Id 固定取值登记与软引用元数据） | `FieldSchema` 字段为 `Name`/`Kind`/`Required`/`EnumValues`/`ReferenceTable`/`ReferenceDomain`/`Description`/`Range`/`Group`/`Unit`/`FreeIds`/`Map`/`AllowedValues`/`SoftReferenceTable`/`SoftReferenceDomain`（见 `FieldSchema.cs`）；`TableSchema` 含 `PrimaryKey`/`CurrentSchemaVersion`/`Fields`/`Migrations`/`IsRegistryTable`/`HasLocaleCompositeKey`/`Layer`/`Module`/`Domain`/`TimeScope` | 编辑器读取这些声明自动生成网格列与表单控件（第 5.4.2 节控件映射表），子结构登记补齐后 `Object`/`Array` 字段也能自动生成卡片表单（第 4.2 节）；**字段范围可从 schema 导出用于输入校验**——`Number`/`Int` 字段登记的 `Range`（下界/上界、含端点选择）随 `toolchain/validator --list-tables --json` 每张表的 `field_ranges` 一并导出（`presentation/assembly/SchemaFieldRangeExport`），编辑器可据此在数值输入控件上直接做范围校验，不必等到一次完整加载校验才发现越界；**表归属/字段分组/时间单位/IdList 引用目标同样可从 schema 导出**——每张表条目新增 `layer`/`module`/`domain`/`time_scope`，每个顶层字段新增 `field_meta`（`group`/`unit`/`reference_table`/`reference_domain`/`free_ids`），分别驱动第 5.3.3 节导航树、第 5.4.1 节表单分组、第 5.4.2 节 `IdList` 自动补全；**动态键映射同样可从 schema 导出**——已登记 `Map`（键为动态、值种类固定的复合字段，如一份属性表 `{属性id: 数值}`）的顶层字段，`field_meta` 新增 `map_key`（`reference_table`/`reference_domain`/`free_keys` 三选一，键约束）/`map_value`（值种类），编辑器可据此为这类字段提供键补全（按键约束枚举候选）与值输入校验，不必再退化为 JSON 子编辑（第 5.4.2 节 `Object`/`Array` 控件行）；**IdList/Id 固定取值与软引用同样可从 schema 导出**（消费方反馈第 28/29 条）——`field_meta` 新增 `allowed_values`（已登记 `AllowedValues` 的字段，有序固定取值数组，供渲染下拉/多选而非自由文本，如 `creature.template.npc_flags` 六个 `npc_flag.<name>` 固定项）与 `soft_reference_table`/`soft_reference_domain`（已登记软引用的字段，仅供自动补全/跳转，编辑器不得据此做存在性强校验——软引用不参与加载期引用完整性检查） |
| schema 迁移链 | `TableSchema.Migrations`（`IReadOnlyList<TableMigration>`），`TableMigration.FromVersion`/`ToVersion`/`Migrate` | 编辑器"执行迁移"（第 5.7.5 节）按迁移链顺序执行，链中若缺少衔接某个历史版本的环节，加载期报 `schema_version` 错误 |
| `DataRegistry` 的加载/校验/重载接口 | `LoadAll`/`RegisterSchema`/`Reload(domain)`/`GetAll`/`GetOverrideDiagnostics` 等（`core/foundation/data_registry/`）；消费方反馈第三批第 20 条新增 `TryGetAll`/`TryQuery`（`IDataRegistryView` 带默认实现，`DataRegistry` 显式覆盖）：**仅供编辑器等内容工具使用**，阻断态（数据未通过校验）下也返回当前已合并的记录视图，供作者在校验未通过时仍能定位/修复问题；编辑器运行期正常读取仍须用 `GetAll`/`Query`，阻断态即禁止读取的既有结论不变。第三批第 22 条起 `OverrideDiagnostic` 新增 `OverridingRootIndex`/`OverriddenRootIndex`（覆盖行/被覆盖行所在数据根在 `loadAll` 传入的根列表里的下标）与 `OverridingRelativePath`/`OverriddenRelativePath`（相对各自数据根的路径，`IDataSource` 未提供 `Root` 时退化为绝对路径），绝对路径字段（`OverridingLocation`/`OverriddenLocation`）保留；编辑器"覆盖清单"展示（第 5.7.4 节风格的覆盖诊断面板）应优先用"根序号 + 相对路径"，比完整绝对路径更适合跨机器截图核对。第四批第 25 条起，`Query(string, string)` 便捷重载解析谓词文本时用到的 `RecordExprSchema.For(TableSchema)` 不再把 `FieldKind.Expr` 字段注册为 `self.<field>` 引用——该字段种类的值是待求值的表达式文本，不是可直接比较的标量数据，此前误按 `String` 注册；谓词文本引用到 `Expr` 字段名时按 ADR-0015 默认规则整体解析为 `<id_literal>`，不抛异常（与 `IdList`/`Vec2`/`Object`/`Array` 四种本就不登记的字段种类同等对待）。第四批第 26 条起，`RecordExprMapping`/`RecordExprMapping.ToExprValueKind(FieldKind)`（字段种类 → Expr 标量类型的映射函数，`self.<field>` 注册即由它驱动）由框架内部实现放宽为 `public static`，纯可见性放宽、不改变任何映射结果 | 编辑器进程内直接引用同一套接口做加载、多根合并、字段级/表级校验、保存后热重载转发；阻断态下的"仍能浏览已加载内容定位问题"是编辑器诊断面板的常规场景（数据校验失败时用户第一反应通常是"哪些表还能看、坏在哪"），第 20 条之前编辑器只能捕获 `GetAll` 抛出的异常后自行拼一份降级视图，现在直接调用配套的 `TryGetAll`/`TryQuery`；`RecordExprMapping.ToExprValueKind` 放宽为公开后，编辑器可直接复用同一份"字段种类 → Expr 标量类型"映射规则（如字段级联动提示、Expr 编辑器里判断某字段是否可能是谓词可比较字段），不必依赖 `RecordExprSchema.For` 的输出间接推断 |
| Expr 解析器 | `core/foundation/expr/`，九个宿主分组（`self`/`target`/`event`/`world`/`quest`/`player`/`combat`/`enemies`/`time`）；`ExprParser.Parse(string, IExprSchema)` 解析为 AST，`ExprLexer.Tokenize(string)` 词法切分为只读 `IReadOnlyList<ExprToken>`（[ADR-0020](../../architecture/adr/0020-表达式词法器纳入公开契约.md) 新增契约面，`ExprToken` 含 `Kind`/`Start`/`Length`/`Text`）；消费方反馈第三批第 19 条起，`ExprNode`（及各子类）与 `ExprValidator` 产出的 `ExprIssue` 同样携带 `Start`/`Length`（`ExprParser.Parse` 产出的节点带精确区间，手写节点默认区间未知，`-1`/`0`）；第 18 条起 `IExprSchema` 新增 `KnownKeys(group)`/`KnownGroups`（带默认实现，恒返回空集合；`ExprSchema` 显式覆盖为按分组枚举全部已登记 key/全部已登记分组，有序、确定性） | 编辑器 Expr 编辑器（第 5.4.2 节）语法高亮、自动补全、失焦解析全部调用同一份解析器/词法器，不自己实现一套 BNF 或词法规则——语法高亮按 `ExprLexer.Tokenize` 返回的 token 种类与 `Start`/`Length` 区间着色，不得自行正则切词；`ExprValidator` 问题项的 `Start`/`Length` 供编辑器把"未登记的引用""参数类型不匹配"等问题精确高亮到源文本对应片段，不必自己重新做字符串匹配去猜测问题出在哪一段；`KnownKeys`/`KnownGroups` 供编辑器 Expr 编辑器自动补全下拉列表按分组枚举候选项，不必先枚举全部已登记签名再自行按分组过滤 |
| 校验装配入口 | 现状不存在（`toolchain/validator/Program.cs` 内联调用 `PresentationSchemaCatalog.RegisterAll` + 手工设置 `FailOnUnknownTable`/`Strictness`），第 4.4 节要求新增为核心库公开入口 | `toolchain/validator` 与编辑器基础套件调用同一个入口，避免"编辑器全绿但门禁报错"（04 第 5.1 节）的割裂 |
| 无头适配层 | 现状 `Adapters.Stub` 明确"专供测试与 CI，不对外发布"，不在分发包与三个私服包里，第 4.3 节要求转正；消费方反馈"结算中间步骤经真实施法路径不可观测"（编辑器第 31 条）起，`CombatOptions` 新增可选回调 `ResolveTrace: Action<EffectContext, ResolveResult>?`——结算管线（06 第 4.1 节）每次真实返回前（含判定即终止的短路分支）都会带上本次 `EffectContext` 与完整 `ResolveResult`（含各步骤中间值 `Steps`）调用一次，未设置时零开销、不改变既有行为 | 编辑器数值沙盘（第 5.8 章）借它跑确定性结算/掉落抽取/经验换算，不依赖引擎、不依赖网络；`ResolveTrace` 供第 5.5.2 节"结算预览"直接订阅真实结算管线拿到分步明细，不必自行重复实现/复刻一份九步计算逻辑，预览结果与真实施法路径保证逐步一致 |
| `toolchain` 命令行工具 | `validate_data.py`/`import_assets.py`/`get_framework.ps1` 等 | 编辑器把这些工具作为子进程调用（校验、资源检查、框架版本拉取），不重新实现同等逻辑 |

### 4.2 复合字段子结构登记（[ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md)要点）

现状：`TableSchema`/`FieldSchema` 把 `Object`/`Array` 定义为"结构未知、由上层模块自行解释的 JSON 对象/数组"，登记上只有一句自由文本描述——如 `core/rules/skill/schema/SkillSchemas.cs` 里 `skill.def.effects` 登记为：

```csharp
new FieldSchema("effects", FieldKind.Array, required: true,
    description: "[{kind: String, params: Object}, ...]")
```

19 种效果原语各自的 `params` 结构只存在于运行时解析代码（`core/rules/skill/core/ParamsX.cs` 等）与 06 号文档的表格里，`Object`/`Array` 字段在编辑器里因此只能退化为 JSON 子编辑（第 5.4.2 节 `Object`/`Array` 控件行）。

[ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md) 提议给 `FieldSchema` 增加可选的子结构描述，不新增 `FieldKind` 枚举值、既有登记不填子结构时行为不变（向后兼容，MINOR 变更）：

- **`Object` 字段**：可登记 `fields: List<FieldSchema>`（递归，子字段同样可以是 `Object`/`Array`）。
- **`Array` 字段**：可登记 `item: FieldSchema`（元素结构；元素本身可以是标量、`Reference`、`Object` 等任一 `FieldKind`）。
- **需要按判别字段分派结构的复合字段**（效果原语的 `params`、光环效果、锁的 `requirement`、区域触发的 `params` 等）登记为**变体**：`variants: {discriminator: String, cases: Map<String, List<FieldSchema>>}`，判别字段合法取值集合即变体表的键集合，等价于对该判别字段的枚举校验。

以 `skill.def.effects` 为例（19 种原语里选 `school_damage`/`apply_aura`/`projectile` 三个变体举例，其余原语登记方式相同）：

```
effects: Array<Object>
  item.variants:
    discriminator: "kind"
    cases:
      "school_damage":
        - base_value: Number, required
        - coefficient: Number, required
        - school: Id, required=false（缺省沿用 skill.def.school）
      "apply_aura":
        - aura_def: Reference(skill.aura_def), required
        - duration_override: Number, required=false
      "projectile":
        - travel_mode: Enum[straight, arc, homing], required=false（缺省 straight）
        - hit_behavior: Enum[impact_on_first, pierce, impact_on_expiry], required=false（缺省 impact_on_first）
        - speed: Number
        - max_range: Number
        - impact_radius: Number, required=false（hit_behavior 为 impact_on_expiry 时使用）
        - max_pierce_count: Int, required=false（hit_behavior 为 pierce 时使用）
        - display_ref: Reference(display.map), required=false
        - on_hit_effects: Array<Object>（嵌套同一份 effects 变体表，递归引用）
```

**登记与校验同源**：`DataRegistry` 的字段级校验按子结构递归检查必填/类型/枚举/引用/Expr 可解析；已登记子结构的复合字段，其结构检查以登记为唯一权威，各模块既有的手写结构校验规则逐步改为只保留"登记表达不了的业务判断"（如预算超标、叠加类别冲突、循环引用）。运行时解析代码可以继续用现有方式读参数，但新增参数必须先登记再使用。

**原语注册表与子结构登记合一**：新增一种效果原语/光环效果/物件类型等（ADR-0010 的受控开口）时，在 [12_扩展与变更流程.md](../../architecture/12_扩展与变更流程.md) 第 2 节"再改注册表"这一步同时登记其变体子结构，作为该步骤的必做项；校验器新增检查项"变体表键集合与运行时注册的原语集合一致"。

**首批登记范围**（按对编辑器价值排序，分批落地，与第 3.4 节 ws-game 工作项①同一清单）：`skill.def.effects`（19 种原语变体）、`skill.aura_def.effects`（10 种变体）、`skill.proc_def`/`skill.spell_mod_def` 的复合字段、`loot.table.groups`、`quest.def` 的目标与奖励、`dialog.*` 节点与动作、`encounter.def` 单位/波次/阶段、`spawn.table` 条目、`area.trigger_def.params`、`gobj.lock.requirement`、`display.map`/`display.anim_set` 的复合字段。

登记补齐前后编辑器行为对照：

| 阶段 | `Object`/`Array` 字段在编辑器里的表现 |
|---|---|
| 登记补齐前（现状） | 退化为 JSON 子编辑器（同源码视图体验，只作用于该字段），专项编辑器里的"效果卡片"（第 5.5.2 节）是套件手工硬编码的定制视图，与登记描述是两套口径 |
| 登记补齐后 | 通用表编辑器可对任意已登记子结构的字段自动生成卡片式子表单（含变体判别字段驱动的"添加效果原语 ▾"下拉），专项编辑器的卡片视图改为读同一份登记生成，不再手工硬编码，登记变化自动反映到界面 |

### 4.4 校验装配入口

**状态：已落地。**

现状：`toolchain/validator/Program.cs`（第 40～150 行左右）内联完成三件事——调用 `PresentationSchemaCatalog.CreateOptions()`/`RegisterAll(registry)` 汇总注册 L0～L5 的 `TableSchema`/`IValidationRule`、手工设置 `options.FailOnUnknownTable = true`/`options.Strictness`、构造 `DataRegistry` 并 `LoadAll`；`SpawnSummonOnlyCreatureRule`（需 `ICreatureTemplateQuery`，见 `GameplaySchemaCatalog.RegisterAll(IDataRegistry, Id?, ICreatureTemplateQuery?)` 第三参数）与 `DisplayMapCoverageRule`（需 sources）两个可选规则在 `toolchain/validator` 里均未接线（第三参数缺省为 `null`）。

[ADR-0018](../../architecture/adr/0018-编辑器随游戏走与框架为此提供的交付物.md) 要求把"调用汇总注册目录 + 可选规则接线参数 + 装配选项"这段抽为核心库内的**单一公开入口**（落在 `presentation/assembly` 或等价的最外层装配目录），签名形态（**默认方案，可调整**，具体命名与参数留待实现阶段对齐 `toolchain/validator` 现有代码结构）：

```
AssembleValidator(
    IDataRegistry registry,
    ValidatorAssemblyOptions options)
  -> ValidatorAssemblyResult { UnenabledOptionalRules: IReadOnlyList<string> }

ValidatorAssemblyOptions {
    bool FailOnUnknownTable;
    DataRegistryStrictness Strictness;
    ICreatureTemplateQuery? CreatureTemplateQuery;   // 未提供 → SpawnSummonOnlyCreatureRule 不接线
    DisplayMapCoverageSources? DisplayMapSources;     // 未提供 → DisplayMapCoverageRule 不接线
}
```

`toolchain/validator` 与编辑器基础套件都只调用这一个入口；未提供的可选规则接线参数时，入口返回 `UnenabledOptionalRules` 供调用方展示"未启用规则清单"，而不是静默跳过——编辑器"校验设置"面板（第 5.7.6 节）据此显示"未启用"标注。这一入口本身不改变现有 `PresentationSchemaCatalog.RegisterAll`/`GameplaySchemaCatalog.RegisterAll` 的级联注册结构（04 第 5.1 节、第 9.5 节"技术选型建议"16.4 节引用处），只是把装配这一步骤本身也收敛为一个公开、可被第二个消费方直接调用的入口。

### 4.5 元数据门禁（状态：已落地）

`check.ps1` 新增一步"元数据门禁：validator --schema-audit（ADR-0018 决策 3/ADR-0019 决策 4）"，在两道数据校验之后、`-Quick` 下也跑（秒级，不需要 `--data-root`、不加载任何实际数据，只审计代码里已登记的 `TableSchema`/`FieldSchema` 结构声明本身）。审计逻辑落在核心库 `presentation/assembly/SchemaAudit.cs`（`Presentation.Assembly.SchemaAudit`），与"数据校验"共用同一份 `ContentValidationAssembly` 装配顺序；`toolchain/validator` 新增 `--schema-audit [--allowlist <path>] [--json]` 命令行模式（`toolchain/README.md`"元数据门禁"一节）。实际落地的检查项与本节此前的"默认方案"table 略有出入（构造期已经强约束的项不必再做运行期巡检，见下表判断记录），以本表为准：

| 检查项 | 级别 | 判定规则 |
|---|---|---|
| `missing_description` | error | 任一层级 `FieldSchema.Description` 为空/空白（含递归进入 `Fields`/`Item`/`Variants` 子结构的字段） |
| `composite_without_substructure` | error | `FieldKind.Object` 无 `Fields`/`Variants`，或 `FieldKind.Array` 无 `Item`，且未在白名单里豁免（豁免须写明 reason，见下） |
| `allowlist_entry_unused` | warning | 白名单条目在当前登记里找不到对应的 `composite_without_substructure` 命中（登记补齐后忘删） |
| `reference_target_unknown` | error | `FieldKind.Reference` 字段的 `ReferenceTable` 不在已登记表清单；`ReferenceDomain` 不在 04 第 2.2 节域名清单 |
| `variant_shape` | error | `Variants.Cases` 键为空、某 case 字段与 `CommonFields`/判别字段同名 |
| `unschematized_table` | warning | `TableSchema.IsUnschematized` 的表（列出，供编辑器知道哪些表只能用 JSON 编辑） |

与"默认方案"表的两点已知差异及原因：① 没有单独的"枚举有值"检查——`FieldKind.Enum` 字段的 `EnumValues` 非空已由 `FieldSchema` 构造函数强制（违反即构造期抛异常），运行期审计再巡检一遍是重复劳动；② 没有单独的"引用有目标"检查（`ReferenceTable`/`ReferenceDomain` 至少设置一个）——实际登记中不设置两者中任何一个的 `Reference` 字段目前尚未出现，且这属于登记疏漏而非结构性风险，留给代码审查而非自动化门禁；"复合字段有子结构"改为不区分"首批登记范围清单内外"，全量检查——ADR-0019 首批登记已在 F1a/F1b/F1c 完成收口，不再需要清单内外的过渡态区分，未登记子结构的字段一律要求显式加入白名单并写明 reason（`toolchain/schema_audit_allowlist.json`）。

首次跑出的全部 `missing_description` 已在字段声明处真正补齐中文一句话描述（不是加白名单——白名单只允许豁免 `composite_without_substructure`），`toolchain/schema_audit_allowlist.json` 收录了 20 条经逐条核实、无法或暂不适合登记为 `Fields`/`Item`/`Variants` 的字段（多数是键动态的 Map 型对象，如 `arch.class.base_stats`；少数是模块显式声明"暂不解析"的扩展位）；`encounter.def.rewards` 经核实有明确的固定子键解析代码，改为复用 `quest.def`/`achv.def` 已有的 `QuestSchemas.RewardsFields` 登记，未进白名单。测试见 `presentation/assembly/tests/SchemaAuditTests.cs`（每个检查项的命中/放行 + 对真实全量登记跑一遍断言 0 error）。

### 4.6 开发期热重载标准实现（状态：已落地）

`games/_template/Runtime/DataHotReload.cs`（`Game.Template.DataHotReload`，`MonoBehaviour`）：`GameBootstrap` 在数据加载成功后按新增口味开关 `GameOptions.EnableDataHotReload`（默认 `true`）挂载；监视框架数据根与游戏数据根下 `*.json`（`System.IO.FileSystemWatcher`，`IncludeSubdirectories`），去抖 300ms 后在主线程（`Update`）调用 `DataRegistry.Reload(<表名>)`，成功经事件总线补发一次 `data.load_completed`（`Reload` 本身不发这个事件，只有整体 `LoadAll` 会发），失败补发 `data.validation_failed` 并打印完整问题清单。仅在 `UNITY_EDITOR || DEVELOPMENT_BUILD` 下编译为有效实现，其余情况是一具空壳（不创建文件监视、不定义 `Update()`），保证发布构建零开销，不依赖游戏层记得手动关闭开关。已知限制（`games/_template/README.md`"开发期数据热重载"一节有明确记录）：`DataRegistry` 的只读查询是全局阻断语义，热重载改坏一张表会让**整个数据集**（不只是这一张表）在下一次成功的重载/加载之前都无法读取，不是"只冻结出问题的那一张表"。

## 5. 编辑器项目：基础套件

本章是编辑器项目（第 3.2 节）产出的基础套件——通用能力全部由这一层提供，"由基础套件提供"是本章的统一归属口径。第 6 章之前，本章内容对任何具体游戏都是通用的，游戏专属定制走第 6、7 章的插件与配置。本章内容延续 v1.1 已定稿的通用能力设计（原 v1.1 第 3～13 章），仅调整归属口径与节号，全部线框图、表格照原样保留。

#### 5.1.2 数据流

```
打开工程（第 5.2.1 节向导）
  → 探测数据根（框架层 data/_framework/ + 游戏层 data/<game>/）
  → DataRegistry.loadAll(多根) —— 按主键合并、按 schema_version 检查、跑迁移
  → 内存记录集（DataRecord 集合，按表分组）
  → 用户编辑（网格/表单/源码三视图任一）
  → 字段级即时校验（编辑动作发生时，FieldKind 对应的单字段规则）
  → 保存（该记录所属表文件整份格式化写回：稳定字段顺序、2 空格缩进、LF、无 BOM）
  → 表级校验（该表全部记录的 IValidationRule）
  → （用户手动触发或提交前）全量校验 —— 等价 toolchain/validate_data.py 两道校验，可选 --strict
  → git（编辑器展示状态与 diff，用户在编辑器内或外部 git 工具提交）
```

#### 5.1.3 核心技术主张（编辑器实现层面的选型建议，非架构结论）

> 本节标注的三点是"基础套件如何实现"层面的建议，供第 9 章"技术选型建议"进一步展开评估，不是架构文档的结论，不影响 `architecture/` 的任何既有拍板。

基础套件进程内**直接引用框架的六个核心类库**（`Core.Foundation` → `Core.Numbers` → `Core.Rules` → `Core.Carriers` → `Core.Gameplay` → `Presentation.Common`，由 `build.ps1` 编译出的 Release DLL，目标框架 `.NET Standard 2.1`）与无头适配层（`Adapters.Stub`，纯 .NET 实现，第 4.3 节），而不是自己重新描述表结构、重新实现校验、重新实现结算算法。这样做换来三个"零重复"：

1. **表结构零重复**：核心库的 `TableSchema`/`FieldSchema`（`core/foundation/data_registry/contracts/`）已经登记了每张表的字段名、`FieldKind`（`Bool`/`Int`/`Number`/`String`/`Id`/`IdList`/`Reference`/`TextKey`/`Expr`/`Enum`/`Vec2`/`Object`/`Array`，见 `FieldKind.cs`）、`Required`、`EnumValues`、`ReferenceTable`/`ReferenceDomain`、`Description`（见 `FieldSchema.cs`）、当前 `CurrentSchemaVersion` 与 `Migrations` 迁移链（见 `TableSchema.cs`）；补齐 [ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md) 子结构登记（第 4.2 节）后还能读到 `Object`/`Array` 字段的 `fields`/`item`/`variants`。基础套件读取这些声明**自动生成**网格列与表单控件（第 5.4.2 节控件映射表），新表/新字段只要在核心库登记，基础套件零改动即可编辑——不需要为每张新表单独写一份 UI 代码。这也是 v1.1 旧 14.3 节"schema 变化自动适配的原则"的完整表述，见 5.1.5 节。
2. **校验规则零重复**：基础套件直接调用 `DataRegistry.LoadAll`/`Validate`/`Reload` 与全部已注册的 `IValidationRule`（经第 4.4 节"校验装配入口"，与 `toolchain/validator` 用同一入口），做到"编辑器里看到的红线 = 运行时/门禁会报的错"这一硬承诺；不存在"编辑器说没问题，但 `validate_data.py` 报错"的割裂体验。
3. **数值预览与模拟零重复**：确定性固定步长模拟（拍板决策 3）本身可以脱离引擎运行，基础套件借无头适配层（`Adapters.Stub`，第 4.3 节）跑结算管线（06 第 4.1 节）、掉落抽取（08 第 1 节）、经验曲线换算等"数值沙盘"（第 5.8 节），预览结果与游戏内真实运行结果保证一致，因为走的是同一份规则层代码与同一份适配层实现。

版本对齐不再是"基础套件与框架同号发布"（v1.1 旧写法已作废），而是第 3.3 节"版本与兼容矩阵"描述的独立版本关系：基础套件声明自己兼容的框架 MAJOR 段，编辑器实例打开工程时按第 5.2.1 节流程读取游戏仓库根 `ws-game.lock` 判定当前锁定的框架版本，MAJOR 段超出编辑器项目兼容矩阵直接拒绝打开并提示升级编辑器项目版本，MINOR 段不同不阻断，仅提示查阅框架 `CHANGELOG.md` 对应版本区间"编辑器相关契约"标注的迁移说明（见第 5.7.5 节"schema 迁移"与用户故事 5）。

#### 5.1.4 与既有工具链的复用关系一览

| 既有工具/文档 | 基础套件如何复用 |
|---|---|
| [data/README.md](../../data/README.md) | 文件组织（`data/<game>/<domain>/<table>.json`）、信封（`table`/`schema_version`/`rows`）、主键规则（内容表 `id`、登记表 `key`、`l10n.text` 复合键）、编码格式（UTF-8 无 BOM、2 空格、LF）全部照搬，保存动作严格产出符合此约定的文件 |
| `toolchain/validate_data.py` | 基础套件"手动全量校验"命令等价调用它的两道校验（骨架级 + `toolchain/validator`），支持传等价的 `--strict` |
| `toolchain/validator`（.NET） | 基础套件进程内直接引用同一套 `DataRegistry` + `IValidationRule` 实现（而非再拉起子进程），字段级/表级校验走同一套代码路径；全量校验可选择"进程内跑"或"拉起子进程跑，日志汇入输出面板"两种模式（后者用于跟门禁行为完全对齐地复核）；基础套件装配校验器时必须调用第 4.4 节"校验装配入口"并传入与 `toolchain/validator` 相同的可选来源与选项（`FailOnUnknownTable`/`Strictness`，以及 `SpawnSummonOnlyCreatureRule`/`DisplayMapCoverageRule` 等需装配层显式接线的规则来源，游戏侧经第 6.1 节"校验来源声明"扩展点提供），避免"编辑器全绿但门禁报错"的割裂，见第 5.7.6 节"校验覆盖矩阵与可选规则装配"、04 第 5.1 节 |
| `toolchain/import_assets.py` | 基础套件"外形与表现编辑器"按六个子命令（`sprite`/`icon`/`vfx`/`sfx`/`map`/`check`）分别提供调用入口（见第 5.5.9 节）：前五个把出图产物/地图分层图合并写入 `display.map`/`vfx.def`/`sfx.def`/`world.map`（同主键整行替换，其余行保留），`check` 交叉校验 `assets/<dataset>/` 与这四张表的引用是否存在；资源存在性黄标全部来自解析 `check` 的输出，基础套件不自建路径推导逻辑，资源路径规则统一由 `toolchain/resource_layout_map.json` 定义 |
| 04 第 4 节多根加载与合并规则 | 基础套件打开工程即按此规则加载框架根 + 游戏根，`override`/`final` 字段在记录操作里可视化呈现（见第 5.4.3 节） |
| 04 §4 `DataRegistry.reload(domain)` | 基础套件保存文件后，若联调面板检测到游戏侧以开发期构建运行，转发一次 reload 请求触发热重载（第 4.6 节标准实现，见第 5.11 章） |

#### 5.1.5 schema 变化自动适配的原则

核心库新增一张表或给已有表新增字段时，基础套件不需要跟着改代码即可继续工作：新表自动出现在导航区"按层/域/表"树中（归入通用表编辑器，第 5.4 节）；已有表新增字段自动出现在表单视图的对应分组末尾与网格视图的新增列（默认显示，用户可手动隐藏）。只有当某张表需要**专属**的可视化（画布、卡片、图表）时才需要更新对应专项编辑器（第 5.5 节）或走第 6 章插件机制补一个专项编辑器插件；这是"零改动可编辑新表"（第 5.1.3 节主张 1）与"专项体验需要额外投入"之间的边界。补齐 [ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md) 子结构登记（第 4.2 节）后，已登记 `fields`/`item`/`variants` 的复合字段也能零改动生成卡片式子表单，进一步收窄"需要专属可视化"的范围。

### 5.2 工程与工作区

#### 5.2.1 新建/打开工程向导

编辑器实例首次启动或点"新建/打开工程"时弹出向导（编辑器实例即游戏仓库 `<game>/editor/` 下的具体程序，见第 7 章；本节描述的能力由基础套件提供）：

1. **选游戏仓库根**：文件选择器选中某个 `<game>` 仓库的根目录（例如用户本地的游戏仓库路径）。
2. **自动探测数据根**：编辑器在所选根目录下查找 `data/<game>/`（`<game>` 段名由该仓库自己决定，编辑器不关心具体拼写），探测到即列为"游戏层数据根";若找不到，提示用户手动指定路径或改为"仅浏览框架层"的只读模式。
3. **自动探测框架来源**：读取所选仓库根的 `ws-game.lock`（若存在），据其 `version` 与 `source.channel` 字段判断消费通道：`channel: "zip"` 时按 `packages/ws-game-<version>/` 定位框架层数据根（`packages/ws-game-<version>/data/_framework/`）、核心 DLL（`packages/ws-game-<version>/adapters/unity/Packages/com.gamefoundation.adapter.unity/Runtime/Plugins/Core/`）与工具链（`packages/ws-game-<version>/toolchain/`）；`channel: "registry"` 时框架内容已由 Unity 解析到该工程 `Library/PackageCache/` 下的三个包目录（`com.gamefoundation.framework-data` 包内 `Data~/` 为框架层数据根、`com.gamefoundation.adapter.unity` 包内 `Runtime/Plugins/Core/` 为核心 DLL、`com.gamefoundation.toolchain` 包内 `Tools~/` 为工具链），编辑器按包名在 `Library/PackageCache/<包名>@<版本>/` 下查找。找不到 `ws-game.lock`（尚未接入任何通道，或锁文件缺失）时，退回弹出对话框让用户手选一个 `packages/ws-game-<ver>/` 目录，或本机 `dist/<ver>/` 目录。
4. **读取编辑器项目版本锁定**：读取该编辑器实例自身的 `<game>/editor/editor.lock`（第 3.3、7.2 节），得到当前锁定的编辑器项目版本号与来源通道；编辑器实例自身即按这个版本号编译，本步骤只做"锁定记录与实际运行的编辑器实例版本是否一致"的自检，不一致时提示"editor.lock 记录的版本与当前运行的编辑器实例版本不符，可能是复制/覆盖模板时遗留的旧锁文件，建议核对"。
5. **显示框架版本与兼容性**：向导展示"检测到框架版本 `1.12.0`（来源：zip 通道 / 私服通道 / 本机 `dist` 目录），本编辑器项目版本 `<editor.lock 记录的版本号>` 声明兼容框架 MAJOR = 1 的全部版本"一类结论；兼容判定按第 3.3 节"版本与兼容矩阵"：MAJOR 相同即视为兼容，MINOR 不同只在本步骤提示"建议查阅框架 `CHANGELOG.md` 对应区间'编辑器相关契约'标注的迁移说明"（不阻断，见第 5.7.5 节）；MAJOR 不同则拒绝打开工程并提示"框架 MAJOR 版本超出当前编辑器项目版本的兼容矩阵，请先升级编辑器项目版本"。
6. 确认后进入主界面，状态栏立即显示工程名、框架版本与编辑器项目版本（见第 5.3.7 节）。

#### 5.2.2 最近工程

主界面欢迎页与"文件"菜单下列出最近打开的工程（路径 + 上次打开时间 + 框架版本 + 编辑器项目版本），点击直接按 5.2.1 节流程重新加载；工程路径不存在时该项标灰并提示"未找到，是否移除记录"。

#### 5.2.3 工程文件 `.gfeditor/workspace.json`

工程首次打开成功后，编辑器在该游戏编辑器实例目录 `<game>/editor/.gfeditor/workspace.json` 写入/更新一份工作区文件，记录：

| 字段 | 说明 |
|---|---|
| `dataRoots` | 已探测/手动指定的数据根路径列表（框架层 + 游戏层） |
| `frameworkRoot` | 当前锁定的框架内容根路径：zip 通道为 `packages/ws-game-<ver>/`，私服通道为 Unity 解析到的 `Library/PackageCache/` 下对应包目录，本机 `dist` 退回场景为用户手选的 `dist/<ver>/` |
| `frameworkChannel` | 框架来源通道：`zip`\|`registry`\|`local_dist` |
| `frameworkVersion` | 当前锁定的框架版本号（来自 `ws-game.lock` 的 `version` 字段） |
| `editorSdkVersion` | 当前锁定的编辑器项目版本号（来自 `editor.lock` 的 `version` 字段，第 7.2 节） |
| `defaultLocale` | 默认语言，用于文本键校验与内联编辑默认显示语言 |
| `preferences` | 编辑器偏好（布局、主题、最近打开的标签页等，纯 UI 状态） |
| `lastValidationSummary` | 上次全量校验的时间与结果摘要，供打开工程时快速展示"距上次校验已过 N 天" |

**是否入库的建议（默认方案，可调整）**：`workspace.json` 里 `dataRoots`/`frameworkRoot`/`frameworkChannel`/`frameworkVersion`/`editorSdkVersion`/`defaultLocale` 属于"团队共享的工程配置"，建议入库（多人打开工程时行为一致）；`preferences`（布局、最近标签等纯个人偏好）与自动保存草稿目录（见第 8.2 节 `.gfeditor/autosave/`）不建议入库，建议在游戏仓库 `.gitignore` 里为 `<game>/editor/.gfeditor/autosave/` 与 `<game>/editor/.gfeditor/*.local.json` 加忽略规则；编辑器首次写入 `workspace.json` 时如检测到仓库尚无对应 `.gitignore` 规则，弹出一次性提示询问是否代为写入。

#### 5.3.2 顶部：菜单栏 / 工具栏 / 全局搜索

- **菜单栏**：文件（新建/打开/最近/保存/另存/退出）、编辑（撤销/重做/查找替换）、视图（面板显隐/布局保存重置/主题）、工程（工程设置/数据根管理/框架版本核对/编辑器项目版本核对）、校验（字段级开关/表级校验/全量校验/严格模式开关）、工具（数值沙盘/批量编辑/导入导出/调用 `import_assets.py`）、运行（配置可执行文件路径/一键运行/热重载设置）、帮助（快捷键表/关于/日志目录）。

| Tab | 内容 |
|---|---|
| 按层/域/表 | 树形结构：L0 基础层 → L1 数值层 → L2 规则层 → L3 载体层 → L4 玩法层 → L5 表现层 → 显示与本地化，逐层展开到模块再到具体表；每张表节点右侧显示"行数"与"错误数徽标"（红色数字，0 时不显示；有警告无错误时显示黄色感叹号） |

#### 5.3.8 主题、DPI、窗口与布局

- 主题：浅色 / 深色 / 跟随系统三选一，设置项见第 5.12 节；切换即时生效不需重启。
- DPI 缩放：跟随系统 DPI 设置自动缩放界面元素与字体，最小窗口尺寸 `1280×800`（低于该尺寸时禁止进一步缩小，允许滚动）。
- 布局：导航区/检视区/面板区的宽高、折叠状态、文档区分栏结构整体可"保存为默认布局"或"重置为出厂布局"（视图菜单）；布局保存在 `workspace.json` 的 `preferences` 段（个人偏好，见第 5.2.3 节，不建议入库）。

### 5.4 通用表编辑器（Schema 驱动）

通用表编辑器是基础套件的地基：任何一张登记在 `TableSchema` 里的表，不需要任何专项定制即可用它编辑；第 5.5 节的专项编辑器都是在通用表编辑器基础上叠加的"更好用的皮肤 + 专属校验/预览"，专项编辑器覆盖不到的表（第 5.5.10 节）直接落回通用表编辑器。

#### 5.4.1 三视图同步

一条记录或一整张表在文档区可以三种视图打开，三者对同一份内存记录集读写，切换视图不丢失未保存的编辑，字段级校验状态三视图共享。

```
+----------------------------------------------------------------------------------+
| [网格视图] [表单视图] [源码视图]                              记录: skill.sample_burn |
+----------------------------------------------------------------------------------+
| 网格视图（整表）：                                                                  |
|  id 冻结列 | school | kind | range | cast_time | cost | ... （可排序/筛选/分组/隐藏列）|
|  多选后可批量改字段（见第 5.9 章）；行内编辑，Tab/Enter 移动焦点                       |
+----------------------------------------------------------------------------------+
| 表单视图（单条记录，按 schema 顺序分组）：                                            |
|  [基础] id / school / kind / range                                                |
|  [引用] target_shape_ref                                                          |
|  [数值] cast_time / cooldown_duration / cost                                       |
|  [表现] （该表若有 display 相关字段则归入本组）                                        |
|  [高级] tags / interrupt_flags / action_cost                                       |
|  必填字段星标(*)，字段旁 (?) 悬停显示 FieldSchema.Description                          |
+----------------------------------------------------------------------------------+
| 源码视图（该记录或整表 JSON，语法高亮）：                                             |
|  {                                                                                 |
|    "id": "skill.sample_burn",                                                     |
|    "school": "school.fire",                                                       |
|    ...                                                                            |
|  }                                                                                 |
|  保存时若 JSON 解析失败 → 进入"修复模式"（红色边框 + 错误行号提示），不覆盖磁盘文件      |
+----------------------------------------------------------------------------------+
```

- **网格视图**：列 = 字段，虚拟化渲染（保证 5 万行级表滚动流畅，见第 8.1 节性能指标）；冻结主键列（`id`/`key`）；支持列排序、按字段值筛选、按枚举字段分组折叠、隐藏/显示列（列头右键菜单）；行内编辑（双击进入编辑态，控件按第 5.4.2 节映射表渲染）；支持多选（`Shift`/`Ctrl` 点选，或框选）。
- **表单视图**：按 `TableSchema.Fields` 的登记顺序分组展示（基础/引用/数值/表现/高级五个语义分组，直接读取 `FieldSchema.Group`，[ADR-0022](../../architecture/adr/0022-登记表补充导航与编辑元数据.md) 已提供——核心库未显式登记时按字段命名与 `FieldKind` 计算默认分组，编辑器不需要自己再启发式判断一遍；附录 B 控件映射表最后一列的"分组建议"仅作参照）；必填字段（`FieldSchema.Required == true`）显示红色星标；每个字段标签旁的 `(?)` 图标悬停显示 `FieldSchema.Description`。
- **源码视图**：可查看/编辑单条记录或整张表的原始 JSON，语法高亮（键名/字符串/数字/布尔各自配色）；保存时先做 JSON 语法解析，解析失败不覆盖磁盘文件、进入"修复模式"（编辑区红框 + 错误所在行号与列号提示），修复通过后才允许写盘。

#### 5.4.2 字段类型 → 控件映射表

| `FieldKind` | 渲染控件 | 交互细节 |
|---|---|---|
| `Bool` | 开关（Toggle） | 点击切换，无需二次确认 |
| `Int` / `Number` | 数字输入框 | 支持步进按钮与拖拽微调；`FieldSchema.Unit` 登记为"时间模型单位"（[ADR-0022](../../architecture/adr/0022-登记表补充导航与编辑元数据.md)，04 第 3.1/3.4 节；不再靠字段名清单猜）时，输入框带单位后缀（"秒"或"回合"，取决于所属表 `TableSchema.TimeScope` 对照的 `found.time_model.mode`——`TimeScope` 为"两者皆有"时按该条记录实际归属的作用域取值），离散模式下拒绝输入小数（失焦时四舍五入并提示"离散模式下时间字段必须为整数"） |
| `String` | 单行文本框 | 无格式限制的自由文本（如 `sprite_set_id` 一类资源引用字符串） |
| `Enum` | 下拉选择框 | 选项列表 = `FieldSchema.EnumValues`；不允许手输不在列表内的值 |
| `Id` | Id 输入框 | 自动补全 `domain` 前缀（按所属表的 domain 段，见 04 第 2.2 节）；实时按正则 `^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$` 校验格式；主键字段额外做同表唯一性检查，冲突时输入框标红并提示已存在的记录 |
| `IdList` | 标签编辑器（Chips） | 每个 id 显示为一个可删除的标签；已登记 `ReferenceTable`/`ReferenceDomain`（[ADR-0022](../../architecture/adr/0022-登记表补充导航与编辑元数据.md)）的字段，输入区提供按目标表/域筛选的自动补全下拉，`Ctrl+点击`已填标签跳转到目标记录，目标缺失时标签标红（惯例同 `Reference` 控件）；登记为 `FreeIds`（自由 id 列表）的字段不提供自动补全，仅做格式校验 |
| `Reference` | 引用选择器 | 点击弹出搜索浮层，可搜索 `ReferenceTable`/`ReferenceDomain` 声明的目标表/域内记录，列表显示"显示名 + id + 缩略图"；`Ctrl+点击`已填值直接跳转到目标记录；悬停已填值显示目标记录的预览卡（名称/关键字段摘要）；目标缺失时输入框标红并提供"创建目标记录"按钮（跳转到对应新增流程，见第 5.6 节） |
| `TextKey` | 本地化内联编辑框 | 直接显示/编辑默认语言（`workspace.json.defaultLocale`）正文；首次填入非空文本时按规则 `l10n.<来源域>.<来源记录id去掉domain前缀>.<字段名>` 自动生成 key 并写入 `l10n.text`；其余已登记语言若该 key 缺失，框下方显示"缺失 N 种语言"提示，点击展开逐语言小输入框 |
| `Expr` | 表达式编辑器 | 语法高亮（关键字/分组名/字符串/数字/括号配色）；输入 `group.` 后弹出该分组下已知 `key` 的自动补全列表（九个分组：`self`/`target`/`event`/`world`/`quest`/`player`/`combat`/`enemies`/`time`，见 04 第 6.2 节），补全项分两档颜色：已登记的 `group.key` 正常展示，悬停显示其类型；未登记的组合悬停显示回退结果说明（见下）；括号自动匹配高亮；失焦时按 04 第 6.1 节 BNF 做实时解析，**语法错误、类型不匹配**标红下划线并阻断保存（04 第 6.4 节解析期红线，两者不区分显示，统一按"错误"级处理）；点分标识符按 04 第 6.3/6.4 节分级处理未登记的 `group.key`：域名段属于八个普通分组（`self`/`target`/`world`/`quest`/`player`/`combat`/`enemies`/`time`）之一但未登记，回退为 id 字面量，标黄"疑似引用拼写错误"警告（不阻断）；域名段是 `event` 分组，回退为签名未知的引用，不标红不标黄（04 第 6.3 节"`event` 分组例外"，运行期按分组默认值求值）；识别为合法内容 id 字面量的片段可点击跳转到目标记录 |
| `Vec2` | 双数字框（x/y） | 相邻两个数字框；若该记录所属专项编辑器提供地图画布（第 5.5.7 节），双数字框与画布上的点位联动：拖拽画布上的点等价于改这两个数字 |
| `Object` | 结构化子表单 / JSON 子编辑 | 已登记子结构（`FieldSchema.Fields`，第 4.2 节 [ADR-0019](../../architecture/adr/0019-复合字段子结构登记为机器可读schema.md)）的字段渲染对应的结构化子表单（如技能 `effects`、掉落 `groups`、任务 `objectives`、对话 `nodes` 等，均在第 5.5 节专项编辑器中定制为卡片/子表格）；未登记子结构的 `Object` 字段退化为一段内嵌的 JSON 子编辑器（同源码视图的编辑体验，但只作用于该字段） |
| `Array` | 结构化子表格 / JSON 子编辑 | 已登记子结构（`FieldSchema.Item`，含 `variants` 判别分派）的字段渲染为可增删排序的子表格（如效果列表卡片可拖拽排序，`variants` 字段驱动"添加效果原语 ▾"下拉列出全部已登记 `cases` 键），未登记子结构的退化为 JSON 子编辑 |

#### 5.4.3 记录操作

| 操作 | 用户怎么做 | 系统反馈 |
|---|---|---|
| 新增 | 网格视图工具栏"新增"按钮，或右键"在此表新增记录" | 生成新记录，主键按"表 domain 前缀 + 用户输入名字段"规则自动生成 id 建议值（可编辑），其余字段按 `FieldSchema` 声明的类型给出合理默认值（`Bool→false`、`Number→0`、`Enum→` 第一个枚举值等，模板可由专项编辑器覆盖为更贴合语义的默认值，见第 5.6 节新增内容向导）；新记录自动打开表单视图供继续填写 |
| 克隆 | 选中记录右键"克隆" | 弹出对话框要求输入新 id，默认建议 `<原id>_copy`；若原记录存在被同类结构引用的关联行（如物品的 `display_ref`），提供"级联克隆关联行"复选框（默认不勾选），勾选后连带克隆并重新绑定引用 |
| 删除 | 选中记录右键"删除"或按 `Delete` | 先弹出"影响分析"对话框（见第 5.7.4 节引用图）列出"哪些记录引用了本记录"，若存在引用则默认按钮为"取消"，需用户显式点击"仍然删除"二次确认；确认后记录从内存集移除并标记该表为脏 |
| 重命名 id | 选中记录右键"重命名 id" | 弹出对话框输入新 id，系统扫描全部表中的引用字段、`Expr` 中的 id 字面量、`l10n.text` 的 key 前缀，生成一份"改动清单"预览（哪些表哪些字段会被级联更新），用户确认后统一执行并标记全部受影响表为脏 |
| 移动到另一层 | 框架层只读记录右键"覆盖到游戏层" | 在游戏层数据根生成一份内容相同、带 `override: true` 的副本记录，覆盖诊断面板新增一条"该记录已被游戏层覆盖"的信息级提示（非错误）；若原框架层记录声明 `final: true`，菜单项显示为禁用并附锁形图标提示"该记录不可覆盖" |

#### 5.4.4 撤销/重做

跨记录、跨表的**事务式撤销栈**：一次原子编辑（改一个字段值、执行一次批量替换、执行一次重命名 id 级联更新）作为一个撤销单元；`Ctrl+Z`/`Ctrl+Y` 在整个工程范围内撤销/重做，不限定在当前打开的标签；**保存动作不清空撤销栈**（保存只是把当前内存状态落盘，撤销栈仍保留保存前后的完整历史，允许"保存后又想撤销回保存前的状态"）。撤销栈上限为可配置的操作步数（默认 500 步，见第 5.12 节设置项），超出上限从最早的操作开始丢弃。

#### 5.4.5 保存

- 按表文件写回：一次保存动作只重写该记录所属的表文件（`data/<game>/<domain>/<table>.json`），不触碰其它未改动的表文件。
- 稳定字段顺序：按 `TableSchema.Fields` 声明的顺序输出字段；核心库尚未登记但文件里已存在的未知字段，保留在已知字段之后、按原文件中的相对顺序追加，不丢弃。
- 格式：2 空格缩进、LF 行尾、UTF-8 无 BOM，与 [data/README.md](../../data/README.md) "编码与格式"一节要求一致，保证 git diff 最小（只有真正改动的字段产生 diff 行）。
- 外部修改检测：编辑器对已打开工程的数据根文件保持文件系统监视；若磁盘文件在编辑器外被修改（如另一进程的脚本改了 JSON，或 git 切换分支），弹出提示"检测到外部修改"，提供"重新加载（丢弃编辑器内改动）"与"对比差异后决定"两个选项，避免静默覆盖。

### 5.5 专项编辑器

专项编辑器是通用表编辑器之上，针对高频域定制的更好用的界面：更贴合语义的布局、专属的可视化控件（画布、卡片、图表）、更聚焦的专属校验与预览。每个专项编辑器覆盖固定的一组表，不覆盖到的表仍可从导航区"按层/域/表"进入通用表编辑器直接编辑。九个专项编辑器全部由基础套件提供；游戏侧可经第 6.1 节"专项编辑器插件"扩展点新增游戏专属的第十个及以上专项编辑器。

#### 5.5.1 人物与生物编辑器

**目的**：编辑生物模板与其依赖的职业/种族/天赋/资源类型/属性/阵营定义，让策划一次看清"一只生物由哪些表拼成"。

**覆盖的表**：`creature.template`、`creature.tier_definition`、`arch.class`、`arch.race`、`arch.talent_tree`、`arch.power_type`、`stat.definition`、`fac.faction`、`fac.reaction_matrix`。

**交互流程**：

1. 左侧列表选中一只生物，中央区域按上图分块展示；每块都是对通用表单视图的重新编排，字段控件仍按第 5.4.2 节映射表渲染，只是布局更贴合"策划心里怎么想一只生物"的顺序。
2. 属性面板的"等级 1..N 成长预览"：读取 `stat_growth_ref` 指向的成长曲线（与 `prog.level_curve` 同类结构）与 `tier` 对应的分档倍率，逐级算出 `base_stats` 之外每级的最终属性值，渲染为表格 + 折线图；纯预览，不产生任何写盘副作用。
3. 职能标志位为复选框组（第 07 文档 2.2 节六项固定枚举，存储值为 `npc_flag.<name>`，如 `npc_flag.vendor`；`FieldSchema.AllowedValues` 登记，`FieldKind.IdList` 的语义化呈现），勾选/取消即改 `npc_flags` 列表；六个勾选项即 `field_meta.allowed_values` 给出的固定集合，不需要编辑器自行硬编码。
4. AI 绑定、掉落绑定两处的下拉是按 `field_meta.soft_reference_table`（消费方反馈第 29 条：`ai_rotation_ref`/`ai_behavior_ref`/`loot_table_ref` 均已登记）渲染的软引用控件，与真正的 `Reference` 控件外观一致但语义不同——只做自动补全/跳转，不做存在性强校验（目标表未加载/记录不存在也不报错）；"打开"按钮跳转到对应记录（AI 优先级表落回通用表编辑器，掉落表跳到 5.5.4 节掉落编辑器）。
5. **职业编辑（`arch.class`）**：主属性引用（`Reference` 到 `stat.definition`）、资源类型引用（`Reference` 到 `arch.power_type`，可多选）、技能书（`Reference` 到 `skill.book`）、天赋树引用（`Reference` 到 `arch.talent_tree`）四个字段按同样的分块表单呈现；点击天赋树引用旁"打开"进入下方的天赋树画布。
6. **天赋树画布**：节点（每个节点 = 一条天赋，绑定一个被动光环或 `override_skill`/`spell_mod` 效果，见 06 第 3.5、5 节）以卡片形式摆放在画布上，前置关系画连线；拖拽节点改变位置（纯展示布局，不影响数据语义）；拖拽节点边缘到另一节点建立/删除前置连线；系统在每次连线改动后运行成环检测（DFS 沿前置边遍历），检测到环时该连线显示红色警示线并在问题面板报"循环引用检测"错误，阻止保存。
7. **反应矩阵（`fac.reaction_matrix`）**：二维网格呈现，行/列均为 `fac.faction` 记录，单元格是枚举下拉（敌对/中立/友好）；对角线单元格（阵营对自身）灰化不可编辑，恒为"友好"。

**专属校验/预览**：属性成长预览、天赋树成环检测（对应 04 第 5 节"循环引用检测"）、反应矩阵对称性提示（若 A 对 B 是敌对但 B 对 A 未设为敌对，出信息级提示，不阻断，因为设计上允许单向敌意）。

8. **右侧结算预览**：下拉选施法者模板与目标模板（数据源为 `creature.template`），点"运行结算预览"调用无头适配层跑一次确定性结算（06 第 4.1 节固定管线：判定 → 基础值 → 暴击 → 施法者乘区 → 减免 → 目标乘区 → 免疫吸收 → 落地 → 后置），分步展示每一步的中间值与最终伤害/治疗量，并给出"期望 DPS"（若 `cast_time` > 0，按读条时间折算）。字段改动后预览自动标记为"已过期"（半透明 + "结果可能已过期，重新运行"提示），不做静默自动重算（避免频繁改字段时预览抖动）。实现上直接订阅第 4.1 节 `CombatOptions.ResolveTrace`（消费方反馈"结算中间步骤经真实施法路径不可观测"，编辑器第 31 条）拿到每一步的中间值，不必自行重新实现一份结算公式——预览分步展示与游戏内真实施法路径逐步一致，保证不会出现"预览面板算法与实际结算算法各自维护、逐渐漂移"。

**专属校验/预览**：效果数上限进度提示、叠加类别冲突高亮、结算预览分步展示。

2. `objectives` 列表：每条按 `type`（八种枚举，见 08 第 2.1 节表）切换 `targetRef` 的引用选择器过滤范围（`kill`→`creature.template`，`collect`→`item.template`，`interact`→`gobj.template`，`explore`→`area.trigger_def`，`escort`→`creature.template`，`event`→事件类型选择器，`cast`→`skill.def`，`talk`→对话节点选择器）；`count`、`descriptionKey`、`param`（随 `type` 显示专属参数子表单，如 `collect` 类型显示 `consume_on_progress` 开关）。
3. **前置任务 DAG 图**：读取 `prerequisite` 中出现的 `quest.is_active(...)`/`quest.is_completed(...)` 类引用与 `exclusive_group` 归属，画出任务间的前置箭头图；成环检测（对应 08 无直接声明但沿用 04 第 5 节"循环引用检测"的通用能力）跑在这张图上，检出环时红色高亮该环并阻止保存。
4. rewards 区块：`items`/`currency` 为可增删的行列表，`xp`/`talent_points` 为数字框，`skills` 为 `IdList`，`world_flags` 为"标志键 + 值"配对列表。

**界面布局线框（对话）**：

```
+----------------------------------------------------------------------------------------+
| 对话列表(左)  |  中央：gossip选项表 / 剧情树节点画布                                        |
+---------------+----------------------------------------------------------------------------+
| ▾ gossip      | dialog.innkeeper_greet                                                      |
|   innkeeper_..| options:                                                                     |
| ▾ story       |  #1 textKey:[你好，旅人] visibleIf:[ - ] actions:[quest_accept:quest.intro] |
|   intro_tree  |  #2 textKey:[我要买点东西] visibleIf:[ - ] actions:[vendor]                  |
|               |  [+添加选项]                                                                 |
+---------------+----------------------------------------------------------------------------+
|               | 剧情树节点画布（story_tree）：                                               |
|               |  [起始:node_1]──分支A(cond)──▶[node_2]                                       |
|               |        └──────分支B────────▶[node_3(终止)]                                   |
|               |  点击节点：右侧编辑 textKey / speakerRef / performanceHookRef                |
|               |  [试讲] 从选中节点开始模拟走一遍分支                                          |
+----------------------------------------------------------------------------------------+
```

1. gossip 菜单：选项列表，`visibleIf` 是 `Expr` 编辑器，`actions` 是可增删的动作列表（十种动作类型，见 08 第 3.1 节：`vendor`/`quest_accept`/`quest_turn_in`/`teleport`/`save`/`set_flag`/`start_encounter`/`cast_skill`/`start_story`/`script`，每种类型切换对应的参数子表单）。
2. 剧情树：节点画布，起始节点固定为 `nodes` 数组第一个元素（画布上用特殊边框标出）；分支连线标注 `condition`（若有）；`performanceHookRef` 下拉数据源来自 `found.hook`（框架层只读登记表）。
3. 剧情树成环检测：沿 `branches[].nextNodeId` 遍历，检出环时高亮环路径并阻止保存。
4. **"试讲"**：从选中节点开始，按分支 `condition`（用当前选定的一组模拟 Expr 上下文，如"假设 world 标志全为默认值"）走一遍最可能的分支路径，在画布上高亮经过的节点序列，供文案快速核对台词衔接是否通顺；纯预览，不产生任何写盘副作用。

**专属校验/预览**：任务前置 DAG 成环检测、剧情树分支成环检测、试讲预览。

**交互流程**：

1. 列表按 `category`（`skill`|`aura`|`item`|`creature`|`gobj`|`projectile`）与"资源缺失"筛选；缺失（由 `import_assets.py check` 判定 `sprite_set_id`/`icon_id`/`model_ref`/`resource_ref` 等对应目录或文件不存在，见下方第 3 点）的行前缀黄色感叹号。
2. `kind` 单选切换 `sprite`/`model` 两组专属字段（07 表现层 7.1 节字段表），未选中的一组整体灰化只读，对应 04 第 5 节"外形类型字段组完整"校验项在此以界面禁用的方式提前预防，而不是等保存后报错。
3. **资源引用存在性检查**：编辑器不自建目录扫描/路径推导，而是作为子进程调用 `python toolchain/import_assets.py check --dataset <dataset> [--assets-root ...] [--data-root ...] [--only sprite,vfx,sfx,world]`，解析其问题清单（资产/目录缺失、`mirror_pairs` 完整性、声明锚点缺失、精灵集跨方向档位尺寸不一致等，见 `toolchain/README.md`"资产导入工具"一节 `check` 子命令说明）回填到对应记录/字段的黄标；资源路径规则统一由 `toolchain/resource_layout_map.json` 定义，编辑器读取该文件解析预览缩略图的实际路径，不重复实现路径推导。打开工程时与用户手动点"重新扫描"时各触发一次调用。
4. 预览：精灵/图标类字段显示缩略图（读取匹配到的实际图片文件）；`sfx_id` 提供"试听"按钮（本地播放对应音频文件，无音频输出设备时按钮置灰并提示）。

6. **调用 `import_assets.py`**：面板按六个子命令（`sprite`/`icon`/`vfx`/`sfx`/`map`/`check`）分别提供参数表单——`sprite` 对应源目录选择 + `--mirror`/`--anchors`/`--anchor-default`/`--trim`/`--scale`/`--shadow`/`--pixels-per-unit`；`icon` 对应一批源图选择；`vfx` 对应序列帧目录 + `--attach-mode`/`--fps`/`--loop`/`--lifetime`；`sfx` 对应多文件（同 id 随机变体）选择；`map` 对应地图分层图目录 + `--spawn`；`check` 对应 `--dataset`/`--only` 选择（即第 3 点复用的同一入口）。选定参数后作为子进程调用对应 `toolchain/import_assets.py <子命令>`，标准输出/错误实时汇入本面板下方日志区（同时也汇入主界面"输出"面板，见第 5.3.6 节），执行完成后自动重跑一次 `check` 刷新资源存在性黄标与相关 `display.map`/`vfx.def`/`sfx.def`/`world.map` 记录（新写入的行按主键整行替换，其余行原样保留，对应 ADR-0014"外形表行由工具生成而非手填"）。
7. 其余表（`display.anim_set`/`display.equip_visual`/`display.weapon_style`/`vfx.def`/`sfx.def`/`feedback.binding`/`feedback.floating_text_style`/`camera_profile`/`ui_layout_definition`/`shell_menu_definition`）在本编辑器内以标签页形式提供紧凑表单，字段渲染沿用第 5.4.2 节映射表，不单独定制画布。

**专属校验/预览**：资源存在性检查（复用 `import_assets.py check`）、外形映射存在反查、外形类型字段组完整的界面级预防、`import_assets.py` 六个子命令调用与日志。

### 5.7 校验、诊断与引用分析

#### 5.7.1 三个校验时机

| 时机 | 触发条件 | 范围 | 反馈方式 |
|---|---|---|---|
| 编辑即字段级 | 字段失焦、下拉选择变更、卡片参数改动 | 仅该字段（格式、枚举、引用格式、Expr 语法等不依赖同表其它记录的检查） | 字段旁即时标红/标黄下划线，悬停显示错误文本 |
| 保存即表级 | 保存该表文件时 | 该表全部记录的 `IValidationRule`（预算超标、叠加类别冲突、效果数上限等需要跨记录/跨表核对的规则） | 问题面板增量刷新该表相关问题；保存本身不因表级警告而失败，但表级错误会在问题面板高亮且状态栏错误数增加 |
| 手动/提交前全量 | 用户点"校验"菜单"全量校验"，或提交前钩子触发 | 全部已加载数据根，等价 `toolchain/validate_data.py` 两道校验，可选 `--strict`（警告也阻断） | 弹出/刷新完整校验报告，问题面板全量重建，状态栏错误/警告数刷新为全量结果 |

#### 5.7.2 问题面板设计

问题面板（第 5.3.6 节底部面板区）列表每行结构：`[级别图标] 所属表.记录id: 检查项名称 — 说明文本 [跳转]`；支持按"所属表"/"问题类型"（对应 04 第 5 节 14 项检查项名称）/"来源"（字段级/表级/全量）三维筛选与组合排序；双击任意一行跳转到对应记录的对应字段并高亮闪烁一次。Expr 相关问题按第 5.4.2 节的分级出现：语法错误/类型不匹配为错误级；未登记的普通分组 `group.key` 回退为 id 字面量时为警告级"疑似引用拼写错误"；未登记的 `event` 分组回退为签名未知的引用，不产生问题条目。由需装配层显式接线的可选规则（`SpawnSummonOnlyCreatureRule`/`DisplayMapCoverageRule` 等，见第 5.7.6 节）产出的问题额外标注"本条来自可选规则"。

#### 5.7.3 覆盖诊断

多根合并产生的 `override: true`/`final: true` 行为（见 04 第 4 节 2026-09-06 修订）不是错误，而是一类**信息级诊断**，单独列在问题面板的"覆盖诊断"分类下：

- 某记录被后层 `override: true` 覆盖：显示"框架层原始版本 vs 游戏层覆盖版本"的并排字段差异对比。
- 某记录声明 `final: true` 且被后层尝试覆盖：显示为阻断错误（04 定义为仍判定阻断），提示"该记录禁止被覆盖，请改用其它 id 新增而非覆盖同名记录"。
- 单根场景（该表本次未跨根合并）出现 `override`/`final` 字段为真值：显示为警告"该字段仅在跨根同主键重叠时生效，当前单根场景下已被忽略"，对应 04 第 4 节该行为定义。

#### 5.7.4 引用图（引用了谁 / 被谁引用）

- 检视区"引用面板"（第 5.3.5 节）对当前选中记录展示两个列表：**引用了谁**（本记录全部 `Reference`/`Id`（识别为引用字面量）/`Expr` 中 id 字面量指向的目标，逐条可点击跳转）与**被谁引用**（反向索引，扫描全部已加载记录中指向本记录的引用字段，逐条可点击跳转）。
- **删除影响分析对话框**（第 5.4.3 节"删除"操作触发）：复用同一份反向索引，列出"被谁引用"的完整清单，按所属表分组，用户可展开查看具体字段路径。
- **孤儿视图**：本地化编辑器（5.5.8）与通用表编辑器筛选行（"孤儿"复选框，第 5.3.3 节）共用同一份反向索引数据源，展示"没有被任何已知入口引用"的记录（对应 04 第 5 节"孤儿记录检测"，警告级，不阻断，便于清理）。

#### 5.7.5 schema 迁移

打开工程时若检测到某表记录的 `schema_version` 低于核心库 `TableSchema.CurrentSchemaVersion`，状态栏与问题面板同时提示"N 张表待迁移"；用户在"校验"菜单点"执行迁移"，弹出预览对话框逐表展示迁移前后的字段差异（新增字段的默认值、被拆分/合并的字段），确认后按 `TableSchema.Migrations` 声明的迁移链顺序执行（04 第 3 节"迁移链只增不减"），执行完成后记录的 `schema_version` 写为当前版本、`migrated_from` 记为原始版本号，随后自动触发一次全量校验确认迁移未引入新问题。

#### 5.7.6 校验覆盖矩阵与可选规则装配

对应 04 第 5.1 节"校验覆盖矩阵"：不是所有声明为引用语义的字段/规则都随第 4.4 节"校验装配入口"一次性自动注册，部分需要装配层显式接线才生效；基础套件装配校验器时必须调用第 4.4 节的校验装配入口并与 `toolchain/validator` 走相同的接线方式，避免"编辑器全绿但门禁报错"的割裂：

| 规则/字段 | 默认注册情况 | 编辑器行为 |
|---|---|---|
| 常规按模块自动注册的规则（`LootContentValidationRule`/`EconomyContentValidationRule`/`QuestContentValidationRule` 等，见 04 §5.1） | 随校验装配入口一次性注册齐 L0～L5 | 基础套件进程内引用同一个入口，随之自动生效，无需额外配置 |
| `SpawnSummonOnlyCreatureRule`（校验 `spawn.table.content_ref` 指向的生物模板不是"仅供召唤"） | 默认不注册（校验装配入口的 `CreatureTemplateQuery` 参数默认为 `null`，见第 4.4 节） | 游戏侧需按第 6.1 节"校验来源声明"扩展点提供 `ICreatureTemplateQuery` 才启用；未接线时"校验设置"面板将该规则显示为"未启用"，而不是静默跳过 |
| `DisplayMapCoverageRule`（校验 `display` 域引用集合中的逻辑 id 必须在 `display.map` 有对应行） | 默认不注册（校验装配入口的 `DisplayMapSources` 参数默认为 `null`） | 游戏侧需经第 6.1 节"校验来源声明"扩展点声明"哪些内容表参与外形域覆盖检查"，与 `toolchain/validator` 的调用方接线来源保持一致；未声明时同样显示"未启用" |
| `arch.class.power_types`/`skill_book_ref`、`arch.race.passive_auras` | 仅做 id 格式校验（`FieldKind.IdList`/`FieldKind.Id`），不做跨表存在性检查 | 问题面板不会为这三个字段产出"引用完整性"类问题（格式合法即通过），相关字段的引用选择器悬停提示标注"本字段仅做格式校验，不做存在性检查（04 §5.1）" |

`FailOnUnknownTable`/`Strictness` 等装配选项，基础套件"校验设置"面板必须与 `toolchain/validator` 保持同一份默认值来源（均经第 4.4 节校验装配入口获取）；由以上可选规则产出的问题在问题面板额外标注"本条来自可选规则"（见第 5.7.2 节）。

### 5.8 数值沙盘（预览与模拟）

数值沙盘全部基于框架核心库 + 无头适配层（`Adapters.Stub`，第 4.3 节）运行，不依赖引擎、不依赖网络；种子可复现（同种子同输入必然同输出，对应确定性拍板决策 3），是编辑器区别于"纯表格编辑工具"的核心差异化能力。沙盘以独立标签页形式在文档区打开（"工具"菜单"数值沙盘"或各专项编辑器内的快捷入口）。

| 沙盘 | 输入 | 输出 | 依据 |
|---|---|---|---|
| 伤害/治疗结算器 | 施法者模板、目标模板、技能/效果、（可选）种子 | 分步结算过程（判定→基础值→暴击→施法者乘区→减免→目标乘区→免疫吸收→落地）与最终数值、期望 DPS | 06 第 4.1 节结算管线固定步骤；实现经 `CombatOptions.ResolveTrace`（第 4.1 节契约面"无头适配层"行）拿到分步明细，见第 5.5.2 节"右侧结算预览" |
| 掉落模拟 | 掉落表、次数、种子 | 每件物品出现次数/概率/平均数量/期望价值 | 08 第 1 节 `LootHost.roll` |
| 经验估算 | 等级曲线、经验来源假设 | 达到目标等级所需击杀数/时长估算 | 见第 5.5.5 节 |
| 生物属性成长 | 生物模板、成长曲线、tier 分档倍率 | 等级 1..N 属性表格与折线图 | 见第 5.5.1 节 |
| 简易战斗回放（可选） | 两个生物模板、时长（N 秒或 N 回合）、种子 | 战斗日志（逐条 Combat Log 风格事件文本）与胜率统计（多次重复跑取胜率，若跑多次） | 06 第 8 节事件词汇表、结算管线 |

**简易战斗回放细节**：两套模板互相攻击直到一方死亡或达到时长上限，输出格式对齐 06 第 8 节"Combat Log 风格"事件词汇表（如 `combat.damage_dealt`、`aura.applied`、`unit.died` 逐条按时间顺序列出，附带触发该事件的字段值）；若时间模型为离散（回合制），日志按"回合 N：行动者 X 使用 Y"分组呈现；若为连续，按"第 N 秒"分组。回放结果窗口提供"导出为文本"按钮，便于策划贴到评审文档里讨论平衡性问题（导出为本地文本文件，见第 8 章不涉及云上传）。此前落地总量只对应最终 `combat.damage_dealt`/`combat.heal_done` 事件字段，同样一笔命中的判定/减免中间过程不可见；`CombatOptions.ResolveTrace` 接入后，回放沙盘可选展开某一条 Combat Log 事件对应的分步明细（与右侧结算预览同一份数据来源），不必额外重算。

游戏侧可经第 6.1 节"沙盘预设"扩展点新增本清单之外的游戏专属沙盘（如某游戏特有的经济系统模拟器），必须使用无头适配层跑逻辑，不允许沙盘内直接读写磁盘数据文件（第 6.1 节约束）。

### 5.10 版本控制与协作

#### 5.10.1 git 状态显示

底部面板区"git 变更"子面板（第 5.3.6 节）列出当前工程数据根内相对 git `HEAD` 的文件级改动（新增/修改/删除三色图标），实时随保存动作刷新；状态栏（第 5.3.7 节）显示当前分支名与脏文件计数。

#### 5.10.2 变更文件列表与 diff 预览

点击"git 变更"面板中的任一文件，右侧弹出并排 diff 预览（旧内容 | 新内容，逐行高亮增删），diff 渲染基于文本行比较（因为保存动作保证稳定字段顺序，diff 天然聚焦在真正改动的字段行，见第 5.4.5 节）；面板提供"暂存该文件"/"撤销该文件改动（还原为 `HEAD` 版本）"两个操作，其余 git 操作（提交、拉取、推送、分支管理）引导用户使用外部专业 git 工具或命令行完成，编辑器不重复实现完整 git 客户端（第 2.3 节范围外声明）。

#### 5.10.3 提交前自动校验

对应仓库既有 `.githooks/pre-commit` 的快速门禁思想：编辑器"校验"菜单提供"提交前检查"命令，一键跑一次全量校验（等价 `validate_data.py` 两道校验）并汇总结果；若配置了自动模式（第 5.12 节设置项），编辑器检测到用户即将通过其内置的"暂存"操作提交时会先自动跑一次该检查，报错时弹出确认框"仍有 N 个错误，是否继续提交"，默认按钮为"取消"。

#### 5.10.4 冲突时的记录级合并辅助

当 git 报告某数据表文件存在合并冲突（例如 pull 时与远端改动冲突）时，编辑器提供"记录级合并"辅助视图：读取冲突文件的双方版本（`--ours`/`--theirs`，经外部 git 命令获取原始文本），按主键对比出"仅本地改""仅远端改""双方都改"三类记录，双方都改的记录并排展示字段级差异，用户逐条选择"用本地"/"用远端"/"手动编辑合并"，全部记录确认后拼装出合并结果并写回文件，供用户在 git 里标记该文件为已解决冲突；此辅助视图不自动执行 git 命令本身（`add`/`commit` 等），只负责生成正确的合并后文件内容。

### 5.11 运行联调

#### 5.11.1 配置游戏可执行文件/Unity 工程路径

"运行"菜单"配置联调目标"：选择该游戏的 Unity 工程路径（用于一键在编辑器内启动 Unity 编辑器打开该工程）或独立版可执行文件路径（用于一键启动打包后的游戏）；两者均可配置，互不冲突（开发阶段常用 Unity 工程内运行，验收阶段用独立版可执行文件运行）。

#### 5.11.2 一键运行

"运行"菜单"运行▶"（或工具栏按钮）按已配置的目标启动：若目标是 Unity 工程，拉起本机 Unity Editor 以命令行参数打开该工程并进入 Play 模式（需要该工程已同步过最新的 `data/<game>/`，编辑器保存动作已保证这一点）；若目标是独立版可执行文件，直接启动该进程；启动日志汇入"输出"面板。

#### 5.11.3 保存触发热重载

保存动作完成后，若联调面板检测到目标游戏进程正以**开发期构建**运行（编辑器与目标进程之间通过本地约定的开发期热重载通道通信，具体传输机制由第 4.6 节"开发期热重载标准实现"落在 `games/_template` 里的实现约定），编辑器发出一次针对该表所属 domain 的 reload 请求；成功回执后"输出"面板打印"已触发 `<domain>` 热重载"。

**前提与限制（必须在界面上明确提示，避免用户误判"为什么没生效"）**：

- 仅对开发期构建有效，发布构建默认关闭热重载通道（对应第 4.6 节"仅限编辑器内构建"）。
- 结构性改动（新增字段、改变字段类型、`schema_version` 提升）仍需要重启游戏进程才能生效，热重载只对"同结构下的数值/内容变化"生效；编辑器保存后若判断本次改动可能涉及结构变化（如触发了迁移），主动提示"本次改动建议重启联调目标"而不是尝试热重载。

#### 5.11.4 从游戏日志反查编辑器记录

联调运行时，编辑器订阅目标进程输出的日志流（若目标提供，默认约定读取标准输出/标准错误或指定日志文件路径，具体接入方式属实现细节）；日志文本中出现符合 id 格式（`^[a-z][a-z0-9_]*(\.[a-z0-9_]+)+$`）的片段时，"输出"面板对该片段做超链接高亮，点击直接在编辑器内跳转打开对应记录，便于"游戏里报了个奇怪的 `skill.xxx` 找不到"这类问题的快速定位。

#### 5.11.5 外部工具调用的编码约定

编辑器调用 `toolchain/` 下 Python 脚本（`validate_data.py`/`import_assets.py` 等，见第 5.7.1、5.5.9 节）与 `get_framework.ps1` 一类 PowerShell 脚本（游戏侧升级框架，见用户故事 5）时统一遵守以下约定，保证中文输出/中文路径在 Windows 非 UTF-8 默认代码页的控制台环境下不崩溃、不乱码（见 `toolchain/README.md`"控制台编码"/"`.ps1` 脚本源码编码"两节）：

- **Python 子进程**：以 UTF-8 解码 stdout/stderr；额外设置环境变量 `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8` 作为双保险——脚本自身已在 `main()` 里调用 `toolchain/_console.py` 的 `ensure_utf8_stdio()`，编辑器侧的环境变量是第二层兜底，不依赖"脚本没有漏调用这一前提"。
- **PowerShell 子进程**：用 `powershell -NoProfile -ExecutionPolicy Bypass -File <script>` 调用，不依赖用户本机的全局执行策略设置；被调用的 `.ps1` 脚本源码本身须带 UTF-8 BOM（无 BOM 时 Windows PowerShell 5.1 在非 UTF-8 控制台代码页下会把中文注释误读为其它字符导致解析错误，见 `toolchain/README.md` 判断记录），随框架分发的脚本副本已保证这一点，编辑器不需要额外处理。

外部工具调用日志（"输出"面板，见第 5.3.6 节）与本节约定处理后的输出内容保证一致，不因编码问题丢字符或整段乱码。

## 6. 编辑器项目：插件 API 与模板工程

第 5 章的基础套件只提供通用能力；游戏专属的一切（校验规则接入、专属表单、专属向导、品牌与命名、沙盘预设）都通过本章定义的正式契约接入，不允许游戏侧直接改动基础套件源码——这是编辑器项目对外的**正式契约**，兼容性与基础套件自身版本号同一套语义化版本承诺（第 6.6 节）。

### 6.1 五类扩展点接口表

在 v1.1 旧"插件机制"（四类扩展点）基础上新增第五类"校验来源声明"（v2 新增，对应第 5.7.6 节"可选规则装配"需要游戏侧提供的接线来源）：

| 扩展点 | 用途 | 接口契约（**默认方案，可调整**：具体命名留待实现阶段与基础套件代码结构对齐） | 约束 |
|---|---|---|---|
| 专项编辑器插件 | 为某张/某组表提供更定制的界面（类似第 5.5 节九个专项编辑器的编写方式） | `ISpecializedEditorPlugin { string DisplayName; IReadOnlyList<string> CoveredTables; IEditorPanel CreatePanel(IEditorHost host); }` | 必须通过核心库 `DataRegistry` 读写记录，不允许绕过其校验直接操作文件 |
| 字段控件插件 | 为特定 `FieldKind` 或特定字段（按"表名.字段路径"匹配，覆盖默认控件）提供自定义控件渲染 | `IFieldControlPlugin { bool Matches(string table, string fieldPath, FieldSchema schema); IFieldControl CreateControl(FieldEditContext ctx); }` | 控件只做展示与编辑交互，字段值的读写仍经统一的记录模型 API |
| 沙盘预设插件 | 新增一种数值预览/模拟面板（第 5.8 节之外的自定义沙盘） | `ISandboxPlugin { string DisplayName; ISandboxPanel CreatePanel(IHeadlessAdapterHost host); }` | 必须使用无头适配层（第 4.3 节）跑逻辑，不允许沙盘内直接读写磁盘数据文件 |
| 导入器插件 | 新增一种批量导入格式（CSV 之外，如 Excel、专有格式） | `IImporterPlugin { string DisplayName; string[] SupportedExtensions; ImportPreview Preview(Stream input); ImportResult Apply(ImportPreview preview); }` | 导入结果必须经过与手工编辑相同的字段级/表级校验，不允许跳过校验直接写盘 |
| 校验来源声明（v2 新增） | 为需装配层显式接线的可选规则（`SpawnSummonOnlyCreatureRule`/`DisplayMapCoverageRule` 等，第 5.7.6 节）提供来源实现 | `IValidationSourcesPlugin { ICreatureTemplateQuery? CreatureTemplateQuery; DisplayMapCoverageSources? DisplayMapSources; }` | 提供的实现必须与游戏侧运行时装配根（`GameBootstrap.cs`）用的是同一份数据源，不允许编辑器另建一份影子数据 |

### 6.2 加载游戏程序集获取游戏侧 IValidationRule

游戏专属的校验判断（如超出五类扩展点覆盖范围的复杂业务规则）允许以标准 `IValidationRule` 实现的形式存在于游戏自己的程序集里；编辑器实例启动时按 `editor.config.json`（第 6.5 节）`gamePluginAssemblies` 字段列出的程序集路径加载，反射扫描其中实现 `IValidationRule`/上述五个插件接口的公开类型并注册。加载失败（程序集缺失、类型初始化异常）按第 6.3 节"隔离与失败处理"处理，不阻断编辑器启动。这条路径与第 4.4 节"校验装配入口"是互补关系：入口负责框架内置规则的统一装配，本节负责游戏侧规则的动态加载，两者产出的规则集合在装配阶段合并后一并跑校验。

### 6.3 插件发现与生命周期、隔离与失败处理

- **插件目录**：`<game>/editor/plugins/<插件名>/`，每个插件是独立目录，含清单文件 `plugin.json`（字段：`name`/`type`（五类扩展点之一）/`entryAssembly`/`minEditorSdkVersion`/`maxEditorSdkVersion`）与实现程序集；编辑器实例启动时扫描该目录加载。
- **生命周期**：编辑器启动 → 扫描 `plugins/` 目录 → 逐个读取 `plugin.json` → 校验 `minEditorSdkVersion`/`maxEditorSdkVersion` 是否覆盖当前编辑器项目版本 → 加载程序集 → 反射实例化声明的扩展点类型 → 注册进对应扩展点注册表（专项编辑器出现在导航区"专项编辑器"Tab、字段控件按匹配规则参与控件工厂决议、沙盘出现在"工具"菜单、导入器出现在导入弹窗格式下拉、校验来源汇入第 6.2 节装配流程）。
- **隔离与失败处理**：单个插件加载失败（清单格式错误、版本不兼容、程序集加载异常、构造函数抛异常）只影响该插件本身，记录到"输出"面板一条错误日志并在"工程"菜单"插件"子菜单里标注该插件为"加载失败"，其余插件与基础套件本身正常工作，**不拖垮整个编辑器进程**（对应第 3.4 节游戏项目工作项"游戏专属代码"里"插件异常不拖垮套件"这一硬约束）；插件运行期抛出的未捕获异常同样只使该插件对应的面板/控件显示"插件异常"占位，不传播到编辑器进程其它部分。
- **不允许绕过核心库校验**：与 v1.1 旧插件机制约束一致——全部五类扩展点都必须通过核心库 `DataRegistry` 读写记录，不允许插件直接操作磁盘文件或绕过字段级/表级校验，这是插件机制的硬约束（对应第 1.2 节"编辑器只编辑内容，不新增原语"的产品定位，插件也不例外）。

### 6.4 编辑器模板工程内容清单

编辑器项目产出的编辑器模板是一个最小可运行工程，供每款游戏复制到 `<game>/editor/` 并按第 7.1 节改名接入。内容清单：

| 内容 | 说明 |
|---|---|
| 对基础套件的引用 | 按编辑器项目自己的分发形态引用基础套件类库（**默认方案，可调整**：NuGet 包或直接 DLL 引用，取决于第 9.1 节技术选型的最终落地） |
| 对框架的引用 | `get_framework.ps1` 锁定的框架发布产物引用（`editor.lock`，第 3.3、7.2 节），与游戏工程共用同一份 `ws-game.lock` 判定的框架版本 |
| `editor.config.json` 模板 | 空白/示例配置，第 6.5 节字段契约表的全部字段均给出占位值或注释说明（第 11 章附录 G 给出完整示例） |

| 构建与打包脚本 | 编译编辑器实例可执行文件的脚本（**默认方案，可调整**：具体命令与 `games/_template` 的 `validate.ps1` 同一惯例，随游戏 CI 调用） |
| 冒烟测试 | 最小验收脚本：用 `data/_sample` + `assets/_sample`（框架自带验收数据集，第 10 章）打开工程、跑一次全量校验、加载全部专项编辑器面板不抛异常 |
| `editor.lock` 模板 | 空白锁文件，首次运行编辑器模板自带的初始化脚本时写入实际锁定的编辑器项目版本 |

### 6.5 `editor.config.json` 字段契约表

编辑器实例的游戏专属配置文件，位于 `<game>/editor/editor.config.json`，随游戏仓库入库（团队共享配置）。字段契约（**默认方案，可调整**：具体字段名与分组留待实现阶段最终定稿，完整示例见附录 G）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `dataRoot` | String | 游戏层数据根相对路径，通常为 `../data/<game>` |
| `assetsRoot` | String | 游戏层资产根相对路径，通常为 `../assets/<game>`；验收/演示场景可指向 `assets/_sample` |
| `resourceLayoutOverride` | String? | 覆盖默认 `toolchain/resource_layout_map.json` 的路径，未提供时使用框架默认布局 |
| `locales` | Array\<String\> | 本游戏启用的语言列表（对应 `l10n.locale` 表登记内容，供本地化编辑器矩阵列头使用） |
| `flavor` | Object | 口味项集合，字段与 `games/_template/Runtime/GameOptions.cs` 的口味配置项同名对应，至少含 `timeModel`（`continuous`\|`discrete`，决定编辑器全局时间单位显示） |
| `enabledSpecializedEditors` | Array\<String\> | 启用的专项编辑器 id 列表（第 5.5 节九个固定 id + 第 6.1 节插件声明的游戏专属 id），未列出的专项编辑器不出现在导航区"专项编辑器"Tab（但对应表仍可从"按层/域/表"Tab 用通用编辑器打开） |
| `sandboxDefaults.casterTemplateId` / `sandboxDefaults.targetTemplateId` | Id | 数值沙盘（第 5.8 节）结算预览默认选中的施法者/目标模板，未配置时沙盘面板要求用户每次手选 |
| `git.repoRoot` | String? | git 仓库根相对路径，未提供时按 `dataRoot` 向上查找 `.git` 目录自动探测 |
| `run.unityProjectPath` / `run.executablePath` | String? | 第 5.11.1 节联调目标路径，两者均可留空（用户在编辑器内配置后写回本文件或写回 `workspace.json`，具体落点**默认方案，可调整**） |
| `run.externalToolPaths.pythonExecutable` | String? | 未提供时使用系统 `PATH` 里的 `python` |
| `gamePluginAssemblies` | Array\<String\> | 第 6.2 节游戏专属程序集路径列表 |

### 6.6 套件的版本、兼容矩阵测试与发布

- **自己的语义化版本**：编辑器项目维护独立于框架的语义化版本号（首个基线号留待实现立项时拍板，本文档不预设），变更记录、破坏兼容判定（新增/移除扩展点接口成员、`editor.config.json` 字段契约变更）均按标准语义化版本规则：破坏兼容升 MAJOR，新增能力升 MINOR，修复升 PATCH。
- **Release 附件**：编辑器项目每次发布产出基础套件类库、编辑器模板工程压缩包两个附件（**默认方案，可调整**：具体附件命名与打包方式留待实现阶段与编辑器项目自己的构建脚本对齐，参考 ws-game 的 `dist/<ver>/` + `ws-game-<ver>.zip` 惯例）。
- **可选私服包 `com.gamefoundation.editor-sdk`**：与框架既有三个私服包（第 9.1 节引用）并列的第四类分发方式，供已在用私服通道的游戏团队按版本号依赖到基础套件；是否落地留待实现阶段按团队实际分发习惯决定（对应第 3.4 节编辑器项目工作项⑤）。
- **兼容矩阵测试**：每次发布前，至少覆盖当前框架 MAJOR 内两个 MINOR 版本（如同时对框架 `1.11.0` 与 `1.12.0` 跑一遍第 10 章 S1～S5 验收数据集）验证基础套件行为一致，兼容矩阵结果记入编辑器项目自己的变更记录，供游戏侧升级前查阅（对应第 3.3 节"版本与兼容矩阵"、用户故事 5）。

## 7. 游戏项目：编辑器接入指南

本章与 [games/_template/README.md](../../games/_template/README.md)"复制为新游戏：改哪几处"同一模式：给出"复制模板 → 改名 → 锁版本 → 填配置 → 写游戏专属代码 → 接入 CI → 团队日常怎么用"的具体步骤，供每款游戏接入编辑器时照做。

### 7.1 复制模板与改名

1. 从编辑器项目取得目标版本的编辑器模板发布产物（第 6.4、6.6 节），复制到游戏仓库 `<game>/editor/`。
2. 改名：模板内的程序集/命名空间从占位名改为 `Editor.<Game>`（`<Game>` 替换为具体游戏代号），与 `games/_template/README.md`"复制为新游戏：改哪几处"第 2 步"四个 asmdef 改名"同一模式——若编辑器实现层面同样采用类似的工程/程序集拆分（**默认方案，可调整**：具体是否为 Unity 包形态取决于第 9 章技术选型的最终落地，本步骤的"改名"动作本身不依赖该选型结论）。
3. 对应 [13_新游戏接入指南.md](../../architecture/13_新游戏接入指南.md) 第 4.7 节要求补的一步"复制编辑器模板到游戏仓库"：作为立项步骤的可选项，不强制每款游戏立项当天就建编辑器，可在需要图形化编辑内容时再执行本章步骤。

### 7.2 锁定版本

- **共用 `ws-game.lock`**：编辑器实例不单独锁定框架版本，直接读取游戏工程根已有的 `ws-game.lock`（该文件本就服务于游戏运行时对框架的引用，见 [games/_template/README.md](../../games/_template/README.md) 第 5 步），保证"编辑器看到的表结构与校验规则就是该游戏在用的那一份"由构造保证（对应 [ADR-0018](../../architecture/adr/0018-编辑器随游戏走与框架为此提供的交付物.md) 决策 1 的正面后果）。
- **锁定编辑器项目版本**：在 `<game>/editor/editor.lock` 写入当前锁定的编辑器项目版本号，格式与 `ws-game.lock` 同构（`version`/`source.channel`/来源哈希或注册表来源字段，见第 3.3 节）；首次接入时由编辑器模板自带的初始化脚本按第 7.1 节取得的发布产物版本号写入。
- 两个锁文件均入库，团队所有成员打开编辑器实例时读到同一份版本判定（第 5.2.1 节向导第 4、5 步）。

### 7.3 填 `editor.config.json`

按第 6.5 节字段契约表逐项填写：`dataRoot`/`assetsRoot` 指向该游戏实际的 `data/<game>`/`assets/<game>`；`locales` 填该游戏实际启用的语言列表；`flavor.timeModel` 与该游戏 `found.time_model` 表的登记保持一致（两处不一致时编辑器第 5.5.10 节"其余表"小增强会在 `found.time_model` 表单顶部提示核对）；`enabledSpecializedEditors` 按该游戏实际用到的内容域勾选（如一款没有任务系统的游戏可以不启用"任务与对话编辑器"）；`gamePluginAssemblies` 填第 7.4 节游戏专属程序集的产出路径。

### 7.4 游戏专属代码四类

1. **校验规则接入与校验来源声明**：游戏侧实现 `IValidationSourcesPlugin`（第 6.1 节），为 `SpawnSummonOnlyCreatureRule` 提供 `ICreatureTemplateQuery`（通常复用游戏运行时装配根 `GameBootstrap.cs` 已有的 `CreatureFactory` 查询能力）、为 `DisplayMapCoverageRule` 提供 `DisplayMapCoverageSources`（声明该游戏参与外形域覆盖检查的具体内容表集合）；游戏专属的复杂业务校验规则实现 `IValidationRule` 并放在第 6.2 节"游戏程序集"里。
2. **游戏自定义子结构的专用表单**：若该游戏的内容需要框架标准 60 余张表之外的复合字段专用编辑体验（如某游戏在 `item.template` 之外自定义了词条组合表），实现 `IFieldControlPlugin`（第 6.1 节）覆盖对应"表名.字段路径"。
3. **专属向导**：实现 `ISpecializedEditorPlugin` 或直接扩展第 5.6 节向导框架（**默认方案，可调整**：具体扩展点形态与第 6.1 节"专项编辑器插件"是否共用同一套注册机制留待实现阶段对齐）。
4. **品牌与命名**：编辑器实例窗口标题、图标、关于对话框等品牌元素随游戏改名（第 7.1 节步骤 2 的一部分），不涉及扩展点契约。
5. **沙盘预设**：`editor.config.json` 的 `sandboxDefaults`（第 6.5 节）配好该游戏最常用的施法者/目标模板；如需框架标准五种沙盘（第 5.8 节）之外的游戏专属沙盘，实现 `ISandboxPlugin`（第 6.1 节）。

### 7.5 构建与随游戏发布、纳入游戏 CI

编辑器实例随第 6.4 节模板自带的构建脚本编译，产出物随该游戏自己的版本发布节奏走（不单独发版，对应第 3.2 节职责表"版本"列）；纳入游戏 CI 的检查项（**默认方案，可调整**，参照 `games/_template` 的 `validate.ps1` 与本仓库 `check.ps1 -Quick` 惯例给出建议子集）：

| CI 检查项 | 内容 |
|---|---|
| 编辑器实例编译通过 | 第 6.4 节构建脚本产出 0 编译错误 |
| 冒烟测试通过 | 第 6.4 节冒烟测试（用真实游戏数据替换 `data/_sample`）跑通：打开工程、全量校验、专项编辑器面板加载不抛异常 |
| 数据全量校验 | `python toolchain/validate_data.py --data-root <game>/data`（游戏已有的数据校验步骤，本身不新增，只是编辑器改动可能间接触发数据变化时复用同一步骤把关） |
| 两个锁文件一致性 | `ws-game.lock`/`editor.lock` 记录的版本号与实际引用的发布产物一致，防止手改锁文件后未同步实际引用 |

### 7.6 升级流程（对应用户故事 5）

1. **先查 `CHANGELOG.md` 迁移说明**：框架升级时查阅框架 `CHANGELOG.md` 对应版本区间标注"编辑器相关契约"的条目（第 4.7 节）；编辑器项目升级时查阅编辑器项目自己变更记录里的兼容矩阵（第 6.6 节）与破坏性变更说明。
2. **再跑 `validate_data`**：`python toolchain/validate_data.py --data-root <game>/data`（框架版本升级后的数据校验，游戏既有步骤）。
3. **再做编辑器冒烟**：第 6.4/7.5 节冒烟测试，确认新版本框架/编辑器项目下编辑器实例仍能正常打开工程、跑全量校验、加载全部专项编辑器面板。
4. 三步顺序不能颠倒（对应第 3.3 节"升级顺序"的具体化：迁移说明在先，是因为后两步的"预期结果"依赖迁移说明里标注的已知行为变化）。

### 7.7 团队流程

- **策划**：用编辑器改 `data/<game>` 下的内容，日常操作走第 5 章基础套件功能；改动通过编辑器内 git 感知面板（第 5.10.1 节）确认改动范围后提交，或用外部 git 工具提交；`.githooks/pre-commit` 走该游戏自己的 pre-commit 配置（若已接入，通常复用第 5.10.3 节"提交前自动校验"触发的同一次全量校验逻辑）。
- **程序**：维护 `<game>/editor/` 目录本身——第 7.4 节游戏专属代码的编写与维护、第 7.2 节两个锁文件的升级、第 7.5 节 CI 配置；程序不代替策划日常改数据，但负责编辑器实例本身"能不能打开、校验准不准"这类基础设施问题。
- **协作边界**：与第 5.10 节"版本控制与协作"整体一致——编辑器不做账号体系、不做多人实时协作，团队各自用编辑器改自己负责的表，靠 git 提交、review、合并。

### 7.8 游戏接入检查表

| 检查项 | 判定标准 |
|---|---|
| 编辑器实例已复制并改名 | `<game>/editor/` 存在，程序集/命名空间已改为 `Editor.<Game>`，不再包含模板占位名 |
| `ws-game.lock` 共用 | `<game>/editor/` 未额外维护一份框架版本锁定，直接读取游戏工程根 `ws-game.lock` |
| `editor.lock` 已写入 | 记录的编辑器项目版本号与实际引用的发布产物一致 |
| `editor.config.json` 已填齐 | 第 6.5 节字段契约表全部必填字段（`dataRoot`/`assetsRoot`/`locales`/`flavor.timeModel`）非占位值 |
| 游戏专属校验来源已接入 | 若该游戏用到 `spawn.table`/`display.map` 覆盖检查，`IValidationSourcesPlugin`（第 6.1 节）已实现并在"校验设置"面板显示"已启用"而非"未启用" |
| 冒烟测试通过 | 第 6.4/7.5 节冒烟测试用该游戏真实数据跑通 |
| 纳入游戏 CI | 第 7.5 节 CI 检查项清单已接入该游戏的持续集成流程 |
| 团队流程已确认 | 第 7.7 节策划/程序职责分工已在该游戏团队内部达成一致（非机器可判定项，人工确认） |

## 8. 非功能需求

以下指标哪些是基础套件承诺、哪些需要由具体游戏的编辑器实例验证，逐项标注（v2 新增区分列，因为基础套件与游戏实例分属编辑器项目与游戏项目两个不同的验收责任方，见第 3.2 节职责表）。

### 8.1 性能指标

| 场景 | 目标 | 验收责任方 |
|---|---|---|
| 冷启动到主界面可交互 | ≤ 3 秒（不含首次打开工程的数据加载） | 基础套件承诺（第 6.6 节兼容矩阵测试的一部分） |
| 打开工程（框架层+游戏层两根合并加载） | 中等规模数据集（约 60 张表、单表数千行以内）≤ 5 秒 | 基础套件承诺；具体游戏数据规模超出"中等规模"时由该游戏的编辑器实例验证（第 7.8 节接入检查表） |
| 5 万行 `l10n.text` 网格滚动 | 虚拟化渲染，滚动帧率不低于 30fps，无明显掉帧卡顿 | 基础套件承诺 |
| 保存单张表（数千行内） | ≤ 1 秒 | 基础套件承诺 |
| 全量校验（中等规模数据集） | ≤ 10 秒（进程内跑；拉子进程跑对齐 `validate_data.py` 实际耗时，不额外设上限） | 基础套件承诺 |

### 8.2 可靠性

**崩溃恢复**：编辑器按第 5.12 节设置的间隔（默认 120 秒）自动把当前未保存的变更集快照写入 `<game>/editor/.gfeditor/autosave/`（不覆盖用户的正式保存文件）；异常退出后再次启动时检测到该目录存在快照，提示"检测到上次异常退出遗留的自动保存草稿，是否恢复"，用户可选择恢复、丢弃或先对比差异；正常退出（用户主动关闭且已无未保存改动，或已确认放弃改动）时清空该次会话对应的草稿文件。此能力由基础套件承诺。

### 8.3 可用性

- 键盘优先：全部高频操作有快捷键（见附录 A），网格视图/表单视图之间的字段导航支持 `Tab`/`Shift+Tab`/方向键。
- 无鼠标可完成主要流程：新增记录、填字段、保存、触发校验、切换标签均可纯键盘完成（命令面板 `Ctrl+K` 是无鼠标操作的核心入口）。
- 屏幕阅读器基本支持：控件具备可读的名称/角色/值（Name/Role/Value）语义标注，满足基本的辅助技术识别需求（不要求达到完整无障碍认证等级，作为基础可用性底线）。

此三项均由基础套件承诺；游戏侧经第 6 章插入的专属插件面板需自行保证同等可用性水平（第 7.8 节接入检查表未把这一项列为强制门槛，作为团队自查建议）。

### 8.4 兼容性

- 操作系统：Windows 10/11 x64。
- 分辨率：1080p 至 4K，含 125%/150%/200% 等常见 DPI 缩放档位（见第 5.3.8 节）。
- 最小窗口尺寸 `1280×800`（见第 5.3.8 节）。

由基础套件承诺；编辑器实例（含游戏专属插件面板）继承同一套兼容性约束，不单独测试。

### 8.5 安全

编辑器**不联网、不上传**任何数据（不含遥测、不含自动检查更新的默认开启项——若未来加入检查更新功能，须默认关闭并需用户显式开启）；全部数据读写限定在用户显式打开的工程目录、`<game>/editor/.gfeditor/` 子目录与用户显式指定的导入导出路径内。由基础套件承诺；游戏侧插件（第 6 章）同样不得联网或上传数据，游戏接入检查表（第 7.8 节）未把这一项列为机器可判定的强制门槛，作为代码评审要求。

### 8.6 子进程编码健壮性

编辑器调用外部工具子进程（`toolchain/` 下 Python 脚本、`get_framework.ps1` 一类 PowerShell 脚本）时统一按第 5.11.5 节"外部工具调用的编码约定"处理，保证在非 UTF-8 默认代码页的 Windows 控制台环境下不因中文输出/中文路径崩溃或产生乱码；这是"输出面板/问题面板展示的外部工具日志与执行结果始终可读、可信"这一可靠性底线的前提，纳入非功能需求而非仅作为实现细节，因为一旦编码处理缺失，第 5.7 章"全量校验"、第 5.5.9 节"调用 `import_assets.py`"等依赖子进程回显的功能会直接不可用。由基础套件承诺。

## 9. 技术选型建议

> 本章标注为**实现层面的建议，非架构结论**，可在实现立项时另出评估文档拍板，不影响 `architecture/` 目录下任何既有结论；本章面向编辑器项目的实现选型，不涉及框架仓库任何既有拍板。

### 9.1 桌面壳：WPF 与 Avalonia 对比

| 维度 | WPF（.NET 8） | Avalonia（.NET 8） |
|---|---|---|
| 平台范围 | 仅 Windows | 跨平台（本产品只需 Windows，此项非决定因素） |
| 与核心 DLL（.NET Standard 2.1）互操作 | 原生，无额外适配层 | 原生，无额外适配层 |
| 生态成熟度（数据网格、代码高亮控件） | 成熟（第三方控件库选择多，社区历史悠久） | 逐步成熟（部分控件需自行封装或用较新的第三方库） |
| 主题/深浅色支持 | 需要自行搭建资源字典体系 | 内置 Fluent 主题与浅深色切换支持较完善 |
| 团队现有经验（假设） | Windows 桌面团队通常更熟悉 | 需要一定学习曲线 |
| **建议** | **首选**（默认方案，可调整）：本产品明确只需 Windows，WPF 生态里的数据网格/代码编辑控件选型更直接，减少自研控件的工作量 | 若未来有跨平台需求（当前无）可重新评估 |

### 9.2 理由与备选（Web 壳 + 本地服务）对比

| 维度 | 桌面壳（WPF/Avalonia）直接引用核心 DLL | Web 壳（本地 HTTP 服务 + 浏览器/内嵌 WebView 前端） |
|---|---|---|
| 与核心库集成方式 | 进程内直接引用，无序列化开销 | 核心库跑在本地服务进程，前端通过 HTTP/WebSocket 调用，需要额外设计 API 协议与序列化 |
| 启动性能 | 更快（无需起服务进程 + 浏览器渲染进程） | 较慢（两个进程 + WebView 启动开销） |
| 离线可靠性（第 8.5 节"不联网"要求下的自洽性） | 天然离线，无端口占用/防火墙提示等困扰 | 本地服务仍可能触发系统防火墙首次提示，用户体验有干扰 |
| UI 生态（图表、代码高亮控件） | 需要选型桌面端专属控件库 | 可直接复用成熟的 Web 前端生态（图表库、代码编辑器组件更丰富） |
| **结论** | **选桌面壳**：第 8.5 节离线要求与启动性能优先级更高，UI 生态差距可通过桌面端成熟的第三方控件库弥补 | 仅在未来若需要"团队远程协作查看只读快照"一类场景时才重新评估 Web 壳路线 |

### 9.3 图表、代码编辑控件、文件监视、git 调用方式（默认方案，可调整）

| 能力 | 建议方案 |
|---|---|
| 图表（成长曲线、经验曲线、结算预览条形图） | 桌面端成熟图表库（如 OxyPlot 一类开源图表库），满足折线/柱状/进度条即可，不需要复杂交互式图表 |
| 代码/JSON 高亮编辑控件（源码视图、Expr 编辑器） | 桌面端成熟的代码编辑控件（如 AvalonEdit 一类），自行扩展语法高亮规则以支持 Expr 语法与 JSON |
| 文件监视（外部修改检测、资源存在性扫描） | 操作系统原生文件系统监视 API（.NET `FileSystemWatcher` 一类），叠加去抖动处理避免同一次外部改动触发多次刷新 |
| git 调用方式 | 拉起本机已安装的 `git` 命令行工具（子进程），解析其文本输出得到状态/diff；不内嵌完整 git 实现库，保持与用户本机 git 配置（凭据、hooks）行为一致 |
| 子进程调用编码 | Python 子进程以 UTF-8 解码 stdout/stderr，并设置 `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8` 环境变量作为双保险；PowerShell 子进程用 `-NoProfile -ExecutionPolicy Bypass -File` 调用，脚本源码保持 UTF-8 BOM（详见第 5.11.5 节"外部工具调用的编码约定"） |

### 9.4 与校验装配入口共享注册逻辑的方式

现状：`toolchain/validator`（.NET）的 `Program.cs` 并不自己枚举各层的表与规则，而是直接调用核心库已经存在的级联注册目录：`core/rules/assembly/RulesSchemaCatalog`（注册 L0 内置 + L1 五模块 + L2 四模块的 `TableSchema`/`IValidationRule`）→ `core/carriers/assembly/CarriersSchemaCatalog`（级联 `RulesSchemaCatalog` 后再补 L3）→ `core/gameplay/assembly/GameplaySchemaCatalog`（级联后再补 L4，`RegisterAll(IDataRegistry, Id? itemBudgetCurveId, ICreatureTemplateQuery? creatureTemplateQuery)`）→ `presentation/assembly/PresentationSchemaCatalog`（级联后再补 L5）；`toolchain/validator/Program.cs` 实际调用的正是最外层的 `PresentationSchemaCatalog.RegisterAll`，一次性注册齐全部 L0～L5 模块。

第 4.4 节"校验装配入口"是这条既有级联注册链之上再抽的一层：入口内部仍然调用同一套 `RulesSchemaCatalog`/`CarriersSchemaCatalog`/`GameplaySchemaCatalog`/`PresentationSchemaCatalog` 级联注册目录，只是把"调用汇总注册目录 + 可选规则接线参数（`ICreatureTemplateQuery`/`DisplayMapCoverageSources`）+ 装配选项（`FailOnUnknownTable`/`Strictness`）"这一步骤本身收敛为一个核心库内、`toolchain/validator` 与编辑器基础套件两个消费方共用的公开入口。编辑器项目建议直接调用这一个入口，而不是像 v1.1 旧版建议的那样自行引用 `PresentationSchemaCatalog` 之类的级联注册目录并重复一遍装配逻辑——这样"编辑器已知的表清单与校验规则"与"门禁用的校验器已知的表清单与校验规则"永远是同一份代码产出的同一份注册结果，不需要人工保持两处同步；对需要显式接线的可选规则，编辑器项目同样通过第 6.1 节"校验来源声明"扩展点获得游戏侧提供的来源实现，再一并传给这一个入口（第 5.7.6 节）。本节结论不影响 `architecture/` 的任何既有拍板。

### 9.5 打包与发布方式（配合第 6.6 节，默认方案，可调整）

编辑器项目维护自己的构建脚本，产出基础套件类库与编辑器模板两个 Release 附件，以及可选的私服包 `com.gamefoundation.editor-sdk`（第 6.6 节）；与框架既有三个私服包（`com.gamefoundation.adapter.unity`/`com.gamefoundation.framework-data`/`com.gamefoundation.toolchain`，见 [落地方案与分阶段计划.md](../../architecture/落地计划/落地方案与分阶段计划.md) 第 3.5.1 节）分属两个不同仓库的分发通道，互不干扰——编辑器项目自己的构建脚本不复用框架 `build.ps1` 的具体实现，但可以参考其"打包范围、`npm pack`/私服发布分离"的组织方式（**默认方案，可调整**，具体落地留待编辑器项目实现立项时另定）。是否落地 `com.gamefoundation.editor-sdk`、编辑器模板压缩包的具体内容边界，留待实现阶段按第 6.6 节结论对齐。

## 10. 里程碑与验收标准

v1.1 旧版 M1～M5 单一里程碑线是"编辑器随框架发布"假设下的产物，已随三层结构重排作废。v2 按第 3 章三层结构拆成三条验收线：**F 线**（ws-game 前置，框架侧交付契约与交付物）→ **S 线**（编辑器项目，基础套件与模板）→ **G 线**（首个游戏接入）。三线之间存在依赖：S 线部分条目依赖 F 线先完成对应交付物，G 线依赖 S 线已发布可用的编辑器项目版本。

|---|---|
| 数据即内容 | ADR-0004 拍板：游戏世界一切具体内容是结构化文本表里的行，运行时只认 id 与字段 |
| `DataRegistry` | L0 基础层暴露给全架构的唯一数据入口，见 04 第 4 节 |

| `FieldKind` | 字段类型标签枚举：`Bool`/`Int`/`Number`/`String`/`Id`/`IdList`/`Reference`/`TextKey`/`Expr`/`Enum`/`Vec2`/`Object`/`Array` |
| Expr | 全架构统一的条件表达式语言，九个宿主分组：`self`/`target`/`event`/`world`/`quest`/`player`/`combat`/`enemies`/`time` |
| `override`/`final` | 多根合并时的行级显式覆盖控制字段，见 04 第 4 节 2026-09-06 修订 |

| 无头适配层（`Adapters.Stub`） | ws-game 正式交付物：纯 .NET 实现的最小可用适配层，供脱离引擎的测试与数值沙盘使用，见第 4.3 节 |
| 确定性模拟 | 拍板决策 3：同种子同输入必然同输出，是数值沙盘"可复现"的基础 |
| 万物皆法术 | 拍板决策 1：任何"让世界发生变化"的动作都建模为 Skill（效果+光环+触发） |
| ws-game（框架） | 本仓库；对编辑器只承诺契约面，不承载编辑器代码，见第 3、4 章 |
| 编辑器项目 | 独立于框架仓库的消费方项目，产出基础套件与编辑器模板，见第 3、5、6 章 |
| 基础套件 | 编辑器项目产出的类库，第 5 章全部通用能力 |
| 编辑器模板 | 编辑器项目产出的最小可运行工程，见第 6.4 节 |
| 编辑器实例 | 某款游戏仓库里由编辑器模板复制而来的具体编辑器工程，见第 7 章 |
| 插件 | 游戏侧经五类扩展点接入编辑器实例的游戏专属扩展，见第 6.1～6.3 节 |
| 校验装配入口 | ws-game 核心库内的公开入口，把注册目录+可选规则接线+装配选项收敛为单一调用点，见第 4.4 节 |
