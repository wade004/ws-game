# 消费方反馈处理记录（读档触发脱战回满，2026-09-17）

> 本文档允许出现具体技术名（引擎/语言/框架/工具名），不受 `architecture/00～14` 与
> `architecture/adr/` 正文的禁用词约束（见仓库根 `CLAUDE.md`"硬性规则"）。记录下游游戏项目
> （接入方）反馈"存档读档后生命值被意外回满"的复现、根因、处理方式与验证结果。

**结论先行**：反馈属实，是回归缺陷（引入点早于反馈提出时间，此前潜伏未被察觉）。已在 main
当前代码（1.39.0 起点）复核确认仍然存在，已根治并补测试回归；全仓搜索同类"恢复路径调用了带
业务副作用的 setter"模式，未发现其它同类缺陷（见"排查范围"一节）。

处理方式：新增的公开成员是"新增默认接口方法 + 具体类型显式覆盖"，不删改任何既有公开签名。

## 复现

真实探针场景：某单位战斗中受伤至生命值 37（上限 100），存档写入
`player.vitals = {health: 37, in_combat: false}`；读档发生时运行期状态恰好仍是
`in_combat = true`（例如玩家在移动/战斗中触发了读档）。读档完成后，生命值不是存档写入的 37，
而是被回满成上限 100。

## 根因因果链

1. `core/gameplay/assembly/PlayerVitalsPersistable.cs`（`Load`）：先按存档 `powers` 字段用
   `IPowerHost.ModifyPower` 把当前值改写为存档值——`PowerHost` 内部 `Current` 在这一步已经
   正确变成 `37`。此时尚未触碰 `in_combat`。
2. 随后读存档 `in_combat` 字段（本例为 `false`），调用私有方法 `RestoreInCombat(false)`。
3. 生产装配路径 `_combat != null`：调用 `CombatHost.RestoreCombatState(unitId, false)`
   （`core/rules/combat/core/CombatHost.cs`）；旧两参构造函数兜底路径（`_combat == null`，源码
   兼容分支）则直接调用 `IPowerHost.SetInCombat(unitId, false)`——**两条路径最终都落到了同一个
   有副作用的方法上**。
4. `CombatHost.RestoreCombatState` 写入自身 `_inCombat[unitId] = false` 后，只要该单位存在于
   世界模拟中，就调用 `IPowerHost.SetInCombat(unitId, false)` 同步 `PowerHost`。该方法当时的
   判断记录明确写着"本方法本身不做这一步，只管赋值"——这个假设是**错误**的。
5. `PowerHost.SetInCombat`：读到 `wasInCombat`（读档前运行期真实值，`true`）；写入
   `state.InCombat = false`；因为发生了 `true → false` 转换，继续往下执行"脱战回满"逻辑——对
   `RefillOnLeaveCombat = true` 的资源类型（`arch.power.health`，框架默认自 v1.33.0/ADR-0031
   起即为 `true`）调用 `SetCurrentClamped(..., power.Max)`，把第 1 步刚恢复的 `37` 覆盖为
   `100`。

**根因一句话**：`IPowerHost.SetInCombat` 是唯一一个同时承担"设置进出战布尔状态"与
"`true→false` 时触发脱战回满业务副作用"两件事的公开方法；存档/回滚恢复场景把"运行期状态从
读档前的 `true` 变成存档快照的 `false`"这一单纯的赋值动作，误判成了一次真实的"战斗结束"。

**是否回归**：`CombatHost.RestoreCombatState` 由 commit `d2e95d0`（C11-RELOAD 根治，
2026-09-11）引入时该缺陷即已存在，但当时框架默认 `arch.power.health` 尚未启用
`refill_on_leave_combat`，缺陷潜伏不可见；`arch.power.health` 在 v1.33.0（ADR-0031）打开该
字段后，缺陷对"生命值"这一最常见资源变为默认可见。`v1.33.0..v1.39.0` 区间对
`PowerHost.cs`/`CombatHost.cs`/`PlayerVitalsPersistable.cs` 三个关键文件没有任何相关提交，
缺陷持续存在到 1.39.0（main HEAD）。

## 修复

新增 `IPowerHost.RestoreInCombat(Id unitId, bool inCombat)`（`core/numbers/power_set/
contracts/IPowerHost.cs`）——C#8 默认接口方法，ABI 只新增：

- 默认实现回落为调用 `SetInCombat`（保持除 `PowerHost` 外其它 `IPowerHost` 实现方——均为测试
  假类型——行为与修复前一致，不构成编译或行为破坏）。
- `core/numbers/power_set/core/PowerHost.cs` 显式覆盖为真正的纯赋值实现：只做
  `RequireUnit(unitId).InCombat = inCombat;` 一行，不遍历资源类型、不调用
  `SetCurrentClamped`、不触发回满、不发任何事件。

调用点改动：

- `core/rules/combat/core/CombatHost.cs`（`RestoreCombatState`）：`_powers.SetInCombat(...)`
  改为 `_powers.RestoreInCombat(...)`；同步更正此前"本方法本身不做这一步，只管赋值"这句在
  当时并不成立的判断记录。
- `core/gameplay/assembly/PlayerVitalsPersistable.cs`（私有方法 `RestoreInCombat`，
  `_combat == null` 兜底分支）：同款缺陷一并修，同样改调用 `PowerHost.RestoreInCombat`。

`SetInCombat` 本体逻辑未改动，"真实脱战仍回满"这条既定玩法语义不受影响。

## 排查范围：全仓搜索同类缺陷

按"`SetInCombat` 的所有调用方"与"`Restore*`/`Load*` 路径中调用的 `Set*`"两个方向排查：

- `SetInCombat` 的调用方：`CombatHost.NotifyCombatEvent`（真实进战，false→true，不构成本类
  缺陷条件）、`CombatHost.Update`（真实脱战延迟到期，true→false，是设计意图本身，不是缺陷）、
  以上两处 `RestoreCombatState`/`PlayerVitalsPersistable` 兜底分支（已修）。
- 各 `*Persistable.Load()` 内的 `Set*` 调用逐一核对是否存在"依赖此前状态分支、产生额外副作用"
  的写法：
  - `UnitPersistable.Load` → `IUnitAccess.SetPosition`：纯坐标写入 + 空间索引同步，无状态
    分支副作用，不是缺陷。
  - `RngStreamsPersistable.Load` → `IRngHost.SetStreamState`：纯替换或新建生成器，无副作用，
    不是缺陷。
  - `VendorStockPersistable.Load` → `EconomyHost.SetStock`：纯字段替换，不发事件，不是缺陷。
  - `CurrencyPersistable.Load` → `EconomyHost.SetBalance`：本仓库已有的"恢复态安全 setter"
    正面先例——设计上就是"读档等以快照为准场景，整体替换，不触发 `Add` 那条业务事件路径"
    （`EconomyHost.README.md` 已有判断记录明确区分），不是缺陷，反而是本次 `RestoreInCombat`
    修复所遵循的既有惯例参照。
  - `GameObjectHost.RestorePendingLoot`/`LootHost.RestoreDropped`：整体替换/归零重建，无分支
    副作用，不是缺陷。
  - `ProgressionHost.RestoreState`：本身就是独立于 `AddXp` 正常升级路径的专用恢复入口，发布的
    是独立的 `ProgressionRestoredEvent` 而非会触发下游"升级奖励"链路的 `LevelUpEvent`，是与本
    次 `RestoreInCombat` 同构的既有正面先例，不是缺陷。
- 未发现其它同类缺陷。
