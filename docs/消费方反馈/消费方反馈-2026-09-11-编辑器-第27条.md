## 现象

`ws-game-editor` 对正式装配的 `PresentationSchemaCatalog.FullExprSchema` 逐分组调用
`KnownKeys("target")`/`KnownKeys("self")` 等九个分组，全部返回空集合；但
`RulesExprSchema.Base.KnownKeys("self")` 单独调用能正确返回已登记 key 列表。编辑器侧据此做的
字段自动补全/清单展示功能对正式入口完全失效。

## 根因

`IExprSchema.KnownKeys(string)`/`IExprSchema.KnownGroups` 是 1.17.0（消费方反馈第三批第 18 条）
新增的带默认实现接口成员，默认实现恒返回空集合——这是刻意设计（保证新增成员不破坏既有实现方的
编译，见 `architecture/11_工程规范与测试.md` 第 7 节"默认实现"路线），只有 `ExprSchema` 本身
显式重写为返回真实已登记 key 的有序、确定性列表。

`PresentationSchemaCatalog.FullExprSchema` 实际是一条组合/包装链：

```
PresentationSchemaCatalog.FullExprSchema
  = GameplaySchemaCatalog.FullExprSchema
  = new CompositeExprSchema(
        QuestExprSchemaEntries.BuildParsingSchema(),   // = new EventGroupPermissiveSchema(内层 ExprSchema)
        RulesExprSchema.Base)                          // 内部持有 _known: ExprSchema
```

链上三种类型——`CompositeExprSchema`（并集转发多份 schema）、`RulesExprSchema`（委托给内部
`_known: ExprSchema`）、`QuestExprSchemaEntries` 内的 `EventGroupPermissiveSchema`（委托给内层
`ExprSchema` 再叠加 `event` 分组恒放行）——均只重写了 `TryGetSignature`，没有同步重写
`KnownKeys`/`KnownGroups`。三层委托链上任何一环没有转发，最终结果就是接口默认实现（空集合），
即使最底层的 `ExprSchema`/`RulesExprSchema._known` 各自持有真实、非空的已登记 key 集合。

额外发现：`core/foundation/data_registry/core/RecordExprSchema.cs`（`DataRegistry.Query(table,
predicateText)` 便捷重载用、把表字段登记为 `self.<field>` 的独立 `IExprSchema` 实现）同样只重写
`TryGetSignature`，不在上面的组合链上，但同一批遗漏。

## 处理

**根治四处组合/包装实现，均补齐显式转发（有序、去重、确定性）**：

1. `core/rules/expr_host/CompositeExprSchema.cs`：`KnownKeys(group)`/`KnownGroups` 按
   `_schemas` 数组顺序对每个成员 schema 调用同名成员，取并集（`SortedSet<string>`，
   `StringComparer.Ordinal`），不是"第一个命中即返回"的 `TryGetSignature` 语义——已知 key/分组
   清单需要"全部成员各自贡献结果的并集"。
2. `core/rules/expr_host/RulesExprSchema.cs`：`KnownKeys`/`KnownGroups` 直接转发给内部
   `_known: ExprSchema`（与 `TryGetSignature` 已有的委托方式一致）。
3. `core/gameplay/quest/contracts/QuestExprSchemaEntries.cs` 内的私有嵌套类型
   `EventGroupPermissiveSchema`：`KnownKeys(group)` 对 `event` 分组恒返回空集合并在注释写明
   "恒放行、无登记集合"的语义（该分组从不登记任何具体 `event.*` 签名，"恒放行"是匹配规则本身，
   不等价于"已登记过 key"，与 `KnownKeys`/`KnownGroups` 接口契约"已出现过至少一个已登记 key
   的分组"字面语义一致）；其余分组转发给内层 `_inner`。`KnownGroups` 同理直接转发给
   `_inner.KnownGroups`，不额外把 `event` 塞进结果（同一份"已登记 key"契约语义判断）。
4. `core/foundation/data_registry/core/RecordExprSchema.cs`：`KnownKeys(group)` 在
   `group == ExprGroups.Self` 时返回 `For(TableSchema)` 登记过的全部字段名（排序，确定性），
   其它分组恒空；`KnownGroups` 在字段非空时返回 `{ "self" }`，否则空集合。

`ExprSchema` 本身（第三批第 18 条已落地的实现）不改动，继续作为"真实存有已登记 key/分组"的
唯一权威数据来源，其余四处均为纯转发，不引入新的登记逻辑或改变任何签名匹配行为
（`TryGetSignature` 逐字节未变）。

**新增通用门禁测试**（根治同类遗漏，不止本次涉及的 `IExprSchema`）：

`presentation/assembly/tests/InterfaceDefaultMemberForwardingTests.cs`——反射枚举六个核心程序集
（`Core.Foundation`/`Core.Numbers`/`Core.Carriers`/`Core.Rules`/`Core.Gameplay`/
`Presentation.Common`）内全部公开接口的"带默认实现的成员"（`IsVirtual && !IsAbstract`），再枚举
这六个程序集内全部实现该接口的非抽象类型（含内部/私有嵌套类型，`Assembly.GetTypes()` 本就返回
全部可见性的类型），用 `Type.GetInterfaceMap` 判断每个默认成员的落地方法是否仍指向接口自身的
默认实现（未转发/未重写）；命中即失败并列出"类型.成员"，除非登记在测试内的显式豁免清单
（"类型.成员" + 理由）。

该测试放在 `presentation/assembly/tests` 而非 `core/foundation/common/tests`——后者所在的
`Tests.Foundation.csproj` 只引用 `Core.Foundation.csproj`，反射不到其余五个程序集；
`presentation/tests/Tests.PresentationCommon.csproj` 经 `Presentation.Common → Core.Gameplay
→ Core.Carriers → Core.Rules → Core.Numbers → Core.Foundation` 的项目引用链可传递引用全部六个。

## 门禁揪出的其它遗漏（逐一处理）

跑一遍新增门禁（在补齐上述四处转发**之前**）额外揪出两类、共 18 处默认成员未转发/未重写，均已
逐个核实并登记豁免（理由写在测试文件的 `Exemptions` 字典内，摘要如下）：

### `Core.Foundation.DataRegistry.InMemoryDataSource.Root`（1 处）

`IDataSource.Root` 默认实现恒返回 `null`（语义是"退化为用完整 `Location` 本身作为相对路径"，见
该接口成员判断记录）。`InMemoryDataSource` 是内存数据源，没有文件系统根目录概念，没有比 `null`
更好的值可转发——默认值本身就是正确语义，登记豁免。（`FileSystemDataSource` 已正确显式覆盖为
构造期传入的根目录，不受影响。）

### `IPersistable.KeepStateWhenSectionMissing`（17 处）

该成员是刻意设计的"opt-in"默认接口成员：默认值 `false`（"存档缺段时清空到从未发生过的默认态"）
是"绝大多数段"的正确语义，接口文档原句"不覆盖时对全部既有实现完全透明，不需要逐一改动既有
`IPersistable` 实现签名"。该成员此前已经过一轮专项复核（AUD-02 收边，
`architecture/落地计划/audit-85f1f4f-20260908`），结论是只有"缺段时清空到默认值会产生错误状态"
的少数段需要显式覆盖为 `true`（`core/carriers/unit/core/UnitPersistable.cs` 的
`CurrentMapIdPersistable`/`ArchetypeIdPersistable`/`CurrentPositionPersistable`、
`core/foundation/save_system/core/RngStreamsPersistable.cs`——均已按该复核显式覆盖，源码内可核对
判断记录），其余段沿用默认值 `false` 是同一轮复核确认过的正确语义（例如
`UnitPersistable+RaceIdPersistable` 紧邻 `CurrentMapIdPersistable`，源码判断记录明确写"不声明
例外"并给出理由——`Id?` 本身有明确无歧义的"空"值可用，不存在"清空成什么才对"的两难）。逐一登记
豁免的 17 处类型：

`Core.Carriers.Gobj.GobjPendingLootPersistable`、`Core.Carriers.Item.EquipmentPersistable`、
`Core.Carriers.Item.InventoryPersistable`、`Core.Carriers.Unit.SkillBindingPersistable+Impl`、
`Core.Carriers.Unit.UnitPersistable+RaceIdPersistable`、`Core.Foundation.SimLoop.TurnScheduler`、
`Core.Gameplay.Achievement.AchievementHost`、`Core.Gameplay.Assembly.PlayerVitalsPersistable`、
`Core.Gameplay.Difficulty.DifficultyHost`、`Core.Gameplay.Economy.CurrencyPersistable`、
`Core.Gameplay.Economy.VendorStockPersistable`、`Core.Gameplay.Loot.DroppedLootPersistable`、
`Core.Gameplay.Quest.QuestPersistable`、`Core.Gameplay.Spawn.SpawnHost`、
`Core.Gameplay.WorldState.WorldState`、`Core.Numbers.Progression.ProgressionPersistable+Impl`、
`Core.Rules.Skill.KnownSkillsPersistable+Impl`。

**判断记录（为什么这批不是"再来一次第 27 条"）**：`IExprSchema.KnownKeys` 的默认实现对
组合/包装实现方而言必定是错的——包装方本来就应该转发到内层的真实结果，默认值只是"权宜之计，
不代表正确语义"；而 `IPersistable.KeepStateWhenSectionMissing` 是终端实现方（不是委托/包装另一份
同接口实例的类型）的一个是/否语义开关，"不覆盖"本身就是该成员设计之初就打算让大多数实现方做出的
选择，且已有专门复核轮次确认过具体答案，两者性质不同：前者是"遗漏"，后者是"经过审查的默认值"。
门禁测试不区分这两种情况（也不应该区分——区分需要理解每个成员的业务语义，这正是门禁要交给人工
判断、只负责"揪出所有候选、不代为下结论"的部分），因此新增的 18 处豁免登记是预期内的正常产出，
不是门禁本身有误报。

## 对消费方提示

`PresentationSchemaCatalog.FullExprSchema.KnownKeys(group)`/`.KnownGroups` 现在对
`self`/`target`/`world`/`quest`/`player`/`combat`/`enemies`/`time` 八个分组各自返回真实已登记
key/分组集合（有序、确定性）；`event` 分组按设计恒返回空集合（该分组从不登记具体 key，运行时
仍然对任意 `event.<key>` 恒放行，行为本身未变，见第四批第 24 条）。若编辑器一侧此前因为
`KnownKeys`/`KnownGroups` 恒为空而绕开了这两个查询、改用其它方式（如硬编码字段清单、或干脆不做
自动补全），建议切回直接调用正式装配入口的这两个成员。
