## 二、第 74 条——`import_assets.py check --json` 补 `domain_counts`

`toolchain/asset_import/check_cmd.py` 的 `--json` 顶层新增 `domain_counts` 字段（`dict[str, int]`），
既有六个顶层键（`tool`/`dataset`/`domains`/`ok`/`counts`/`issues`）名字、类型、含义**一个未改**，贵方
现有解析代码不用改也能继续跑。

真实运行 `python -m toolchain.import_assets check --dataset _sample --json`（本仓库当前 `_sample`
数据集，1.50.0）得到的完整示例：

```json
{
  "tool": "import_assets.check",
  "dataset": "_sample",
  "domains": ["display_anim", "sfx", "sprite", "vfx", "world"],
  "ok": true,
  "counts": {"error": 0, "warning": 0},
  "domain_counts": {
    "display.anim_set": 2,
    "display.equip_visual": 4,
    "display.map": 30,
    "display.weapon_style": 3,
    "sfx.def": 3,
    "vfx.def": 3,
    "world.map": 1
  },
  "issues": []
}
```

（该批数据现状与贵方反馈原文里引用的旧数字——`display.map` 4 条、`display.weapon_style`/
`display.equip_visual` 各 1 条——不同，是 `_sample` 数据集本身在这之间被扩充了，不是本次交付改变了
计数口径。）

**条数口径**：与文本汇总行完全同源，都是 `run()` 内部 `_load_rows()` 读到的该表 `rows` 数组长度——
数的是"这一域实际加载了多少条记录"，与这些记录是否命中检查条件、是否报出问题无关（0 条问题的域
也如实给出真实行数，不代表"跳过未检查"）。

**`--only` 未选中的域**：该域对应的键在 `domain_counts` 里**整体不出现**，不是给 `0`——用于区分
"这次没跑这个域"和"跑了这个域但恰好 0 条记录"，这两种情况用贵方 `AssetCheckSummary` 的口径就是
"该字段应为 `null`"与"该字段为 `0`"的区别。示例：`--only sprite,world` 时 `domain_counts` 只有
`display.map`/`world.map` 两个键，`vfx.def`/`sfx.def`/`display.anim_set`/`display.weapon_style`/
`display.equip_visual` 五个键均不出现。

**键的排序保证**：`domain_counts` 按表名字符串排序输出（`{k: domain_counts[k] for k in
sorted(domain_counts)}`），与既有 `domains` 字段"`sorted(only)`"同一手法，不依赖字典插入顺序或
运行环境差异。

这条解除了贵方"拆除 `Editor.Core.Tools.AssetCheckOutputParser` 文本正则解析、改用 `--json`"的停工
项，可以拆了。

## 三、第 75 条——`AssetRefConventions` 补齐地图分层图路径

`Core.Foundation.EngineAdapter.AssetRefConventions`（既有 14 个公开方法覆盖
sprite/icon/vfx/sfx/anim/model/sprite_anim/paperdoll 各类前缀）新增五个静态方法（ADR-0053），签名
与既有方法同一形态（均以带类别前缀的资源引用标识 `Id` 为输入，不接收已拆前缀的裸字符串）：

| 方法 | 输出形态 |
|---|---|
| `MapDirectory(Id mapId)` | 地图目录：`"maps/<map>"`（资产根相对，不以 `/` 结尾，不含扩展名） |
| `MapGroundFile(Id mapId)` | 地面层文件（框架固定项，必需）：`"maps/<map>/ground.png"` |
| `MapOverlayFile(Id mapId)` | 前景遮挡层文件（框架固定项，必需）：`"maps/<map>/overlay.png"` |
| `MapDecalFile(Id mapId)` | 装饰层文件（可选）：`"maps/<map>/decal.png"` |
| `MapNavHintFile(Id mapId)` | 导航标注参考图（可选）：`"maps/<map>/nav_hint.png"` |

**输入是 `world.map` 行的 `id`**（形如 `world.<map>`），不是已经拆过前缀的裸地图名——与
`SpriteSetDirectory`/`IconFile` 等既有方法的输入形状一致，不需要为地图分层图单独记一条"这里要先
自己拆前缀"的例外规则。

**层名表达**：`ground`/`overlay`/`decal`/`nav_hint` 四层用四个独立方法各自表达，不收裸字符串层名、
不新增枚举或分派参数——与既有契约面"一个类别前缀一个专属方法"的既有惯例一致。

**Python 侧等价函数**：`toolchain/asset_import/ref_conventions.py` 新增 `map_directory`/
`map_ground_file`/`map_overlay_file`/`map_decal_file`/`map_nav_hint_file` 五个函数，签名
`(map_id: str) -> str`，独立实现（不调用 C# 侧，也不互相调用彼此之外的规则本身），与 C# 侧逐字节
对应。`toolchain/asset_import/map_cmd.py` 已改为调用这组函数，不再自行拼接路径。

**dataset 段由谁拼接**：与既有 14 个方法同一口径——这五个方法只给出资产根相对路径（`"maps/<map>/
..."`），不包含 `assets/<dataset>/` 前缀；调用方自行拼接 `assets/<dataset>/` 前缀后再做文件系统
存在性检查，框架侧不感知 dataset 概念。

贵方 `MapAssetPathConvention` 这个自写绕行现在可以拆掉了，改为依赖这组公开契约。

## 四、必须如实说明的边界：地图名含多个点号时的差异

ADR-0053"负面"一节记录了一个已知边界，答复稿单独列出，不藏在正文里：

- 旧实现（`map_cmd.py` 改动前的 `out_dir` 拼接）直接把 `--map` 命令行参数原始字符串当作单一目录段，
  **只在第一处点号切一次**（`strip_domain` 语义）。
- 新方法（`MapDirectory`/`map_directory`）内部用 `StripCategoryPrefix`/`strip_category_prefix`，
  去掉 `world.` 前缀后，**把剩余部分里所有点号都换成下划线**。
- 两者**只在地图名本身含多个点号**（形如 `world.zone.dungeon`，即地图名部分本身是多段 id）时才会
  给出不同的路径结果；地图名不含点号（当前所有已知数据的形状）时两者逐字节相同。

**当前影响范围**：仓库内现有全部 `world.map` 数据（默认示例数据根、`<game>` 模板数据根、内置数值
仿真测试数据根）逐字节相同，均为不含点号的单段地图名，因此**本次交付不改变任何现有数据的路径**。
如果贵方数据集里存在地图 id 含多个点号的 `world.map` 行，这条路径在升级后会发生变化，请自查一遍
`world.map` 表全部行的 `id` 字段是否存在这种形状。

## 五、顺带收口：检查命令里第二处地图路径拼接

这一轮同时把 `toolchain/asset_import/check_cmd.py` 的 `_check_world_row`（校验 `world.map` 行时用于
定位分层图目录/文件是否存在）原本自行拼接的第二处独立地图路径实现，也改为调用
`map_directory`/`map_ground_file`/`map_overlay_file` 这组共享函数——地图路径约定现在**只有一个
出处**。已全仓复核过，未发现第三处对 `world.map` 行 id 做同类推导的硬编码拼接（`gen_placeholder_assets.py`
里存在形状相似的字面量拼接，但那是无内容 id 的占位资产生成脚本，与本次治理对象"从登记表行 id 推导
路径"不是同一性质，评估后判定不在收口范围内，详见 ADR-0053 修订记录）。

## 六、与本次答复无关、但请自查的一条行为变更

1.50.0 同时包含一条**行为变更**：掉落条目随机子流隔离（ADR-0052）——同一种子下的掉落判定序列与
此前版本不同（一个条目自己消耗几次随机数只影响它自己这条子流，不再挪动其它条目/其它表的结果）。这条
不是给内容编辑器项目的答复内容，但如果贵方工具链里有依赖固定种子掉落结果的测试，升级后需要重新生成
期望值。
