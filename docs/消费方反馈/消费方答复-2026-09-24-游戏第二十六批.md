## 现象 2：为什么你方抓不到

三个数字放在一起就清楚了：

| 量 | 实测值 |
| --- | --- |
| 冷资源从播放请求到真正开始播放的墙钟延迟 | **19.08ms** |
| `ui_click_01.wav` 的实际时长 | **0.05 秒** |
| `ui_open_01.wav` 的实际时长 | **0.15 秒** |

也就是说：那次播放大约在第 20 毫秒开始、第 70 毫秒结束，**整段"正在播放"只存在约 50 毫秒**。
冷加载完全没有把它推迟到你方的 0.4 秒窗口之外——恰恰相反，它在窗口的**最开头**就播完了。

我方在真实引擎适配层复现了你方的观测形态：冷资源、真实 `ui.action_invoked` 事件、0.4 秒窗口按
100ms 间隔轮询播放状态。结果：

- **黑盒轮询：一次都没抓到**（4 个采样点分别落在 100/200/300/400ms，播放在 70ms 就结束了）；
- **同一次运行的累计计数：确实播放过，恰好一次**，最近一次播放记录里就是那条冷资源的引用 id。

**这条用例带阳性对照**：同一轮采样里同时观测一条已预热、时长 0.4 秒的音效——**对照命中、冷短音效
不命中**。没有这个对照，"轮询抓不到"可能只是因为剪辑命名对不上之类的错误原因恒为真，否定结论就
不成立。加上对照之后，这个否定才是有意义的。

## 一句实话：这两个占位音效基本等于听不见

0.05 秒的音效，即使你方抓到了播放状态，人耳也几乎感知不到。你方核实过这两个文件与框架占位样例
逐字节一致——**这正是问题所在**：框架的 `_placeholder` 音效是给自动化用例用的最短可用信号，不是
给游戏实际使用的素材。你方要做真实的 UI 音效反馈，需要换成你方自己的素材。这属于内容，不是契约，
我方不会把占位音效改长（改长会动到既有用例的时序前提）。

## 交付：不需要抓瞬态的播放凭据

新增一份播放诊断契约，从表现层装配根就能读到（`PresentationAssembly` 那一层，你方只读代码够得着）：

- **三个单调累计计数**：播放请求数、真正开始播放数、被丢弃数。累计值不会因为错过瞬态而丢失。
- **最近一次播放记录**：资源引用 id + 单调递增序号。

纯加法，不改任何既有播放语义与既有公开方法签名的行为。你方今后判断"到底播没播"，读计数即可，
不要再去轮询播放状态。

## 排查过程中顺带查清的几件事（对你方有用）

1. **冷加载完成后是补播放，不是丢弃**，而且恰好一次——你方不用担心冷资源的第一次触发被吞。
2. **三条丢弃路径（资源未登记 / 加载失败 / 加载超时）都各自记了诊断**，逐处通读未发现静默吞掉
   播放请求的分支。
3. **有一条相邻行为要提醒你方**：同时播放的音效实例数达到上限时，框架会抢占停止一个已经在播的
   实例，**而这一步目前不记诊断**。你方如果后续出现"某些音效偶尔没声音"，这是一个真实的嫌疑点。
   本轮不改（它不是你方现象的成因），但你方遇到了就直接反馈，我方补诊断。

## 仍然没有完全定论的部分（如实说）

我方不知道你方那个 0.4 秒轮询的**采样间隔**是多少。如果你方是逐帧轮询，理论上 50ms 约 3 帧是有
机会抓到的——那样的话你方那边可能还有一层我方这轮没接触到的额外延迟。

**所以请你方升到 1.68.0 后先做这一件事**：不要再看播放状态，直接读新的累计计数，在触发 UI 音效
前后各读一次。

- 计数**有增长** → 结论落定：播放确实发生，此前只是观测方式抓不到，这条可以关掉了。
- 计数**没有增长** → 那就是另一回事了，请把两次读数、以及你方轮询的真实采样间隔一并发回，我方
  接着查。
