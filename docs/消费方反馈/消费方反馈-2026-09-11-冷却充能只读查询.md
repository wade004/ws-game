## 观察（消费方反馈原文摘要）

反射并对照冻结源码确认：`ISkillHost.GetCooldown` 是冷却查询方面对外唯一的出口——不区分究竟是
技能自身冷却、分类冷却还是充能未恢复（有可用充能时可能直接返回 0），不呈现当前充能数、下次充能
恢复剩余，也不呈现公共冷却状态；`SkillHost` 内部的 `CooldownTracker` 早已各自独立持有
`GetCooldown`/`GetCharges`/`GetGcdRemaining` 三块状态，只是从未通过宿主统一公开。消费方明确"这是
对外只读可观测性缺口，不定性为结算错误"——冷却/充能/公共冷却的原生判定机制本身没有问题。

## 契约决定

按消费方"建议的兼容性改进"给出的方向拍板：新增一个公开的只读统一快照类型与配套查询方法，覆盖
反馈列出的全部三项——有效充能上限/当前充能数/下次充能恢复剩余、技能冷却/分类冷却/公共冷却剩余、
修饰后（`SpellMod` 生效后）的有效状态且能区分各计时来源；保持 `ISkillHost` 既有兼容性（只新增，
不删改任何既有签名），`CastSkill` 仍是唯一的最终裁决；查询只读取宿主现有账本，不推进时间、不创建
第二套计时器、不要求调用方复制冷却账本。

具体落地为 06 第 3.1/3.6/7 节同批勘误（见变更记录，细节勘误，版本号不变）：

1. 新增不可变值类型 `Core.Rules.Skill.SkillReadiness`（`SkillId`/`IsReady`/`BlockingSources`/
   `SkillCooldownRemaining`/`CategoryCooldownRemaining`/`GlobalCooldownRemaining`/`MaxCharges`/
   `CurrentCharges`/`NextChargeRemaining`/`EffectiveCooldownDuration` 十个只读字段）、
   `[Flags] SkillReadinessBlockers`（`None`/`SkillCooldown`/`CategoryCooldown`/`GlobalCooldown`/
   `NoCharges`，可按位或组合，呈现"此刻若施法会被哪几项挡下"）、`CategoryCooldownStatus`（分类
   id + 该分类剩余的不可变结构体，让"这个剩余时间属于哪个分类"随结果一并携带，不需要调用方另外
   回查 `skill.def.cooldown_category`）。时间单位与既有 `GetCooldown` 完全一致（按当前生效时间
   模型折算后的计时单位，不是数据 authoring 时的原始规范单位）。
2. `ISkillHost` 新增带默认实现的 `GetSkillReadiness(Id unitId, Id skillId): SkillReadiness`
   （C# 8 default interface member，公开 API 只新增，既有实现方零改动仍可编译）。默认实现只能
   借 `GetCooldown` 拼一个降级快照（`IsReady`/`BlockingSources` 粗略推断，公共冷却完全不参与
   判定，其余字段一律 `null` 表示"未知"）。
3. 生产实现 `Core.Rules.Skill.SkillHost.GetSkillReadiness` 显式覆盖，直接从
   `CooldownTracker`/`SpellModResolver`/`SkillOptions` 读取精确字段，裁决口径与
   `CastSkill`（经 `CastPipeline`）步骤 3（冷却/充能）、步骤 4（公共冷却）逐字对齐：有 `charges`
   配置的技能只看充能数、不检查分类冷却（`CooldownTracker.IsSkillReady` 既有语义）；否则看技能
   自身冷却与（若声明了 `cooldown_category`）所属分类冷却是否均已归零；公共冷却只在
   `SkillOptions.GcdEnabled && def.RespectsGcd && !isDiscreteStep` 同时成立时才参与裁决。
   `EffectiveCooldownDuration` 与 `CastPipeline.StartCooldownAndGcd` 的 `modifiedCooldown`
   计算同一算式（只读不写）。全程不调用 `CooldownTracker` 任何写方法，不推进时间、不修改任何
   状态。
4. `CooldownTracker` 补充四个只读公开出口：`CurrentTimeFactor`（原私有 `_currentFactor` 的只读
   转发）、`GetChargeRechargeRemaining`、`GetEffectiveChargesMax`、
   `GetEffectiveRechargeTimeScaled`（均为既有私有状态/私有方法的只读转发，不新增账本、不改变
   既有写路径）。

## 对消费方的提示

1. **新增只读查询，`CastSkill` 仍是唯一最终裁决**：`ISkillHost.GetSkillReadiness(unitId, skillId)`
   返回的 `IsReady`/`BlockingSources` 只覆盖施法管线步骤 3（冷却/充能）、步骤 4（公共冷却）两项
   拒绝原因，不含存活/控制、学派锁定、资源、目标合法性、距离与视线等其它步骤——`IsReady` 为
   `true` 只表示"不会被冷却/充能/公共冷却挡下"，不代表此刻 `CastSkill` 一定成功（可能仍因资源
   不足/无合法目标等原因失败）。若需要完整的"这一刀能不能放"判断，仍需调用 `CastSkill` 本身。
2. **字段口径**：时间单位与既有 `GetCooldown` 完全一致；`MaxCharges`/`CurrentCharges`/
   `NextChargeRemaining` 在技能未配置 `charges` 时为 `null`（不是"充能数未知"，是"没有充能机制
   可言"）；`CategoryCooldownRemaining` 在技能未声明 `cooldown_category`，或技能配置了 `charges`
   （该引擎充能技能从不检查分类冷却）时为 `null`；`skillId` 按调用方传入的 id 原样查询，不做
   `override_skill` 光环重定向（与 `GetCooldown` 同一惯例）。
3. **公开 API 只新增，未删改**：`ISkillHost` 新增一个带默认实现的成员，既有实现方（含消费方自己
   若曾实现过 `ISkillHost`）零改动仍可编译；本仓库 `toolchain/abi_probe.ps1` 已核实（基线
   1.12.0）`breaks=0`，不需要做任何升级前的兼容性核对。若消费方自己也实现了 `ISkillHost`（例如
   测试替身），未显式覆盖 `GetSkillReadiness` 时会落回默认接口成员提供的降级快照（只能从
   `GetCooldown` 粗略推断，公共冷却不参与判定，其余字段为 `null`）——这是刻意设计的兼容兜底，
   不是缺陷；如需精确结果，请在自己的实现里显式覆盖该成员。
