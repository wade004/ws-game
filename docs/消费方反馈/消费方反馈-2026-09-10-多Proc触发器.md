# 消费方反馈回复：同一光环多个 Proc 触发器静默忽略问题（2026-09-10）

- 反馈来源：消费方游戏项目"框架反馈"提交的 `同一光环多个Proc触发器静默忽略问题.md`（`D:\workespace\ws-game-wow\docs\框架反馈\同一光环多个Proc触发器静默忽略问题.md`），完整探针/原始日志/结果/DLL 哈希与发布清单在同仓库
  `docs\框架反馈\证据\c07-multiple-proc-1.15.0-20260910\`（只读，未修改）。
- 提交：`5ef4128`（代码 + 校验规则 + 测试）、本笔提交（文档 + 本回复 + CHANGELOG，哈希见 `git log`）。

## 现象

固定版本 1.15.0（源码 `15c6a443d8021553046ef22897e4f773910263f4`），消费方探针引用锁定 PackageCache
五个核心 DLL 复现：`skill.aura_def.effects` 登记两个 `proc_trigger` 效果条目（各自引用不同的
`skill.proc_def`）加载校验通过，但运行期只有 `effects` 数组里**最后一个**条目真正生效——不管登记
顺序是 [A, B] 还是 [B, A]，观察到的 `ProcTriggeredEvent` 都只有一条，且总是对应数组末尾那个
`proc_ref`；作为对照的"两个独立光环各挂一个触发器"场景两个都正常触发。内容作者无法从加载成功这件
事判断配置是否真的生效。

## 根因

`core/rules/skill/core/AuraHost.cs`：

- `AuraInstanceState.ProcDefRef` 此前是单值字段 `Id?`，`ApplyStaticEffects` 遍历同一光环定义的
  多个 `proc_trigger` 效果条目时后一个覆盖前一个，字段最终只留下数组里最后一个 `proc_ref`。
- `CreateInstance` 只按这个单值字段调一次 `ProcHost.Attach`，前面被覆盖掉的 `proc_ref` 从未被
  挂载过，不是"挂载了但没触发"，是从未挂载。

`core/rules/skill/core/ProcHost.cs`：

- `_attachments` 此前是 `Dictionary<Id, Attachment>`，以光环实例 id 为单值键——即使 `AuraHost`
  侧被修好、对同一实例调用两次 `Attach`，第二次也会直接覆盖第一次的 `Attachment`（连带这次覆盖
  丢失的旧 `SubscriptionHandle` 从未 `Dispose`，是另一层未回收的订阅泄漏），单槽存储与
  `AuraHost` 的单值字段是同一个缺陷在两处的重复体现，两处都要改。

`core/rules/skill/schema/SkillSchemas.cs` 的 `AuraEffectsItemSchema` 对 `proc_ref` 做了引用
完整性校验（指向的 `proc_def` 必须存在），但未对"同一光环内允许几个 `proc_trigger` 条目"这件事
做任何数量或重复性约束——因此这不是概率、条件、内部冷却或事件目标造成的偶发现象，而是成功通过
加载校验的早期效果条目在运行期被无声覆盖，且加载期没有任何信号提示这一点。

## 契约决定

按消费方反馈"建议与验收"给出的两条路径之一拍板：**支持单光环多个触发器**（而不是加载期直接拒绝
第二个 `proc_trigger`）——多个不同被动共用一个光环是合理的内容形态，本次落地为：

1. 单光环可登记多个 `proc_trigger` 效果条目；保存完整触发器集合，各自独立经 `ProcHost` 挂载、
   独立结算条件（Expr）/概率（`proc_chance`）/内部冷却（`internal_cooldown`）。
2. 光环整体移除（到期、`RemoveAura`、`Dispel` 驱散、吸收耗尽、叠加溢出被 `Replace`、目标销毁）
   时，该光环挂载的**全部**触发器一并注销，不残留孤儿订阅。
3. 同一光环内**重复引用同一个** `proc_def`（两条 `proc_trigger` 的 `proc_ref` 取值相同）没有
   可区分的运行时语义——两次独立挂载会各自起一份内部冷却计时器争抢同一个触发事件，行为对内容
   作者不可预测，因此改在**加载期直接拒绝**，报错定位到具体重复的那一条
   `effects[index].params.proc_ref`。

## 修复位置

- `core/rules/skill/core/AuraHost.cs`：`AuraInstanceState.ProcDefRef`（单值）改为
  `ProcDefRefs`（`List<Id>` 有序集合，按 `effects` 原始顺序追加，不再覆盖）；`ApplyStaticEffects`
  的 `ProcTrigger` 分支从赋值改为追加；`CreateInstance` 对集合内每个 `proc_ref` 各调一次
  `ProcHost.Attach`（原单次调用改为循环）；`RemoveInstanceInternal` 仍只调一次
  `ProcHost.Detach(instanceId)`——该方法语义已变更为"摘除该实例的全部触发器"，本类无需逐个记账，
  全部六条既有移除路径（到期 `Update`、`RemoveAura`、`Dispel`、`ConsumeAbsorb` 吸收耗尽、叠加
  溢出 `Replace`、`OnEntityDestroyed` 目标销毁）均经由这一处统一收口，自动获得"整体一起注销"的
  行为，不需要逐个路径改动。
- `core/rules/skill/core/ProcHost.cs`：`_attachments` 从 `Dictionary<Id, Attachment>` 改为
  `Dictionary<Id, List<Attachment>>`（按光环实例 id 分桶的多槽列表）；`Attach` 改为向桶里追加
  （不再覆盖）；`Detach(Id instanceId)` 语义变更为摘除该实例桶内的全部 `Attachment`（逐个
  `Dispose` 订阅）；新增重载 `Detach(Id instanceId, Id procDefId)`（按单个 `procDef` 精细摘除，
  纯新增，当前调用方未使用）；`Update`/`RescaleAll` 改为遍历桶内全部 `Attachment`（同一实例下的
  多个触发器各自持有独立的 `IcdRemaining`，互不干扰）。
- `core/rules/skill/schema/SkillValidationRules.cs`：新增 `AuraProcTriggerDuplicateRule`
  （检查名 `aura_proc_trigger_duplicate`），扫描每条 `skill.aura_def` 记录的 `effects`，按
  `proc_ref` 取值查重，命中时报错并定位到 `effects[index].params.proc_ref`；已在
  `core/rules/assembly/RulesSchemaCatalog.cs` 的 `RegisterAll` 默认登记。
- **公开 API 变化**：`ProcHost` 新增重载 `Detach(Id instanceId, Id procDefId)`；既有公开方法
  `Attach(Id, Id, ProcDef)`/`Detach(Id instanceId)`/`Update(double)`/`RescaleAll(double)` 签名
  与外部可观察行为契约均未改变（`Detach(Id)` 的内部实现语义变化——从"摘除唯一一个"变为"摘除全部"
  ——对唯一调用方 `AuraHost` 透明，此前每个实例本就至多一个附着，行为不变）。
  `AuraInstanceState`/`ProcHost.Attachment` 均为内部类型，不在公开 API 表面，无需兼容包袱。

## 对消费方的提示

1. **升级后可以合并被动**：升级到包含本次改动的版本后，此前因为"一个光环只有一个 Proc 真正生效"
   而拆成多个原生光环的多个被动，可以合并回一个光环、在同一个 `effects` 列表里登记多个
   `proc_trigger`，各自独立生效，不再需要为每个被动单独建一个光环。
2. **同一光环内不能重复引用同一个触发器定义**：若合并后不小心把同一个 `proc_def` 在同一个光环
   的 `effects` 里引用了两次，升级后这条内容会在加载期被拒绝（检查名
   `aura_proc_trigger_duplicate`），错误会定位到具体是 `effects` 数组的第几条、哪个字段——这是
   刻意的契约收紧（此前这类配置会静默通过加载但只有一个生效），请改为引用不同的 `proc_def`
   记录，或拆成独立光环。
3. **公开 API 只新增，未删改**：`ProcHost` 新增了一个 `Detach` 重载，既有公开方法签名与外部
   可观察行为均未变化，不需要做任何升级前的兼容性核对；本仓库 `toolchain/abi_probe.ps1` 已核实
   `breaks=0`。
4. **不需要重跑你方探针来"验证缺陷仍存在"**：你方探针的 oracle（`product_gap` 判定）写的是旧
   缺陷的特征模式，升级后重跑会报 `product_gap: false`/退出码非 0——这是预期的正向信号（特征
   模式消失），不是新的异常，建议你方后续如需在自己仓库复核，同步更新 oracle 为"AB/BA 两组均应
   各自触发两次、HP 100→86"。
