# 发布候选阶段：`-SamplesRepo` 指向已关联工作树时主工作树快照误报（待办，2026-10-09）

> 本文档允许出现具体技术名，不受 `architecture/00～14` 与 `architecture/adr/` 正文的禁用词约束。
> 来源：2.10.0 发布时的自查（框架自己发现，不是消费方反馈）。登记在这里是为了让下一版带上修复；2.10.0 已按"候选阶段传样板主工作树路径"的形态发布，行为正确。

**结论先行**：`build.ps1 -Release X.Y.Z -SamplesRepo <样板仓库的已关联工作树>` 时，候选阶段的样板全量门禁通过后，仍会因"样板主工作树快照比对不一致"而失败，发布在打标签前终止。传样板**主工作树**路径（候选阶段自建临时工作树）不受影响，续跑用主工作树路径即可。

## 症状

- 候选阶段日志里样板门禁全绿，随后报"候选阶段改动了样板主工作树（HEAD 或未提交改动清单与阶段开始前不同）……请检查样板仓库 <传入的路径> 的 git status"。
- 发布提交与门禁通过记录保留，`-Resume` 可续跑，但同样的参数续跑会再次误报。

## 根因

`toolchain/_release_candidate.ps1` 的 `Invoke-ReleaseCandidateStage`（约第 300 行）在阶段前后各调一次 `Get-SamplesMainSnapshot -SamplesRepo $samples`。
`$samples` 是调用方传入的样板仓库路径；它本身是已关联工作树时，阶段直接在它上面做升级与门禁（把 manifest 改成候选版本，这是合法的），快照却拍的是这个工作树，前后必然不同。
判断记录 6 要保护的是**真正的主工作树**（用户的试玩目录），不是传入的那一个。

## 修法（已做）

- 快照对象改为真正的主工作树：`git -C <样板路径> rev-parse --path-format=absolute --git-common-dir` 的上级目录（样板路径本身就是主工作树时等于它自己）。
- 传入的已关联工作树不再参与快照比对。
- 复现与不变量用例（`toolchain/tests/test_release_candidate.py`，真实 git）：
  - 红绿对照：样板仓库建一个已关联工作树，把它作为 `-SamplesRepo`，候选阶段绿时不抛异常，主工作树的 HEAD 与 `git status` 前后逐字节一致；
  - 不变量：仍在已关联工作树里的升级被写进该工作树，而主工作树被意外改动时照样失败。

## 状态

**已修**（2026-10-10，随 2.14.0）：`toolchain/_release_candidate.ps1` 新增 `Get-SamplesMainWorktreePath`（`git rev-parse --path-format=absolute --git-common-dir` 的上级目录；传入的就是主工作树、不是 git 仓库或裸仓库时原样返回），候选阶段前后的快照改拍它；传入的已关联工作树不再参与比对。用例（`toolchain/tests/test_release_candidate.py`，真实 git，修复前红、修复后绿）：
`test_main_worktree_path_is_the_parent_of_the_common_git_dir_for_a_linked_worktree`、
`test_real_git_linked_worktree_as_samples_repo_passes_and_upgrades_in_it_while_main_stays_untouched`（绿了的候选阶段不再误报，升级写进已关联工作树，主工作树 HEAD 与 `git status` 前后逐字节一致）、
`test_real_git_linked_worktree_still_fails_when_the_real_main_worktree_is_touched`（升级意外写到主工作树时照样失败，报错指向真正的主工作树）。
