## 根因：不是打包缺陷，是包管理器对只读包内 `Resources` 目录的既有限制

我方直接下载**你方正在用的那份 1.65.0 发布包**核对过：`.mat` / `.mat.meta` / `.shader` /
`.shader.meta` 四个文件路径与 GUID 全部正确，**打包没有任何遗漏**——你方的核实结论一字不差。

真正的原因是：**"按包内相对路径检索资产"这条机制，在"经独立分发通道按版本号安装的不可变只读包"
这一消费形态下取不到资产**；以源码/内嵌形态直接引用时正常。也就是说，框架开发库里怎么测都是好的，
装到你方工程里就是坏的。

**这正是我方的验收漏洞**：ADR-0074 当初的验收全部在开发库内嵌形态下做的，**从来没有在"经安装形态
消费"下验证过随包分发的引擎资产能不能加载到**。你方等于替我方发现了一整类盲区。

## 修法

**绕开那条机制**：改为运行期按着色器名称检索并现场构造材质，不再依赖"按路径检索包内专用目录资产"。
同时新增编辑器侧自动登记，保证该着色器不会被独立版构建的未使用资源裁剪掉——**两处缺一不可**，
只改前者会在独立版里同样落空。

`blend_mode` 不声明或声明 `alpha` 时的材质选择路径**一字未动**。

**实测**（同一安装形态，用真实发布的包）：
- 修复前：`RESULT=FAIL shader=<引擎默认精灵材质>`（与你方日志一致）
- 修复后：`RESULT=PASS shader=GameFoundation/Vfx/AdditiveUnlit`

**防复发**：`consumer_smoke.ps1`（我方的消费方演练）新增一步，专门覆盖"经独立分发通道按版本号安装"
这条**此前从未被该脚本走过**的消费路径，断言该材质确实加载到、且实际用的就是叠加混合材质。这条
断言对修复前的代码 FAIL、对修复后 PASS，**两个方向都实测过**。没有这一步，同样的洞还会再开一次。

## 有一件事你方需要知道（会改到你方工程的文件）

那个编辑器侧自动登记，会**往你方工程自己的 `ProjectSettings/GraphicsSettings.asset` 里追加一条
着色器引用**（Always Included Shaders 列表）。你方会在自己仓库的 git status 里看到这个文件被改动。

- 它**幂等**：已经在列表里就直接返回，不重复写入。
- 它**只追加**，不覆盖你方已有的任何其它条目。
- 它**可逆**：你方随时可以手工从列表里移除（代价是独立版构建时该着色器会被裁掉，additive 又会退回
  alpha）。

这是我方拒绝"让消费方自己再配置一步"之后的必然代价——换来的是**装上就能用，不需要你方做任何手工
步骤**。你方问的"是否需要显式触发一次资源库刷新"，答案是不需要，也不该需要。
