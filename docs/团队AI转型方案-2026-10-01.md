## 一、结论先行

从下一个迭代起，本项目的开发方式改为：**人负责设计、拍板与验收，AI 负责执行与验证，机器门禁负责守底线。**

两个目标，各对应一组 12 周后必须达到的硬指标：

| 目标 | 指标 | 现状基线 | 12 周目标 |
|---|---|---|---|
| 产出效率 | 每人每周合并的功能切片数 | 阶段 0 第一周测量 | 基线 × 3 |
| 产出效率 | 一个切片从派工到合并的时长 | 阶段 0 第一周测量 | ≤ 1 个工作日 |
| 产出效率 | 每人同时推进的并行切片数 | 1 | ≥ 3 |
| 线上稳定 | 消费方报上来的阻塞级缺陷 | 按消费方反馈总表统计 | 每版本 ≤ 1，且 48 小时内补丁发版 |
| 线上稳定 | 主干门禁通过率 | 已有门禁 | 100%（红了不合并，无人可绕过） |
| 开发质量 | 返工率（合并后 7 天内被修复的切片占比） | 阶段 0 测量 | ≤ 10% |
| 开发质量 | 发版前全量回归 | 已有 | 每次发版全绿并登记 REGRESSION_LOG.md |

这套方法不是从零设计。本仓库到今天的全部成果就是用这种方式做出来的：

| 事实 | 数值 |
|---|---|
| 提交数 | 1105 |
| 当前发布版本 | v1.91.0（语义化版本，标签 + dist zip + lock 不可变发布） |
| 架构决策记录（ADR） | 121 条 |
| 测试文件 / 源码文件 | 522 / 837 |
| 已答复的消费方反馈批次 | 63 批 |

以上全部由「一个设计者 + 若干执行 agent」完成。现在要做的，是把这条已经跑通的流水线扩展到整个团队，并把过程中踩过的坑（已沉淀在 AGENTS.md）变成团队规则，不让每个人再踩一遍。

## 二、三条原则

1. **进度优先。** 每一轮工作先问一句：这一轮让交付物多了什么？交付物指用户能感知的东西：能跑的功能、能用的数据、能转发的文档。审计、重复验证、订正旧文档都不算。答不上来就停下换做法。
2. **人只做非人不可的事。** 设计、拍板、验收、跟外部协调，这四件事人做。写代码、查事实、跑测试、写文档初稿、下载安装、批量改文件，交给 AI。工程师亲手写的代码，应当只剩「几行以内、派 agent 反而更慢」的那种。
3. **质量靠机器门禁和写下来的规则，不靠人盯。** 任何质量要求，能自动化的写进门禁脚本，不能自动化的写进 AGENTS.md。口头传达的规则等于不存在。线上出一次事故，产出的不是一份复盘文档，而是一条新规则或一条新门禁。

## 三、新的角色与分工

| 角色 | 谁 | 做什么 | 不做什么 |
|---|---|---|---|
| 项目负责人 | 我 | 里程碑定义与验收拍板；跨仓库边界与发布；规则终审；对外协调上游/消费方 | 不亲手写业务代码；不逐条审 AI 的 diff |
| 切片负责人 | 每位工程师 | 设计切片、写派工提示词、核对交付凭据、合并、登记 ADR/判断记录 | 不亲手写业务代码（试点期允许 ≤ 20 行的小改）；不替 AI 跑测试 |
| 执行 AI | 每人若干个并行的执行 agent | 在独立工作树内写代码、写测试、跑冒烟、查事实、写文档初稿、按规范提交 | 不扩大范围；不自行追加全量回归；不绕上游缺口；不 merge、不 push |
| 机器门禁 | check.ps1、ABI 探针、meta 门禁、全量回归 | 编译、单测、PlayMode、ABI 兼容、生成物入库检查 | 无豁免通道 |

**工程师的定位变化**：从「写代码的人」变成「出题、验题、拍板的人」。评价一位工程师，看的是切片设计得准不准、验收标准写得能不能被机器判定、合并后的返工率有多低，不再看提交行数。

**模型分层**：设计层用当前最强模型（主会话），执行层用性价比模型（执行 agent）。执行模型查不出根因就直接升级到主模型，不反复派同一层。

## 四、工作循环：按垂直切片交付

一个切片 = 一个用户可感知的最小功能闭环 = 数据 + 接线 + 运行时冒烟，由一个执行 agent 端到端做完。

1. **定切片。** 切片负责人写清三件事：目标、已拍板的设计决定、运行时验收标准。验收标准只写可观测的量：程序里哪个值从什么变成什么，期望值由规则算出来，不写裸数。这三件事直接写成给 AI 的自包含提示词，方案不单独成文。
2. **派工。** 提示词只写该任务特有的内容，通用规则一句「先读取并遵守 AGENTS.md」。AI 在独立工作树内工作。互不相干的切片并行派出，耗时任务放后台。
3. **核对。** AI 交付后，切片负责人只核对凭据：提交 sha、冒烟实测数值、汇报里逐条列出的「已知限制」。不另派验收 agent，不逐行审 diff。
4. **合并与登记。** 门禁绿才合并。CHANGELOG 的 Unreleased 加条目；涉及取舍的写模块 README 判断记录；改架构结论的先出 ADR。
5. **里程碑收口。** 一个功能闭环全部打通时，派一次独立验收 agent，跑一次全量回归，然后发版。

**明令禁止的做法：**

- 串行审计链：「勘察 → 再勘察 → 订正 → 验收订正」一律不做。
- 为「再确认一次」跑全量回归。
- AI 自行扩大范围、自行追加门禁、自行绕过上游缺口。
- 用 `--no-verify`、`--amend`、`add -A`、`reset --hard` 这类操作。
- 把「已知限制」写在代码注释里而不出现在汇报里。

## 五、质量与线上稳定性体系

### 5.1 门禁与回归分级

| 时机 | 跑什么 | 实测耗时（2026-10-01，1.91.0 门禁产物） |
|---|---|---|
| 每个切片 | 该切片自己的冒烟 + 被它直接波及的模块定向重跑 | 数十秒 |
| 里程碑收口 | 全量回归（含引擎侧 PlayMode）+ ABI 探针 + meta 门禁 | 约 7 分钟墙钟 |
| 升级框架 / 依赖版本之后 | 全量回归 | 约 7 分钟墙钟 |
| 改了生产装配入口或多模块共享数据之后 | 全量回归 | 约 7 分钟墙钟 |

全量门禁的真实构成（两条线并行，墙钟取长的一条）：

| 线 | 步骤 | 用例数 | 实测秒数 |
|---|---|---|---|
| 非引擎线 | 编译 Core.sln | | 6 |
| 非引擎线 | dotnet test 七个测试工程 | 4793 条 Fact/Theory | 26 |
| 非引擎线 | ABI 探针 | | 4 |
| 非引擎线 | 工具链 pytest | 370 条 | 130 |
| 非引擎线 | 数值仿真基线比对 | | 16 |
| 引擎线 | 同步 DLL + 包清单核对 | | 25 |
| 引擎线 | 引擎编译检查 | | 39 |
| 引擎线 | EditMode 测试 | | 14 |
| 引擎线 | PlayMode 测试 | 362 条 | 105 |
| 引擎线 | 独立版构建 + 两种冒烟 | | 36 |
| 引擎线 | 消费方演练（构建 + 模板冒烟 + 私服安装） | | 60～120 |

结论：全量不是「一整天」，是 7 分钟；核心层 4793 条用例只要 26 秒。真正贵的不是用例数，是下面三样：引擎线只能串行、执行 agent 不能开引擎所以全部排队到主会话；工具链 pytest 一步 130 秒对核心层改动毫无关系却每次都跑；门禁全文进了 agent 上下文。

除上述三种时机外不跑全量。每轮全量只在 REGRESSION_LOG.md 追加一行（run_id / 通过或失败 / 对应提交），证据文件一律留在本地不入库。

### 5.2 兼容与发布

- **ABI 只新增**：新增重载、新增类型、默认接口成员、可选属性；不删改既有公开签名，可选参数也算加参数。改了公开签名必须自己跑一遍 ABI 探针。
- 破坏性变更走 ADR + 主版本号。
- 语义化版本；发布不可变（标签 + dist zip + lock）；维护分支 release/X.Y.x。
- **线上阻塞缺陷：修一个发一个**，不攒批；48 小时内出补丁版本并通知消费方版本号。

### 5.3 测试的写法

- 每个缺陷修复 = 一条复现用例 + 一条不变量用例。
- 不删测试、不放宽既有断言、不加重试掩盖问题；先复现再根治。
- 冷加载（资源异步加载完成）路径必须与热路径同一出口、同一规则，作为不变量的一支。
- 引擎侧 PlayMode 用例自带渲染隔离，不依赖别的用例清理。
- 保持确定性：不依赖字典枚举顺序、系统时间、当前文化。
- 因换真实数据翻红的旧用例：只是依赖了占位值就改期望；暴露真问题才修问题。

### 5.4 消费方（线上）反馈闭环

- 消费方反馈进总表续编号，整批处理，阻塞项优先。
- 上游缺口不绕行：需要上游动的，该功能停工，写成自包含反馈文档交由我转给上游；转去做不依赖它的切片。
- **每次发版后做一次复盘，复盘的产出是当场改 AGENTS.md 或门禁脚本**，不是一份放在文件夹里的文档。

### 5.5 AI 特有的风险与已有对策

这些坑本仓库已经踩过，规则已经在 AGENTS.md 里，团队接入后一条不少：

| 风险 | 表现 | 对策 |
|---|---|---|
| 假验证 | AI 把编辑落到主检出，门禁测的是未改动的代码 | 工作树自证：跑门禁前对照两处 `git status` |
| 藏缺陷 | 把「不处理的边缘路径」写成注释里的已知限制 | 已知限制必须逐条出现在汇报里，由人决定是否接受 |
| 结果丢失 | 提交、测试放后台，回合结束子进程被杀 | 提交、测试、构建、引擎批处理一律前台，拿到 sha 和输出才算完 |
| 并行撞号 | ADR 编号、判断记录编号顺序追加时自动合并不报冲突 | ADR 编号由派单方预分配；判断记录合并后统一核对重排 |
| 引擎元数据 | 新文件的 .meta 必须由真实引擎导入生成 | 涉及引擎导入范围的改动，AI 暂存后停下，由人跑一次含引擎的门禁再提交 |
| 规则膨胀 | 规则文件越写越长，新人先读一百条才能开工 | AGENTS.md 只放硬约束，方法论与旧教训进归档索引 |
| 上下文失效 | 会话过长后 AI 开始重复、遗忘 | 40 万 token 找任务边界切会话，60 万硬上限；切换前写交接文件 |

## 十一、模块边界与定向门禁（解决「改一处跑全量」）

### 11.1 问题与现状

现在的痛点：改一个子模块，门禁跑全量（核心六层 + 表现层 + 引擎侧 PlayMode），并且全量输出进了执行 agent 的上下文，token 与工时双重浪费。实测数据见 5.1：一次全量约 7 分钟墙钟，其中核心层 4793 条用例只占 26 秒。所以定向门禁省下的主要不是 dotnet test 的时间，而是：引擎线（串行、只有主会话能跑）、工具链 pytest（130 秒、与核心层改动无关）、以及进上下文的日志文本。

现状盘点后的判断：**模块边界已经存在且干净，不需要重新分模块。** 缺的是三样东西：影响集规则、门禁的定向模式、引擎侧用例的模块标签。

| 现状 | 事实 |
|---|---|
| 层级依赖 | 核心六层严格线性：foundation → numbers → rules → carriers → gameplay → sim；presentation 依赖 gameplay。每层一个类库、一个测试工程 |
| 子模块 | 每层 2～13 个子模块，各自带 `contracts/`、`core/`、`tests/`、README |
| 测试命名 | 测试命名空间统一为 `Tests.<层>.<模块>`，可以按模块过滤 |
| 已知跨模块交互 | 少量例外已写在 AGENTS.md 的文字里（如移动逻辑改动必须跑引擎侧移动 PlayMode 用例） |
| 门禁 | check.ps1 只有跳过类开关（Quick / SkipUnity / DocsOnly），没有「按改动路径选测试」的模式 |

### 11.2 设计决定

**一张表，两个用途。** 新增机器可读的模块表（建议 `toolchain/module_map.json`），每个子模块一条：路径前缀、所属层、测试过滤器、引擎侧 PlayMode 分类名、负责人、显式的跨模块交互例外。这张表同时是「模块分工表」和「定向门禁的选测依据」，不另写第二份。

**影响集分四级，由改动路径自动判定，执行 agent 不自己决定跑什么。**

| 级别 | 触发路径 | 跑什么 | 预期耗时（按 5.1 实测推算） |
|---|---|---|---|
| T0 文档 | `*.md`、`architecture/**`、`docs/**` | 门禁的 DocsOnly 模式 | 秒级 |
| T1 子模块内部 | `core/<层>/<模块>/core/**`、`tests/**`，未动 `contracts/` 与 `schema/` | 该模块过滤器 + 所在层测试工程 + 模块表里登记的交互例外 | 编译 + 十几秒，不碰引擎线、不跑工具链 pytest |
| T2 公开面 | 任何 `contracts/**`、`schema/**`、`Events.cs` 类公开类型 | T1 + 下游一层的测试工程 + ABI 探针；引擎侧只跑该模块分类的 PlayMode | 1～2 分钟 |
| T3 共享面 | `assembly/**`、`common/**`、`data/**`、`Directory.Build.props`、`adapters/stub/**`、`check.ps1`、`build.ps1`、编译进核心 DLL 包的入口 | 全量 | 约 7 分钟墙钟 |

T3 的 7 分钟本身可以接受；要控制的是它的频率。`common/`、`assembly/` 一旦成为高频改动路径，说明有东西放错了层，按 ADR 流程拆出去，而不是给 T3 再做细分。

补充规则：

- 一次改动命中多级，取最高级。
- 全量回归的三种时刻不变（里程碑收口、升级依赖、改共享面）。T3 只是把「改共享面」变成机器判定。
- 层级线性依赖意味着改 foundation 理论上波及全部；切片级只跑下游一层，剩余风险由里程碑全量兜底。这是有意的取舍，写进 ADR。
- **门禁输出分流**：全文写日志文件，回给执行 agent 的只有汇总表（步骤 / 结果 / 秒数 / 首个失败）。这是 token 消耗的直接来源，与选测同等重要。

### 11.3 要做的事（一个切片 + 一条 ADR）

1. ADR：登记四级影响集与「切片级只跑下游一层」的取舍。
2. `toolchain/module_map.json`：从现有目录与测试命名空间自动生成初版，人工补负责人与交互例外；AGENTS.md 里散落的定向回归文字迁入表中，文字只留一句「以模块表为准」。
3. check.ps1 增加 `-Changed <基线提交>` 模式：读 `git diff --name-only`，查表得出级别与测试集合，打印「本次判定：T? / 命中模块 / 将跑的过滤器」后执行；并支持 `-Modules a,b` 手动指定。
4. 引擎侧 PlayMode 用例按模块表加分类标签，定向模式按分类过滤。
5. 门禁增加一条自检：模块表覆盖所有子模块目录，出现未登记的目录即红。
6. 验收：对最近 20 个提交回放 `-Changed`，统计各级别命中次数与实测耗时，写进 ADR 作为凭据；目标是 T1/T2 占比 ≥ 80%，T1 单次 ≤ 5 分钟。

### 11.4 模块分工

负责人按层分配，每层一名切片负责人，登记在模块表里；跨层改动由上游层负责人拍板。团队规模小于层数时一人可负责多层，但表里必须有名字，不留空。

引擎侧适配层（`adapters/unity`）单独一名负责人，负责 PlayMode 分类标签与 .meta 门禁。
