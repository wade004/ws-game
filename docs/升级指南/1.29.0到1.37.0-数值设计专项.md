# 1.29.0 → 1.37.0 跨版本升级指南（数值设计专项 N0～N6）

本指南覆盖数值设计专项七个连续 MINOR 发布——1.30.0（阶段 N0 横切前置）、1.31.0（N1 属性）、
1.32.0（N2 装备与掉落）、1.33.0（N3 技能）、1.34.0（N4 经验与经济）、1.35.0（N5 校验全集与
编辑器契约面）、1.36.0（N6 数值仿真）——以及紧随其后的 1.37.0（N0～N6 深度代码复审修复版，
必须修 7 项、建议修 11 项、测试覆盖缺口 19 条，契约只新增，不改变本区间前七个版本的既有结论）。
每条结论标注来源版本号，来源是 `CHANGELOG.md` 对应版本的"新增/变更/迁移说明"小节、
`architecture/落地计划/数值设计分阶段落地计划.md` 末节"落地进度记录"对应阶段小节、相关 ADR
（0029～0035）的"决策"节；本指南不复制这些原文，只提炼"游戏要做什么"。全部代码标识符/表名/
检查名已经过 `git grep` 核对，与代码库拼写逐字一致。

## 1. 适用范围与读者

- **适用对象**：任何消费本框架、当前引用版本在 1.29.x～1.36.x 之间、打算升到 1.37.0 的游戏
  项目；若当前版本早于 1.29.0，先按其它已发布的迁移说明逐版升到 1.29.0，再从本指南开始。
- **游戏项目读者**：关注每节"必做"与"行为变更"，"可选采用"按需评估，"编辑器"一节可跳过
  （除非该游戏自带内容编辑器）。
- **编辑器项目读者**：每节"编辑器"小段是本指南面向编辑器项目的部分；也应通读对应版本
  `CHANGELOG.md` 文首"编辑器相关契约"索引小节——该索引按 `（1.3x.0）` 标注哪些条目属于契约面
  变化，是编辑器项目升级时唯一需要通读的入口，不必逐条重读框架 CHANGELOG 全文。
- **不适用**：本指南只覆盖数值设计专项（N0～N6）落地的变化；同一版本区间若框架还发布过其它
  专项的变化（本区间内没有），不在本指南覆盖范围。

## 3. 推荐升级路径

**直接升到 1.37.0**（推荐，适用于当前版本 ≥ 1.29.0 且团队能一次性投入评审窗口的项目）：一次性
按第 5 节"总检查表"逐项打勾即可，不需要在中间版本停留；本指南第 4 节的逐版本说明是给"总检查表"
条目提供上下文与理由，不是要求真的一版一版升级。

**逐版升级**（适用于希望每一步都单独跑一遍验收、或团队评审窗口有限、想把"必做/行为变更"拆成
多个小批次消化的项目）：按 1.30.0 → 1.31.0 → … → 1.36.0 → 1.37.0 顺序，每升一版跑一遍第 4 节
对应小节的"验证"命令，确认无异常再升下一版；两种路径最终检查表内容相同，只是节奏不同。

**版本号四处联动**：升级前确认下列四处将指向同一个目标版本号（不一致会在 `check.ps1` 的"版本
一致性"步骤或 `get_framework.ps1` 的锁文件校验环节报错）——

1. `toolchain/get_framework.ps1 -Version 1.37.0 -FromRegistry`（私服通道）或
   `-Version 1.37.0`（zip 通道，默认从 GitHub Release 拉取 `ws-game-1.37.0.zip`/`.lock`）；
2. 拉取后写入/校验游戏仓库根的 `ws-game.lock`（版本号、六个核心 DLL 哈希，若锁文件带
   `headless_dlls`/`validator_dlls` 字段则一并校验，1.36.0 起新增 `Core.Sim.dll` 归入
   `headless_dlls`，见附录 E）；
3. Unity 工程 `Packages/manifest.json` 里 `com.gamefoundation.adapter.unity`/
   `com.gamefoundation.adapter.headless`/`com.gamefoundation.toolchain` 三个包的依赖版本号
   （私服通道）；
4. `com.gamefoundation.framework-data` 包内容——首次或版本变化后需要重跑
   `toolchain/sync_package_content.ps1 -UnityProjectPath <你的 Unity 工程>` 把包内容同步到工程
   `StreamingAssets`/`TextMesh Pro`。

**升级前备份数据与存档**：本区间内多个版本改变了随机数消耗序列（1.32.0 掉落三次掷骰）、事件
发放行为（1.34.0 `TryPay`/货币掉落）与自动化行为（1.34.0 `RefillOnLevelUp`），升级前建议对
`data/`（游戏内容数据目录）与玩家存档做一次快照，便于升级后对比行为差异是否符合预期。

**升级后跑验证**：`python toolchain/validate_data.py --strict`（对合并后的数据根，以及
`data/_framework` 单独跑一次）+ 游戏自己的测试套件；若游戏侧维护了 `check.ps1`/CI 骨架，跑一遍
`-SkipUnity` 全量确认门禁步骤数与结果符合预期（1.36.0 起全量/`-SkipUnity` 步骤数由 24 变 25，
见第 4.7 节；1.37.0 步骤数不再变化，仍为 25，见第 4.8 节）。

**`SchemaMigrator` 迁移链的标准用法**（ADR-0029，`core/foundation/data_registry/core/
SchemaMigrator.cs`）：本区间三张表经历 schema 版本升级（`item.budget_curve`/`stat.rating_
conversion` 1.30.0、`stat.definition` 1.31.0、`skill.def`/`skill.aura_def` 1.33.0），均由框架
在**加载期自动迁移**，游戏侧数据文件不需要手改；但如果游戏侧内容工具需要"批量迁移一批行并
**写回磁盘**"（例如离线批处理脚本要把旧格式文件重写为新格式），标准做法是调用框架公开的整表
迁移入口，不要自行复刻链选取逻辑：

```csharp
// envelope 是符合 04 号文档"文件顶层信封"约定的完整表内容（表名、schema_version、记录数组）
var migrated = Core.Foundation.DataRegistry.SchemaMigrator.MigrateEnvelope(schema, envelope);
// migrated.schema_version 已改为当前版本；migrated_from 写入"最早的原始版本号"
// （若输入信封已带合法 migrated_from，保留那个更早的值，不用本次迁移前的版本号覆盖）
```

底层构件 `SchemaMigrator.BuildChain(schema, fromVersion, toVersion)`（只读链构造）与
`SchemaMigrator.MigrateRow(chain, row)`（单行迁移）也是公开契约，`MigrateEnvelope` 内部调用
它们；框架示例数据集 `data/_framework/found/found.migration_sample.json`（无运行时消费方）
专供内容工具端到端验证复刻实现是否与框架行为一致。

## 4. 逐版本升级说明

### 4.1 升级到 1.30.0（阶段 N0：横切前置）

**必做**

1. **数据表版本升级**：`item.budget_curve`、`stat.rating_conversion` schema 1→2——`entries`
   元素改名 `{item_level, budget}`/`{level, points_per_percent}` → `{x, y}`；框架加载期经
   `SchemaMigrator` 自动迁移，旧数据文件不用手改；若游戏侧有工具绕开框架加载直接读原始 JSON，
   需要改读 `x`/`y` 两个键。
2. **新的阻断级校验及踩雷点**：新增检查名 `curve_monotonic_finite`——对全部登记为断点表形态
   （`CurveSchema.BreakpointsField`）的曲线字段统一生效（不只是上面两张表，未来任何新登记的
   断点表曲线都自动受约束），要求断点非空、逐值有限、横轴严格递增无重复、纵轴不递减（允许平台
   段）；游戏层若已有自定义曲线数据违反此约束，升级后 `validate_data.py`/`dotnet test` 会报错，
   需要先修正数据。
3. **新的阻断级校验**：新增检查名 `level_curve_xp_monotonic`——`prog.level_curve.xp_to_next`
   必须沿等级不递减（末级条目按约定为 0，不参与比较）；游戏层若有"高等级所需经验反而更少"的
   自定义等级曲线，需要修正。
4. **元数据门禁**：新增 `field_curve_shape`（检查字段种类/子结构是否与登记的曲线形态相符）——
   只在框架/游戏层自行新增登记曲线形态字段（走 `FieldSchema.Curve`/`WithCurve`）时才会触发，
   多数游戏项目无需操作。
5. **报告结构变化**：`toolchain/validator --json` 新增 `rules[]`（每项含 `id`/`severity`/
   `non_escalatable`/`hits`）与 `issues[].group/note/rule_id`；均为纯新增字段，既有字段不变，
   若游戏侧脚本按字段集合数量做精确断言（而非只读已知字段），需要更新预期。
6. **不可提升警告新语义**：校验规则元数据新增 `NonEscalatable` 标记——这组警告在
   `Strictness=WarningsBlock`（把警告也当阻断的严格级别）下不会被提升为阻断。若游戏内容管线用
   了 `WarningsBlock` 且此前依赖"全部警告都会阻断"这一假设，需要了解本版本起有一组警告是例外
   （目前只影响框架自身规则，游戏层规则若未声明该标记不受影响）。

**行为变更**

- **`Strictness=WarningsBlock` 下"不可提升"警告组不阻断**：变了什么——校验框架新增
  `NonEscalatable` 概念；对游戏的影响——如果游戏走的是严格模式（警告也当错误），从本版本起某些
  警告即使命中也不会让内容加载失败（目前实际受益的是框架内置的少数规则，游戏侧新增自定义规则
  若也想享受这个语义，需要显式在自己的 `IValidationRule` 实现里覆盖 `NonEscalatable`）；保留旧
  行为的开关——无需操作，游戏层规则默认 `NonEscalatable=false`，行为与升级前一致。

**可选采用**

- `CurvePoint`/`PiecewiseCurve`/`CurveSchema.BreakpointsField`/`SaturationField`
  （`core/foundation/common`、`core/foundation/data_registry`）：通用曲线插值与形态登记工具；
  游戏层若要新增自己的曲线表，可直接复用，不必自己写插值算法。
- `SchemaMigrator.BuildChain`/`MigrateRow`/`MigrateEnvelope`（ADR-0029，见第 3 节末尾）：内容
  工具批量迁移写回磁盘的权威入口。
- `found.migration_sample` 演示表：无运行时消费方，仅供内容工具端到端验证迁移复刻实现。

**编辑器**

- `toolchain/validator --json` 新增 `rules[]`/`issues[].group/note/rule_id`：编辑器问题面板
  可按 `group` 分组展示、显示规则 id 与命中统计，非强制改动项。
- `--list-tables --json` 的 `field_meta` 新增 `curve`（曲线形态标记）：供曲线编辑控件区分断点表
  与饱和两种渲染方式（数值输入两参数 vs 断点表格）。
- 本版本 CHANGELOG 正文未单设"编辑器接入建议"小节，契约面变化以上述两点为主，详见
  `CHANGELOG.md` `[1.30.0]`。

**验证**

```powershell
python toolchain/validate_data.py --strict
# 期望：合并根与 data/_framework 单独校验均 0 error 0 warning（若游戏层曲线数据本身合规）

dotnet test Core.sln --filter "FullyQualifiedName~PiecewiseCurve|CurveMonotonicFiniteRule|ItemBudgetCurveMigration|RatingConversionMigration"
# 期望：全部通过

python -m pytest toolchain/tests -q
```

### 4.2 升级到 1.31.0（阶段 N1：属性）

**必做**

1. **数据表版本升级**：`stat.definition` schema 1→2——新增 `category`
   （`primary|derived|percent|defense|misc`）、`derived_from`（`Array<{stat, coefficient}>`，
   仅 `derived` 类别）、`clamp`（`{min?, max?}`，取代平级 `min`/`max`）、`conversion_ref`
   （仅 `percent` 类别）、`scope`（`any|from_player|from_creature`，缺省 `any`）五个字段；旧
   字段 `group`/`min`/`max`/`is_rating`/`rating_conversion_ref` 标废弃保留一个版本周期（本版本
   仍可读，`group` 起自本版本改为可选）。框架加载期自动迁移（`group→category` 映射：
   `resistance→defense`，`primary`/`derived` 恒等，`secondary` 按 `is_rating` 分裂为
   `percent`/`misc`；`min`/`max` 嵌套进 `clamp`；`is_rating=true` 且带
   `rating_conversion_ref` 时映射出 `conversion_ref`），旧数据文件不需要手改。
2. **被移除/废弃的 API**：`Core.Numbers.StatBlock.StatHostOptions.EnableRatingConversion` 标
   `[Obsolete]` 且**无效化**——评级换算层自本版本起始终启用，代码里不再有任何路径读取这个属性，
   不存在"关闭换算层"的开关；若游戏层代码显式设置过该属性（无论 `true`/`false`），编译期会收到
   过时警告但行为不受影响，可以直接删除这行设置。
3. **新的阻断级校验**：五个新检查名——`stat_definition_derivation_cycle`（派生无环）、
   `stat_definition_derived_from_requires_derived`（`derived_from` 仅限 `derived` 类别）、
   `stat_definition_conversion_ref_requires_percent`（`conversion_ref` 仅限 `percent` 类别）、
   `stat_rating_conversion_requires_one_shape`（`entries`/`saturation` 恰好二选一）、
   `arch_class_derivation_override_requires_existing_edge`（职业派生系数覆盖的边必须真实存在）。
   常见踩雷点：给非 `derived` 属性填了 `derived_from`，或给非 `percent` 属性填了
   `conversion_ref`——这两种此前不受检查，升级后会阻断加载。
4. **新的警告级校验（不可提升）**：`stat_definition_no_consumer`——`stat.definition` 记录未被
   任何登记为引用它的字段/引用声明/框架内置消费者清单（`stat.armor`/
   `stat.damage_done_pct`/`stat.damage_taken_pct`/`stat.healing_done_pct`）消费时报警告；1.35.0
   起额外把 Expr 表达式里的 `self.stat(<id>)`/`target.stat(<id>)` 引用也计入消费者（见 4.6 节），
   本版本尚未纳入这一条，可能比升级到 1.35.0 后看到更多告警，属预期，会在 1.35.0 收窄。
5. **兼容性字段新增**（不阻断，但改变可读取到的选项集合）：`combat.hit_table_config.miss` 新增
   可选字段 `hit_stat`（攻击者命中属性引用）；`CombatOptions.DamageTakenPctStat`（单值）之外
   新增 `DamageTakenPctStats`/`CritTakenReductionStats`（集合，默认空列表）。两者均"未配置则
   行为与升级前逐位一致"，不强制操作，但游戏层若准备使用等级差表（见下"可选采用"）或多属性承伤
   减免，需要知道这两处新入口。

**行为变更**

- **评级换算层始终启用**：变了什么——`category=percent` 的属性即使未引用曲线（`conversion_ref`
  缺省），也会经"恒等曲线"处理（数值上等价于直通，但确实经过了换算路径）；对游戏的影响——若
  游戏层此前依赖"显式设置 `EnableRatingConversion=false` 时百分比属性直通原始值"这一行为，
  升级后该设置不再有任何效果（换算层始终执行，恒等曲线下数值结果不变，但如果游戏层同时给某个
  `percent` 属性配置了非恒等的 `conversion_ref` 曲线，该曲线现在会真正生效）；保留旧行为的
  开关——无，唯一能维持"直通"效果的办法是不给该属性配置 `conversion_ref`（保持恒等）。

### 4.4 升级到 1.33.0（阶段 N3：技能）

**必做**

1. **数据表版本升级**：`skill.def`/`skill.aura_def` schema 1→2——`school_damage`/`heal`/
   `periodic_damage`/`periodic_heal` 效果参数新增 `scaling`（`Array<{stat, coefficient}>`）与
   `base_curve_ref`（引用新表 `skill.base_curve`）。框架加载期自动迁移（旧单字段
   `scaling_stat`/`coefficient` 补出等价 `scaling` 列表，旧字段原样保留不删除），旧数据文件不
   需要手改。
2. **新增表**：`skill.budget_rule`（技能预算规则：施放时间当量、冷却溢价/范围折价/消耗溢价
   曲线、带宽、硬上限、控制类别权重、玩家档/怪物档）——未注册对应 id（缺省
   `skill.budget_rule.default`）时按缺省值处理（`beat_seconds=1.0`）不阻断；游戏层不急于填写
   完整字段也能升级，但预算类校验（见下）在 1.36.0 接入锚点表后才会真正产出问题。
3. **新的阻断级校验**：`skill_budget_hard_cap_exceeded`（技能预算比值超硬上限且无 `budget_note`
   说明）——本版本因锚点表（1.36.0 才落地）未接入，实际不产出任何问题，属预期。
4. **新的警告级校验（不可提升）**：`skill_no_time_cost`（主动技能 `cast_time` 为零且
   `respects_gcd` 为真、未声明反应类）——**本条本版本即真实生效**，游戏层若有这类技能配置需要
   补 `cast_time` 或声明为反应类（`respects_gcd=false`）；`skill_budget_deviation`/
   `item_grant_value_exceeds_share`（不可提升，均依赖锚点表，1.36.0 前不产出问题）。
5. **`weapon_damage_pct` 效果原语语义变化**：由"武器单次伤害 × 百分比"改为"武器秒伤 × 一拍
   常数 × 百分比"。**游戏侧已有使用该原语的技能，其百分比数值需要重新校准**（不受武器攻速影响
   这一新特性本身是设计意图，但意味着旧百分比在新公式下算出的绝对值会变）。
6. **新失败原因码**：`CastFailureReason.ConditionNotMet`/`ActionLocked`（与 `SkillReadinessBlockers`
   同名两位）——UI/AI 消费方若对施法失败原因码做穷尽 `switch`，需要补处理分支（未处理时按
   "未知失败原因"通用兜底展示，不会崩溃，但用户体验会打折）。
7. **`MaxEffectsPerSkillRule` 改读选项**：构造上限由硬编码 8 改读 `SkillOptions.
   MaxEffectsPerSkill`（缺省仍是 8）——纯回归，无需操作。

**行为变更**

- **周期效果来源缺失时"冻结"取代"归零"**：变了什么——`periodic_damage`/`periodic_heal` 的来源
  单位在光环仍生效期间被销毁后，每跳值从"缩放贡献按 0 处理"改为"冻结为最后一次来源仍存在时算
  出的每跳值"；对游戏的影响——数值上通常显著更高（不再归零）；保留旧行为的开关——无，恒生效，
  无策略配置项。
- **`SkillOptions.PlagueRefreshRatio` 缺省 0.3**：变了什么——同来源同光环再次施加（刷新）时，
  新持续时间 = 定义持续时间 + `min(剩余时长, 定义持续时间 × 0.3)`，取代此前"直接重置为定义持续
  时间"；对游戏的影响——不显式设置该项的游戏默认即获得"刷新最多额外保留 30% 定义时长"这一新
  行为，光环刷新后持续时间比旧版本更长，需要重新评估战斗节奏/DPS 曲线；保留旧行为的开关——显式
  设置 `SkillOptions.PlagueRefreshRatio = 0` 精确退化为旧行为。
- **`GcdEnabled=false` 下节拍锁新语义**：变了什么——`respects_gcd=true` 的技能在他技能动作
  时长内返回新增失败原因码 `ActionLocked`；`respects_gcd=false` 的瞬发反应类技能（打断/格挡/
  保命）可在动作中插入执行、不占用法术队列；`respects_gcd=false` 但非瞬发时回退 `Busy`；对
  游戏的影响——关闭公共冷却（`GcdEnabled=false`）的游戏里，已声明 `respects_gcd=false` 的既有
  技能行为由"读条中一律拒绝/排队"变为"可插入立即执行"，需要确认这符合设计意图；保留旧行为的
  开关——通过 `respects_gcd` 字段本身控制（既有字段，无新增开关，把该字段改回 `true` 即回到
  受节拍锁约束的行为）。

**可选采用**

- `SkillBudgetAnalyzer.Analyze`/`ComputeGrantValue`（`core/rules/skill`）：技能预算分析，锚点
  接入前可用 `null`/自定义 `ISkillBudgetAnchorProvider` 调用做预评审。

  施放一次技能，是"一键智能释放"功能的天然实现入口。

  `creature.tier_definition.control_immune_categories`：按控制类别免疫，可选，与既有
  `control_immune`（全部类别）并存、互不覆盖。

- `skill.base_curve`：技能效果基础值按施法者等级取曲线值，可选，不填则效果保持既有 `base_value`
  写法。

   游戏层已有手填价格的商品需要一次性评审是否在带宽内。

   EconomyCurrencyOverflow` 常量。事件流查看器/日志面板若按事件名过滤展示，需要认识这两个新
   事件。
5. **旧签名行为断裂点**：`IEconomyHost.TryPay(Id,Id,long)`（无 `reason` 三参签名）**从本版本
   起也会在扣费成功时发 `economy.charged`**（此前该签名不发任何"扣费"事件，只有 `Add` 间接发
   `currency_changed`）。**依赖"旧签名不发扣费事件"这一既有行为的下游逻辑需要重新核对**（新的
   四参签名 `TryPay(unitId, currencyId, amount, reason)` 是推荐用法，旧签名内部转发新签名并
   传占位 `reason="unspecified"`）。

   需要处理"条目可以是物品或货币"两种类型**，货币恒能全额入账、不受背包容量影响。

   上限（此前该字段只是登记壳，不产生任何效果）；不想要该新行为需要显式设置
   `ProgressionOptions.RefillOnLevelUp = false`。

**行为变更**

- **`EconomyOptions.DefaultBuyPricePct` 语义变化**：变了什么——字段名与默认值 `0.25` 不变，但
