是否发生、是否是新增行为的正面效果）才能不误判为回归。

## 教训一：不要靠"用例之间清空全局资源缓存"解决测试串味

**背景**：`SpriteEquipVisualWiringTests`/`EquipmentVisualReplayTests` 共享同一资源引用字面量
（`paperdoll.item.sample_hero_hat_test`）。单独跑各自的用例都通过，但全量门禁里出现执行顺序
依赖：一个用例先把该资源标记为"已加载"，后一个用例的"加载前进度应为 0"断言就会落空。

**第一版方案（提交 `0a07c0c`，已撤销）**：新增 `UnityResourceLoader.UnloadAllImages`，由
`Tests/Runtime/PlayModeIsolation.cs` 的 `TearDownAfterTest` 在每条 PlayMode 用例结束后清空
`ResourceKind.Image` 类别的"已加载"缓存，试图让每条用例都从"未加载"状态开始。

**为什么这是反例**：`UnityResourceLoader` 是 `DontDestroyOnLoad` 单例，跨整个 `-runTests` 进程
只有一份实例。清空它内部的 Image 类缓存，只是清掉了"底层已加载资源"的记录，但上层各处维护的
"是否已发起过加载/是否已加载完成"去重表、进度缓存等状态并不会跟着一起清空——两边一旦脱节，会
出现"底层缓存说没加载过，上层去重表说已经处理过，于是这次加载请求被去重逻辑直接跳过，资源
永远不会真正重新加载"的新故障模式。真实引擎门禁实测（288 条，285 通过，3 失败）证伪了这个方案：
`GreyBoxTests.Move_Right_IncreasesPlayerX_AndTurnsSideways`/`GreyBoxTests.
PlayerView_ExistsAndLayerResourcesLoaded_NotPlaceholder`/`VerticalSliceTests.
Paperdoll_LayerOrder_MatchesDisplayMapDeclaredOrder` 三个原本毫不相干的用例全部新增失败，症状
统一是"精灵/纸娃娃层资源加载不到"——比原来两个用例的串味问题更严重。

**正确做法（提交 `3242702`，已落地）**：不清理任何共享状态，而是给 `SpriteEquipVisualWiringTests`
换一个它独有的资源引用字面量 `paperdoll.item.sample_hero_hat_wiring_test`（新增
`display.equip_visual.sample_hero_hat_wiring_test` 一行 + 配套占位资产，并入
`toolchain/import_sample_assets.py` 既有生成流水线的 `PAPERDOLL_FILES` 列表）。"这个资源之前
未被加载过"这一前提由夹具本身独占保证，断言与其它用例的执行顺序无关，不需要任何跨用例清理逻辑。
`EquipmentVisualReplayTests` 未改动。

**推广到规则**：`DontDestroyOnLoad` 单例（或任何跨用例存活的全局状态）里，"看起来只是一份缓存"
的字段，背后可能有其它模块按同一份数据维护的派生状态（去重表、索引、计数器等）。清空缓存本身
容易做，但很难保证清空动作覆盖了所有依赖该缓存做去重/去抖的下游状态；一旦遗漏，故障会从"两个
用例互相看见对方的痕迹"变成"资源再也无法重新加载"这种更隐蔽、影响面更大的新问题。**优先给
失败用例配专属输入（专属字面量/专属数据行/专属占位资产），让断言不依赖执行顺序，而不是尝试
在用例之间清理共享状态**——专属夹具的成本通常比"梳理清楚一份全局缓存有哪些下游依赖"低得多。

## 教训二：PlayMode 用例失败先分诊再归因，不要默认是回归

本轮 3 处失败中：

- 2 处（`VerticalSliceTests` 的 `FullVerticalSlice_...`/`PRES180_...`）的真实性质是**测试把
  旧的错误行为写成了预期**：这两处用例此前用 `LogAssert.Expect` 断言"`sprite_anim.sample_hero_*`
  六个状态里尚未发起过加载的那些会产生一条加载失败警告"——这本身是在给"资源加载失败"这个此前
  存在的缺陷（`ResolveEffectDir` 固定拼 `vfx/`，`sprite_anim.*` 必然找不到文件）拍照。本批把
  `ResolveEffectDir` 修好之后，六个状态的资源全部能真实加载成功，原先预期的警告自然不再出现，
  `LogAssert.Expect` 因此落空。**这不是回归，是修复生效后旧测试口径过期**；正确处理是把断言
  换成正面验证新行为（新增 `AssertAnimResourcesLoadedSuccessfully`，轮询确认六个状态均已真实
  加载成功），而不是恢复旧的失败预期或删除断言。
- 1 处（`SpriteEquipVisualWiringTests`/`EquipmentVisualReplayTests` 串味）是既有的、教训一
  描述的测试互相干扰问题，**同样非产品缺陷**。

三处失败**均非产品缺陷**，但如果不先分诊，仅凭"全量门禁新增了失败用例"这个表面事实，很容易
误判为本批改动引入了回归，从而在产品代码里做不必要甚至方向错误的修改。正确顺序是：

1. 先用 `python toolchain/unity_test_triage.py --xml <path>.xml --log <path>.log` 分诊，看
   用例窗口内的首个异常（不是 NUnit message 表面文本，理由见
   [排查复盘-2026-09-15-PlayMode-PRES180.md](排查复盘-2026-09-15-PlayMode-PRES180.md)"真实
   根因"一节）。
2. 核对失败用例的断言在验证什么、对应的产品行为在本批改动前后是否发生了预期内的变化——若断言
   本身是在给"已知即将被修复的旧错误行为"拍照，修复生效后断言过期，是测试侧问题，不是回归。
3. 只有排除"断言写的是旧行为"和"跨用例共享状态串味"两类测试侧问题之后，才需要怀疑产品代码
   本身引入了新缺陷。

## 教训三（补记，2026-09-19 同日）：资源加载类断言必须自行等待，不能靠"更早的用例已经预热"

本文档发布同一天，真实引擎门禁又实测暴露了同一大类问题的另外两个实例（与教训一的"共享
资源引用字面量互相看见对方痕迹"不同，这两处是"断言依赖某资源已加载，用例自身既不触发加载
也不等待"）：

- `GreyBoxTests.Move_Right_IncreasesPlayerX_AndTurnsSideways`：移动后立即断言场景里存在一个
  侧向方向档位的纸娃娃层精灵，但侧向档位（`layer.{spriteSetName}__side_r__{layerName}` 等）
  是本用例移动之后才第一次被引用的资源——`SpriteViewBase.ResolveLayerResourceId` 把方向档位
  编码进资源 id 本身，front 与 side_r 是两个完全不同的资源，各自独立经 `UnityResourceLoader`
  异步加载。全量门禁里能通过，是因为更早跑过的其它用例（例如本套件的
  `PlayerView_ExistsAndLayerResourcesLoaded_NotPlaceholder`）已经引用过同一份资源、把它预热
  进跨用例共享的 `UnityResourceLoader` 缓存；单独用 `-testFilter` 跑本用例，资源确实还没加载
  完成，断言必然落空（实测：total=1 passed=0 failed=1）。
- `VerticalSliceTests.Paperdoll_LayerOrder_MatchesDisplayMapDeclaredOrder`：进入世界后立即
  断言纸娃娃层精灵数量 ≥ 2，同理——三层纸娃娃资源是异步加载的，本用例自己完全没有等待，全量
  门禁里靠同套件更早跑过的 `FullVerticalSlice_.../PRES180_...`（两者都会为同一玩家外形
  `EnterInWorld`）预热缓存才侥幸通过。

**这与教训一的区别**：教训一是两个用例共享同一份资源引用字面量，互相看见对方"已加载/进度非
零"的痕迹，解法是给失败用例换一个专属字面量。这里的两个用例并不共享字面量、也不会被别的用例
"污染"出错误状态——问题是用例自己完全没有对"资源确实已经加载完成"这件事做任何等待或触发，
断言能通过纯粹是运气好、命中了资源已经被别人预热的时机。解法方向也不同：不是换专属输入，而是
让用例自己轮询等待到资源真正加载完成再断言，超时给出"等的是哪个资源、等了多久"的明确失败
信息——即"正面做法"一节。

## 正面做法：用轮询等待代替"假设资源已经预热"

根治上面两处用例，用的是本仓库已有的既有惯例（并非新发明）：`GreyBoxTests.
PlayerView_ExistsAndLayerResourcesLoaded_NotPlaceholder`（等纸娃娃 body 层精灵出现，超时 5
秒）与 `VerticalSliceTests.AssertAnimResourcesLoadedSuccessfully`（1.44.0 新增，轮询
`UnityResourceLoader.TryGetEffect` 命中作为"确实加载成功"的正面判据）已经示范了正确写法：

1. 用一个有限的超时（秒数或帧数上限），循环里重新查询一次"资源是否已经就位"的正面判据（本仓库
   目前有两种判据形态：`FindObjectsByType<SpriteRenderer>` 查找符合命名规则的真实精灵实例；
   或 `IResourceLoader.TryGetEffect`/`IsLoaded`/`GetLoadProgress` 直接问资源加载器本身），成立
   就跳出循环。
2. 循环体必须 `yield return null` 让 Unity 至少跑一帧（`UnityResourceLoader` 的加载是后台线程
   读取 + 主线程 `Tick` 完成解码/回调，不让引擎跑帧，回调永远不会被执行）。
3. 超时后再做一次断言（不是在循环内断言失败就退出），失败信息要点名"在等哪个资源引用/命名
   规则、等了多长时间、目前的实际状态是什么"，方便下次真的回归时不需要重新排查就知道卡在哪。
4. 不同类别的资源要用各自对应的正面判据，不能把某一类的写法直接照抄到另一类（本次两处修复：
   纸娃娃层与方向档位精灵用 `SpriteRenderer` 命名查找，动画剪辑用 `TryGetEffect`——判据形态
   不同，不能混用）。

反过来，"额外起一次 `-testFilter` 隔离门禁步骤，专门跑这类资源加载敏感用例来防回归"这条路径
已评估但未采纳，理由与更轻的替代方案见
`adapters/unity/Packages/com.gamefoundation.adapter.unity/README.md`"PlayMode 用例写法约定：
资源加载类断言必须自行等待"一节，不在本文档重复。

## 教训四：测试在全量跑里假通过，掩盖了一个真实产品缺陷——轮询等待本身修不好一个"结构性从不回填"的缺口

**背景**：`aeef183`（`fix/resource-load-refresh` 的上一轮，`fix/playmode-order-dependency` 分支）
把 `GreyBoxTests.Move_Right_IncreasesPlayerX_AndTurnsSideways`/`VerticalSliceTests.
Paperdoll_LayerOrder_MatchesDisplayMapDeclaredOrder` 两处一次性快照断言改成了轮询等待 5 秒，
意图根治"隐性执行顺序依赖"（全量跑靠更早用例预热缓存才通过，单独跑必失败）。但主会话实测复核
（隔离跑两条用例，`scratchpad/iso_fix1.xml`/`iso_fix2.xml`）显示：改成轮询等待后，两条用例
**仍然在 5 秒超时后失败，等待时长完全不影响结果**——这不是"轮询等待写得不够久"，而是轮询这个
修法从设计上就假设了一个不成立的前提："资源加载完成后，画面会自动跟上"。

**真因（诊断记录 `scratchpad/diag-isolation.md`，本轮修复的产品缺陷本体）**：
`ResourceReferenceTracker.EnsureLoading`（`presentation/common/core/ResourceReferenceTracker.cs`）
此前调用 `IResourceLoader.LoadAsync` 时固定传空操作回调 `(_, _) => { }`；
`UnityRenderer2D.SetLayers`（`adapters/unity/.../UnityRenderer2D.cs`）在被调用的那一瞬间**同步**
把当时能解析到的精灵（命中缓存则真实精灵，未命中则占位方块）写进 `SpriteRenderer.sprite`，此后
除非"层集合变化"（装备事件）或"朝向变化"（`UnitySpriteView.SyncPose` 的边沿触发）再次调用一次
`SetLayers`，没有任何机制在资源异步加载**真正完成之后**回头刷新已经画出来的占位方块。全量门禁
能通过，只是因为同一 `-runTests` 进程里更早的用例用同样有缺口的一次性调用碰巧先把相同资源 id
读进了跨用例共享的 `UnityResourceLoader` 缓存——两条用例自己发起的加载"发起了也没用，除非缓存
提前已有值"。

**教训一（"清空全局缓存"）与本教训的关系**：教训一处理的是"两个用例互相看见对方缓存痕迹"这类
串味，正确做法是给失败用例配专属夹具；本教训是同一类"全量跑假通过"现象背后的**另一种**根因——
不是缓存脏了，而是缓存"命中之后没有人负责通知渲染层"这个环节本身就不存在。两类问题的表面症状
相似（单独跑失败、全量跑通过），但診断与修法完全不同，再次印证"先分诊、核对被测行为是否真的
发生，再动手"（教训二）比"看到表面相似就套用上一次的修法"更重要——本轮如果不做隔离跑+诊断
（`diag-isolation.md`），只按"轮询等待不够久"的表面猜测去加长超时时间，无论加多久都不会通过。

**正确做法（本次提交，分支 `fix/resource-load-refresh`）**：给
`ResourceReferenceTracker.EnsureLoading` 新增 `onComplete` 回调重载（ABI 只新增，保留原双参数
重载不变）；`SpriteCharacterRig`/`SpriteViewBase` 把这个回调统一接到
`SpriteCharacterRig.HandleResourceLoadCompleted`——加载成功时用"最近一次已知的完整层列表"重新
调用一次 `ApplyLayers`，让占位方块有机会被迟到的真实资源替换；加载失败时不重新应用，改记一条
`IPresentationDiagnostics` 警告，不静默。`GreyBoxTests`/`VerticalSliceTests` 那两处轮询等待
**保留不改**——轮询等待本身的写法没有错（超时给出明确失败信息、不放宽断言），只是在产品代码
缺口补上之前，等多久都没用；补上之后，轮询等待才真正有意义（等的是一个会在合理时间内变为真的
条件，不是一个永远不会变的条件）。核对后发现两处断言（`r.sprite.name.StartsWith("layer....")`）
本身已经在区分"真实精灵"与"占位方块"（占位方块的 `Sprite.name` 固定是 `"placeholder.sprite"`，
不会匹配该前缀），不需要按"从'有精灵'改成'是真实精灵而非占位'"再额外加强——这是本次复核确认
"断言本身已经写对，只是背后的产品代码没有能力让它在合理时间内变真"的又一个例子。

## 教训五：三轮"修复无效"其实是构建产物陈旧——`git checkout` 从不更新 Unity 加载的 DLL 副本

**现象**：教训四那处修复（改的是
`presentation/render/core/SpriteCharacterRig.cs`，编译进 `Presentation.Common.dll`）落地后，
连续三轮只切源码分支、不重新构建就直接跑 PlayMode 隔离用例（`GreyBoxTests.
Move_Right_IncreasesPlayerX_AndTurnsSideways`/`VerticalSliceTests.
Paperdoll_LayerOrder_MatchesDisplayMapDeclaredOrder`），三次结果都是同样的失败、报错文字
一字不变，被误判为"这个修复没生效"。

**误判链条**：
1. 第一层误判——"构建产物陈旧"被误读为"修复无效"：三轮切分支后直接跑 Unity 测试，
   `adapters/unity/Packages/com.gamefoundation.adapter.unity/Runtime/Plugins/Core/*.dll`
   是 gitignore 的构建产物，`git checkout`/切分支从不更新它；Unity 编辑器实际加载的是这份
   旧二进制，跑的从始至终是教训四修复之前的代码，报错文字当然不变。
2. 第二层误判——"修复无效"被进一步误读为"时序竞态"：一个诊断 agent 为了加日志排查，顺带
   触发了一次完整重建（构建时会重新生成并同步 DLL），之后用同样的输入不再复现失败，
   于是得出"加了诊断探针就不复现 = 存在时序竞态"的结论——实际上探针本身没有改变任何时序，
   改变结果的是探针连带触发的那次重建让 Unity 第一次真正加载到了教训四的修复。

**真因与证据**：
- 根治：重新构建并同步 DLL（不带 `--artifacts-path`、默认路径构建 + `build.ps1 -SyncOnly`）
  之后，同样两条隔离用例 4/4 通过。
- 反向确认：把教训四的修复注释掉、重新构建同步后，同样两条用例必然失败——因果关系至此钉死，
  排除"环境抖动"等其它解释。
- 证伪"竞态"猜测：探针实测资源加载全程耗时约 8ms，远小于用例原本等待的 5 秒轮询窗口；如果
  真是"5 秒窗口不够"的时序竞态，8ms 的实测耗时不可能支持这个假设——进一步说明第二层误判
  （"加日志就不复现 = 竞态"）从一开始就没有认真核对时间量级，只是因果颠倒后的顺手结论。

**根因定位（技术侧）**：`build.ps1:525` 一带的 DLL 同步步骤，源路径固定读
`$asm.Dir + "\bin\$Configuration\netstandard2.1\"`（dotnet 默认构建输出路径），而 AGENTS.md
§4 原文要求"`dotnet` 命令一律带 `--artifacts-path`"。两条规则字面上冲突：按 §4 用
`--artifacts-path` 构建后再 `build.ps1 -SyncOnly`，同步的是**默认路径下更早一次构建**遗留的
陈旧 DLL；此前 `build.ps1:528-529` 只在源文件**缺失**时报错，文件存在但陈旧则静默同步旧的，
没有任何提示，三轮假失败由此而来。

**可复用的教训**：
1. gitignore 的构建产物不随 git 操作更新——切分支、`git checkout`、`git stash` 都不会重新
   编译；要验证"某处 Unity 侧行为是否因为一处 C# 改动而变化"，必须先确认对应的产物已经用
   当前源码重新构建过，切提交本身对二进制行为的验证是无效的。
2. "加了诊断动作就不复现"不能直接当成"存在时序竞态"的证据——诊断动作本身（尤其是会顺带
   触发重建/同步/重新加载资源的动作）可能才是让结果变化的原因；应先核实诊断动作本身有没有
   副作用，再考虑竞态一类更复杂的解释。
3. 类似"某处修复看起来无效"的结论，落笔之前应该有一步反向确认：把修复改动去掉、走一遍完全
   相同的验证流程，确认失败**必然**复现；如果反向确认也通不过复现（比如产物没同步），说明
   前面的"验证"根本没有验证到目标代码，结论应作废重来。

**本单已落地的技术根治**：`build.ps1` 的 DLL 同步步骤新增陈旧检测（源 DLL 早于其对应源码
目录下最新 `.cs` 文件时直接报错终止，见 `build.ps1` 内 `Test-CoreAssemblyDllStale` 函数），
并在 AGENTS.md §4 明确了"涉及 Unity 侧感知的 C# 改动必须用默认路径构建再 `-SyncOnly`"的例外
条款，见该文件本节改动与判断记录。
