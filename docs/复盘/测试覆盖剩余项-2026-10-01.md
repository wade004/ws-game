## 需拍板项

### 门禁（第 4 节 I-5～I-13 中需设计层决定是否做）

- **I-5 工具链环境矩阵（不设 `PYTHONUTF8` + PowerShell 5.1/7 双宿主）**：利是补上 11 章 §8 要求的矩阵，能抓编码/宿主差异类缺陷；弊是工具链 pytest 与 CI 时长近翻倍，且需维护双宿主夹具。折中：只对涉及子进程与文件编码的少数用例跑矩阵。
- **I-6 IL2CPP/AOT 进默认门禁或发布门禁**：利是核心库在 AOT 下的真实可运行性发布前有证据，消除发布盲区；弊是每轮多出一次 IL2CPP 构建（分钟到十余分钟）且依赖 IL2CPP 模块与许可。折中：只进 `build.ps1 -Release`，不进日常 `check.ps1`。
- **I-7 `build.ps1 -Release`/`-Dist` 自动化 dry-run 用例**：利是发布脚本回归（zip/lock、半途恢复，1.39.0 曾因 `Compress-Archive` 出过事）能被自动捕获；弊是 1842 行脚本、仅 Windows、耗时长，写不稳易 flaky。折中：复用已有 `-Dist X-dryrun` 路径，只断言产物清单与 lock。
- **I-9 无测试脚本补测（`sim_baseline`、`install_hooks`、`init_publisher`、`sync_package_content`、`consumer_smoke`）**：利是脚本改动不再裸奔；弊是多数依赖私服、git hooks、Unity 环境，测试耦合重而收益低。折中：只补 `sync_package_content`（影响包内容）。
- **I-10 生成器逻辑单测（`gen_placeholder_assets`、`import_sample_assets` 等）**：利是在现有 `--check` 一致性之上再保正确性；弊是体量大（单文件 1255 行）、投入大而已有门禁已兜住产物一致。折中：只补 `unity_test_triage`、`format_data`。
- **I-13 CI 跑 Unity / 限制 `-ReleaseSkipUnity`**：利是 EditMode/PlayMode/消费方演练进 CI，堵住发布时整段跳过 Unity 的口子；弊是需自托管 Windows runner 与 Unity 许可（批处理许可曾报错误码 198），成本高。折中：不上 CI，改为 `-Release` 要求 `REGRESSION_LOG.md` 里有同提交的含 Unity 全量记录，禁用 `-ReleaseSkipUnity`。

I-2 余项（Perf 诊断行缺失改 FAIL）、I-8 余项、I-12 余项是低成本的直接可做项，不需拍板。
