## 1. 定位声明

本架构是一套**技术无关、游戏无关**的 2.5D Windows 单机 RPG 技术基础架构：

- **技术无关**：架构描述只使用中立的接口签名与数据表结构，不出现任何引擎、编程语言、框架或工具的名字。所有对具体技术的依赖被收拢到「引擎适配层」（见 `02_引擎适配层.md`）背后，引擎选型是独立于本架构的研究课题，**本架构不预设选型结论**。
- **游戏无关**：架构不承载任何一款具体游戏的专属设定。任何"这个游戏有几个技能""目标怎么选""有没有消耗品"之类由游戏口味决定的问题，架构只提供机制与配置位，不给出答案；答案由「游戏层」的数据与配置回答。
- **参考系明确**：架构在系统结构上参照魔兽世界的真实设计（法术/效果/光环/触发体系、战斗日志、命中判定表、仇恨表、物品与生物模板、掉落与任务模板、通用条件表、阶段化、外形映射、数据化 AI 等），但裁剪为单机、单玩家、无网络的 2.5D 形态。参照关系在各专题文档中逐项点明对应物与裁剪方式。
- **表现形态可选**：表现形态由游戏层选择：默认 2D 精灵，可选 3D 模型；逻辑均为二维平面坐标，场景默认 2D 地面图，具体外形类型的机制与数据结构见 `02_引擎适配层.md`、`04_数据与内容管线.md`、`09_表现层.md` 与 ADR-0012。
- **时间模型可选**：战斗时间模型由游戏层选择：即时、回合制、或探索即时战斗回合（探索连续推进、进入战斗切换为离散回合）；规则层（技能、光环、触发、结算、仇恨、目标选择）只依赖"经过了多少时间单位"，不区分具体时间模型，机制见 `03_运行时骨架.md`、`04_数据与内容管线.md`、`06_规则层_属性技能战斗AI.md` 与 ADR-0013。

## 2. 目标与非目标

### 2.1 目标

1. **一套骨架承载后续所有游戏**：新游戏 = 选引擎实现适配层 + 写薄薄的游戏层 + 填数据表 + 配表现资源；新内容 = 加数据行加资源，不改运行时；新原语是唯一代码开口，且必须走审批。
2. **逻辑与表现彻底分离**：逻辑不知道画面与引擎；表现只订阅事件与只读状态，不能反向驱动逻辑。
3. **引擎可替换**：运行时核心不依赖任何引擎；引擎能力全部经适配层接口进入运行时。
4. **可测试可确定**：核心模拟采用固定步长驱动，同种子、同输入产生同结果（在同一平台与同一运行时二进制下逐位一致；跨平台只承诺逻辑等价、不承诺逐位一致）；每个模块可脱离引擎独立测试。
5. **模块可拆走复用**：每个系统是一个独立目录，只靠窄契约接口与事件总线接入整体，可被单独抽出复用到其他项目。

### 2.2 非目标

以下能力明确不在本架构范围内，后续任何文档不得为它们设计支撑机制：

| 非目标 | 不做的理由 |
|---|---|
| 网络多人 | 目标形态是单机单玩家，网络同步与服务端权威模型会给对象模型、时序模型带来架构级复杂度，与"单机骨架"定位冲突 |
| 服务端 | 没有网络多人就没有服务端权威的必要性，避免为不存在的客户端-服务端边界预留抽象层 |
| 反作弊 | 反作弊只在存在他方博弈（网络对战、排行榜）时才有意义，单机本地运行没有作弊对象 |
| PvP | PvP 需要平衡性对抗设计、控制递减、战场/竞技场等专属系统，属于游戏口味而非通用骨架 |
| 社交经济（公会/邮件/拍卖行/聊天） | 依赖多玩家共同在线，单机环境下没有交易对手方，做了也用不上 |
| 跨服 | 跨服是多服务器部署的产物，单机没有"服"的概念 |
| 玩家插件 API | 插件 API 是面向终端玩家开放的二次开发接口，与"架构面向游戏开发方"的定位不同层次，且引入不可控的运行时安全面 |
| 3D 渲染 | 目标形态明确是 2.5D（二维世界坐标 + 纵向排序）；表现形态由游戏层选择，默认 2D 精灵，可选 3D 模型作为可选外形路线（见 ADR-0012），逻辑均为二维平面，场景默认 2D 地面图；本行排除的是脱离该约定的全三维场景、三维碰撞与三维导航，它们是完全不同的技术栈，不在裁剪范围内 |
| 载具飞行 | 飞行载具依赖三维寻路与空域管理，超出 2.5D 平面世界的范畴 |
| 宠物对战 | 是一套独立的小型对战子系统（独立数值、独立回合规则），与主战斗系统解耦程度高，收益低于维护成本，作为游戏口味完全交给游戏层用现有机制拼装 |
| 账号层 | 单机无需登录与账号绑定，存档即身份 |

## 3. 从魔兽世界裁剪的原则

裁剪分四类：**直接去掉**（网络与社交相关，单机环境下无意义或无对象）、**大幅简化**（保留概念但去掉多人权威与三维复杂度）、**原样保留**（数据驱动与表现分离等设计精髓，与是否联网无关）、**单机新增**（单机单人形态特有的必要能力，魔兽的网络游戏定位下不需要）。

| 系统/能力 | 处置 | 理由 | 单机替代/落地方式 |
|---|---|---|---|
| 网络同步 / 服务端权威 | 直接去掉 | 单机单进程运行，没有多客户端一致性问题 | 逻辑与表现在同一进程内直接绑定，见 `03_运行时骨架.md` 的 View 绑定协议 |
| 反作弊 | 直接去掉 | 没有博弈对手方，本地存档本就允许玩家自行修改 | 不设置任何服务端校验层 |
| 匹配与跨服 | 直接去掉 | 单机没有多服务器与玩家匹配需求 | 无替代，功能整体不存在 |
| 账号层 | 直接去掉 | 单机无需登录 | 存档槽即"身份"，见 `10_存档与持久化.md` |
| 公会 / 聊天 / 邮件 / 交易 / 拍卖行 / 日历 / 好友 | 直接去掉 | 均依赖多玩家同时在线互动 | 商人与货币收拢进 `Economy`（单机版"经济"，见 `08_玩法层_掉落任务对话关卡.md`） |
| PvP 全部 | 直接去掉 | 需要专属平衡与战场机制，单机无对战对象 | 无替代，战斗系统只面向玩家对环境 |
| 控制递减 | 直接去掉 | 是 PvP 与高难度多人副本的平衡机制 | 改为 Boss/精英单位的「控制免疫标志」，由 Creature 模板声明，见 `07_载体层_物品生物物件.md` |
| 拾取分配方式（需求/贪婪/放弃等） | 直接去掉 | 分配机制服务于多玩家共享掉落 | 掉落直接归玩家所有，见 `08_玩法层_掉落任务对话关卡.md` 的 Loot |
| 副本锁定 | 直接去掉 | 锁定是防止多人重复获取奖励的服务端机制 | 改为存档状态位（该遭遇是否已完成），见 WorldState |
| 休息经验 | 直接去掉 | 是鼓励玩家下线的多人在线运营机制 | 不设置，经验获取速率直接由 Progression 曲线控制 |
| 真实日历节日 | 直接去掉 | 依赖真实世界时间与运营活动 | 不设置；如某游戏需要节日内容，用剧情演出与 WorldState 标志自行拼装 |
| 宠物对战 | 直接去掉 | 独立小型对战子系统，维护成本高于收益 | 若某游戏需要，用 Skill + Creature 现有机制拼装，不设专属系统 |
| 载具 / 飞行 / 飞行路径 | 直接去掉 | 依赖三维空域与远距离寻路，超出 2.5D 平面范畴 | 不设置；地图切换用场景路由代替长距离移动 |
| 附魔 / 宝石插槽 / 随机后缀 / 耐久修理 / 绑定 | 直接去掉，但保留扩展点 | 深化数值成长系统，属于游戏口味而非骨架必需 | Item 数据表为这些字段预留空位（schema 位保留但默认不启用），见 `07_载体层_物品生物物件.md` |
| 插件脚本 API | 直接去掉 | 面向终端玩家开放二次开发引入不可控安全面，且不属于"游戏开发方使用的架构"范畴 | 游戏层内部的脚本钩子（HookRegistry）仅供开发方注册，不对玩家开放 |
| 对象模型的网络同步字段 | 大幅简化 | 单机没有网络快照与插值同步需求 | 逻辑对象只保留模拟所需字段，见 `05_对象模型与世界.md` |
| 大陆/多地图无缝寻路与可见范围网格 | 大幅简化 | 单机一次只加载一张地图，没有"跨大陆同屏"问题 | 一个场景即一张地图，场景切换走 SceneRouter，见 `03_运行时骨架.md` |
| 三维导航寻路 | 大幅简化 | 目标形态是 2.5D 平面世界坐标 | 二维导航网格与二维寻路，见 `INavigation2D` 与 `05_对象模型与世界.md` |
| 属性评级换算（等级相关的评级转百分比） | 大幅简化 | 是多人游戏长期数值曲线平衡的工具，非必需 | 作为 StatBlock 的可选策略，默认关闭，见 `06_规则层_属性技能战斗AI.md` |
| 抗性系统 | 大幅简化 | 元素抗性是特定数值风格的产物 | 作为可选属性维度，游戏层决定是否启用 |
| 资源类型数量（怒气/法力/连击点等） | 大幅简化 | 不同游戏口味的资源模型差异很大 | PowerSet 的资源类型与数量做成可配置项，见 `06_规则层_属性技能战斗AI.md` |
| 阵营矩阵 | 大幅简化 | 魔兽的阵营系统服务于跨阵营 PvP 与声望网络 | 缩到小矩阵（敌对/中立/友好等有限枚举），见 `01_分层与依赖.md` 的 Faction 模块 |
| 命中判定表（招架/偏斜/格挡/致命等） | 大幅简化 | 多段判定服务于装备驱动的战斗深度，非所有游戏都需要 | 命中表做成可配置项列表，默认只保留命中/未命中/致命，招架偏斜格挡默认关闭，见 `06_规则层_属性技能战斗AI.md` |
| 仇恨表 | 大幅简化保留 | 多人 MMO 的仇恨用于坦克分摊伤害，单机没有多玩家分摊需求 | 仇恨表保留，但只作为 AI 选择攻击目标的依据，见 `06_规则层_属性技能战斗AI.md` 的 Threat |
| 死亡与复活 | 大幅简化 | 多人游戏的复活点网络、幽灵态、尸体奔跑不适用单机 | 死亡改为回到复活点或读档重来，由游戏层配置选择哪种，见 `05_对象模型与世界.md` |
| 生物重生 | 大幅简化 | 服务端定时重生服务于多玩家刷怪位竞争 | 改为"进图刷新策略"：进入场景时按规则重新生成，见 `05_对象模型与世界.md` 的 Spawn |
| 锁与钥匙 | 大幅简化 | 原版锁系统面向多职业开锁技能与随机数值 | 简化为"需要钥匙道具"或"需要世界状态标志"两种判定，见 `07_载体层_物品生物物件.md` 的 GameObject.Lock |
| 万物皆法术（Spell 驱动一切世界变化） | 原样保留 | 与是否联网无关，是"数据驱动内容、代码只写引擎"的核心设计精髓 | 直接采纳，见 ADR-0001 与 `06_规则层_属性技能战斗AI.md` |
| 逻辑与表现分离的外形映射（DisplayInfo） | 原样保留 | 让美术资源替换不触碰逻辑数据，是复用与快速迭代的关键 | 直接采纳，见 `01_分层与依赖.md` 的 DisplayInfo 与 `09_表现层.md` |
| 通用条件表（Conditions） | 原样保留 | 用一种条件语言表达触发、任务前置、显隐等一切判定，避免每个系统各写一套条件解析器 | 统一为 Expr，见 ADR-0005 与 `04_数据与内容管线.md` |
| 数据化 AI 与脚本钩子（SmartAI 思路） | 原样保留 | 让行为逻辑同样数据化，减少为单个内容写专用代码的冲动 | 行为外壳状态机 + 优先级表，见 `06_规则层_属性技能战斗AI.md` 的 AI |
| NPC 职能标志位（npc_flags） | 原样保留 | 用标志位声明"是商人/是任务给予者/可对话"等职能，避免为每种职能派生子类 | 直接采纳，见 `07_载体层_物品生物物件.md` 的 Creature |
| 等级与经验 | 原样保留 | 是 RPG 成长曲线的通用表达方式，与联网与否无关 | 直接采纳，见 `01_分层与依赖.md` 的 Progression |
| 职业与种族模板 | 原样保留 | 是角色初始化数据的通用组织方式 | 直接采纳，见 `01_分层与依赖.md` 的 Archetype |
| 存档读档 | 单机新增 | 单机没有服务端持久化，必须自带存档系统 | 见 `10_存档与持久化.md` |
| 暂停与时间缩放 | 单机新增 | 单机允许随时暂停与调节节奏，多人游戏不允许单人暂停全局时间 | 见 `03_运行时骨架.md` 的固定步长主循环 |
| 难度选择与新游戏加 | 单机新增 | 是单机 RPG 的通行体验，多人游戏由匹配到的对手/队友决定难度 | 见 `08_玩法层_掉落任务对话关卡.md` 的 Difficulty |
| 剧情演出（对话树 + 过场钩子） | 单机新增 | 单机 RPG 以剧情驱动为主，需要结构化的对话与演出编排能力 | 见 `08_玩法层_掉落任务对话关卡.md` 的 Dialog |
| 输入映射（键鼠 + 手柄） | 单机新增 | 单机需要直接处理本地输入设备与重绑定，无需服务端参与 | 见 `03_运行时骨架.md` 的 InputMap |

## 4. 设计原则

以下 11 条原则各有一份 ADR（见 `adr/`）展开动机与备选方案，此处给出精炼说明：

1. **万物皆法术**：任何"让世界发生变化"的动作都建模为 Skill（效果 + 光环 + 触发）。装备特效是"授予技能 + 挂被动光环"，天赋是"被动光环里的效果修饰或覆盖"，坐骑是"速度光环 + 外形层"，开门开箱采集传送是"物件的使用动作指向一个技能或对话动作"，Boss 机制是"遭遇阶段 + 触发器 + 技能"。禁止为单个内容写专用代码，任何看起来需要专用代码的需求都应先问"能不能用一个新的效果/光环组合表达"。
2. **逻辑对象不依赖引擎对象**：世界模拟由纯逻辑对象构成（实体、单位、玩家单位、生物单位、物件、抛射物、区域触发器、掉落物），不继承任何引擎节点或组件。每个逻辑对象在创建时由表现层绑定一个只读、只订阅事件的视图对象；视图销毁不影响逻辑，逻辑销毁驱动视图销毁。这保证核心模拟可以完全脱离引擎运行与测试。
3. **固定步长模拟与可替换时间模型**：核心模拟按固定步长驱动（默认步长对应 60 次/秒，可配置），渲染层在步与步之间做插值以保持画面平滑；暂停即停止推进模拟步，慢动作通过缩放"每帧累积的模拟时间"实现，不影响真实时间驱动的界面时钟（菜单动画、系统提示等）。时间模型是可替换策略：连续模式下每个模拟步对应固定的时间量（秒），是探索与战斗的默认模式；离散模式下每个模拟步对应一个回合内的一个行动，由回合调度器按先攻规则产生步序列。两种模式共享同一套 tick 顺序与"同种子同输入产生同结果"的确定性保证（在同一平台与同一运行时二进制下逐位一致；跨平台只承诺逻辑等价、不承诺逐位一致），规则层不因时间模型不同而分叉出第二套实现。
4. **数据即内容**：所有游戏内容都是结构化文本表，存储格式待技术选型阶段确定；每张表带 schema 版本号；所有 id 使用统一的"领域.名称"小写点分格式；数据注册表在启动时全量加载并做引用完整性校验；校验器是内容提交的强制门槛；每个模块自带字段说明文档。
5. **一个条件语言**：全架构只使用一种条件表达式语言表达一切判定逻辑——触发条件、优先级表条件、掉落条件、任务前置、对话显隐、遭遇阶段推进、成就达成条件、刷新条件全部用它书写；调用方通过统一的查询接口向条件语言注入可引用的上下文数据。
6. **逻辑 id 到外形的映射**：外形注册表把生物、物品、物件、技能、光环等的逻辑 id 映射到精灵集合、纸娃娃分层、锚点、方向数量、图标、特效 id、音效 id；逻辑数据表本身只存 id，绝不直接存资源路径；新增或替换外形只需要新增一条映射记录，不改逻辑数据。
7. **窄契约 + 事件总线**：模块之间只通过窄契约接口（明确的方法签名）与事件总线（发布订阅）交互，禁止模块间直接持有对方内部状态。事件命名沿用魔兽战斗日志的风格（动作+来源+目标+结果），并在全架构范围内统一登记，避免同一概念在不同模块里叫不同名字。
8. **世界状态标志替代阶段化**：世界状态是一个带命名空间的标志字典，用来表达"这段剧情是否发生过""这个区域当前处于什么阶段"等世界级状态；刷新策略、物件显隐、任务可见性、对话分支都通过条件语言引用它来判断；存档在持久化层面等价于"世界状态字典 + 玩家数据"。
9. **存档是唯一持久化方式**：每个存档槽是一份带版本号的结构化文档，包含玩家数据、世界状态、当前地图与位置、随机种子；配一条版本迁移函数链处理跨版本兼容；游戏设置独立于存档槽单独存储；自动存档的触发时机是可配置项。
10. **新增原语走审批**：新增效果类型、光环类型、事件类型、物件类型、任务目标类型、对话动作类型、AI 行为状态，都必须先写一份 ADR 说明动机，再修改对应注册表，再实现代码，最后补齐校验器规则与测试用例；除此之外的一切新增需求都应该只通过新增数据行满足，不应该触碰代码。
11. **引擎适配层隔离技术选型**：运行时核心对引擎零依赖，一切引擎能力都经过引擎适配层的接口进入运行时；引擎选型是独立于本架构的研究课题，通过一套多维度评估框架打分决策（渲染能力、导航能力、界面能力、测试能力、平台支持、生态与许可证等），本文档集不预设任何候选或结论。

## 4.1 接口与数据的记法约定（本文档集不含任何代码）

本文档集是方案设计，不做技术选型，也不含任何编程语言的代码。各专题文档里出现的 `interface X { ... }` 一类写法，是一种**中立的接口描述记法**，作用只有一个：把"某个模块对外承诺提供哪些能力、需要什么输入、给出什么输出"写得没有歧义，让不同模块可以被不同的人、在任何语言里独立实现和独立测试。它不属于任何语言，也不能直接运行；将来选定技术后，每一条签名都会按所选语言重新表达一次。

读法与约定：

| 写法 | 含义 |
|---|---|
| `interface 名字 { ... }` | 一份契约：某模块对外提供的一组能力清单 |
| `方法名(参数: 类型, ...): 返回类型` | 一项能力：名字、需要的输入、给出的输出；`void` 表示不返回值 |
| `type 名字 = A{...} \| B{...}` | 一种数据可能是 A 或 B 两种形态之一 |
| `struct 名字 { 字段: 类型 }` | 一条记录包含哪些字段 |
| 类型只有这些：`Bool`、`Int`、`Number`、`String`、`Id`、`Vec2`、`List<T>`、`Map<K,V>`、`Optional<T>`，以及用 `a\|b\|c` 写的枚举 | 刻意只用最通用的类型，避免绑定任何语言 |
| `// 注释` | 对该行的中文说明 |

数据表用"字段、类型、必填、说明"四列的字段表加一条缩进键值对示例来描述，同样不指定存储格式（格式待选型）。

## 6. 基础架构提供 / 游戏层提供

| 基础架构提供 | 游戏层提供 |
|---|---|
| 七层运行时骨架与依赖规则 | 具体游戏要不要用到某一层的全部模块（可裁剪组装） |

| 数据表结构与校验规则 | 数据表里的实际数据行 |
| 事件总线与统一事件词汇 | 订阅哪些事件、如何响应 |
| 新增原语的审批流程 | 提出新增原语的诉求与理由 |
