**结论先行**：第 31 条已根治并验证，采用消费方反馈原文三个候选方案里的**方案 1**。

- **现象**：结算中间步骤经真实施法路径不可观测——`Resolver.Resolve` 每次结算都会把"判定→基础值→
  暴击→施法者乘区→减免→目标乘区→免疫吸收→落地→后置"每一步的中间值追加进
  `ResolveResult.Steps`（见 06 第 4.1 节固定管线），但 `CastPipeline.ExecuteEffectsOnly` 遍历
  `def.Effects × targets` 调用 `_effects.ApplyEffect(context)` 时直接丢弃了返回值（不接收、不
  转发）；落地事件 `CombatDamageDealtEvent`/`CombatHealDoneEvent` 只携带落地总量字段，不含分步
  明细；`RulesAssembly` 的既有 `combatOptions` 构造参数只透传给 `CombatHost`，没有任何"结算宿主
  回调"这一层概念；`core/rules/combat` 模块整体没有对外暴露任何钩子点。综合结果：内容编辑器无法
  按 06 第 4.1 节固定管线分步展示一次真实结算（第 5.5.2 节"右侧结算预览"、第 5.8 节"简易战斗
  回放"两处规划的分步展示功能都缺一个数据来源），只能自行在编辑器侧复刻一份结算公式脱离真实施法
  路径单独计算——这条独立复刻的算法与框架内部真实实现容易逐步漂移，且重复实现本身就是要避免的
  维护负担。
- **处理（方案 1）**：`CombatOptions` 新增可选属性 `ResolveTrace: Action<EffectContext,
  ResolveResult>?`；`Resolver.Resolve` 是全部伤害/治疗效果原语（`school_damage`/
  `weapon_damage_pct`/`heal`）落地的唯一出口（`EffectDispatcher.ApplyDamageOrHeal` 恒调用
  `ICombatHost.ResolveEffect` → `Resolver.Resolve`），本方法全部三条返回路径在各自 `return` 前
  统一经私有方法 `InvokeResolveTrace` 调用回调一次，传入本次 `EffectContext` 与完整
  `ResolveResult`（含 `Steps`）；未设置（缺省 `null`）时只多一次 null 判断，零开销，不改变既有
  输出；回调抛出的异常被捕获后经 `ICombatDiagnostics.Warn` 记一次警告并继续，不向上传播、不
  影响结算与事件。`RulesAssembly` 既有的 `combatOptions` 构造参数原样透传，事件契约与装配根
  代码零改动。

## 现象复现与根因

### `Steps` 与 06 第 4.1 节固定步骤的对应关系（勘察结论，未发现偏差）

逐行核对 `core/rules/combat/core/Resolver.cs` 的 `Resolve` 方法，`Steps` 追加点与 06 第 4.1 节
九个固定步骤一一对应：

| `Steps` 前缀 | 对应 06 第 4.1 节步骤 |
|---|---|
| `hit_check:` | 判定 |
| `base_value:`/`glancing_adjust:`/`block_adjust:` | 基础值 |
| `crit_multiplier:` | 暴击 |
| `caster_multiplier:` | 施法者乘区 |
| `mitigation:`/`mitigation_applied:` | 减免 |
| `target_multiplier:` | 目标乘区 |
| `immune_absorb:` | 免疫吸收 |
| `land:` | 落地 |
| `heal_threat:`/`post:` | 后置 |

此外还有两条不属于九步、属于结算入口的防御性短路分支，各自独立记一条 `Steps`：
`precheck: target already dead -> Miss`（目标已死亡，直接按 Miss 处理，见判断记录 7）与
`terminal: hit=..., 跳过步骤 2-8`（miss/dodge/parry 判定终止，见判断记录 4 上方）。这两条短路
分支同样经 `InvokeResolveTrace` 触发回调（"结算返回前恰好调用一次"覆盖全部三条返回路径，不只
是完整九步落地这一条），`ResolveResult.Steps` 依旧非空、可供工具展示"为什么这次结算没有落地"。

**结论**：`Steps` 内容与 06 第 4.1 节固定步骤逐一对应，未发现文档与实现的偏差，本次改动不涉及
任何 06 文档结论层面的勘误，只是补一句说明性文字（见"文档"一节）。

### 落地路径覆盖清单

`Resolver.Resolve` 是全部伤害/治疗效果原语落地的唯一出口，以下调用路径均经同一出口，`Resolve
Trace` 因此天然覆盖，不需要在各调用点分别接线：

| 落地路径 | 调用链 |
|---|---|
| 技能瞬发伤害/治疗 | `CastPipeline.EnterCastOrChannel`（瞬发分支）→ `ExecuteEffectsOnly` → `EffectDispatcher.ApplyEffect` → `ApplyDamageOrHeal` → `CombatHost.ResolveEffect` → `Resolver.Resolve` |
| 技能读条完成 | `CastPipeline.FinishCast` → `ExecuteEffectsOnly` → 同上 |
| 技能引导周期跳（channel tick） | `CastPipeline.AdvanceOne` → `ExecuteEffectsOnly` → 同上 |
| 光环周期伤害/治疗（`periodic_damage`/`periodic_heal`） | `AuraHost.FirePeriodic` 直调 `EffectSink.ApplyEffect` → 同上（不经过 `CastPipeline`） |
| Proc 触发的嵌套施法 | `ProcHost.OnEvent` → `CastPipeline.TriggerCast` → `ExecuteEffectsOnly` → 同上 |
| 弹道命中后效果（`on_hit_effects`） | `IProjectileSpawner` 命中回调 → `IEffectSink.ApplyEffect` → 同上 |
| 免疫吸收（`absorb` 光环扣减） | 发生在 `Resolver.Resolve` 步骤 7 内部（`IAuraQuery.ConsumeAbsorb`），与主结算共享同一次 `Resolve` 调用，天然覆盖，不是独立出口 |

消费方反馈原文提到"反弹"——本仓库当前 19 种效果原语（06 第 3.2 节原语注册表）里没有独立的
"反弹伤害"原语，判定为反馈原文对"吸收类光环"的泛称；吸收（`absorb`）已在上表列出并覆盖。若后续
确实新增独立的反弹类效果原语，只要该原语最终落地仍经 `Resolver.Resolve`（当前 06 未规定任何
绕过结算管线的落地路径），`ResolveTrace` 同样自动覆盖，不需要额外改动。

## 处理

### 契约新增

`core/rules/combat/contracts/CombatOptions.cs`：

```csharp
/// <summary>结算追踪回调……</summary>
public Action<EffectContext, ResolveResult>? ResolveTrace { get; set; }
```

新增可选 `get; set;` 属性，与本类既有 11 个策略配置项同一写法（无显式构造函数，全部成员为对象
初始化器可设置的属性），既有（隐式）构造签名不受影响。

### 结算管线接入

`core/rules/combat/core/Resolver.cs`：`Resolve` 方法三条 `return` 语句前分别改为"构造
`ResolveResult` → 调用 `InvokeResolveTrace(context, result)` → 返回"；新增私有方法：

```csharp
private void InvokeResolveTrace(EffectContext context, ResolveResult result)
{
    var trace = _options.ResolveTrace;
    if (trace == null) return;
    try { trace(context, result); }
    catch (Exception ex)
    {
        _diagnostics.Warn($"Resolver.Resolve: CombatOptions.ResolveTrace 回调抛出异常，" +
            $"已捕获并忽略，不影响本次结算……：{ex}");
    }
}
```

`RulesAssembly` 零改动——其构造函数早已接受 `CombatOptions? combatOptions = null` 并原样透传给
`new CombatHost(...)`，消费方装配时只需在自己构造的 `CombatOptions` 上设置 `ResolveTrace` 即可
生效，不需要框架侧新增任何注入点。
