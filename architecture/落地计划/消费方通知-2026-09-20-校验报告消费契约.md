## 背景

- **第 71 条原始诉求**（`docs/上游反馈.md` 第 71 条，2026-09-19 登记）：消费方核实
  `core/foundation/data_registry/contracts/ValidationReport.cs` 后指出，
  `ValidationIssue.ToString()` 产出的文本（形如
  `[Error] required_field display.map[display.sample_map].sprite_set_id: ...`）全篇无
  `[Stable]`/"稳定契约"一类标注；消费方 `LogRecordLookup`（日志反查跳转功能）依赖这份文本格式做
  非锚定扫描定位记录，担心框架未来调整格式（如去掉方括号、调整字段顺序）会导致该功能静默失效。
- **框架侧当初核实后的反问原文**（摘自
  [消费方反馈-2026-09-19-编辑器-第67-72条.md](消费方反馈-2026-09-19-编辑器-第67-72条.md)
  "待消费方答复"节）：

  > 关于第 71 条 `ValidationIssue.ToString()` 格式稳定性：我们已经确认 `ValidationIssue` 本身是
  > 结构化数据（`Table`/`RecordKey`/`Field`/`Check`/`Message`/`Severity` 等均为公开只读属性），
  > 并且命令行层已有两条结构化出口——`toolchain/validator --json`（常规校验与 `--schema-audit`
  > 两条路径都支持）与 `toolchain/asset_import/check_cmd.py check --json`（1.43.0 起可用）。
  >
  > 想请编辑器项目确认一下：`LogRecordLookup`（或其它依赖该文本格式做日志反查跳转的功能）实际
  > 消费校验结果走的是哪条路径？
  >
  > 1. 直接调用上述某个命令行入口的 `--json` 输出（或直接使用 C# API 拿到 `ValidationReport`/
  >    `ValidationIssue` 对象本身）；还是
  > 2. 解析 Unity 运行期（Editor Play 模式或独立版）产生的日志文本（目前运行期唯一会把校验问题
  >    写出来的两处——`GameBootstrap` 启动校验失败、`DataHotReload` 热重载失败——都只输出
  >    `ValidationIssue.ToString()` 拼接后的人类可读文本，没有任何结构化投影）？
  >
  > 如果是后者，能否说明是什么场景迫使功能必须走运行期日志这条路（例如：反查跳转需要在游戏实际
  > 运行时、以某条具体记录触发校验失败为上下文，命令行入口的静态校验覆盖不到这类场景；或者只是
  > 历史实现顺手用了日志，其实换成命令行 `--json` 或直接读 API 也能满足）？这会决定我们是否需要、
  > 以及以什么形状给运行期补一条结构化诊断出口（目前评估下来这会是一个需要正式承诺格式稳定的新
  > 契约，想先弄清楚真实需求形状再动手，避免选错方案后再来一次破坏性调整）。

- **这个反问为什么挡住后续决策**：运行期结构化诊断出口一旦发布，就是一个需要对外承诺格式稳定的
  新契约（文件路径/事件字段/日志前缀等一旦定型就要长期维持兼容）。在没有确认消费方真实消费路径
  与场景诉求之前，框架侧无法判断"要不要做、做成什么形状"，选错形状会导致上线后又要一次破坏性
  调整。因此设计层在收到答复前不会擅自实现，此前也未实现。

## 本问询之前框架侧已经做了什么

**核实结论：1.46.0 随 [ADR-0042](../adr/0042-诊断契约统一转发到宿主控制台.md) 落地的诊断契约
统一转发机制，与第 71 条反问的主题相近，但覆盖范围完全不重叠——反问没有被部分或全部回答，
仍然原样有效，不需要因为 ADR-0042 而重新表述。**核实过程与依据：

- **ADR-0042 解决的问题**：框架内大量模块各自定义了一套"最小诊断出口契约"（形如"记一条警告""记
  一条错误，可选带异常"，默认实现只把消息收集到内存列表），但此前的装配实践从未真正把这些实例
  接到宿主（Unity）控制台——契约产生的消息完全静默，只能通过阅读代码或调试手段发现。ADR-0042
  新增 `Adapter.Unity.Diagnostics.DiagnosticsHub`（注册制轮询集线器：登记"来源名 + 只增不减的
  消息列表引用"，每帧轮询新增消息转发到宿主控制台），本轮全仓普查后接入了 21 个可达的 `I*Diagnostics`
  契约：L0 基础模块（`event_bus`/`hook_registry`/`save_system`/`scene_router`/`app_lifecycle`/
  `input_map`/`localization`）、L4 玩法宿主（`area_trigger`/`dialog`/`spawn`/`death`/`common`
  奖励/`world_state`）、数值模块（`power_set`/`progression`）、规则模块（`combat`/`skill`）、
  `presentation/ui` 独立契约，加上此前三批已接完的表现层 `IPresentationDiagnostics`（六条链路）。
  错误级消息统一映射为控制台 Warning 级别（额外带 `[error]` 文本标记，不改变实际严重级别，见
  ADR-0042 决策 4）。结构性排除 `IExprDiagnostics`——其绝大多数实例是单次调用内临时构造、调用
  结束即丢弃，不满足"跨帧可持续读取同一份消息列表引用"这一轮询前提，需要另一种"异常分支处直接
  同步转发"的机制，留待后续单独立项。
- **`data_registry` 的 `ValidationReport`/`ValidationIssue` 机制不属于 ADR-0042 的普查对象**：
  已核对 ADR-0042 落地清单（`CHANGELOG.md` `[1.46.0]` 对应条目、24 个补充判断记录的模块 README
  列表），`core/foundation/data_registry/README.md` **不在**这份清单内，既不是本轮接入的 21 个
  契约之一，也不是结构性排除清单里列出的项（该清单只列了 `IExprDiagnostics` 一项）。这是因为
  `ValidationReport`/`ValidationIssue` 本身不是"`I*Diagnostics`"这一族"记警告/记错误到内存"的
  最小诊断出口契约——它是数据校验完成后产出的一份报告对象，由调用方（`GameBootstrap`/
  `DataHotReload`）自行决定如何呈现，从设计上就是与 ADR-0042 覆盖的契约族群完全独立的另一条路径。
- **实测复核（2026-09-20，本次问询前）**：`games/_template/Runtime/GameBootstrap.cs:282` 仍是
  `Debug.LogError("[GameBootstrap] 数据集校验未通过，已停止：" + string.Join("; ", report.Issues));`；
  `games/_template/Runtime/DataHotReload.cs:386-387` 仍是
  `var issueText = string.Join("; ", ...i.ToString());` 后 `Debug.LogError(...)`。两处运行期
  输出路径与 2026-09-19 核实时的现状完全一致，均未接入 `DiagnosticsHub`，也未新增任何结构化
  投影；事件总线 `DataValidationFailedEvent` 仍只带 `ErrorCount`/`WarningCount` 两个汇总计数，
  不携带任何单条 `ValidationIssue`。`core/foundation/data_registry/README.md`"`ValidationIssue.
  ToString()` 格式稳定性声明与运行期结构化出口现状"判断记录（第 71 条，2026-09-19）本身也未被
  1.46.0 或之后的任何提交更新过，其"评估后暂不动手，留给设计层"的结论仍是当前状态。
- **结论**：ADR-0042 与第 71 条反问是"背景取向一致、具体范围不重叠"的两件事——两者都体现"框架
  诊断信息应当有出口"这一共同架构取向，但 ADR-0042 解决的是"契约已经产生了消息、只是从未被转发
  出去"这批模块的静默问题，其解法（接入既有集线器）是新增装配接线；第 71 条的运行期缺口性质不同
  ——不是"没转发"，而是"转发的东西本身不是结构化数据、且这条路径压根不是走契约/集线器机制，是
  校验报告对象由业务代码直接 `Debug.LogError`"，需要的解法也不同（可能是新增事件字段或新契约面，
  不是"接入既有集线器"就能覆盖）。因此**没有任何部分需要消费方因 ADR-0042 而重新作答**，反问
  全文原样有效，以下逐条列出需要消费方确认的问题。

## 仍然需要消费方回答的问题

### 问题 1：`LogRecordLookup`（或其它依赖 `ValidationIssue.ToString()` 文本格式做日志反查跳转的
功能）实际消费校验结果走的是哪条路径？

- 候选 A：直接调用命令行入口的 `--json` 输出（`toolchain/validator --json`——常规校验与
  `--schema-audit` 两条路径均支持，或 `toolchain/asset_import/check_cmd.py check --json`），
  或直接使用 C# API 拿到 `ValidationReport`/`ValidationIssue` 对象本身按公开属性
  （`Table`/`RecordKey`/`Field`/`Check`/`Message`/`Severity`/`Group`/`Note`/`RuleId`/
  `AffectedNodeIds`）消费。
- 候选 B：解析 Unity 运行期（Editor Play 模式或独立版）产生的日志文本——即
  `GameBootstrap.cs:282` 启动校验失败、`DataHotReload.cs:386-387` 热重载失败这两处
  `Debug.LogError` 输出的 `ValidationIssue.ToString()` 拼接文本。
- **框架侧倾向候选 A**：两条命令行结构化出口分别自更早版本与 1.43.0 起已可用，且更贴合"编辑器是
  独立于游戏运行进程之外的工具"这一定位。若消费方确认走的是候选 A，说明本条反问所指向的脆弱点
  实际不成立，不需要框架新增任何运行期契约。若消费方倾向候选 B 或实际情况是 B，请说明具体场景
  理由（见问题 2）。

### 问题 2：若问题 1 的答案是候选 B（解析运行期日志文本），是什么场景迫使功能必须走这条路？

- 候选 A：反查跳转需要在游戏实际运行时、以某条具体记录触发校验失败为上下文（例如
  `DataHotReload` 热重载失败是运行时才会发生的事件，命令行工具在这个时间点之前已经跑完，拿不到
  这次运行时触发的具体失败记录），命令行入口的静态校验时机覆盖不到这类场景。
- 候选 B：只是历史实现顺手用了日志文本解析，能力上换成命令行 `--json` 或直接读 C# API 也能满足
  同样的诉求，可以直接切换。
- **框架侧倾向**：若为候选 A，说明确实存在命令行工具在时机上覆盖不到的运行时触发场景，值得评估
  运行期结构化出口（见问题 3）；若为候选 B，建议消费方直接切换到命令行 `--json` 或 C# API 消费
  方式，绕开当前的文本格式脆弱点，不需要等待框架新增契约。

### 问题 3（仅当问题 2 答案为候选 A 时需要作答）：若确实需要运行期结构化出口，倾向哪种形状？

- 候选 A：给 `DataValidationFailedEvent`/`DataLoadCompletedEvent`
  （`core/foundation/data_registry/contracts/Events.cs`）新增一个携带
  `IReadOnlyList<ValidationIssue>` 的构造重载（ABI 只新增，代价小），供同进程内订阅事件总线的
  C# 消费方直接拿到结构化问题清单。**局限**：只服务与 Unity 进程同进程内的消费方，编辑器一类
  独立进程外部工具拿不到进程内事件，这个方案不解决"外部进程读运行期校验结果"的诉求。
- 候选 B：运行期额外落一份结构化诊断（如日志旁再写一份 JSON 文件，或额外打一行专用前缀的结构化
  日志供外部按行解析），能真正解决外部进程读取运行期校验结果的诉求。**代价**：等于新开一个对外
  承诺格式稳定的运行期契约（文件路径/日志前缀/字段形状一旦发布就要长期维持兼容）。
- **框架侧倾向**：若消费方是"编辑器一类独立进程外部工具"（问题 2 若确实成立，场景大概率如此），
  候选 B 更贴合真实需求；但候选 B 涉及新对外契约的格式稳定承诺，框架侧不预先拍板，需要先确认
  问题 1/2 的答案证实真实必要性后再定。若消费方认为存在候选 A/B 之外的第三种形状更合适，请给出
  具体场景理由。

## 为什么需要这个答复

如实说明：**这个答复不卡当前工作**——第 71 条反问提出以来框架侧未新增任何相关工作项，也没有
其它任务在等待这个答复才能推进。它影响的是**下一轮运行期诊断出口的设计方向**：在没有确认消费方
真实消费路径与场景诉求之前，框架侧不会评估、更不会实现任何运行期结构化契约，避免选错形状后再来
一次破坏性调整（背景一节已说明）。答复到达后，若结论是"不需要"（问题 1 为候选 A，或问题 2 为
候选 B），此事可以直接归档；若结论是"需要"，会转入正式的 ADR 立项流程，不在本次问询范围内预先
拍板。
