## 原第 71 条诉求（一句话）

消费方 `LogRecordLookup`（日志反查跳转功能）依赖 `ValidationIssue.ToString()` 拼出的
人类可读一行文本做非锚定扫描定位，担心该文本格式未标注稳定性承诺、框架未来调整措辞会导致
该功能静默失效，因此要求框架侧确认消费方实际走哪条路径、是否需要新增运行期结构化出口。

## 框架侧已定的契约

设计层已通过 [ADR-0046](../adr/0046-运行期校验报告结构化转发出口.md) 与
[ADR-0047](../adr/0047-运行期校验报告落盘出口.md) 拍板并落地，以下逐条以两份 ADR 正文为准：

1. **日志文本永远不是契约，这是一条独立于本次反馈的架构边界**（ADR-0046 决策 1）：任何
   诊断/校验信息"拼接成一行、供人阅读"的文本表示，不论有没有被标注"不稳定"，一律不得被下游
   当作程序化消费的隐式契约来解析。框架侧**不追认**任何解析 `ValidationIssue.ToString()`
   或运行期日志文本的既有用法——这不是"暂时还没有稳定承诺"，而是"这条路径从来就不属于契约
   范畴，解析它是下游自己的选择，不构成框架侧的兼容性负担"。
2. **同进程消费：`DataValidationFailedEvent` 携带结构化 `Issues`**（ADR-0046 决策 3/4）：
   `core/foundation/data_registry/contracts/Events.cs` 的 `DataValidationFailedEvent`
   新增一个三参数构造函数，携带 `IReadOnlyList<ValidationIssue> Issues`（ABI 只新增，既有
   两参数构造函数保留、内部委派，未提供 `Issues` 时默认空集合、不是 `null`）。`DataRegistry.
   LoadAllCore` 与 `games/_template/Runtime/DataHotReload.cs` 两处既有发布点均已改用新构造
   函数传入 `report.Issues`。服务对象：与运行期宿主**同进程内、订阅该事件总线**的调用方。
3. **跨进程消费：运行期落盘结构化文档**（ADR-0047）：运行期宿主把每次校验结果（不论通过还是
   阻断）原子落盘为结构化文档，供与宿主完全独立的外部进程（例如编辑器）监视/轮询读取：
   - 落盘路径由运行期选项**显式指定**——命令行参数 `-gfValidationReportPath` 或环境变量
     `GF_VALIDATION_REPORT_PATH`（命令行优先），**未设置时不产生任何文件**，不设默认路径
     （ADR-0047 决策 3）：正式发布给玩家的进程不会因为这条能力而产生意料之外的磁盘副作用。
   - 文档带**单调递增序号**与**触发来源**标识（`startup`/`hot_reload`，区分是宿主启动阶段
     的首次校验还是开发期数据热重载触发的重新校验），据此可判断"这是不是最新一次结果"
     （ADR-0047 决策 4）。
   - **通过、阻断都写**（ADR-0047 决策 4）：若只在阻断态落盘，消费方无法区分"最近一次已经
     通过"与"文件还没更新"这两种截然不同的情况。
   - **原子写**（ADR-0047 决策 5）：先写临时文件，再用同卷文件系统改名操作替换到目标路径，
     监视/轮询方不会读到写了一半的半截文档。
4. **落盘文档的 `issues[]` 元素形状与命令行 `--json` 完全一致，两者共用同一份序列化实现**
   （ADR-0046 决策 4、ADR-0047 决策 2）：新增
   `Core.Foundation.DataRegistry.ValidationIssueJsonWriter`
   （`core/foundation/data_registry/contracts/ValidationIssueJsonWriter.cs`），把此前只在
   `toolchain/validator/Program.cs` 内部私有的 `ValidationIssue` JSON 序列化逻辑搬到本模块
   公开，`Program.cs` 与运行期落盘出口（`Adapter.Unity.Diagnostics.
   ValidationReportFileOutlet`）均改为调用同一份实现——不是两处各自维护、需要人工同步的两份
   格式约定，未来任一方新增字段，另一方自然可见，不会漂移。

## 消费方需要怎么改

从"解析 `ValidationIssue.ToString()` 拼接文本或运行期日志文本"迁移到上面两条结构化出口
之一，按消费方自身进程形态选择：

- **消费方是独立进程**（例如编辑器一类随游戏走、但不与游戏运行进程共享内存空间的外部工具）
  ——选**落盘出口**（第 3 条）：给运行期宿主传入 `-gfValidationReportPath` 或设置
  `GF_VALIDATION_REPORT_PATH`，监视/轮询该路径，按信封的序号字段判断是否为最新结果。
- **消费方运行在与宿主同一个进程内**（例如订阅数据注册表事件总线的 C# 代码）——选**事件
  出口**（第 2 条）：直接消费 `DataValidationFailedEvent.Issues`，不需要任何磁盘 I/O，
  延迟最低。
- 两条通道服务不同前提、互不替代，不需要"该选哪个"以外的额外判断——消费方按自己是否与宿主
  同进程这一个事实就能确定选哪条。

## 原三个问题不需要回答了

原问询文档提出的三个问题（消费方实际走命令行结构化出口还是解析运行期日志文本；若是后者，
是什么场景迫使功能必须走这条路；若确实需要运行期结构化出口，倾向哪种形状）**均不需要消费方
再作答**——设计层已经不再等待具体场景确认，直接把两条结构化出口（同进程事件、跨进程落盘）
都落地了，覆盖了原问题 3 列出的候选 A 与候选 B 两种形状，消费方现在可以直接从上面两条中选一条
迁移，不再需要先说明自己属于哪种场景。
