## 处理

### A. 公开 `SchemaMigrator`

新文件 `core/foundation/data_registry/core/SchemaMigrator.cs`（`Core.Foundation.DataRegistry`
命名空间，`public static class`）：

- `BuildChain(TableSchema schema, int fromVersion, int toVersion): IReadOnlyList<TableMigration>?`
  ——与原私有 `DataRegistry.BuildMigrationChain` 逐字一致的链选取语义（每步取第一条
  `FromVersion` 等于当前版本的环节，直到精确到达目标版本；缺环节或越过目标返回 `null`；
  `fromVersion == toVersion` 返回空链）。新增两条参数守卫（`schema` 为 `null` 抛
  `ArgumentNullException`；`fromVersion < 1` 或 `toVersion < fromVersion` 抛
  `ArgumentOutOfRangeException`）——`DataRegistry` 自身的调用路径恒满足这两条前提（信封
  `schema_version` 已在更早处校验过、只在版本落后时才调用），不会触发，这两条守卫只是新公开
  入口面向任意调用方新增的输入校验，不改变加载器既有行为。
- `MigrateRow(IReadOnlyList<TableMigration> chain, JsonObject row): JsonObject`——按链顺序依次
  调用 `Migrate`，与加载器行内循环逐字一致；`null` 参数抛 `ArgumentNullException`。
- `MigrateEnvelope(TableSchema schema, JsonObject envelope): JsonObject`——整表迁移的权威实现，
  输入/输出均为 `data/README.md`"文件顶层信封"形态。规则：
  - `schema_version` 缺失/非法、`rows` 非数组、`schema_version` 超过
    `TableSchema.CurrentSchemaVersion`，均抛 `ArgumentException`。
  - `schema_version` 已等于当前版本，原样返回**同一实例**（不做任何拷贝）。
  - 否则调用 `BuildChain`；返回 `null`（缺少迁移环节）抛 `InvalidOperationException`。
  - 成功时返回**新的** `JsonObject`：保留原信封其它键与键序，`schema_version` 改为当前版本，
    `migrated_from` 写入"最早的原始版本"（若信封已带合法 `migrated_from`，保留那个更早的值，
    不覆盖），`rows` 每个对象元素经 `MigrateRow`；非对象元素抛 `ArgumentException`（工具侧应
    先修好数据，不静默跳过——与加载器"记一条 Error、跳过该行、继续处理其余行"的宽容策略不同，
    本方法是单次写回操作，没有"部分成功"的中间态）。
  - 输入信封不被修改——`JsonObject` 本身不可变（见该类型注释"构造之后不提供任何修改方法"），
    本方法全程只读取、从不调用修改方法，天然满足"不改输入"，不需要额外的防御性拷贝。

`DataRegistry.LoadOneTablePartial` 与私有 `BuildMigrationChain` 改为委托
`SchemaMigrator.BuildChain`/`MigrateRow`（删除私有实现），报错文案与既有行为逐字不变——既有
`DataRegistryTests.cs` 全部原样通过（无需修改任何既有测试断言）。

### B. 加载器接受信封级 `migrated_from`

`LoadOneTablePartial` 在 `schema_version` 解析完成后新增校验：若信封出现 `migrated_from` 键，
必须是 `[1, schema_version - 1]` 范围内的整数，否则判定为阻断错误（检查名 `envelope`，消息点出
实际收到的取值，与 `schema_version` 自身非法共用同一检查名，风格一致）；合法时不做其它事——不
参与迁移触发判断（触发迁移只看 `schema_version` 是否落后），只是放行一个此前从未被显式承认、
也未被拒绝过的信封键。

核实改动前行为：`toolchain/validate_data.py` 第一道骨架检查本就不校验信封多余键（只检查
`table`/`schema_version`/`rows` 三键是否存在，见 `check_envelope`），`format_data.py
--schema-order --check` 同理不检查多余键——两者均已"静默接受"该键，本次改动不需要为此新增任何
豁免逻辑，只需要确认 `toolchain/validator --list-tables --json` 导出与 `format_data.py` 的字段
重排不会因为这张新表的低版本示例文件而误报（见下"D. format_data.py 根治"）。

### D. `format_data.py` 根治"低版本文件误报需要重排"

`toolchain/format_data.py --schema-order` 此前只按"表当前登记的字段顺序"重排，没有考虑文件
信封版本是否落后——`found.migration_sample` 的 v1 示例文件字段名是 `label`（不在当前版本字段
清单 `["id", "display_name", "note"]` 内），若原始文件字段顺序恰好不是"已登记字段先出现、未
登记字段后出现"，会被误判为"需要重排"，而按当前版本字段顺序重排一张字段名都对不上的旧版本文件
没有意义。

根治：`get_field_order_map` 从 `--list-tables --json`（见下"E"）额外取每张表的当前
`schema_version`，返回值改为 `(field_order_map, schema_version_map)` 二元组；`process_file`
新增判断——文件信封 `schema_version` 低于该表当前版本时整体跳过（不判断、不改写），如实打印
一行"跳过（版本落后，未判断字段顺序）"（`--verbose` 下额外打印具体原因），不静默吞掉。真实仓库
验证：

```
python toolchain/format_data.py --schema-order --check --verbose
```

```
[verbose] 跳过（信封 schema_version=1 低于表 'found.migration_sample' 当前版本 2，
按当前字段顺序重排没有意义，见文件头判断记录）: ...\data\_sample\found\found.migration_sample.json
跳过（版本落后，未判断字段顺序）: data\_sample\found\found.migration_sample.json
[format_data.py --schema-order --check] 共检查 66 个文件，需要重排 0 个，跳过版本落后 1 个
```

退出码 0——其余 65 个文件字段顺序均已符合各自表当前的 schema 登记顺序，新表的 v1 示例文件被
正确跳过、不误报。新增 `toolchain/tests/test_format_data_schema_order.py` 两个用例锁死这条
行为（低版本文件跳过不重排、当前版本文件照常重排）。

### E. `--list-tables --json` 新增 `schema_version`/`migrations`

`toolchain/validator/Program.cs` `PrintJson` 每张表条目追加在既有 `field_ranges` 字段之后、
闭合大括号之前，不改动任何既有字段：

- `schema_version`：该表当前登记的 `TableSchema.CurrentSchemaVersion`。
- `migrations`：该表登记的迁移环节清单，按登记顺序，每项 `{"from": int, "to": int}`——只是
  如实导出登记形状，**不代表**已从任意起始版本到 `CurrentSchemaVersion` 全部串通，链是否可用
  仍须调用 `SchemaMigrator.BuildChain` 确认（多条环节可能存在缺口，只是各自单独合法）。

真实仓库验证（`found.migration_sample` 条目）：

  "record_count": 2,
  "layer": "Foundation",
  "module": "foundation",
  "domain": "found",
  "schema_version": 2,

（完整字段见验收证据一节；上表节选自 `field_meta`/`field_ranges` 之外的新增两项。）

## 对编辑器的使用建议

1. **"执行迁移并写回磁盘"直接调用 `SchemaMigrator.MigrateEnvelope(schema, envelope)`**，不要
   再自行拼装 `BuildChain` + 手写信封改写逻辑——`migrated_from` 的"保留最早原始版本"这条细节
   容易在手写实现里遗漏（多次增量迁移场景）。
2. **"预览迁移前后字段差异"这类不立即执行迁移的场景**，可以单独调用
   `SchemaMigrator.BuildChain(schema, fromVersion, toVersion)` 判断链是否可用（返回 `null`
   时在预览对话框提示"无法迁移，请联系框架维护方补齐环节"），不需要为了"只是想看一眼"而调用
   会产出新对象的 `MigrateEnvelope`。
3. **`found.migration_sample` 是唯一的真实迁移链用例**，建议编辑器侧新增一条端到端测试：加载
   该表 v1 示例数据 → 调用 `MigrateEnvelope` → 断言产出信封与直接用 `DataRegistry` 加载同一份
   v1 数据得到的记录字段值一致（本仓库 `MigrateEnvelope_ThenLoad_MatchesDirectLoaderMigration`
   即是这条用例的框架侧对照实现，可直接照抄测试结构）。这张表没有任何运行时消费方，可以放心
   用真实数据反复练习迁移流程，不会影响任何其它功能。
4. **`--list-tables --json` 新增的 `migrations` 字段只是登记形状**，不代表任意版本区间可迁移
   ——编辑器判断"这张表能不能从 X 迁移到 Y"仍应调用 `SchemaMigrator.BuildChain` 得到权威答案，
   不要自行用 `migrations` 数组拼接推断（那正是本条反馈原本要根治的"自行复刻链选取语义"）。
5. **`migrated_from` 是信封级键**，编辑器的表单模型/差异展示如果此前把它当成逐行字段处理，
   需要同步改为按表统一处理（与 `schema_version` 完全同级、同一套展示逻辑）。
