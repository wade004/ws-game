## 第 24 条：`event` 分组"未登记 → 不报"的措辞暗示了不存在的两态

**现象**：`PresentationSchemaCatalog.FullExprSchema` 对 `event` 分组的 `TryGetSignature` 实际
恒返回 `true`（内部是 `QuestExprSchemaEntries.EventGroupPermissiveSchema` 全放行，见
`core/gameplay/quest/contracts/QuestExprSchemaEntries.cs`），不存在"某个 `event.<key>` 已登记、
会被真正校验"这种状态——本类型从未登记过任何具体 `event.*` 签名。但 04 第 6.3/6.4 节与
`QuestExprSchemaEntries` 的注释此前写"未登记的 `event.<key>` 组合…回退为签名未知的引用"，
措辞上把 `event` 分组套进了普通分组"已登记/未登记"两态的框架里，读者容易误以为该分组也存在
"已登记态会被拦截"的行为。

**根因**：该措辞是历史上从"普通分组未登记则回退为 id 字面量"这条 ADR-0015 规则顺势类推写出
的，类推本身没错（结论——不报错——是对的），但没有把"`event` 分组根本不做静态签名校验"这个
更准确的因果关系说清楚，遗留下"两态"的错误暗示。

**处理**（仅改文档与代码注释，不改任何运行时代码/行为）：

- `architecture/04_数据与内容管线.md` 第 6.3 节两处措辞改写——明确"普通分组区分已登记/未登记
  两态；`event` 分组不适用这一区分，该分组的签名校验被整体恒放行，不区分某个具体 key 是否曾经
  登记过"；第 6.4 节错误处理表同步改写。第 4 节 `query` 一行之后顺带补充了 `self.<field>`
  自动登记的字段种类范围说明（与第 25 条相关，见下）。
- `core/gameplay/quest/contracts/QuestExprSchemaEntries.cs`：`BuildParsingSchema` 与内部类
  `EventGroupPermissiveSchema` 的 XML 注释改写为"`event` 分组不做签名校验，`TryGetSignature`
  对该分组恒放行；原因是事件键由内容自由定义、可能在运行时才登记，任何静态登记表都无法穷举"，
  不再用"未登记 key 一律放行"这种暗示"存在已登记 key"的措辞。

**涉及文件**：`architecture/04_数据与内容管线.md`（第 6.3/6.4 节 + 变更记录）、
`core/gameplay/quest/contracts/QuestExprSchemaEntries.cs`（仅 XML 注释）。无代码逻辑改动。

**验证**：`git diff` 确认 `QuestExprSchemaEntries.cs` 改动范围仅在 `///` 注释行内，
`EventGroupPermissiveSchema.TryGetSignature` 方法体逐字节未变；六工程 `dotnet test` 全绿
（见文末汇总）；`python toolchain/validate_data.py --strict` 0 error（Expr 校验行为不变，
`event.*` 引用解析结果与本批改动前一致）。

**对消费方提示**：行为本身没有变化——`event.<key>` 无论是什么 key，此前和现在都会被解析为
`<reference>`、签名未知、放行、不报"疑似引用拼写错误"。如果编辑器一侧此前依据旧措辞实现过
"event 分组也区分已登记/未登记"的逻辑（例如给已知 event key 单独做静态类型提示、给未知 key
报警告），这部分逻辑本身依据的是错误的文档描述，建议核对并按"该分组不做签名校验"重新设计
提示逻辑（`IExprSchema.KnownKeys("event")`/`KnownGroups`——见第三批第 18 条——对 `event` 分组
恒返回空集合，因为本类型从不登记任何具体 `event.*` key，这与"不做签名校验"的结论一致，不是
遗漏）。

## 第 25 条：`RecordExprSchema.For` 把 `Expr` 字段也注册成 `self.<field>` 引用

**现象**：`core/foundation/data_registry/core/RecordExprSchema.cs` 的 `For(TableSchema)` 把
表的全部字段登记为 `self.<field>` 零参引用（供 `DataRegistry.Query(table, predicateText)`
便捷重载解析谓词用），`FieldKind.Expr` 字段此前与 `String`/`Enum` 一样映射为
`ExprValueKind.String`——但 Expr 字段的值是待求值的表达式文本，不是可直接比较的标量数据，
`self.<expr_field>` 没有明确的取值语义（对比 `self.<string_field>`，其值本身就是可比较的字符串
字面量）。

**排查（设计层要求：先 grep 全仓确认有无真实使用者，再决定排除还是保留）**：

- 先列出全仓所有 `FieldKind.Expr` 字段名（非测试代码）：`filter`（`achievement`）、
  `condition`（`area_trigger`/`dialog`/`loot`/`spawn`/`prog`/`ai`/`skill`/`feedback_binder`
  八处同名字段）、`visible_if`（`dialog`）、`buy_price_rule`（`economy`）、
  `trigger_condition`/`enter_condition`/`victory_condition`/`defeat_condition`（
  `encounter`）、`eventFilter`（`quest`）、`prerequisite`（`quest`）。
- 用这份字段名清单在 `data/`、`core/`、`presentation/`、`games/`、`editor/` 全仓 grep
  `self.<字段名>` 组合（含正则 `self\.(filter|condition|visible_if|buy_price_rule|
  trigger_condition|enter_condition|victory_condition|defeat_condition|eventFilter|
  prerequisite)`），**零命中**。进一步放宽到全仓任意 `self.` 前缀出现的位置（`data/` 目录内
  仅 2 个文件共 3 处），核实为 `self.distance_to_target`/`self.hp_pct`——分别来自
  `RulesExprSchema.Base` 登记的 `self` 分组（运行时判定用的 Expr，单位自身状态），与本条讨论
  的 `RecordExprSchema`（`DataRegistry.Query` 谓词场景、字面意思是"记录自身字段"）是两套完全
  独立的 `self` 分组登记表，同名不同义，与本条无关。
- **结论：全仓（含既有测试）没有任何 `self.<Expr 字段名>` 的真实引用**，属安全的行为收紧，
  按任务书"没有则排除"方案落地，不采用"保留注册但只在文档说明取到的是文本"的折中。

**处理**：

- `RecordExprMapping.ToExprValueKind(FieldKind.Expr)` 从并入 `String` 分支改为单独一个
  `case`，返回 `null`（不登记），与 `IdList`/`Vec2`/`Object`/`Array` 四种本就不登记的字段种类
  同等对待；新增 `case` 内联注释写明判断记录。
- `RecordExprSchema`/`RecordExprMapping` 两处 XML 类型注释补充判断记录，说明排除理由与 grep
  结论、指向新增的验收测试。
- 文档同步：04 第 4 节 `query` 一行之后新增一句勘误，说明 `self.<field>` 只登记能映射为 Expr
  标量类型的字段种类；`core/foundation/data_registry/README.md`"Query 的宿主上下文"一节同步
  补充同样的说明。

**涉及文件**：`core/foundation/data_registry/core/RecordExprSchema.cs`（`ToExprValueKind` 拆出
`FieldKind.Expr` 独立分支）、`architecture/04_数据与内容管线.md`（第 4 节 + 变更记录）、
`core/foundation/data_registry/README.md`；新增测试
`core/foundation/data_registry/tests/RecordExprSchemaExprFieldExclusionTests.cs`。

**验证**：新增测试全部通过——

- `For_ExprField_NotRegisteredAsSelfReference`：合成一张含 `Expr` 字段（`visible_if`）的
  `TableSchema`，`RecordExprSchema.For(table).TryGetSignature("self", "visible_if")` 为
  `false`（任务书要求的验收断言）。
- `ExprParser_SelfDotExprField_FallsBackToIdLiteral`：`self.visible_if` 经该 schema 解析不
  抛异常（按 ADR-0015 默认规则整体退化为 `<id_literal>`）。
- `For_NonExprFields_StillRegisteredAsSelfReference`：同一张表里 `Id`/`String` 字段仍正确登记
  为 `self.<field>`（回归保护，避免误伤其它字段种类）。
- `ToExprValueKind_CoversAllThirteenFieldKinds`（Theory，13 组数据）：逐一断言全部 13 种
  `FieldKind` 的映射结果，`Expr` 断言为"无值"。

六工程 `dotnet test` 全绿（Tests.Foundation 927 通过，含本文件新增 17 个测试）；
`python toolchain/validate_data.py --strict`：`tables 63, records 300, errors 0, warnings 0`
（与改动前一致，`data/` 里没有任何谓词文本用到 `self.<Expr 字段名>`，行为不变）；
`toolchain/abi_probe.ps1 -BaselineZip dist/ws-game-1.12.0.zip`：`breaks=0`（`ToExprValueKind`
对 `Expr` 从"映射为 String"改为"映射为 null"是一处运行时行为变化，但不是公开 API 物理签名
变化，`abi_probe` 比对的是二进制 ABI 兼容性，不比对运行时返回值，故不计入 breaks；行为变化
本身已由上面的排查结论确认"无真实使用者受影响"）。

**对消费方提示**：若编辑器一侧曾经依赖"`self.<Expr 字段名>` 可以在 `Query(table,
predicateText)` 谓词里当字符串比较"这个（未被记录的）行为，本批改动后该写法会被解析为
`<id_literal>`（需要满足 04 第 2 节 id 格式，否则解析期报错），不再是"合法引用、按字符串比较"。
排查结论是全仓（含编辑器已知场景）没有这种用法，但如消费方自有工程里存在类似写法，请改为在
应用代码里先取出记录、自行读取 Expr 字段文本，不要经 `Query` 谓词比较。

## 第 26 条：`RecordExprMapping`/`ToExprValueKind` 不可见，编辑器无法复用同一份映射规则

**现象**：`RecordExprMapping` 是 `internal static class`（其 `public` 成员 `ToExprValueKind`
因容器类可见性上限实际也只在框架内部可见），编辑器等框架外消费方想复用"字段种类 → Expr 标量
类型"这份映射规则（例如做字段级联动提示、判断某字段是否可能出现在谓词比较里）时，只能通过
`RecordExprSchema.For` 的输出间接观察结果，拿不到可直接调用的映射函数本身。

**根因**：该类型最初只服务 `RecordExprSchema`/`RecordExprHost` 框架内部两个消费点，设计时未
预留对外可见性。

**处理**：`RecordExprMapping` 类型与其唯一成员 `ToExprValueKind` 由 `internal` 显式放宽为
`public static`——纯可见性放宽，不改变任何映射结果或既有调用点行为（`RecordExprSchema.For`/
`RecordExprHost` 两处框架内部调用点不受影响）。XML 注释同步补充完整映射表说明（13 种
`FieldKind` 各自映射到什么，或不登记的理由），供消费方一次性查阅全貌而不必逐个 case 试探。

**涉及文件**：`core/foundation/data_registry/core/RecordExprSchema.cs`（`RecordExprMapping`
类声明与 `ToExprValueKind` 方法均改为 `public static`，方法体不变）；
`editor/docs/编辑器产品文档.md` 第 4.1 节契约面清单 `DataRegistry` 一行补充说明。

**验证**：`ToExprValueKind_CoversAllThirteenFieldKinds`（与第 25 条共用同一个 Theory，见上）
逐一断言全部 13 种 `FieldKind` 的映射结果——`Bool`→`Bool`、`Int`→`Int`、`Number`→`Number`、
`String`/`Enum`→`String`、`Id`/`Reference`/`TextKey`→`Id`、`IdList`/`Vec2`/`Object`/`Array`/
`Expr`→ 无值；`AllFieldKindMappings_CoversExactlyThirteenKinds` 用
`Enum.GetValues(typeof(FieldKind)).Length == 13` 防止未来新增 `FieldKind` 枚举值时本测试
静默漏检。`toolchain/abi_probe.ps1` 确认这是一次纯新增可见性变更，`breaks=0`
（新增 255 行 API surface，含本条与第 25 条引入的新公开成员，均计入"新增"不计入"破坏"）。

**对消费方提示**：`Core.Foundation.DataRegistry.RecordExprMapping.ToExprValueKind(FieldKind)`
现在可直接从编辑器代码调用；返回 `null` 表示该字段种类不会被 `RecordExprSchema.For` 登记为
`self.<field>` 引用（`IdList`/`Vec2`/`Object`/`Array`/`Expr` 五种，第 25 条起 `Expr` 加入此
集合）。
