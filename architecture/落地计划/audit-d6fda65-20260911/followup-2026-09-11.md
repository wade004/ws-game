## validation.md 首次 pytest 失败根因排查

[validation/validation.md](validation/validation.md) 记录：`check.ps1 -SkipUnity` 首次运行的
`python -m pytest toolchain/tests -q` 步骤失败（仅 2.7 秒、输出只有两个 `.` 后即报"失败"，未捕获到
任何异常/回溯文本），同一份记录里独立重跑（`validation/raw/pytest-toolchain-rerun.log`）与本 agent
自己的多次重跑（含一次完整模拟 `check.ps1` 调用方式：`$env:PYTHONUTF8="1"; Push-Location <repo>;
python -m pytest toolchain/tests -q`）均是 186/185 passed（视本轮新增用例数而定）、0 failed，全绿。

排查结论：**未能复现，判断为环境瞬时问题，不是我们代码/测试本身的缺陷**——理由：

1. 失败仅耗时 2.7 秒，而完整套件正常需要 30～75 秒；结合只打印两个 `.` 就中断、且 `check.ps1`
   的 transcript 里完全没有捕获到 pytest 通常会打印的失败摘要（`FAILED ...`/回溯），更像是 pytest
   子进程本身被外部因素（例如实时防病毒扫描对刚创建的临时目录/刚启动的 `powershell.exe` 子进程
   的拦截、系统资源瞬时争用）异常中断，而不是某条断言真的失败——真正的断言失败会有明确的
   `FAILED`/`AssertionError` 文本，这次完全没有。
2. 同一份 `validation.md` 记录里，独立重跑立即就是全绿（186 passed，4 skipped，见
   `validation/raw/pytest-toolchain-rerun.log`），审核过程本身已经区分记录了"首次失败"与"重跑通过"
   两个独立事实，未把首次失败掩盖成"整体 PASS"。
3. 本 agent 在自己的工作树内按 `check.ps1` 的确切调用方式（含 `$env:PYTHONUTF8="1"`、
   `Push-Location` 到仓库根）额外重跑一次，同样全绿，进一步排除是本轮改动引入的新回归。
4. 前几轮审计已经处理过一类相关但不同的问题（"第九轮审计工具链条目"：本机 GBK 控制台代码页下
   `subprocess` 输出解码），`check.ps1`/相关测试已加 `PYTHONUTF8=1`/显式 `encoding="utf-8"` 双保险
   （见 `check.ps1` 第 703-718 行判断记录）——本次现象（进程提前中断、无回溯文本）与该类编码问题
   的表现（`UnicodeDecodeError`/乱码）不同，不是同一根因的复发。

**处理方式**：不 skip、不删测试、不新增兜底重试逻辑（没有可复现的具体故障点可修）；如实记录在
