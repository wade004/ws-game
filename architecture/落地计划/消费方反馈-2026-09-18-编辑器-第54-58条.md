## 现象与复现

原文见 `ws-game-editor` 仓库 `docs/上游反馈-待转发-2026-09-18.md`（`phase/p4.3` 分支）。

### 第 54 条

`core/gameplay/quest/core/QuestContentValidationRule.cs:356` 的
`CollectQuestIdLiteralArgs(ExprNode, List<ExprLiteralNode>)` 是私有方法，唯一调用点是同文件的
`ValidatePrerequisiteGraph`（:306）。内容工具（如编辑器"任务前置关系"面板）想拿到"某条
`prerequisite` 引用了哪些任务 id"这一能力，没有任何公开等价入口，只能自己重新实现一遍 Expr
语法树遍历。全仓库 grep 只命中这一处定义，确认无其它公开等价入口。

### 第 56 条

`story_tree`/`quest_prerequisite`/`talent_tree` 三类"节点 + 有向边"图形数据均无孤岛/不可达节点
诊断——逐条核实三条规则的完整校验清单：`DialogContentValidationRule.ValidateStoryTree`（只有
`story_tree_min_nodes`/`story_tree_duplicate_node_id`/`story_tree_dangling_next_node`/
`story_tree_cycle` 四项）、`QuestContentValidationRule.ValidatePrerequisiteGraph`（只有
`quest_prerequisite_unknown`/`quest_prerequisite_cycle` 两项）、
`ArchTalentTreeCycleValidationRule`（只有 `talent_node_id`/`talent_prerequisite_missing`/
`talent_prerequisite_cycle` 三项），均无可达性/孤立节点检查。

### 第 57 条

九项图诊断（`story_tree`/`quest_prerequisite`/`talent_tree` 各自的结构性检查，4+2+3=9，与反馈
原文计数一致）的 `ValidationIssue.Field` 逐项核对，均为静态字符串或未传（`null`），不含具体节点
下标——问题面板/图形化画布拿到诊断后无法直接定位到具体是哪个节点/哪条边，只能自己重新解析一遍
数据反查。

### 第 58 条

`core/gameplay/dialog/core/DialogSchemas.cs:169`
（`dialog.story_tree.nodes[].id`，`FieldKind.Id`）与
`core/numbers/archetype/contracts/ArchSchemas.cs:146`
（`arch.talent_tree.nodes[].id`，`FieldKind.String`）两处节点 id 声明确实不同。核实
`arch.talent_tree` 一侧是有意为之——紧邻的代码注释（改动前 :144～145）已写明"`ArchetypeRegistry
.ParseTalentTree`：id 缺失/非字符串直接抛异常，必填；只检查 JsonString，不做 Id 格式校验，登记
为 String 而非 Id（以运行时为准）"，只是这份判断记录此前只存在于代码注释，未同步到消费方可见的
文档层。`core/sim/tests/data/arch/arch.talent_tree.json` 的既有节点 id 就是 `"node_a"`/
`"node_b"`（不含点），若把 `FieldKind` 改成 `Id` 会被 `field_id_format` 判为非法格式，直接击穿
现有 `validate_data.py --strict` 零警告基线——这是"改 `FieldKind`"这条路径的具体化风险证据。

## 根因

- 第 54 条：`QuestContentValidationRule` 收窄改造（消费方反馈第 38 条）时只从"校验规则自己需要
  什么"的角度实现了引用提取，没有预见到内容工具也需要同等能力，是"契约面覆盖不全"而不是缺陷。
- 第 56 条：三条规则各自独立演进，从未有人系统性地对齐"这三类图共同缺什么诊断维度"；孤立节点
  在三类图里的语义差异很大（story_tree 有单一入口、quest_prerequisite/talent_tree 允许合法孤立）
  ，此前也没有一个中立的图分析层可以被复用。
- 第 57 条：`ValidationIssue` 最初设计时 `Field` 只承载"字段路径"这一单一定位维度，没有为"一条
  诊断涉及多个节点"（如成环）这类场景预留结构化字段，只能塞进消息文本，历史设计假设"一条问题
  对应一个字段"，没有预见图结构类诊断的定位需求。
- 第 58 条：两处 `FieldKind` 差异是实现方在登记 schema 时已经知情并主动选择的结果（代码注释
  为证），不是疏漏；只是这类"有意不同"的判断记录习惯性只写在代码里，没有同步抛给消费方可见的
  文档，是文档同步流程的缺口，不是设计缺陷。

## 处理

### 第 54 条：`QuestReferenceExtractor` 公开静态入口

新增 `core/gameplay/quest/contracts/QuestReferenceExtractor.cs`：

- `public static IReadOnlyList<Id> ExtractReferencedQuestIds(string prerequisiteExprText,
  IExprSchema? schema = null)`——提取 `prerequisite` 文本里全部 `quest.*` 引用指向的任务 id，
  已去重、按首次出现顺序排列；`schema` 缺省时退回 `QuestExprSchemaEntries.BuildParsingSchema()`，
  与 `QuestContentValidationRule` 无参构造的退回策略一致。
- 语法解析失败（`ExprParseException`）返回空列表，不向调用方抛出新的未处理异常路径——与
  `ValidatePrerequisiteGraph` 内部"语法错误已由 `expr_parsable` 报告，这里跳过"的既有语义保持
  一致，不给消费方一个新的未处理异常路径（判断记录写在类型/方法文档注释里）。
- 不直接暴露内部 `ExprNode`/`ExprLiteralNode` 语法树类型——那些是 `Core.Foundation.Expr` 的内部
  AST 类型，暴露出去会把编辑器耦合到表达式解析器内部结构。
- `QuestContentValidationRule` 原私有的 `CollectQuestIdLiteralArgs`（AST 遍历逻辑）整体迁移为
  `QuestReferenceExtractor` 的 `internal` 方法（两者同属 `Core.Gameplay` 程序集），
  `ValidatePrerequisiteGraph` 改为调用它，不再各自维护一份遍历逻辑；`ValidatePrerequisiteGraph`
  本身继续消费未去重的原始遍历结果（需要逐次出现的位置信息报 `quest_prerequisite_unknown`，且
  对同一未知 id 的多次引用逐条报告是既有行为），不直接复用去重后的公开入口，行为不变。

测试：`core/gameplay/quest/tests/QuestReferenceExtractorTests.cs`（新增 7 例）——多引用（按源
顺序返回）、重复引用去重（保留首次出现顺序）、无引用返回空、`null`/空串返回空、非法表达式返回
空不抛异常、嵌套在 `and`/`or`/`not` 内仍能收集、自定义 schema 与默认 schema 结果一致。

### 第 56 条：`ContentGraphAnalyzer` 统一图分析 + `story_tree_node_unreachable`

新增 `core/foundation/data_registry/contracts/ContentGraphAnalyzer.cs`：

- `public static ContentGraphAnalysis Analyze(IReadOnlyList<string> nodeIds,
  IReadOnlyDictionary<string, IReadOnlyList<string>> edges, IReadOnlyList<string>? roots = null)`
  ——对调用方给定的"节点 id 全集 + 有向邻接表"统一给出：`InDegree`/`OutDegree`（入度出度）、
  `IsolatedNodeIds`（入度出度均为 0）、`ReachableNodeIds`/`UnreachableNodeIds`（相对
  `roots` 的可达性，未传 `roots` 时均为空列表）、`Cycles`（三色标记 DFS 发现的全部回边对应的环，
  不是穷举的最小环基）。纯只读分析，不产出任何 `ValidationIssue`，不感知任何具体表结构——放在
  `Core.Foundation`（而不是 `Core.Gameplay`/`Core.Numbers` 任一具体模块）是因为
  `story_tree`/`quest_prerequisite` 在 `Core.Gameplay`、`talent_tree` 在 `Core.Numbers`，两者
  互不依赖，唯一公共祖先是 `Core.Foundation`。
- 边引用了 `nodeIds` 之外的目标（悬空引用）时直接忽略该条边（不计入度数/可达性/成环分析）——
  悬空引用属于各自模块单独校验的问题，不重复报告。

`DialogContentValidationRule.ValidateStoryTree` 内部复用它新增
`story_tree_node_unreachable`（Warning，`NonEscalatable`）：从运行时实际入口 `nodes[0]`（核实
`StoryTreeDefinition.FirstNode`/`DialogHost.StartStory` 确认起点定义即 `nodes[0]`，不是假设）
出发不可达的节点。`DialogContentValidationRule.NonEscalatable` 改为 `true`（本规则此前全部检查
项均为 Error，本项是唯一的 Warning，不影响既有行为）。

`quest_prerequisite`/`talent_tree` **不落地等价校验警告**：多数任务合法地没有前置、也不被任何
其它任务引用（一条独立支线任务本身就是正常内容形态）；天赋树允许多个并列根节点
（`prerequisites=[]` 可以有多个，是合法的并列分支设计）。照搬"孤立即警告"会在示例数据上产生
大量误报，破坏 `validate_data.py --strict` 零警告基线。两者改为把 `ContentGraphAnalyzer` 作为
公开分析能力暴露给内容工具，由内容工具自行决定如何展示（如天赋树画布高亮孤立节点、任务链面板
提示断链），框架不代为拍板"这算不算问题"。

测试：`core/foundation/data_registry/tests/ContentGraphAnalyzerTests.cs`（新增 9 例，覆盖可达/
不可达、无起点、孤立、入度出度、悬空边、两节点环、自环、无环菱形、起点不在图内）；
`core/gameplay/dialog/tests/DialogSchemaCoverageTests.cs` 新增 2 例
（`StoryTree_UnreachableNode_ReportsStoryTreeNodeUnreachable`/
`StoryTree_AllNodesReachable_DoesNotReportUnreachable`）；
`core/numbers/archetype/tests/ArchTalentTreeCycleValidationRuleTests.cs` 新增
`IsolatedNode_NoPrerequisiteNoReference_DoesNotReportAnyIssue` 锁定"不报警告"这一行为。

### 第 57 条：`ValidationIssue.AffectedNodeIds` + 四项 `Field` 下标路径

`core/foundation/data_registry/contracts/ValidationReport.cs`：

- `ValidationIssue` 新增只读属性 `AffectedNodeIds: IReadOnlyList<string>`（默认空集合，不是
  `null`），经新增的十参数构造函数传入（ABI 只新增：走既有"新构造重载"惯例，六参数/九参数构造
  物理签名不变）；新增 `WithAffectedNodeIds(IReadOnlyList<string>)`，同既有 `WithRuleId` 惯例返回
  副本。
- 跨节点路径类诊断（`story_tree_cycle`/`quest_prerequisite_cycle`/`talent_prerequisite_cycle`）
  按环上出现顺序填入环上全部节点 id；单节点类诊断
  （`story_tree_duplicate_node_id`/`story_tree_dangling_next_node`/`quest_prerequisite_unknown`/
  `talent_prerequisite_missing`）填入该节点自身 id；`story_tree_min_nodes`/`talent_node_id`
  两项不涉及具体已知节点（前者是"数组整体为空"，后者是"id 本身缺失/非法，没有合法 id 可填"），
  `AffectedNodeIds` 维持默认空集合。

四项单节点类诊断补齐 `Field` 具体下标路径：

| 检查名 | 改动前 | 改动后 |
| --- | --- | --- |
| `story_tree_duplicate_node_id` | `"nodes"` | `nodes[{首次出现下标}].id` |
| `story_tree_dangling_next_node` | `"nodes"` | `nodes[{节点下标}].branches[{分支下标}].next_node_id` |
| `talent_node_id` | 未传 | `nodes[{数组下标}].id` |
| `talent_prerequisite_missing` | 未传 | `nodes[{节点下标}].prerequisites[{JSON 数组下标}]` |

`quest_prerequisite_unknown`/`quest_prerequisite_cycle` 的 `Field` 维持既有的 `"prerequisite"`
不变——任务记录本身经 `RecordKey` 已是最小定位单元，`prerequisite` 是标量字符串字段，没有数组
下标可补。

`toolchain/validator/Program.cs` 的 `AppendIssueJson` 新增 `affected_node_ids` 字段——**只在
非空时输出**（与 `group`/`note`/`rule_id` 恒输出 `null` 的既有约定不同，这是本字段专属口径：
绝大多数诊断都不涉及图节点，恒定输出空数组会让 JSON 体积无谓膨胀）。

**成环检测算法一并勘误（`ArchTalentTreeCycleValidationRule`）**：原实现每个候选起点各自新开一套
`visiting`/`visited` 集合跑递归（等价于三色标记但无路径记录，无法产出 `AffectedNodeIds` 要求的
环上节点序列），且按 `Dictionary.Keys` 枚举顺序选取候选起点（违反 AGENTS.md"保持确定性：不依赖
字典枚举顺序"）。改为与 `story_tree_cycle`/`quest_prerequisite_cycle` 同款的单次共享状态三色
标记 DFS + 显式 `path` 列表，候选起点顺序改用节点在原始 JSON 数组里的出现顺序；"是否存在环""
报告首个发现的环"两条既有语义不变，`talent_prerequisite_cycle` 消息文本顺带补上完整环路链
（原消息只报告 DFS 起点），无既有测试断言该文本，判定为无风险勘误。

测试：`core/foundation/data_registry/tests/ValidationRuleMetadataTests.cs` 新增 4 例
（`AffectedNodeIds` 默认空/十参数构造设置/`WithAffectedNodeIds` 返回副本/`WithRuleId` 保留
`AffectedNodeIds`）；`DialogSchemaCoverageTests.cs` 新增 3 例（重复节点/悬空引用的 `Field`+
`AffectedNodeIds`、成环的 `AffectedNodeIds`）；`E38_QuestPrerequisiteCycleTests.cs` 就地扩展 3
个既有用例补充 `AffectedNodeIds` 断言（不新增用例数、不放宽既有断言）；
`ArchTalentTreeCycleValidationRuleTests.cs`（新文件）新增 6 例覆盖 `talent_node_id`/
`talent_prerequisite_missing` 的 `Field` 下标路径与 `talent_prerequisite_cycle` 的
`AffectedNodeIds`。

### 第 58 条：`FieldKind` 差异纯文档补齐（方案 A，不动 schema）

采纳推荐方案 A：把已经存在于 `ArchSchemas.cs` 代码注释里的判断记录同步到消费方可见的文档层，

- 两处 `FieldSchema.Description`（`DialogSchemas.cs` 的 `story_tree.nodes[].id`、

`validate_data.py --strict` 零警告基线（已用现有数据验证过这一风险，不是猜测）；且这类"收紧既有
字段格式约束"属于内容数据的有效 breaking change，需要设计层先拍板并出变更记录，本次不默认选择。
