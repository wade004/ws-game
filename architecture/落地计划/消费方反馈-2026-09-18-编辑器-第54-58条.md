## 现象与复现

原文见 `ws-game-editor` 仓库 `docs/上游反馈-待转发-2026-09-18.md`（`phase/p4.3` 分支）。

### 第 54 条

`core/gameplay/quest/core/QuestContentValidationRule.cs:356` 的
`CollectQuestIdLiteralArgs(ExprNode, List<ExprLiteralNode>)` 是私有方法，唯一调用点是同文件的
`ValidatePrerequisiteGraph`（:306）。内容工具（如编辑器"任务前置关系"面板）想拿到"某条
`prerequisite` 引用了哪些任务 id"这一能力，没有任何公开等价入口，只能自己重新实现一遍 Expr
语法树遍历。全仓库 grep 只命中这一处定义，确认无其它公开等价入口。

### 第 55 条

`IDialogHost`（`core/gameplay/dialog/contracts/IDialogHost.cs`）的只读方法
（`GetGossipView`/`GetStoryView`）要求单位"当前已处于一个已打开的会话中"；`IQuestHost.GetState`
要求给定具体单位，按其运行期上下文（世界状态/其它任务进度）实时求值 `prerequisite`。两者都不
支持"给定任意剧情树/任务 id，脱离任何单位/会话，分析结构"这一预演场景——编辑器"剧情/任务链
试走"面板此前只能手工读 `dialog.story_tree`/`quest.def` 原始 JSON 核对分支/前置关系，容易出错
且效率低。

### 第 56 条

`story_tree`/`quest_prerequisite`/`talent_tree` 三类"节点 + 有向边"图形数据均无孤岛/不可达节点
诊断——逐条核实三条规则的完整校验清单：`DialogContentValidationRule.ValidateStoryTree`（只有
`story_tree_min_nodes`/`story_tree_duplicate_node_id`/`story_tree_dangling_next_node`/
`story_tree_cycle` 四项）、`QuestContentValidationRule.ValidatePrerequisiteGraph`（只有
`quest_prerequisite_unknown`/`quest_prerequisite_cycle` 两项）、
`ArchTalentTreeCycleValidationRule`（只有 `talent_node_id`/`talent_prerequisite_missing`/
`talent_prerequisite_cycle` 三项），均无可达性/孤立节点检查。

### 第 57 条

九项图诊断（`story_tree`/`quest_prerequisite`/`talent_tree` 各自的结构性检查，4+2+3=9，与反馈
原文计数一致）的 `ValidationIssue.Field` 逐项核对，均为静态字符串或未传（`null`），不含具体节点
下标——问题面板/图形化画布拿到诊断后无法直接定位到具体是哪个节点/哪条边，只能自己重新解析一遍
数据反查。

### 第 58 条

`core/gameplay/dialog/core/DialogSchemas.cs:169`
（`dialog.story_tree.nodes[].id`，`FieldKind.Id`）与
`core/numbers/archetype/contracts/ArchSchemas.cs:146`
（`arch.talent_tree.nodes[].id`，`FieldKind.String`）两处节点 id 声明确实不同。核实
`arch.talent_tree` 一侧是有意为之——紧邻的代码注释（改动前 :144～145）已写明"`ArchetypeRegistry
.ParseTalentTree`：id 缺失/非字符串直接抛异常，必填；只检查 JsonString，不做 Id 格式校验，登记
为 String 而非 Id（以运行时为准）"，只是这份判断记录此前只存在于代码注释，未同步到消费方可见的
文档层。`core/sim/tests/data/arch/arch.talent_tree.json` 的既有节点 id 就是 `"node_a"`/
`"node_b"`（不含点），若把 `FieldKind` 改成 `Id` 会被 `field_id_format` 判为非法格式，直接击穿
现有 `validate_data.py --strict` 零警告基线——这是"改 `FieldKind`"这条路径的具体化风险证据。

## 根因

- 第 54 条：`QuestContentValidationRule` 收窄改造（消费方反馈第 38 条）时只从"校验规则自己需要
  什么"的角度实现了引用提取，没有预见到内容工具也需要同等能力，是"契约面覆盖不全"而不是缺陷。
- 第 55 条：`IDialogHost`/`IQuestHost` 从任务书拍板时起就是围绕"单位的运行期会话/状态机"设计的
  有状态契约，从未规划过"脱离单位、纯读结构"这一使用场景——不是遗漏，是两种不同的使用场景
  （"驱动一次真实交互"与"预演/分析内容"）此前只覆盖了前者。
- 第 56 条：三条规则各自独立演进，从未有人系统性地对齐"这三类图共同缺什么诊断维度"；孤立节点
  在三类图里的语义差异很大（story_tree 有单一入口、quest_prerequisite/talent_tree 允许合法孤立）
  ，此前也没有一个中立的图分析层可以被复用。
- 第 57 条：`ValidationIssue` 最初设计时 `Field` 只承载"字段路径"这一单一定位维度，没有为"一条
  诊断涉及多个节点"（如成环）这类场景预留结构化字段，只能塞进消息文本，历史设计假设"一条问题
  对应一个字段"，没有预见图结构类诊断的定位需求。
- 第 58 条：两处 `FieldKind` 差异是实现方在登记 schema 时已经知情并主动选择的结果（代码注释
  为证），不是疏漏；只是这类"有意不同"的判断记录习惯性只写在代码里，没有同步抛给消费方可见的
  文档，是文档同步流程的缺口，不是设计缺陷。

## 处理

### 第 54 条：`QuestReferenceExtractor` 公开静态入口

新增 `core/gameplay/quest/contracts/QuestReferenceExtractor.cs`：

- `public static IReadOnlyList<Id> ExtractReferencedQuestIds(string prerequisiteExprText,
  IExprSchema? schema = null)`——提取 `prerequisite` 文本里全部 `quest.*` 引用指向的任务 id，
  已去重、按首次出现顺序排列；`schema` 缺省时退回 `QuestExprSchemaEntries.BuildParsingSchema()`，
  与 `QuestContentValidationRule` 无参构造的退回策略一致。
- 语法解析失败（`ExprParseException`）返回空列表，不向调用方抛出新的未处理异常路径——与
  `ValidatePrerequisiteGraph` 内部"语法错误已由 `expr_parsable` 报告，这里跳过"的既有语义保持
  一致，不给消费方一个新的未处理异常路径（判断记录写在类型/方法文档注释里）。
- 不直接暴露内部 `ExprNode`/`ExprLiteralNode` 语法树类型——那些是 `Core.Foundation.Expr` 的内部
  AST 类型，暴露出去会把编辑器耦合到表达式解析器内部结构。
- `QuestContentValidationRule` 原私有的 `CollectQuestIdLiteralArgs`（AST 遍历逻辑）整体迁移为
  `QuestReferenceExtractor` 的 `internal` 方法（两者同属 `Core.Gameplay` 程序集），
  `ValidatePrerequisiteGraph` 改为调用它，不再各自维护一份遍历逻辑；`ValidatePrerequisiteGraph`
  本身继续消费未去重的原始遍历结果（需要逐次出现的位置信息报 `quest_prerequisite_unknown`，且
  对同一未知 id 的多次引用逐条报告是既有行为），不直接复用去重后的公开入口，行为不变。

测试：`core/gameplay/quest/tests/QuestReferenceExtractorTests.cs`（新增 7 例）——多引用（按源
顺序返回）、重复引用去重（保留首次出现顺序）、无引用返回空、`null`/空串返回空、非法表达式返回
空不抛异常、嵌套在 `and`/`or`/`not` 内仍能收集、自定义 schema 与默认 schema 结果一致。

### 第 55 条：`DialogStoryPreview`/`QuestPrerequisitePreview` 只读无状态预演入口

**设计口径拍板（勘察报告标注的"需要先回设计层"的两点）**：

1. **对话预演是路径枚举还是单一路径**：拍板为"两者都要"——默认（不传条件回调）只给纯结构信息
   （节点/出边/起点/终止节点）；传入可选的条件判定回调时，额外给出可达节点集合与**全部**路径
   枚举（深度优先，`maxPaths`/`maxDepth` 双上限防御，遇环/悬空引用/命中上限均安全截断并显式
   标记）。
2. **任务链预演是否涉及 objective 语义**：拍板为"不涉及"——只分析 `prerequisite` 表达式里
   `quest.*` 引用构成的任务依赖图（直接前置/传递闭包/成环/拓扑序/可接性），不碰 `QuestObjective`。

**`DialogStoryPreview`——对话/剧情树预演**：
`Core.Gameplay.Dialog.DialogStoryPreview.Preview(StoryTreeDefinition tree, Func<string, bool?>?
evaluateCondition = null, int maxPaths = 200, int maxDepth = 64): DialogStoryPreviewResult`：

- **纯结构信息**（恒返回）：`Nodes`（每个节点的 id/文本键/说话者引用 + 每条分支的下标/文本键/
  条件规范化文本/目标节点 id）、`StartNodeId`（直接读 `StoryTreeDefinition.FirstNode`，与
  `DialogHost.StartStory` 共用同一段取值逻辑，不复制一份）、`TerminalNodeIds`（该节点全部分支
  `next_node_id` 均为空，或零分支）。
- **条件文本**：`ConditionText` 是 `StoryBranchDef.Condition`（`ExprNode`）的 `ToString()` 规范化
  文本，不是原始逐字符文本——语法树本身不保留原始字符串，规范化文本语义等价，与
  `ExprNode.ToString()` 既有承诺一致；验收复核确认反馈原文与本条设计口径均未要求保留原始逐字符
  文本，编辑器需要的是"给定回调求值"这一用法，不需要 `RawConditionText`，本次不新增。
- **可选可达性/路径枚举**：提供 `evaluateCondition` 回调（入参为分支条件的规范化文本，返回
  `true`/`false`/`null`；`null`=未知按"可能"处理）时，额外给出 `ReachableNodeIds`（从起点出发，
  沿"可能可见"分支能到达的全部节点）与 `Paths`（全部路径枚举，每条是节点 id 序列）；命中
  `maxPaths`/`maxDepth`、或遇到环（当前路径已访问过目标节点——不假设输入已通过
  `story_tree_cycle` 校验，预演入口面向任意/编辑中数据必须自行防御）、或悬空 `next_node_id`
  （引用了不存在的节点，另见第 56 条校验缺口），均安全终止该路径并把 `PathsTruncated` 置真。
- **不执行**：不调用任何 `PerformanceHookRef`、不推进任务/世界状态、不发布任何事件、不自己求值
  `condition`——是否可见完全由调用方回调决定。

**`QuestPrerequisitePreview`——任务前置链预演**：
`Core.Gameplay.Quest.QuestPrerequisitePreview.Preview(Id questId, IEnumerable<QuestDefinition>
definitions, IReadOnlyCollection<Id>? completedQuestIds = null, int maxNodes = 10000):
QuestPrerequisitePreviewResult`：

- **前置引用提取**（整合验收时勘误，见文末"整合验收补充"一节）：本方法原在并行分支上直接调用
  框架已公开的 `Core.Foundation.Expr.ExprReferenceCollector.Collect` 自行过滤 `Group == quest` +
  取 Id 字面量参数——与第 54 条 `QuestReferenceExtractor.CollectQuestIdLiteralArgs`（同样最终基于
  `ExprReferenceCollector.Collect`）重复了这一步过滤逻辑。整合到 `integrate/1.41.0` 时改为直接
  调用 `QuestReferenceExtractor` 新增的 `internal` 重载（接受已解析的 `ExprNode`，不重新解析
  文本），消除两处重复实现，行为不变（`E55_QuestPrerequisitePreviewTests` 全量复跑通过）。
- **图结构分析**：`DirectPrerequisiteQuestIds`（`questId` 直接引用的任务 id，按表达式出现顺序
  去重）、`TransitiveClosureQuestIds`（广度优先可达的全部已知任务 id）、`UnknownReferencedQuestIds`
  （引用了不在给定定义集合内的任务 id——数据缺陷的显式标记，不静默丢弃）、`HasCycle`/`CyclePath`
  （子图内是否成环，成环时给出首尾重复的环路径）、`TopologicalOrder`（前置排在被依赖任务之前的
  合法顺序；`HasCycle` 为真时恒为空——不是"无前置"的误导性空值）。图算法（BFS 闭包、Kahn 拓扑序、
  三色标记找环）独立实现，不依赖字典枚举顺序或哈希顺序，保证确定性。
- **可选可接性判定**：提供 `completedQuestIds` 时，额外给出 `IsAvailableByReferencedQuests`/
  `BlockingQuestIds`（`DirectPrerequisiteQuestIds` 中不在已完成集合内的子集，含未知引用——未知
  引用恒视为"未满足"）。
- **语义边界（重要限制）**：只看 `prerequisite` 里引用了哪些任务，不看 `and`/`or`/`not` 组合方式
  （与既有 `quest_prerequisite_cycle`/`quest_prerequisite_unknown` 校验构图同一套口径），也不涉及
  `QuestObjective` 语义。`IsAvailableByReferencedQuests` 因此是"假设 `prerequisite` 只由这些
  `quest.*` 引用以合取方式组成"这一简化视角下的可接性，不是 `IQuestHost.GetState` 的等价物——
  `prerequisite` 里若还混有世界标志/玩家属性等其它条件，或用 `or` 组合，真正可接性仍须调用
  `GetState`。面板应如实向用户说明这一范围，不能把预演结果当作最终可接性结论展示。
- **防御上限**：`maxNodes`（默认 10000）防止极端数据下子图扩展失控，命中时 `ClosureTruncated`
  置真；真实内容规模不预期触发。

**为何不改 `IDialogHost`/`IQuestHost`**：预演是与运行期会话/状态机正交的无状态查询，加进两个
接口（哪怕用默认接口成员）会把"预演"这一新概念混进"运行期契约"，且未来预演能力的演进（如接入
更丰富的条件求值上下文）不应该受两个接口的兼容性约束牵连。拆成独立静态类是本仓库既有惯例（同
`ExprReferenceCollector`"只读遍历入口"）。

测试：`core/gameplay/dialog/tests/E55_DialogStoryPreviewTests.cs`（新增 15 例）、
`core/gameplay/quest/tests/E55_QuestPrerequisitePreviewTests.cs`（新增 15 例，共 30 例）：

1. **与真实宿主对账（核心证据）**：Dialog——`Preview_StartNodeId_MatchesRealHostStartStory`
   （起点）、`Preview_VisibleBranchesUnderCallback_MatchesRealHostGetStoryView`（可选分支，条件
   回调用与 `DialogHost` 内部同一份 `QuestExprSchemaEntries.BuildParsingSchema` 把
   `ConditionText` 重新解析回 `ExprNode` 再求值）、
   `Preview_ReachableNodeIds_MatchesRealHostWalkAcrossBothBranches`（可达节点，二分支剧情树在
   两种玩家等级下分别对账）；Quest——`Preview_Availability_MatchesRealHostGetState_SinglePrerequisite`
   （单前置，"可接任务"对账）、`Preview_ClosureAndTopologicalOrder_MatchesRealHostThreeQuestChain`
   （三级任务链，"接取→交付"真实流程逐步核对）。
2. **拓扑序有效性**：`Preview_DiamondDependency_TopologicalOrderRespectsAllEdges`——菱形依赖

   通用性质。
3. **无状态证明**：`Preview_RepeatedCalls_ProduceEqualResults`/
   `Preview_ConcurrentCalls_ProduceEqualResultsAndDoNotThrow`（Dialog）、
   `Preview_RepeatedAndConcurrentCalls_ProduceEqualResults`（Quest，含 16 路并发）。
4. **边界用例**：空/单节点树、环（含自环）、悬空引用、`maxPaths`/`maxDepth`/`maxNodes` 截断、
   `null` 参数校验，均验证安全终止（不抛异常/不死循环）且显式标记降级（`PathsTruncated`/
   `ClosureTruncated`）。

既有 `core/gameplay/dialog/tests/DialogHostTests.cs`、`core/gameplay/quest/tests/QuestHostTests.cs`
等既有测试逐字节不变通过，证明本次改动未影响 `IDialogHost`/`IQuestHost` 既有行为。

### 第 56 条：`ContentGraphAnalyzer` 统一图分析 + `story_tree_node_unreachable`

新增 `core/foundation/data_registry/contracts/ContentGraphAnalyzer.cs`：

- `public static ContentGraphAnalysis Analyze(IReadOnlyList<string> nodeIds,
  IReadOnlyDictionary<string, IReadOnlyList<string>> edges, IReadOnlyList<string>? roots = null)`
  ——对调用方给定的"节点 id 全集 + 有向邻接表"统一给出：`InDegree`/`OutDegree`（入度出度）、
  `IsolatedNodeIds`（入度出度均为 0）、`ReachableNodeIds`/`UnreachableNodeIds`（相对
  `roots` 的可达性，未传 `roots` 时均为空列表）、`Cycles`（三色标记 DFS 发现的全部回边对应的环，
  不是穷举的最小环基）。纯只读分析，不产出任何 `ValidationIssue`，不感知任何具体表结构——放在
  `Core.Foundation`（而不是 `Core.Gameplay`/`Core.Numbers` 任一具体模块）是因为
  `story_tree`/`quest_prerequisite` 在 `Core.Gameplay`、`talent_tree` 在 `Core.Numbers`，两者
  互不依赖，唯一公共祖先是 `Core.Foundation`。
- 边引用了 `nodeIds` 之外的目标（悬空引用）时直接忽略该条边（不计入度数/可达性/成环分析）——
  悬空引用属于各自模块单独校验的问题，不重复报告。

`DialogContentValidationRule.ValidateStoryTree` 内部复用它新增
