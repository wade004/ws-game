# 问题 A：读条完成当帧新冷却被提前推进

## 现象

固定配置 `cast_time=0.5`、`cooldown_duration=1`，关闭 GCD 与随机命中因素。消费方独立复现程序
（最小 `RulesAssembly` 装配直接调用原生 `SkillHost.Update`）观察到：技能完成时新开启的冷却剩余
秒数受推进时如何拆分成多个 `dt` 子步影响——同一个完成时刻，不同拆分给出不同结果：

| 推进到 0.5 秒的分段 | 完成时预期新冷却 | 修复前实际新冷却 |
|---|---:|---:|
| `[0.5]`（单步） | 1 | 0.5 |
| `[0.25, 0.25]` | 1 | 0.75 |
| `[0.25, 0.125, 0.125]` | 1 | 0.875 |
| 瞬发同次调用对照（调用后尚未推进时间） | 1 | 1（正常） |

固定消耗（7）、固定伤害（10）、技能成功事件（1）均正确，问题仅出在新冷却的时间基准上。

## 根因

`core/rules/skill/core/SkillHost.cs` 的 `Update(double dt)`：

```
public void Update(double dt)
{
    _pipeline.Update(dt);       // 读条恰好在本次 dt 内完成 → CastPipeline.FinishCast 开启新冷却
    AdvanceRoundTimers(dt);     // 又用同一个 dt 推进（含刚创建的新冷却）
}
```

`_pipeline.Update(dt)` 内部经 `CastPipeline.AdvanceOne`→`FinishCast` 完成读条时，通过
`StartCooldownAndGcd`→`CooldownTracker.StartCooldown` 新建一条冷却记录；紧接着同一次方法调用里的
`AdvanceRoundTimers(dt)` 又调用 `CooldownTracker.Update(dt)`，把这条刚创建、原本应该"从现在起满额
计时"的冷却，按"进入本次 `dt` 之前就已经计时了整个 `dt`"的逻辑再扣一次。新状态从"不存在"到
"存在"这一瞬间被当成已经存在了整个 `dt`，多扣的量自然随 `dt` 如何被拆成子步而变化——这正是消费方
观察到的"分段不一致"症状的根源。

## 处理

选择方案 a（调换调用顺序，未选方案 b"给每个计时器额外记一个创建于本 tick 的标记"）：

```
public void Update(double dt)
{
    AdvanceRoundTimers(dt);     // 先推进"进入本次 dt 之前就已存在"的状态
    _pipeline.Update(dt);       // 读条/引导完成时新建的状态自然不会被本次调用碰到
}
```

判断记录（为什么方案 a 足够、且更简单）：`AdvanceRoundTimers` 只读写既有冷却/GCD/充能/光环/Proc
内部冷却/学派锁定状态，不依赖 `_pipeline` 内部字段，调换顺序不改变它自身的语义；调换后，读条/引导
在本次 `dt` 内完成而新创建的计时状态，天然要等到**下一次** `Update` 调用才第一次被推进——此时它已
经真实存在了一整个 tick，用那次调用的 `dt` 扣减是正确的。需要核实"是否引入其它时序变化"的唯一边界
是：读条完成时若有排队的下一个施法（`FinishCast` 的 `Queued` 分支），`TryStartCast` 检查 GCD/冷却
是否就绪时，读到的现在是"已经按本次 `dt` 推进过"的最新值而不是调换前"尚未被本次 tick 推进"的旧值
——这只会让排队技能的就绪判定更及时（少算一次滞后），不存在把原本不就绪判成就绪的错误方向；学派锁定
推进（`AdvanceSchoolLocks`）与读条/引导完成之间没有数据依赖（写入学派锁定的两条路径只在事件总线批
处理派发时触发，不在 `Update` 内部同步发生），调换顺序不影响它。以上判断均已用测试钉住（见下）。

离散模式（[ADR-0013](../adr/0013-时间模型可替换即时与回合制同一规则层.md)）单独核对：
`AdvanceCastForActor`（行动者自己的离散步）与 `AdvanceRoundTimers`（round-end）的 `dt` 恒为
`1.0`，不可再分——不存在"同一完成时刻因拆分方式不同产生不同结果"这一可观测症状的前提条件（本次
反馈复现的三组分段差异，根源正是"同一个总时长被拆成不同数量的子步"，离散模式没有子步可拆）。
现状行为（mid-round 新建冷却在同一 round-end 立即被扣减 1 轮，效果等价于"下一轮即可再次使用"）
本次不做改动——这更接近"是否应当改成下一轮才开始扣减"的**离散冷却起算语义**判断，需要独立走一轮
[ADR](../12_扩展与变更流程.md) 拍板，不属于本次反馈复现的缺陷范围；已新增对照测试钉住现状。

### 相邻计时状态排查结论

| 计时状态 | 创建点是否与读条/引导完成同一调用 | 是否同类缺陷 | 处理 |
|---|---|---|---|
| 技能自身/分类冷却 | 是（`FinishCast`→`StartCooldownAndGcd`→`CooldownTracker.StartCooldown`） | 是 | 随本次改动根治 |
| GCD（公共冷却） | 是（同一调用点 `StartCooldownAndGcd`→`CooldownTracker.StartGcd`） | 是 | 随本次改动根治 |
| 充能恢复窗口 | 是（充能耗尽的那一刻，同一调用点写入 `RechargeRemaining`） | 是 | 随本次改动根治 |
| 光环持续时间/周期累加器 | 是（`ExecuteEffectsOnly` 里的 `apply_aura` 效果落地新实例） | 是 | 随本次改动根治 |
| Proc 内部冷却（ICD） | 否——只在 `ProcHost.OnEvent`（经事件总线 `DispatchPending` 批处理才派发）里写入，不在 `SkillHost.Update` 内部同步发生 | 否 | 新增对照测试钉住"不受影响" |
| 离散模式冷却/GCD/充能/光环 | `AdvanceCastForActor`/`AdvanceRoundTimers` 的 `dt` 恒为 1.0，不可再分 | 不适用 | 现状（mid-round 新建冷却同一 round-end 立即扣减）保留，新增对照测试钉住；起算语义需另走 ADR |

# 问题 B：施法生命周期事件缺少实例关联标识

## 现象

`CastResult.CastInstanceId` 已公开，但 `SkillCastStartEvent`/`SkillCastSuccessEvent`/
`SkillCastFailedEvent`/`SkillCastInterruptedEvent` 没有对应字段。消费方反射固定版本 1.15.0 的
`Core.Rules.dll` 确认：

| 类型 | 修复前公开属性 |
|---|---|
| `SkillCastStartEvent` | `Key`, `CasterId`, `SkillId`, `CastTime` |
| `SkillCastSuccessEvent` | `Key`, `CasterId`, `SkillId`, `Targets`, `IsInstant`, `CastTimeSeconds` |
| `SkillCastFailedEvent` | `Key`, `CasterId`, `SkillId`, `ReasonCode` |
| `SkillCastInterruptedEvent` | `Key`, `CasterId`, `SkillId`, `InterrupterId` |

同一单位连续释放相同技能、读条中排队、取消后立即重试等场景下，仅靠 `(casterId, skillId)` 无法稳定
关联"这一次请求"的开始/成功/失败/打断。

## 根因

不是运行时缺陷，是公开契约缺口：`CastPipeline` 内部一直有一个每次施法请求分配一次的
`NextCastInstanceId()`（`CastResult.CastInstanceId` 的值就来自它），但这个 id 从未被戳到四个
生命周期事件类上；此外，排队请求被覆盖或所在读条被打断而清空队列这两条路径，原实现完全静默——
调用方拿着排队时返回的 id，却永远等不到任何结果通知（这一点消费方反馈里也点名要求明确）。

## 契约决定（身份规则）

1. **分配时机**：`CastSkill` 在步骤 1～7 全部校验通过、真正进入步骤 8（立即开始读条/引导/瞬发）
   或进入法术队列时分配 id，随 `CastResult` 返回；步骤 1～7 任一步校验失败不分配
   （`SkillCastFailedEvent.CastInstanceId` 为 `null`，`CastResult.Reason` 仍可辨明失败原因）。
2. **贯穿生命周期**：真正开始读条/引导/瞬发时发出的 `SkillCastStartEvent`，与随后的
   `SkillCastSuccessEvent`/`SkillCastInterruptedEvent`（若发生）携带同一个 id；排队接受本身就是
   一次"分配 id 并随 `CastResult` 返回"的时刻，这个 id 一路带到排队请求真正开始时的
   `SkillCastStartEvent`（不因为"排队接受"与"真正开始"是两次不同的方法调用而分配两个不同的 id）。
3. **排队被清空的通知**：排队请求在真正轮到它之前被清空——两种情形共用新原因码
   `CastFailureReason.QueueCleared`：a) 同一施法者又发起一次落在队列窗口内的新请求，覆盖了尚未
   执行的旧排队请求；b) 占用队列槽位的那次读条/引导本身被打断，排队的下一个技能连同打断一起被
   清空。两种情形都发出一条携带**被清空的那个排队请求自己的实例 id**（不是覆盖它的新请求、也不是
   被打断的当前施法各自的 id）的 `SkillCastFailedEvent`。
4. **`trigger_spell`/Proc 直接效果**：核实现状——`CastPipeline.TriggerCast` 不经过步骤 1～9 施法
   管线，不发本节四个主动施法生命周期事件，维持"不伪造主动施法事件"。它与
   `EffectContext.AttackInstanceId` 的关系：后者是"这一次结算"（一批目标同时应用同一组
   `effects`）的批次标识，每次 `ExecuteEffectsOnly` 调用分配一个全新值，读条/引导期间的多次周期
   跳各自拿到不同的攻击实例 id，即使它们同属一次施法/一次触发——两者是不同层面的标识，不互相冒用。

## 修复位置

- `core/rules/common/contracts/Events.cs`：四个事件类各自新增只读属性 `CastInstanceId`（`Id?`）与

  二义性，同 `SkillHost` 十七/十八参数构造重载判断记录同一套推导）；旧构造原样保留、物理签名不变，
  `CastInstanceId` 恒为 `null`。

## 对消费方的提示

1. **问题 A 升级后即可复验**：升级到包含本次改动的版本后，原复现程序（无需任何修改）三组分段的
   `cooldown_after` 均应为 `1`，`product_gap` 应为 `false`——这是预期的正向信号。
2. **问题 B 新增字段是纯新增**：四个事件的 `CastInstanceId` 属性与新构造重载均为新增，旧编译
   消费程序集无需重新编译即可继续加载运行（已用 `abi_probe.ps1` 核实）；若消费方希望关联施法
   实例生命周期，改用新构造/读取新属性即可，不需要修改任何现有调用点。
3. **`QueueCleared` 是新的失败原因码**：若消费方订阅 `skill.cast_failed` 事件时对 `reasonCode`
   做了穷举分支（如 `switch` 语句），升级后需要补上这个新分支（或有默认兜底分支），否则会漏判
   "排队请求被清空"这一新增的失败原因；此前这类情形完全没有对应事件，不存在"从其它原因码误判过来"
   的兼容性风险。
4. **不需要重跑现有断言来"验证问题 A 仍存在"**：消费方原验收断言写的是"预期 1、实际 0.5/0.75/0.875"
   这种旧缺陷特征，升级后重跑会转为通过——这是预期的正向信号，不是新的异常。
