# 消费方变更通知（内容编辑器项目，TryGet 单记录查询契约行为修正，2026-09-19）

> 本文档允许出现具体技术名（引擎/语言/框架/工具名），不受 `architecture/00～14` 与
> `architecture/adr/` 正文的禁用词约束（见仓库根 `CLAUDE.md`"硬性规则"）。本文档是主动的**变更
> 通知**（不是回复某一条具体反馈编号），面向下游"内容编辑器"项目（仓库 `ws-game-editor`）——
> 通知 `IDataRegistryView.TryGet` 单记录查询方法返回值语义的破坏性修正、给出自查指引。关联决策：
> [ADR-0041](../adr/0041-数据注册表单记录容错查询语义修正.md)。本次修正是在发布 1.45.0
> 过程中实测发现的缺陷根治，不是回应某一条已编号的消费方反馈。

**结论先行**：`IDataRegistryView.TryGet(string, string, out DataRecord)`/`TryGet(string,
CommonId, out DataRecord)`（消费方反馈第 45 条、1.38.0 引入）此前实现有缺陷——只要注册表整体
未处于阻断态，该方法恒返回 `true`，哪怕按主键根本查不到任何记录（`record` 为 `null` 时也返回
`true`）。这与同类"按键查询、返回值表示是否成功"方法的通用调用惯例相悖：调用方按惯例会认为
"返回 `true` 就代表确实读到了记录"，但原实现的返回值实际只表示"这次查询有没有因为阻断态被拒绝"。
现已修正为：**返回值即"是否找到记录"**——记录存在才返回 `true`，记录不存在或整体阻断都返回
`false`。方法名与参数签名未变，只是"记录不存在但未阻断"这一分支的返回值从 `true` 改成了
`false`。若编辑器项目直接使用了这两个方法的返回值判断"是否找到"，请按第 2 节自查。

## 1. 三种情形 before/after 对照

| 情形 | 修正前 | 修正后 |
|---|---|---|
| 记录存在 | 返回 `true`，`record` 为该记录 | 不变 |
| 记录不存在（表可正常访问，未阻断） | 返回 `true`，`record` 为 `null` | **返回 `false`，`record` 为 `null`** |
| 整体阻断态（数据校验未通过，禁止读取） | 返回 `false`，`record` 为 `null` | 不变 |

两处物理实现（`IDataRegistryView` 接口默认实现、`Core.Foundation.DataRegistry.DataRegistry` 的
显式覆盖）口径完全一致，均已按上表修正。

## 2. 编辑器侧需要自查什么

如果编辑器代码里有类似下面这种写法：

```
if (registry.TryGet(table, key, out var record))
{
    // 此前：这个分支在"记录不存在但未阻断"时也会被执行进来，record 实际是 null，
    //       若后续代码没有再判空就直接使用 record，此前可能已经在阻断态之外的场景里
    //       因为 record 为 null 而抛 NullReferenceException 或产生其它非预期行为——
    //       如果编辑器侧此前已经自行加了 record != null 的判空，说明编辑器侧实际上
    //       从未真正依赖过 TryGet 的返回值本身表达"找到与否"，不受本次修正影响。
}
```

自查步骤：
1. 全局搜索编辑器代码库里对 `TryGet(...)`（数据注册表这一具体重载，注意与其它同名方法区分）的
   调用点。
2. 对每个调用点确认：调用方是否把返回值 `true` 当作"确实找到了记录"的依据来分支处理？
   - 若是，且原本没有对 `record` 做额外判空——修正后行为变得**更符合直觉**（此前若命中"记录
     不存在"这一情形，返回值是 `true`、`out` 参数是 `null`，若调用方紧接着直接用
     `record.某字段`，此前就已经会抛异常，只是"阻断态下会被防住"给了一种"这个方法已经处理好了
     异常情况"的错觉；修正后这类场景直接从 `if` 分支的条件处被挡住，`record` 从不会以 `null`
     的形态流入 `if` 分支内部）——通常不需要改代码，行为只是变得更安全。
   - 若调用方原本就在 `if` 分支内部又对 `record` 做了一次判空（说明调用方已经不信任返回值本身
     表达"找到与否"，是防御性写法）——不受影响，无需改动，可以按需去掉这层多余判空（非必须）。
   - 若调用方把返回值当"这次读取有没有被阻断"来用（即真正想问的是"数据是不是整体不可信"，不是
     "这条记录是否存在"）——这一用法现在得不到想要的答案（修正后"记录不存在"也会返回
     `false`，不能再据此反推"是不是阻断"）。这类场景请改用
     `Core.Foundation.DataRegistry.TolerantRegistryView`（`IsDegraded`/`MissingTables`/
     `WasMissing(table)`）获取这一更细粒度的诊断信息，见第 3 节。
3. 若编辑器侧有测试断言直接判断 `TryGet(...)` 的返回值（例如断言"这条记录应该能查到"），且测试
   数据里该记录确实存在——断言行为不变，仍会通过。若断言的记录其实不存在、此前"意外"因为恒真
   而通过——这类断言此前就是摆设（没有真正验证到期望的行为），修正后会如实转为失败，说明测试
   本身在断言一个不成立的前提，应更正测试数据或断言本身，不应视为本次修正引入的回归。

## 3. 需要区分"阻断"与"记录不存在"时怎么办

`TolerantRegistryView`（消费方反馈第 45 条同批引入的包装类型，未随本次修正改名/改签名）承担这一
更细粒度的诊断职责，本次同步修正了其内部判定算法（不再依赖 `TryGet` 返回值反推阻断状态，改为
"找不到时另外探测一次该表是否可正常访问"），对外的 `IsDegraded`/`MissingTables`/
`WasMissing(string)` 语义与诊断准确度未受影响：

```
var tolerant = TolerantRegistryView.Wrap(registry);
var record = tolerant.Get(table, key); // record 为 null 时：
if (tolerant.WasMissing(table))
{
    // 因阻断读不到——这份结果可能不完整，建议在界面上提示
}
else
{
    // 记录本就不存在——正常的"没有这一条"，不代表数据整体有问题
}
```

## 4. 影响面核实结论（框架仓库自查，供编辑器项目参考排查方法）

框架仓库内全仓扫描了所有实际调用 `IDataRegistryView.TryGet(...)` 单记录重载的位置，结论：
- `core/foundation/data_registry/tests/GameDatasetRootOverrideEquivalenceTests.cs`
  （两处）、`core/foundation/scene_router/tests/SceneDescriptorTests.cs`（一处）——均配合
  直接断言记录字段值（`record!.GetString(...)`）或利用阻断态直读通道取出已加载记录，未单独
  依赖 `TryGet` 返回值表达"找到与否"，修正后行为不变；前者的 `Assert.True(found, ...)` 断言
  修正前是"只要不阻断就恒真"的摆设，修正后成为真正有效的断言。
- `games/_template/Tests/Runtime/GameTemplateResidentTests.cs` 两条 PlayMode 用例已在
  1.45.0 发布过程中随二次修复改为直接判断 `Get(...)` 的返回值是否为 `null`，不再依赖
  `TryGet` 的布尔返回值，不受本次修正影响（该文件判断记录"2026-09-19 二次修复"段已记录起因）。
- 未发现任何调用点因本次修正而产生行为回归。

如编辑器项目自查后发现受影响的调用点，或对第 2/3 节的自查方法有疑问，请反馈给框架维护方。
