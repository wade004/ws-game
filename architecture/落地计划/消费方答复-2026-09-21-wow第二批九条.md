## 三、已修条目：消费方要如何升级使用

### 第 1 条——`ISkillHost` 契约缺口（ADR-0050）

`Core.Rules.Common.ISkillHost` 新增四个**带默认实现的接口成员**，签名与既有具体实现类
`Core.Rules.Skill.SkillHost` 上的同名公开方法一致：

- `bool Knows(Id unitId, Id skillId)` —— 默认实现恒返回 `false`。
- `IReadOnlyList<Id> GetKnownSkills(Id unitId)` —— 默认实现恒返回空列表。
- `void LearnSkill(Id unitId, Id skillId)` —— 不带来源/永久标记的两参数重载；默认实现**抛
  `NotSupportedException`**（写路径不允许静默降级，见 AGENTS.md §3）。
- `void LearnFromBook(Id unitId, Id bookId, int level)` —— 默认实现同样抛异常。

`SkillHost` 本身四个既有同名公开方法**物理签名逐字节不变**，新增的是四个显式接口实现转发方法
（不是隐式实现——隐式实现会把既有方法的物理 IL 属性改写成 `virtual sealed`，被 ABI 探针误判为
破坏性变更）。带来源、区分永久/临时的学习/遗忘重载**未**提升到契约，仍只在 `SkillHost` 具体类
上（本次范围只收口反馈点名的四个基础成员）。

顺带把 `SkillHost.GetSkillNameKey`（ADR-0048 新增，见第 3/9 条）同批提升为 `ISkillHost` 默认接口
成员（默认返回 `null`）。

**消费方要怎么改**：如果此前为了调用这四个方法而持有 `Core.Rules.Skill.SkillHost` 具体类型引用，
现在可以改成只持有 `ISkillHost` 接口引用。表现层适配器 `Presentation.Ui.SkillHostSkillBookQuery`
新增了一个接受 `ISkillHost`（原有接受 `SkillHost` 具体类型的构造函数重载保留）的构造函数重载，
今后装配代码可以直接传接口引用。**不需要改任何数据**；只要仍然直接持有 `SkillHost` 具体类型，
行为完全不变。

### 第 2 条——生物原生交互路径（ADR-0051）

新增独立接口 `Core.Carriers.Common.ICreatureInteractionHost`（与既有的场景物件交互接口并列，
不合并），默认实现 `Core.Carriers.Creature.CreatureInteractionHost`：

```
InteractResult Interact(Id unitId, Id creatureInstanceId)
```

复用既有的 `InteractResult`/`InteractOutcome`（生物侧只产出 `Dialog`/`NoAction`/`Unknown` 三个
取值，不产出 gobj 专属的 `Skill`/`Locked`）。

配套新增：

- `Core.Carriers.Creature.CreatureTemplate` 新增可选字段 `GossipMenuRef`（`Id?`），指向
  `dialog.gossip_menu`；缺省（`null`）表示该生物当前没有原生可交互内容。
- 新增回调类型 `CreatureGossipOpenerDelegate(Id unitId, Id creatureInstanceId, Id dialogRef)`，
  经新增的 `CreatureInteractOptions.GossipOpener` 属性注入。
- 新增 `Core.Carriers.Creature.CreatureInteractIntentTickHandler`，与既有
  `Core.Carriers.Gobj.InteractIntentTickHandler` 共用同一个 `"interact"` 意图种类，按
  `Args` 是否携带 `creature_instance_id`/`gobj_instance_id` 分流，互不影响，不新增意图种类。
- `CarriersAssembly`/`GameplayAssembly` 各新增一个构造重载（既有签名原样保留），新增只读属性
  `CarriersAssembly.CreatureInteractions`。

运行时不静默降级：生物未配置 `GossipMenuRef`、已配置但未注入 `GossipOpener`、交互目标未登记为
已知生物实例，三种情形均经新增的 `ICreatureDiagnostics.Warn` 留痕（交互距离不足这一游玩节奏场景
仍维持静默，避免逐帧刷屏）。

**消费方要怎么改**：可以拆除此前自建的"生物包装成场景物件模板"绕行与平行实现，改为在装配根接入
`ICreatureInteractionHost`/`CreatureInteractIntentTickHandler`，给需要被交互的生物模板登记
`GossipMenuRef`，并注入 `CreatureInteractOptions.GossipOpener` 完成对话打开回调。**不需要改动
既有场景物件那条交互链路的任何数据或代码**——两套契约并列、互不影响。

### 第 3 条——技能名称与目标身份字段（ADR-0048，部分修复）

**技能名称——全量到位**：`skill.def` 新增可选字段 `name_key`（`FieldKind.TextKey`，惯例同
ADR-0043 的 `greeting_key`，缺省不渲染、不回退占位文案）。`Core.Rules.Skill.SkillDef` 新增携带
`NameKey` 的构造函数重载；`SkillHost.GetSkillNameKey(Id skillId)` 新增只读查询方法（并提升为
`ISkillHost` 默认接口成员，见第 1 条）。表现层 `Presentation.Ui.ISkillBookQuery` 新增默认接口
成员 `Id? GetNameKey(Id skillId)`；`ActionBarViewModel`/`ActionBarSlotSnapshot` 新增携带
`NameKey`/`ISkillBookQuery` 的构造函数重载（既有构造函数原样保留）。参考界面
`ActionBarPanel.Construct` 新增携带 `IL10nHost` 的构造函数重载，槽位标签在新重载下优先展示
`name_key` 解析出的技能名称，取不到时才回退既有的引用短串展示。

**目标身份——只给了最小可用项**：反馈原文的期望行为是"`HudViewModel` 增加可选 `TargetUnitId`
（至少这一个，游戏侧自行查名字/阵营）；`IUiDataSource` 增加 `target.name`/`target.faction`"。
本次只交付了前半句的最小项：`HudViewModel` 新增只读属性 `TargetId`（`Id?`，经新增的
`target.id` 路径查询解析，转发原始引用，不解析显示文本；当前无目标时为 `null`）。
**`IUiDataSource` 并未新增 `target.name`/`target.faction` 路径**，这两个字段仍不可查询。
框架侧的判断记录（ADR-0048 决策 4）是：视图模型一贯只转发原始引用，把"要不要解析成文本"完全
交给消费端，避免为这一个字段单独新开一套显示名称解析服务。

**消费方要怎么改**：

- 技能名称：数据侧给需要展示名称的 `skill.def` 记录补 `name_key` 字段（可选，不补则维持原有
  引用短串展示）；代码侧若自建了"技能 id → 文本键"的静态映射表，现在可以改为直接读
  `SkillHost.GetSkillNameKey`/`ISkillBookQuery.GetNameKey`，逐步淘汰自建映射表。
- 目标身份：`HudViewModel.TargetId` 只给出目标的原始引用 id，名字/阵营仍需消费端自行按 id 查询
  （框架未提供 `target.name`/`target.faction` 路径）。若已自建了取名字/阵营的适配层，**这部分
  绕行暂时还不能拆除**，只能把"取目标 id"这一步换成读框架原生的 `HudViewModel.TargetId`，其余
  查名字/阵营的逻辑继续保留。

  `InMemoryProgressionBridgeDiagnostics`）。`GameplayAssembly` 新增只读属性

`GameplayAssembly.ProgressionBridgeDiagnostics`/`GameplayAssembly.LootDiagnostics` 只读属性

### 第 7 条——抗性曲线截距项 `k0`（ADR-0049）

`combat.resist_curve` 表 `kind=saturation` 分支的公式由
`reduction = value / (value + k × attackerLevel)` 改为
`reduction = value / (value + k × attackerLevel + k0)`。数据侧新增可选字段 `k0`
（`Number` 种类，无默认值声明，求值层落地默认值 `0`）；`Core.Rules.Combat.ResistCurve` 新增
只读属性 `K0`（`double`，未登记时从 `TryGetNumber("k0", ...)` 取不到就是 `0.0`）。

**消费方要怎么改**：`k0` 缺省 0 时公式与升级前逐位相同（对分母加 0 不改变其值），**不需要任何
数据迁移**——这一结论已用仓库随附三处数据集的既有 `kind=saturation` 记录逐条对比验证过，不是
靠推理认定的。若想表达"存在一个不随等级缩放的基础门槛"（修正低等级段护甲/抗性值稍大就直接顶到
封顶减免的退化区间），可以给数据行加 `k0`（正值收紧曲线、负值放宽，符号不受限）。

### 第 8 条——发布产物不可变强制校验

`build.ps1` 打 `dist/<版本>/` 目录、`dist/ws-game-<版本>.zip`/`.lock` 三处产物之前，新增
`toolchain/_dist_immutability_guard.ps1`（`Assert-DistVersionNotAlreadyReleased`）校验目标
版本号是否已存在对应 `v<版本>` 标签；已发布则直接报错终止，覆盖 `-Release`/`-Dist`/`-Zip`
三条入口的任意组合（此前只有 `-Release` 第 7 步打标签这一道防线，且在产物已被覆盖之后才执行，
`-Dist`/`-Zip` 独立打包路径完全不经过它）。新增 `-AllowOverwriteDist` 开关作为显式例外通道
（默认关闭，仅用于重跑一次失败/半途的发布，启用时打印醒目警告）。

**消费方要怎么改**：这是框架侧构建脚本内部的校验，不涉及任何消费方公开 API 或数据 schema，
**消费方不需要做任何改动**。核对版本产物时可以继续用 `dist/ws-game-<版本>.zip`+`.lock`（本条
落地前就已是接入方自己选用的核验方式），现在额外获得的保证是：该 zip/lock 一旦对应版本已发布，
框架侧不会再静默覆盖同名产物。

### 第 9 条——`quest.def.start_method` 新增 `gobj_interact`（ADR-0048）

`QuestStartMethod` 枚举追加第五个取值 `GobjInteract`（对应数据侧字符串 `gobj_interact`，追加
在 `NpcGossip, ItemUse, AreaTrigger, Auto` 之后，序数与既有四值的线上文本均不改动）。这条取值
描述的是框架早已存在、早已能正常触发接取的链路（场景物件宿主对任务类物件的交互分发 →
`IQuestHost.Accept`），本次改动**不新增任何门禁分支**——接取接口不会因为任务没有声明这个取值
就拒绝通过物件交互触发它，声明了这个取值也不会触发任何新的强制校验。

**消费方要怎么改**：此前如果某些"实际由场景物件交互触发"的任务只能挑一个语义不符的既有取值
（如 `npc_gossip`）顶替标注，现在可以把这些任务定义的 `start_method` 改成 `gobj_interact`，
**这是一次纯粹的数据订正，不影响任务本身能否被触发**（触发链路本身零改动）。不改也完全合法，
只是标注不够准确。

## 四、行为变更与迁移提示

第 1、2、3（技能名称部分）、5、6、7、8、9 条**缺省行为逐位不变、纯加法**，不需要任何数据迁移，
可以直接升级后按需选用新能力。第 3 条目标身份部分只是新增一个只读属性，同样不影响既有行为。

**唯一的例外是第 4 条**：这一条将来交付时，会改变**同一随机数种子下的掉落结果序列**（详见下一
节的原因）。请**不要把当前版本下、某个具体随机数种子对应的具体掉落结果，作为断言写死进测试或
录像回放校验**——第 4 条交付后，同一种子很可能会掉出不同的战利品，这不是回归，是随机数消费方式
本身的调整。

## 五、第 4 条：为什么还没交付

`core/gameplay/loot/core/LootHost.cs` 里，`chance_each` 掉落判定与数量骰 `RollCount` 在
"结果已确定"时的随机数消耗行为不对称（前者即使 `weight_or_chance>=1.0` 仍无条件消耗一次随机数，
后者 `CountMin==CountMax` 时完全不消耗）。这两处随机数都来自同一个 `RngStream`，逐一修正任何一处
都会移动该 `RngStream` 上所有**后续**消费者的取值序列——而这套随机数序列正是三份数值仿真基线
（`core/sim/tests/baseline/*.json`）比对"零差异"的直接输入之一。贸然改动前必须先评估这次改动
会波及仿真基线里哪些统计量、需要重新烘焙到什么程度，这是一次有实际影响面、需要谨慎处理的改动，
不是可以顺手改掉的小修补。

已拍板的方向：按 `(loot_table_id, entry_id)` 派生一条独立的随机数子流，让"这一条掉落表目录下这
一个条目"的判定与骰数各自消费自己的子流，不再共用同一个全局 `RngStream`——这样修正不对称的同时,
也顺带解决了"改一个条目的数量范围会移动其它条目乃至其它表随机结果"这一更大范围的耦合问题。这会
是下一个版本要做的事。

**消费方不要自己在游戏侧搞绕行**（如自行拦截 `RngStream`、在游戏侧模拟"补偿消耗次数"）。框架
交付这条改动后，任何游戏侧的绕行都需要跟着框架的新随机数子流方案重新对齐，拆除绕行的成本会比
现在直接等框架交付更高。当前生产数据如果按接入方原先登记的"绕行方式"（掉落表单行、
`weight_or_chance=1.0`、`count_range:{min:1,max:1}`）配置，本条缺陷不会被触发，可以继续安全
沿用到框架交付为止。

## 六、我核对 CHANGELOG 后与设计层原有判断的出入

设计层原有的映射（第 1 条→ADR-0050、第 2 条→ADR-0051、第 3/9 条合并→ADR-0048、第 7 条→
ADR-0049、第 5/6 条→补诊断出口、第 8 条→不可变校验、第 4 条尚未交付）经逐条核对 1.49.0/1.48.0
CHANGELOG 与代码，**方向全部相符**。唯一需要细化的一点：第 3 条和第 9 条虽然合并在同一份
ADR-0048 里落地，但**修复完整度不同**——第 9 条（`gobj_interact` 枚举值）是完全修复；第 3 条
里"技能名称"字段（`skill.def.name_key`）也完全修复，但"目标身份"字段只交付了反馈原文里明确
写的最小项 `TargetUnitId`（对应现在的 `HudViewModel.TargetId`），`IUiDataSource` 的
`target.name`/`target.faction` 两个路径**没有**一并新增。因此本文档第二节的表格把第 3 条单独
标注为"部分"，与第 9 条的"已修"区分开，而不是把两条都笼统记成"已修"。
