## 第 30 条：`arch.class.primary_stat` 等字段引用元数据缺失

### 现象

`arch.class.primary_stat`（`FieldKind.Id`）的 `Description` 写"引用 stat.\*"但未补登
`SoftReferenceTable`，同表 `base_stats` 的 Map 键已登记引用 `stat.definition`
（`map_key.reference_table`）。P2.3 时期靠手工映射（`CreatureBlockLayouts.ManualJumpTargets`
一类登记）临时提供的"打开"能力，在编辑器改用 `SoftReferenceTable`/`SoftReferenceDomain` 驱动、
删除手工映射后随之消失——`primary_stat` 字段没有候选与"打开"按钮，退化为纯文本输入。

### 处理

1. **`arch.class.primary_stat` 补登软引用**（`core/numbers/archetype/contracts/ArchSchemas.cs`）：
   `.WithSoftReference(table: "stat.definition")`；同步修正字段 `Description` 里"stat_block
   模块尚未登记 schema"的过时表述（该模块早已实现，`base_stats` 已在引用它）——按 `skill_book_ref`
   同一分层边界选择（L1 不同模块间不静态耦合表结构）不升级为 `Reference`。
2. **全仓排查**：用脚本解析全部 `*Schemas.cs`（排除测试目录）里 `Kind` 为 `Id`/`IdList`、
   `Description` 含"引用"/"指向"字样、且未登记 `ReferenceTable`/`ReferenceDomain`/
   `SoftReferenceTable`/`SoftReferenceDomain`/`AllowedValues`/`WithFreeIds` 的字段，命中 43 处
   （逐处人工核实目标表是否已注册、是否单一确定）：
   - **21 处目标可确定，补登 `WithSoftReference`**——含本条原始字段 `arch.class.primary_stat`；
     其余见下方"软引用补齐清单"。
   - **22 处目标不确定，改写描述**（不登记软引用，移除"引用"/"指向"暗示存在单一引用关系的措辞，
     改用"标识"/"标签"/"不透明标识"等中性表述），归为四类：
     - **多态目标**（`display.map.logical_id`：具体指向技能/光环/物品/生物/物件哪张表由
       `category` 决定，无法用单一 `SoftReferenceTable` 表达）；
     - **二选一/多选一目标**（`spawn.table.content_ref` 指向 `creature.template` 或
       `gobj.template`；`dialog.story_tree.speaker_ref` 指向 `creature.template` 或占位角色 id）；
     - **尚未定义的表**（`item.template.enchant_slot`/`stat_roll_ref` 指向 07 第 1.6 节留位的
       未来扩展表；`quest.def` 的 `escort_route_ref` 04 §2.2 域名清单无对应登记表；
       `creature.template.on_hit_reaction_ref`/`on_death_reaction_ref` 消费方反馈第 29 条已核实
       无消费方无目标表，维持预留结论）；
     - **引擎适配层解析的不透明资源标识，不对应任何内容表**（`display.map.model_ref`/
       `default_slot_meshes` 的网格资源、`display.anim_set.clips[*].resource_ref`、
       `vfx.def`/`sfx.def`/`display.weapon_style` 的 `resource_ref`/动作剪辑引用——与第 32 条
       `sprite_set_id`/`icon_id` 同一类字段，但这些字段本身不落在第 32 条 ADR-0025 的收口范围
       内，见该条判断记录）；
     - 另有少量纯标签字段（`gobj.template` 的 `required_skill_tag`/`skill_tag`：标签而非表引用）
       与"本字段是被关联方、不对外声明引用目标"的反向描述误判（`camera_profile` 的
       `shake_presets[].id`）。
3. **`SchemaAudit` 新增告警级检查 `id_description_reference_hint`**
   （`presentation/assembly/SchemaAudit.cs`）：`Id`/`IdList` 字段 `Description` 含"引用"/"指向"
   字样，但 `ReferenceTable`/`ReferenceDomain`/`SoftReferenceTable`/`SoftReferenceDomain`/
   `AllowedValues` 均未登记、也未调用 `WithFreeIds()` 时命中——四类中任一存在即视为"已对取值
   来源做出显式声明"，不再报告（与既有 `idlist_reference_target` 检查"四选一"同一既有风格，
   本检查在此基础上把 `FreeIds` 也纳入豁免范围）。当前全量登记（`SchemaAudit.
   EnumerateRegisteredSchemas()` + 仓库根白名单）0 命中，新增测试

4. **04 文档**：第 5 节新增本检查项说明（第五项元数据门禁）；变更记录补一行。

## 第 32 条：`sprite_set_id`/`icon_id` 无公开的标识 → 路径解析函数

### 现象

04 第 7.1 节、14 把 `sprite_set_id`/`icon_id` 定义为"由引擎适配层解析的不透明字符串"，没有
id→相对路径的公开函数。编辑器只能按 `data/_sample` 具体样例反推（`sprite.item.sample_blade` →
`sprites/item_sample_blade/`、`icon.creature.sample_beast` → `icons/creature/sample_beast.png`）。

### 现行约定原文（核实结果）

逐处读取源码判断记录后确认，两条规则实际存在但分散、且不完全对称：

1. **`sprite_set_id`（形如 `sprite.<category>.<name>`）→ 相对目录 `sprites/<category>_<name>`**：
   去掉第一个点分段（类别前缀）、剩余点号换成下划线。核实到**两处独立的私有实现**，字节级相同：
   - `Adapter.Unity.EngineAdapter.UnityResourceLoader.StripCategoryPrefix`（引擎适配层资源加载
     入口，消费侧，`adapters/unity/Packages/com.gamefoundation.adapter.unity/Runtime/
     EngineAdapter/UnityResourceLoader.cs`，原注释"资源 id → 相对路径映射规则……
     presentation/render/core/SpriteViewBase.ResolveLayerResourceId 已经采用的……规则"）；
   - `Presentation.Render.Core.SpriteViewBase.StripCategoryPrefix`
     （`presentation/render/core/SpriteViewBase.cs`，框架表现层，产出纸娃娃层资源 id 时用来
     编码 `spriteSetName` 片段，原注释"本方法选择让资源 Id 的'名字'部分直接复用 14 §1.2 的文件名
     模板"）。
   - `toolchain/asset_import/sprite_cmd.py` 的 `sprite_out_dir` 计算与之逐字节一致（该脚本原
     注释"输出路径：目录名与运行时资源 id 解析规则对齐……不能只用 sprite_set_name 本身（会与
     运行时按 sprite_set_id 解析出的路径不一致）"），是**第三处独立实现**（Python，无法与 C#
     侧共享源码）。
2. **`icon_id`（形如 `icon.<category>.<name>`）→ 相对文件 `icons/<category>/<name>.png`**：
   类别前缀去掉后**不 flatten**，`category` 段保留为独立子目录——**这条规则此前完全没有 C# 侧
   实现**，只存在于 `toolchain/asset_import/icon_cmd.py`（独立图标导入）与
   `sprite_cmd.py`（随精灵集登记的 `icon.png`）两处 Python 脚本；`toolchain/import_sample_assets.py`
   产出的 `data/_sample/display/display.map.json` 全部 `icon_id` 样例（如
   `icon.creature.sample_beast` → `icons/creature/sample_beast.png`）实测与该规则完全一致——
   编辑器反推出的示例正是这条唯一存在于 Python 侧的规则，只是不知道来源、是否权威。已落地的
   引擎适配层实现从未实现对 `icon_id` 的加载路径解析（该标识目前只作为元数据随
   `display.map` 记录读出，尚无运行期消费方把它解析为具体图片资源并加载）。
3. **`gen_placeholder_assets.py`（bootstrap 占位素材生成器）不在本次收口范围**：该脚本产出的
   `assets/_placeholder/` 下文件是"手绘占位图的原始素材"，本身不带 `sprite_set_id`/`icon_id`
   语义（如 `icons/icon_placeholder_blade.png` 是扁平文件名，与任何 id 规则无关），真正的
   id→路径推导发生在下游 `import_sample_assets.py` 调用 `sprite_cmd.py`/`icon_cmd.py` 时。

### ADR-0025 决策

新增 [ADR-0025](../adr/0025-资源引用标识到资产相对路径的约定纳入公开契约.md)：

1. 两条规则收口为公开契约（`Core.Foundation.EngineAdapter.AssetRefConventions`：
   `SpriteSetDirectory(Id)`/`IconFile(Id)`/`TryParseSpriteSetId(string, out Id)`/
   `TryParseIconId(string, out Id)`），放在 `Core.Foundation`（全仓最底层依赖，任何消费方都能
   引用到）。
2. 规则本身不变（均取现行已在真实内容数据集上验证过的实现），不需要重新生成/迁移任何已产出
   资产。
3. `UnityResourceLoader.StripCategoryPrefix`/`SpriteViewBase.StripCategoryPrefix` 两处私有实现
   改为转发调用 `AssetRefConventions.StripCategoryPrefix`，不再各自持有独立副本；
   `toolchain/asset_import/sprite_cmd.py`/`icon_cmd.py` 改为调用新增的
   `toolchain/asset_import/ref_conventions.py`（Python 独立实现），不再内联计算路径。
4. 往后调整这两条规则须走 ADR。
5. 不扩大收口范围——14 第 1.2 节"通用扁平文件名模板"覆盖的其余资源引用标识（`model_ref`/
   `resource_ref` 等）目前各自只有一处实现，不构成"重复实现导致漂移"问题，本次不纳入。

## 第 33 条：`CreatureFactory.Spawn` 资源类型注册与真实数据脱节

### 现象

`CreatureOptions.DefaultPowerTypes` 默认只有 `[WellKnownPowers.Health]` 一种；
`CreatureFactory.Spawn` 恒按该默认值向 `IPowerHost.RegisterUnit` 注册资源类型，与模板/数据集
实际定义的资源类型无关——示例技能消耗 `arch.power.mana` 时，生成的生物从未注册过 `mana`，
`PowerHost.GetPower` 直接抛异常。

### 处理

1. **`CreatureOptions.DefaultPowerTypes` 语义改写**
   （`core/carriers/creature/core/CreatureOptions.cs`）：类型由 `IReadOnlyList<Id>` 改为
   `IReadOnlyList<Id>?`，默认值由 `[Health]` 改为 `null`（"不显式覆盖"）——物理签名仍是
   `IReadOnlyList<Id>`（引用类型的 `?` 只是可空标注，不产生新的 IL 类型），不构成 ABI 破坏。
2. **`CreatureFactory.Spawn` 新增资源类型解析顺序**
   （`core/carriers/creature/core/CreatureFactory.cs`，`ResolvePowerTypes` 方法）：
   - ① `DefaultPowerTypes` 非 `null` 时直接使用（显式覆盖，优先级最高）；
   - ② 否则尝试"模板/职业实际声明或引用的资源类型"——`creature.template` 当前未登记此类
     字段（07 第 2.1 节字段表无对应项；`arch.class` 才有 `power_types`，但 `creature.template`
     与 `arch.class` 之间目前没有任何关联字段），本步骤恒空，为未来该表补充职业/资源类型引用
     字段预留扩展点；
