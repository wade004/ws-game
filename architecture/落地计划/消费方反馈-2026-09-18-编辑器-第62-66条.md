## 现象与复现

### 第 62 条

`toolchain/asset_import/check_cmd.py` 的 `add_arguments`（改造前 50～59 行）只注册
`--dataset`/`--assets-root`/`--data-root`/`--only`，无输出格式选项；`run()` 内把问题追加进
`list[str]`，逐条 `print(f"{row_id}: {message}")`，末尾再打一行人类可读汇总，均为纯文本，无表名/
字段名/规则码等结构化信息。消费方只能做行级文本切分，`row_id → 所属表` 需在当前会话候选表内逐条
反查记录键是否命中，命中多张表时无法从输出本身区分。

### 第 63 条

`display.equip_visual` 的 `mode` 字段（`slot_mesh`/`socket_attach`）分别要求两组条件必填字段
（`slot_id`/`mesh_ref` 或 `socket_id`/`model_ref`），但源码类型注释与模块 README 均明确写"留给
后续任务"，框架未实现对应 `IValidationRule`——与同表内其它条件字段组
（`DisplayKindFieldGroupRule`/`AnimSetEventsShapeRule`，均已强制注册）待遇不一致。构造一条字段
组合不完整的 `display.equip_visual` 记录，加载期不会产出任何诊断。

### 第 64 条

`check_cmd.py` 内 `_check_world_row` 函数定义两次（改造前第 275～297 行、第 300～322 行），两份
函数体逐字节相同。Python 顶层 `def` 按执行顺序重新绑定同名标识符，第二份覆盖第一份，不产生运行期
异常，但增加阅读/维护该文件时的困惑成本。

### 第 65 条

`AssetRefConventions` 改造前只公开 `SpriteSetDirectory(Id)`/`IconFile(Id)` 两个方法，覆盖
`sprite_set_id`/`icon_id` 两个字段；`vfx.def.resource_ref`、`sfx.def.resource_ref`（含
`variants`）、`display.anim_set.clips.resource_ref`、`display.equip_visual.mesh_ref`/
`model_ref` 均无对应公开路径推导 API，各消费点各自独立实现，未收口成公开契约。消费方（本仓库
`sfx_id` 试听功能）需自建 `Editor.ViewModels.Assets.SfxAssetPathConvention` 手工对齐脚本固定拼接
规则作临时替代，非框架公开契约，框架若日后调整该规则消费方无法从版本变更记录直接感知。

### 第 66 条

`check` 只覆盖 `display.map.sprite_set_id`/`icon_id`、`vfx.def.resource_ref`、
`sfx.def.resource_ref`/`variants`、`world.map` 地图分层图四类；反馈原文列出 7 张表（字段组）无
资源文件存在性检查：`display.anim_set.clips.resource_ref`、`display.equip_visual.mesh_ref`、
`display.weapon_style.auto_attack_anim`/`cast_anim_override`、`display.weapon_style.swing_vfx`/
`impact_vfx_override`、`camera_profile`、`ui_layout_definition`、`shell_menu_definition`。构造
一条指向不存在资源文件的 `display.anim_set.clips.resource_ref` 记录，`check` 不会报告任何问题。

## 根因

- 第 62 条：`check_cmd.py` 自初版起只面向本机命令行人工阅读设计，未预留结构化输出通道。
- 第 63 条：`display.equip_visual` 的 schema 登记时（04 第 7.1.2 节字段表）只写了 `Description`
  级别的"条件必填"说明，未同批补配套 `IValidationRule`——`TableSchema`/`FieldSchema.Required`
  只能表达无条件必填/可选，无法表达"按 `mode` 取值决定另一组字段是否必填"，需要独立扩展点实现，
  当时任务范围只点名了 `DisplayKindFieldGroupRule`，`EquipVisual` 的配套规则被留白。
- 第 64 条：一次历史改动误留了重复定义，此后未被任何审计发现（该函数当时无直接单元测试覆盖，只被
  `check` 子命令的集成场景间接跑到）。
- 第 65 条：`vfx`/`sfx`/model/`anim_set` 四类字段的路径推导规则分散在内容导入工具链产出侧
  （`vfx_cmd.py`/`sfx_cmd.py` 内联计算）、引擎适配层资源加载侧（`UnityResourceLoader`）、
  `check_cmd.py` 校验侧（sfx 一处内联实现）三处独立维护，从未收口为单一公开来源，ADR-0025 当时
  只收口了 `sprite_set_id`/`icon_id` 两个字段，本类推导规则列为待办未处理。
- 第 66 条：`check` 子命令随 vfx/sfx/sprite/world 四域按需增量搭建，从未按"全部资源引用字段"做过
  一次系统性盘点；核实后确认前 4 项缺口的根本原因是架构性的（见"处理"第 66 条），后 3 项是反馈
  原文对"资源存在性检查缺口"范围判断的误差（这 3 张表本身无资源引用字段）。

## 处理

### 第 62 条：`--json` 结构化诊断

- 新增 `CheckIssue` 数据类（`check_cmd.py`）：`severity`/`table`/`record_key`/`check`/`message`/
  `field_path`/`path` 七个字段。全部 `_check_*` 函数改为先产出该对象，文本模式（`render_text`）与
  `--json` 模式（`as_dict`）共享同一份诊断来源，只是渲染方式不同——不重复实现判断逻辑本身。
- 字段语义与 `toolchain/validator --json` 的 `issues[]`（`Program.cs`）对齐：`severity`/`table`/
  `check`/`message` 同名同语义；`record_key` 对应 validator 的同名字段（本工具语境下即"行 id"）。
  `field_path` 是本工具新增字段名，语义同 validator `ValidationIssue.Field` 已支持的下标路径能力
  （消费方反馈第 57 条落地，支持如 `"variants[0]"` 的定位），有意不与 validator 沿用的历史键名
  `field` 同名——本工具是独立新契约，只要求同语义，不强求同名。`path` 是本工具专属新增字段
  （validator 不做资源文件存在性检查，无对应字段）：给出"期望存在但实际缺失"的资源相对路径，格式/
  一致性类诊断无具体缺失路径，留 `None`。
- `--json` 顶层结构：`{tool, dataset, domains, ok, counts:{error, warning}, issues:[...]}`。
  `--json` 时 stdout 只输出这一份 JSON 文档（`ensure_ascii=False`，中文不转义），其余人类可读输出
  （逐问题文本、末尾汇总行）改走 stderr；不加 `--json` 时文本输出与改造前逐字节一致（实测见"验收
  证据"，与 main 分支 diff 为空）。加或不加 `--json`，返回码语义相同（无问题为 0，有问题为 1）。
- 新增 26 个稳定 snake_case 检查名常量（`check_cmd.CHECK_NAMES`），清单：
  `sprite_set_id_missing`、`sprite_set_id_format_invalid`、`sprite_set_dir_missing`、
  `sprite_atlas_json_missing`、`sprite_anchors_json_missing`、`sprite_atlas_png_missing`、
  `sprite_direction_count_mismatch`、`sprite_layer_size_inconsistent`、
  `sprite_frame_file_missing`、`sprite_mirror_pair_source_not_landed`、
  `sprite_mirror_pair_missing`、`sprite_anchor_out_of_canvas`、`sprite_declared_anchor_missing`、
  `icon_id_format_invalid`、`icon_file_missing`、`vfx_resource_ref_missing`、
  `vfx_atlas_missing`、`vfx_frames_json_missing`、`sfx_resource_ref_missing`、
  `sfx_resource_file_missing`、`sfx_variants_missing_resource_ref`、`sfx_variant_file_missing`、
  `world_map_dir_missing`、`world_map_layer_missing`、`world_map_scene_ref_mismatch`、
  `world_map_nav_ref_mismatch`——供消费方按 `check` 字段过滤/分类，不要复制字面量，供后续新增检查
  项时对照防止漏登记。命名风格参照 `toolchain/validator` 既有检查名（如
  `world_map_point_outside_image`）。
- `toolchain/README.md` 同步补充 `--json` 契约说明与 26 个检查名清单。

### 第 63 条：`EquipVisualModeFieldGroupRule`

- 新增 `Core.Foundation.DisplayInfo.EquipVisualModeFieldGroupRule`（检查名
  `equip_visual_mode_field_group`），登记进 `PresentationSchemaCatalog.RegisterAll`，与建议方案
  点名的类名/注册位置一致。

  | `mode` 取值 | 必填字段 |
  |---|---|
  | `slot_mesh` | `slot_id`、`mesh_ref` |
  | `socket_attach` | `socket_id`、`model_ref` |

- `mode` 字段缺失/取值不在合法枚举内属 `required_field`/字段类型/枚举合法检查项职责（由
  `DataRegistry` 内建校验负责），本规则只处理 `mode` 合法时的字段组完整性，避免与内建校验重复
  报错（同 `DisplayKindFieldGroupRule` 惯例）。
- **明确只查必填、不查另一 mode 字段留空**：04 第 7.1.2 节字段表与本模块 `schema/README.md` 对
  `slot_id`/`mesh_ref`/`socket_id`/`model_ref` 四个字段的文档描述只写了"`mode: slot_mesh` 时
  必填"/"`mode: socket_attach` 时必填"，均未写"另一模式下必须留空"——与 `DisplayKindFieldGroupRule`
  不同（该规则的 `display.map` sprite/model 两组专属字段在 04 第 7.1 节原文与第 5 节检查项说明均
  明确"另一组字段必须留空"）。反馈原文本身也只要求补"条件必填"，未要求补"互斥留空"。本规则因此
  只检查每条记录按自己的 `mode` 是否填齐对应必填字段组，不检查是否同时携带了另一模式的字段——
  避免在文档未明确写"必填"的组合上自行发明更严格的语义（有歧义处取最保守解释）。是否收紧为互斥
  留空，需要先在 04/schema README 补明确措辞，见"待设计层确认"。
- **升级影响**：`EquipVisualModeFieldGroupRule` 是无条件注册的 Error 级新规则（不可提升），既有
  `display.equip_visual` 数据若 `mode=slot_mesh` 但缺 `slot_id`/`mesh_ref`，或
  `mode=socket_attach` 但缺 `socket_id`/`model_ref`，升级后首次加载/`validate_data.py --strict`/
  `toolchain/validator` 会新增该检查名的阻断错误；处理方式是给对应记录补齐所缺字段，无豁免开关。
  已在 `CHANGELOG.md` `[Unreleased]`"第 63 条"条目补充同一说明。

### 第 64 条：删除重复定义

- 删除 `check_cmd.py` 内 `_check_world_row` 的第二份重复定义（原第 300～322 行），保留第一份
  （原第 275～297 行），与建议方案的行号一致。全仓库无其它文件引用该私有函数，删除不影响任何调用
  点与运行结果。

### 第 65 条：四类字段路径推导方法（新命名：`LogicalPath` 与 `Dir`/`File` 区分路径空间）

| 方法（C#）/ 函数（Python） | 输入 | 输出 | 路径空间 |
|---|---|---|---|
| `VfxResourceDir` / `vfx_resource_dir` | `vfx.def.resource_ref` | `"vfx/<去类别前缀>"`（目录） | 资产根目录相对路径 |
| `SfxResourceFile` / `sfx_resource_file` | `sfx.def.resource_ref`/`variants` | `"sfx/<去类别前缀>.wav"`（文件） | 资产根目录相对路径 |
| `AnimClipLogicalPath` / `anim_clip_logical_path` | model 型 `display.anim_set.clips.resource_ref` | `"GameFoundation/anim_clips/<去类别前缀>"` | 引擎侧已导入逻辑资源路径 |
| `ModelLogicalPath` / `model_logical_path` | `display.map.model_ref`、model 型 `display.equip_visual.mesh_ref`/`model_ref` | `"GameFoundation/models/<去类别前缀>"` | 引擎侧已导入逻辑资源路径 |

- **两种路径空间的区别**：`VfxResourceDir`/`SfxResourceFile` 返回的是相对资产导入工具
  `--assets-root`（默认仓库 `assets/`）的相对路径，与既有的 `SpriteSetDirectory`/`IconFile` 同一
  路径空间，可直接与 `assets/<dataset>/` 拼接后做文件系统存在性检查（`check_cmd.py` 已在用）。
  `AnimClipLogicalPath`/`ModelLogicalPath` 返回的是引擎侧 `Resources.Load` 可消费的"逻辑资源
  路径"（不含扩展名、不以任何"资产根目录"为基准），实际对应引擎适配层内部一个独立、非按数据集
  分区的资源目录树（`adapters/unity/Assets/Resources/GameFoundation/<子目录>/<name>`），由引擎
  适配层内部一个编辑器脚本直接生成，不经过内容导入工具链任何子命令、不落在资产导入工具的资产
  根目录下——这两个方法的返回值**不能**拼进 `assets/<dataset>/` 做文件存在性检查。
- **改名（设计层裁决）**：反馈原文建议的方法名是 `AnimClipResourceFile`/`ModelFile`，与
  `VfxResourceDir`/`SfxResourceFile` 的 `Dir`/`File` 后缀放在一起容易让调用方误以为四者是同一
  路径空间（"File"/"Dir" 均暗示磁盘路径）。整合时按设计层裁决改为 `AnimClipLogicalPath`/
  `ModelLogicalPath`，内容导入工具链侧对应 `anim_clip_resource_path`/`model_resource_path` 同步
  改名为 `anim_clip_logical_path`/`model_logical_path`，从方法名本身就能区分两种不能互换使用的
  路径语义。详见 [ADR-0037](../adr/0037-资源引用路径推导契约扩展到vfx-sfx-model-anim_set.md)
  决策 1（已在该 ADR 补充命名区分说明）。全仓库已 grep 确认旧名（`AnimClipResourceFile`/
  `ModelFile`/`anim_clip_resource_path`/`model_resource_path`）零残留。
- **sprite/model 并存规则边界（未收口，未擅自裁决）**：`display.anim_set.clips.resource_ref` 与
  `display.equip_visual.mesh_ref` 两个字段在运行期存在"按消费实体是 sprite 型还是 model 型"的两条
  并存加载规则，且两条规则不是同一路径空间——`AnimClipLogicalPath`/`ModelLogicalPath` 只收口 04/09
  文档与 `EquipVisualDef`/`AnimSetDef` 类型注释描述的 model 型规则，sprite 型的两条并存规则（引擎
  适配层表现层实现里的"默认接线约定"）是既有的"已知简化"，不在本次收口范围，是否提升为同等地位的
  公开契约、如何在数据层面区分"某行该按哪条规则消费"，见"待设计层确认"。`model_ref` 本身没有
  sprite 型并存规则（sprite 型表现层不处理装备槽挂载显示模式），`ModelLogicalPath` 对
  `model_ref` 无此边界。
- **消费方自建替代可改为调用公开方法**：`ws-game-editor` 仓库的
  `Editor.ViewModels.Assets.SfxAssetPathConvention` 可直接改为调用 `SfxResourceFile`/
  `sfx_resource_file`（视消费方运行环境是 C# 还是 Python 侧而定），不必再自行维护固定拼接规则。
- **引擎适配层实现暂未转发**：`UnityResourceLoader.ResolveModelResourcesPath`/
  `ResolveAnimClipResourcesPath` 尚未改为转发本次新增的 C# 方法——与 `SpriteSetDirectory` 落地时
  （ADR-0025）不同，本次未在本机跑通引擎侧批处理编译/测试验证转发改动，保持引擎适配层代码不动，
  列为后续项（两处实现目前逐字节一致，不转发不产生行为分歧，只是多一份未来需要同步维护的拷贝）。
  见"待设计层确认"。

### 第 66 条：如实说明检查域缺口范围，本轮新增检查域 = 0 个

逐项核实结论：

1. `display.anim_set.clips.resource_ref`——确认存在、确认 `check` 未覆盖。被第 65 条 sprite/model
   并存规则阻塞：`check` 单看数据表本身无法判定某一行该按哪条规则核对，勉强实现会产生假阳性/
   假阴性；即便判定为 model 型，`AnimClipLogicalPath` 返回的引擎侧逻辑资源路径也不在
   `check_cmd.py` 的 `--assets-root` 检查域内（不是磁盘文件，无法直接做文件存在性检查）。
2. `display.equip_visual.mesh_ref`——同上，被并存规则阻塞。`model_ref`（反馈原文未列出的同类
   字段，一并核实）无并存规则，但 `ModelLogicalPath` 解析出的引擎侧逻辑资源路径同样不在检查域内。
3. `display.weapon_style.auto_attack_anim`/`cast_anim_override`——资源文件引用，但同被并存规则
   阻塞，理由同第 1 项。
4. `display.weapon_style.swing_vfx`/`impact_vfx_override`——**表引用，不是文件引用**：`schema`
   登记为 `WithSoftReference(table: "vfx.def")`（`presentation/vfx_sfx/schema/VfxSfxSchemas.cs`
   第 71～77 行），指向 `vfx.def` 表的某一行 id，不是磁盘上的某个资源文件。引用完整性属
   `toolchain/validator` 的软引用校验域，不属于 `check_cmd.py`（本工具做的是"资源引用 id → 磁盘
   文件是否存在"，不是"表间引用完整性"）。事实核查结论见下一节。
5. `camera_profile`——`CameraSchemas.cs` 全字段核对（俯角/缩放/跟随/震屏等数值型参数），**不含
   任何 `_ref`/资源路径类字段**。该表本身不含资源引用，`check` 覆盖不到它是因为它没有可查的
   资源字段，不构成"资源存在性检查缺口"。
6. `ui_layout_definition`——`UiLayoutSchema.cs`：`id`/`panel`/`slots`/`fields`（`fields` 为
   `FieldKind.Object`，description 明写"结构留给引擎适配层解释"，schema 层不透明）。**同样无声明
   的资源引用字段**，情况同 `camera_profile`。
7. `shell_menu_definition`——`ShellMenuSchema.cs`：字段为 `id`/`entries[].{id, text_key, action,
   target_panel}`，`target_panel` 是 `FieldKind.Reference` 指向 `ui_layout_definition`（表内
   引用，非资源文件引用）。**同样无资源引用字段**。

结论：7 项候选里，前 4 项是真实的"有 resource_ref/软引用字段但检查覆盖不到"缺口，但均被架构性
问题阻塞（sprite/model 并存规则未收口、model 型路径不在检查域内、`swing_vfx`/
`impact_vfx_override` 是表引用而非文件引用）；后 3 项经独立复核 schema 源码确认表本身不含资源
引用字段，`check` 覆盖不到它们是必然结果，反馈原文把这 3 张表也归入"资源存在性检查缺口"的定性
不够精确。本轮不做"通用批量核对入口"（反馈建议的备选方案）——有了第 65 条新增的公开路径推导
方法后，消费方已可自行对 `vfx`/`sfx` 两类字段调用 `VfxResourceDir`/`SfxResourceFile` 核对文件
存在性（这两类恰好是唯一落在资产根目录检查域内、且无并存规则阻塞的字段），无需框架额外提供批量
入口；`model`/`anim_set` 相关字段因不落在资产根目录检查域内，批量入口同样无法覆盖，不构成"做了
入口就能补齐"的情形。

## 事实核查（步骤 3，只核实不改动，供设计层裁决参考）

**问题**：`display.weapon_style.swing_vfx`/`impact_vfx_override` 对 `vfx.def` 的引用，校验器
目前为什么是"软引用、不做存在性校验"？仓库里现有的"依赖驱动可选规则"机制能否/是否已经覆盖这类
跨模块引用存在性？

**核实结论**：

1. **为什么当前不做存在性校验**：`swing_vfx` 登记为 `FieldKind.Id` +
   `.WithSoftReference(table: "vfx.def")`（`presentation/vfx_sfx/schema/VfxSfxSchemas.cs:71-72`），
   `impact_vfx_override` 的 Map 值同样登记 `WithSoftReference(table: "vfx.def")`（同文件
   `73-77` 行）。`FieldSchema.WithSoftReference` 的判断记录
   （`core/foundation/data_registry/contracts/FieldSchema.cs:203-210`）明确：软引用"只传达跨层
   引用语义（供内容工具做自动补全/跳转），刻意不像 `FieldKind.Reference`/`ReferenceTable`/
   `ReferenceDomain` 那样参与 `DataRegistry` 加载期的 `reference_integrity` 校验"。
   `toolchain/validator/Program.cs:956-962` 的注释同样确认：`soft_reference_table`/
   `soft_reference_domain` 随字段元信息导出供编辑器用，"不参与 DataRegistry 加载期的引用完整性
   校验……纯粹是传达给内容工具的提示"。这是**设计上的刻意选择**，不是遗漏——具体到
   `swing_vfx`/`impact_vfx_override`，登记为软引用而非硬引用（`FieldKind.Reference`）的理由已
   写在 `VfxSfxSchemas.cs:49-58` 的判断记录里："本模块不静态耦合 skill.def/vfx.def 的表结构"，
   与消费方反馈第 30 条（2026-09-11，见
   [消费方反馈-2026-09-11-编辑器-第30-32-33-34条.md](消费方反馈-2026-09-11-编辑器-第30-32-33-34条.md)
   第 44～47 行）为同批 21 处字段补软引用时定下的统一口径一致："按 skill_book_ref 同一分层边界
   选择（L1/L3 不同模块间不静态耦合表结构）不升级为 Reference"。
2. **"依赖驱动可选规则"机制能否覆盖这类跨模块引用存在性**：**技术上可以，但目前没有覆盖，是
   一个需要新写规则才能补上的缺口，不是现有机制的自动副产品**。`IValidationRule.Validate` 接收
   `IDataRegistryView view`（`core/foundation/data_registry/contracts/IValidationRule.cs:24`），
   可经 `view.GetAll(table)` 只读访问同一次加载里任意表的全部记录，不限于规则自己所属的表——
   `DisplayMapCoverageRule`（`core/foundation/display_info/core/DisplayMapCoverageRule.cs:24-65`）
   正是这一机制的现成示例：它经构造函数注入 `IReadOnlyList<(string table, string idField)>
   sources`（"提供依赖即启用"的"依赖驱动可选规则"模式，见
   `presentation/assembly/README.md:76-94` 判断记录），遍历若干张表的某个 id 字段，检查其值是否
   被另一张表（`display.map`）覆盖——与"检查 `swing_vfx`/`impact_vfx_override` 的值是否存在于
   `vfx.def` 表"是同构问题（"字段 A 值 → 是否存在于表 B"）。要覆盖 `swing_vfx`/
   `impact_vfx_override`，需要新写一条类似的 `IValidationRule`（如经构造函数注入"要核对的软引用
   字段 → 目标表"清单），按 `ContentValidationAssembly.cs:398-411` 同一套"提供依赖对象即启用、
   未提供则跳过/用默认接线"的注册模式接入——机制本身现成，具体规则未写。是否要新写这样一条规则
   （或是否应该把 `swing_vfx`/`impact_vfx_override` 直接升级为 `FieldKind.Reference`，从而复用
   既有的 `reference_integrity` 通用检查，不必新写专属规则），是设计取舍问题，本次只如实核查
   现状与技术可行性，不代为裁决，见"待设计层确认"。

## 待设计层确认

1. **sprite/model 并存加载规则是否提升为正式契约**（第 65/66 条前置问题）：
   `display.anim_set.clips.resource_ref`/`display.equip_visual.mesh_ref`/
   `display.weapon_style.auto_attack_anim`/`cast_anim_override` 四个字段在运行期按消费实体是
   sprite 型还是 model 型存在两条并存的加载规则（sprite 型经引擎适配层表现层"默认接线约定"当
   `VfxResourceDir` 同一路径空间加载；model 型经本次新增方法当引擎侧逻辑资源路径加载）。是否要
   把 sprite 型规则也提升为与 model 型同等地位的公开契约、以及如何在数据层面区分"某一行该按哪条
   规则消费"（当前无任何字段显式标注），是解锁第 66 条其余字段存在性检查的前置——不解决这个问题，
   `check`/`validator` 都无法安全地对这些字段做存在性检查（会产生假阳性/假阴性）。
2. **`swing_vfx`/`impact_vfx_override` 引用完整性核查结论**（步骤 3）：当前"不做存在性校验"是
   设计上的刻意选择（软引用機制的既定语义），技术上可以经"依赖驱动可选规则"机制（参照
   `DisplayMapCoverageRule` 的实现模式）新写一条专属规则覆盖，或直接把这两个字段升级为
   `FieldKind.Reference` 复用既有 `reference_integrity` 通用检查——两条路径均可行，是否要做、
   做哪一种，需要设计层裁决是否值得为此打破"L1/L3 不同模块间不静态耦合表结构"这一既定原则（该
   原则是消费方反馈第 30 条时定下的统一口径，覆盖不止这两个字段）。
3. **`equip_visual_mode_field_group` 是否要收紧为互斥留空**：当前只检查按 `mode` 对应的字段组是
   否必填，不检查是否同时携带另一模式的字段（04/schema README 均未写"必须留空"）。是否需要补
   这一层更严格的语义，需要先在 04 或 schema README 补明确措辞，再扩展本规则或另开检查项。
4. **引擎适配层转发新方法的后续项**：`UnityResourceLoader.ResolveModelResourcesPath`/
   `ResolveAnimClipResourcesPath` 尚未改为转发 `AnimClipLogicalPath`/`ModelLogicalPath`（本机
   无法跑通引擎侧批处理编译/测试验证），两处实现目前逐字节一致、不产生行为分歧，但存在"未来需要
   同步维护两份拷贝"的风险，列为后续任务。
