## 结论

消费方复核结论成立，但不是算法缺陷：`stack_category` 一直只是**加载期静态内容校验分组**，运行时叠加与溢出一直按 `(target, aura_def, sourceKey)` 槽位处理，"同类别不同定义可并存"是既有实现的既定行为，未发生任何变化。问题出在文档措辞——06 第 3.3/3.8 节此前的表述容易被读成"`stack_category` 是跨定义共享的运行时叠加槽位"，与实现范围不一致。本次按 [ADR-0023](../adr/0023-光环叠加类别为静态校验分组.md) 把契约在文档、代码注释/诊断文案、模块 README 三处统一收口为一致措辞，**不改动任何运行时算法、不删改任何公开签名**。

历史脉络：这条文档措辞落差此前已被一轮独立的外部审计（`architecture/落地计划/audit-b3b91ee-20260907/doc-code-matrix.md` 第 49 行）发现并记录过一次，建议"补 ADR/代码或收窄文档"，当时未继续跟进拍板；本次消费方复核是第二次独立发现同一条落差，借此机会一并拍板收口。

## 处理方式

1. **ADR-0023**：把"`stack_category` 是静态校验分组、运行时按 `(target, aura_def, sourceKey)` 分槽、不同定义即使类别相同也并存、跨定义互斥槽位是未提供能力"记录为架构级决策，详见该 ADR"决策"一节四条。
2. **06 文档**（`architecture/06_规则层_属性技能战斗AI.md`）：
   - 第 3.3 节 `stack_category` 字段说明由"用于叠加冲突检测，见 04 校验器"改写为"跨定义的静态叠加校验分组，仅供加载期内容校验使用"，并补一段结论说明段落，明确运行时槽位键不含 `stack_category`。
   - 第 3.8 节"叠加与刷新规则"表首行由"同 `stack_category` 的光环叠加数超过 `max_stacks`"改写为"同一 `aura_def` 与来源槽位……叠加数超过 `max_stacks`"，并补一句说明 `stack_category` 不参与槽位键。
   - 第 3.8 节表格之后新增一段说明：`sourceKey` 在默认共享计时模式（`AllowMultiSourceTiming=false`）下恒为 `null`，不按来源区分；仅开启独立来源计时时才按 `(aura_def, sourceId)` 分别维护实例——呼应消费方反馈原文"避免误读为总是逐来源计时"的具体要求。
   - 变更记录追加一行，ADR 列写 [ADR-0023](../adr/0023-光环叠加类别为静态校验分组.md)；文档版本号不变（12 第 5 节口径：本次不改变既有结论/运行时行为，是对既有结论的措辞明确化）。
3. **04 文档**（`architecture/04_数据与内容管线.md`）：第 5 节"叠加类别冲突"行措辞对齐——改写为"同一 `stack_category` 静态分组下不得同时登记可叠加/不可叠加两种叠加形态的定义；本项是加载期静态内容校验，不改变运行时按 `(target, aura_def, sourceKey)` 分槽的叠加行为"，标注勘误 + ADR-0023 引用，变更记录追加一行。
4. **落地方案能力索引**（`architecture/落地计划/落地方案与分阶段计划.md`）："能力边界与未默认接入能力索引"表"未提供"分类新增一行"跨定义光环互斥槽位（ADR-0023）"，说明若未来需要需另立 ADR 明确替换目标/层数与效果归属/策略作用范围/缺省类别语义。
5. **代码侧措辞对齐**（均只改注释/诊断文案，未改任何运行时逻辑或公开签名）：
   - `core/rules/skill/core/AuraHost.cs`：`_slots` 字段补充 XML 注释，说明键构成、`stack_category` 不参与、`StackOverflowPolicy` 只作用于同一槽位、`sourceKey` 取值规则。
   - `core/rules/skill/contracts/SkillOptions.cs`：`StackOverflowPolicy` 枚举的 XML 注释改写为明确指向 `AuraHost` 运行时槽位定义，补充 `stack_category` 不参与槽位键的说明。
   - `core/rules/skill/schema/SkillValidationRules.cs`：`StackCategoryConflictRule` 类注释补一段"范围说明"，明确本规则只做加载期静态校验；校验失败的问题消息文案改写，明确"本项不影响运行时叠加行为"。
   - `core/rules/skill/schema/README.md`：`stack_category` 字段说明行、`StackCategoryConflictRule` 校验规则行同步改写。
   - `core/rules/skill/README.md`：新增判断记录条目 41，完整记录本次消费方反馈的现象、结论与处理方式，供后续排查引用。

## 对消费方的提示

1. **不是缺陷，是文档措辞收口**：本次改动确认你方 Runtime 验收报告观察到的"同类别不同定义可并存"就是框架从 1.0.0 起的既定行为，不是等待修复的 bug；升级到包含本次改动的版本后，行为与你方已验收的 1.15.0 完全一致，无需重跑修复前后对照。
2. **公开签名与运行时行为均未变化**：`AuraHost`/`SkillOptions`/`StackCategoryConflictRule` 的公开签名与判定逻辑均未改动，本次只改了 XML 文档注释、诊断/校验问题文案与架构文档措辞；不需要做任何升级前的兼容性核对。
3. **`sourceKey` 语义已写入文档**：06 第 3.8 节新增说明——默认（`AllowMultiSourceTiming=false`）下 `sourceKey` 恒为 `null`，同一目标身上同一 `aura_def` 无论来源是谁都命中同一槽位；只有显式开启 `AllowMultiSourceTiming` 才按来源分别计时。若你方内容或文档中曾按"总是逐来源计时"理解过这一行为，请按新措辞复核。
4. **跨定义互斥槽位仍是未提供能力**：若未来确有具体设计需要"同类别不同光环定义共享一个叠加槽位、按优先级互相替换"（类似魔兽光环组），请作为新的产品需求提出，框架侧需要另立 ADR 明确替换目标、层数与效果归属、策略作用范围与缺省类别语义后才能实现，当前不在既有契约范围内。
