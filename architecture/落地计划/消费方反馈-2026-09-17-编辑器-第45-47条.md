## 处理

### 45　只读分析入口在 registry 阻断态下不再抛异常

**状态**：已修复（1.38.0）。

**现象确认**：`Core.Carriers.Item.ItemBudgetCurve.BuildStatBudgetInfo`、
`Core.Carriers.Item.EquipmentScoreAnalyzer.Score`、`Core.Rules.Skill.SkillBudgetAnalyzer.Analyze`/
`ComputeGrantValue`、`Core.Sim.ExpectedStatCalculator` 构造函数等"只读分析、供内容工具展示用"的
入口，此前内部一律用严格的 `IDataRegistryView.Get`/`GetAll`（不是 `TryGet`/`TryGetAll`）读取支持
表；`Core.Foundation.DataRegistry.DataRegistry.EnsureReadable` 的阻断标记是整个 registry 级别
（不按表/记录粒度），哪怕触发阻断的记录与被分析对象完全无关，这些入口仍会抛
`InvalidOperationException`，炸穿"编辑器用户刚把数值改到触发 Error 校验的那一刻，仍需要看到预算
消耗展示"这一类场景。

**根因**：这批入口产出的是给人看的分析/展示信息，不是驱动运行期业务逻辑的权威数据（同
`IDataRegistryView.TryGetAll`/`RecordCount`——消费方反馈第 17/20 条已根治的"阻断态诊断/内容工具
只读通道"同一类场景），语义上不属于 `architecture/11_工程规范与测试.md` 第 4 节"运行时不做静默
降级"要防的对象，但此前始终没有对应的容错读取路径。

**处理方式**：

1. `IDataRegistryView` 新增带默认实现的 `bool TryGet(string table, string key, out DataRecord?
   record)`（及 `CommonId` 重载），语义与既有 `TryGetAll` 完全对称——阻断态返回 `false`，非阻断态
   与 `Get` 结果一致（含"记录本就不存在"仍返回 `true`、`record` 为 `null`）。`DataRegistry` 显式
   覆盖为直接读内部快照，不经过 `EnsureReadable`。
2. 新增 `Core.Foundation.DataRegistry.TolerantRegistryView`（`sealed class`，实现
   `IDataRegistryView`）：把任意 `IDataRegistryView` 包装成"读不到就退化为空/null，不向外抛阻断
   异常"的只读视图，静态工厂 `TolerantRegistryView.Wrap(view)`（对已经是该类型的入参直接复用，
   不重复包装）；新增 `IsDegraded`（本次包装期间是否曾因阻断读不到过任何一张表）、`MissingTables`
   （具体缺失表名列表）、`WasMissing(table)`（按名查询）。只应由分析入口在方法体内部构造使用，不
   改变调用方传入的原始 `IDataRegistryView` 本身的阻断行为。
3. `ItemBudgetCurve.BuildStatBudgetInfo` 新增两个带 `out TolerantReadDiagnostics diagnostics`
   出参的重载（纯新增，不改既有签名）；`EquipmentScoreAnalyzer.Score`、`SkillBudgetAnalyzer
   .Analyze`/`ComputeGrantValue`、`ExpectedStatCalculator` 构造函数/`Compute` 内部全程改用
   `TolerantRegistryView.Wrap(view)` 包装后的引用。`EquipmentScoreResult`/`SkillBudgetResult` 各
   新增一个带 `isDegraded`/`missingTables` 两参的构造函数重载（纯新增，ABI 只允许新增）与对应
   `IsDegraded`/`MissingTables` 只读属性；`ExpectedStatCalculator` 新增同名属性、实时读内部
   `TolerantRegistryView` 状态（不是构造期快照）。旧构造函数/不带诊断出参的既有重载行为在非阻断态
   下逐位不变，阻断态下从"抛异常"变为"不抛异常、按 `TolerantRegistryView` 语义降级"。
4. 被分析对象自身"因阻断读不到"（如 `EquipmentScoreAnalyzer.Score` 的 `templateId`、
   `SkillBudgetAnalyzer.Analyze` 的 `skillId`）与"确实不存在"两种情形分开处理：前者不再抛
   `ArgumentException`，改为返回一条 `IsDegraded = true` 的降级结果（`EquipmentScoreResult.Score`
   置 0、`SkillBudgetResult.Verdict` 置 `NotApplicable`）；后者维持既有行为（调用方传了个不存在的
   id，是用法错误，继续抛异常）。
5. **运行期入口不变**：`Core.Rules.Item.IBudgetSolver.Solve`（服务 `EquipmentHost
   .ApplyAffixValues` 等运行期宿主）与 `Core.Rules.Skill.SkillDefCache`（同时服务 `SkillHost`）本身
   均未改动，仍按 `EnsureReadable` 语义、阻断即禁止读取（`architecture/11_工程规范与测试.md` 第 4
   节"运行时不做静默降级"不变）；`ExpectedStatCalculator`/`SkillBudgetAnalyzer` 只是给它们的构造
   参数喂一个自己私有持有的容错视图，不影响运行期宿主用真实 `view` 的另一条调用路径。

`feedback/integrate-45-47`）。新增契约：`IDataRegistryView.TryGet`（2 重载）、
`TolerantRegistryView`（含 `Wrap`/`IsDegraded`/`MissingTables`/`WasMissing`/`Diagnostics`）、
`TolerantReadDiagnostics`、`EquipmentScoreResult.IsDegraded`/`MissingTables`、

### 46　`FieldSchema` 补充字段废弃元数据

**状态**：已修复（1.38.0）；嵌套字段的 CLI 导出缺口（下方"消费方需注意"第 4 点）已在整合同批收口。

**现象确认**：`FieldSchema` 此前没有任何"该字段已废弃"的结构化标记成员——`stat.definition
.group`/`min`/`max`/`is_rating`/`rating_conversion_ref`、`prog.xp_source.base_xp`/`weight`、
`quest.def`/`encounter.def`/`achv.def` 的 `rewards.xp`、`skill.def`/`skill.aura_def` 效果参数
`scaling_stat`/`coefficient` 等字段的废弃事实只写在自由文本 `Description` 与升级指南附录 C 里，
`IDataRegistryView.GetSchema(table).GetField(name)` 返回的 `FieldSchema` 无法程序化区分"这个字段
废弃了"与"这个字段只是 Description 里恰好提到了别的字段名"；`toolchain/validator --list-tables
--json` 导出的字段元数据同样不含废弃标记。

**根因**：内容工具（编辑器侧 `Editor.Core.Validation.DeprecatedFieldHints`）只能手工维护一份与
框架 `Description`/升级指南人工核对的静态清单，框架升级后清单漂移无编译期/加载期一致性保证。

**处理方式**：

1. `FieldSchema` 新增 `WithDeprecated(string sinceVersion, string? replacedBy, string? note =
   null)` 修饰方法（同 `WithCurve`/`WithSoftReference` 惯例，不破坏既有构造签名，只能设置一次），
   登记 `IsDeprecated`/`DeprecatedSince`/`ReplacedBy`/`DeprecationNote` 四个新只读属性。
   `sinceVersion` 须形如 `"X.Y.Z"`（构造期正则校验）；`replacedBy` 非空时须是"同一级字段清单里
   已登记的字段名"——该存在性校验推迟到"兄弟字段清单第一次被完整组装"处（`FieldSchema` 构造函数
   `fields` 参数分支、`TableSchema` 构造函数），经 `FieldSchema.ValidateDeprecatedReplacedBy` 统一
   实现。
2. `stat.definition.group`/`min`/`max`/`is_rating`/`rating_conversion_ref`（→
   `category`/`clamp`/`clamp`/`category`/`conversion_ref`，1.31.0）、`item.affix.effects`（→
   `null`，多字段共同取代，1.32.0，见 `DeprecationNote`）、`prog.xp_source.base_xp`/`weight`（→
   `base_curve_ref`，1.34.0）、`quest.def`/`encounter.def`/`achv.def` 共用的 `rewards.xp`（→
   `xp_equivalent`，1.34.0）、`skill.def`/`skill.aura_def` 的 `coefficient`/`scaling_stat`（→
   `scaling`，1.33.0）均补登 `WithDeprecated`。
3. `presentation/assembly/SchemaAudit.cs` 新增检查名 `field_deprecated_metadata`：
   `IsDeprecated=true` 但 `DeprecatedSince` 为空（理论上不可能触发，`WithDeprecated` 构造期已挡，
   仍留一道软失败防线）、`ReplacedBy` 在同表找不到对应字段两种情形。
4. `toolchain/validator --list-tables --json` 每个字段的 `field_meta` 追加 `deprecated` 键：未
   登记时为 `null`；登记时为 `{"since": "...", "replaced_by": "..."|null, "note": "..."|null}`。
   不改动任何既有字段，`--json` 输出对不消费本键的调用方逐字节兼容。`field_meta` 只覆盖顶层
   字段——独立验收发现 `quest.def.rewards.xp`、`skill.def`/`skill.aura_def` 效果参数
   `scaling_stat`/`coefficient` 这类嵌套在子结构内的废弃字段，`FieldSchema.IsDeprecated` 虽已
   正确登记，`field_meta` 这条导出路径读不到（验收报告"必须修项"）。整合同批收口：新增表级
   `deprecated_paths`（`[{path, since, replaced_by, note}]`，见
   `presentation/assembly/SchemaFieldDeprecationExport.cs`），递归全量导出本表全部（含顶层与
   任意深度嵌套）废弃字段，点路径记法与 `field_ranges`/`SchemaAudit` 的 `FieldPath` 记法一致。

### 47　`SkillBudgetValidationRule.Validate` 未捕获 `DataFieldException`，结构非法记录不再中断整批校验

**状态**：已修复（1.38.0）。

**现象确认**：`core/rules/skill/schema/SkillValidationRules.cs`
`SkillBudgetValidationRule.Validate` 此前只 `catch (ArgumentException)`；`SkillDefCache
.ParseSkillDef → DataRecord.GetId("school")` 对结构合法字符串但非法 Id 语法的字段（如空字符串）
抛出的是 `Core.Foundation.DataRegistry.DataFieldException`（不是 `ArgumentException` 子类），未被
拦下、一路冒出中断整个 `DataRegistry.RunValidationAndBuildReport → LoadAll` 流程——与该方法自己的
判断记录"加载期结构性校验已经能拦下这类坏形状……不让一条坏记录中断整批预算校验"的设计意图相悖。

**根因**：`required_field`/`field_type` 只保证字段"存在且是字符串"，不保证字符串满足 `Id` 语法，
`GetId` 更强的语法校验发生在字段级校验之后的 `IValidationRule.Validate` 阶段，此时已经来不及产出
普通诊断，只能抛异常，而原 `catch` 类型没有覆盖这条异常路径。

**处理方式**：

1. **双层根治**：`DataRegistry` 字段级校验新增专用检查名 `field_id_format`——`FieldKind.Id`/
   `Reference`（含子结构递归）、已登记 `IdList` 逐元素、`MapSchema.ValueSchema` 值种类为
   `Id`/`Reference` 时的值，取值确是字符串但不满足 `Id` 语法时，从此前笼统归入的 `field_type` 中
   拆出，改报 `field_id_format`（阻断级）；取值本身不是字符串仍归 `field_type`，两者互斥。
   `Map` 键格式校验**不变**，仍归 `reference_integrity`（键按 `MapSchema.KeyReferenceTable`/
   `KeyReferenceDomain` 并入该检查项，`FreeKeys` 时键不做任何校验，本次未触碰）。
2. `SkillBudgetValidationRule.Validate` 的 `catch` 扩大为同时捕获 `ArgumentException` 与
   `DataFieldException`（`when` 过滤两种类型），且不再彻底静默——产出一条新检查名
   `skill_budget_record_unparseable`（`Warning`，`NonEscalatable`）的诊断，说明"该记录结构不合法
   已由字段级校验报告，本规则跳过预算校验、不重复诊断"，而不是让异常直接冒出 `LoadAll`。
3. **同批一并根治的原本零兜底规则**：`ItemGrantValueExceedsShareRule`（`item_grant_value_exceeds
   _share`）此前对 `SkillBudgetAnalyzer.ComputeGrantValue` 的调用**完全没有**任何 try/catch——
   `grants.skills`/`grants.auras` 引用的 Id 字面量结构非法（`new Id(...)` 直接抛
   `ArgumentException`）或被引用记录本身结构非法，均会中断整批校验。新增检查名
   `item_grant_value_unparseable`（`Warning`，`NonEscalatable`）：任一授予项解析失败即整件装备
   跳过超预算份额判定（不用部分求和结果误判"未超预算"），改产出该检查名诊断。
4. 反馈原文提到的"同类 `try/catch` 一并核查"范围内，`SkillBudgetValidationRule`/
   `ItemGrantValueExceedsShareRule` 均已覆盖；其余依赖 `SkillDefCache`/`DataRecord.GetId` 解析的
   规则本次核实未发现同类缺口。

提交：`0155173`（反馈 47 原始提交，分支 `feedback/47`）→ `3eb5bbb`（合并进
`feedback/integrate-45-47`，无冲突）。新增检查名：`field_id_format`、
`skill_budget_record_unparseable`、`item_grant_value_unparseable`。

**消费方需注意**：

1. **行为变更（需跟进）**：此前笼统归入 `field_type` 的"Id 语法非法"诊断，1.38.0 起改报
   `field_id_format`——若编辑器按检查名过滤/映射诊断（如问题面板分类、消费方反馈第 43 条的
   `TryGetOptionalRuleByCheck` 一类按检查名索引的逻辑），需要把原先隐含在 `field_type` 里的这部分
   诊断改指向新检查名；`field_type` 本身语义不变（仍表示"取值类型根本不对"，如非字符串）。
2. `Map` 字段的键格式校验**未受影响**，仍归 `reference_integrity`，不要误以为本次拆分覆盖了
   `Map` 键。
3. `skill_budget_record_unparseable`/`item_grant_value_unparseable` 两个新检查名均为 `Warning`
   级、`NonEscalatable`（规则整体登记，不可被"警告也阻断"提升）——出现这两条诊断意味着"某条记录
   结构不合法、本规则已跳过它的预算/份额校验"，真正的结构问题会由字段级 `required_field`/
   `field_type`/`field_id_format` 等检查项单独报出，不需要在这两条诊断上重复排查。
