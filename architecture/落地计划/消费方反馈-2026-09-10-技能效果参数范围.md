# 消费方反馈回复：技能效果参数数值范围校验改进建议（2026-09-10）

- 反馈来源：消费方游戏项目"框架反馈"提交的 `技能效果参数数值范围校验改进建议.md`，证据目录 `effect-ranges-1.14.0-20260910/`（探针源码 `Program.cs`、`effect-ranges-result.json`、`root-run.log`、`evidence-manifest.json`）。
- 关联 ADR：[ADR-0021](../adr/0021-字段登记表纳入数值范围约束.md)。
- 处理分支：`wf/field-range`（基于 `main` `bdb314c`）。
- 提交：<提交待填>。

## 现象

消费方的只读探针（引用 `dist/1.14.0` 程序集，调用 `Core.Rules.Assembly.RulesSchemaCatalog.RegisterAll` + 原生 `DataRegistry.LoadAll`，不执行运行时 `SkillHost`）复现：

- `skill.aura_def` 的 `periodic_damage.params.interval` 已登记为必填 `FieldKind.Number`，但填 `0`、`-1` 均以 `0 error` 通过加载期校验。
- `skill.def` 的 `apply_aura.params.duration_override` 已登记为可选 `FieldKind.Number`，但填 `-1` 同样以 `0 error` 通过。
- 对照组：把 `interval` 填成字符串（类型错误）会被 `field_type` 正确拦截阻断。

即"类型错误能被拦，取值范围错误不能"——这条不一致正是问题所在。

## 根因

`FieldSchema` 的 `Number`/`Int` 两种字段种类此前只支持"存在且类型匹配"的校验（检查项 `field_type`），没有取值范围这一维度。`interval`/`duration_override` 虽然在运行时逻辑（`AuraHost.Update`/`EffectDispatcher.ApplyAuraEffectPrimitive`）里早已对越界值有隐含的语义约束（`interval <= 0` 时周期效果整体不生效；`duration_override` 原样作为光环剩余时长），但这条约束此前只存在于运行时代码里、从未在登记表层面表达出来——内容错误因此只能在运行期以"效果看起来不生效"这种不易察觉的方式暴露，而不是在加载期像类型错误那样直接报错阻断。

## 处理方式

1. **`FieldSchema` 新增数值范围登记能力**（`core/foundation/data_registry/contracts/FieldRange.cs`、`FieldSchema.cs`）：新增 `FieldRange` 值类型（下界/上界各自可选、含端点各自可选）与 `FieldSchema.WithRange(FieldRange)` 方法；不改动任何既有构造函数签名（见下"公开 API"一节）。
2. **`DataRegistry.LoadAll` 统一在字段级校验阶段检查范围**（`core/foundation/data_registry/core/DataRegistry.cs`）：新增检查项 `field_range`，类型检查通过之后才检查范围（类型都不对时不重复报范围问题），递归适用于子结构/变体内部的字段，问题定位到记录主键与完整字段路径（如 `effects[0].params.interval`）。
3. **`SchemaAudit` 新增自洽检查**（`presentation/assembly/SchemaAudit.cs`）：范围只能登记在 `Number`/`Int` 字段上，登记在其它字段种类上判定为一条独立的登记自洽问题（检查名 `field_range_kind`），不是数据校验问题。
4. **`toolchain/validator --list-tables --json` 一并导出字段范围**（`toolchain/validator/Program.cs`、新文件 `presentation/assembly/SchemaFieldRangeExport.cs`）：每张表的 `field_ranges` 数组列出该表全部已登记范围的 `Number`/`Int` 字段（含子结构/变体内部字段），供内容工具（编辑器）做输入侧校验。
5. **登记范围**：`skill.aura_def` 的 `periodic_damage`/`periodic_heal` 效果 `interval`（`> 0`）、`skill.def` 的 `apply_aura.duration_override`（`>= 0`，省略沿用光环定义时长，永久光环约定不变）——本次反馈明确要求的两处。另按"运行时逻辑已隐含范围/文档已写明区间"的依据，一并补齐了同批可核实的字段（详见下"登记范围与依据"）。
6. **`AuraHost.Update` 的静默跳过改为先记诊断**（`core/rules/skill/core/AuraHost.cs`）：正常内容路径现已在加载期被 `field_range` 拦下，这里改的是保留下来的防御性分支（覆盖"绕过登记表校验"的路径，如直接构造走内存数据源、未经登记范围的工具场景）——`interval <= 0` 时先经 `ISkillDiagnostics.Warn` 记一条诊断，再按原逻辑跳过，不改变"该效果不生效"这条行为本身。
7. **ADR-0021**：把以上决策记录为架构级 ADR，`architecture/04_数据与内容管线.md` 新增 3.3 节"数值范围约束"与第 5 节校验项清单新增行（勘误方式，不改变既有结论，不升文档版本号）。
8. **编辑器产品文档**：契约面清单补充"字段范围可从 schema 导出用于输入校验"。

### 公开 API：新增成员的确切签名

`FieldSchema` 既有全部构造函数签名（含 1.12 兼容 façade）**原样保留**，本次只新增成员，不删改任何公开签名：

```
// core/foundation/data_registry/contracts/FieldSchema.cs
public FieldRange? Range { get; }                          // 新增只读属性
public FieldSchema WithRange(FieldRange range);             // 新增方法，返回 this 支持链式调用，只能设置一次

// core/foundation/data_registry/contracts/FieldRange.cs（新文件，新公开类型）
public sealed class FieldRange
{
    public double? Min { get; }
    public bool MinExclusive { get; }
    public double? Max { get; }
    public bool MaxExclusive { get; }

    public static FieldRange Range(
        double? min = null, bool minExclusive = false,
        double? max = null, bool maxExclusive = false);      // 唯一构造入口，min/max 至少给一个，min<=max，端点选择不产生空区间

    public bool Contains(double value);
    public string Describe();                                // 人类可读区间描述，如 "(0, +∞)"、"[0, 1]"
}
```

未改动 `FieldSchema` 任何既有构造函数的参数列表（不产生新的物理构造签名），符合仓库当前的"公开 API 表面差异"门禁（只能新增，不得删改已有公开签名）。

### 登记范围与依据

| 表.字段 | 范围 | 依据 |
|---|---|---|
| `skill.aura_def.effects[]{periodic_damage/periodic_heal}.params.interval` | `> 0` | `AuraHost.Update`：折算后 `interval <= 0` 时整条周期效果被跳过（本次反馈明确要求） |
| `skill.def.effects[]{apply_aura}.params.duration_override` | `>= 0` | `EffectDispatcher.ApplyAuraEffectPrimitive` 原样转发给 `AuraHost.ApplyAura` 作为光环剩余时长，负值无意义（本次反馈明确要求） |
| `skill.def.effects[]{...}.params.proc_chance` | `[0, 1]` | 字段自身文档"触发概率 0~1"；`ProcHost` 按均匀分布阈值比较使用 |
| `skill.def.charges.max` | `>= 1` | `SkillValidationRules.ChargesMaxAtLeastOneRule`（既有 Error 级业务规则，此前"登记表达不了"，现补齐登记） |
| `combat.hit_table_config` 六分支 `.base` | `[0, 1]` | `CombatHitTableValidationRule` 既有判断 |
| `combat.hit_table_config.crit_multiplier_base` | `>= 0` | `CombatHitTableValidationRule` 既有判断（非负） |
| `combat.hit_table_config.glancing_damage_pct` | `>= 0` | `CombatHitTableValidationRule` 既有判断（只检查非负，未卡上限，登记与既有校验行为一致） |
| `combat.resist_curve.max_reduction` | `[0, 1]` | `CombatResistCurveValidationRule` 既有判断 |
| `combat.resist_curve.entries[].reduction` | `[0, 1]` | 字段自身文档"减免百分比（0~1）" |
| `loot.table.groups[].entries[].count_range.min` | `>= 1` | `LootContentValidationRule` 既有判断 |
| `loot.table.groups[].pick_count` | `>= 1` | `LootContentValidationRule` 既有判断 |
| `loot.table.guaranteed_min` | `>= 0` | `LootContentValidationRule` 既有判断 |
| `econ.currency.cap` | `>= 0` | `EconomyHost` 文档"按 `[0, cap]` 夹取余额" |
| `econ.vendor.sell_items[].price_amount` | `>= 0` | `EconomyContentValidationRule` 既有判断 |
| `econ.vendor.sell_items[].stock_limit` | `>= 0` | `EconomyContentValidationRule` 既有判断 |
| `stat.rating_conversion.entries[].points_per_percent` | `> 0` | `StatHost.DivideByPointsPerPercent` 对 0 特判返回 0（同款"内容错误被静默降级"模式） |
| `item.template.stack_size` | `>= 1` | `ItemStackSizeRule.CheckMin` 既有判断"必须 >= 1" |
| `target.chain_def.max_targets` | `>= 0` | `TargetChainDef` 构造函数对负数直接 `throw DataFieldException`（此前是运行期崩溃，不是静默） |

以上"既有判断"均未删除（登记范围与既有 `IValidationRule` 并存，不是互斥关系——字段级范围校验先于业务规则运行，命中同一处坏数据时两者都会报告，不是回归，见各表 schema 文件里补充的判断记录）。逐一核对现有框架/示例数据（`python toolchain/validate_data.py --strict`，合并根与 `--data-root data/_framework` 两种跑法）均为 `0 error`，**未修改任何数据**。

未登记的其余 `Number`/`Int` 字段（如冷却增量 `delta` 允许正负、伤害基础值等语义仍存疑的字段）维持现状，仅在有明确依据时才补，避免机械补齐误伤合法内容语义。

## 对消费方的提示

1. **新检查名 `field_range`**：加载期字段级校验新增此检查项，`ValidationIssue.Check == "field_range"`，`Field` 为完整字段路径（子结构/变体内部同样给出完整路径，如 `effects[0].params.interval`）；消息格式固定为 `字段 "<路径>" 取值 <实际值> 超出范围 <区间描述>`，区间描述用数学记法（如 `(0, +∞)`、`[0, 1]`），可用于自动化断言匹配。
2. **类型错误优先**：同一字段的值若类型都不对，只报 `field_type`，不会额外报 `field_range`；不需要同时处理两种检查名重复告警同一处坏数据。
3. **编辑器可消费的导出**：`toolchain/validator --list-tables --json` 每张表新增 `field_ranges` 数组（`field_path`/`kind`/`min`/`min_exclusive`/`max`/`max_exclusive`/`describe` 六个字段），可用于内容编辑器在数值输入控件上做即时校验，不必等一次完整加载。
4. **本次未覆盖的字段**：只登记了本次反馈明确要求的两处，以及走查后有明确依据（既有业务规则、字段自身文档、运行时隐含约束）的同批字段（见上表），未做无依据的机械补齐；若消费方在其它字段上遇到类似"取值范围应该被拦但没被拦"的场景，欢迎按同样的证据链（探针 + 运行时判断依据）继续反馈。
5. 若消费方自己的内容预检脚本此前把 `interval=0`/`duration_override=-1` 当作"合法但运行期需要另行判断"的特殊值使用，升级到本分支后这些值会在加载期直接阻断，需要在自己的内容里改正（不是本次改动的兼容性问题，是内容本身此前就不合法）。
