## 第 18 条：`IExprSchema` 无法按分组枚举已登记的 key

**现象**：编辑器 Expr 编辑器（产品文档 5.4.2 节）做自动补全时，只能拿到"给定 group+key 是否已
登记签名"这一个查询（`TryGetSignature`），要展示"这个分组下有哪些可用的 key"这种下拉列表，
只能自己维护一份重复的登记表，或者遍历全部可能的 key 逐个试探。

**根因**：`IExprSchema` 从设计之初就只服务"点分标识符归类"这一个用途（ADR-0015），没有枚举能力。

**处理**：`IExprSchema` 新增两个带默认实现的成员（恒返回空集合，不要求已有实现方改动即可编译
通过）：

- `IReadOnlyCollection<string> KnownKeys(string group)`：该分组下全部已登记 key。
- `IReadOnlyCollection<string> KnownGroups`：本登记表已出现过至少一个已登记 key 的全部分组。

`ExprSchema`（持有登记字典的具体实现）显式覆盖为返回有序、确定性的结果——内部新增
`Dictionary<string, List<string>> _keysByGroup`，与既有 `_signatures` 字典在 `Register` 里
同步更新；`KnownKeys`/`KnownGroups` 各自返回前按 `StringComparer.Ordinal` 排序，不依赖
`Register` 调用顺序（避免"换一种代码书写顺序，补全下拉列表顺序就变"这种不确定性）。

**涉及文件**：`core/foundation/expr/contracts/{IExprSchema.cs, ExprSchema.cs}`；测试
`core/foundation/expr/tests/ExprSchemaKnownKeysTests.cs`（新增文件）。

**验证**：`KnownKeys_ReturnsAllRegisteredKeys_ForGroup_OrderedDeterministically`（登记若干签名后
按组枚举，顺序确定）、`KnownKeys_UnknownGroup_ReturnsEmpty`、`KnownKeys_ReRegisteringSameKey_
DoesNotDuplicate`、`KnownGroups_ReturnsAllGroupsWithAtLeastOneKey_OrderedDeterministically`、
`DefaultInterfaceImplementation_UsedByLegacyImplementer_ReturnsEmpty`（旧的、未跟改的
`IExprSchema` 实现方走默认实现，不抛异常）。

**对消费方提示**：`schema.KnownKeys("self")`/`schema.KnownGroups` 直接可用；只持有旧版本框架
编译出的 `IExprSchema` 实现类（未重新编译）在新版本框架下调用这两个成员，会走接口默认实现
（恒返回空集合），不会因为"没实现"而抛异常或编译失败。

## 第 19 条：`ExprValidator` 产出的问题项不带源文本位置

**现象**：编辑器 Expr 编辑器要把"未登记的引用""参数类型不匹配"这类校验问题在源文本里加下划线/
弹出气泡提示，只能自己对 `ExprIssue.Message` 里的自由文本做字符串匹配去猜测问题对应哪一段，
准确率低且随消息措辞变化而碎。

**根因**：`ExprIssue`/`ExprNode` 从设计之初就不携带源区间；ADR-0020 已经给词法 token
（`ExprToken`）补上了 `Start`/`Length`，但语法树节点与校验器产出的问题项没有跟进。

**处理**：

- `ExprIssue` 新增 `Start`/`Length`（默认 `-1`/`0` 表示未知）：以**新增重载构造**而不是给既有
  构造加可选参数的方式实现——`ExprIssue(kind, message)`/`ExprIssue(kind, severity, message)`
  两个既有构造物理签名完全不变，新增 `ExprIssue(kind, message, start, length=0)`/
  `ExprIssue(kind, severity, message, start, length=0)` 两个更多参数的重载。
- `ExprNode`（及 `ExprLiteralNode`/`ExprReferenceNode`/`ExprNotNode`/`ExprCompareNode`/
  `ExprAndNode`/`ExprOrNode` 六个子类）同样新增 `Start`/`Length` 只读属性，**每个子类都新增
  一个额外的重载构造**（如 `ExprLiteralNode(ExprValue value, int start, int length)`），既有
  构造保留不变。`ExprParser` 解析源文本时用新重载构造节点，从对应 token 填入区间；比较/`not`/
  `and`/`or` 等复合节点的区间由子节点的区间推出（起点取最左子节点起点，终点取最右子节点终点，
  任一子节点区间未知则整体未知）。手写构造的节点（既有测试、非解析器产出的场景）落在默认值
  `-1`/`0`。
- `ExprValidator` 产出问题项时带上对应节点的区间：`UnknownGroup`/`UnknownKey`/
  `ArgCountMismatch` 用整个引用节点的区间，`ArgTypeMismatch` 精确到具体哪个参数子节点，
  `CompareTypeMismatch`/`InvalidCompareForType` 用整个比较节点，`LogicalOperandNotBool` 精确到
  具体哪个操作数子节点，`SuspiciousReferenceSpelling` 用该 id 字面量节点本身。

**踩坑记录（供消费方参考，避免同类问题）**：最初实现直接给既有构造函数加了可选参数（如
`ExprLiteralNode(ExprValue value, int start = -1, int length = 0)`），源码层面完全向后兼容
（既有调用点不用改），但 `toolchain/abi_probe.ps1` 对照 1.12.0 基线运行时真实拦到 7 处
二进制破坏——C# 的可选参数只是编译期语法糖，物理上仍是同一个构造函数、只是参数数量变多，
已编译的旧消费方对"少参数版本"的调用指令在新 DLL 里找不到对应物理签名，运行期会抛
`System.MissingMethodException`。改为"新增一个真正独立的重载构造，旧构造物理签名完全不动"
后，`abi_probe.ps1 -BaselineZip dist/ws-game-1.12.0.zip` 复跑 `breaks=0`。这不是本条反馈本身
的内容，但因为直接影响本条改动的最终形态，一并记录在这里。

**涉及文件**：`core/foundation/expr/contracts/{ExprIssue.cs, ExprNode.cs}`、
`core/foundation/expr/core/{ExprParser.cs, ExprValidator.cs}`；测试
`core/foundation/expr/tests/{ExprParserTests.cs, ExprValidatorTests.cs}`（均为既有文件追加用例）。

**验证**：`UnknownKey_IssueSpan_MatchesHandBuiltReferenceNodeSpan`、
`ArgTypeMismatch_IssueSpan_MatchesOffendingArgumentText`、
`CompareTypeMismatch_IssueSpan_CoversWholeCompareExpression`、
`SuspiciousReferenceSpelling_IssueSpan_MatchesIdLiteralText`、
`SameGroupKey_AppearingTwice_ProducesIssuesWithDistinctSpans`（同一个 `group.key` 在文本里出现
两次，各自问题项区间不同）、`LogicalOperandNotBool_IssueSpan_MatchesOffendingOperandText`、
`LegacyTwoArgConstructor_LeavesStartAtMinusOne`；`ExprParserTests` 侧
`Parse_LiteralNode_HasSourceSpan`/`Parse_ReferenceNodeWithoutArgs_SpanIsJustTheIdentifier`/
`Parse_ReferenceNodeWithArgs_SpanCoversClosingParen`（含闭括号）/
`Parse_NotNode_SpanStartsAtNotKeyword`/`Parse_AndOrNode_SpanCoversFirstToLastOperand`/
`ExprNode_LegacyConstructor_WithoutPosition_DefaultsToUnknown`。

**对消费方提示**：`issue.Start >= 0` 时可直接用 `[Start, Start+Length)` 在源文本上定位/高亮；
`-1` 表示该问题项未携带区间信息（历史遗留手写 AST 场景），仍需退回按消息文本展示。

## 第 20 条：数据校验阻断态下，内容工具完全无法读取任何数据

**现象**：编辑器诊断面板希望在"数据校验未通过"时仍能展示已加载的记录，帮助作者定位/修复问题；
但 `GetAll`/`Query` 阻断态一律抛 `InvalidOperationException`，编辑器此前只能捕获异常后自己另外
维护一份"合并视图"重新实现一遍框架内部的多根合并逻辑。

**根因**：`GetAll`/`Query` 的阻断限制是"防止运行期宿主把未经校验的数据当权威数据用"（11 第 4
节"运行时不做静默降级"），这条限制对内容工具（作者本来就在修复问题，不存在"把坏数据当权威
数据用"的风险）过度保守，且没有为这类场景单独开一条口子。

**处理**：`IDataRegistryView` 新增三个带默认实现的成员：

- `bool TryGetAll(string table, out IReadOnlyList<DataRecord> records)`
- `bool TryQuery(string table, ExprNode predicate, out IReadOnlyList<DataRecord> records)`
- `bool TryQuery(string table, string predicateText, out IReadOnlyList<DataRecord> records)`

默认实现均为"try 对应的 `GetAll`/`Query`，只捕获 `System.InvalidOperationException`（
`DataRegistry.EnsureReadable` 阻断态精确抛出的类型），阻断则返回 `false` 且置空列表；不用
`catch (Exception)` 掩盖其它意外异常"。`DataRegistry` 显式接口实现（`bool
IDataRegistryView.TryGetAll(...)` 语法，不是同签名公开成员）覆盖为：直接读取内部按表合并去重
后的记录快照（与 `RecordCount`——见第二批第 17 条——同一份数据源），不经过 `EnsureReadable`，
阻断态也恒返回 `true`。刻意用显式接口实现而不是公开成员，是为了让这条"阻断态也能读"的通道只能
经 `IDataRegistryView` 接口引用触碰到，不会出现在 `DataRegistry` 具体类型的公开成员列表上，
呼应"仅供内容工具使用"的定位。

**涉及文件**：`core/foundation/data_registry/contracts/IDataRegistry.cs`、
`core/foundation/data_registry/core/DataRegistry.cs`（`GetAll`/`Query` 内部重构出
`GetAllUnchecked`/`QueryUnchecked` 私有辅助方法，公开方法与阻断态通道共用同一份读取/求值逻辑，
只是前者多一道 `EnsureReadable`）；测试
`core/foundation/data_registry/tests/DataRegistryTests.cs`（追加，新增 `ThrowingQueryView`
测试替身）。

**验证**：`TryGetAll_OnDataRegistry_BlockingState_ReturnsTrueWithMergedRecords`（坏表+好表夹具，
`GetAll` 抛、`TryGetAll` 返回 true 且能读到好表记录）、
`TryGetAll_OnDataRegistry_NotBlocking_MatchesGetAll`、
`TryGetAll_OnDataRegistry_UnknownTable_ReturnsTrueWithEmptyList`、
`TryQuery_ExprNodeOverload_OnDataRegistry_BlockingState_ReturnsTrueWithMergedResult`、
`TryQuery_PredicateTextOverload_OnDataRegistry_BlockingState_ReturnsTrueWithMergedResult`、
`TryGetAll_DefaultInterfaceImplementation_BlockingLikeException_ReturnsFalseWithoutThrowing`（
只实现 `IDataRegistryView`、未覆盖新成员的假类走默认实现返回 false）、
`TryGetAll_DefaultInterfaceImplementation_NotBlocking_ReturnsTrueMatchingGetAll`、
`TryQuery_ExprNodeOverload_DefaultInterfaceImplementation_BlockingLikeException_ReturnsFalse`、
`TryQuery_PredicateTextOverload_DefaultInterfaceImplementation_BlockingLikeException_ReturnsFalse`。

**对消费方提示**：编辑器诊断面板应改用 `((IDataRegistryView)registry).TryGetAll(table, out var
records)`（或对 `TryQuery` 同理）替换自建的降级视图；**运行期宿主不应该使用这条通道**——阻断态
下运行期读取仍必须走 `GetAll`/`Query` 并处理其抛出的异常（11 第 4 节"运行时不做静默降级"这条
结论完全不变，本条只是给内容工具单独开的口子）。

## 第 22 条：`OverrideDiagnostic` 只给绝对路径，跨机器/长路径下不便阅读

**现象**：多根合并加载产生的覆盖诊断（`OverrideDiagnostic.OverridingLocation`/
`OverriddenLocation`）是完整绝对路径；`toolchain/validator` 文本输出与 `--json` 输出都是绝对
路径，编辑器展示"覆盖清单"面板、或团队成员截图互相核对时，路径普遍很长且各自机器上的根前缀
不同，不便阅读/比对。

**根因**：`OverrideDiagnostic` 从设计之初就只记录 `DataTableSource.Location`（各 `IDataSource`
实现自行决定含义，`FileSystemDataSource` 场景下就是拼接后的完整路径），没有"这是第几个根"、
"相对这个根本身的路径是什么"这两个更适合人类阅读的维度。

**处理**：

- `IDataSource` 新增带默认实现的只读成员 `string? Root => null`（表示"不提供根标识"）；
  `FileSystemDataSource` 显式覆盖为构造时传入的根目录字符串——`ListTables` 产出的每条
  `Location` 都是 `根目录 + 相对路径` 拼成，这个新成员就是那个前缀本身。
- `OverrideDiagnostic` 新增 `OverridingRootIndex`/`OverriddenRootIndex`（该行所在数据根在
  `LoadAll(sources)` 传入的 `sources` 列表里的下标，0 基，即"根序号"）与
  `OverridingRelativePath`/`OverriddenRelativePath`（`Location` 相对其 `Root` 的路径，
  `Root` 未提供或不是 `Location` 前缀时退化为与 `Location` 相同）；绝对路径字段
  （`OverridingLocation`/`OverriddenLocation`）保留不变。新增一个完整参数的构造重载，既有
  四参数构造保留不变（新字段落在默认值：根序号 `-1`，相对路径退化为绝对路径本身）。
  `DataRegistry` 内部新增私有 `SourcedTable`/`ComputeRelativeLocation` 支撑这份计算，贯穿
  `LoadAllCore`（按表分组时记下每个 `DataTableSource` 来自 `sources` 的第几个下标与该根的
  `Root`）到 `LoadMergedTable`（构造 `OverrideDiagnostic` 时用上）。
- `toolchain/validator` 文本输出的"覆盖清单"一行改用 `"根{index}:{相对路径}"` 格式；
  `--json` 输出（`overrides` 数组每个元素）新增 `overriding_root_index`/
  `overriding_relative_path`/`overridden_root_index`/`overridden_relative_path` 四个字段，
  `overriding_location`/`overridden_location`（绝对路径）保留——**两者都给**。

**涉及文件**：`core/foundation/data_registry/contracts/{IDataSource.cs, OverrideDiagnostic.cs}`、
`core/foundation/data_registry/core/{DataRegistry.cs, FileSystemDataSource.cs}`、
`toolchain/validator/Program.cs`；测试
`core/foundation/data_registry/tests/DataRegistryTests.cs`（追加）。

**验证**：`OverrideDiagnostic_RootIndex_MatchesPositionInSourcesList`（`InMemoryDataSource` 不
提供 `Root`，相对路径退化为绝对路径，根序号仍正确）、
`OverrideDiagnostic_RelativePath_StripsDeclaredRootPrefix`（自建的 `RootedSource` 测试替身，
验证相对路径真的被裁剪）、
`OverrideDiagnostic_LegacyFourArgConstructor_DefaultsRootIndexToMinusOneAndRelativePathToLocation`；
对真实 `data/_framework`+`data/_sample` 合并加载跑了一遍端到端验证（`python
toolchain/validate_data.py --strict`），实际产出：`` 根1:arch/arch.power_type.json" 覆盖
"根0:arch/arch.power_type.json ``；`--json` 输出核对四个新字段均正确出现。

**对消费方提示**：编辑器"覆盖清单"面板展示应改用"根{index}:{相对路径}"格式；绝对路径字段仍在，
需要跳转打开文件等场景继续用绝对路径。`IDataSource` 自定义实现若想让相对路径生效，需要显式
覆盖 `Root` 属性返回自己的根标识字符串；不覆盖时该实现产出的诊断相对路径会退化为绝对路径
（不是错误，只是裁不出更短的形式）。

## 第 21 条：ADR-0019 子结构登记第二批（18 个字段）——本轮未完成，如实说明

**现象**：`docs/验收/P2.1-degraded-fields.md` 列出 18 个仍未按 ADR-0019 登记子结构、停留在
`toolchain/schema_audit_allowlist.json` 豁免名单里的字段，要求逐一确定结构、能登记的登记、
确属不透明的写清理由。

**当前状态核实**：`toolchain/schema_audit_allowlist.json` 当前 20 条豁免记录中，与本条清单
对应的 18 条（`arch.class.base_stats`、`arch.race.stat_mods`、`creature.template.base_stats`、
`dialog.gossip_menu.options[].actions[].params`、`display.map.{anchor_points,
default_slot_meshes,material_params}`、`display.anim_set.clips`、
`display.weapon_style.{cast_anim_override,impact_vfx_override}`、
`encounter.def.phases[].ai_rotation_override`、`prog.level_curve.entries[].growth`、
`gobj.template.type_data.trigger_shape`、`ai.behavior_profile.transitions`、
`arch.talent_tree.nodes[].grants`、`found.time_model.grid_snap`、
`found.event_catalog.fields`、`ui_layout_definition.fields`）**本轮未动**，均维持原状（另外
2 条 `item.affix.effects`/`world.flag_schema.allowed_values` 不在本条清单内，属"确属不透明的
扩展位占位字段"，本轮同样未动，见各自 `TableSchema` 定义注释）。`--schema-audit --allowlist
toolchain/schema_audit_allowlist.json` 核实：`tables 63, fields 783, errors 0, warnings 0`，
与本轮开始前一致。

**为什么没做，如实说明**：任务书本身已经点出这条的技术难点——至少 `arch.class.base_stats`/
`arch.race.stat_mods`/`creature.template.base_stats` 三个字段是"键为 `stat.definition` 引用、
值为数值"的动态键 Map 结构，而 `FieldSchema` 当前的 `Fields`/`Variants` 登记机制只能表达"固定
键清单"，不能表达"键本身是另一张表的引用、值种类固定"这类动态键 Map；`display.anim_set.clips`
是"动态键（剪辑名）→ 固定值结构"，同样超出现有登记 DSL 表达力（allowlist 对应条目已经写明
这一点，任务书本身也提示"若 FieldSchema 目前没有对应形态，就以最小新增形态支持"）。这意味着
这 18 个字段不是"逐一照抄登记 API 填个 `Fields`/`Item`/`Variants`"就能完成的机械劳动——
真正要交付的是：

1. 先给 `FieldSchema` 设计并新增一种"动态键 Map"登记形态（新增枚举值或等价的最小扩展），
   这本身是一次需要单独评审的契约面变更（可能涉及 `SchemaAudit`/`toolchain/validator --list-
   tables --json` 导出格式同步跟进、`04`/ADR 补充说明），不是"顺手加"的规模。
2. 对其余不需要新 Map 形态、能用现有 `Fields`/`Item`/`Variants` 直接表达的字段（如
   `dialog.gossip_menu.options[].actions[].params` 按 `kind` 分派的变体、
   `encounter.def.phases[].ai_rotation_override`、`display.weapon_style.*_override`、
   `gobj.template.type_data.trigger_shape`、`arch.talent_tree.nodes[].grants`、
   `ai.behavior_profile.transitions`），逐一登记前必须先找到并读懂对应的运行时解析代码
   （`*.FromRecord`/`ParamsX` 一类），核对登记与解析代码逐字段一致——这是本仓库 04 文档"以

   定位到具体解析实现并逐字段比对，工作量与出错风险不小（登记错了比不登记更危险——会让编辑器
   等工具生成误导性的表单/自动补全，且会被 `SchemaAudit` 当作"已登记"放行，不再有 allowlist
   兜底提醒）。
3. 每张表登记完成后还需要补/更新 coverage 测试（`*SchemaCoverageTests` 既有惯例），并重新跑
   `validate_data.py --strict`/`validator --schema-audit` 确认 0 error。

## 第 23 条：`data/_sample` 部分已登记表没有任何示例数据

**现象**：`item.affix`、`item.set`、`world.flag_schema` 三张表已在代码里登记了 `TableSchema`，
但 `data/_sample` 与 `data/_framework` 两个数据根都没有对应的数据文件——编辑器新建工程/演示时
这几张表永远是空表，`item.template.affixes`/`item.template.set_id` 这两个引用字段也从未在
示例数据里被实际用过，无法用真实数据验证编辑器的引用自动补全/跳转。

**处理**：

- 排查口径：已登记 `TableSchema` 但 `data/_sample` 与 `data/_framework` **两个根的并集**都没
  有任何一行的表——按这个口径排查出的确实只有 `item.affix`/`item.set`/`world.flag_schema`
  三张（`found.event_catalog`/`found.game_state`/`found.hook`/`found.input_action` 四张
  框架单例表已在 `data/_framework` 有数据，不计入）。
- `data/_sample/item/item.affix.json` 补 3 行（`sample_of_strength`/`sample_of_fire`/
  `sample_of_frost`）；`data/_sample/item/item.template.json` 的 `item.sample_blade`/
  `item.sample_model_sword` 两条记录补上 `affixes` 字段引用它们（此前示例数据从未使用过这个
  字段）。
- `data/_sample/item/item.set.json` 补 1 行（`sample_starter_set`）：`pieces` 引用既有的
  `item.sample_blade`/`item.sample_model_sword`，`bonuses` 引用既有的
  `skill.aura_def.sample_fortify`（未给这两件物品补 `set_id` 回指——`ItemSetMembershipRule`
  只单向校验"声明了 `set_id` 的物品必须出现在对应 `item.set.pieces` 里"，不要求反向，补
  `set_id` 不是必需，保持改动最小）。
- `data/_sample/world/world.flag_schema.json` 补 2 行（`world.sample_bridge_repaired`/
  `world.sample_gobj`，覆盖 `bool`/`id` 两种 `kind` 取值）。
- `data/_sample/l10n/l10n.text.json` 补齐上述新增 `name_key` 对应的文本条目。
  `python toolchain/format_data.py --schema-order --check` 确认全部 64 个文件字段序均无需
  重排（新增内容落笔时已按 `TableSchema.Fields` 登记顺序书写）。
- 新增 `sample_table_empty` 告警级门禁（pytest 形式，`toolchain/tests/
  test_sample_table_empty.py`）：经 `toolchain/validator --schema-audit --json` 新增的
  `table_names` 字段（纯增量，全架构已注册表名权威列表，本次一并新增）拿到已注册表清单，
  与 `data/_sample`/`data/_framework` 两根并集里"至少有一行"的表集合比较，命中"两根都没有
  任何行"时用 `warnings.warn` 提醒但**不 assert False**——测试本身恒 PASS，不阻断
  `pytest toolchain/tests` 的退出码。**判断记录（为什么按两根并集判定，不是严格"只看
  _sample"）**：任务原文口径是"仅对 _sample"，但严格只看 `_sample` 会让
  `found.event_catalog` 一类框架单例表永久触发告警（按设计这类表永远不会出现在 `_sample`），
  长期噪音会盖过真正的信号；改为按两根并集判定，与本条实际排查、补数据时使用的是同一套口径，
  见测试文件模块级判断记录。
