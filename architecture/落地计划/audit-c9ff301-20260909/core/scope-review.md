## Closed replay evidence with separated ownership

### CORE-111-01 Mana / InCombat rollback

The general contract is the ordered `SaveSystem` failure rollback plus `PlayerVitalsPersistable` and `PowerHost` persistence. The framework modules own snapshot, rollback order, registered power state, and combat-state persistence; a game or assembly root owns which persistables are registered and which save document is supplied. The existing probe precondition is a registered assembled world, a valid A save, a valid B document whose later section fails, and a saved power/combat state. It proves the registered power and combat flag return to the pre-load snapshot, including after one advance under the fixture's `regen_in_combat=0`. It does not prove every persistable, every migration, nonzero regeneration policy, Unity serialization, or arbitrary game save content. The general acceptance is equality between all participating registered fields and the pre-load snapshot after a failed load, with derived-state rebuilding respecting the documented order; `Mana=30` is only fixture data.

### UI-111-01 same-map InventoryViewModel refresh

The general contract is that a presentation view model observing `SaveLoaded` refreshes its query projection from the live source. `presentation/ui` owns the view model and event reaction; the game supplies the `IUiDataSource` implementation and item/equipment data. Preconditions are a successful same-map load, a live source that reflects the loaded state, and delivery of the documented event. The direct live inventory/equipment query matching the VM proves the refresh contract for this view model. It does not prove Unity binding, rendering, cross-map behavior, or other view models. General acceptance is projection equality after the event, independent of item ids and visual presentation.

### TP-111-01 consecutive public Dialog teleport while Loading

The general contract is atomic route/scene commit: `SceneRouter` controls loading state and `GameplayAssembly` commits player/map state only after route acceptance. The game supplies map data, the public Dialog option, post-load completion, and the real `WorldSim` entities; the framework owns the ordering invariant. Preconditions are two public requests while the first load is `Loading`, a real post-load callback, and `WorldSim.AddEntity` for the destination player. The probe proves router/player/WorldSim map and position consistency through that assembled path. It does not prove Unity scene-manager behavior, every loader failure mode, or arbitrary game route data. General acceptance is cross-system state consistency after accepted, rejected, queued, or replaced requests; no particular request policy is required by this invariant.

## Static contract review: mechanisms that must stay separated from game content

### Talent mechanism: tree data is implemented; allocation is not an owned runtime API

The architecture promise is narrow and reusable: `07_载体层_物品生物物件.md:237-238` defines a talent as a tree node whose activated grant is expressed through the Skill system (`SpellMod` or `override_skill`), while `:303-304` places the mechanism in the framework and the concrete tree/grants in the game. The current `IArchetypeRegistry` only exposes read/query and `ApplyTo` (`core/numbers/archetype/contracts/IArchetypeRegistry.cs:7-36`); `ArchetypeRegistry` parses and indexes trees (`core/numbers/archetype/core/ArchetypeRegistry.cs:60-88,154-197`) but does not offer point spend, activate, refund, or talent-state persistence. The default `GameplayAssembly` passes `talentPointGranter: null` (`core/gameplay/assembly/GameplayAssembly.cs:506-507`).

This is a static contract ownership gap, not a reproduced P2. The framework currently provides schema, cycle validation, tree read access, and the Skill primitives used by a future activation path. This review found no complete general talent-management API promise for allocation, refund, or persistence; those choices cannot be silently assigned to `ArchetypeRegistry` or to a particular game. The existing passive-aura reuse promise does not equal an allocator promise. If a separate decision promotes full management to a general framework capability, that decision must name its owner and contract; until then, a game's absence of talent gameplay is an integration scope decision, while `arch.talent_tree` parsing remains usable framework functionality.

### FindUnits: explicit framework convenience API gap, separate from target.chain

The general `ISkillHost.FindUnits(shape, origin, filter)` contract is documented in `core/rules/common/contracts/ISkillHost.cs:13-31` and `06_规则层_属性技能战斗AI.md:430-434`; it is intended to delegate shape selection to the injected spatial capability. `ISpatialQuery.QueryShape` exists at `core/foundation/engine_adapter/contracts/ISpatialQuery.cs:123`. However, `SkillHost.FindUnits` unconditionally warns and returns an empty list at `core/rules/skill/core/SkillHost.cs:169-176`, even though the host passes the optional spatial query into `CastPipeline` (`:93,140`) and that pipeline uses it for line-of-sight (`core/rules/skill/core/CastPipeline.cs:94,113-126,273-277`).

This is a static framework contract difference, not a claim that all area targeting is unavailable and not a new P2: `target.chain` is a separate path and already delegates through `TargetHost`/`BuiltinTargetStrategies` to `Spatial.QueryShape` (`core/rules/targeting/core/TargetHost.cs:126-149`, `BuiltinTargetStrategies.cs:102-122`). The framework owner is `SkillHost` if `FindUnits` is retained; the game owns providing an `ISpatialQuery` implementation and choosing whether a skill uses this convenience API or `target.chain`. Acceptance is either a documented unsupported API with a changed contract, or delegation that returns the injected spatial query's filtered result with explicit null behavior. No particular game's area skill or target list should be hard-coded.

### Summon duration: continuous lifecycle is implemented; discrete advancement is a declared boundary

The reusable contract in `07_载体层_物品生物物件.md:227-234` is creation from the `summon` effect, optional duration expiry, owner follow/loss behavior, and no summon-specific save segment. `SummonHost.Summon` registers owner and optional remaining duration (`core/carriers/summon/core/SummonHost.cs:35-63`), and `AdvanceAndCheckExpired` handles continuous elapsed time (`:165-180`). `SummonTickHandler` performs expiry, owner/liveness checks, combat/threat integration, and follow (`core/carriers/summon/core/SummonTickHandler.cs:77-118`), but explicitly skips `Discrete` steps at `:53-62`; the source records this as current design, and 07 does not require discrete duration/follow advancement.

The responsibility is L3 `SummonHost`/`SummonTickHandler`, with L0 tick registration and injected L2 combat/movement contracts; the game chooses `SummonOptions` and time model. Preconditions for the implemented expiry/follow behavior are a registered handler, continuous `SimStep`, creature factory, world/unit access, and any enabled combat/threat dependencies. The source and existing module tests support the continuous path, but this review adds no runtime probe. Therefore this is not “summon lifecycle unimplemented” and not a P2. Consumers may choose strategies within the supported time model; any proposal to extend framework discrete advancement requires a separate time-model contract decision and is not automatically scheduled. The current no-op is a documented support boundary.

### Escort: objective representation and manual state transitions are framework; route driving is integration

The general Quest contract includes the `escort` objective type and `escort_route_ref` field (`architecture/08_玩法层_掉落任务对话关卡.md:86,91,105`). `QuestObjective` stores the optional route id (`core/gameplay/quest/contracts/QuestObjective.cs:32-36`), and `QuestDefinition` parses it without interpreting route geometry (`core/gameplay/quest/contracts/QuestDefinition.cs:152-178`). The public `IQuestHost` contract explicitly makes `UpdateProgress` the manual driver, primarily for escort objectives (`core/gameplay/quest/contracts/IQuestHost.cs:25-39`); `Fail` is the explicit failure transition (`:61-68`, implemented in `core/gameplay/quest/core/QuestHost.cs:327-346`).

The framework owner is Quest's objective/state machine. A game or a future explicitly assigned route/escort module owns the escorted entity movement, route resolution, arrival/death detection, and calls to `UpdateProgress`/`Fail`; `QuestHost` has no generic navigation or route provider contract. This proves that escort can be represented and progressed through a narrow state API, not that a game receives automatic escort movement. It is a static integration boundary, not a reproduced P2. General acceptance for the current framework is deterministic manual progress/failure and event/state transitions; automatic route completion requires a separately named provider contract and a game-level route/data choice.

## Extensions and non-findings audit

No conclusion here assigns a game-specific content implementation to the framework.
