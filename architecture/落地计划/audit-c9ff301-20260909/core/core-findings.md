### CORE-113-01 [P2] gobj.lock world_flag expected bypasses the content gate

**Source.** `core/carriers/gobj/schema/GobjSchemas.cs:128-158` documents retirement of `GobjLockRequirementFieldGroupRule`; the `world_flag` variant registers only `flag_key` at `:148-153`, leaving `expected` unregistered. `core/carriers/assembly/CarriersSchemaCatalog.cs:93-104` confirms the old rule is not registered. Runtime parsing still requires it in `core/carriers/gobj/contracts/LockDef.cs:42-53`, where `ParseRequirement` calls `RequireExprValue(..., "expected")`; the missing-field throw is implemented at `:98-106`.

**Legal reproduction and actual result.** `core/repro/GobjLockBoundaryProbe.cs` loads a single `gobj.lock` record `{requirement:{kind:world_flag,flag_key:world.flag.test}}` through default `Presentation.Assembly.ContentValidationAssembly.Run` and a direct `CarriersSchemaCatalog` registry with `FailOnUnknownTable=true`. Both report `blocking=False`, `error_count=0`, and the actual `LockDef.FromRecord` call throws `DataFieldException` for missing `expected`. The positive `expected=true` fixture reports zero errors and parses to `WorldFlag`. Evidence: `core/logs/gobj-lock-boundary.log` and `.exit.txt`.

**Oracle and impact.** A record that is legal for the formal schema must be legal for `LockDef.FromRecord`; missing a required variant field must be rejected during content validation. Current behavior lets bad content pass the gate and fails when a real `GobjHost`/parser reads it, potentially during gameplay or load. The positive fixture proves the probe is exercising the intended variant rather than rejecting the whole table for unrelated reasons.

**Recommendation and acceptance.** P2: register `expected` in the `world_flag` variant with an explicit Bool/JsonNumber shape validator, or restore an equivalent rule. For this `LockDef` contract, `JsonNumber` includes both integer and non-integer numbers; String and `{"$id":...}` are not valid `expected` forms. Acceptance requires the missing-`expected` fixture to produce at least one blocking error and never reach runtime parsing; `expected=true`, integer, and number fixtures remain accepted and the positive fixture parses successfully.

**Responsibility boundary review.** The promised general contract is the framework content gate and the `LockDef` parser agreeing on the same `world_flag` requirement shape; the game supplies `gobj.lock` rows and chooses to invoke the formal validation assembly. Ownership is `core/carriers/gobj/schema` plus `core/carriers/gobj/contracts/LockDef`, with `CarriersSchemaCatalog` responsible for registration. The demonstrated preconditions are a registered `gobj.lock` schema, a valid envelope, the formal `ContentValidationAssembly`/carrier catalog, and strict `FailOnUnknownTable=true`; no game-specific lock id is part of the rule. The probe proves a schema/parser mismatch for one supported variant and proves the positive Bool route; it does not prove every GobjHost interaction, every lock variant, or Unity content loading. General acceptance is that missing `expected` is blocked before parsing while Bool and JsonNumber values accepted by `LockDef` remain valid. This is a framework validation contract; the fixture's ids and gameplay use remain game data.

### CORE-113-02 [P2] SkillHost keeps stale SkillDefCache after DataLoadCompleted

**Source.** `core/rules/skill/core/SkillDefCache.cs:38-55` lazily reads and permanently stores a parsed `SkillDef` in `_skills`; cache hits return before consulting the registry. `core/rules/skill/core/SkillHost.cs:83-114` constructs one cache per host, and the host reads it for cooldown/cast paths at `:186` and `:419`. No `DataLoadCompleted` subscription or cache invalidation exists in these paths.

**Legal reproduction and actual result.** `core/repro/SkillHotReloadBoundaryProbe.cs` builds a real `SkillWorld`/`SkillHost`, first queries cooldown and casts a skill with cooldown=0 and effect `EffectContext.BaseValue=7`, mutates the source to cooldown=5/base=99, calls `registry.Reload("skill.def")`, computes the record count by summing `registry.Tables`→`GetAll(table).Count`, then publishes `DataLoadCompletedEvent` immediately. The registry exposes cooldown=5/damage base=99. After the second cast, the existing host still emits `BaseValue=7` and its cooldown is 0. A fresh real host built from the new registry data emits `BaseValue=99` and cooldown 5. The labels are FakeCombatHost `EffectContext.BaseValue` observations, not HP application. Evidence: `core/logs/skill-hot-reload-boundary.log` and `.exit.txt`.

**Oracle and impact.** Under the declared immediate-effect workflow, after a successful hot reload notification an existing host must invalidate its parsed definition cache. A separately approved reconstruction-only contract would be a public contract change and would require an implemented generic reconstruction path. The independent fresh-host comparison is the oracle here. Current resident-host behavior diverges from the new registry and fresh-host behavior, so live balance/cooldown changes can be silently ignored until host reconstruction.

**Recommendation and acceptance.** P2 under the declared template development workflow: subscribe `SkillHost`/`SkillDefCache` to `DataLoadCompleted` and clear affected/all definition caches. A reconstruction alternative is acceptable only when the template's general reconstruction path is actually implemented and still makes the existing host's next cast observe the new definition; merely changing the wording of the public contract is not the default fix for this finding. Acceptance requires the same existing host's post-reload second cast to observe the reloaded definition, matching a fresh host; the event record count must equal the sum across all loaded registry tables. This does not require every game to support live balance changes or every cache consumer to hot reload.

**Responsibility boundary review.** The general contract in scope is the development-only template data hot-reload path: `DataRegistry.Reload` plus `DataHotReload` publishes the immediate load-completed notification, and a resident `SkillHost` is expected to honor the template's declared “next cast sees the new definition” behavior. `core/foundation/data_registry` and `games/_template/Runtime/DataHotReload` own reload/event production; `core/rules/skill` owns the resident definition cache. The pure .NET probe preconditions are one initialized registry/bus, a successful manual `Reload`, immediate manual `DataLoadCompleted` publication, an already constructed host, and a new cast after the event with no prior cooldown masking the comparison. Applying this contract through the template additionally requires editor/development compilation and a watcher path wired to that same registry/bus; the probe did not initialize the watcher. The probe proves only this existing-host cache boundary against a fresh host; it does not prove the Unity `FileSystemWatcher` entry, release-build behavior, or unrelated `DisplayInfoRegistry`/`L10nHost`/`QuestHost` caches. General acceptance is reloaded data visible to the next cast of an existing host whenever the immediate-effect contract is enabled. A reconstruction alternative is acceptable only when a generic template reconstruction path is actually implemented and enforced; changing wording alone is not acceptance. The skill id and numeric values are fixture data, not framework requirements.

### CORE-113-03 [P2] quest rewards.world_flags value shape passes validation then crashes parser

**Source.** `core/gameplay/quest/core/QuestContentValidationRule.cs:194-206` checks only whether `world_flags[].value` exists/non-null. `core/gameplay/quest/core/QuestSchemas.cs:188-206` leaves the union field unregistered. Runtime parsing in `core/gameplay/common/contracts/RewardBundle.cs:164-182` calls `ExprValueJson.Parse`; `core/gameplay/common/contracts/ExprValueJson.cs:18-33` accepts Bool, Number (Int/Number), String, or the one-field `{"$id":...}` object and throws `FormatException` for an Array.

**Legal reproduction and actual result.** `core/repro/QuestWorldFlagValueBoundaryProbe.cs` uses the default formal `ContentValidationAssembly.Run` configuration (`WarningsAllowed`, `FailOnUnknownTable=true`) with valid `l10n.locale.zh_cn`/`l10n.text` rows and one valid event objective, so no missing-text warning masks the result. For `value=[]`, the formal report is `blocking=False`, `issue_count=0`, `error_count=0`, then `QuestDefinition.FromRecord` throws `FormatException` naming `Array`. The positive `value=true` path uses a separate real `ContentValidationAssembly` registry, loads successfully, parses a real `QuestDefinition`, and reads `positive_true_world_flag_count=1`. Evidence: `core/logs/quest-world-flag-value-boundary.log` and `.exit.txt`.

**Oracle and impact.** The formal content gate should reject any value outside the `ExprValueJson.Parse` union before `QuestHost`/`QuestDefinition` runtime parsing. Current validation admits a shape that the runtime parser cannot consume, turning content error into a load/gameplay exception. The positive real parse demonstrates the accepted Bool path.

**Recommendation and acceptance.** P2: add a shape check for each `rewards.world_flags[].value` that matches `ExprValueJson.Parse` (including Int versus Number and the `{"$id":...}` form), or register an equivalent recursive schema validator. Acceptance requires `value=[]` to be a blocking validation error and never reach the runtime parser; `true`, integer/number, string, and valid Id fixtures remain accepted.

**Responsibility boundary review.** The promised general contract is that the Quest content gate accepts exactly the `RewardBundle`/`ExprValueJson` value language before `QuestDefinition` parsing; the game supplies quest rows, reward values, localization rows, and any event objective ids. `core/gameplay/quest` owns the quest-specific validation and definition parser, while `core/gameplay/common/contracts/RewardBundle` owns the shared reward value interpretation. Preconditions are the default formal `ContentValidationAssembly.Run` configuration (`WarningsAllowed`, `FailOnUnknownTable=true`) with the Quest schema/rules registered, valid required localization/objective data, and a real registry load followed by `QuestDefinition.FromRecord`. The probe proves an array passes the Quest gate and fails the generic parser, plus a real Bool positive path; it does not prove quest progress, turn-in, achievement behavior, or all reward kinds. General acceptance is rejection of every shape outside the parser's declared union before runtime parsing, with all shapes inside that union accepted. The test quest and its ids are content fixtures, not a mandate for a particular game.
