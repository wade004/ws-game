## 第 28 条：`npc_flags` 固定取值未登记

### 现象

`creature.template.npc_flags` 是 `IdList` 且 `FreeIds`，合法取值是 `Core.Carriers.Creature.
NpcFlagIds` 的六个固定 Id，但 `FieldSchema` 未登记该集合——`EnumValues` 只对 `FieldKind.Enum`
可用，`IdList`/`Id` 无法使用；`CreatureContentValidationRule` 只能用代码手写校验，与登记表脱节，
编辑器读不到这份固定取值集合，无法渲染下拉/多选控件，只能退化为自由文本输入。07 文档与产品
文档把取值写成裸词（如 `vendor`），未说明实际数据表侧写法是 `npc_flag.vendor`。`NpcFlagIds.
ToTag` 在编辑器侧检索不到调用方，怀疑是死代码。

### 处理

1. **`FieldSchema` 新增 `AllowedValues`**（`core/foundation/data_registry/contracts/
   FieldSchema.cs`）：`IReadOnlyList<Id>? AllowedValues` + `WithAllowedValues(IReadOnlyList<Id>
   values)`——只能设置一次（重复设置抛 `InvalidOperationException`），值集合不能为空
   （`ArgumentException`）。与 `FreeIds`/`ReferenceTable` 语义上互斥，刻意不在挂载时检查冲突
   （同 `WithRange`/`WithMap` 既有风格"让登记在错误组合上的错误停留在可枚举的软失败"），冲突由
   `SchemaAudit` 新检查项 `idlist_allowed_values_conflict` 事后报告。既有 `idlist_reference_
   target` 检查项扩展：`IdList` 字段在 `ReferenceTable`/`ReferenceDomain`/`FreeIds`/
   `AllowedValues` 四者中登记其一即满足，不再只认三者。
2. **`DataRegistry.LoadAll` 新增 `field_allowed_value` 检查项**（`core/foundation/data_registry/
   core/DataRegistry.cs`）：`ValidateIdList` 对每个已通过 Id 格式检查的元素，若字段登记了
   `AllowedValues` 则额外检查是否 ∈ 该集合，不在集合内报错，定位到 `字段路径[下标]`；
   `FieldKind.Id` 单值分支同样检查，定位到字段路径本身。与既有 `ReferenceTable`/
   `ReferenceDomain` 检查各自独立（互不依赖，即使两者同时登记也各自按自己的规则检查——冲突本身
   由 `idlist_allowed_values_conflict` 静态门禁负责，不在运行期数据校验里假设"二者互斥"）。
3. **`CreatureSchemas.Template.npc_flags` 改用登记表**：`.WithFreeIds(...)` 改为
   `.WithAllowedValues(NpcFlagIds.All)`；`NpcFlagIds` 新增 `public static readonly
   IReadOnlyList<Id> All`（六个值，顺序照抄 `NpcFlag` 枚举声明顺序，即 07 第 2.2 节表格行序）。
4. **`CreatureContentValidationRule` 收口**：此前手写的 `npc_flags` 逐元素校验（`creature_
   content` 检查项）与新的 `field_allowed_value` 是同一份数据上的重复校验，会对同一处非法值
   报告两条问题——已删除该校验逻辑，`Validate` 改为 `yield break`（空实现）；类型与
   `IValidationRule` 注册点保留（不删除公开类型，供未来真正需要的 creature 模块专属、且无法用
   登记表元数据表达的校验项落地，惯例同 `AiContentValidationRule` 一类扩展点）。
5. **`NpcFlagIds.ToTag` 消费方核实（非死代码）**：`core/carriers/creature/core/
   CreatureFactory.cs:103`（`Spawn` 方法）：

   ```csharp
   foreach (var flag in template.NpcFlags)
   {
       unit.NpcFlags.Add(NpcFlagIds.ToId(flag));
       unit.Tags.Add(NpcFlagIds.ToTag(flag));
   }
   ```

   每个职能标志额外映射为一个单位标签 `tag.npc.<name>` 写入 `unit.Tags`，供
   `Core.Rules.Common.IUnitAccess.GetTags` 一类按标签过滤索敌/交互目标的场景使用（如排除/筛选
   贩卖商、训练师等 NPC）。编辑器侧检索不到调用方的原因是调用点位于 `core/carriers/creature`
   （核心库），不在编辑器代码检索范围内；已有回归测试
   `core/carriers/creature/tests/CreatureFactoryTests.cs.Spawn_ConvertsNpcFlagsToTags_
   AndSetsTierTag` 覆盖该消费路径（断言 `unit.Tags` 含 `tag.npc.vendor`/`tag.npc.questgiver`）。
   `NpcFlagIds` 类型注释已补充该判断记录。
6. **`toolchain/validator --list-tables --json` 导出**：`field_meta` 新增 `allowed_values`
   （已登记时为该字段固定取值的字符串数组，未登记为 `null`）。
7. **文档**：07 文档 2.1 节字段表 `npc_flags` 说明、2.2 节整节改写为正式 `npc_flag.<name>` 写法
   （原裸词 `vendor`/`trainer`/... 改为 `vendor`（`npc_flag.vendor`）/... 并列展示），补充
   `tag.npc.<name>` 消费方说明；`editor/docs/编辑器产品文档.md`（v2.6）4.1 节契约面清单、5.5.1
   节生物编辑器交互流程第 3 条同步。

## 第 29 条：软引用字段无目标表元数据

### 现象

`creature.template` 的 `ai_rotation_ref`/`ai_behavior_ref`/`loot_table_ref`/`display_ref`/
`on_hit_reaction_ref`/`on_death_reaction_ref` 登记为 `Id`（非 `Reference`，因 L3 不可
`Reference` L2/L4 的分层边界，见 `CreatureSchemas` 判断记录），登记表里没有任何元数据说明这些
字段语义上指向哪张表，内容工具（编辑器）无从为这些字段提供自动补全/跳转，只能当成自由文本输入。
`on_hit_reaction_ref`/`on_death_reaction_ref` 在当前 63 张表里找不到目标表，`CreatureTemplate.
cs:144-145` 只做解析，需核实是否有任何消费方。

### 处理

1. **`FieldSchema` 新增软引用元数据**（`core/foundation/data_registry/contracts/
   FieldSchema.cs`）：`string? SoftReferenceTable`/`string? SoftReferenceDomain` +
   `WithSoftReference(string? table = null, string? domain = null)`——`table`/`domain` 至多
   设置一个、至少设置一个，只能整体设置一次。**刻意不参与**加载期任何校验（既不检查目标表是否
   已加载、也不检查记录是否存在）——纯粹是传达给内容工具的提示，不改变第 29 条现象描述的分层
   边界（不能声明为 `Reference` 的原因不变）。登记种类限制（仅 `Id`/`IdList` 可设）由 `SchemaAudit`
   新检查项 `soft_reference_kind` 事后报告（同 `field_range_kind`/`field_map_kind` 既有风格，
   不在 `WithSoftReference` 挂载时检查）。
2. **`toolchain/validator --list-tables --json` 导出**：`field_meta` 新增 `soft_reference_
   table`/`soft_reference_domain`（未登记均为 `null`）。
3. **`creature.template` 四个已确认目标表的字段完成登记**：

   | 字段 | 软引用目标 |
   |---|---|
   | `ai_rotation_ref` | 表 `ai.rotation` |
   | `ai_behavior_ref` | 表 `ai.behavior_profile` |
   | `loot_table_ref` | 表 `loot.table` |
   | `display_ref` | 表 `display.map` |

4. **全仓走查**（`grep -rn '_ref"' core/*/*/*/*Schemas.cs` 及各表数据表 schema 目录）：凡是
   登记为 `FieldKind.Id`/`FieldKind.IdList` 且无 `ReferenceTable`/`ReferenceDomain`、且字段自身
   `Description`/相邻判断记录已明确点名具体目标表（或按全仓一致的字段命名惯例可确凿推定）的，
   一并补登软引用，逐条核实目标表名确实存在于对应模块的 `*Schemas.cs`。清单见下节；未列入清单的
   `_ref` 字段（如 `item.stat_roll_ref`"指向未来的随机属性生成规则表，本版不展开"、
   `dialog.speaker_ref`"指向 creature.template 或占位角色 id"二选一、`spawn.table.content_ref`
   "指向 creature.template 或 gobj.template"二选一、`quest.escort_route_ref`"04 §2.2 域名清单
   无对应登记表"）均因"无单一确定目标表"或"目标表尚不存在"未登记，避免用软引用元数据误导内容
   工具。
5. **`on_hit_reaction_ref`/`on_death_reaction_ref` 结论：预留字段，无消费方、无目标表**：

   ```
   grep -rn "OnHitReactionRef|OnDeathReactionRef|on_hit_reaction_ref|on_death_reaction_ref" \
     --include=*.cs .
   ```

   （排除另一会话的 `.claude/worktrees/` 工作树）只命中 `CreatureTemplate.cs` 自身的属性声明/
   赋值与 `CreatureSchemas.cs`/07 文档——`core`/`presentation`/`adapters`/`games` 范围内没有任何
   代码读取这两个属性，63 张已登记表里也没有承载"受击/死亡反应配置"的表。判定为"预留字段、当前
   无目标表与消费方，填写不生效"：`CreatureSchemas.cs` 两字段 `Description` 补充说明，不登记
   `WithSoftReference`（登记会给内容工具一个不存在的自动补全目标，比"什么都不给"更误导）；07
   文档字段表两行标注"预留"；`落地方案与分阶段计划.md`"能力边界与未默认接入能力索引"表新增一行
   （分类"未提供"）。

不准确的自动补全目标，不产生数据层面的风险，已在两处字段 `Description` 内注明"按惯例推定"。若
后续确认有误，直接改 `WithSoftReference` 参数即可，不涉及任何数据迁移。

## 对消费方提示

- `toolchain/validator --list-tables --json` 的 `field_meta` 新增三个键：`allowed_values`
  （已登记 `AllowedValues` 的字段，有序固定取值字符串数组；未登记为 `null`）、
  `soft_reference_table`/`soft_reference_domain`（已登记软引用的字段；未登记均为 `null`）。
  三者均为纯新增字段，追加在既有键之后，对不消费这三个新键的既有调用方逐字节兼容。
- `creature.template.npc_flags` 的合法取值现固定为六个 `npc_flag.<name>` 字符串（见上表），
  建议编辑器据 `field_meta.allowed_values` 渲染复选框/下拉，不再自行硬编码这份清单——本框架若
  未来新增职能标志（走审批），`allowed_values` 会自动同步，不需要编辑器代码改动。
- `field_meta.soft_reference_table`/`soft_reference_domain` **不代表该字段的值一定存在于目标
  表**——软引用不参与任何加载期校验，编辑器据此做自动补全/跳转是合适的用法，但不应该用它做"值
  是否合法"的判断（那仍需另行调用 `toolchain/validator`/`validate_data.py` 的加载期校验）。
- `on_hit_reaction_ref`/`on_death_reaction_ref` 目前填什么都不会生效，建议编辑器在这两个字段的
  表单控件上加一个"预留，暂无效果"的提示，避免内容作者误以为填了就有反应效果。
