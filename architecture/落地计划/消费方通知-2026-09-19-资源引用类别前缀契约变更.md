# 消费方变更通知（内容编辑器项目，资源引用类别前缀契约变更，2026-09-19）

> 本文档允许出现具体技术名（引擎/语言/框架/工具名），不受 `architecture/00～14` 与
> `architecture/adr/` 正文的禁用词约束（见仓库根 `CLAUDE.md`"硬性规则"）。本文档是主动的**变更
> 通知**（不是回复某一条具体反馈编号），面向下游"内容编辑器"项目（仓库 `ws-game-editor`）——
> 通知资源引用类别前缀契约的破坏性变更、给出迁移指引，并回应消费方反馈第 65 条曾提出的"编辑器
> 侧如何按资源引用字符串本身解析出预览路径"这一诉求（见
> [消费方反馈-2026-09-18-编辑器-第62-66条.md](消费方反馈-2026-09-18-编辑器-第62-66条.md)"待设计层
> 确认"第 1 项）。关联决策：[ADR-0038](../adr/0038-资源引用类别前缀唯一决定路径空间.md)/
> [ADR-0039](../adr/0039-内容数据schema破坏性变更政策.md)。

**结论先行**：`display.anim_set.clips.resource_ref`/`display.weapon_style.auto_attack_anim`/
`cast_anim_override`/`display.equip_visual.mesh_ref` 四个字段此前存在的"同一类别前缀按消费方
不同落在不同路径空间"的架构缺陷已消除——每个类别前缀现在唯一对应一个路径空间与推导方法，编辑器
可以只凭资源引用字符串本身（不需要先弄清楚"这一行被哪种类型的实体消费"）判断如何预览/展示它。
样例数据已完成迁移，`RefCategoryFieldRule` 已转正为无条件校验规则。**尚未做的两项**：引擎适配层
仍未改为调用本次契约面新增的路由入口（两侧实现目前逐字节一致，行为不受影响）；sprite 型"按
消费实体行 id 末段命名"的隐式接线约定仍未改为显式引用字段。

## 1. 契约变更说明

[ADR-0025](../adr/0025-资源引用标识到资产相对路径的约定纳入公开契约.md) 确立的"资源引用标识 → 相对
路径"约定本意是"类别前缀唯一决定路径空间"，但 `display.anim_set.clips.resource_ref`/
`display.weapon_style.auto_attack_anim`/`cast_anim_override`/`display.equip_visual.mesh_ref`
四个字段此前是仅存的例外：同一个 `anim.*`/`sprite.*` 字符串，按运行期消费实体是 sprite 型还是
model 型，走两条不同的加载规则，解释成两种不同的资源（“同一字符串两种路径空间解释”的架构性
风险）。ADR-0038 决策 1 把这一例外消除，办法是新增两个独立类别前缀（`sprite_anim`/`paperdoll`），
让 sprite 型消费与 model 型消费从此使用**不同的字符串**，字符串本身即可区分路径空间。

本次任务（数据迁移）把 `data/_sample` 里实际按 sprite 型消费的样例数据行迁移到新前缀，并把
`RefCategoryFieldRule`（校验类别前缀合法性 + 落在字段允许集合内）从默认关闭转正为无条件生效。

## 2. 8 类前缀 → 路径空间对照表

| 前缀 | 路径空间 | 相对路径/逻辑路径形态 | 能否做资产存在性检查 | 推导方法（C#／Python） |
|---|---|---|---|---|
| `sprite` | 资产根相对 | `sprites/<category>_<name>`（目录，含逐方向/层文件） | 能 | `SpriteSetDirectory` / `sprite_set_directory` |
| `icon` | 资产根相对 | `icons/<category>/<name>.png`（文件） | 能 | `IconFile` / `icon_file` |
| `vfx` | 资产根相对 | `vfx/<去前缀>`（目录，含 `atlas.png`+`frames.json`） | 能 | `VfxResourceDir` / `vfx_resource_dir` |
| `sfx` | 资产根相对 | `sfx/<去前缀>.wav`（文件） | 能 | `SfxResourceFile` / `sfx_resource_file` |
| `sprite_anim`（新增） | 资产根相对 | `sprite_anim/<去前缀>`（目录，含 `atlas.png`+`frames.json`，结构同 `vfx`） | 能 | `SpriteAnimDir` / `sprite_anim_dir` |
| `paperdoll`（新增） | 资产根相对 | `paperdoll/<去前缀>.png`（扁平文件） | 能 | `PaperdollLayerFile` / `paperdoll_layer_file` |
| `anim` | 引擎侧逻辑路径 | `GameFoundation/anim_clips/<去前缀>`（不含扩展名，不在资产根目录下） | **不能**（不是磁盘资产根内的文件，见下） | `AnimClipLogicalPath` / `anim_clip_logical_path` |
| `model` | 引擎侧逻辑路径 | `GameFoundation/models/<去前缀>`（不含扩展名，不在资产根目录下） | **不能** | `ModelLogicalPath` / `model_logical_path` |

"资产根相对"路径可以直接与内容工具 `--assets-root`（默认仓库 `assets/`）拼接后做文件系统存在性
检查（`toolchain/asset_import/check_cmd.py` 的 `sprite`/`vfx`/`sfx`/`display_anim` 域都是这样做
的）。"引擎侧逻辑路径"是引擎适配层内部一个独立、非按数据集分区的资源目录树，不落在资产导入工具
的资产根目录下（同 [ADR-0037](../adr/0037-资源引用路径推导契约扩展到vfx-sfx-model-anim_set.md)
决策 3），编辑器不应该把这两类值拼进 `assets/<dataset>/` 尝试查找文件——查不到不代表数据非法，
只代表这类资源需要经引擎适配层自己的资源管线才能定位。

## 3. 逐字段迁移指引

| 字段 | 何时用 `anim`/`model`（引擎侧逻辑路径） | 何时用 `sprite_anim`/`paperdoll`（资产根相对） |
|---|---|---|
| `display.anim_set.clips.<clip>.resource_ref` | 该 `display.anim_set` 行被某个 `kind=model` 的 `display.map` 行经 `anim_set_ref` 显式引用时，用 `anim.<name>` | 该 `display.anim_set` 行被某个 `kind=sprite` 的 `display.map` 行按"行 id 末段命名"隐式接线消费时，用 `sprite_anim.<name>` |
| `display.weapon_style.auto_attack_anim`/`cast_anim_override.<skill_id>` | 该武器风格实际被 model 型角色的攻击/施法状态切换消费时，用 `anim.<name>`（**不是**看武器自己的 `display.map` 行 `kind`——武器自身的外观 `kind` 与"谁在攻击/施法时触发这条剪辑"是两件独立的事，见下方"重要澄清"） | 该武器风格实际被 sprite 型角色消费时，用 `sprite_anim.<name>` |
| `display.equip_visual.mesh_ref` | `mode: socket_attach`/`mode: slot_mesh` 且实际经 `ModelCharacterRig.ApplyEquipVisual` 消费（model 型角色装备该外观）时，用 `model.<name>` | `mode: slot_mesh` 且实际经 sprite 型角色的纸娃娃层覆盖消费时，用 `paperdoll.<category>.<name>`（**不是** `sprite.<category>.<name>`，见下一节） |

**重要澄清（本次迁移期实测发现，供编辑器侧同样避坑）**：判断一个 `display.weapon_style`/
`display.equip_visual` 行该用哪一类前缀，正确做法是**核实这条武器/装备实际被哪种角色消费**（看
运行期真的会装备/使用它的角色是 sprite 型还是 model 型），**不是看武器/装备物品自己的
`display.map` 行的 `kind`**——物品自己的 `kind` 只决定这件物品作为地面掉落物/图标时怎么画，与
"谁装备了它、触发动作剪辑时按哪条规则解释剪辑引用"是两个独立的问题。样例数据里
`display.weapon_style.sample_model_sword` 就是一个真实的反例：该武器自己的 `display.map` 行
`kind=sprite`（图标按 sprite 规则画），但它挂接的 `display.equip_visual.sample_model_sword`
用的是 `mode: socket_attach`+`model_ref`（这个模式只有 model 型角色的装备外观流程会处理），实测
（`adapters/unity/.../Tests/Runtime/ModelIntegrationTests.cs`）也确认它被 model 型角色
`creature.sample_model_hero` 装备并触发攻击动画——因此它的 `auto_attack_anim`/
`cast_anim_override` 保持 `anim.*` 不变，没有迁移。若编辑器侧有类似的"猜测消费类型"逻辑，建议
同样以实际消费路径（或后续 ADR-0038 决策 8 落地后的显式引用字段）为准，不要只看物品自己的
`display.map.kind`。

## 4. 新公开路由入口怎么用（回应第 65 条"编辑器如何按资源引用字符串本身解析预览路径"）

框架新增了一个总入口：

- C#：`Core.Foundation.EngineAdapter.AssetRefConventions.ResolvePathSpace(Id resourceRefId)` →
  `(AssetRefPathSpace Space, string RelativePath)`
- Python：`toolchain.asset_import.ref_conventions.resolve_path_space(resource_ref_id: str)` →
  `(AssetRefPathSpace, str)`

输入任意合法的资源引用标识（如 `"sprite_anim.sample_hero_idle"`），内部按第一个点分段（类别
前缀）唯一分派到本文档第 2 节表格对应的推导方法，返回"路径空间"枚举（`AssetRootRelative`/
`EngineLogicalPath`）与相对路径字符串。遇到未登记的类别前缀，或标识不含点号（无法取出类别
前缀），两侧实现均抛异常（C# `ArgumentException`／Python `ValueError`），消息含收到的前缀与
合法前缀全集，不做静默兜底。

**编辑器侧建议的预览解析入口**（框架不提供编辑器专属 API，以下是给消费方的实现建议，命名可自定，
下文用 `DisplayPreviewPathResolver` 指代这一类封装）：

```
function ResolvePreviewAsset(resourceRefId, assetsRoot, dataset):
    (space, relativePath) = ResolvePathSpace(resourceRefId)
    if space == AssetRootRelative:
        fullPath = join(assetsRoot, dataset, relativePath)
        if space 对应的类别前缀是 sprite_anim/vfx:
            展示 fullPath 下的 atlas.png + frames.json 序列帧预览
        elif 类别前缀是 sprite/icon/paperdoll/sfx:
            展示 fullPath 本身（图片/音频）
        return 是否存在 fullPath（可复用 check_cmd.py display_anim 域同一套存在性判断）
    else:  # EngineLogicalPath
        提示"该资源由引擎适配层管理，编辑器内无法直接预览，需在具体引擎里查看该逻辑路径"
        return 不可预览，但不应报错/标红为数据非法
```

这样编辑器只需要调用一次 `ResolvePathSpace`，不再需要先反查"这一行被哪种类型的实体消费"再决定
走哪条预览逻辑——这正是 ADR-0038 决策 1 的总原则（类别前缀唯一决定路径空间）在编辑器侧的直接
收益。

## 5. `paperdoll` 前缀为何独立于 `sprite`

`display.equip_visual.mesh_ref` 的 sprite 型取值此前直接把原始值当"纸娃娃层资源 id"使用
（`presentation/render/core/SpriteViewBase.cs HandleItemEquipped`：`_equipOverridesBySlot[slot]
= (layerName, def.MeshRef.Value)`，不经任何路径推导函数中转，运行期按单个扁平文件解析，不按
方向档位展开）。这与 `sprite` 前缀既有承载的"精灵集目录标识"（`SpriteSetDirectory`：产出一个
目录，内部再按方向档位/层名展开为多个文件）语义**不等价**——一个是单文件、一个是多文件目录。
按 ADR-0038 决策 1 总原则（同一前缀不能承载两种不同语义/路径空间），新增独立前缀 `paperdoll`
承载"纸娃娃层资源 id"这一单文件语义，`sprite` 前缀继续专属"精灵集目录标识"。两者互不干扰，编辑器
按前缀即可区分该按目录逻辑还是按单文件逻辑处理。

## 6. 编辑器侧需要做什么

1. 按第 2 节表格更新任何硬编码的"资源引用前缀 → 路径"映射逻辑，新增对 `sprite_anim`/`paperdoll`
   两个前缀的识别与预览支持。
2. 若编辑器已经实现了"猜测某一行该按 sprite 还是 model 规则解释资源引用"的逻辑，改为直接读取
   资源引用字符串的类别前缀（不再需要猜），可大幅简化该逻辑或直接删除。
3. 若编辑器要展示"数据是否合法"的红字提示，`field_ref_category`（`RefCategoryFieldRule`）现已
   无条件生效，会对类别前缀不合法/不在字段允许集合内的取值统一报错，编辑器侧不需要重复实现这层
   校验，可以直接透传该检查名的诊断文本。
4. 参考第 4 节实现（或复用）预览路径解析逻辑，替换掉此前只能反查消费类型才能预览的旧逻辑。

## 7. 哪些还没做

1. **引擎适配层尚未改为调用本次新增的路由入口**：`UnityResourceLoader`/`SpriteViewBase` 等实现
   仍是各自内联的路径推导逻辑，尚未改为转发 `AssetRefConventions.ResolvePathSpace` 及其分派的
   六个既有方法与两个新方法。两侧实现目前逐字节一致，行为不受影响，只是存在"未来需要同步维护两份
   拷贝"的风险，列为后续任务（ADR-0038 决策 8 第二项）。
2. **sprite 型"按消费实体行 id 末段命名"的隐式接线约定尚未改为显式引用字段**：
   `display.anim_set` 行与 sprite 型 `display.map` 行之间目前仍靠"id 末段相同"的命名约定隐式
   接线（`UnityViewFactory.TryResolveAnimSet`），不是数据里的一个显式字段（如
   `anim_set_ref`）。ADR-0038 决策 8 第一项已把这一项列为后续项，本次数据迁移只是把隐式接线
   推导出的资源引用值改用了新前缀，接线方式本身未变。编辑器侧若要展示"这个 `display.map` 行的
   动画帧动画从哪张 `display.anim_set` 表来"，目前仍需自行按同一条命名约定反查（`"display.
   anim_set." + display.map 行 id 的最后一段`），framework 尚未提供显式字段替代这一猜测。
