## 现象与复现

消费方反馈：`DataRegistry.RunValidationAndBuildReport` 对每条 `IValidationRule.Validate()` 的
执行没有任何 try/catch 隔离，单条规则抛异常就击穿整个 `LoadAll`，进程以 `0xE0434352`（.NET
"未捕获托管异常"标准终止码）终止，不产出校验报告。给出两条独立复现路径，均对
`item/item.budget_curve.json` 记录 `item.budget.default` 的 `entries` 字段注入：

- **路径一**：`entries[0].x` 由数值改成字符串（元素仍是合法的 `{x, y}` 对象，只是值类型不对）——
  异常来自规则自身业务解析代码 `Core.Carriers.Item.ItemBudgetCurve.ParseCurve`
  （`System.ArgumentException`，消息"entries 元素缺少 x/y（或 v1 的 item_level/budget）"）。
- **路径二**：`entries` 整个字段由数组替换成 JSON 对象（结构不合法，不再是数组）——异常来自框架
  严格访问器 `Core.Foundation.DataRegistry.DataRecord.GetArray`
  （`Core.Foundation.DataRegistry.DataFieldException`，消息"期望 Array，实际 Object"）。

两条路径的调用栈从 `ItemBudgetValidationRule.Validate` 往上完全一致：
`Validate+MoveNext() → RunValidationAndBuildReport → LoadAllCore → LoadAll`。

**本仓库复现确认（改动前，用真实数据根 + `toolchain/validator`）**：以 `data/_sample` 为基础，
把 `item/item.budget_curve.json` 分别改成路径一/路径二的形态，`dotnet run --project
toolchain/validator -- --data-root data/_framework --data-root data/_sample` 均以
`Unhandled exception` 崩溃，进程退出码均为 **`-532462766`**（即 `0xE0434352` 的有符号 32 位
表示，与消费方原文完全一致），栈顶为 `ItemBudgetCurve.ParseCurve`，逐帧与消费方原文栈完全一致，
不产出任何报告。两条路径均复现，与消费方陈述一致（详见下方"事实核查"）。

## 根因

`RunValidationAndBuildReport` 对 `foreach (var rule in _rules)` 内 `rule.Validate(this)` 的
调用不做任何 try/catch。`IValidationRule.Validate` 的公开签名是
`IEnumerable<ValidationIssue>`，几乎所有实现（含本条两条路径涉及的 `ItemBudgetValidationRule`，
以及同批命中的 `ItemTemplateAffixShareExceedsBudgetRule`/`ItemGrantValueExceedsShareRule`，
见下方"事实核查"）是编译器生成的惰性迭代器：调用 `Validate(this)` 本身不执行任何规则代码，
真正的规则逻辑与异常都发生在**枚举期**（`GetEnumerator` 之后每次 `MoveNext`）。异常一旦在枚举期
抛出，会一路冒出 `RunValidationAndBuildReport → LoadAllCore → LoadAll`，独立进程表现为未捕获
异常崩溃退出。

**补充根因细节（本仓库勘察发现，消费方原文未提及）**：两条路径注入的畸形 `entries` 其实都会被
`RunFieldValidation`（字段级校验，先于规则 foreach 执行）正确拦下并报出 `field_type`
诊断——本仓库用真实 `Core.Carriers.Item.ItemSchemas.BudgetCurve` schema 实测确认两条路径均有
此诊断。但 `field_type` 只是往报告的问题列表里追加一条诊断，不会把这条记录从"逐条已注册规则
再跑一遍"的候选池里剔除；`RunFieldValidation` 与规则 foreach 是互不知会的两道独立通道，
`ItemBudgetCurve.ParseCurve` 之类的规则级解析代码不查字段级是否已经报过问题，照样对同一份原始
JSON 值再解析一次，仍会抛出。这是"字段级诊断齐全、规则执行期仍会崩溃"的真正原因，也是必须在
规则执行这一级单独隔离（而不是止步于"字段级已经报错了"）的理由。

## 处理

**隔离实现**：`RunValidationAndBuildReport` 的规则 foreach 循环体改为逐条规则包一层
try/catch，且**包住整个 `foreach (var issue in rule.Validate(this))` 语句**，不是只包
`rule.Validate(this)` 这一次调用——只包一次调用的写法接不住任何异常（迭代器方法调用本身不执行
代码），已用两条回归测试反向验证（见下方"验收证据"）。

```csharp
foreach (var rule in _rules)
{
    var ruleId = ResolveRuleId(rule);
    var hits = 0;
    try
    {
        foreach (var issue in rule.Validate(this))
        {
            issues.Add(issue.RuleId == null ? issue.WithRuleId(ruleId) : issue);
            hits++;
        }
    }
    catch (Exception ex)
    {
        issues.Add(BuildRuleExecutionFailedIssue(ruleId, ex));
        hits++;
    }
    ruleSummaries.Add(new ValidationRuleSummary(ruleId, rule.DefaultSeverity, rule.NonEscalatable, hits));
}
```

**设计要点**（均按设计层拍板落地）：

1. **隔离粒度=单条规则**：catch 到异常后继续处理下一条规则（不 return/rethrow），其余规则照常
   跑完、各自产出自己的问题。
2. **新检查名 `rule_execution_failed`，Error 级（不是 Warning）**：规则没跑完意味着报告本该
   由它产出的那部分结论缺失，不能让消费方误以为"没报错=通过"（AGENTS.md 第 3 节"不静默降级"）。
3. **issue 定位信息**：`Message` 固定包含规则名、异常类型名（`ex.GetType().Name`）、异常消息
   三项；异常若是 `DataFieldException`（框架严格访问器抛出，天然带 `Table`/`RecordKey`/
   `Field`），顺手带上定位到具体表/记录/字段（路径二命中此分支）；其它异常类型没有通用途径拿到
   这些定位信息（不为此改动 `IValidationRule.Validate` 接口签名新增出参），`ValidationIssue
   .Table`（构造函数要求非空）退化为规则自身的 `RuleId`——不代表真的存在这样一张表，读者据
   `Check == "rule_execution_failed"` 即可识别（路径一命中此分支）。
4. **异常前已产出的问题保留**：try 块内逐条 `issues.Add`，不是攒批提交，异常发生时已经 `Add`
   过的问题不会被这次 catch 撤销。
5. **严格访问器契约不变**：`DataRecord.GetArray` 等"类型不符即抛"的行为保持原样，本次只在
   "跑全部规则产出报告"这一级做隔离。

**ADR 判断（设计层拍板，理由如下）**：本条**不需要新出 ADR**。

- 这是修复"框架应当隔离单条规则执行期异常"的健壮性缺陷，不是改变已记录的架构结论——
  `architecture/04_数据与内容管线.md` 第 4 节"reload 验收线"第 5 条本就已经写明"内容校验入口对
  任何不满足预期形状的输入……必须产出可定位的校验报告项，不能任由内部实现抛出未被捕获的异常向上
  冒泡"，本次改动是把既有架构结论真正落实到 `RunValidationAndBuildReport` 这一处此前的遗留缺口，
  不是新拍板一条结论；按 `architecture/12_扩展与变更流程.md` 第 1/2 节，这既不属于"新增内容"也不
  属于"新增原语"，不进入 ADR 审批流程。
- **新增检查名 `rule_execution_failed` 是否受 ADR-0039"新增无条件 Error 级校验规则视同破坏性
  变更"政策管辖：不受管辖。** ADR-0039 该条款的适用前提是"此前满足旧规则但不满足新规则的既有
  数据会首次报错"（数据不变、规则变了、结果从"通过"变成"报错"）。本条恰恰相反：`rule_execution
  _failed` 只在某条规则**执行期抛出异常**时才会出现，而"执行期抛出异常"这件事在改动前的后果是
  **整个 `LoadAll` 崩溃、进程以 CLR 崩溃码终止、连报告都产出不了**——不存在"改动前这份数据能拿到
  一份不含错误的报告、改动后同一份数据首次报错"这种情形；改动前会让这份数据崩溃的，改动后仍然是
  "阻断"（`report.IsBlocking = true`），只是从"进程崩溃、无报告"变成"报告里多一条 Error"，是
  纯粹的健壮性提升，不存在此前被判定"通过"的数据现在被判定"不通过"。同理，本条也不落入 ADR-0039
  决策 2 定义的"破坏性变更"三类（新增必填字段/改字段名/改字段语义/改资源引用取值约定/删字段）
  任何一类——没有触碰任何数据 schema 定义。
- 沿用消费方反馈第 47 条的既有先例：`field_id_format`/`skill_budget_record_unparseable`/
  `item_grant_value_unparseable` 三个新检查名当时也只是补 CHANGELOG + 消费方反馈回复文档，未走
  ADR。

**新检查名登记**：本仓库新检查名走"README 检查名清单表 + CHANGELOG `[Unreleased]` + 消费方反馈
回复文档"这一既有惯例（同 `expr_validation_error`/`field_id_format` 等既有框架级检查名的登记
方式），不是走仓库唯一的"结构化诊断/稳定 check 名"清单（`toolchain/validator --json`/
`check_cmd.py check --json` 两条命令行出口本就把 `Check` 字段透传，不需要在别处单独登记一份
清单）；已在 `core/foundation/data_registry/README.md`"校验项检查名"表新增一行、并新增"单条
规则执行期异常隔离"小节记录完整判断记录。

**同类未隔离的执行点扫描**：全仓库搜索"遍历规则/插件并调用外部实现"的同类模式
（`foreach.*rule/analyzer/plugin`、`IValidationRule`/`IExprSchema` 等扩展点接口的调用点），
发现：

- `ValidateExprField` 已有兜底（`expr_validation_error`，第十八方深度审核 F-03 落地，早于本次）。
- `DataRegistry` 内部 `LoadOneTablePartial`（信封解析阶段）对 `SchemaMigrator.MigrateRow`
  （表结构版本迁移，各内容模块随 `TableSchema` 自行注册迁移函数）的调用**同样没有 try/catch**——
  语义上与 `IValidationRule` 同属"框架遍历、调用各模块自行提供的实现"，若某个模块的迁移函数对
  不满足预期形状的输入抛出未预期异常，会同样击穿整个 `LoadAll`。**本次未修**，留给后续单独处理。
  **更新（2026-09-19，后续单独任务已落地）**：已根治，未采用与本条相同的"记一条 issue 后仍照常
  收录"口径——设计层拍板：迁移跑挂意味着该行根本没能迁到目标 schema_version，属于"这一行数据不
  可用"而不是"报告缺一部分结论"，处理方式改为**整行剔除**（不进入加载结果，不以任何半迁移状态
  留在注册表），新增检查名 `row_migration_failed`（Error 级、阻断），并在消息中点明"下游
  `reference_integrity` 等错误可能系连带产生"。详见
  `core/foundation/data_registry/README.md`"单行迁移执行期异常隔离"一节判断记录、
  `CHANGELOG.md` `[Unreleased]`"`SchemaMigrator.MigrateRow` 单行迁移执行期异常隔离"条目。
- 其余 `foreach (var rule in rules)` 命中点（`core/carriers/item/tests/TestSupport.cs` 等）均为
  测试夹具里的"注册规则"循环（调用 `RegisterValidationRule`），不是执行循环，不在此列；
  `presentation/feedback_binder`（运行期反馈/VFX 绑定规则）不是 `IValidationRule` 扩展点，数据
  校验期发生在规则解析阶段（`FeedbackRule.FromRecord`），执行期只消费已校验通过的声明式数据，
  不属于同类风险。
