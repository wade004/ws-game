## 第 38 条：`quest.def.prerequisite` 前置链循环检测

### 复现（改造前）

真实 `Presentation.Assembly.ContentValidationAssembly.Run` 默认参数装配下，构造两个任务：

```json
{"id": "quest.a", ..., "prerequisite": "quest.is_completed(quest.b)", ...}
{"id": "quest.b", ..., "prerequisite": "quest.is_completed(quest.a)", ...}
```

`run.Report.ErrorCount == 0`——`prerequisite` 登记为 `FieldKind.Expr`，`DataRegistry` 内置的
`expr_parsable` 检查只验证表达式本身语法是否合法（两条表达式单独看都合法），
`QuestContentValidationRule.Validate` 全文没有解析 `prerequisite` 里 `quest.*` 引用、构图找环的
代码路径（仅 `ValidateObjectives`/`ValidateRewards` 两个业务判断方法）。复现测试固化在
`core/gameplay/quest/tests/E38_QuestPrerequisiteCycleTests.cs` 顶部判断记录（不单独保留改造前
状态的测试，因为该测试文件是在实现修复后新增的；改造前的复现过程见本节描述与任务执行记录）。

### 根因

`prerequisite` 只有"表达式语法可解析"一层结构性校验，缺"表达式里引用的其它任务是否存在""引用
关系是否成环"两层业务判断——04 第 8 节"新任务"表格行早就在"跑哪些校验"列写了"循环引用检测
（前置链）"，但从未有对应实现落地，属于文档承诺与实现之间的历史缺口（不是本次改动引入的实现
错误，是此前遗漏的功能未落地）。

### 处理

`core/gameplay/quest/core/QuestContentValidationRule.cs`：

1. **构造函数起真正使用 `exprSchema` 参数**：此前该参数只保留构造签名兼容（`_ = exprSchema;`），
   本次起持有为 `_exprSchema`，未提供时退回 `QuestExprSchemaEntries.BuildParsingSchema()`（保证
   `new QuestContentValidationRule()` 无参构造仍可用，不依赖调用方一定传入）。
2. **新增 `ValidatePrerequisiteGraph`**：对全表 `quest.def` 记录，逐条 `prerequisite` 文本用
   `ExprParser.Parse(text, _exprSchema)` 重新解析成 AST；语法本身不可解析
   （`ExprParseException`）时跳过该记录（已由 `expr_parsable` 报告，不重复、不在损坏语法树上
   继续构图）。递归遍历 AST（`CollectQuestIdLiteralArgs`），收集全部 `quest.*` 引用
   （`ExprReferenceNode.Group == "quest"`，不限定具体 key）参数里的 `ExprLiteralNode`（Id 种类）
   字面量，构成"任务 → 前置任务"有向边。
3. **`quest_prerequisite_unknown`**（阻断级）：边的目标 id 不在本表已知 id 集合内时报告，
   `Field = "prerequisite"`，消息附带该字面量在源文本里的位置（复用 `ExprNode.Start`/`Length`，
   `ExprIssue` 同款"位置 X，长度 Y"格式）；该条边不参与后续成环检测。
4. **`quest_prerequisite_cycle`**（阻断级）：对已知节点构成的图跑三色标记 DFS（算法与
   `DialogContentValidationRule.story_tree_cycle` 同款，`TryFindCycle`/`Visit` 两个私有方法直接
   照抄该规则的结构，只是节点/边来源不同），自环（任务在自身 `prerequisite` 里直接引用自己）
   按同一套算法自然判定为环，不需要特判；只报告首个发现的环，`RecordKey` 取环路径第一个节点、
   `Field = "prerequisite"`，消息含完整环路径（如 `quest.a -> quest.b -> quest.a`）。

### 测试

`core/gameplay/quest/tests/E38_QuestPrerequisiteCycleTests.cs`（7 例，均经正式
`ContentValidationAssembly.Run` 默认参数装配，不是手工拼 `DataRegistry`）：

既有 `QuestSchemaCoverageTests`/`QuestHostTests` 等既有 quest 测试用例全部不变（无需修改，回归

### 消费方排查结论（原文，2026-09-13 现场核实）


`script` 效果 `hook_id` 子字段）。核心发现：

- **`found.hook` 早已有实现级 `TableSchema` 登记**——`core/foundation/hook_registry/schema/
  FoundHookSchema.cs`（`Table` 字段：`id`/`signature`/`description`/`allow_multiple`，
  `SchemaLayer.Foundation`），由 `core/rules/assembly/RulesSchemaCatalog.cs:90`
  （`RegisterL0Schemas`）注册进真实默认装配——这条注册链正是 04 变更记录 2026-09-05 行"两表已于
  收边 I1 完成登记并落入框架级数据目录"所指的落地；`data/_framework/found/found.hook.json` 已有

  `DialogHost` 进入剧情节点、`AreaTriggerHost` 触发脚本类型区域，均按 id 调用注册表分发回调。
- **反馈原文复现步骤的目录遗漏**：`grep -rln "TableSchema" core/foundation/app_lifecycle/ |
  xargs grep -l "found.hook"` 只在 `core/foundation/app_lifecycle/` 目录内查找，`found.hook` 的
  真实登记文件在 `core/foundation/hook_registry/schema/`——不同目录，该 grep 天然找不到，
  `Registry.GetSchema("found.hook")` 在真实默认装配下实际返回非空 schema，不是 `null`。
- **真正的空白**：`dialog.story_tree.nodes[].performance_hook_ref`/`dialog.gossip_menu.
  options[].actions[]{kind=script}.ref`/`encounter.def.phases[].on_enter_hook`（反馈原文点名
  三处）与全仓排查另外发现的 `skill.def.effects[]{kind=script}.params.hook_id`/`area.trigger_def.
  params{trigger_type=script}.hook_id`（同根因第四、五处症状）五处字段的判断记录仍写"found.hook
  当前无实现级 schema 登记"——这是代码注释未随 `FoundHookSchema` 收边 I1 落地同步更新的历史
  遗留，字段种类本身仍是 `FieldKind.Id`（未升级），也没有任何软引用元数据。

### 采取的分支

**分支 A（存在真实消费方，`TableSchema` 已完整登记）**：不新建/不改动 `FoundHookSchema.Table`
本身（`id`/`signature`/`description`/`allow_multiple` 四字段已准确对应 `HookRegistry.

这类猜测性形状——按"按其实际消费字段登记"的原则，不强行套用与真实消费代码不符的 `kind`/`params`

`FieldKind.Reference`**：`found.hook` 是运行时按 id 分发的挂载点注册表，内容作者可能调用的具体
