## 现象复现与根因

- **现象**：`LootHost` 只提供 `Roll(tableId, context): IReadOnlyList<ItemStack>` 这一个"抽一次
  给我结果"的黑箱接口（`core/gameplay/loot/contracts/ILootHost.cs`），`LootTableDef`（`core/
  gameplay/loot/contracts/LootTableDef.cs`）只是数据结构（`LootGroup`/`LootEntry` 的强类型视图），
  不提供任何计算方法。内容编辑器"掉落与爆率编辑器"（`editor/docs/编辑器产品文档.md` 第 5.5.4 节）
  需要在策划编辑掉落表结构的同时实时展示"这条会不会掉、大概掉多少"，但嵌套表（`loot.*` 引用整体
  再抽取 `count` 次）、条件（`Expr`，依赖运行期上下文）、`weighted_pick_one` 多抽不放回、
  `guaranteed_min` 保底补抽这几类结构的期望概率没有闭式公式可以让编辑器侧简单复算——唯二选择是
  照抄 `LootHost` 私有算法在编辑器侧重新实现一遍（存在漂移风险：框架抽取语义调整后编辑器侧的复刻
  实现不会自动同步），或者用蒙特卡洛模拟逼近（编辑器现状方案，第 5.5.4 节"模拟面板"，需要用户
  手动指定次数/种子、等模拟跑完才能看到结果，不是实时反馈）。
- **根因**：`LootHost.RollTableInto`/`RollChanceEachGroup`/`RollWeightedGroup`/`PickWeighted`
  几个私有方法把"条件筛选""权重归一化""按随机阈值选中一条"这几个与随机数消耗本身无关的纯计算
  步骤，同"实际消耗 `IRngHost` 采样"耦合在一起，没有任何可独立调用、不消耗随机数的入口能只做
  "给定权重/条件，算出理论概率"这件事。

## 处理

### 第一步：抽取核心纯步骤收口（`core/gameplay/loot/core/LootRollCore.cs`，`internal`）

把以下步骤原样（不改变任何一步的浮点运算顺序）从 `LootHost` 私有方法体搬出：

| `LootRollCore` 成员 | 对应原 `LootHost` 私有实现 |
|---|---|
| `Clamp01(double)` | `LootHost.Clamp01` |
| `ConditionPasses(LootEntry, IExprHost, IExprDiagnostics)` | `LootHost.ConditionPasses` |
| `FilterEligible(IEnumerable<LootEntry>, IExprHost, IExprDiagnostics)` | `RollWeightedGroup`/保底候选池构建里内联的过滤循环 |
| `TotalWeight(IReadOnlyList<LootEntry>)` | `PickWeighted` 局部变量 `totalWeight = pool.Sum(...)` |
| `SelectByThreshold(IReadOnlyList<LootEntry>, double totalWeight, double thresholdFraction)` | `PickWeighted` 消耗 `IRngHost.Next` 之后的累加权重选中逻辑（阈值本身由调用方 `LootHost` 算好传入，本函数不消耗随机数） |
| `EffectiveChanceEach(double weightOrChance, double multiplier)` | `RollChanceEachGroup` 局部变量 `baseChance` |
| `ApplyPseudoRandomStep(double baseChance, int missStreak, double step)` | `RollChanceEachGroup` 局部变量 `effectiveChance` |
| `ExpectedCount(LootEntry)` | 新增（`LootHost.RollCount` 消耗的 `IRngHost.NextInt` 是闭区间均匀分布，`(min+max)/2`；`LootHost` 本身不需要期望值，只有 `LootTableAnalyzer` 使用） |

`LootHost` 改为调用 `LootRollCore` 的对应函数，只在真正采样处（`PickWeighted` 消耗一次
`IRngHost.Next` 得到阈值分数、`RollChanceEachGroup` 消耗一次 `IRngHost.Next` 判定命中、
`RollCount` 消耗 `IRngHost.NextInt`）注入随机数——`IRngHost` 的调用次数、顺序、每一步的浮点
运算与重构前逐字节相同。

### 第二步：新增 `LootTableAnalyzer`（消费方需要的公开入口）

**契约面**（`core/gameplay/loot/contracts/LootAnalysisContext.cs` + `core/gameplay/loot/core/
LootTableAnalyzer.cs`）：

```csharp
public static class LootTableAnalyzer
{
    public static IReadOnlyList<LootExpectedOutcome> ExpectedProbabilities(
        LootTableDef def, LootAnalysisContext context);
}

public enum LootConditionEvaluationMode { AssumeTrue, AssumeFalse, Evaluate }

public sealed class LootAnalysisContext
{
    public LootConditionEvaluationMode ConditionMode { get; set; } = AssumeTrue;
    public IExprHost? ExprHost { get; set; }              // ConditionMode=Evaluate 时必填
    public IExprDiagnostics? Diagnostics { get; set; }
    public double Multiplier { get; set; } = 1.0;
    public Id? ContextId { get; set; }                     // 供伪随机 key 拼接，可留空
    public bool PseudoRandom { get; set; }
    public double PseudoRandomStep { get; set; } = 0.1;
    public IReadOnlyDictionary<LootPseudoRandomKey, int>? PseudoRandomMissStreaks { get; set; }
    public IReadOnlyDictionary<Id, LootTableDef> Tables { get; set; } = <empty>;  // 嵌套 loot.* 解析源
    public int MaxNestedDepth { get; set; } = 8;
    public int ExactWithoutReplacementMaxEntries { get; set; } = 12;
}

public readonly struct LootPseudoRandomKey
    { public Id ContextId; public Id TableId; public int GroupIndex; public int EntryIndex; }

public sealed class LootExpectedOutcome
{
    public Id LeafRef { get; }              // 嵌套展开后的 item.* 引用
    public double DropProbability { get; }  // 一次 Roll 里至少出现一次的概率 [0,1]
    public double ExpectedCount { get; }    // 一次 Roll 里的期望产出数量
    public IReadOnlyList<string> SourcePaths { get; }  // 贡献路径可读描述
    public bool IsApproximate { get; }
}
```

**语义清单**（逐条对照 `LootHost` 实际抽取算法，详见 `LootTableAnalyzer.cs` 类型注释"抽取语义
清单"一节，`core/gameplay/loot/README.md` 判断记录 14）：

| 结构 | 精确式 | 备注 |
|---|---|---|
| `chance_each` 单条 | `p = Clamp01(weightOrChance × multiplier)`（启用伪随机再按连续未中次数线性放大） | 一次 `Roll` 只判定一次，不是"重复抽到保底为止" |
| `weighted_pick_one` 单抽 | `p_i = w_i / ΣW`（候选池归一化） | — |
| `weighted_pick_one` 多抽不放回，候选池 ≤ 阈值（默认 12） | 位掩码动态规划精确枚举全部抽取顺序分支 | 与 `LootHost.PickWeighted` 逐步"按剩余候选池归一权重抽一条、移出、重复"完全同构，含"剩余权重合计 ≤0 时整体提前停止"这一行为 |
| `weighted_pick_one` 多抽不放回，候选池 > 阈值 | 近似 `1-(1-w_i/ΣW)^k`（视作放回抽样） | 标注 `IsApproximate=true` |
| 嵌套 `loot.*` 引用 | `count` 次独立子抽取，`P(none)=avg_{n∈[min,max]}((1-p_leaf)^n)` | `count` 闭区间均匀分布；引用了 `context.Tables` 里不存在的表或超过 `MaxNestedDepth` 时静默跳过，语义同 `LootHost.ResolveEntryAtDepth`/`RollTableInto` |
| `guaranteed_min` 保底，`chance_each`/`weighted_pick_one` 直接条目 | 精确条件合并（见下） | 不标注近似 |
| `guaranteed_min` 保底，`loot.*` 嵌套条目落在候选池 | 独立近似合并 | 标注 `IsApproximate=true`（"自然命中与补抽命中同时发生等价于两次独立嵌套子抽取"这一层未展开建模） |

**`guaranteed_min` 精确合并推导**（核心判断记录，也是本次实现里唯一有实质数学内容、容易做错
的一步）：自然产出数 `c`（不含保底补抽）是"各 `weighted_pick_one` 组确定性选中数之和" +
"`chance_each` 部分独立但概率不同的伯努利之和"，后者用标准 O(n²) 动态规划（泊松二项分布）
精确建模。"该条目自然命中"与"该条目被保底补抽命中"两件事能否当独立事件合并，按条目类型
分两种情形：

- **`weighted_pick_one` 条目**：一次抽取固定选出 `k` 条（`k` 本身不随机，选中哪几条不影响
  `k`），因此该条目是否被自然选中与 `c` 的分布无关，用边际分布独立合并
  `1-(1-p_natural)(1-p_topup)` 就是精确值。
- **`chance_each` 直接条目**：自身是否命中直接是 `c` 的一个加数，与补抽规模天然相关，笼统的
  独立合并会算错——用条件概率精确展开：`P(至少一次) = p_natural + (1-p_natural) × P(补抽命中
  | 该条目未自然命中)`，其中"给定未自然命中"的条件分布 = 排除该条目自身贡献后，剩余
  `chance_each` 概率的泊松二项分布（这几个概率天生互相独立，排除一个不影响其它的边际分布，
  是精确的条件化，不是近似）。

  手算校验（`E35_LootTableAnalyzerTests.GuaranteedMin_DirectItems_ExactMatchesMonteCarlo`
  用例，`guaranteed_min=2`，候选池 `{A:0.2, B:0.3, C:0.1}`）：排除 A 后 `{B,C}` 独立伯努利
  分布 `P(0)=0.63, P(1)=0.34, P(2)=0.03`；对应补抽规模 `topUpSize = clamp(2-c,0,3)` 分别是
  `2/1/0`；`{A,B,C}` 权重 `0.2/0.3/0.1`（合计 0.6）不放回抽 2 条时 A 被抽中的概率
  `= 11/15 ≈ 0.7333`（手算：`P(首抽=A)=1/3` 时 A 必中；`P(首抽=B)=1/2` 时次抽从 `{A,C}`
  抽中 A 概率 `2/3`，贡献 `1/3`；`P(首抽=C)=1/6` 时次抽从 `{A,B}` 抽中 A 概率 `0.4`，贡献
  `1/15`；合计 `1/3+1/3+1/15=11/15`），不放回抽 1 条时 A 被抽中概率 `=1/3`，抽 0 条时为 0；
  `topUpGivenNotFired = 0.63×11/15 + 0.34×1/3 + 0.03×0 ≈ 0.57533`；
  `P(A 至少一次) = 0.2 + 0.8×0.57533 ≈ 0.660267`——代码输出精确等于 `0.660267`（容差
  `0.0005` 内），蒙特卡洛（固定种子、100000 次）实测 `0.66106`，二者一致；若改用"笼统独立
  合并"（`1-(1-0.2)(1-marginalTopUp)`），算出的是 `0.601808`，与蒙特卡洛结果相差 0.059（约
  9% 相对误差）——这是实现过程中先写出的错误版本，被本条测试的紧容差（0.0005）当场抓出，
  改成条件展开后修复，过程记录见提交历史（`2e9bb6f` 之后同一提交内的迭代，未单独提交中间
  错误版本）。

**期望数量**恒可加（数学期望的线性性，与相关性无关），因此不受上面这层相关性影响，直接按
"自然命中概率 × 期望数量 + 补抽命中的边际概率 × 期望数量"求和即可，两条路径都用无条件（边际）
概率。

### 条件三种求值模式

- `AssumeTrue`/`AssumeFalse`：不需要 `IExprHost`，全体条件统一视为真/假——分别对应"编辑器不
  代入具体世界/任务状态的结构预览"（默认）与"条件相关上下文尚未配齐，宁可保守估计下限"两种
  场景。
- `Evaluate`：需要调用方提供已装配好的 `IExprHost`（`self`=击杀者或来源单位、`target`=来源
  单位，与 `LootHost.Roll` 内部 `_exprHostFactory.CreateFor(...)` 同一约定），复用同一份
  `LootRollCore.ConditionPasses`，语义与真实抽取完全一致。未提供 `ExprHost` 时在入口抛
  `InvalidOperationException`（不静默退化，避免调用方以为条件生效了但实际被忽略）。

### 分析不改变宿主/输入状态

`LootTableAnalyzer` 只接受 `LootTableDef`（值对象，来自 `LootTableParser.Parse` 或
`IDataRegistryView`）与 `LootAnalysisContext`，从不持有或引用任何 `LootHost` 实例，不消耗
`IRngHost`，不修改传入对象——重复调用幂等（同输入同输出），与任意 `LootHost` 实例的 `Roll`
调用序列互不干扰（见
`E35_LootTableAnalyzerTests.ExpectedProbabilities_DoesNotAffectUnrelatedLootHostRollSequence`：
200 次交叉调用"分析 → Roll"与 200 次纯"Roll"的结果序列逐条相同）。
