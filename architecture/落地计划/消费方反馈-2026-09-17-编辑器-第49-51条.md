## 处理

### 50　四个长任务 `Run` 入口新增 `CancellationToken`/`IProgress<SimProgress>`（高优先级）

**状态**：已实现（分支 `feedback/49-51`，未发布）。

**处理方式**：

1. 新只读结构体 `Core.Sim.SimProgress`（`core/sim/core/SimProgress.cs`）：`Stage: string`/
   `Completed: int`/`Total: int`/`Detail: string?`。
2. `FightRunner.Run`/`ArenaSimulation.Run`/`GrowthSimulation.Run`/`CoverageSimulation.Run` 各新增
   一个尾部追加 `CancellationToken cancellationToken`、`IProgress<SimProgress>? progress = null`
   的重载；旧签名保留并转发到新重载（默认 `CancellationToken.None`/`progress: null`），非取消场景
   下返回值与旧签名逐字段/逐字节一致（同种子，已测试断言）。纯新增重载，不破坏 ABI。
3. **取消语义**：`cancellationToken.IsCancellationRequested` 为真时抛 `OperationCanceledException`
   （携带该 token），绝不返回半成品报告。检查点：`GrowthSimulation` 每个种子边界、
   `ArenaSimulation` 每个等级×等级偏移矩阵格边界、`CoverageSimulation` 技能/装备/生物三段遍历的
   每一条；`FightRunner.Run`（及经它跑内层战斗的 `ArenaSimulation.RunCell`）额外在单场战斗内部
   逐 tick 检查（`FightRunner.RunWithinWorld` 新增的 10 参重载在循环顶部调用
   `ThrowIfCancellationRequested()`），取消延迟在单场战斗场景下是一个 tick 量级。
4. **进度语义**：只在外层迭代边界上报，不做 tick 粒度上报；`Total` 提前已知，`Completed` 单调
   不减，最后一次上报 `Completed==Total`；`progress` 传 `null` 时不产生任何额外分配/调用，零开销。
5. `toolchain/simrunner`：`Main` 新建 `CancellationTokenSource`，挂 `Console.CancelKeyPress`（
   Ctrl+C 时 `eventArgs.Cancel = true` 并 `cts.Cancel()`，避免进程被系统直接杀死、改走取消路径
   优雅退出）；新增 `--progress` 开关（内部 `ScenarioProgressWriter : IProgress<SimProgress>` 把
   `PROGRESS scenario={id} stage={stage} completed={n} total={n}` 同步写到 `stderr`，不占用
   `stdout`，不影响既有摘要行/`--json` 输出的可解析性）；`Execute` 捕获
   `OperationCanceledException` 返回新退出码 `4`="cancelled"（`0`/`1`/`2`/`3` 不变），不写任何
   部分报告；README/`--help` 文案同步更新。

**与并行分支的协调**：`feedback/52-53` 分支同期改 `GrowthSimulation` 的
`ResolveCreatureFamily`/`ResolveCreatureTemplateForLevel` 与 `StandardPlayer`/装备换算代码，为
降低合并冲突面，本分支对 `GrowthSimulation.cs` 的改动刻意收紧到新增的 `Run` 重载本身与它的外层
种子循环（取消检查/进度上报插入点），未触碰 `RunOnce`/`ResolveCreatureFamily`/
`ResolveCreatureTemplateForLevel`——`GrowthSimulation.Run` 因此只在种子边界取消/报告进度，不像
`ArenaSimulation`/`FightRunner` 那样把 token 一路下传到单场战斗内部；`ArenaSimulation.RunCell` 无
此项约束，改为把 `cancellationToken` 继续下传给内层 `FightRunner.Run`，额外获得 tick 级取消响应
（超出本条最低要求，属主动加强，不影响与 `feedback/52-53` 的合并）。

**新增公开 API**：`Core.Sim.SimProgress`（结构体）；`FightRunner.Run(FightRunnerOptions,
CancellationToken, IProgress<SimProgress>?)`；`ArenaSimulation.Run(ScenarioDef, AnchorTable,
IReadOnlyList<IDataSource>, CancellationToken, IProgress<SimProgress>?)`；
`GrowthSimulation.Run(...)` 同形；`CoverageSimulation.Run(ScenarioDef, AnchorTable,
IReadOnlyList<IDataSource>, bool failOnUnknownTable, CancellationToken, IProgress<SimProgress>?)`；
`toolchain/simrunner` 新增 `--progress` 命令行开关与退出码 `4`。

**测试**：四个入口各自新增——预取消令牌立即抛出、执行期间经进度回调触发取消能抛出且不产生结果、
不取消时结果与旧签名同种子逐字段/逐字节一致、进度序列单调且末项 `Completed==Total` 四类用例。

### 49　`FightRunnerOptions.CaptureEvents`/`FightResult.CapturedEvents`（中优先级）

**状态**：已实现（分支 `feedback/49-51`，未发布）；API-only，见下"已知限制"。

**处理方式**：

1. `FightRunnerOptions` 新增 `CaptureEvents`（`bool`，默认 `false`，不改变默认行为）与
   `MaxCapturedEvents`（`int`，默认 100000，防止极端长战斗把内存打爆）。
2. `FightResult` 新增只读属性 `CapturedEvents: IReadOnlyList<FightLogEntry>`（关闭时为
   `Array.Empty<FightLogEntry>()`，不是 `null`，调用方不必先判空）与
   `CapturedEventsTruncated: bool`（超过 `MaxCapturedEvents` 后置真并停止继续追加，已捕获的条目
   不受影响）。
3. 新类型 `FightLogEntry`（`core/sim/core/FightLogEntry.cs`）：`Tick`/`Category`/`SourceId`/
   `TargetId`/`SkillOrEffectId`/`Amount`/`ResultTag`，公开构造。`FightLogEventCategory` 枚举
   （`Damage`/`Heal`/`SkillCastSuccess`/`SkillCastFailed`/`AuraApplied`/`AuraRemoved`/`UnitDied`/
   `ResourceChanged` 八种）覆盖反馈原文点名的"伤害/治疗/施法成功失败/增益施加移除/死亡/资源变化"
   六类事件；由 `FightRunner.FightAccumulator` 新增的私有 `MapToLogEntry(IEvent, int tick)` 静态
   方法从既有具体事件类型（`Core.Rules.Common`/`Core.Numbers.PowerSet` 两个契约程序集下的事件
   类型）映射得到，不新增事件总线契约、不改变任何事件类型既有字段。
4. **聚合结果不受开关影响**：捕获逻辑挂在既有事件消费循环上"顺带记一笔"，不改变任何聚合统计量
   的计算路径——`CaptureEvents` 开/关两次跑同一战斗，`FightResult` 除
   `CapturedEvents`/`CapturedEventsTruncated` 外逐字段一致（已测试断言）。

**已知限制（按反馈原文"若 CLI 无对应模式可仅提供 API 并如实标注"的口径处理）**：
`toolchain/simrunner` 目前没有单场战斗命令行模式（`run` 子命令只支持"跑一个/全部
`sim.scenario` 场景"，场景内部是否含单场战斗由场景类型决定，命令行层面不存在"直接指定两个模板
打一场"的入口），因此 `--fight-log <path>` **未落地为命令行选项**。本条能力目前仅能通过直接
引用 `core/sim` 类库、构造 `FightRunnerOptions { CaptureEvents = true }` 后调用
`FightRunner.Run` 使用。若后续需要 CLI 出口，需先给 `simrunner` 补一个单场战斗子命令（超出本次
反馈范围，建议作为独立需求提出）。

**新增公开 API**：`FightRunnerOptions.CaptureEvents`/`MaxCapturedEvents`；
`FightResult.CapturedEvents`/`CapturedEventsTruncated`；`FightLogEntry`（含构造函数）；
`FightLogEventCategory` 枚举。

**测试**：关闭时 `CapturedEvents` 为空非 `null`、开启时产生条目且聚合结果不变、超过
`MaxCapturedEvents` 时截断并置位标志三类用例。

### 51　`core/sim` 补充线程安全承诺（低优先级）

**状态**：已实现（分支 `feedback/49-51`，未发布）；落地前复审额外发现并修复一处真实并发缺陷
（见下"复审发现"）。

**处理方式**：

1. `core/sim/README.md` 新增独立"线程安全与并发"章节：承诺四个 `Run` 入口本身无静态可变状态、
   side-effect-free，每次调用经 `HeadlessWorldBuilder.Build` 内部构建全新的 `HeadlessWorld`，
   两次独立调用互不共享框架侧对象；调用方在"调用期间不并发修改传入的同一份
   `IDataSource`/`AnchorTable`/`ScenarioDef` 等输入对象"的前提下，可以安全地在多个线程上并发
   调用四个 `Run` 入口。同一章节明确列出"调用方责任"（自定义 `IDataSource`/`IProgress` 的线程
   安全由调用方自行负责，框架不做兜底同步）与"不承诺什么"（不承诺单次调用内部多线程并行、不承诺
   对调用方自定义实现做加锁保护、审计范围限定在 `Run` 调用路径上而非整仓通用结论）。
2. 新增并发回归测试 `core/sim/tests/ConcurrencyTests.cs`：四个 `Fact`，对四个 `Run` 入口分别用
   `Parallel.For` 并发跑 8 份相同种子调用，与串行结果逐字段/`ToJson()` 比对完全一致——不是只
   断言"不抛异常"（并发数据竞争经常表现为偶发性结果错误而非崩溃）。

**复审发现（按反馈要求"落笔承诺前先复审静态可变状态"进行，不限于 `core/sim` 自身）**：审计
`Run` 调用路径上会经过的其它 Core 程序集，发现
`Core.Foundation.DataRegistry.FileSystemDataSource.ListTables()`
（`core/foundation/data_registry/core/FileSystemDataSource.cs`）此前在共享实例字段
`_skippedNonTableFiles`（`List<string>`）上做 `Clear()` + 逐条 `Add()`，同一个
`FileSystemDataSource` 实例被多个线程并发调用 `ListTables()` 时会在同一个 `List<T>` 上产生真实
数据竞争（可能抛 `ArgumentException`/`IndexOutOfRangeException` 或损坏内部状态，不只是"读到过期
值"）——这正是"线程安全与并发"章节承诺"框架内置 `IDataSource` 实现可安全被并发复用"所依赖的
前提，若不修复，该承诺对使用 `FileSystemDataSource` 的调用方是一句空话。**已根治**：改为"局部
构建、一次性整体替换只读引用"（字段改为
`private volatile IReadOnlyList<string> _skippedNonTableFiles`）；`ListTables()` 实际装载用的
返回值本就是每次调用新建的局部变量，从未受这处竞争影响，本次是纯粹的"消除共享字段上的数据竞争"
修复，不改变任何一次调用的返回结果。新增回归测试
`FileSystemDataSourceSkipsNonTableJsonTests.ListTables_CalledConcurrentlyOnSameInstance_
DoesNotThrow_AndTableListIsStable`（16 线程 × 50 次并发调用，断言不抛异常且每次返回表数量
恒定）。未在四个 `Run` 入口实际调用路径上发现其它同类共享可变状态问题。

**新增公开 API**：无（本条主要是文档承诺 + 一处内部字段实现修复，`FileSystemDataSource` 公开
成员签名不变）。

**测试**：`ConcurrencyTests.cs`（4 例）+ `FileSystemDataSourceSkipsNonTableJsonTests.cs` 新增
1 例并发回归。

## 对编辑器的使用建议

1. 批量沙盘（如"内容覆盖仿真离群值列表"）若改为子进程调用 `simrunner`，可用新增的 `--progress`
   输出驱动进度条，用户点"取消"时向子进程发 Ctrl+C 信号即可在一个 tick 量级延迟内安全中止；若
   改为进程内直接引用 `core/sim` 类库，可直接传入 `CancellationToken`/`IProgress<SimProgress>`。
2. "简易战斗回放"若需要真正的逐条战斗日志文本（而不是只有资源曲线采样点/最终聚合），开启
   `FightRunnerOptions.CaptureEvents` 后可从 `FightResult.CapturedEvents` 直接拿到结构化事件
   序列；子进程调用 `simrunner` 场景暂无 CLI 出口（`--fight-log` 未实现），需改走进程内引用或
   等待后续单场战斗 CLI 子命令。
3. 若打算并行跑多个数值沙盘任务，现在有框架侧"线程安全与并发"章节的书面承诺可依据；若自行实现
   了 `IDataSource`（如内存态未保存草稿数据源）用于并发场景，线程安全需要自行保证。
4. `IBudgetSolver.Solve` 等运行期入口本次未涉及，不在本条反馈范围内。
