## 第 76 条：资产/数据根目录推导纳入公开契约

已按 [ADR-0054](../adr/0054-资产数据根目录与目录内固定文件名纳入公开契约.md) 交付。新增
`Core.Foundation.EngineAdapter.AssetRootConventions` 静态类（`core/foundation/engine_adapter/
contracts/AssetRootConventions.cs`），四个方法确切签名：

```csharp
public static string ResolveAssetsRoot(string repoRoot, string? assetsRootOverride);
public static string ResolveDataRoot(string repoRoot, string? dataRootOverride);
public static string DatasetAssetsDirectory(string assetsRoot, string dataset);
public static string DatasetDataDirectory(string dataRoot, string dataset);
```

- `ResolveAssetsRoot`/`ResolveDataRoot`：`assetsRootOverride`/`dataRootOverride` 为 `null` 时分别
  默认 `<repoRoot>/assets`、`<repoRoot>/data`；传入值经 `Path.IsPathFullyQualified` 判定为已是完全
  限定路径时原样返回，否则按 `repoRoot` 用 `Path.Combine` 解析。`repoRoot` 为 `null` 抛
  `ArgumentNullException`。
- `DatasetAssetsDirectory`/`DatasetDataDirectory`：`<assetsRoot>/<dataset>`、`<dataRoot>/<dataset>`，
  同样用 `Path.Combine`（真实文件系统路径，不是 `AssetRefConventions` 那种正斜杠拼接的相对路径
  空间记法）。

**为什么新建 `AssetRootConventions` 而不是并进 `AssetRefConventions`**：两者输入形状不同——
`AssetRefConventions` 全部既有方法都以「资源引用 `Id`」为输入，回答「给定一个资源引用 id，它在
资产根目录下的哪个相对路径」；`AssetRootConventions` 全部方法以「仓库根路径 + 数据集名/根目录
覆盖值」为输入，回答「资产根/数据根目录本身在哪」。两者是消费方从「游戏仓库根 + 数据集名 + 资源
引用 id」定位到磁盘文件过程中依次经过的两个不同维度，不共享方法签名，因此单独归为一组（ADR-0054
决策 1）。

Python 等价函数在 `toolchain/asset_import/ref_conventions.py`：`resolve_assets_root`、
`resolve_data_root`、`dataset_assets_directory`、`dataset_data_directory`，与上述四个 C# 方法逐字
对应，两侧各自独立实现，靠单元测试与跨语言一致性测试互相对照。`toolchain/asset_import/common.py`
的 `resolve_root(value, repo_root, default_name)` 对 `default_name` 为 `"assets"`/`"data"` 两个
已知取值（六个子命令实际调用点仅有这两种）已改为委托 `ref_conventions.resolve_assets_root`/
`resolve_data_root`，不再自行维护一份拷贝。

**你们可以拆的绕行**：`AssetsRootResolver`、`ImportDatasetRootsConvention` 这两个你们为绕开本条
缺口自建的机制，交付后可以拆了，改为直接调用上述框架公开方法。

## 第 77 条：目录型资源固定文件名与 `frames.json` 结构化契约

已按 ADR-0054 交付。`Core.Foundation.EngineAdapter.AssetRefConventions`
（`core/foundation/engine_adapter/contracts/AssetRefConventions.cs`）新增五个方法，确切签名与
各自输出：

```csharp
public static string VfxAtlasFile(Id resourceRefId);        // VfxResourceDir(id) + "/atlas.png"
public static string VfxFramesFile(Id resourceRefId);       // VfxResourceDir(id) + "/frames.json"
public static string SpriteAnimAtlasFile(Id resourceRefId); // SpriteAnimDir(id) + "/atlas.png"
public static string SpriteAnimFramesFile(Id resourceRefId);// SpriteAnimDir(id) + "/frames.json"
public static string SpriteSetAtlasFile(Id spriteSetId);    // SpriteSetDirectory(id) + "/atlas.png"
```

五个方法都返回与既有 `VfxResourceDir`/`SpriteAnimDir`/`SpriteSetDirectory` 同一路径空间的资产根
相对路径（正斜杠拼接）。`toolchain/asset_import/ref_conventions.py` 同步新增等价函数
`vfx_atlas_file`/`vfx_frames_file`/`sprite_anim_atlas_file`/`sprite_anim_frames_file`/
`sprite_set_atlas_file`，逐字对应。

**并一并给了你们没要求的东西**：`frames.json` 的结构化只读解析契约新增
`Core.Foundation.EngineAdapter.EffectFramesDocument`（含 `EffectFrameData`），位于
`core/foundation/engine_adapter/contracts/EffectFramesDocument.cs`，不依赖 Unity：

```csharp
public sealed class EffectFramesDocument
{
    public double? FrameWidth { get; }   // 顶层 frame_w，未写出为 null
    public double? FrameHeight { get; }  // 顶层 frame_h，未写出为 null
    public double Fps { get; }           // 顶层 fps，未写出缺省 12
    public double DefaultFrameDuration { get; } // 顶层 frame_duration，未写出按 fps>0 ? 1.0/fps : 0.05 推算
    public bool Loop { get; }            // 顶层 loop，未写出缺省 false
    public IReadOnlyList<EffectFrameData> Frames { get; }

    public static bool TryParse(string json, out EffectFramesDocument document);
}

public readonly struct EffectFrameData
{
    public int Index { get; }      // 数组下标，不读取 JSON 里的 index 字段
    public double X { get; }       // 未写出缺省 0
    public double Y { get; }       // 未写出缺省 0
    public double? Width { get; }  // 未写出为 null（历史兜底依赖已解码图集纹理整宽，留给调用方）
    public double? Height { get; } // 同 Width
    public double Duration { get; } // 未写出退回 DefaultFrameDuration
}
```

`Adapter.Unity.EngineAdapter.UnityResourceLoader.TryDecodeEffect`（原来唯一的解码实现，Unity 内部
私有方法）已改为调用 `EffectFramesDocument.TryParse` 取得结构化数据后只做「按裁剪矩形从图集切出
`Sprite`」这一步 Unity 特有收尾，不再自行解析 JSON——不再有第二份解析实现。所有缺省值规则
（`loop`/`fps`/`frame_duration`/单帧 `duration`）与原实现逐字节一致，`Width`/`Height` 缺省时依赖
图集实际尺寸这一运行环境相关的兜底值，明确留在 `EffectFramesDocument` 职责范围之外，由调用方自行
决定。

**如实说明：`sprite_set` 目录下的 `atlas.json` 没有加对应方法**。判断记录（ADR-0054 决策 2、
备选方案一节）：`sprite_set` 目录内与 `atlas.png` 配套的索引文件是 `atlas.json`（按方向档位/层名
分帧的字典结构），字段形状与 `frames.json`（按序列帧顺序排列、含播放时序字段）完全不同；且
`atlas.json` 目前只被内容工具自身的存在性校验消费，运行时精灵渲染走同目录下按方向档位/层名展开的
独立扁平文件，不经 `atlas.png`/`atlas.json`。你们的反馈原文与现有代码都未提出这一需求，不借机
扩大收口范围。

**你们可以恢复的界面接线**：精灵集/特效/动画三类预览的界面接线可以恢复了。

## 第 78 条：`ValidationReportFileOutlet` 落盘信封补 `table` 字段

已按 [ADR-0055](../adr/0055-运行期校验报告落盘出口补表名字段.md) 交付。`ValidationReportFileOutlet`
（`adapters/unity/Packages/com.gamefoundation.adapter.unity/Runtime/Diagnostics/
ValidationReportFileOutlet.cs`）的 `WriteIfConfigured`/`Write`/`BuildJson` 三个方法各自新增一个带
`string? table` 形参的重载（ABI 只新增，既有不带 `table` 的重载保留并委托给新重载、`table` 缺省
`null`）。落盘信封顶层新增可选字段 `table`：

- 热重载来源（`source: "hot_reload"`）：`table` 是被重载的那张表的确切名字。示例：

```json
{"sequence": 3, "source": "hot_reload", "table": "skill.definition", "timestamp_utc": "2026-09-21T08:00:00Z", "issues": []}
```

- 启动全量校验来源（`source: "startup"`）：`table` 固定输出 JSON **`null`**，不输出空字符串，也不
  输出 `"all"` 一类占位值。示例：

```json
{"sequence": 1, "source": "startup", "table": null, "timestamp_utc": "2026-09-21T08:00:00Z", "issues": [...]}
```

**为什么是 `null` 而不是 `""`/`"all"`**（ADR-0055 决策 2）：启动全量校验校验的是当前已注册的全部
表，不是某一张单一确定的表，「这次校验针对哪一张表」这个问题在这个场景下本身没有一个有意义的答案，
不该为了让字段「看起来总有值」而编造一个场景中并不存在的答案。空字符串在很多字符串处理惯例里会被
当作「合法但为空」与「缺失」两种含义混用；`"all"` 更可能被字面理解成一张真实存在、名字恰好叫 `all`
的表。`null` 是本落盘信封与逐条问题字段集合里已经在用的「本场景不适用」的既有记法（`record_key`/
`field`/`group`/`note`/`rule_id` 均如此），不需要为这一个新字段学一套新的缺失约定。

唯一改动的调用点是 `games/_template/Runtime/DataHotReload.cs` 的 `ReloadTable(string table)`，把
已持有的 `table` 局部变量一并传给新重载；三处启动全量校验调用点（`GameBootstrap.cs`/
`GameFoundationBootstrap.cs`/`FrameworkResidentHost.cs`）原样不动，继续走既有不带 `table` 的重载。

**为什么 `toolchain/validator --json` 那个出口没有加这个字段**：`ValidationIssueJsonWriter`
（逐条问题层的共享序列化实现，落盘出口与 `toolchain/validator --json` 共用）不改动——本次新增的
`table` 属于信封层，不属于逐条问题层，两层语义不同：逐条问题层已有的 `table` 字段是「这一条问题
出在哪张表」；本次新增的信封级 `table` 是「这次校验触发时确切针对哪张表」，热重载校验干净
（`issues` 为空数组）时前者从空集合里完全拿不到信息，只有信封层能覆盖这个场景。而
`toolchain/validator --json` 的信封天生覆盖「命令行本次传入的全部数据根、全部已注册表」这一批的
统计量（`tables`/`fields`/`errors`/`warnings`/`blocking`/`table_names`/`issues`，`table_names`
本身就是数组），结构上没有与运行期「某一次触发确切针对哪一张表」对应的单一值——命令行出口没有
与运行期热重载等价的「单表触发」场景，加一个多数时候只能是 `null` 的字段没有实际消费场景，故不加。

**你们不用再解析日志文本了**：原有依赖 `Debug.Log` 文本行 `[DataHotReload] 热重载 "<表名>" ...`
判定表名的路径可以删除，改读落盘 JSON 的 `table` 字段。

## 行为变更（务必单列自查）

`toolchain/import_sample_assets.py` 的相对路径根目录覆盖值解析基准发生了变化：**此前按当前工作
目录解析，现按仓库根解析**（收口到与 `AssetRootConventions`/`ref_conventions.py` 共享函数后，与
`check_cmd.py`/`icon_cmd.py`/`map_cmd.py`/`sfx_cmd.py`/`sprite_cmd.py`/`vfx_cmd.py` 六个子命令的
既有口径统一）。

只影响一种用法：**从非仓库根目录调用该脚本、且传了相对路径的 `--assets-root`/`--data-root` 覆盖
值**。传绝对路径、或不传覆盖值（走默认的 `<repo_root>/assets`、`<repo_root>/data`）的调用不受
影响。请自查你们的工具链/CI 里是否有这种调用方式。
