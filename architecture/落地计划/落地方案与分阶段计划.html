3. 解决方案与工程结构

3.1 .NET 解决方案 Core.sln

项目顺序（引用只允许向下）：Core.Foundation → Core.Numbers → Core.Rules → Core.Carriers → Core.Gameplay → Presentation.Common；每层配一个 xUnit 测试项目（Tests.Foundation…Tests.PresentationCommon），只依赖对应层与 Adapters.Stub，不依赖 Unity；Adapters.Stub 是独立类库，实现全部必需接口为最小可用桩，供测试驱动 WorldSim，不对外发布；目标框架统一 .NET Standard 2.1。

3.2 Unity 工程 adapters/unity/

asmdef 划分：Adapter.Unity（实现 L-1 全部接口 + L5 引擎侧）位于嵌入式 UPM 包 adapters/unity/Packages/com.gamefoundation.adapter.unity/；Game.<Game>（游戏层：组装、策略配置、钩子回调）的模板位于本地包 games/_template/（程序集 Game.Template，新游戏复制改名）。Unity 工程只引用 Core.sln 的 Release DLL（由 build.ps1 复制到适配层包内 Runtime/Plugins/Core/），核心逻辑与引擎工程物理隔离，只经 DLL 边界交互；build.ps1 -Dist <version> 另产出版本快照 dist/<version>/，供各游戏以 file: 引用（见 3.5 节）。Unity 包依赖 URP（2D Renderer）、Input System、TextMeshPro、2D 寻路第三方包（NavMeshPlus 或 A* Pathfinding Project 二选一，阶段 4 试后定，封装在 INavigation2D 之后）。

3.3 数据与资产目录

data/<game>/<system>/*.json 每表一文件、带 schema_version；assets/<game>/ 正式资产、assets/_placeholder/ 阶段 4 灰盒占位资产；toolchain/ 与二者平级，读取并校验。

3.5 新游戏如何消费本框架（多游戏共用规则）

原则：框架仓库是被依赖方，任何游戏不进入框架仓库。新游戏 = 自己目录里的一个 Unity 工程（含 Game.<Game> 程序集）+ data/ + assets/ + 该游戏的设计文档 + 自己的 git 仓库。

四条消费通道

通道框架侧提供物游戏侧接入方式
核心逻辑 L0～L4 与 Presentation.Commonbuild.ps1 编译出 6 个 DLL，随适配层包一起交付，不单独分发随 com.gamefoundation.adapter.unity 包内 Runtime/Plugins/Core/ 一并获得
Unity 适配层 + 表现层引擎侧 + UI 套件默认皮肤嵌入式 UPM 包 com.gamefoundation.adapter.unity（程序集 Adapter.Unity，DLL 位于包内 Runtime/Plugins/Core/）游戏工程 Packages/manifest.json 用 file: 相对路径引用
游戏层骨架games/_template/ 是本地包 com.gamefoundation.game-template（程序集 Game.Template）新游戏复制它改名为 Game.<Game>
占位资产包与工具链assets/_placeholder/ 随快照交付；toolchain/validate_data.py --data-root <game>/data 按路径调用打包时由游戏侧构建脚本把 data/ 拷入 StreamingAssets

Packages/manifest.json 示例片段（示例路径以游戏工程 Packages/ 目录为基准，实际相对层级按各游戏目录位置调整）：

{
  "dependencies": {
    "com.gamefoundation.adapter.unity": "file:../../ws-game/dist/0.3.0/com.gamefoundation.adapter.unity",
    "com.gamefoundation.game-template": "file:../../ws-game/dist/0.3.0/games/_template"
  }
}

多游戏共用的五条规则

  1. 游戏引用框架的版本快照而不是开发目录：框架每次发布打 git tag（vX.Y.Z），build.ps1 -Dist X.Y.Z 产出 dist/X.Y.Z/（含适配层包、games/_template、toolchain、assets/_placeholder、MANIFEST.txt）；每个游戏锁定一个版本，升级时主动改版本号并跑自己的校验与测试；多个游戏可锁在不同版本。dist/ 是构建产物不入库，可由 tag 重建。
  2. 框架变更受语义化版本与 ADR 双重约束：契约接口、事件名、数据表结构、存档结构的变更走 12 篇扩展与变更流程；破坏兼容的变更升主版本并附迁移说明；数据表靠 04 篇的 schema_version 迁移链、存档靠 10 篇的版本迁移链让老游戏的数据与存档迁到新版本。
  3. 游戏专属需求不回流框架：先在游戏层用策略注入与钩子解决；只有多个游戏都需要的能力才走 ADR 进框架；框架仓库永不出现游戏名。
  4. 每个游戏物理独立：各自 Unity 工程、data/、assets/、设计文档、git 仓库；Unity 把 file: 引用的包导入各工程自己的 Library/，工程间无共享状态；工具链按路径调用，输入输出都在游戏目录内。
  5. 框架有独立验收面：单测、确定性回放、桩适配层集成测试、占位资产灰盒竖切构成发布门槛，每次打 tag 前全过；框架是否被改坏由框架自己的测试回答，不依赖任何游戏。
两个问题的答案
  • 框架开发完后新游戏在自己的目录里怎么用它——按上表四条通道，在自己的 Packages/manifest.json 里用 file: 相对路径指向框架某个 dist/<version>/ 快照，复制 games/_template 改名即得到游戏层起点，其余（核心 DLL、适配层、占位资产、工具链）随包与快照一并获得，游戏目录内不出现框架源码。
  • 多个新游戏同时引用同一框架会不会乱——不会乱，分别对应规则 1 与规则 4：每个游戏锁定自己的版本快照（规则 1），互不干扰；每个游戏的 Unity 工程、数据、资产、Library/ 物理独立（规则 4），一个游戏的改动不触达另一个游戏或框架仓库本身。

升级一个游戏所用框架版本的步骤

  1. 重建或获取目标版本快照：在框架仓库对应 tag 上跑 build.ps1 -Dist <新版本号>，或直接使用已产出的 dist/<新版本号>/。
  2. 改游戏工程 Packages/manifest.json 里两个 file: 依赖的版本号路径，指向新快照。
  3. 跑 python toolchain/validate_data.py --data-root <game>/data（新版本自带的校验器）与游戏自己的测试套件。
  4. 若变更记录标注了 schema_version 或存档版本迁移，按迁移说明对 data/<game>/ 与既有存档执行迁移。
  5. 把本次升级（旧版本号→新版本号、日期、迁移是否执行）记录到该游戏自己的接入记录里。

4. 关键技术决策的落地细节

4.1 确定性

核心库不读取引擎时间源，不使用系统级随机；固定步长 dt 只来自 SimClockHost.advance 或 TurnScheduler.nextStep；随机经 RngHost 按用途分流；浮点运算固定顺序；回放录像 = 意图序列 + 初始种子状态。

4.2 事件总线

同步派发 + tick 末批处理（对应 03 篇第 4.2 节第 7 步）；事件类型登记表由工具链生成脚本读取数据定义、生成 C# 常量类，避免手写字符串拼错。

4.3 数据加载

Unity 侧经 IResourceLoader 读 JSON 文本交给 DataRegistry；编辑期提供热重载开关，发布构建关闭。

4.4 存档

JSON + writeTextAtomic 原子写入；架构的 user:// 对应 Unity persistentDataPath，映射在 Adapter.Unity 内完成，core/ 不感知具体路径。

4.5 2D 渲染

Transparency Sort Axis 按 Y；Sorting Group 做纸娃娃合成；Shader Graph 做闪白/溶解；高频特效走对象池化的粒子系统；镜头固定俯角用正交相机 + 固定偏移。

4.6 UI

UGUI + TextMeshPro；思源黑体承担中文字体；UI Toolkit 列为后续评估项，本阶段不采用。

4.7 寻路

第三方 2D 寻路包封装在 INavigation2D 之后，阶段 4 用同一张测试地图对比 NavMeshPlus 与 A* Pathfinding Project 后二选一，替换不影响 core/。

8. 执行规范

每个派发给执行层（Sonnet 子 agent）的任务，必须自包含以下五项
  • 目标：一句话说明产出，不依赖对话上下文即可理解
  • 涉及文件：明确列出新建/修改的文件路径
  • 契约引用：指向 architecture/ 对应文档的具体章节，不得凭空发明契约签名
  • 验收标准：可执行的测试/校验命令，不接受"看起来对"这种不可验证的标准
  • 禁止事项：明确列出不允许做的事

设计层收到执行层完成汇报后必须独立复核（跑验收命令、抽查文件、对照契约核对），复核通过才计入完成，执行层自我汇报不能替代复核。执行层因契约不清、发现架构缺口而无法继续时如实上报，不允许在游戏层"绕过"实现。

第三部分 分阶段落地计划

9. 估算前提

  • 人力模型：一人（用户）+ AI 代理（设计层 + 执行层），按"全职投入"估算每周可用时间。
  • 数字口径：本计划给出的周期是首版基准，允许 ±30% 浮动；实际进度以里程碑验收是否通过为准，不以日历时间为准。
  • 阶段 0～5 均有明确终止条件（对应验收标准全部达成）。
  • 每阶段"依赖"只列硬依赖；并行阶段（4、5）之间没有硬依赖，只有用户精力上的软性协调。

10. 阶段 0：环境与仓库骨架

周期：1 周（2026-09-08～2026-09-14，±30% 即 5～9 个工作日）

目标：把"人+工具+框架仓库+最小可编译骨架"做完，为后续阶段提供地基，不写任何游戏逻辑。

20. 变更控制

  • 改架构：任何触及 architecture/ 文档集定义的内容（新增/修改层、模块、契约接口、事件、数据表结构，或新增原语）一律先走 12_扩展与变更流程.md 的 ADR 流程，经设计层确认后才允许改动文档与实现。
  • 改计划：本文档描述的分工方式、阶段划分、周期估算、验收标准如需调整，在文档变更记录表追加一行，不需要走 ADR 流程。
  • 判断边界：只看是否触及 architecture/ 文档集定义的内容——触及即改架构，否则即改计划；执行层发现"架构不够用"时如实上报设计层判断类型，不得自行绕过流程。

附：本计划中估算最不可靠的阶段

阶段 4（Unity 适配层 + 表现层 + UI 套件）是全文估算最不可靠的一项，理由：

阶段 4 是首次把架构接口在真实引擎上落地，2D 寻路包选型与 URP 自定义 Shader Graph 效果在不同显卡上的表现差异（风险 3）带来一定不确定性；但接口层已用 INavigation2D/IRenderer2D 隔离，替换或调整不影响 core/ 一行代码，使风险敞口可控。

建议：阶段 4 保留比 ±30% 更宽的弹性，并在第 2 周末设一个内部检查点，若接口落地或第三方包接入明显超出预期，及时评估范围与排期调整。
