## 3. 解决方案与工程结构

### 3.1 .NET 解决方案 `Core.sln`

- 项目顺序（引用只允许向下，与 `01_分层与依赖.md` 依赖矩阵一致）：`Core.Foundation` → `Core.Numbers` → `Core.Rules` → `Core.Carriers` → `Core.Gameplay` → `Presentation.Common`。
- 每层配一个独立测试项目：`Tests.Foundation`、`Tests.Numbers`、`Tests.Rules`、`Tests.Carriers`、`Tests.Gameplay`、`Tests.PresentationCommon`，全部基于 xUnit，且只依赖对应层与 `Adapters.Stub`，不依赖 Unity。
- `Adapters.Stub` 是独立类库，实现 `02_引擎适配层.md` 的全部必需接口为最小可用桩（内存渲染句柄、假时钟、内存文件系统等），供 `Tests.*` 与集成测试驱动 `WorldSim` 使用，不对外发布。
- 目标框架统一 `.NET Standard 2.1`（Unity 6 LTS 对应的 IL2CPP/Mono 运行时兼容基线），构建产物为 Release DLL。

### 3.2 Unity 工程 `adapters/unity/`

- asmdef 划分：`Adapter.Unity`（实现 L-1 全部接口 + L5 引擎侧：渲染、相机、UI 承载、输入、音频、文件、资源加载、空间查询、2D 导航封装）位于嵌入式 UPM 包 `adapters/unity/Packages/com.gamefoundation.adapter.unity/`；`Game.<Game>`（游戏层：组装、策略配置、钩子回调、场景内胶水代码）的模板位于本地包 `games/_template/`（程序集 `Game.Template`），新游戏复制该包并改名为 `Game.<Game>`。
- Unity 工程不直接引用 `Core.sln` 的源码，而是引用其 Release 构建产物 DLL：`build.ps1` 负责把 `Core.Foundation.dll`…`Presentation.Common.dll` 复制到适配层包内 `adapters/unity/Packages/com.gamefoundation.adapter.unity/Runtime/Plugins/Core/`，实现"核心逻辑与引擎工程物理隔离、只经 DLL 边界交互"；`build.ps1 -Dist <version>` 额外把适配层包、`games/_template`、`toolchain`、`assets/_placeholder` 打成一份版本快照 `dist/<version>/`，供各游戏以 `file:` 引用（见 3.5 节）。
- Unity 包依赖：URP（含 2D Renderer）、Input System、TextMeshPro、2D 寻路第三方包（候选 NavMeshPlus 或 A* Pathfinding Project，二选一，阶段 4 试用后定，封装在 `INavigation2D` 接口之后，选型结果不影响 `core/` 任何代码）。
- 渲染管线选 URP 2D Renderer 的理由：原生支持 2D Light、Sprite 遮罩与自定义 Shader Graph 效果（闪白/溶解），与 `IRenderer2D` 的着色器参数语义（`setShaderParam`）对应关系清晰。

### 3.3 数据与资产目录

- `data/<game>/<system>/*.json`：按 `04_数据与内容管线.md` 的表清单逐表建文件，例如 `data/<game>/skill/skill.def.json`、`data/<game>/item/item.template.json`；每个文件顶层带 `schema_version` 字段。
- `assets/<game>/`：正式表现资产（精灵图集、特效、音效、字体）；`assets/_placeholder/`：阶段 4 灰盒竖切使用的占位资产；真实游戏接入时替换为该游戏的正式资产，替换过程不改变 `DisplayInfo` 映射的逻辑 id。
- `toolchain/` 与 `data/`、`assets/` 平级，Python 校验脚本读取 `data/<game>/` 做引用完整性校验，读取 `assets/<game>/` 做资产存在性核对。

### 3.5 新游戏如何消费本框架（多游戏共用规则）

**原则**：框架仓库是被依赖方，任何游戏不进入框架仓库。新游戏 = 自己目录里的一个 Unity 工程（含 `Game.<Game>` 程序集）+ `data/` + `assets/` + 该游戏的设计文档 + 自己的 git 仓库。

**四条消费通道**

| 通道 | 框架侧提供物 | 游戏侧接入方式 |
|---|---|---|
| 核心逻辑 L0～L4 与 `Presentation.Common` | `build.ps1` 编译出 6 个 DLL，随适配层包一起交付，不单独分发 | 随 `com.gamefoundation.adapter.unity` 包内 `Runtime/Plugins/Core/` 一并获得 |
| Unity 适配层 + 表现层引擎侧 + UI 套件默认皮肤 | 嵌入式 UPM 包 `com.gamefoundation.adapter.unity`（程序集 `Adapter.Unity`，DLL 位于包内 `Runtime/Plugins/Core/`） | 游戏工程 `Packages/manifest.json` 用 `file:` 相对路径引用 |
| 游戏层骨架 | `games/_template/` 是本地包 `com.gamefoundation.game-template`（程序集 `Game.Template`）：`Runtime/GameBootstrap.cs` + `GameOptions`（口味配置容器）+ `SampleNewGameStarter`、`Editor/GameSceneBuilder.cs`（一键生成 Shell + 首张地图场景）、`Tests/Runtime`（PlayMode 最小验收） | 新游戏复制它改名为 `Game.<Game>`（含三个 asmdef、`package.json`、`GameOptions` 默认 id），见 `games/_template/README.md`"复制为新游戏：改哪几处" |
| 框架级数据表 | `data/_framework/`（`found.event_catalog`/`found.input_action` 等，行由框架代码引用或生成，见仓库根 `data/README.md`）随快照交付，不含 `data/_sample`（那是框架仓库自测用的示例数据） | 与游戏自己的 `data/<game>/` 按 `DataRegistry.loadAll` 多根合并加载（同名表按主键合并，见 04 第 4 节），`games/_template/validate.ps1` 已封装好合并校验调用 |
| 占位资产包与工具链 | `assets/_placeholder/` 随快照交付；`toolchain/validate_data.py --framework-root <dist>/data/_framework --data-root <game>/data` 按路径调用 | 打包时由游戏侧构建脚本把 `data/` 拷入 `StreamingAssets` |
| 发布产物 + 锁文件 | 正式发布（`build.ps1 -Release X.Y.Z`）额外产出 `dist/ws-game-X.Y.Z.zip`（`dist/X.Y.Z/` 打包压缩，供作为 GitHub Release 附件）与 `dist/ws-game-X.Y.Z.lock`（版本号、`git_commit`、六个核心 DLL 的 sha256） | `toolchain/get_framework.ps1 -Version X.Y.Z` 按版本号从 Release 拉取 zip+lock（或 `-FromLocalDist` 指向本机已有的 zip），校验 DLL 哈希后解压到自己工程的 `packages/ws-game-X.Y.Z/`，并在游戏仓库根写入/校验 `ws-game.lock`（内容与下载到的锁文件一致） |

`Packages/manifest.json` 示例片段（示例路径以游戏工程 `Packages/` 目录为基准，`packages/ws-game-X.Y.Z/` 是 `toolchain/get_framework.ps1` 的默认落地目录，实际相对层级按各游戏目录位置调整）：

```json
{
  "dependencies": {
    "com.gamefoundation.adapter.unity": "file:../../packages/ws-game-0.3.0/adapters/unity/Packages/com.gamefoundation.adapter.unity",
    "com.gamefoundation.game-template": "file:../../packages/ws-game-0.3.0/games/_template"
  }
}
```

**多游戏共用的五条规则**

1. 游戏引用框架的**版本快照**而不是开发目录：框架每次发布打带注释标签 `vX.Y.Z`（标签信息取自 `CHANGELOG.md` 对应版本条目），`build.ps1 -Release X.Y.Z` 校验版本号递增/工作树干净/`CHANGELOG.md` 已有该版本条目、写回版本号、跑一遍全量门禁、**门禁通过后先提交版本号改动**（使随后打包产出的锁文件/清单里的提交信息指向这次发布提交本身而不是尚未提交的工作树状态），再产出 `dist/X.Y.Z/`（含适配层包、`games/_template`、`toolchain`、`assets/_placeholder`、`MANIFEST.txt`）与打包压缩、锁文件两个附件（打包完成后自检提交信息确实指向刚才那次提交、工作树干净，不满足则报错退出），最后打标签；每个游戏锁定一个版本，升级时用 `toolchain/get_framework.ps1` 拉取新版本号并跑自己的校验与测试；多个游戏可锁在不同版本。`dist/` 是构建产物不入库，可由标签重建；已发布的版本号一旦打了标签即视为不可变发布（见 11 号文档第 7 节"发布不可变"），发现问题一律发新的 PATCH 版本修复，不回头覆盖旧版本号——不兼容变更修复经 `release/X.Y.x` 维护分支（从对应 `vX.Y.0` 标签切出）发布，修复完成后回合到主线。
2. 框架变更受语义化版本与 ADR 双重约束：契约接口、事件名、数据表结构、存档结构的变更走 `12_扩展与变更流程.md`；破坏兼容的变更升主版本并附迁移说明；数据表靠 04 的 `schema_version` 迁移链、存档靠 10 的版本迁移链让老游戏的数据与存档迁到新版本。
3. 游戏专属需求不回流框架：先在游戏层用策略注入与钩子解决；只有多个游戏都需要的能力才走 ADR 进框架；框架仓库永不出现游戏名。
4. 每个游戏物理独立：各自 Unity 工程、`data/`、`assets/`、设计文档、git 仓库；Unity 把 `file:` 引用的包导入各工程自己的 `Library/`，工程间无共享状态；工具链按路径调用，输入输出都在游戏目录内。
5. 框架有独立验收面：单测、确定性回放、桩适配层集成测试、占位资产灰盒竖切构成发布门槛，每次打 tag 前全过；框架是否被改坏由框架自己的测试回答，不依赖任何游戏。

**两个问题的答案**：

- "框架开发完后新游戏在自己的目录里怎么用它"——按上表四条通道，在自己的 `Packages/manifest.json` 里用 `file:` 相对路径指向框架某个 `dist/<version>/` 快照，复制 `games/_template` 改名即得到游戏层起点，其余（核心 DLL、适配层、占位资产、工具链）随包与快照一并获得，游戏目录内不出现框架源码。
- "多个新游戏同时引用同一框架会不会乱"——不会乱，原因分别对应规则 1 与规则 4：每个游戏锁定自己的版本快照（规则 1），互不干扰；每个游戏的 Unity 工程、数据、资产、`Library/` 物理独立（规则 4），一个游戏的改动不触达另一个游戏或框架仓库本身。

**升级一个游戏所用框架版本的步骤**：

1. 获取目标版本的发布产物：`toolchain/get_framework.ps1 -Version <新版本号>` 从框架的 Release 拉取该版本的打包压缩与锁文件、校验六个核心 DLL 哈希后解压到 `packages/ws-game-<新版本号>/`，并更新游戏仓库根的 `ws-game.lock`（离线场景可用 `-FromLocalDist <本机 zip 路径>`，或在框架仓库对应标签上本机跑 `build.ps1 -Dist <新版本号>` 后直接使用产出的 `dist/<新版本号>/`）。
2. 改游戏工程 `Packages/manifest.json` 里两个 `file:` 依赖的路径，指向新的 `packages/ws-game-<新版本号>/`。
3. 跑 `python toolchain/validate_data.py --framework-root <packages/ws-game-<新版本号>>/data/_framework --data-root <game>/data`（新版本自带的校验器，与快照的 `data/_framework` 合并校验；`games/_template/validate.ps1` 封装了同一调用）与游戏自己的测试套件。
4. 查阅框架 `CHANGELOG.md` 对应版本区间的条目，若标注了 `schema_version` 或存档版本迁移，按迁移说明对 `data/<game>/` 与既有存档执行迁移；若版本号跨越了主版本号（MAJOR），额外核对该版本 `CHANGELOG.md` 的"兼容性说明"是否涉及本游戏用到的契约。
5. 把本次升级（旧版本号 → 新版本号、日期、迁移是否执行）记录到该游戏自己的接入记录里。

### 3.5.1 私服通道（与 zip 快照通道并存）

上表"发布产物 + 锁文件"一行描述的 zip 快照通道之外，新增第二条消费通道：把框架拆成三个可独立按
版本号依赖的包，发布到一个私有包仓库（Verdaccio，npm 兼容协议），游戏侧 Unity 工程用作用域注册表
（`scopedRegistries.scopes: ["com.gamefoundation"]`）依赖。两条通道打包的内容一致（同一次
`build.ps1 -Dist`/`-Release` 产出），选哪条不影响该版本号对应的实际内容，游戏可以只用其中一条，
也可以两条都配置、按环境切换（例如本机开发用私服省去手工解压校验，CI/离线归档场景用 zip）。

**三个包**（版本号统一来自仓库根 `VERSION`，随 `build.ps1 -Dist`/`-Release` 一次性组装 + 发布）：

| 包名 | 内容 | 用途 |
|---|---|---|
| `com.gamefoundation.adapter.unity` | 现有引擎适配层包本身（含 `Runtime/Plugins/Core/` 下六个核心 DLL） | 与 zip 通道同一份内容，只是换了分发协议 |
| `com.gamefoundation.framework-data` | `data/_framework/` + `assets/_placeholder/` + `assets/textmesh_pro_essentials/`，放包内 `Data~/`（Unity 资产管线不导入，游戏侧按解析路径读字节） | 框架级数据表、占位资产、TextMeshPro 运行期资源；配套 `toolchain/sync_package_content.ps1` 同步进消费游戏工程的 `Assets/StreamingAssets/`（数据/占位资产）与 `Assets/TextMesh Pro/`（TMP 运行期资源，不进 `StreamingAssets`，原因见该包 README"判断记录"） |
| `com.gamefoundation.toolchain` | `toolchain/` 内容（不含 `toolchain/registry/` 自身、`__pycache__`、`.venv`、`toolchain/validator/bin|obj`），放包内 `Tools~/` | 数据校验/资产导入 Python 工具链，游戏侧按包解析路径直接 `python` 调用 |

**私服基础设施**（`toolchain/registry/`，框架仓库自己维护、不随三个包分发）：`config.yaml`（存储
`./storage`，包名规则 `com.gamefoundation.*` 允许匿名读、发布需登录，不代理任何上游注册表）、
`package.json`（Verdaccio 固定版本，`npm ci` 装到本目录 `node_modules`，不装全局）、
`start_registry.ps1`（起/停私服，`-Detach` 后台常驻）、`init_publisher.ps1`（无人值守建发布账号 +
令牌，写入项目本地 `.npmrc`，不碰用户全局配置——原理是直接调用 Verdaccio 内置 htpasswd 插件复用的
`PUT /-/user/org.couchdb.user:<name>` 接口，等价于免交互跑完 `npm adduser`，见该脚本头注释）、
`registry.json`（地址与作用域，供 `build.ps1 -PublishRegistry`/`get_framework.ps1 -FromRegistry`
读取默认值）；默认监听 `127.0.0.1:4873`（仅本机），传 `-Listen 0.0.0.0:4873` 可给同一局域网内其它
机器访问。

**`build.ps1` 侧**：`-Dist`（含 `-Release` 内部转译出的等价 `-Dist` 请求）无条件额外产出
`dist/<ver>/packages/{三个包名}/`（各含正确版本号的 `package.json`）与对应的三个 `.tgz`
（`npm pack`，本地打包不联网，因此不受 `-DryRun` 影响，始终会跑）；真正有副作用的
`npm publish` 由 `-Release` 新增的 `-PublishRegistry [-RegistryUrl <url>]` 独立控制（省略
`-RegistryUrl` 时读 `toolchain/registry/registry.json`），与 `-Publish`（`git push` + 建
GitHub Release）各自独立开关、可任意组合；已发布的版本号 `npm publish` 会天然拒绝覆盖，与
"发布不可变"语义一致，不需要额外校验；`-DryRun` 与 `-PublishRegistry` 不能同传（`-DryRun` 只
`npm pack` 验证打包流程，不会有任何东西可以真正发布）。

**游戏侧**：`toolchain/get_framework.ps1` 新增 `-FromRegistry`（与拉 zip 解压是完全不同的分支，
不下载任何文件——UPM 私服场景下"拉包"由 Unity 编辑器自己向注册表请求完成）：生成/更新游戏工程
`Packages/manifest.json` 里的作用域注册表条目与三个包依赖（版本号 = 目标版本），并写
`ws-game.lock`（新增 `source` 字段区分 `channel: "registry"`/`"zip"`，前者记注册表地址/作用域/
包名列表，后者记 `git_commit`/DLL 哈希，两条通道共用同一个锁文件概念，只是记录内容对应各自通道
的完整性保证方式——zip 通道靠本地哈希比对，私服通道的完整性交给 npm/UPM 自己的包传输校验和，
不重复实现）。`toolchain/sync_package_content.ps1`（新增）在游戏工程首次解析完包（`Library/
PackageCache/` 下出现对应目录）之后运行一次，把 `com.gamefoundation.framework-data` 包内
`Data~/` 同步到工程自己的 `Assets/StreamingAssets/GameFoundation/`（数据表、占位资产）与
`Assets/TextMesh Pro/`（TMP 运行期资源）、`Assets/Framework/Resources/Fonts/`（占位字体）——
原理与判断记录同 zip 通道下 `games/_template/README.md`"复制为新游戏：改哪几处"第 8 步描述的
"TMP/字体不能只靠包解析、必须额外一步拷贝"是同一个根因（引擎运行时的内容根固定是工程自己的
`Application.streamingAssetsPath`，不可能直接指向某个包在包缓存里的解析路径）。

**两条通道的取舍**：私服通道优点是游戏侧只改版本号即可升级、不需要手工下载解压校验，适合内网
多台机器/多个游戏并行开发/需要频繁试验不同版本号的场景；zip 通道优点是不依赖任何常驻服务、产物
自带哈希锁文件可离线校验完整性，适合没有内网私服、或需要长期归档某个版本号产物的场景。两者不是
互斥关系，`.github/workflows/release.yml` 仍然只把 zip/lock 与三个 `.tgz` 一并作为 GitHub Release
附件上传，不在托管运行器上启动或依赖任何私服实例（私服是内网/本机基础设施，不适合放进公网 CI）。

## 4. 关键技术决策的落地细节

### 4.1 确定性

核心库不读取任何引擎时间源（不调用 `DateTime.Now`、不使用 Unity 的 `Time.deltaTime`），固定步长的 `dt` 只能来自 `SimClockHost.advance` 或 `TurnScheduler.nextStep`；不使用系统级 `Random`，一切随机经 `RngHost` 按用途分流（掉落流、AI 流、技能流互不干扰）；浮点运算在结算管线内固定运算顺序（先加法后乘法、同类项按声明顺序累加），避免因运算顺序不同导致同种子不同结果；回放录像格式 = 意图序列（`SimStep` 输入 + 每步的输入意图列表）+ 初始种子状态，不记录中间状态快照，靠重放意图重新推导状态。

### 4.2 事件总线

`EventBus` 采用"同步派发 + tick 末批处理"：`WorldSim.tick` 的第 7 步统一派发本 tick 内产生的全部事件（见 `03_运行时骨架.md` 第 4.2 节八步顺序），tick 中间产生的事件先入队、tick 末尾按产生顺序批量派发，保证订阅方看到的事件顺序与逻辑因果顺序一致；事件类型登记表（`found.event_catalog`）由工具链的生成脚本读取数据表定义、生成 C# 常量类（例如 `EventKeys.CombatDamageDealt`），避免手写字符串拼错。

### 4.3 数据加载

Unity 侧经 `IResourceLoader.loadAsync(kind: data_table)` 读取 JSON 文本，交给 `DataRegistry` 解析、校验、登记；编辑期提供"热重载"开关（`Game.<Game>` 侧监听 JSON 文件变化，触发 `DataRegistry` 重新加载并发出 `data.load_completed`），仅限编辑器内构建，发布构建关闭。

### 4.4 存档

存档格式 = JSON + `IFileSystem.writeTextAtomic` 原子写入（先写临时文件再原子替换，杜绝写到一半崩溃损坏存档）；架构的 `user://` 逻辑路径对应 Unity 的 `Application.persistentDataPath`，由 `Adapter.Unity` 内 `IFileSystem` 实现映射，`core/` 层完全不知道具体路径。

### 4.5 2D 渲染

`Transparency Sort Axis` 按 Y 轴设置，配合 `IRenderer2D.setTransform` 的 `sortY` 参数实现"越靠下越靠前"的 2.5D 遮挡关系；纸娃娃分层用 Sorting Group 把身体/装备/武器等层打包为一个视觉整体，随主体统一排序；受击闪白、溶解等效果用 Shader Graph 编写，对外只暴露 `setShaderParam` 约定的数值参数；高频短生命周期的特效走 `GPUParticles`（Unity VFX Graph 或 Shuriken 二选一，阶段 4 定）配对象池；镜头固定俯角，用正交相机 + 固定偏移实现 `ICamera.configure` 的语义（本项目不启用可自由旋转视角）。

### 4.6 UI

UGUI + TextMeshPro 承担 `IUISurface` 的 Unity 侧实现与 `presentation/ui` 框架的界面绘制；中文字体用 Noto Sans CJK SC（思源黑体同源，与 Source Han Sans 同属 Adobe/Google 联合发布的同一套字形，SIL Open Font License，可随项目分发；实际落地文件见 `assets/_placeholder/fonts/README.md`）；UI Toolkit 列为后续评估项，本阶段不采用，避免引入第二套 UI 技术栈增加维护成本。

### 4.7 寻路

`INavigation2D` 接口之后封装一个第三方 2D 寻路包（NavMeshPlus 或 A* Pathfinding Project），阶段 4 用同一张测试地图各跑一遍导航网格生成与路径查询、比较接入成本与性能后二选一；`core/` 与游戏层代码只调用 `INavigation2D` 契约，不感知具体寻路包，更换寻路包不影响 `core/` 一行代码。

## 5. 三方角色

|---|---|---|

## 8. 执行规范

每一个派发给执行层（Sonnet 子 agent）的任务，必须是自包含提示词，至少包含以下五项：

1. **目标**：一句话说明这个任务要产出什么，不依赖对话上下文即可理解。
2. **涉及文件**：明确列出要新建/修改的文件路径（绝对路径或相对仓库根路径）。
3. **契约引用**：指向 `architecture/` 对应文档的具体章节（例如"实现 `02_引擎适配层.md` 第 1.3 节 `IRenderer2D`"），任务不得凭空发明契约签名。
4. **验收标准**：可执行的测试命令或校验命令（例如 `dotnet test Tests.Foundation`、`python toolchain/validate_data.py`），不接受"看起来对"这种不可验证的标准。
5. **禁止事项**：明确列出这个任务不允许做的事（例如"禁止修改 `Core.Foundation` 之外的项目""禁止新增架构原语""禁止引入网络请求"）。

设计层在收到执行层的完成汇报后，必须独立复核（跑一遍验收标准里给的测试/校验命令、抽查关键文件的实际内容、必要时对照契约文档逐条核对），复核通过才计入该任务完成；执行层的自我汇报不能替代复核。任何执行层因契约不清、发现架构缺口而无法继续的情况，如实上报给设计层，不允许在游戏层"绕过"实现（对应 `01_分层与依赖.md` 第 6 节禁止事项第 5 条）。

## 9. 估算前提

- 人力模型：一人（用户）+ AI 代理（设计层 + 执行层），按"全职投入"估算每周可用时间。
- 数字口径：本计划给出的周期是**首版基准**，允许 **±30%** 浮动；实际进度以里程碑验收是否通过为准，不以日历时间为准——即某阶段验收标准未达成前不得推进到下一阶段（除非明确标注"与阶段 N 并行"）。
- 阶段 0～5 均有明确终止条件（对应验收标准全部达成）。
- 每阶段的"依赖"一栏只列硬依赖（上一阶段验收不过就无法开始的关系），并行阶段（4、5）之间没有硬依赖，只有资源占用上的软性协调（同一用户精力有限，需要交替确认）。

## 20. 变更控制

- **改架构**：任何触及 `architecture/` 文档集定义的内容（新增/修改层、模块、契约接口、事件、数据表结构，或新增效果/光环/事件/物件/任务目标/对话动作等原语）一律先走 `12_扩展与变更流程.md` 规定的 ADR 流程，经设计层确认后才允许改动对应文档与实现，本计划不承载这类变更的决策权。
- **改计划**：本文档描述的分工方式、阶段划分、周期估算、验收标准如需调整（例如某阶段实际耗时超出 ±30% 需要重排后续里程碑），在第"文档变更记录"表追加一行说明日期、摘要、受影响的阶段/章节，不需要走 ADR 流程（因为这类变更不改变架构本身）。
- **两类变更的判断边界**：判断一次变更是"改架构"还是"改计划"，只看是否触及 `architecture/` 文档集定义的内容——触及即改架构，否则即改计划；执行层若在任务中发现"当前架构不够用"，如实上报设计层判断类型，不得自行决定绕过流程直接改代码（`01_分层与依赖.md` 第 6 节禁止事项第 5 条、`13_新游戏接入指南.md` 立项检查表最后一条）。

## 附：本计划中估算最不可靠的阶段

**阶段 4（Unity 适配层 + 表现层 + UI 套件）是全文估算最不可靠的一项**，理由：

阶段 4 是首次把架构接口在真实引擎上落地，2D 寻路包选型与 URP 自定义 Shader Graph 效果在不同显卡上的表现差异（风险 3）带来一定不确定性；但接口层已用 `INavigation2D`/`IRenderer2D` 隔离，替换或调整不影响 `core/` 一行代码，使风险敞口可控。

建议：阶段 4 保留比 ±30% 更宽的弹性，并在第 2 周末设一个内部检查点，若接口落地或第三方包接入明显超出预期，及时评估范围与排期调整。
