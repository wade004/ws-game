## 第 12 条：`TableSchema` 没有层与模块归属元数据

**现象**：编辑器导航树"层→域→表"只能靠编辑器自己维护一份从 01 文档人工抄录的域到层对照表；上游新增域或调整分层时，编辑器不会自动跟上，新表落到"其他"。

**根因**：`TableSchema` 此前只登记数据校验所需的结构（主键、字段、迁移链），没有登记"这张表属于哪一层、哪个模块"这类导航用元数据——这类信息只存在于架构文档的自然语言表格里。

**处理**：[ADR-0022](../adr/0022-登记表补充导航与编辑元数据.md) 决策 1。`TableSchema` 新增只读属性 `Layer`（架构分层，七值枚举，对应 01 第 4 节 L-1～L5）、`Module`（模块名，与 01 第 1.1 节"模块"列一致）、新增链式方法 `WithOwnership(layer, module)`（一次性登记，重复调用抛异常）。全部 63 张已登记表在各层 `schema catalog` 构造 `TableSchema` 的现场追加 `.WithOwnership(...)` 调用，逐表填齐。

**涉及文件**：`core/foundation/data_registry/contracts/{TableSchema.cs, SchemaLayer.cs}`；全部 30 个声明 `TableSchema` 的 schema 文件（`core/numbers/archetype/contracts/ArchSchemas.cs` 等，完整清单见提交 diff）。

**验证**：`presentation/assembly/tests/SchemaAuditTests.cs` 新增 `TableOwnership_*` 系列用例（未登记报错/已登记放行/Domain 不一致报错/命名例外未显式声明报错）；`RealRegisteredSchemas_WithRepoAllowlist_ZeroErrors` 门禁测试对全部真实登记表断言 0 error，已通过。

**对消费方提示**：导航树可直接读取 `toolchain/validator --list-tables --json` 新增的 `layer`/`module` 字段生成，不再需要维护对照表。

## 第 13 条：三张表命名不符合"域.表"约定

**现象**：`camera_profile`、`ui_layout_definition`、`shell_menu_definition` 三张表是单段名，编辑器需要为其单独写解析域名的例外。

**根因**：这三张表是历史遗留命名（04 变更记录 2026-09-05 行"补 4 行已落地但未登记的表"时一并登记，未按"域.表"约定改名）。

**处理**：[ADR-0022](../adr/0022-登记表补充导航与编辑元数据.md) 决策 1。**不改表名**（改名是破坏性变更，波及内容数据文件名与既有测试，本版不做）。`TableSchema` 新增只读属性 `Domain`（默认取表名第一段），新增链式方法 `WithDomain(domain)`；这三张表在各自 schema 文件里显式登记 `Domain` 为 `camera`/`ui`/`shell`。04 第 2.2 节补充"命名例外"说明，注明工具应统一读取 `Domain` 元数据。

**涉及文件**：`presentation/camera/schema/CameraSchemas.cs`、`presentation/ui/schema/UiLayoutSchema.cs`、`presentation/shell/schema/ShellMenuSchema.cs`；`architecture/04_数据与内容管线.md` 第 2.2 节。

**验证**：`SchemaAuditTests.TableOwnership_NamingExceptionTableWithoutExplicitDomain_ReportsError`（反例：命名例外表未显式 `WithDomain` 时报错）；门禁测试对真实登记（三张表均已正确登记）断言 0 error。

**对消费方提示**：`toolchain/validator --list-tables --json` 每张表新增 `domain` 字段，编辑器解析域名应统一读取这个字段，不要再自行解析表名首段。

## 第 14 条：`FieldSchema` 没有语义分组元数据

**现象**：编辑器通用表单视图（产品文档 5.4.1 节）只能按字段名与类型启发式分组，分组可能与登记时的设计意图不符。

**根因**：`FieldSchema` 没有"基础/引用/数值/表现/高级"这类语义分组的登记，产品文档 5.4.1 节此前写"未来若核心库补充字段分组元数据，编辑器优先读取显式声明"，一直未兑现。

**处理**：[ADR-0022](../adr/0022-登记表补充导航与编辑元数据.md) 决策 2。`FieldSchema` 新增只读属性 `Group`（五值枚举，与产品文档五组一一对应）。为避免对全仓超过 800 个已登记字段逐一手工登记带来的重复劳动与持续性遗漏风险，`Group` 未显式登记时按固定规则计算默认值（主键/名称描述类文本键→基础；`Reference`/`IdList`/`Id`→引用；`Number`/`Int`→数值；名称含表现类关键词→表现；其余→高级），新增链式方法 `WithGroup` 用于覆盖规则误判的少量字段（如 `display.map.icon_id` 一类已通过默认规则正确归类、不需要覆盖的字段不再逐一列出）。

**涉及文件**：`core/foundation/data_registry/contracts/{FieldSchema.cs, FieldGroup.cs}`。

**验证**：`core/foundation/data_registry/tests/SchemaMetadataTests.cs` 的 `Group_*` 系列用例覆盖五类默认规则各一个正例 + `WithGroup` 覆盖用例；`SchemaAuditTests.FieldGroup_*` 覆盖门禁检查；`--schema-audit` 对全仓 783 个已登记字段跑一遍，0 error。

**对消费方提示**：`toolchain/validator --list-tables --json` 每个字段新增 `field_meta.group`，编辑器表单分组应直接读取这个字段，不再需要自己的启发式规则；产品文档 5.4.1 节已同步改为"已提供"。

## 第 15 条：时间字段与时间作用域无类型级标记

**现象**：时间字段只能靠 04 第 3.1 节的字段名清单识别，记录属于探索还是战斗作用域没有 schema 或数据定义，框架内部"时间字段与时间模型一致"校验规则的判定逻辑不对外可见，编辑器按表名首段猜作用域，猜错时用错误的单位后缀（"秒"/"回合"）误导内容作者。

**根因**：`TimeFieldConsistencyRule`/`TimeFieldDeclaration` 的判定逻辑（哪些表哪些字段是时间字段、各自对照哪个作用域）只存在于各层 `schema catalog`（`RulesSchemaCatalog`/`GameplaySchemaCatalog`）内部手写的登记列表里，没有暴露成登记表本身的元数据或公开只读入口。

**处理**：[ADR-0022](../adr/0022-登记表补充导航与编辑元数据.md) 决策 3。`FieldSchema` 新增只读属性 `Unit`（含"时间模型单位"取值），`TableSchema` 新增只读属性 `TimeScope`（无/探索/战斗/两者皆有）。新增公开静态工具类 `Core.Foundation.SimLoop.TimeModelRules`（`GetTimeScope(TableSchema)`/`IsTimeField(FieldSchema)`），把此前封装在 `TimeFieldConsistencyRule` 内部的判定入口对外暴露。按 `RulesSchemaCatalog`/`GameplaySchemaCatalog` 里已实际接线的 `TimeFieldDeclaration` 列表逐一核对，给对应表登记 `TimeScope`、对应字段登记 `Unit=Time`：`skill.def`（`cast_time`/`channel_time`/`cooldown_duration`/`charges.recharge_time`，`TimeScope=Combat`）、`skill.aura_def`（`duration` 及 `effects[].params.interval`，`TimeScope=Combat`）、`skill.proc_def`（`internal_cooldown`，`TimeScope=Combat`）、`arch.power_type`（`regen_in_combat`/`regen_out_of_combat`/`decay_out_of_combat`，`TimeScope=Both`）、`spawn.table`（`respawn_timer`，`TimeScope=Exploration`）。04 第 3.1 节的自然语言清单保留作说明，改为不再是唯一权威来源。

**涉及文件**：`core/foundation/data_registry/contracts/{FieldSchema.cs, TableSchema.cs, FieldUnit.cs, TimeScope.cs}`、`core/foundation/sim_loop/schema/TimeModelRules.cs`、`core/rules/skill/schema/SkillSchemas.cs`、`core/numbers/power_set/contracts/PowerSchemas.cs`、`core/gameplay/spawn/contracts/SpawnSchemas.cs`、`architecture/04_数据与内容管线.md` 第 3.1/3.4 节。

**验证**：`SchemaMetadataTests.TimeModelRules_*`（读取元数据的公开入口）、`SchemaAuditTests.TimeScopeDeclared_*`（Unit=Time 但表未声明 TimeScope 报错/已声明放行）；`--schema-audit` 新增 `time_unit_missing` 检查对已知的 10 个时间字段逐一核对，0 error。

**对消费方提示**：`toolchain/validator --list-tables --json` 每张表新增 `time_scope`、每个字段新增 `field_meta.unit`；编辑器判定字段单位后缀应改读 `field_meta.unit`，判定记录所属时间模型 mode 应改读所属表的 `time_scope` 对照 `found.time_model.scope=<该值>` 的那条记录，不再按表名首段猜。`TableSchema.TimeScope` 为"两者皆有"（目前只有 `arch.power_type` 一张表）时，具体某条记录/字段实际归属探索还是战斗由字段名本身语义决定（如 `regen_in_combat` 显然是战斗），编辑器可按已实现的固定字段清单继续区分，本版未新增"记录级/字段级 TimeScope 覆盖表级 TimeScope"的更细粒度登记机制——如后续需要，走独立 ADR。

## 第 16 条：`IdList` 字段没有引用目标元数据

**现象**：`IdList` 字段没有 `ReferenceTable`/`ReferenceDomain` 之类的引用目标元数据，编辑器无法为其输入区提供按域筛选的自动补全候选或跳转；产品文档 5.4.2 节要求 `IdList` 输入区支持按域筛选的自动补全。

**根因**：`FieldSchema` 对 `Reference` 种类已有 `ReferenceTable`/`ReferenceDomain` 记法，但从未有 `IdList` 字段使用它——`reference_integrity` 校验此前也只处理标量 `Reference` 字段，不覆盖数组元素。

**处理**：[ADR-0022](../adr/0022-登记表补充导航与编辑元数据.md) 决策 4。`FieldSchema` 对 `IdList` 种类沿用与 `Reference` 相同的 `ReferenceTable`/`ReferenceDomain` 构造参数；`DataRegistry.LoadAll` 的 `reference_integrity` 检查扩展为对 `IdList` 逐元素核对，问题定位到具体下标（`refs[2]` 一类路径）。新增 `FreeIds`/`FreeIdsReason` 只读属性与 `WithFreeIds(reason)` 链式方法，供确属自由 id 列表的字段显式声明理由（与 `ReferenceTable`/`ReferenceDomain` 互斥）。

对全仓 22 个已登记 `IdList` 字段逐一核实语义：

- 登记为引用目标（4 个）：`item.template.affixes`→`item.affix`、`item.slot_definition.accepts`→`item.slot_definition`（自引用，跨槽兼容）、`item.set.pieces`→`item.template`、`world.map.allowed_difficulties`→`diff.tier`（此前因该表"未登记进 DataRegistry"未做引用检查，现已登记，补上）。
- 登记为自由列表（18 个）并写明理由：局部声明的挂点/槽位/子区域名字（`display.map.sockets`/`slots`、`world.map.regions`）、内容作者自由标签或混合词汇（`skill.def.tags`、`gobj.template.tags`、`skill.aura_def` 的 `immunity` 效果 `params.schools`、`skill.spell_mod_def.affects.{schools,tags}`、`creature.template.{npc_flags,immunities}`）、分层边界或既有测试装配约束当前无法静态声明引用目标的（`arch.class.power_types`、`arch.race.passive_auras`、`item.template.socket_ids`（07 第 1.6 节扩展位，本版不展开）、`skill.spell_mod_def.affects.skill_ids`、`gobj.template.type_data.linked_object_ids`、`difficulty.tier.modifier_aura_refs`、`encounter.level.{encounter_sequence,entry_difficulty_options}`、`presentation/vfx_sfx` 的 `sfx.def.variants`）。

**涉及文件**：`core/foundation/data_registry/contracts/FieldSchema.cs`、`core/foundation/data_registry/core/DataRegistry.cs`（`ValidateIdList` 改为实例方法并接入引用检查）；22 个字段分布在 `core/carriers/{creature,gobj,item}`、`core/foundation/{display_info,scene_router}`、`core/gameplay/{difficulty,encounter}`、`core/numbers/archetype`、`core/rules/skill`、`presentation/vfx_sfx`。

**验证**：`SchemaMetadataTests.IdList_*`（元素全存在放行/单个缺失报 `reference_integrity` 且路径含下标/未登记引用目标只做格式检查）、`SchemaAuditTests.IdListReferenceTarget_*`（未登记引用目标报 `idlist_reference_target`/`FreeIds`放行/`ReferenceTable`放行）；两条既有测试因语义辨析需要同步修正（详见"备注"下方说明），修正后全绿：`Tests.Rules.Skill.SpellModTests.Affects_FiltersBySkillId`（该字段实为过滤条件而非内容关系，改登记 `WithFreeIds`）、`Tests.Carriers.Item.ItemValidationRulesTests.SetMembershipRule_MismatchedPieces_ReportsIssue`（测试夹具改为让 `pieces` 指向另一件真实存在的物品，而不是一个不存在的 id——"不存在的 id"现由更早的 `reference_integrity` 拦下，本规则测的是"两条记录互相不认可对方"这条更窄的业务判断，两者不是同一件事）。

**对消费方提示**：`toolchain/validator --list-tables --json` 每个 `IdList` 字段新增 `field_meta.reference_table`/`reference_domain`/`free_ids`，编辑器应据此为已登记引用目标的字段提供自动补全/跳转，为 `free_ids=true` 的字段维持纯文本标签编辑（不提供补全）。

## 第 17 条：`IDataRegistryView.RecordCount` 默认实现在阻断态抛异常

**现象**：1.15.0 新增的 `IDataRegistryView.RecordCount` 默认实现按 `Tables`/`GetAll` 求和；`GetAll` 在校验阻断态（`_blocked` 为真）会抛 `System.InvalidOperationException`（消息"数据校验未通过，禁止读取"），因此阻断态下读 `RecordCount` 同样抛异常。已用最小夹具复现：一个表是坏 JSON（本次加载不进入已加载表集合）、另一个表是能正常解析的一条记录，整体报告阻断；此时通过 `IDataRegistry`（接口类型）持有的 registry 访问 `RecordCount`，命中该接口默认实现内部的 `GetAll` 调用，抛出上述异常（复现测试：`Core.sln` 反例见下方"验证"一行；异常类型/消息与上游反馈原文逐字一致）。编辑器在存在错误的数据集上仍需要显示记录数，此前只能退回自行按合并视图求和。

**根因**：`RecordCount` 默认实现为了兼容"只持有 `IDataRegistryView`、不持有具体 `DataRegistry` 实现"的第三方/测试替身（本仓库 `core/carriers/creature/tests/CreatureTestSupport.cs` 的 `UnknownTierRegistryView` 即一例），只能用 `Tables`/`GetAll` 这套通用求和算法兜底；而 `GetAll` 的阻断态限制（防止调用方把未通过校验的数据当权威数据用）与"读取记录计数"这一纯诊断需求本不应该共用同一个拒绝条件，但默认实现别无选择只能继承该限制。

**处理**：不改默认实现本身（它仍是"只有接口、没有具体实现"场景下唯一通用的兜底算法，继续可能在阻断态抛异常，已在其 XML 注释里写明并建议改用下述新成员），根治落在具体的 `DataRegistry` 类型与接口新增成员两处：

- `DataRegistry` 内部在 `LoadAllCore`/`Reload` 期间维护的 `_tables`（按表合并去重后的已加载记录快照）本就贯穿阻断态与非阻断态持续可读（`_blocked` 只拦截 `Get`/`GetAll`/`Query`，不拦截内部字典本身）；`DataRegistry` 新增公开同签名属性 `RecordCount`，直接对 `_tables` 逐表累加 `Records.Count`，不经过 `EnsureReadable`。按 C# 8+ 默认接口成员规则，实现类提供的同签名公开成员覆盖接口默认实现——无论调用方以 `DataRegistry` 具体类型还是以 `IDataRegistryView`/`IDataRegistry` 接口类型持有该实例，读到的都是这个永不抛出的实现。未 `LoadAll` 过时 `_tables` 为空字典，返回 0；同一宿主重复 `LoadAll` 是整体覆盖 `_tables`（不是累加）；`Reload(table)` 只替换该表的条目，其余表不受影响，计数自动反映最新状态。
- `IDataRegistryView` 新增带默认实现的 `bool TryGetRecordCount(out int count)`：默认实现 `try { count = RecordCount; return true; } catch (System.InvalidOperationException) { count = 0; return false; }`——只精确捕获 `DataRegistry.EnsureReadable` 阻断态抛出的那个类型，不用 `catch (Exception)` 掩盖其它意外异常。`DataRegistry` 同样显式覆盖为直接返回 `true` + 计数（其 `RecordCount` 已永不抛出，不需要 try/catch）。两个新成员均为带默认实现的接口成员，不要求任何现有实现类改动即可编译通过，不构成"公开 API 表面"意义上的破坏性变更。
- `ContentValidationAssembly.Run` 此前为了在阻断态也能拿到记录数，另开了一条订阅 `data.load_completed` 事件的旁路（非阻断态读 `IDataRegistryView.RecordCount`、阻断态读事件值），两条路径分叉、只是数值上"恰好相等"。`DataRegistry.RecordCount` 阻断态也不抛之后，这条旁路不再必要：`Run` 改为无条件读 `registry.RecordCount`（`CreateRegistryCore` 内部构造的就是具体 `DataRegistry` 实例，读到的正是上面那个覆盖实现），与 `CreateRegistry`+调用方自行 `LoadAll`/`Reload` 场景统一成同一个读数入口，不再是两套独立实现。

**口径说明（编辑器计数 vs 框架计数）**：核对编辑器侧实现（`EditorSession.ValidateAll` 内 `Merged.Tables.Sum(t => Merged.GetRecords(t).Count)`，`Merged` 由 `MergedView.Build(Roots, Registry.Tables)` 按框架合并后的表集合构建）与框架侧 `DataLoadCompletedEvent.RecordCount`（`LoadAllCore` 内部边解析边累加的 `recordCount` 局部变量，单根表按 `partial.RecordsInOrder.Count` 计，跨根合并表按去重后追加进 `mergedRecords` 的次数计，覆盖行是替换不追加、不重复计数），两者口径一致——都是"覆盖层合并、按表去重后的记录条数"，均已由既有测试互证相等（编辑器侧 `RegistryRecordCount_EqualsMergedRecordCount_OnCleanSnapshot`；框架侧本次新增 `RecordCount_EqualsDataLoadCompletedEventRecordCount_EvenWhenBlocking`，验证阻断态下同样相等，不只是非阻断态"恰好相等"）。`DataRegistry.RecordCount` 直接读取 `_tables`（即 `LoadAllCore` 最终写入的合并结果），与 `recordCount` 局部变量对每张表的计数规则逐条相同，本质是对同一份计数的快照读取，不存在第二套口径分叉的风险；未发现两者口径不一致，因此不需要"以事件口径为准、说明差异"这一步。
