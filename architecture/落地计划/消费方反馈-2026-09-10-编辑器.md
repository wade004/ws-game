## 高优先级

### E1 产物内 validator 现场编译受消费方 `Directory.Build.props` 影响

**复现**：把只读的 `dist/ws-game-1.14.0.zip` 解压到临时目录，在其上级目录放一个
`Directory.Build.props`（`<TreatWarningsAsErrors>true</TreatWarningsAsErrors>`），运行
`validate_data.py`。实测两种消费方 props 组合都能复现失败：

- 只带 `TreatWarningsAsErrors=true`：`toolchain/validator/DiskFileSystem.cs`/`Program.cs` 的
  可空引用类型注解（`string?`）在未继承仓库根 `Nullable=enable` 时触发 `CS8632`，被提升为错误。
- 额外带 `GenerateDocumentationFile=true`（常见的"要求生成文档"策略组合）：
  `Program.cs(24,26)` 报 `CS0419`——`<see cref="DataRegistry.LoadAll"/>` 未指定参数列表，与
  `DataRegistry.LoadAll()`/`LoadAll(IReadOnlyList<IDataSource>)` 两个重载都能匹配。

两种失败路径根因不同，但都是"MSBuild 沿项目目录向上找 `Directory.Build.props`，继承到消费方仓库
自己的设置"这一件事导致的。

**根因**：`toolchain/validator` 此前一律用 `dotnet run --project` 现场编译，且没有自己的
`Directory.Build.props` 兜底，解压落在消费方仓库工作树内时会隐式继承消费方的构建策略。

**处理方式（三层，任务书要求"三件都做"）**：

1. 修正 `Program.cs(24)` 的歧义 cref 为具体重载
   `DataRegistry.LoadAll(System.Collections.Generic.IReadOnlyList{Core.Foundation.DataRegistry.IDataSource})`；
   全仓扫描到 4 处同类"`DataRegistry.LoadAll` 泛指两个重载"的裸 cref
   （`core/carriers/assembly/tests/CarriersAssemblyTests.cs`、
   `core/foundation/data_registry/contracts/Events.cs`、`IDataSource.cs`、
   `core/gameplay/achievement/schema/AchievementSchemas.cs`），按语境改为具体重载 cref 或
   `<c>DataRegistry.LoadAll</c>` 纯文本（泛指两个重载、不需要指向某一个时）。
2. `build.ps1 -Dist`/`-Release` 新增步骤"5.057"：在 `dist/<ver>/toolchain/validator/` 下生成一份
   空 `Directory.Build.props`（`<Project></Project>`，LF、UTF-8 无 BOM）——MSBuild 只取"向上遇到
   的第一份"，从根上挡住消费方仓库根的设置被继承；**只在打包时生成，不在源码树常驻**（源码树里
   `toolchain/validator` 依赖仓库根 `Directory.Build.props` 的 `LangVersion`/`Nullable`/
   `TreatWarningsAsErrors`/`GenerateDocumentationFile` 四项设置，常驻空文件会截断这份继承、削弱
   仓库内 `TreatWarningsAsErrors=true` 这条门禁）。
3. `build.ps1` 同一步骤把 `Core.sln` 第 1 步已经构建出的 `toolchain/validator/bin/`
   （`Validator.dll`/`.deps.json`/`.runtimeconfig.json` + 六个依赖 DLL 的标准 SDK 输出布局）整份
   拷进 `dist/<ver>/toolchain/validator/bin/`；`validate_data.py` 第二道校验改为优先
   `dotnet <Validator.dll 路径>` 直接执行——这条路径完全不触发 MSBuild/`Directory.Build.props`
   解析，从根上绕开这一整类问题；找不到预编译产物（源码仓库自测、或消费方精简掉了 `bin/`）才退回
   `dotnet run --project`（此时靠第 2 层的空 `Directory.Build.props` 兜底）。四个私服包之一
   `com.gamefoundation.toolchain` 的 `Tools~/validator/` 内容取自同一份 `dist/<ver>/toolchain/`，
   两条通道自动同步，不需要单独打包逻辑。

**涉及文件**：`toolchain/validator/Program.cs`、`core/carriers/assembly/tests/CarriersAssemblyTests.cs`、
`core/foundation/data_registry/contracts/{Events.cs,IDataSource.cs}`、
`core/gameplay/achievement/schema/AchievementSchemas.cs`、`build.ps1`、`toolchain/validate_data.py`、
`check.ps1`（包清单一致性步骤放行 `validator/bin` 路径 + 新增断言其存在）。

**测试/门禁**：`toolchain/tests/test_validate_data_precompiled_validator.py`（2 例，覆盖优先走
预编译路径、找不到时退回现场编译两种分支）；`check.ps1`"包清单一致性"步骤新增对
`com.gamefoundation.toolchain` 包含 `Tools~/validator/bin/Validator.dll` 与
`Tools~/validator/Directory.Build.props` 的正向断言。手工复现验证：用真实生成的
`dist/ws-game-1.14.0.zip` 在带 `TreatWarningsAsErrors=true` + `GenerateDocumentationFile=true` +
`Nullable=enable` 的消费方 `Directory.Build.props` 下跑 `validate_data.py`，根治前失败
（`CS0419`），根治后 `exit=0` 且日志显示"正在运行预编译的 toolchain/validator/bin/Validator.dll"。

**状态**：已根治，已验证。

### E2 `get_framework.ps1` 依赖同目录 `_hash.ps1`，两者都只在 zip 内（引导问题）

**根因**：`get_framework.ps1` 此前 dot-source 同目录 `_hash.ps1` 加载 `Get-Sha256FileHash`；但
游戏侧引用本脚本的典型方式恰恰是"只下载 `get_framework.ps1` 单个文件"（本脚本自身尚未落地前，也
无法先跑它去拉取 `toolchain/` 整个目录），形成"跑本脚本前得先有 `_hash.ps1`，但拿到 `_hash.ps1`
的唯一途径是先用本脚本拉取"的引导死锁。

**处理方式**：

1. 把 `Get-Sha256FileHash` 函数体原样内联进 `get_framework.ps1`（`# BEGIN/END INLINE` 标记
   包裹），不再 dot-source `_hash.ps1`；`toolchain/_hash.ps1` 本身继续保留，供仓库内其它脚本
   （`build.ps1`、`sync_package_content.ps1`）共用。
2. Release 附件集合新增 `get_framework.ps1`（固定文件名，自包含后的推荐下载方式）；继续附上
   `_hash.ps1`（本脚本自身不再读取它，纯粹兼容消费方现有"下载两个文件"的还原脚本）。
   `.github/workflows/release.yml` 新增一个无条件早期步骤把这两个文件拷到 `dist/`，纳入必需
   附件集合（`get_framework.ps1`/`_hash.ps1` 是纯源文件，任何 commit 下都确定性相同，不参与
   "zip 缺失、其它构建产物已存在 -> 阻断混批"那条判定）；`build.ps1 -Release` 末尾打印/执行的
   `gh release create` 命令同步新增这两个附件。
3. 根 `README.md`"游戏侧引用与升级"一节列出完整 Release 附件集合并说明用途；
   `toolchain/README.md`"`get_framework.ps1`"一节补充"下载方式"（三种等价途径）与依赖边界勘误。

**涉及文件**：`toolchain/get_framework.ps1`、`build.ps1`（`-Release` 打印/执行的
`gh release create` 命令）、`.github/workflows/release.yml`、`README.md`、`toolchain/README.md`。

**测试/门禁**：`toolchain/tests/test_get_framework_hash_inline_consistency.py`（2 例：确认脚本
不再 dot-source `_hash.ps1`；内联函数体与 `toolchain/_hash.ps1` 原版逐字节一致的静态比对，任一处
改动而另一处未同步会被拦下）。`release.yml` 的新增/改动 `run:` 正文已用
`[System.Management.Automation.Language.Parser]::ParseInput` 风格的静态解析核对过纯 ASCII 合规
（文件头既有判断记录的硬性要求）。

**状态**：已根治，已验证（含 `-FromLocalDist` 端到端手工验证：自包含的 `get_framework.ps1`
单独复制到全新目录，不携带 `_hash.ps1`，正常完成校验与落地）。

### E3 锁文件含本机绝对路径

**根因**：`-FromLocalDist` 时 `source.local_path` 写入调用方本机的绝对路径；`ws-game.lock`
约定提交进游戏仓库，换机器重新运行会因本机路径不同产生一次与框架引用内容无关的锁文件 diff。

**处理方式**：

1. `source` 不再写绝对路径：`channel` 字段保持不变（`editor/docs/编辑器产品文档.md` 已把
   `source.channel` 记为编辑器探测框架来源通道的契约字段，`channel: "zip"`/`"registry"`
   两个取值不能改名/删除），只把 `local_path` 换成相对信息 `zip_file_name`（不含目录的文件名）。
2. 判定"锁文件是否需要改写"从整份 JSON 字符串比较改为只比较 `version`/`git_commit`/`dlls`/
   `headless_dlls`/`validator_dlls`/`samples` 这几个描述"引用内容本身"的字段（新增
   `Test-LockContentEquivalent` 函数），`source` 字段的任何差异（含新旧字段名不同）不再触发
   改写判定，两台机器用不同本地路径引用同一份发布内容时表现一致；带旧格式 `source.local_path`
   的既有锁文件仍能被正常接受（比较时忽略该字段，不报错、不误判为内容不同）。

**涉及文件**：`toolchain/get_framework.ps1`。

**测试/门禁**：`toolchain/tests/test_get_framework_lock_source_no_local_path.py`（3 例）：
1) 生成的锁文件 `source` 不含本机绝对路径字符串；2) 两台"机器"（不同本地路径）引用同一份发布
内容，锁文件不应被重新写入（用文件 mtime 判定，不解析本机控制台代码页下的本地化输出文本——
同一份判断记录见文件头，规避已知的 GBK/UTF-8 解码陷阱）；3) 预置一份带旧格式
`source.local_path` 的锁文件，重新运行应正常工作且不触发改写。

**状态**：已根治，已验证。

### E6 示例数据自身 3 条警告，`--strict` 不过

**复现**：`python toolchain/validate_data.py --strict` 对合并根（`data/_framework` +
`data/_sample`）报 3 条 `expr_parsable`"疑似引用拼写错误"警告，均指向
`dialog.gossip_menu.json` 里 `dialog.sample_hunter` 两处 `visible_if` 表达式引用的
`quest.sample_hunt`，退出码 1。

**根因判断（证据）**：`quest.sample_hunt` 是 `data/_sample/quest/quest.def.json` 里真实存在、
合法登记的内容 id（`"id": "quest.sample_hunt"`），并且在表达式里的用法
`quest.is_available(quest.sample_hunt)`/`quest.is_active(quest.sample_hunt)` 正是 04 号文档第
6.3 节"点分标识符归类"描述的标准写法——`quest.is_available`/`quest.is_active` 是已在
`core/gameplay/quest/contracts/QuestExprSchemaEntries.cs` 登记的引用（参数类型
`ExprValueKind.Id`），`quest.sample_hunt` 作为其实参，域名与"quest"分组同名，按 ADR-0015 归类为
`Id` 字面量，语义上完全正确、不是拼写错误。**结论：数据合法，是规则误报**——
`core/foundation/expr/core/ExprValidator.cs` 的"疑似引用拼写错误"规则
（`CheckSuspiciousIdLiteral`）此前只认"把该 Id 本身也登记进 schema 签名表"这一种消除警告的
方式（见既有用例
`ExprAdr0015Tests.SuspiciousReferenceSpelling_NotReported_WhenGroupKeyIsRegistered`），对
"该 Id 正被用作某个已登记引用的实参、且那个实参位置的静态期望类型本身就是 `Id`"这一同样合法、且
更常见的场景没有对应豁免——任何"域名与某个分组同名的内容 domain"（`quest`、`world` 都是这样的
domain），只要把自己的 id 当参数传给该分组下任意一个已登记签名，就会系统性触发这条误报。

**处理方式（根治规则，不是改数据迁就）**：`ExprValidator.ValidateReference` 改为：处理每个实参
前先查一次调用本身的签名，若该实参位置的期望类型（`ExprSignature.ArgKinds[i]`）恰好是
`ExprValueKind.Id`，则该位置上的 Id 字面量不再检查"疑似拼写错误"；其它位置（期望类型非 Id、或
签名本身未知）行为不变，仍会正常报警告。`InferKind` 新增一个内部重载携带
`suppressSuspiciousIdWarning` 标志，只在这一处调用点按上述条件传 `true`。

**涉及文件**：`core/foundation/expr/core/ExprValidator.cs`、
`core/foundation/expr/tests/ExprAdr0015Tests.cs`、`core/foundation/expr/README.md`

### E7 生成工具在 Windows 写出 CRLF

**复现范围核实**：任务描述"`data/_sample`/`assets/_sample` 里 23 个 JSON/MD 文件"这一具体症状
在当前代码状态下 `git ls-files --eol` 已查不到（这两棵目录下的文件当前全部是 `i/lf w/lf`）——
`.gitattributes` 已经全局声明 `*.json`/`*.md` 为 `text eol=lf`，Git 在 `add`/检出时会强制规范化，
从 `git status`/`ls-files` 层面看不出生成器本身是否仍在写 CRLF 字节。改为直接审计生成器源码
（`grep` 全仓 `write_text(`/`open(..., "w"...)` 调用是否都带 `newline="\n"`），找到真实存在的
6 处遗漏，均在 `toolchain/gen_placeholder_assets.py`（`MANIFEST.json`、两处 `anchors.json`、
`frames.json`、两处 `README.md`）——这些文件在 Windows 上跑该脚本会现场写出 CRLF 字节，git 的
`eol=lf` 规范化只在 `add`/检出这一层生效，不影响脚本运行时刚落盘、尚未被 git 处理过的原始字节，
也不影响任何不经过 git 直接读取这些文件的下游工具。`toolchain/asset_import/common.py` 的
`write_envelope`/`write_json_pretty`、`toolchain/gen_event_constants.py` 本来就已经正确传了
`newline="\n"`，不需要改动。

**处理方式**：`gen_placeholder_assets.py` 6 处调用补齐 `newline="\n"`；新增
`toolchain/tests/test_generators_write_lf.py`，用 `ast` 静态扫描 `toolchain/` 下全部生成器脚本
（排除 `tests/`/`registry/`），断言任何 `.write_text(...)`/以写模式打开的 `open(...)` 调用都显式
传了 `newline`，防止未来新增/修改生成器时再次遗漏；`check.ps1` 新增"工作树文本文件无 CR"步骤，

（已用脚本转回纯 LF，该步骤新增后能在门禁层面拦住同类问题）。

**涉及文件**：`toolchain/gen_placeholder_assets.py`、
`toolchain/tests/test_generators_write_lf.py`（新增）、`check.ps1`。

**测试/门禁**：`test_generators_write_lf.py`（18 例，覆盖 `toolchain/` 下每个顶层生成器脚本）；

### E8 `validate_data.py` 未透传 `--json`

**处理方式**：新增 `--json`，把第一道骨架检查结果与第二道 `toolchain/validator --json` 输出合并

```json
{
  "skeleton": {
    "files_checked": 0,
    "roots_checked": 0,
```

编译失败打印了构建日志）时降级为 `{"raw_output": ..., "parse_error": ..., "returncode": ...}`，

**测试/门禁**：`toolchain/tests/test_validate_data_json_output.py`（4 例）：标准输出是单份合法

### E9 `--data-root` 相对路径按脚本目录解析

**根因**：相对路径此前按 `find_repo_root()`（本文件所在目录的上一级）解析，不是按调用方实际
运行时的当前工作目录——"从仓库根目录运行本脚本"这一惯例场景下两者恰好相同，看不出区别；游戏侧

绝对路径不受影响。文档（模块 docstring、`--data-root` 帮助文本）同步核对措辞。

**涉及文件**：`toolchain/validate_data.py`。

**测试/门禁**：`toolchain/tests/test_validate_data_relative_root_cwd.py`（2 例，`os.chdir` 切到
与脚本安装位置完全无关的独立临时目录）：从"游戏仓库根"用相对路径能正确找到数据目录；从与数据
目录无关的第三个工作目录调用同一个相对路径应报"目录不存在"（证明解析确实跟随当前工作目录变化，
不是恰好命中某个固定基准）。

**状态**：已根治，已验证。

### E10 `CreateRegistry` 路径拿不到记录计数

**根因**：`ContentValidationAssembly.Run`（一次性装配 + 加载 + 汇总）通过订阅
`DataRegistry.LoadAll` 内部发出的 `data.load_completed` 事件拿到精确记录数（阻断态下 `GetAll`
会抛异常，只有这条事件路径在阻断态下仍可用）；但 `ContentValidationAssembly.CreateRegistry`
（调用方自己持有 registry、自行决定何时调用 `LoadAll`/`Reload`，例如编辑器需要在用户操作间隙
重复单表 `Reload`）没有走这条装配逻辑，此前完全没有拿到记录总数的办法，只能自己遍历
`Tables`/`GetAll` 求和。

**处理方式（不破坏 ABI）**：`IDataRegistryView` 新增一个**带默认实现**的成员
`int RecordCount => Tables.Sum(table => GetAll(table).Count)`（C# 8+/`netstandard2.1` 支持的
默认接口成员，不要求任何已有实现类显式实现它，不是抽象成员——任务书明确要求"禁止给公开接口加
无默认实现的成员"，因为另一位并行工作的 agent 正在加"公开 API 表面差异"门禁，接口新增 abstract
成员会被判为破坏性变更）。`ContentValidationAssembly.Run` 非阻断态下改为直接读
`registry.RecordCount`（与 `CreateRegistry` 场景用同一个计算口径，不是两套互相独立、只是"恰好
数值相同"的实现）；阻断态下继续依赖事件订阅值（`GetAll` 会抛异常，只能保留这条路径，这是 `Run`
相对 `CreateRegistry` 调用方的本质优势——`Run` 自己控制 `LoadAll` 调用时机，能提前订阅到事件）。

**涉及文件**：`core/foundation/data_registry/contracts/IDataRegistry.cs`、
`presentation/assembly/ContentValidationAssembly.cs`、
`presentation/assembly/tests/ContentValidationAssemblyTests.cs`。

**测试/门禁**：`ContentValidationAssemblyTests` 新增 3 例：非阻断态下 `run.RecordCount` 与
`run.Registry.RecordCount` 相等；`CreateRegistry` + 调用方自行 `LoadAll` 后 `registry.RecordCount`
反映真实加载的记录数；`RecordCount` 默认实现正确对多张表求和（不是只统计第一张表）。`Core.sln`
全量 `dotnet test` 回归；`toolchain/abi_probe.ps1`（经 `check.ps1`"ABI 探针"步骤）确认通过——
默认接口成员不构成公开 API 表面的破坏性变更。

**状态**：已根治，已验证。

### E11 示例数据字段顺序与 schema 声明顺序不一致

**处理方式**：新增 `toolchain/format_data.py --schema-order [--check]`。字段顺序信息来源：
`toolchain/validator --list-tables --json` 新增的 `fields` 数组（`tables_list` 每个条目追加
按 `TableSchema.Fields` 登记顺序排列的字段名列表；`GetSchema` 与数据是否通过校验无关，即便

validator 子命令（"选最省事且可测的"方案）。按该顺序重排每条记录的字段，未在 schema 中登记的

**涉及文件**：`toolchain/validator/Program.cs`（`PrintJson` 新增 `fields` 字段）、
