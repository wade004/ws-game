## 现象与复现

原文见 `ws-game-editor` 仓库 `docs/上游反馈.md`（`phase/p4.2` 分支）第 1086～1138 行"52
`CasterWeapon`（编辑器结算预览字段形状）与 `StandardPlayer.EquippedInstances` 无转换 API"、
"53 `GrowthSimulation` 同 `tier`+`level` 生物模板取注册顺序第一条，不过滤 `faction_id`、无
歧义告警"。

### 第 52 条

编辑器 `src/Editor.Core/Sandbox/SettlementPreviewRequest.cs` 的 `CasterWeapon(TemplateId,
QualityId, AffixIds)` 是模板/品质/词缀三元组，框架 `core/sim/core/StandardPlayerBuilder.cs`
的 `StandardPlayer.EquippedInstances: IReadOnlyDictionary<Id, Id>` 是槽位→物品实例 id 映射，
两者字段形状不同，框架未提供两者之间的转换 API。编辑器侧 `StandardPlayerWeaponAdapter` 自建了
一层转换：`EquipmentHost.GetAllEquippedInstances(unitId)` 取到 `ItemInstance`，再手工搬运
`TemplateId`/`Quality`/`Affixes` 三字段拼成 `CasterWeapon`——纯搬运、不计算数值，已在 P4.2
落地并测试通过，不是阻塞项，但每个类似消费方都需要各自实现一遍同样的搬运代码。

### 第 53 条

`Core.Sim.GrowthSimulation.ResolveCreatureFamily`（`core/sim/core/GrowthSimulation.cs`）按
`ScenarioOpponentSpec.TierId` 收集全部同档 `creature.template` 记录，不按 `faction_id` 过滤；
`ResolveCreatureTemplateForLevel` 对同 `level` 的候选用严格 `>` 比较更新"当前最优"，同级时只有
`registry.GetAll("creature.template")` 收集顺序第一条能生效，且没有任何诊断/告警提示"同
`tier`+`level` 存在多条候选，已按顺序丢弃其余候选"。消费方样例数据集把玩家阵营占位生物
`creature.sample_hero`（`faction_id=fac.player`，文件内声明在前）与怪物
`creature.sample_beast`（`faction_id=fac.wildlife`）都登记为 `tier=creature.tier.sample_normal`、
`level=1`，`sim.scenario.sample_growth` 实际打的是 `sample_hero`（一个不适合作战斗对手的占位
生物），战斗必超时，成长仿真逐级样本恒为第 1 级一行、`Kills=0`。框架官方样例
（`core/sim/tests/data/creature/creature.template.json`）本身五条 `tier.sim_normal` 生物模板
`level` 分别为 1/5/10/15/20，互不重叠，且不含任何玩家阵营占位生物，未踩过这个坑——是消费方
自建场景的数据配平疏漏首次暴露了这一隐式行为。

## 根因

- 第 52 条：`StandardPlayer` 设计时只暴露了"槽位→实例 id"这一最基础映射，未考虑消费方需要
  的是身份字段三元组，是"契约面覆盖不全"而不是缺陷。
- 第 53 条：`ResolveCreatureFamily` 从最初实现起就只按 `tier`（可选）过滤，未曾按 `faction_id`
  过滤——历史设计假设"同一 `tier` 下的记录都是可打的怪物"，没有预见到消费方会把非战斗用途的
  占位生物也登记进普通怪物共用的 `tier`。属于既有实现的隐式假设，不是本次改动引入的新问题。

## 处理

### 第 52 条：`EquippedWeaponSummary` 转换 API

新增只读结构体 `Core.Carriers.Common.EquippedWeaponSummary`（`core/carriers/common/contracts/
EquippedWeaponSummary.cs`）：`TemplateId`/`QualityId`/`AffixIds` 三字段，静态工厂
`FromInstance(ItemInstance instance)` 原样映射三个身份字段，纯搬运不计算数值（同
`ItemInstance` 判断记录"物品实例只存身份"的口径）。

`EquipmentHost`（`core/carriers/item/core/EquipmentHost.cs`）新增两个方法，与既有
`GetAllEquippedInstances`（供 `EquipmentPersistable.Save` 用）同一模式：

- `GetEquippedWeaponSummary(Id unitId, Id slot): EquippedWeaponSummary?`——该槽位当前无装备时
  返回 `null`。
- `GetAllEquippedWeaponSummaries(Id unitId): IReadOnlyDictionary<Id, EquippedWeaponSummary>`——
  未装备任何物品时返回空字典。

两者均不要求 `slot` 一定是 `item.slot_definition.is_weapon` 的武器槽——`ItemInstance` 本身不
携带"是不是武器"这个判断，槽位是否为武器槽由调用方自行对照 `item.slot_definition` 判断。

`Core.Sim.StandardPlayer`（`core/sim/core/StandardPlayerBuilder.cs`）新增只读属性
`EquippedWeaponSummaries`（`StandardPlayerBuilder.Build` 内部一次性调用
`EquipmentHost.GetAllEquippedWeaponSummaries` 填充，不从 `chosenAffixes`/`qualityId` 等局部
变量另行拼一份，避免与 `EquipmentHost` 实际落库的身份字段产生潜在不一致）与建议签名一致的
便捷方法 `GetEquippedWeaponSummary(Id weaponSlotId)`。

审计范围内未发现框架内部有另一份手工搬运同样三字段的重复逻辑可供重构复用——
`ItemPersistable`/`EquipmentPersistable.Save` 序列化的是完整存档形状（含 `Count`/`Extra`），
字段集合与用途都不同，不适合改成复用本 API。

### 第 53 条：按阵营过滤 + 歧义诊断 + 全部过滤后显式抛异常

`ResolveCreatureFamily`（`core/sim/core/GrowthSimulation.cs`）新增两个入参
`IFactionMatrix factions`/`Id playerFactionId` 与一个出参
`out IReadOnlyList<GrowthOpponentAmbiguity> ambiguities`（内部方法，ABI 允许新增参数）：

1. 先按 `tier` 收集候选（`ScenarioOpponentSpec.TierId` 为空时退回取 `opponent.CreatureId`
   自身的 `tier`）。
2. 用 `factions.IsHostile(playerFactionId, candidate.FactionId)` 过滤出对玩家阵营敌对的候选
   ——方向是"从玩家阵营看候选是否敌对"，不是反过来。**判断记录**：`data/_sample` 的
   `fac.reaction_matrix` 是非对称的（只登记了 `fac.player → fac.wildlife = hostile`，没有
   反向登记），用反方向会把 `creature.sample_beast` 这类合法怪物错误排除掉；核对过
   `IFactionMatrix.GetReaction(from, to)` 的解析优先级（`from==to` 恒 `Friendly` → 运行时
   `SetReaction` 覆盖 → 显式 `reaction_matrix` 行 → `from` 的 `default_reaction`）后确认
   "以玩家为 `from`"是唯一不会产生假阴性/假阳性的方向。
3. 过滤后一个候选都不剩时直接抛 `InvalidOperationException`（异常信息含 tier id 与候选总数），
   不静默回退到未过滤集合——遵循 AGENTS.md"运行时路径不静默降级"的硬规则，且刻意与"tier 未
   命中任何记录"这另一种"空"区分开（后者维持退回 `opponent.CreatureId` 自身的既有行为）。
4. 过滤后同 `level` 仍有多条候选时，改用 `.OrderBy`（LINQ 稳定排序）而不是 `List.Sort`
   （不保证稳定）保持"数据登记顺序第一条生效"这一既有基线行为不变——本次只补诊断，不改变
   选择结果，避免影响任何依赖当前行为的下游消费方。被丢弃的候选记入新增的只读集合
   `GrowthReport.OpponentAmbiguities`（新类型 `GrowthOpponentAmbiguity`：`TierId`/`Level`/
   `ChosenTemplateId`/`DiscardedTemplateIds`）。

`GrowthReport.ToJson()` 只在该集合非空时才写出 `opponent_ambiguities` 字段——三条官方仿真
基线场景都不存在候选歧义，字段不出现，`BaselineComparerTests` 零改动即保持零 diff，不需要在
基线比较器里另开"忽略新字段"的特判分支。

同批新增校验规则 `Core.Sim.SimGrowthOpponentAmbiguityValidationRule`
（`core/sim/schema/SimValidationRules.cs`，检查名 `sim_growth_opponent_ambiguous`，
Warning 级、不可提升）：离线静态复算"对玩家阵营（假定 `fac.player`，与运行时不同，静态校验
拿不到真实 `StandardPlayer` 实例）是否敌对"，按 `tier`+`level` 分组，组内敌对候选 ≥2 条即对
组内每条记录各产出一条问题；`fac.player`/`fac.faction` 未登记时优雅跳过、不误报。
`NumericValidationRuleCatalog`（`presentation/assembly/NumericValidationRuleCatalog.cs`）
同步登记为第 25 行（阻断 15 + 警告 10，"仿真"分组扩到五行），字符串字面量而非
`nameof(...)`/常量引用的理由与既有三条"仿真"分组条目相同（`Presentation.Common` 不能引用
`Core.Sim`，见该类型类型级判断记录）。

## 对编辑器的使用建议

1. `StandardPlayerWeaponAdapter` 可退役，改调 `player.GetEquippedWeaponSummary(weaponSlotId)`
   或读 `player.EquippedWeaponSummaries`——输出与此前手工搬运逐字段一致（已用测试锁定）。
2. `GrowthReport.OpponentAmbiguities` 是只读诊断，非空时说明对应场景的数据配平存在同档位多个
   敌对候选、当前按登记顺序第一条生效——建议消费方自己的成长仿真报告查看器/CI 如需要更严格的
   把关，可自行决定把该集合非空当作阻断（框架本身不代为决定，详见"待设计层确认"）。
3. `sim_growth_opponent_ambiguous` 警告是提前发现类似 `sample_hero`/`sample_beast` 那种数据
   配平疏漏的手段，出现时优先考虑修数据（挪到独立 tier 或调整 `level`），而不是压制警告。

## 待设计层确认

- **`creature.sample_hero` 未随本次改动挪动/改造**：它已被阵营过滤自动排除、当前也没有
  `kind=growth` 场景会打到它，本次判定为不需要动；但它作为示例数据里"玩家阵营占位生物"与
  普通怪物同 `tier` 共存的既有安排本身是否需要更明确的建模（例如专门的"占位/不可作战斗对手"
  tier 惯例，类推 `sample_summon_totem` 本次的处理），超出本条反馈范围，留待设计层视后续
  同类反馈频率决定是否要系统化处理。
- **`GrowthReport.OpponentAmbiguities` 非空是否应在某个更高层（CI/发布门禁）被当作硬性阻断**：
  反馈原文优先级为"中"、明确"不是阻塞项"，本次落地只补诊断，未新增任何阻断行为；是否需要在
  `check.ps1`/发布流程里对该集合做进一步把关，留待设计层拍板。
