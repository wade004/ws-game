## 反馈 1：地面掉落物原生交互拾取

### 1. `interact` 意图的第三条原生分流

新增 `Core.Gameplay.Loot.LootInteractIntentTickHandler`，和场景物件、生物两条分流一样挂在
`TickPhase.TriggerEvaluation`，由 `GameplayAssembly` 注册（`LootHost` 在玩法层，所以不在
`CarriersAssembly` 里注册）。`Args` 携带 **`{loot_instance_id: <掉落物实例 id>}`**，键名沿用
`gobj_instance_id` / `creature_instance_id` 的惯例。

框架负责：
- 判断掉落物是否存在；
- 判距：沿用既有 `LootOptions.PickupRange`，不另起一套距离配置；
- 判拾取权限（见下）；
- 成功时走既有 `LootHost.PickUp`，拾取逻辑没有另写一份。

同一套判定也提供直接调用的入口：`LootHost.Interact(Id unitId, Id lootInstanceId) : LootPickupResult`。

**失败原因**：`LootPickupFailureReason` 新增 `PermissionDenied`。已有的 `NotFound` / `TooFar` /
`Rejected` 照旧。失败会写进 `ILootDiagnostics`（`LootHost.Diagnostics` 新增为只读属性；如果要自己
注入诊断实现，用新增的 14 参数构造重载）。

**距离过远不写诊断**：`TooFar` 在结果里照常返回，但不写进诊断出口。这和生物交互分流的既有口径一致——
玩家站得远是正常的临时状态，不是错误。存在性和权限失败会写诊断。

### 2. 拾取权限：接缝，默认放行

核实后，框架里原本没有"谁能拾取"的概念：`DroppedLootEntity.OwnerHint` 只是提示，从未强制执行。
所以这次**没有发明一套归属系统**，而是加了一个注入点：`LootOptions.PickupPermissionChecker`（委托
类型 `LootPickupPermissionDelegate`）。**不设置时默认放行**，写法和物件、生物分流既有的回调注入点
一样。你方的"拾取权限差异化"规则注入到这里：返回拒绝时结果为 `PermissionDenied`，掉落物留在地上，
同时写一条诊断。

### 3. 统一的"最近可交互目标"查询

新增 `Core.Carriers.Common.IInteractionTargetRegistry`：

```csharp
bool TryFindNearest(Id unitId, double? maxRange, out InteractionTarget target);
// InteractionTarget { Id EntityId; InteractionTargetKind Kind; double Distance; }
// InteractionTargetKind { GameObject, Creature, Loot }
```

生产实例从 **`CarriersAssembly.InteractionTargets`** 取。它一次查询覆盖场景物件、生物、地面掉落物
三类目标，返回最近的一个，并带上目标类别。

**实现口径**：它没有单独的登记表，每次查询都直接在世界模拟里现场求值。掉落物生成、被拾取、过期消失
都会自动反映出来，不会留下悬挂目标。唯一要注意的是：被拾取的掉落物要到**下一拍**世界完成销毁清理后，
查询才看不到它。距离相同时，取实体 id 序数最小的一个，结果是确定的。

**请核对你方代码里的同名类型**：你方反馈里提到的 `IInteractionTargetRegistry.TryFindNearest`，核实后
在 1.55.0 及以前的框架里**并不存在**，应该是你方游戏侧自己的类型。1.56.0 按这个名字在
`Core.Carriers.Common` 命名空间下补上了框架版本。如果你方同时 `using Core.Carriers.Common` 并保留
自己的同名类型，编译时会有名称歧义。它本来就是要被替换掉的绕行，建议直接删掉，改用框架的。

### 4. 表现层：`interact.nearest.*`

新增 `Presentation.Ui.InteractPathProvider`，已在 `PresentationAssembly` 接好。路径如下：

- `interact.nearest.id`——最近可交互目标的实体 id；
- `interact.nearest.kind`——`"gobj"` / `"creature"` / `"loot"`，沿用 `EntityKinds` 既有的三个字符串；
- `interact.nearest.distance`——距离。

附近没有目标时，三个值都是"无"。要判断"附近是否有可拾取掉落物"，就看
`interact.nearest.kind == "loot"`。之所以做成三类统一的一套路径，而不是单给掉落物开一条，是因为核实后
表现层对物件和生物也从来没有过这个查询。这个查询**不限距离**：各分流在真正交互时各自判距，提示层
只负责告诉玩家"最近的是什么、有多远"。要不要显示提示，由你方按 `distance` 和自己的规则决定。

验收经真实 `PresentationAssembly.Build` 装配，一路读到路径层：场景里同时有一个较近的掉落物和一个较远
的物件时，查询命中掉落物；掉落物被拾取、推进一拍后，查询回退到物件。

### 你方拆除绕行的做法

F 键改为：查 `CarriersAssembly.InteractionTargets.TryFindNearest(...)`，按 `Kind` 发 `interact` 意图，
`Args` 里填对应的实例 id 键（`gobj_instance_id` / `creature_instance_id` / `loot_instance_id`）。
你方自建的 F 键回退委托和"找最近地面掉落物"的实现可以整体删除。

## 反馈 2：装备槽的模板引用

核实结论：1.55.0 确实没有提供，本条成立。

### 契约：`IEquipmentHost` 新增两个只读成员

```csharp
Id? GetEquippedTemplateId(Id unitId, Id slot);
IReadOnlyDictionary<Id, EquippedItemIdentity> GetAllEquippedIdentities(Id unitId);
// EquippedItemIdentity { Id InstanceId; Id TemplateId; }  —— Core.Carriers.Common 新类型
```

两者都是带默认实现的接口成员。只读查询的默认实现返回 `null` / 空字典，口径同 `ISkillHost` 的
`Knows` / `GetSkillNameKey`。生产实现 `EquipmentHost` 显式实现了这两个成员，数据源与
`GetAllEquippedInstances` 是同一个账本。**经 `CarriersAssembly.Equipment` 按接口调用即可，不需要再
向下转型**。`ItemInstanceRef` 和四个既有方法的签名都没有改。

### 路径层

- `player.equipment.<slot>.template`——已装备物品的模板 id；
- `player.equipment.<slot>.instance`——实例 id；
- 既有裸路径 `player.equipment.<slot>` 行为不变，仍返回实例 id。

槽位 id 可以是多段的（如 `equip.main_hand`）：末段恰好是 `template` / `instance` 时按子路径解析。
**空槽或已卸下时，两个子路径都是"无"**，和背包空格的口径一致。

**没有提供 `name_key` / `quality`**：背包侧 `player.inventory[i].*` 也不给，名称和品质由游戏拿模板 id
自己查 `item.template` 表，两侧口径保持一致。也没有提供 `.count`：装备的堆叠数恒为 1，没有信息量。

### 视图模型

`InventoryViewModel` 新增只读属性 `EquippedSlotIdentities`（`IReadOnlyDictionary<Id, EquippedItemIdentity>`，
槽位 id → 实例 id + 模板 id）。既有的 `EquippedSlots`（槽位 id → 实例 id）原样保留。

### 你方拆除绕行的做法

你方装备面板改读 `InventoryViewModel.EquippedSlotIdentities`（或路径
`player.equipment.<slot>.template`，或 `IEquipmentHost.GetAllEquippedIdentities`，三者任选），删掉对
`EquipmentHost.GetAllEquippedInstances` 的直读。
