## 现象

消费方反馈复现的 A/B 场景（技能 `charges: {max: 2, recharge_time: 100}`，无自然冷却时间流逝）：

| 步骤 | A：先查询 | B：不查询 |
|---|---:|---:|
| 初始快照 | 上限 2 / 当前 2 | 未查询 |
| 原生上限光环后（上限 2→3） | 上限 3 / 当前 2 | 上限 3 / 当前 3 |
| 未推进时间，连续施法成功次数 | 2 | 3 |
| 最终拒绝原因 | `NoCharges` | `NoCharges` |

两者只差一次只读查询（`ISkillHost.GetSkillReadiness`，间接调用 `CooldownTracker.GetCharges`）；查询
本身不应推进时间、不应改变状态，但"查没查询过"这一操作本身，决定了后续原生施法能连续成功几次——
与只读查询契约相反的可观测行为。

## 根因

`core/rules/skill/core/CooldownTracker.cs`：`GetCharges(unitId, def)`/`GetChargeRechargeRemaining`/
`IsSkillReady` 等只读方法此前经私有方法 `GetOrCreateChargeState` 惰性创建充能账本状态
（`_charges` 字典），创建时把 `ChargeState.Current` 写死为**查询当下**的 `EffectiveChargesMax`（含
`charges` 维度 SpellMod 修正后的有效上限）。

- 若查询发生在一次上限变化（如施加提高充能上限的光环）**之前**，创建的账本记下旧上限；此后上限
  变化不会追认到已创建的账本——上限提高了，但已存在的 `Current` 不会跟着补齐差值。
- 若该 (unit, skill) 组合从未被任何路径触达过，则第一次触达（不论是另一次只读查询，还是首次施法
  ——`StartCooldown` 同样经 `GetOrCreateChargeState`）会直接按**当下**（已经变化后）的上限创建。

因此"是否提前查询过一次"这一纯读操作，改变了账本创建的时间点，进而改变了后续原生写路径（消耗
充能、判定是否可施法）看到的 `Current` 值。这不只是"查询有副作用"，还暴露了一层更深的语义缺陷：
即便完全不经过任何只读查询，只靠原生写路径各自不同的首次触达时机，同样会产生"有效上限变化时，
当前充能数是否跟着调整"的不一致——查询只是最容易触发它、也最违反直觉的一条路径（消费方反馈"这
不只是查询有副作用"的判断准确）。

## 规则（根治方案）

1. **查询纯化**：只读路径（`GetCharges(Id, SkillDef)`/`GetChargeRechargeRemaining`/
   `GetEffectiveChargesMax`/`GetEffectiveRechargeTimeScaled`/`IsSkillReady`/
   `GetCooldown(Id, SkillDef)`）不得创建、补齐或改变充能账本，也不得推进任何计时器。未初始化的
   (unit, skill) 组合，查询按**当前**有效充能上限计算一个只读默认快照（当前充能 = 有效上限、距下次
   恢复剩余 = 0），不为此创建任何状态。惰性创建收窄为只允许发生在写路径（`StartCooldown`/
   `AddCharge`/`AdvanceCharges`，均经 `GetOrCreateChargeState`）。
2. **充能上限变化守恒规则**：状态新增字段 `KnownEffectiveMax`，记录"上一次对账时的有效上限"。任何
   写路径或推进（`AdvanceCharges`，由 `SkillHost.Update` 对每个已知充能技能定期调用）在真正触达账本
   前，先按以下规则对账：
   - 有效上限较 `KnownEffectiveMax` **提高** Δ → `Current += Δ`（获得的新充能格立即可用，正在进行
     中的恢复窗口 `RechargeRemaining` 不受影响、不重置）。
   - **降低** → `Current = min(Current, 新上限)`，若因此恰好达到新上限（满充能）则
     `RechargeRemaining = 0`（没有正在进行的恢复窗口，与 `AddCharge`/`StartCooldown` 补满时清零的
     既有惯例一致）。
   - 随后把 `KnownEffectiveMax` 更新为当下有效上限。
   只读快照（`ComputeReadOnlySnapshot`）对已存在的状态调用**同一个纯函数**（`ReconcileForMaxChange`）
   计算出对账后的值，但不写回账本本身——保证只读查询看到的数字，与"紧接着这次查询之后立即发生一次
   原生写路径触达"会产生的结果完全一致，从根上消除"查没查询过"对后续原生施法次数的影响。

06 第 3.5 节同批勘误（细节勘误，版本号不变，见变更记录）；判断记录原文见
`core/rules/skill/core/CooldownTracker.cs` 类型注释、`core/rules/skill/README.md` 判断记录条目 47。

## 修复位置

- `core/rules/skill/core/CooldownTracker.cs`：
  - `ChargeState` 新增字段 `KnownEffectiveMax`。
  - 新增私有静态纯函数 `ReconcileForMaxChange(current, rechargeRemaining, knownMax, newMax)`——守恒
    规则的唯一实现，供写路径与只读路径共用同一份口径。
  - 新增私有方法 `ComputeReadOnlySnapshot(unitId, def)`——只读快照计算入口，不创建/不修改 `_charges`。
  - `GetCharges(Id, SkillDef)`/`GetChargeRechargeRemaining`/`GetCooldown(Id, SkillDef)` 改为调用
    `ComputeReadOnlySnapshot`，不再触达 `GetOrCreateChargeState`（`GetCooldown` 此前经
    `GetCharges(Id, SkillDef)` 间接触发创建，是与本反馈同源的独立读路径缺口，一并修复）。
  - `GetOrCreateChargeState`（写路径专用）与 `AdvanceCharges`（推进路径）在真正触达/推进前先调用
    `ReconcileForMaxChange` 对账，再执行各自既定逻辑；`AdvanceCharges` 的对账特别排在"是否有恢复
    窗口"的提前返回判断之前——充能上限光环生效时充能往往已经用满（`RechargeRemaining<=0`），若先
    判断提前返回、后对账，会跳过这类场景。
  - `GetEffectiveChargesMax`/`GetEffectiveRechargeTimeScaled`/`IsSkillReady` 本就是纯函数/组合调用
    只读方法，未直接改动，行为随其内部调用的只读方法一并变得纯粹。
- 公开 API 无变化：以上全部是私有字段/私有方法层面的改动，`CooldownTracker` 对外公开的方法签名
  （`GetCharges`/`GetChargeRechargeRemaining`/`GetEffectiveChargesMax`/
  `GetEffectiveRechargeTimeScaled`/`IsSkillReady`/`GetCooldown`/`StartCooldown`/`AddCharge`/
  `AdvanceCharges`/`TrackedChargeKeys`/`CurrentTimeFactor`/`RescaleAll`）逐一比对未变；
  `SkillHost.GetSkillReadiness`/`ISkillHost.GetSkillReadiness` 签名同样未变，只是其内部调用的
  `CooldownTracker` 只读方法现在返回了正确的值。

## 对消费方的提示

1. **只读查询现在真正只读**：`GetSkillReadiness`/`GetCooldown`/`CooldownTracker` 其余只读出口不再
   因为"查没查询过"而影响后续原生施法的实际充能数或连续可施放次数；可以放心在任意时刻、任意频率
   调用只读查询用于 UI 展示（技能图标充能角标、冷却遮罩等），不需要担心副作用。
2. **上限变化守恒是新引入的行为，不是无变化的"细节勘误"**：修复前，充能上限变化（`charges` 维度
   SpellMod 生效/失效）对已存在账本的技能实际上**不会**调整当前充能数（除非该账本恰好是在变化之后
   才第一次被创建）；修复后，账本存在与否、创建早晚都不再影响结果——上限提高时当前充能数同步增加，
   降低时同步夹取。若消费方此前的数值/技能设计**依赖**"查询后上限提高不生效"这一旧行为（例如刻意
   利用这条路径营造"充能暂不到账，需要重新进入战斗才生效"的效果），需要复核相关配置——这类依赖
   本身就建立在一个未定义、且与文档契约相反的副作用之上，不建议继续依赖。
3. **兼容性**：本次修复不改变任何公开签名（详见"修复位置"末尾逐一比对），ABI 探针（基线 1.12.0）
   `breaks=0`；对 1.12.0～1.21.0 之间已编译的消费方二进制严格模式兼容。
