## 处理

### A. 第 43 条：可选规则描述符（规则名 ↔ 检查名，单一来源）

`core/gameplay/spawn/schema/SpawnValidationRules.cs` 的 `SpawnSummonOnlyCreatureRule.CheckName`
与 `core/foundation/display_info/core/DisplayMapCoverageRule.cs` 的
`DisplayMapCoverageRule.CheckName` 由 `private const` 改为 `public const string CheckName`（补
XML 注释：本规则产出的全部 `ValidationIssue.Check` 取值，消费方按检查名过滤时应引用本常量，不要
复制字面量）。两个规则实现内部继续用同一常量，未改变产出的诊断内容。

`presentation/assembly/ContentValidationAssembly.cs` 新增：

- `OptionalRuleDescriptor`（`sealed class`）：`RuleName`（与 `OptionalRuleNames` 取值逐字相同）、
  `CheckName`（直接引用 `SpawnSummonOnlyCreatureRule.CheckName`/`DisplayMapCoverageRule.CheckName`
  公开常量，不是另行抄写的字面量）、`Description`（一句中文说明）三个只读属性，公开三参构造函数。
- `ContentValidationAssembly.OptionalRules`（`IReadOnlyList<OptionalRuleDescriptor>`，固定两项，
  顺序与 `OptionalRuleNames` 一致）——单一来源：规则若改检查名字符串，本清单自动跟着变，不会像
  此前 `OptionalRuleNames` 那样需要消费方另建一份 PascalCase→snake_case 映射表维护。
  `OptionalRuleNames` 保留不变（既有测试 `OptionalRuleNames_IsFixedTwoEntryList` 未改动就通过），
  改为 `OptionalRules.Select(d => d.RuleName).ToList()` 投影得到。
- `ContentValidationAssembly.TryGetOptionalRuleByCheck(string checkName, out OptionalRuleDescriptor descriptor)`：
  按检查名反查描述符，供内容工具（如问题面板）判断"这条诊断是否来自某个可选规则、来自哪个"；
  游戏侧经 `IDataRegistry.RegisterValidationRule` 注册的自定义规则不在本清单内（预期行为，同反馈
  原文判断记录）。
- `ContentValidationRun` 新增 `EnabledOptionalRuleChecks`/`DisabledOptionalRuleChecks`
  （`IReadOnlyList<string>`，与 `EnabledOptionalRules`/`DisabledOptionalRules` 一一对应，构造函数
  是 `internal`——只有本文件的 `Run` 方法调用，改签名不影响 ABI）。

`toolchain/validator/Program.cs` 的 `--json` 输出：在既有 `disabled_optional_rules`/
`enabled_optional_rules` 之后追加

```
"optional_rules":[{"rule":"SpawnSummonOnlyCreatureRule","check":"spawn_summon_only_creature","enabled":false},{"rule":"DisplayMapCoverageRule","check":"display_map_coverage","enabled":true}]
```

`rule`/`check` 直接来自 `ContentValidationAssembly.OptionalRules`，`enabled` 按
`disabledOptionalRules` 是否含该规则名判定；不改动既有两个字段，`--json` 输出对不读取新字段的
调用方保持逐字节兼容。`toolchain/validate_data.py --json` 是"把整份 validator JSON 原样塞进
`result["validator"]`"的透传路径（不解析/不改写任何字段），核实确认新字段无需该脚本任何改动即
自动带上（见下"测试"一节 `test_json_flag_passes_through_optional_rules_field_unmodified`）。
`data/README.md`/`toolchain/validate_data.py` docstring 均未逐字段列出 `--json` 输出结构，核实
后无需同步。

3. 内存追加一条指向 `creature.sample_summon_totem` 的 `spawn.table` 行（不落盘，走多根合并，
   与真实 `data/_sample/spawn/spawn.table.json` 既有两行不同主键），断言产出的诊断里存在一条
   `Check == "spawn_summon_only_creature"`（同时等于 `SpawnSummonOnlyCreatureRule.CheckName`）、
   `Severity == Error` 的问题，且 `report.IsBlocking == true`。

**判断记录（`toolchain/validator` 侧无法演示同一场景，如实告知的偏离）**：设计原计划还要求在
`toolchain/tests` 补一例 pytest，跑真实 `python toolchain/validate_data.py --strict` 子进程、
往 `spawn.table.json` 加一条违规行，断言退出码非 0 且输出含 `spawn_summon_only_creature`。核实
`toolchain/validator/Program.cs` 现场代码后发现：`SpawnSummonOnlyCreatureRule` 只有
`ContentValidationOptions.CreatureTemplateQuery` 非空时才会注册（见
`GameplaySchemaCatalog.RegisterSpawnSchemas` 判断记录），而 `toolchain/validator`
（一次性命令行进程）按**既有设计**从未接线该依赖——该工具自己的判断记录明确写着"与其注册一条
在未接线时注定产生 Warning 的规则（污染门禁要求的 0 错误 0 警告），不如干脆不注册"。这意味着
`python toolchain/validate_data.py --strict` 这条命令行路径下 `spawn_summon_only_creature`
检查项**恒不生效**，无论示例数据里有没有违规行，都不会在这条路径上产出该诊断——手工验证
`optional_rules` 字段时确认 `SpawnSummonOnlyCreatureRule` 恒为 `enabled: false`（见上"验证"
一节）。这是 `toolchain/validator` 的既有取舍（不是第 44 条反馈引入的缺陷，也不在本条反馈的
"示例数据覆盖面缺口"范围内——要修就要改变该工具"命令行进程不接线 ICreatureTemplateQuery"这条
既有设计决策，属于更大范围的改动，本批不擅自展开），因此**未按原计划新增这例 pytest**，改为把
"规则真的能触发"的演示完整放进上面的 C# 集成测试（用正式装配入口 `ContentValidationAssembly`，
不是自建校验管线，同样具备反馈原文要求的"用真实示例数据、非内存改写既有记录"这一核心诉求）。
已在 `data/README.md` 新增小节里如实写明这条既有边界，供后续消费方查阅时不必重新踩一遍这个坑。

## 对编辑器的使用建议

1. **问题面板"来自可选规则"标注改用 `ContentValidationAssembly.TryGetOptionalRuleByCheck`/
   `OptionalRules`，不再硬编码映射表**——`Editor.ViewModels.Panels.ProblemsPanelViewModel.
   OptionalRuleCheckNames`（反馈原文点名的硬编码位置）可以整段删除，改为对每条诊断的 `Check`
   调用 `ContentValidationAssembly.TryGetOptionalRuleByCheck(issue.Check, out var descriptor)`，
   命中即标注"来自可选规则：`descriptor.Description`"；框架未来新增第三个可选规则或调整检查名
   拼写时，编辑器这段标注逻辑不需要跟着改一行代码。
2. **"校验设置"面板展示可选规则全量选项，建议改用 `OptionalRules` 而不是 `OptionalRuleNames`**
   ——每项自带 `Description`（一句中文说明），面板可以直接展示，不必自己维护规则名到说明文案的
   映射；`RuleName` 取值仍与 `OptionalRuleNames`/`ContentValidationOptions` 两个接线参数完全
   对应，接线逻辑不需要改。
3. **`toolchain/validator --json` 新增 `optional_rules` 字段是编辑器可选择性消费的"更方便的
   形状"，不是强制迁移**——已经在用 `enabled_optional_rules`/`disabled_optional_rules` +
   自行维护映射表的既有实现继续可用（两个旧字段未改动），迁移到新字段纯粹是省掉那份自维护映射表，
   没有紧迫性。
4. **`SpawnSummonOnlyCreatureRule` 在 `toolchain/validator` 命令行路径下恒为禁用**（见上"处理
   B 判断记录"）——编辑器基础套件若走的是自己的装配路径（如 `Editor.SamplePlugins.
   SampleValidationSourcesPlugin` 一类真正持有 `ICreatureTemplateQuery` 实现的场景）不受影响，

## 追记（2026-09-14 二次根治）：`SpawnSummonOnlyCreatureRule` 改为默认接线

上文"处理 B"发现的既有边界——`toolchain/validator`（一次性命令行进程）按既有设计从不接线
`ICreatureTemplateQuery`，`SpawnSummonOnlyCreatureRule` 因此在这条命令行路径下恒不注册，示例数据
门禁从未真正跑过这条规则——经主会话复核认定是真实缺口（不是"本条反馈范围外可以不管"的边界），
决定比照消费方反馈第 34 条 `DisplayMapCoverageRule` 先例一并根治。本节记录该追加改动。

### 处理

`core/carriers/creature/core/RegistryCreatureTemplateQuery.cs`（新文件）：新增
`public sealed class RegistryCreatureTemplateQuery : ICreatureTemplateQuery`，构造参数
`IDataRegistryView view`——直接从已加载的 `view` 现读现解析 `creature.template` 记录（不像
`CreatureFactory` 那样在构造期把全表一次性解析进内存索引，因此不要求 `view` 提前加载完成）。

- `Get(Id)`：`view.Get("creature.template", id)` 未命中时抛 `ArgumentException`（同
  `ICreatureTemplateQuery` 契约）；命中后经 `CreatureTemplate.FromRecord(record)` 解析，该方法
  抛出的 `DataFieldException` 被本类型捕获并包成 `ArgumentException`（`InnerException` 保留原始
  异常）再抛——模板字段非法已由字段级校验（`required_field`/`field_type`/`field_allowed_value`
  等检查项）单独报出，`SpawnSummonOnlyCreatureRule` 不需要重复报告，更不能让本查询的异常把整次
  `ContentValidationAssembly.Run` 从"报告若干诊断"变成进程级未处理异常。
- `HasFlag(Id, NpcFlag)`：`Get(templateId).NpcFlags.Contains(flag)`。
- 不做跨次缓存——每次调用都现读现解析，`IDataRegistry.Reload(string)` 支持单表重载，缓存会读到
  过期数据；本类型典型生命周期是"校验期一次性使用"（每次 `ContentValidationAssembly.Run`/
  `CreateRegistry` 调用都新建一个实例），不缓存不构成性能问题。
- **实测确认的边界**（写入类型级判断记录）：`DataRegistry` 在整次 `LoadAll`/校验期间把内部
  "是否阻断"标记固定为 `false`，只在全部 `IValidationRule`（含本类型接线的
  `SpawnSummonOnlyCreatureRule`）都跑完之后才回填真实阻断状态——因此本类型在 `Validate()` 调用
  期间读取永远不会因为"数据集别处已经有 Error"被拒绝读取。但若调用方在 `LoadAll` 完全结束、报告
  已阻断之后，才另外持有一个本类型实例去读同一个已阻断的 `DataRegistry`，`Get`/`GetAll` 会直接抛
  `InvalidOperationException`（"数据校验未通过，禁止读取"，`DataRegistry.EnsureReadable` 的既有
  契约，与本类型无关）——本类型不吞、也不应该吞这种异常。

`presentation/assembly/ContentValidationAssembly.cs`：

- `CreateRegistryCore` 未提供 `options.CreatureTemplateQuery` 时，改为
  `options.CreatureTemplateQuery ?? new RegistryCreatureTemplateQuery(registry)`（`registry` 是刚
  `new` 出来的 `DataRegistry`，此时可以传给 `RegistryCreatureTemplateQuery` 构造函数——它本身就是
  `IDataRegistryView`，且构造函数不要求已加载完成，见上）后再调用
  `PresentationSchemaCatalog.RegisterAll`，`SpawnSummonOnlyCreatureRule` 因此默认启用，不再计入
  `disabledOptionalRules`；显式提供 `CreatureTemplateQuery` 的调用方仍以传入值为准（覆盖默认）。
- `ContentValidationOptions.CreatureTemplateQuery`、`OptionalRuleDescriptor` 里
  `SpawnSummonOnlyCreatureRule` 对应描述符的 `Description` 同步改写，说明默认接线依赖。

`toolchain/validator/Program.cs`：不需要任何代码改动——该工具从未显式设置过
`CreatureTemplateQuery`，走 `ContentValidationAssembly` 的新默认值即可自动生效；第 193～197 行
判断记录改写（原文"仍不接线——本工具运行时机没有真正的实现可用"已不成立，改为说明
`RegistryCreatureTemplateQuery` 这条运行时机同样可用的默认路径）。
