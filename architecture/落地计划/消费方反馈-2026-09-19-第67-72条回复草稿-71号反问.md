## 核实结论（第 67 条：samples 通道是否真的走得通）

1. **主 zip 内容范围**：`build.ps1` 的 `Copy-DistDir` 把整个 `toolchain/` 目录（含
   `toolchain/README.md`）原样复制进主 zip（`build.ps1:894`），但不复制 `data/_sample`/
   `assets/_sample`（`build.ps1:900` 前后判断记录）。
2. **samples 通道确实存在且独立**：`build.ps1:1496-1513` 额外打
   `dist/ws-game-<ver>-samples.zip`（内含 `data/_sample`、`assets/_sample`）；`.lock` 文件新增
   `samples.sha256` 字段（`build.ps1:1536-1537`）；`toolchain/get_framework.ps1` 的 `-WithSamples`
   开关（`get_framework.ps1:80-90` 文档注释、`:479-529` 下载/定位逻辑、`:700-739` 哈希校验逻辑）
   按该字段校验整份 samples zip，校验通过才落地到与主 zip 相同的 `<Target>/ws-game-<Version>/`
   目录下。
3. **走得通，但有两个此前未写明的前提**：
   - 前提 A（在线拉取路径）：需要 `gh`（GitHub CLI）已登录、对框架仓库（`wade004/ws-game`，公开
     仓库）有读权限；该版本的 GitHub Release 必须已附带三件套
     `ws-game-<ver>.zip`/`.lock`/`ws-game-<ver>-samples.zip`（`build.ps1 -Release` 自 1.15.0 起
     保证三件套同批产出，见 `build.ps1:1639` 附件清单）——若消费方引用的是早于 1.15.0 的旧版本，
     `-WithSamples` 会在锁文件缺 `samples` 字段时明确报错退出（`get_framework.ps1:706-708`），
     不会静默失败。
   - 前提 B（**此前完全没有文档提示的限制**）：`-WithSamples` **只对 zip 快照通道有意义**，传给
     `-FromRegistry`（私服/UPM 通道）时被忽略（`get_framework.ps1:80-81`
     ".PARAMETER WithSamples" 明确写"仅对 zip 通道有意义，`-FromRegistry` 时忽略"）——只走私服
     通道的消费方**没有任何官方途径通过 `get_framework.ps1` 拿到验收样例数据集**，必须切换到 zip
     通道单独拉一次 `-WithSamples`（哪怕平时按包依赖方式消费框架）。这一限制在改动前的
     `README.md`/`toolchain/README.md` 均未提及，属于真实指引缺口，已在两处新增文字说明。
4. 已有文档核实：根 `README.md`"游戏侧引用与升级"一节（未改动前既有文字）已列出
   `ws-game-<ver>-samples.zip` 作为 Release 附件之一并说明"内含验收数据集，
   `get_framework.ps1 -WithSamples` 下载/校验/合并落地"；`toolchain/README.md`"`get_framework.ps1`
   （游戏侧按版本号引用本框架）"一节的"`-WithSamples`"小节（改动前既有文字）给出了同样说明与用法
   示例。这两处文档在本次改动之前就已经写得比较完整，此前的勘察记录（`survey-67-72.md`）与反馈
   原文均未提及这两处、误判为"只有 CHANGELOG 记了这条能力"。

## 反问草稿（给内容编辑器项目，可直接粘贴进回复）

> 关于第 71 条 `ValidationIssue.ToString()` 格式稳定性：我们已经确认 `ValidationIssue` 本身是结构化
> 数据（`Table`/`RecordKey`/`Field`/`Check`/`Message`/`Severity` 等均为公开只读属性），并且命令行层
> 已有两条结构化出口——`toolchain/validator --json`（常规校验与 `--schema-audit` 两条路径都支持）与
> `toolchain/asset_import/check_cmd.py check --json`（1.43.0 起可用）。
>
> 想请编辑器项目确认一下：`LogRecordLookup`（或其它依赖该文本格式做日志反查跳转的功能）实际消费校验
> 结果走的是哪条路径？
>
> 1. 直接调用上述某个命令行入口的 `--json` 输出（或直接使用 C# API 拿到 `ValidationReport`/
>    `ValidationIssue` 对象本身）；还是
> 2. 解析 Unity 运行期（Editor Play 模式或独立版）产生的日志文本（目前运行期唯一会把校验问题写出来
>    的两处——`GameBootstrap` 启动校验失败、`DataHotReload` 热重载失败——都只输出
>    `ValidationIssue.ToString()` 拼接后的人类可读文本，没有任何结构化投影）？
>
> 如果是后者，能否说明是什么场景迫使功能必须走运行期日志这条路（例如：反查跳转需要在游戏实际运行
> 时、以某条具体记录触发校验失败为上下文，命令行入口的静态校验覆盖不到这类场景；或者只是历史实现
> 顺手用了日志，其实换成命令行 `--json` 或直接读 API 也能满足）？这会决定我们是否需要、以及以什么
> 形状给运行期补一条结构化诊断出口（目前评估下来这会是一个需要正式承诺格式稳定的新契约，想先弄清楚
> 真实需求形状再动手，避免选错方案后再来一次破坏性调整）。
