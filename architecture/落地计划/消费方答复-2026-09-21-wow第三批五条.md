## 反馈 1：施法条（读条剩余/总时长）

`Core.Rules.Common.ISkillHost` 契约本身新增三个只读默认接口成员（不需要向下转型到具体类即可
直接调用）：

```csharp
Id? GetCastingSkillId(Id unitId);      // 当前正在读条/引导的技能 id；未读条为 null
double? GetCastingRemaining(Id unitId); // 剩余时间；未读条为 null
double? GetCastingTotal(Id unitId);     // 总时长（经 SpellMod 修正后的 cast_time）；未读条为 null
```

`presentation/ui.ISkillBookQuery` 窄接口上有完全同名的三个成员，签名/语义逐字一致，供只依赖该窄
接口的调用方使用。

`HudViewModel` 新增六个只读属性：

- `CastingSkillId` / `CastingRemaining` / `CastingTotal`（经路径 `player.casting.skill` /
  `player.casting.remaining` / `player.casting.total`）——玩家自己的读条状态；
- `TargetCastingSkillId` / `TargetCastingRemaining` / `TargetCastingTotal`（经路径
  `target.casting.skill` / `target.casting.remaining` / `target.casting.total`）——当前目标的读条
  状态，用于敌方读条预警。

**取值口径**：不在读条时，三个字段（技能 id/剩余/总时长）**全部为 `null`**，不是 `0`——`0` 是
"总时长确实为 0 秒"的合法真实值，不能用来表示"当前没有读条"。`player.casting.*` 与
`target.casting.*` 两组路径行为完全对称，唯一区别是 `target.*` 在当前无目标时同样恒为 `null`。

**核实要点（与我方转发稿的出入）**：ADR-0056 决策 1 原文写的是"施法条数据本次只停在具体类与
`presentation/ui` 窄接口，暂不进入 `ISkillHost` 公开契约"（理由是落地当时 `ISkillHost.cs` 被
ADR-0058 的并行分支占用，怕合并撞车）。但**实际检查 `v1.52.0` 标签下的 `ISkillHost.cs`，这三个
成员已经在契约接口本身上**——收口注释写明"ADR-0057/ADR-0058 均已合入 main 后，占用该契约文件的
顾虑不再成立，已一并提升进 `Core.Rules.Common.ISkillHost` 契约本身"。也就是说 ADR 文档描述的是
中间状态，1.52.0 实际发布的是收口后的最终形态：**你方可以直接面向 `ISkillHost` 接口编程，不需要
向下转型**，比 ADR 原文更方便。

**1.53.0 补充核实**：1.53.0 的 `CHANGELOG.md` 新增一条"勘误"，专门订正了这一处——明确写明

## 反馈 4 补充（1.53.0）：光环极性与图标引用字段补全

**这一条是框架侧自查发现补的，不是你方本轮新提的**：上面"范围裁剪"一节写的 1.52.0 交付范围
不变，仍然只有身份/层数/剩余时长/总时长/名称键。但你方原始反馈第 4 条其实一并提出过极性与图标
引用两项，`ADR-0056` 当时只是把它们留给"后续独立评审"，不是拒绝——没有这两个字段，你方画不出
增益/减益的正负分区，只能自己维护一张 id 清单硬编码，这正是我方一直在帮你方拆的那类绕行。
`ADR-0060`（[architecture/adr/0060-光环极性与图标引用字段补全.md](../adr/0060-光环极性与图标引用字段补全.md)）
完成了这项评审并在 1.53.0 落地，均为纯加法，不提升 `skill.aura_def` schema 版本，ABI 探针
`breaks=0`。

**`skill.aura_def` 新增两个可选字段**：

| 字段 | 登记表类型 | 取值集合 | 缺省 |
|---|---|---|---|
| `polarity` | `FieldKind.Enum` | `beneficial`（对承受者有利）/ `harmful`（对承受者有害） | 缺省未声明 |
| `icon_ref` | `FieldKind.Id`，类别前缀限定 `icon`（`WithAllowedRefCategories("icon")`，遵守
  ADR-0038/0039 既有的"类别前缀唯一决定路径空间"契约，与 `display.anim_set.clips.resource_ref`
  限定 `anim`/`sprite_anim`、`display.equip_visual.mesh_ref` 限定 `model`/`paperdoll` 同一套
  声明式前缀校验） | — | 缺省未声明（`null`） |

**极性在代码里是枚举，不是字符串**：运行时类型是 `Core.Rules.Common.AuraPolarity`（结构化枚举，
理由与同批交付的 `ActionBarSlotBlockReason` 一致——字符串让接入方只能自己拼字面量比较、拼错编译
期不报错，布尔表达不出"未声明"这第三种状态）。全部取值：

- `Undeclared = 0`——**显式取值，不是"可空枚举 + `null`"**。判断记录：如果用 `AuraPolarity?`
  表达未声明，接入方每次读取都要多判断一层"有没有值"，且"有值但恰好是某个哨兵"与"没有值"分别由
  `HasValue`/具体取值两套不同机制表达，容易在传递链路里（例如经过一次 `??` 兜底）把 `null`
  悄悄折叠掉、与某个具体极性混淆；收进枚举取值域后，`Undeclared` 与 `Beneficial`/`Harmful`
  在类型系统里完全平等，只有一种"当前取值是什么"的问题，调用方一次 `switch` 就能穷尽三种状态。
  代表"`skill.aura_def.polarity` 缺省缺失"，不代表"中性"这一具体设计意图。
- `Beneficial = 1`——对应数据表取值 `beneficial`。
- `Harmful = 2`——对应数据表取值 `harmful`。

**图标引用**：`icon_ref` 是不透明资源标识（`FieldKind.Id`），类别前缀必须是 `icon`（资产根相对
路径，解析方法 `AssetRefConventions.IconFile`），登记时不声明 `ReferenceTable`/`SoftReferenceTable`
（不对应任何内容表，由引擎适配层解析），前缀拼写错误（如误填 `sprite.` 而非 `icon.`）会在加载期
直接报错，不必等到表现层渲染时才发现引用解析不出资源。

**`AuraSnapshot` 新重载**（`Core.Rules.Common.AuraSnapshot`）：

```csharp
public AuraSnapshot(Id auraDefId, int stacks, double? remaining, double? total, Id? nameKey,
    AuraPolarity polarity, Id? iconRef)
```

与既有五参数构造函数并存（ABI 只加法，两个重载参数个数不同不冲突）。**既有五参数构造函数构造出
的快照，`Polarity` 恒为 `AuraPolarity.Undeclared`、`IconRef` 恒为 `null`**——旧调用点不用改代码
也不会得到错误的极性/图标引用，只是拿不到新信息。生产实现 `Core.Rules.Skill.AuraHost` 的
`GetActiveAuraSnapshots` 已改用七参数重载，把加载解析出的 `AuraDef.Polarity`/`AuraDef.IconRef`
原样透传进快照，不解析、不本地化、不做任何派生计算。

**表现层路径**：`player.auras[i].polarity` / `player.auras[i].icon_ref`（目标同理
`target.auras[i].*`），与既有 `auras[i].name_key` 同一套惯例。**这一层为什么仍输出字符串，不是
把枚举透传出去**：`Core.Foundation.Expr.ExprValue` 是通用路径查询的取值载体，判别集合只覆盖
布尔/整数/浮点/字符串/标识五种通用形状，不为某一个具体枚举类型单开判别分支——枚举是规则层内部
实现细节，路径协议面向所有表现层消费方，不能因为一个字段是结构化枚举就让协议膨胀出与之一一对应
的判别形状。所以 `polarity` 路径由 `AuraPolarityNames.ToText(snap.Polarity)` 转出固定小写文本
再装入 `ExprValue.OfString`（只在 `Polarity != Undeclared` 时才有值，`Undeclared` 时路径查询
结果为"无"，同 `name_key`/`casting.remaining` 一贯"合法查询、无值"口径，不记诊断）；`icon_ref`
用 `ExprValue.OfId` 承载，未声明时同样为"无"。**转出的文本来自枚举到文本的既定映射，不是把数据
文件里的原始字面量原样透传**——数据文件字符串到路径查询输出之间隔着"文本 → 枚举 → 文本"两次
转换，非法文本已经在第一次转换（加载解析）时被判定为解析失败，不会流入路径查询这一层。

**非法极性值的处理口径（请务必注意）**：

- **字段缺失** → 解析结果为 `AuraPolarity.Undeclared`（合法留白）。
- **字段存在但取值不在 `beneficial`/`harmful` 之内** → `AuraPolarityNames.Parse` **直接抛
  `ArgumentException`，不静默降级为 `Undeclared`**。这是加载解析阶段
  （`SkillDefCache.ParseAuraDef`）的行为：登记表校验理论上已经会挡住这类非法数据，但解析层本身
  仍按"运行时路径不静默降级"的一贯纪律处理——**不能把"字段存在但取值非法（数据错误，或校验被
  绕过，例如热重载路径）"悄悄当成"字段缺失（合法留白）"处理，两者是完全不同的错误**。也就是说：
  数据写错 `polarity`（例如大小写拼错、拼成 `benefit`）会在解析时**直接抛异常**，不会悄悄退化
  成"未声明"然后在你方界面上表现为"这条光环看起来没有极性"——排查时请先看是不是抛了异常，不要
  先怀疑是框架把数据吞掉了。

**样例数据**（`data/_sample/skill/skill.aura_def.json`）：`skill.aura_def.sample_burn`
（`polarity: "harmful"`，`icon_ref: "icon.aura.sample_burn"`）演示减益；
`skill.aura_def.sample_fortify`（`polarity: "beneficial"`，`icon_ref: "icon.aura.sample_fortify"`）
演示增益；`skill.aura_def.sample_mount_speed` 两个字段都未声明，演示"未声明"（解析为
`AuraPolarity.Undeclared`/`IconRef == null`，路径查询与 `AuraSnapshot` 均返回"无"）。

## 反馈 2：技能栏（冷却总时长/充能/结构化阻塞原因）

`presentation/ui.ActionBarSlotSnapshot` 新增四个只读字段（既有两个构造函数——两参数、三参数——
字节级不变，新增一个七参数构造函数）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `EffectiveCooldownDuration` | `double?` | 修饰后的完整冷却/充能恢复周期总时长，与既有 `Cooldown`
  （剩余）同类型，配合算 `remaining / total` 径向遮罩填充比例 |
| `MaxCharges` | `int?` | 修饰后有效充能上限 |
| `CurrentCharges` | `int?` | 当前充能数 |
| `BlockReason` | `ActionBarSlotBlockReason` | 结构化不可用原因，见下表 |

**充能字段为 `null` 的口径**：`MaxCharges`/`CurrentCharges` 在"该技能未配置 `charges` 机制"与
"取不到就绪数据"两种情况下**共用 `null`**——两者对接入方而言都是"不画充能层数 UI"，框架不额外
区分（区分"到底是哪一种"要看 `BlockReason` 是否为 `Unknown`）。

**`ActionBarSlotBlockReason` 全部枚举取值**：

| 取值 | 数值 | 什么情况会取到 |
|---|---|---|
| `None` | 0 | 不受任何已覆盖原因阻塞（等价"无阻塞"）；槽位为空、或未启用新能力（用的是旧构造函数）时
  同样是这个值——**不代表"已确认可用"，只代表"本视图模型未发现阻塞"** |
| `ConditionNotMet` | 1 | 技能使用条件（`skill.def.use_condition`）求值为假 |
| `SkillCooldown` | 2 | 技能自身冷却剩余 > 0 |
| `CategoryCooldown` | 3 | 所属冷却分类剩余 > 0 |
| `NoCharges` | 4 | 配置了充能且当前充能数为 0 |
| `GlobalCooldown` | 5 | 公共冷却（GCD）剩余 > 0 |
| `ActionLocked` | 6 | 节拍锁——施法者正处于另一个技能的动作时长内 |
| `Unknown` | 7 | 取不到完整就绪数据（命中了降级默认接口实现，不是生产宿主的真实转发）——**与
  `None` 严格区分，不能把它当"无阻塞"处理**，此时 `EffectiveCooldownDuration`/`MaxCharges`/
  `CurrentCharges` 同时为 `null`，且框架已经向诊断出口记过一条警告 |

**多个阻塞同时成立时的优先级**（一份写死的显式判定顺序，对齐规则层施法管线的判定步骤先后）：

1. `ConditionNotMet`（使用条件，发生在冷却判定之前，优先级最高）
2. `SkillCooldown` / `CategoryCooldown` / `NoCharges`（冷却与充能判定同一步，三者互斥或有既定
   先后，不会同时置位）
3. `GlobalCooldown` / `ActionLocked`（公共冷却与节拍锁互斥）

**接线方式**：`ActionBarViewModel` 新增一个六参数构造函数重载，额外携带
`ISkillBookQuery` + `IUiDiagnostics`；启用该重载后 `Refresh` 内部改用
`ISkillBookQuery.GetSkillReadiness(unitId, skillId)` 整体转发（取代原来只查
`player.skill.<id>.cooldown` 单个值的做法）。**该重载与"启用新字段"绑定成同一个显式选择**——不换
新构造函数重载，四个新字段恒为缺省值（`null`/`None`），行为与升级前逐位一致。

**既有 `Available` 布尔字段不受影响**：它的计算方式（"有绑定技能且自身冷却已就绪"）保持字节级
不变，不会因为新增了结构化原因字段而扩大判定范围；需要完整判定的新代码应改用
`BlockReason == ActionBarSlotBlockReason.None`（且 `SkillId` 有值），不要继续只看 `Available`。

## 反馈 3：`ISkillHost` 新增 `AuraQuery`/`EffectSink`

```csharp
IAuraQuery? AuraQuery { get; }
IEffectSink? EffectSink { get; }
```

两个只读属性均为 `ISkillHost` 契约新增的默认接口成员，**默认降级为 `null`**——生产实现
`Core.Rules.Skill.SkillHost` 用显式接口实现转发到既有的同名公开属性（属性本身的物理签名/行为
不变），拿到的是与直接持有具体类完全相同的 `IAuraQuery`/`IEffectSink` 实例，不是阉割版。

**接线方式**：你方原本需要靠具体类 `SkillHost` 才能拿到这两个成员来做"被动技能与其常驻光环"的
只读核对（`AuraQuery.HasAura`/`AuraQuery.TryGetInstanceRef`）与施加/移除
（`EffectSink.ApplyAura`/`EffectSink.RemoveAura`），现在只持有 `ISkillHost` 接口引用即可拿到，
可以按此把相关会话对象的构造函数参数类型从具体类 `SkillHost` 改为接口 `ISkillHost`。

**判空口径**：`AuraQuery`/`EffectSink` 是"能不能拿到这根引用"的只读查询，允许显式降级为
`null`——面向一个不确定是否为生产实现的 `ISkillHost` 引用编程时，取用前必须判空；面向确定是生产
`SkillHost` 的场景（你方目前的实际情况），两者恒非空，判空只是防御性写法。这两个属性的降级口径
与 `LearnSkill`/`LearnFromBook` 那种"写路径禁止静默降级、必须抛异常"的口径不同——它们本身是纯
getter，不产生任何副作用。

## 反馈 5：普通攻击（武器驱动的自动重复攻击）

新增 `Core.Rules.Combat.AutoAttackHost`，全部公开方法：

```csharp
void SetEnabled(Id casterId, bool enabled);       // 开关（关闭时挥击计时器清零，目标不受影响）
void SetTarget(Id casterId, Id? targetId);        // 设置/切换/清空目标（切换时计时器清零）
bool IsEnabled(Id casterId);
Id? GetTarget(Id casterId);
AutoAttackState GetState(Id casterId);            // 三值可观测快照
void Update(double deltaSeconds);                 // 挥击计时驱动的核心推进
```

`AutoAttackState` 枚举三值：`Off`（未开启）/ `NoTarget`（已开启但无有效目标，任务原文"未攻击"）/
`Attacking`（已开启且有目标）。目标消失或死亡时目标被清空、状态回落到 `NoTarget`，`Enabled` 本身
不受影响；超出 `AutoAttackOptions.Range`（`double`，默认 `0` = 不限射程，与 `SkillDef.Range` 同一
惯例）时本次挥击被跳过但目标不清空。

**重点：它是挥击计时驱动，不是每帧/每 tick 无条件结算一次。** 新增 `AutoAttackTickHandler`（挂在
新增的 `TickPhase.CombatResolution` 阶段），**只在连续时间模式（`SimStep.Kind == Continuous`）下
驱动**，离散（回合制）模式本版不驱动。`RulesAssembly` 新增只读属性 `AutoAttack` / 
`AttackIntervalFallback`，供你方从既有装配根直接取到 `AutoAttackHost` 实例。

**攻击间隔的两级数据来源**（都取不到时**不产生任何攻击**，不静默降级为某个默认周期）：

1. 已装备武器时优先取 `IWeaponDamageQuery.GetWeaponAttackIntervalSeconds(Id unitId)`（新增默认
   接口成员，取 `item.template.weapon_profile.speed`，多把武器时取按槽位 id 序数最先的一个）；
2. 武器缺失（未装备或该槽没有 `weapon_profile`）时回退
   `IAttackIntervalFallbackProvider.GetAttackIntervalSeconds(Id unitId)`，读
   `core/carriers/creature.CreatureTemplate.AttackInterval`（`double?`，`creature.template` 新增
   可选字段 `attack_interval`，纯新增不升 schema 版本，`min` 严格大于 0）；
3. 两处都取不到值（或回退值 `<= 0`）：本次 tick 不发生任何攻击，计时器不推进，经
   `ICombatDiagnostics` 告警一次（同一原因持续期间只警告一次）。

**伤害走既有结算通道，不新增伤害公式**：命中时复用 `weapon_damage_pct` 效果原语，经
`IEffectSink.ApplyEffect` → `EffectDispatcher.ApplyDamageOrHeal` → `ICombatHost.ResolveEffect` →
`Resolver.Resolve`——与技能造成的伤害走**同一条**结算链路。`EffectContext.SkillId` 固定填
`AutoAttackHost.NativeSkillId`（`skill.native_auto_attack`，不对应任何真实注册的 `skill.def`，
仅供表现层/日志识别"这次结算来自普通攻击"）。

**发什么事件**：命中/致死时发布的 `combat.damage_dealt`（`CombatDamageDealtEvent`）与
`unit.died`（`UnitDiedEvent`）与技能击杀**逐字段同构**。**重点**：既有的 XP（
`CreatureDeathXpListener`）/掉落（`CreatureDeathLootListener`）监听器各自独立订阅同一个
`unit.died`，天然对普通攻击击杀与技能击杀一视同仁——**你方不需要为普通攻击写任何特判**，正常
接入 `AutoAttackHost` 即可让击杀经验/掉落照常触发。

**控制标志位**：`ControlFlags.NoAttack` 由 `AutoAttackHost` 内部单独识别（不要求叠加
`NoCast`/`NoMove`）——一个只打 `no_attack` 的"缴械"类控制光环即可正确拦截普通攻击，你方不需要
再在游戏侧手工判定一遍。命中该门控视为"被拦截、消耗掉"（不结算、不诊断），计时器清零重新计时。

## 不静默降级说明（接线期请留意诊断输出）

以上五条在数据取不到时，**均不是悄悄返回一个看起来正常的缺省值**，而是走诊断出口告警（Warning
级）+ 返回明确的缺省值：

- **反馈 1**：`ISkillHost`/`ISkillBookQuery` 的 `GetCastingSkillId`/`GetCastingRemaining`/
  `GetCastingTotal` 若命中降级默认接口实现（意味着接的是未升级的自定义宿主，你方走生产 `SkillHost`
  不会命中），恒返回 `null`，不发出诊断（这是只读查询的既有降级惯例，不属于本节重点）。
- **反馈 4**：`IAuraQuery.GetActiveAuraSnapshots` 若命中降级默认实现，`Remaining`/`Total`/
  `NameKey` 全部为 `null`（同上，生产实现不会命中）。
- **反馈 2**：这是**你方接线时最容易踩到的一处**——`ActionBarViewModel` 取不到完整就绪数据时会
  **真实调用 `IUiDiagnostics.Warn(...)`**，槽位标记为 `BlockReason.Unknown`，绝不当作
  `None`（无阻塞）处理。接线期请确保诊断出口已经接到你方能看到的控制台输出，若看到这条警告，
  说明 `ActionBarViewModel` 用的还是旧构造函数重载（未携带 `ISkillBookQuery`+`IUiDiagnostics`），
  或 `ISkillBookQuery` 实现没有正确转发 `GetSkillReadiness`。
- **反馈 3**：`ISkillHost.AuraQuery`/`EffectSink` 默认降级为 `null`，不发诊断（纯 getter，判空
  即可）——生产 `SkillHost` 恒非空。
- **反馈 5**：`AutoAttackHost.Update` 在武器攻速与生物模板回退间隔都取不到时，经
  `ICombatDiagnostics.Warn(...)` 告警（同一原因持续期间只警一次，中途数据变得可用又再次缺失会
  重新警告）。**这是最容易被忽视的一处**：如果你方给某个开启了普通攻击的单位既没配武器也没配
  `attack_interval`，普通攻击会"看起来没有生效"，但不是缺陷——去看诊断输出确认原因。

## 可以拆掉的绕行

以上五条交付前，你方各自的自建替代都可以拆除，直接换成框架原生数据：

- 施法条/光环列表：过去只能靠越过表现层直接拼 `ISkillHost`/`IAuraQuery` 才能拿到读条/光环细节，
  现在改用 `HudViewModel` 的新增属性或对应路径查询即可，不需要再自建这层适配。
- 技能栏径向冷却遮罩/就绪态着色：过去依赖直接调用 `ISkillHost.GetSkillReadiness` 拼装，现在换成
  `ActionBarSlotSnapshot` 的新字段 + 携带诊断出口的新构造函数重载。
- 依赖具体类 `SkillHost`（只为了拿 `AuraQuery`/`EffectSink`）而回退的接口化改造，现在可以重新
  推进——把构造函数参数类型从具体类换回 `ISkillHost` 接口。
- 自建的普通攻击控制器（每个固定模拟步手动判定目标合法性/出租绳/追击、手动查
  `IsCasting`/`GetCooldown`、手动调用 `CastSkill` 把普通攻击伪装成"重新施放一个技能"）现在可以
  整个拆除，换成 `AutoAttackHost.SetEnabled`/`SetTarget`/`Update` 三个方法驱动；对应地，之前为了
  让普通攻击"看起来是一个技能"而手填的 `skill.wow_auto_attack` 类技能定义（固定 `cooldown_duration`
  常量、`school_damage` 固定伤害、未接武器数值）也可以一并废弃，改用
  `weapon_profile.speed`/`weapon_school` 驱动真实的武器数值。
