
## 处理

### A. 第 42 条：非默认语言缺失 → Warning 级 `text_key_exists`

`core/foundation/data_registry/contracts/DataRegistryOptions.cs` 新增
`public bool WarnOnMissingTranslation { get; set; } = true;`：对 `l10n.locale` 表已登记、且不等于
`DefaultLocale` 的每个语言，若某 `TextKey` 字段引用的键在该语言下没有对应 `l10n.text` 行，报一条
Warning 级 `text_key_exists`（检查名与默认语言缺失时相同）；默认语言缺失仍是 Error，不受本开关
影响；`l10n.locale` 表未加载时天然跳过，不额外告警；设为 `false` 恢复"只查默认语言"的旧行为。

`core/foundation/data_registry/core/DataRegistry.cs`：

- 新增 `BuildLocaleValidationCaches`，在 `RunFieldValidation` 每次校验开始时调用一次（不是每个
  字段各遍历一次 `l10n.locale`）：建立 `_nonDefaultLocalesCache`（非默认语言 id 清单）与
  `_localeFallbackCache`（语言 id → `fallback`，无则 `null`）两份缓存；`l10n.locale` 未加载时两者
  都置 `null`。
- `ValidateTextKeyField`：默认语言检查不变（Error）；默认语言下该键确认存在、且
  `WarnOnMissingTranslation` 为 `true`、且 `_nonDefaultLocalesCache` 不为 `null` 时，遍历非默认
  语言清单，缺失该键的语言各报一条 Warning，消息形如：

  ```
  文本键 "K" 在语言 "l10n.locale.en_us" 下缺失（该语言经回退链在 "l10n.locale.zh_cn" 下有文本，
  运行时回退）
  ```

  （真实示例见下"验证"一节实测输出，非本文档手写。）
- 新增 `ResolveFallbackLanding`：沿该语言的 `fallback` 链逐级查是否有该键文本，找到即返回；链
  耗尽（或成环，`visited` 集合防御——正常数据构造期不会出现，`DataRegistry` 本身不像
  `core/foundation/localization/core/L10nHost.cs` 的 `ValidateNoFallbackCycle` 那样在构造期拒绝
  这种数据，防御必须独立成立）仍未找到，落到默认语言（调用方已确认默认语言下该键存在，这一步
  保证消息里的"运行时回退"是真话——与 `L10nHost.TryResolve` 的回退语义一致：先查回退链、链耗尽
  兜底默认语言）。
- 默认语言这个键本身缺失时（Error 分支）直接 `return`，不会再额外为非默认语言补 Warning——两者
  互斥，同一字段至多命中其中一种。

`toolchain/validator/Program.cs` 新增命令行开关 `--no-missing-translation-warning`（把
`ContentValidationOptions.WarnOnMissingTranslation` 置 `false`，经
`presentation/assembly/ContentValidationAssembly.cs` 透传给 `DataRegistryOptions`）；非 `--json`
模式追加一行 `missing translation warning: enabled|disabled`（惯例同既有"optional rules
disabled"行）；`--json` 模式在 `display_map_coverage_sources` 字段之后追加
`warn_on_missing_translation` 布尔字段，检查名不新增、仍是 `text_key_exists`，消费方按检查名
过滤的既有逻辑不受影响。`toolchain/validate_data.py` 新增同名 `--no-missing-translation-warning`
透传参数。

契约文档：`architecture/04_数据与内容管线.md` 第 5 节校验项清单"文本键存在"一行改写，变更记录表
新增一行（本条为既有检查项覆盖面的补齐，不改变结论，不出 ADR）。

## 对编辑器的使用建议

1. **本地化矩阵 `HasMissing`（`Editor.Core.Localization.L10nMatrixBuilder`）现可改为复用框架
   `text_key_exists` Warning**——不必再自行扫描 `l10n.text` 判定"哪些键在非默认语言下缺翻译"；
   建议做法：对同一份数据跑一次 `DataRegistry.LoadAll`/`toolchain/validator --json`，按
   `check == "text_key_exists" && severity == "warning"` 过滤即得到与框架诊断同源的缺失清单
   （`field`/`record_key`/`table` 三元组可直接定位到具体记录字段，不必二次推断）。矩阵展示层
   若还想要"回退后实际会显示哪个语言的文本"这类信息，消息文本里已经带了回退落点，也可以直接
   解析复用，不需要重新实现一遍回退链查找。
2. **`WarnOnMissingTranslation` 默认 `true`**——若编辑器基础套件的装配调用未来某个场景不想要
   这条 Warning（例如某些历史项目数据本就大量缺非默认语言翻译、暂不想在校验面板刷屏），可以
   经 `ContentValidationOptions.WarnOnMissingTranslation = false` 关闭，检查名不变，不影响其它
   校验项。
3. **消息文本目前不含结构化的"回退落点语言 id"字段**——落点信息目前只拼在
   `ValidationIssue.Message` 里（人类可读），矩阵展示层若需要结构化提取，建议按
   `在语言 "(.+?)" 下有文本` 这类正则从消息里解析，而不是重新计算一遍回退链（重新计算容易与
   框架实际使用的回退语义出现细微不一致，见 `core/foundation/localization/core/L10nHost.cs`
   `TryResolve` 判断记录）。这不是新增的结构化字段，若后续需要按字段消费，建议消费方提出新的
   反馈条目，本次改动不预先扩展 `ValidationIssue` 结构。
4. **`data/_sample/l10n` 的两个演示键**（`l10n.ui.sample_fallback_demo.text`/
   `l10n.ui.sample_variable_demo.text`）可以直接用于编辑器侧"回退链/变量缺失"UI 交互的手工验证
   或自动化测试固件，不必再自行注入内存态第二语言（`Editor.TestSupport.Localization.
   L10nTestSupport.InjectSecondLocale`）——这两个键与真实数据集共存，跑一次真实加载即可复现两种
   行为路径。

## 复核附带收口：l10n.locale.fallback 改为引用登记

独立复核确认第 41/42 条本身实现无误，但另指出一处既有缺口（非本批新引入，早于本批已存在）：
`core/foundation/localization/contracts/L10nSchemas.cs` 的 `l10n.locale` 表，`fallback` 字段此前
登记为 `FieldKind.Id`（只校验格式合法，不校验目标是否真的存在），指向未登记语言的坏数据在
`DataRegistry.LoadAll` 加载期不会被拦下，要等到 `core/foundation/localization/core/L10nHost.cs`
构造期（`ValidateNoFallbackCycle`）才抛 `ArgumentException`——发现时机偏晚，且报错途径与其它
字段引用类问题（`reference_integrity`，加载期即报）不一致。整合 agent 决定随本批一并收口，不必
另等下一批反馈。

处理：`fallback` 字段改登记为 `FieldKind.Reference`（`referenceTable: "l10n.locale"`），仍
`required: false`，描述改为"回退语言 id，可为空；须为本表已登记的语言 id"。核对确认
`reference_integrity` 检查项对自引用表（目标表就是字段所在表本身）无特殊限制——`ReferenceExists`
只是查目标表名对应的已加载表里是否有该主键，`l10n.locale` 校验自己表内某条记录的 `fallback` 时，
`l10n.locale` 本表显然已加载，判定逻辑与引用任何其它表完全一致；对 `null`（字段可选、未填）也不
报错——`DataRecord.Has` 对 JSON `null` 返回 `false`，`ValidateRecordField` 对非 `Required` 且
`!Has` 的字段直接跳过，不会走到 `ValidateReferenceField`。

新增测试（`core/foundation/localization/tests/L10nHostTests.cs`，紧跟"5. is_default 缺失/重复；
回退链成环"一节之后）：

- `LoadAll_FallbackPointsToUndeclaredLocale_ReportsReferenceIntegrityError`：`fallback` 指向未
  登记的语言（`l10n.locale.ja_jp` 不存在）→ `DataRegistry.LoadAll` 报告中出现一条
  `Severity.Error`、`Check == "reference_integrity"`、`Field == "fallback"` 的问题——即加载期
  （早于 `L10nHost` 构造）就能拦下，不必等到构造期。
- `LoadAll_FallbackNullOrDeclaredLocale_NoReferenceIntegrityIssues`：`fallback: null` 与
  `fallback` 指向已登记语言两种情况混用同一次加载 → `report.ErrorCount == 0`，且不存在任何
  `fallback` 字段的 `reference_integrity` 问题。

原有"自我 fallback"（`Constructor_SelfFallback_ThrowsArgumentException`）与"两语言回退环"
（`Constructor_TwoLocaleFallbackCycle_ThrowsArgumentException`）两例不受影响——它们的 `fallback`
值本身是合法引用（指向已登记语言，含指向自己），`reference_integrity` 不会报错，"不允许成环"是
语义层规则，仍然只能在 `L10nHost` 构造期检测，与本次改动的职责边界（"目标语言 id 是否存在"）不
重叠。

SchemaAudit（`dotnet run --project toolchain/validator -- --schema-audit --allowlist
toolchain/schema_audit_allowlist.json`）复跑：`tables 64, fields 817, errors 0, warnings 0`，
与改动前一致，未因此新增告警。`--list-tables --json` 里 `l10n.locale.fallback` 的
`field_meta.kind` 从 `"Id"` 变为 `"Reference"`，新增 `reference_table: "l10n.locale"`，属登记
