## 现象与复现

### 第 67 条：验收样例数据集不在真实分发产物内

`build.ps1`（主 zip 判断记录）明确"分发包只带框架级数据表（`data/_framework`），不带
`data/_sample`（自测用示例数据）"。按产品文档第 10.2 节 S4 第 4 条验收步骤操作，在只拿到分发
产物、未 clone 框架源仓库的真实消费方环境下，确实找不到 `data/_sample`/`assets/_sample`——复现
步骤本身成立。

### 第 68 条：无命令行入口能无人值守把运行期宿主带入并保持可交互运行

全仓库改动前只有"跑完即退"语义的命令行入口（构建全部场景、`-gf-smoke-template` 无人值守冒烟），
没有一个入口"进入可交互状态后保持存活、供外部持续观察/操作，直到外部主动结束"。"一键运行"对
Unity 工程路径分支只能降级为"打开 Editor 窗口手工点 Play"。

### 第 69 条：无官方工具把任意源内容目录同步到任意目标运行期工程

`toolchain/sync_package_content.ps1` 只同步框架级 `data/_framework`；`build.ps1 -SyncContent`
只能在框架源仓库内运行，写入框架自己的工作台；两者均不接受"任意源目录 + 任意目标工程路径"这样
一对通用参数。

### 第 70 条：`DataHotReload` 只监视部署副本，无开发期直连源码数据目录的入口

`games/_template/Runtime/GameBootstrap.cs`（改动前）构造 `UnityFileSystem` 时未传
`contentRoot`，`watchRoots` 固定拼自 `Application.streamingAssetsPath`；全仓库未见任何"覆盖
内容根"的命令行/环境变量入口。直接改源码数据目录不会触发热重载，须先同步到部署副本。

### 第 71 条：`ValidationIssue.ToString()` 精确格式未在任何接口/契约文档中承诺稳定

`core/foundation/data_registry/contracts/ValidationReport.cs`（改动前）`ToString()` 产出形如
`[Error] required_field display.map[display.sample_map].sprite_set_id: ...` 的文本，全篇无
`[Stable]`/"稳定契约"标注，与框架内其它明确标注的公开 API 待遇不同——复现步骤本身成立。

### 第 72 条：Unity 批处理构建 `-buildWindows64Player` 无开关指定 Development Build

`consumer_smoke.ps1` 第 9 步直接调用 Unity 内置 `-buildWindows64Player`，该开关本身不接受
"是否 Development"参数；全仓库搜索 `Development`/`BuildOptions` 只命中
`games/_template/README.md` 一处纯文字说明，无脚本封装。按现有调用原样构建，产物不是
Development Build。

## 根因

- 第 67 条：`data/_sample` 自初版起定位为框架仓库自测/冒烟数据，从未打算随主分发产物走；独立
  的样例数据获取通道（见"事实核查"）自 1.15.0 起已具备，但 `games/_template/README.md` 这个
  面向新游戏立项的入口文档从未提及，是文档指引缺口而非能力缺口。
- 第 68、69 条：框架历史上只按"自动化门禁需要确定性退出、跑完即退"这一种运行模式设计命令行
  入口，从未设计过"长驻可交互"这一生命周期承诺；内容同步入口也都各自绑死在自己的既定流程
  （私服包解析结果、框架自身工作台固定路径）上，从未抽出一个不带任何专属假设的通用参数化入口。
- 第 70 条：底层 `UnityFileSystem` 构造函数早已支持可选 `contentRoot` 参数，只是模板层
  `GameBootstrap.cs` 从未接线暴露为命令行/环境变量开关——是接线缺口，不是能力缺口。
- 第 71 条：`ToString()` 自初版起就是"给人看的一行诊断文本"这一实现意图，但从未用文档/注释明确
  这一立场；与此同时命令行 `--json`（`toolchain/validator`、`check_cmd.py`）与 C# 结构化属性
  各自独立演进多个版本，两条演进线从未在文档层面互相对照说明，导致消费方误以为"没有稳定格式"
  等于"没有结构化出口"。
- 第 72 条：Unity 批处理内置开关的参数面是引擎方固定的，本身不支持 `BuildOptions.Development`；
  框架侧此前只在 README 写了文字提示，从未封装等价的 `-executeMethod` 入口。

## 处理

### 总原则（第 68、69 条，[ADR-0040](../adr/0040-运行期宿主命令行能力契约.md)）

拍板：框架对外暴露的运行期与内容工具类命令行能力，一律设计为**通用、参数化、可被任意外部工具
调用**的入口；不为任何具体消费方（含内容编辑器项目）定制专属协议。这类入口的参数面、输出格式、
退出码约定本身即是公开契约，纳入与框架其余公开契约同等的稳定性管理。理由与备选方案（"直接做成
专属联调协议"为何不选）见 ADR-0040 正文"决策 1"与"备选方案"两节。

### 第 68 条：长驻可交互运行入口 `-gf-resident`（`ResidentRunner.cs`）

- 与既有 `-gf-smoke-template`（跑完即退，门禁/CI 需要确定性退出码）**并列新增，不取代**，共享
  同一套 `GameBootstrap`/`TemplateShellUi` 装配与场景加载路径。
- **就绪信号**：进入可交互状态（主菜单可见）后用 `File.WriteAllText` 写出就绪文件（默认
  `<persistentDataPath>/gf_resident_ready.txt`），同时打印 `[GF-RESIDENT] status=ready
  ready_file=<路径> stop_file=<路径>` 日志行；外部工具应轮询就绪文件，不应假定"进程已启动"等价
  于"已进入可交互状态"。
- **受控退出**：外部工具创建停止文件（默认同目录 `gf_resident_stop.txt`），本入口每 0.25 秒
  轮询一次，检测到后打印结果、删除停止文件、以退出码 `0` 结束——不依赖 Ctrl+C/SIGINT（判断记录：
  批处理独立版下这类信号能否可靠送达托管代码本身不确定，效果可能等同于强杀，不满足"非强杀"
  要求）。
- **退出码**：复用 `-gf-smoke-template` 既有分级，只用 `0`（成功）/`2`（失败）两档，不使用其
  看门狗超时码 `3`（本入口无总运行时长上限）。
- **游戏数据集根覆盖开关**：命令行参数 `-gf-dataset-root=<相对路径>`（等号连接，短横线全小写
  风格），覆盖 `GameBootstrap.GameDatasetRootOverride`（默认不覆盖，即 `data/game`），与
  `sync_content.ps1` 的目标参数面对齐（先同步内容、再以该子目录启动本入口）。**这不是文件系统
  级的内容根**，只覆盖 `data/game` 这一相对子目录，见下方"撞名已消解"一节。**判断记录（命名）**：
  落地时初名把"数据集根"错写成了"内容根"，与第 70 条的 `-gfContentRoot` 拼写几乎相同、语义却
  完全不同，是两条并行开发分支的偶然撞车；整合阶段（提交 `2552ed8`）已改名为语义更贴切的
  `-gf-dataset-root` 消除歧义，`-gfContentRoot` 不受影响，命名约定详见 ADR-0040 决策 5。
- 测试：`games/_template/Tests/Runtime/GameTemplateResidentTests.cs` 新增 3 个 PlayMode
  `[UnityTest]`——就绪→保持→受控退出→退出码链路 1 例；数据集根覆盖生效改为一对有区分力的
  用例`ResidentRunner_DatasetRootOverride_LoadsProbeTable_FromOverrideRootOnly`/
  `..._Absent_DefaultRootNeverSeesOverrideProbeTable`（写入只存在于覆盖根的探针表，断言只有
  传了覆盖参数才能读到，取代了此前"覆盖值=默认值，通过与失败无法区分"的假测试）；另在纯 .NET
  侧补充等价回归 `core/foundation/data_registry/tests/GameDatasetRootOverrideEquivalenceTests.cs`
  （3 例，已做反向确认）。真实独立版下的进程退出码/长驻行为，以及上述 PlayMode 用例的反向确认，
  仍**待整合时统一跑引擎门禁确认**，不预先宣称通过。

### 第 69 条：通用参数化内容同步入口 `sync_content.ps1`

- 参数面：`-SourceDir`/`-TargetDir`（均必填，任意路径，不对目标做任何 Unity 工程/
  StreamingAssets 子路径拼接假设）、`-OverridePolicy`（`Additive` 默认，只新增/更新、保留目标
  独有文件；`Mirror`，以源为准清理目标多余文件）、`-DryRun`（只报告不写入）。
- 幂等：按内容哈希（非修改时间）判定变化，源不变时重复运行不产生有意义差异。
- **与既有两个同步入口并列，不取代、不包装**——`toolchain/README.md`"三个同步入口如何选"对照表
  给出适用场景：
  | 入口 | 源 | 目标 | 专属规则 | 适用场景 |
  |---|---|---|---|---|
  | `sync_content.ps1`（新增） | 任意路径 | 任意路径，字面同步 | 无，只有 Additive/Mirror 两种 | 框架发布流程与私服通道之外的任意场景 |
  | `sync_package_content.ps1` | 私服解析到的包内容（`Data~/`） | 固定拼到消费方工程 `Assets/StreamingAssets/GameFoundation/` | 按 `resource_layout_map.json` 改名/扁平化 | 走私服通道接入框架的游戏工程 |
  | `build.ps1 -SyncContent` | 框架仓库自己几类内容，源路径硬编码 | 框架自己的开发自测工作台，目标路径硬编码 | 一次同步多组路径对 + 专属自检 | 仅框架仓库自己开发/自测 |
- 测试：`toolchain/tests/test_sync_content.py` 新增 9 例（参数校验×3、Additive、Mirror、
  DryRun、幂等等）。

### 第 70 条：开发期直连内容源目录 `-gfContentRoot`（`ContentSourceRootOverride.cs`）

- 命令行参数 `-gfContentRoot <路径>`（空格分隔，驼峰风格）或环境变量 `GF_CONTENT_ROOT`，把
  `GameBootstrap` 的**内容根整体**指向任意外部目录；数据加载与 `DataHotReload` 监视都会改用
  该目录（两者共享同一套解析规则），不再局限于 StreamingAssets 部署副本——可以直接指向某个游戏
  仓库自己的数据源目录，编辑后立刻生效，不需要每次先跑 `-SyncContent`。
- 命令行参数优先于环境变量；都未指定时行为与改动前完全一致。
- **指定了不存在的目录会让装配显式失败**（`GameBootstrap.BootstrapFailed = true`，Console 打印
  明确原因），不静默回退到默认部署副本根。
- 测试：`games/_template/Tests/Editor/ContentSourceRootOverrideTests.cs` 新增 8 个 EditMode
  `[Test]`（纯函数解析优先级/边界条件）+ `games/_template/Tests/Runtime/
  ContentSourceRootOverridePlayModeTests.cs` 新增 2 个 PlayMode `[UnityTest]`（真实验证热重载
  确实监视覆盖后的根；不存在目录时验证显式报错不静默）。

### 第 71 条：`ValidationIssue.ToString()` 格式稳定性声明（如实澄清，未新增运行期出口）

- `ValidationReport.cs` 的 `ToString()` 新增 XML 文档注释，明确"人类可读、不承诺格式跨版本
  稳定、不应被程序解析"的立场；`core/foundation/data_registry/README.md` 新增对应说明章节。
- **未实现运行期结构化出口**：评估两种方案（事件总线携带结构化列表 / 运行期落盘结构化诊断）后
  认为均需要设计层先拍板的新对外契约，本次不擅自实现，详见"待消费方答复"一节的反问。

### 第 72 条：批处理构建暴露 Development Build 选项
