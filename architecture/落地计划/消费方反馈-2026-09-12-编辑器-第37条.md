## 现象复现与根因

- **现象**：`core/rules/skill/schema/SkillSchemas.cs:499` 把 `trigger_skill` 登记为
  `new FieldSchema("trigger_skill", FieldKind.Id, required: true, description: "触发后释放的技能")`，
  未调用 `.WithSoftReference(...)`；`core/rules/assembly/RulesSchemaCatalog.cs:184-186`
  （`DeclareKnownReferences` 方法）三处 `registry.DeclareReference(fromTable, field, toTable)`
  调用里，`arch.class.primary_stat`（第 30 条，已 1.23.0 修复）与 `skill.def.target_shape_ref`
  （第 29 条，已 1.20.0 修复）对应字段均已同时补登 `SoftReferenceTable`/`ReferenceTable`，唯独
  `registry.DeclareReference("skill.proc_def", "trigger_skill", "skill.def")` 这一处的字段
  一直没有补登。
- **根因（两层）**：
  1. **具体遗漏**：`trigger_skill` 单纯是 29/30 号反馈那一轮全仓排查的漏网之鱼——`declareReference`
     侧的登记与字段元数据侧的登记是两处独立代码，没有任何机制保证"经 `DeclareReference` 声明的
     字段"与"字段元数据登记了引用提示"这两件事同步，只能靠人工排查（本条反馈原文核实：`SkillSchemas.cs`
     与 `RulesSchemaCatalog.cs` 独立维护，前者不知道后者登记了什么）。
  2. **结构性缺口**：`DeclareReference` 只写入 `IDataRegistry`（注册期一侧的私有列表，驱动加载期
     `reference_integrity` 硬校验），`IDataRegistryView`（内容工具实际持有、只读消费的接口）没有
     任何方法可以读回已声明的引用关系——即便字段元数据侧也漏登了，内容工具原本也无法从框架侧
     得到"这里其实声明了一条引用"这个事实，只能通过读源码或按值弱推断发现。第一层遗漏本可以靠
     第二层的读回能力被内容工具及早发现并反馈，但两层同时缺失，问题才拖到 P3.1 引用图实现阶段
     才被发现。

## 处理

### 第一步：`trigger_skill` 补登软引用（原始案例本身）

`core/rules/skill/schema/SkillSchemas.cs`：

```csharp
new FieldSchema("trigger_skill", FieldKind.Id, required: true,
    description: "触发后释放的技能，指向 skill.def（消费方反馈第 37 条：登记为软引用，仅供内容工具补全/跳转，与 RulesSchemaCatalog.DeclareKnownReferences 的加载期硬校验并列）")
    .WithSoftReference(table: "skill.def"),
```

写法与 29/30 号反馈同一路径（`target_shape_ref`/`primary_stat` 已有的登记范式）。

### 第二步：`declareReference` 登记可读回（结构性根治）

**新增只读契约面**（`core/foundation/data_registry/contracts/ReferenceDeclaration.cs`，新增类型；
`IDataRegistry.cs` 新增两个带默认实现的接口成员）：

```csharp
namespace Core.Foundation.DataRegistry
{
    public readonly struct ReferenceDeclaration
    {
        public string FromTable { get; }
        public string FieldPath { get; }
        public string ToTable { get; }
        public string? ToDomain { get; }   // 预留，DeclareReference 当前只支持按表声明，恒为 null
        public bool IsOptional { get; }    // 源字段 FieldSchema.Required 取反；源表/字段未知时保守为 true
        public string? Source { get; }     // 登记来源标注（如 "RulesSchemaCatalog"），旧三参数调用为 null

        public ReferenceDeclaration(string fromTable, string fieldPath, string toTable,
            string? toDomain, bool isOptional, string? source);
    }

    public interface IDataRegistryView
    {
        // ……既有成员不变……

        // 新增，带默认实现（恒返回空集合），DataRegistry 显式覆盖。
        IReadOnlyList<ReferenceDeclaration> GetReferenceDeclarations() =>
            System.Array.Empty<ReferenceDeclaration>();
    }

    public interface IDataRegistry : IDataRegistryView
    {
        void DeclareReference(string fromTable, string field, string toTable);  // 既有签名不变

        // 新增重载，带默认实现（转发到三参数版本、丢弃 source），DataRegistry 显式覆盖为真正记录。
        void DeclareReference(string fromTable, string field, string toTable, string source) =>
            DeclareReference(fromTable, field, toTable);

        // ……既有成员不变……
    }
}
```

**`DataRegistry` 实现**（`core/foundation/data_registry/core/DataRegistry.cs`）：内部
`_declaredReferences` 列表由三元组 `(FromTable, Field, ToTable)` 扩展为四元组（追加
`Source`，`string?`，物理上是新增字段，不是修改既有存储结构的可见部分）；`GetReferenceDeclarations()`
显式实现遍历该列表，现场查一次源表 `TableSchema`/字段 `Required` 算出 `IsOptional`，按登记顺序
（`List<T>` 天然有序）构造 `ReferenceDeclaration` 数组回吐——有序、确定性，不做任何排序/去重。

**`RulesSchemaCatalog` 同步改用带来源重载**（`core/rules/assembly/RulesSchemaCatalog.cs`，
`DeclareKnownReferences` 方法）：三条既有声明统一补上来源标注 `"RulesSchemaCatalog"`（本方法所在
类型名），声明本身（源表/字段/目标表）不变：

```csharp
const string source = nameof(RulesSchemaCatalog);
registry.DeclareReference("arch.class", "primary_stat", "stat.definition", source);
registry.DeclareReference("skill.def", "target_shape_ref", "target.chain_def", source);
registry.DeclareReference("skill.proc_def", "trigger_skill", "skill.def", source);
```

**ABI/兼容性判断记录**：`DeclareReference(string, string, string)` 物理签名完全不变（现有编译
产物的调用点不受影响）；新增的两个接口成员都是"带默认实现"（`IsVirtual && !IsAbstract`），不
要求任何既有实现类型改动即可编译通过——`InterfaceDefaultMemberForwardingTests`（六个核心程序集
反射门禁）验证 `DataRegistry` 已显式转发两者，未新增豁免条目；`SchemaAudit.Run` 的既有两参数
重载物理签名不变（新增三参数重载转发、`referenceDeclarations` 传空集合）；`toolchain/validator
--list-tables --json` 新增字段追加在既有 `display_map_coverage_sources` 之后、闭合大括号之前，
不改动任何既有字段。ABI 探针（见"验证"节）实测 `breaks=0`。

### 第三步：`SchemaAudit` 新增 `declared_reference_unregistered` 检查（防遗漏，告警级）

记录"），新增 `CheckDeclaredReferencesRegistered` 私有方法——对 `referenceDeclarations` 里每条

`ReferenceTable`/`ReferenceDomain`、也无 `SoftReferenceTable`/`SoftReferenceDomain`、也无
`AllowedValues`，报告一条告警（检查名 `declared_reference_unregistered`）；源表不在本次审计范围
内、或声明的字段名在登记表里找不到，均跳过（同 `CheckKnownTimeFieldsHaveUnit` 既有惯例"表未
登记进本次审计范围不属于本检查职责"）。

**全仓排查结果**：真实生产代码里调用 `registry.DeclareReference(...)` 的唯一位置是

| `skill.def.target_shape_ref` | `target.chain_def` | 已登记 `SoftReferenceTable`（第 29 条，1.20.0） | 无需改动 |
| `skill.proc_def.trigger_skill` | `skill.def` | **未登记**（本条原始案例） | 已补登 `SoftReferenceTable`（第一步） |

补齐后，`toolchain/validator --schema-audit --allowlist toolchain/schema_audit_allowlist.json --json`
