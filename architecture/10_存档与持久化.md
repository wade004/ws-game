## 1. 总则

拍板决策 9（存档是唯一持久化，见 [adr/0009-存档是唯一持久化.md](adr/0009-存档是唯一持久化.md)）确立：本架构不存在账号层、不存在服务端持久化，玩家的一切进度都落在"存档"这一份带版本的结构化文档里。存档系统 SaveSystem 属于 L0 基础层（见 [01_分层与依赖.md](01_分层与依赖.md)），对上层暴露窄契约，具体读写落盘经引擎适配层的文件系统接口（见 [02_引擎适配层.md](02_引擎适配层.md)）完成。

## 2. 存档模型

一份存档是一份带 `save_version` 的结构化文档，分为若干段；每段职责单一，允许独立迁移。

### 2.1 meta 段

供存档槽 UI（见 [09_表现层.md](09_表现层.md) Shell 一节）展示摘要，不参与模拟。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| save_version | Int | 是 | 存档 schema 版本号，迁移链据此判断需要跑哪些迁移函数 |
| slot_id | Id | 是 | 存档槽标识 |
| created_at | String | 是 | 创建时间（结构化时间文本，格式待选型） |
| updated_at | String | 是 | 最近一次写入时间 |
| play_time_seconds | Int | 否 | 累计游玩时长，用于摘要展示 |
| display_summary | Map<String, String> | 否 | 游戏层自定义摘要字段（角色名、等级、当前区域名等，供存档槽 UI 展示，键由游戏层约定） |
| game_id | Id | 是 | 标识本存档所属的具体游戏，防止跨游戏误读档 |
| difficulty_id | Id | 否 | 引用 [08_玩法层_掉落任务对话关卡.md](08_玩法层_掉落任务对话关卡.md) 的难度定义 |

### 2.2 player 段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| progression | Map<String, Any> | 是 | 等级、经验等 Progression 状态（见 [01_分层与依赖.md](01_分层与依赖.md) L1 `core/numbers/progression`） |
| archetype_id | Id | 是 | 职业/种族模板引用 |
| known_skills | List<Id> | 是 | 已习得技能 id 列表 |
| skill_bindings | Map<String, Id> | 否 | 技能槽位与技能 id 的绑定关系（口味相关，动作条槽数不固定） |
| inventory | List<ItemInstance> | 是 | 背包物品实例列表 |
| equipment | Map<String, ItemInstance> | 是 | 按槽位存放的已装备物品实例 |
| currencies | Map<Id, Int> | 否 | 货币余额（见 08 Economy） |
| quest_state | Map<Id, QuestProgress> | 是 | 任务状态（见 08 Quest） |
| achievement_state | Map<Id, AchievementProgress> | 否 | 成就进度（见 08 Achievement） |
| input_bindings | Map<String, String> | 否 | 玩家自定义按键绑定（若允许随存档而非随设置文件走，见 5 节说明，默认建议放设置文件） |

`ItemInstance` 是一条独立结构（实例 id、模板 id、堆叠数、实例级词缀/耐久等可选字段），字段细节见 [07_载体层_物品生物物件.md](07_载体层_物品生物物件.md)。

### 2.3 world 段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| current_map_id | Id | 是 | 当前所在地图/场景 id |
| current_position | Vec2 | 是 | 玩家在当前地图的位置 |
| world_state_flags | Map<String, Bool｜Int> | 是 | WorldState 命名空间标志字典的完整快照（见 [05_对象模型与世界.md](05_对象模型与世界.md) 第 8 节、拍板决策 8） |
| spawn_state | Map<Id, SpawnRecord> | 否 | 刷新系统的持久化部分（如已击杀的一次性刷新点），可选，取决于刷新策略是否需要跨读档记忆（见 05 Spawn）；`once` 策略的已触发标志记在 `world_state_flags`，本段只存计时与计数 |
| discovered_areas | List<Id> | 否 | 已探索区域/地图记录，供地图 UI 使用 |
| dropped_loot | Map<Id, DroppedLootRecord> | 否，可选，实现期补录 | 地面掉落物快照，是否持久化为策略配置项，呼应 05 第 1.6 节 |
| vendor_stock | Map<Id, VendorStockRecord> | 否，可选，实现期补录 | 商人限量库存与补货计时 |
| difficulty | {tierId: Id, scope: Id} | 否，可选，实现期补录 | 当前难度档与作用域 |

### 2.4 rng 段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| stream_states | Map<String, RngStreamState> | 是 | 分流随机源（`RngHost` 契约见 [01_分层与依赖.md](01_分层与依赖.md)，时间与计时器约定见 [03_运行时骨架.md](03_运行时骨架.md) 第 8 节）每条流的当前状态，保证读档后随机序列不因存读档而"重置手气" |

### 2.5 哪些不存

| 数据 | 是否存档 | 理由 |
|---|---|---|
| 属性快照（StatBlock 聚合结果） | 默认不存 | 属性是基础值 + 装备 + 光环等来源实时聚合的派生结果（见 06 三段式聚合），存基础来源（装备、已知天赋等）后可在读档时重新聚合得到，避免"存了旧公式算出的值，改了平衡性数值后读档结果与实时计算不一致"的双份真相问题 |
| 光环实例（Aura 运行时实例） | 默认不存 | 光环多数是战斗/临时状态（增益减益、持续时间），单机读档场景下重新进入游戏即视为"回到相对安全状态"更符合玩家预期；魔兽世界的持久性光环（坐骑、天赋被动）本质是"永久授予"，不属于此处讨论的临时光环 |
| 战斗中间状态（施法队列、仇恨表） | 不存 | 属于战斗会话内的瞬时状态，读档后重新进入战斗自然重建 |

（建议）可配置例外：若某游戏的口味需要"读档后光环继续生效"（例如长效增益道具、剧情限定的持续性效果），建议开放一个显式的"可持久光环"标记位（数据层面的字段，而非默认行为），由该光环自身声明需要参与存档，SaveSystem 按标记决定是否序列化其实例，其余光环维持默认不存的规则不变。

## 3. Persistable 契约

存档不是"整个世界状态一次性打包"，而是由各模块各自实现 Persistable 契约、SaveSystem 汇总拼装，保持模块边界清晰、便于独立测试。

```
interface Persistable {
  save(): Map<String, Any>
  load(data: Map<String, Any>): void
}
```

- 任何持有需要跨读档保留状态的模块（Progression、Inventory、QuestState、WorldState 等）都实现该契约，并在 DataRegistry/模块注册表登记自己的存档段 key。
- SaveSystem 汇总顺序（拍板，固定，避免加载时出现"依赖尚未加载的数据"）：

```
1. meta（仅摘要，不影响模拟）
2. world_state_flags（先恢复标志字典，因为后续多数模块的条件判断依赖它）
3. player.progression / archetype
4. player.inventory / equipment（依赖 archetype 已确定的合法槽位规则）
5. player.known_skills / skill_bindings
6. player.quest_state / achievement_state / currencies
7. world.current_map_id / current_position（触发场景路由加载对应地图）
7a. world.dropped_loot / world.vendor_stock / world.difficulty / spawn_state（世界附属段，依赖地图已确定；`spawn_state` 段 key 不带 `world.` 前缀，与第 2.3 节字段表一致）
7b. sim.turn_state（离散时间模型：TurnScheduler 的行动顺序/当前行动者/轮次/行动点账本，见 03 第 3.2 节、ADR-0013；只在离散模式装配时有内容，连续模式为空段）
8. rng.stream_states
9. 各模块 load() 完成后广播 "save.loaded" 事件，供表现层/玩法层做读档后一致性刷新
```

## 4. 存储位置与原子写入

- 存档读写一律经引擎适配层的 `IFileSystem` 接口为唯一定义处（见 [02_引擎适配层.md](02_引擎适配层.md) 第 1.6 节：`writeTextAtomic`/`readText`/`listFiles`/`exists`/`deleteFile`），SaveSystem 不直接触碰具体路径/平台 API，也不重复定义该接口；存档槽枚举经 `listFiles` 对用户数据目录下的存档子目录列举得到，不另设专用的 `listSaveSlots` 方法。
- 写入采用"先写临时文件、校验完整性、再原子替换正式文件"的策略，避免写入过程中断电/崩溃导致存档损坏，`writeTextAtomic` 已保证这一原子性语义（见 02 第 1.6 节性能约定）。
- 若技术选型阶段确定存档走二进制格式而非结构化文本，需在 02 增加 `writeBytesAtomic`/`readBytes` 一对接口，按 [12_扩展与变更流程.md](12_扩展与变更流程.md) 的变更流程评估影响范围后再实现，不得在本文档自行另定一套文件接口。
- （建议）每个存档槽额外保留一份"上一次成功存档"的备份（双缓冲），当校验发现最新文件损坏时自动回退读取备份，具体保留份数为可配置项。

## 5. 版本迁移

- `save_version` 单调递增；每次存档 schema 发生不兼容变更时，登记一个迁移函数，形成迁移函数链：

```
interface SaveMigration {
  fromVersion: Int
  toVersion: Int
  migrate(data: Map<String, Any>): Map<String, Any>
}
```

- 加载流程：读出存档 `save_version` → 依次应用链上所有 `fromVersion >= 当前版本` 的迁移函数直到达到当前运行时版本 → 再走第 3 节的 Persistable 加载顺序。
- 向前兼容：本架构不承诺"新存档在旧版本运行时打开"，只承诺"旧存档在新版本运行时经迁移链正确升级"；若某次变更导致无法逆向迁移，必须在迁移函数里显式标注不可逆。
- 损坏存档处理：读取失败或迁移中途异常时，SaveSystem 不得让整个应用崩溃，须捕获后转入"存档损坏"提示流程（见 Shell 存档槽 UI），并保留原始损坏文件不覆盖，方便人工找回。

## 6. 自动存档时机与手动存档

自动存档时机是口味配置项，基础架构提供触发点机制，不强制具体游戏必须启用哪几个：

| 触发点 | 说明 | 默认值（建议） |
|---|---|---|
| 存档点物件 | 世界中的 GameObject（见 07）触发的显式存档动作 | 开启 |
| 地图切换 | 场景路由完成一次地图切换后自动存档 | 关闭（避免频繁写盘，具体游戏可开启） |
| 任务完成 | Quest 状态机进入"完成"节点时自动存档 | 开启 |

手动存档：玩家在菜单/存档点主动触发的存档意图请求，走与自动存档相同的 SaveSystem 汇总与写入流程，唯一区别是触发来源。

## 7. 设置文件

- 设置（画面、音效音量、按键绑定、语言）与存档分离，单独落盘为一份不带 `save_version` 游戏进度语义的设置文档（可以有自己独立的版本号用于设置项的迁移）。
- 理由：设置是"这台机器/这个玩家"的偏好，不属于某一局游戏进度，删除存档不应清空设置，切换存档槽也不应互相影响设置。

## 8. 确定性与回放

- 呼应拍板决策 3（固定步长模拟）：核心模拟按固定步长 tick，分流随机源（Rng）保证同种子同输入序列产出同结果。
- 回放 = 固定步长 + 分流随机源初始状态 + 输入录像（玩家每个 tick 提交的意图请求序列）。只要三者一致，重放得到与原始运行完全一致的世界状态演变与战斗日志事件流。

```
interface ReplayRecorder {
  beginRecording(rngSeeds: Map<String, RngStreamState>): void
  recordInput(tick: Int, intent: Intent): void
  export(): ReplayData
}

interface ReplayPlayer {
  load(data: ReplayData): void
  stepTo(tick: Int): WorldSnapshot
}
```

`stepTo` 返回的 `WorldSnapshot` 结构为 `struct WorldSnapshot { tick: Int, eventLog: List<String>, digest: String }`——事件 key 序列与实体位置的确定性摘要，用于回放回归的自动比对。

用途：
- 内部验收：数据校验之外的"战斗平衡回归测试"可以用固定的输入录像跑出固定的战斗日志，比对是否与基线一致（见 [11_工程规范与测试.md](11_工程规范与测试.md) 回放回归）。
- 问题复现：玩家反馈的问题若能提供录像，可离线重放定位。
- （建议）游戏内战报/击杀回放这类玩法功能可以直接复用该机制，但是否作为面向玩家的功能是具体游戏的口味决定，不属于基础架构强制提供的玩法。

## 9. 魔兽世界服务端持久化与单机存档的差异

| 维度 | 魔兽世界（服务端持久化） | 本架构（单机存档） |
|---|---|---|
| 权威位置 | 服务端数据库，客户端只是投影 | 本机存档文件即唯一权威 |
| 写入时机 | 高频、增量、事务化（几乎每次状态变化都可能落库） | 低频、整份/分段快照，按触发点写入 |
| 多客户端一致性 | 需要处理断线重连、多端登录等一致性问题 | 不存在，同一时刻只有一份运行时状态 |
| 版本迁移 | 数据库表结构迁移，服务端统一执行一次 | 客户端读档时按需迁移，迁移函数需要长期维护兼容链 |
| 回放/审计 | 服务端日志用于反外挂与客服排查 | 回放用于确定性验收与问题复现，不涉及反作弊 |

## 基础架构提供 / 游戏层提供

| 能力 | 基础架构提供 | 游戏层提供 |
|---|---|---|
| 存档模型分段结构与字段表 | 是 | display_summary 等游戏自定义摘要字段的具体内容 |
| Persistable 契约与 SaveSystem 汇总顺序 | 是 | 各游戏特有模块实现自己的 save/load |
| 原子写入与文件系统接口 | 是（经适配层） | 无 |
| 迁移函数链机制 | 是 | 具体每次 schema 变更对应的迁移函数 |
| 自动存档触发点机制 | 是 | 具体启用哪些触发点、触发条件细节 |
| 确定性回放机制 | 是 | 是否把回放暴露为玩家可见功能 |

## 验收标准

1. 给定任意一份存档文档，能够仅凭本文档字段表还原出玩家进度、世界状态与随机源状态，无需查看具体游戏代码。
2. 人为损坏一份存档文件后，应用能优雅提示而不是崩溃，且原始损坏文件被保留。
3. 对同一份存档连续读取两次并各自推进相同的输入序列，两次结果的战斗日志事件流完全一致（确定性验证）。
4. 新增一个存档字段或调整某段结构，能在文档中定位到迁移函数链的挂接方式，无需推翻已有存档兼容性。
