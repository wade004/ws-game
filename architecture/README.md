## 1. 定位

本文档集描述一套**技术无关、与任何具体游戏解耦**的 2.5D Windows 单机 RPG **技术基础架构**（Game Foundation Architecture）。它不是某一款游戏的设计文档，而是承载**后续所有游戏**的运行时骨架与内容管线：

- 新起一款游戏 = 选定引擎实现「引擎适配层」+ 编写一层薄薄的「游戏层」代码 + 填数据表 + 配表现资源。
- 新增内容（一件装备、一个技能、一条任务）= 加数据行、配表现资源，**不改运行时代码**。
- 新增原语（一种全新的效果类型、光环类型、事件、物件类型、任务目标类型、对话动作类型）是唯一允许改运行时代码的开口，且必须走第 12 篇规定的审批流程。

架构的参考系是魔兽世界的真实系统设计（法术/效果/光环/触发、战斗日志、命中判定、仇恨表、物品与生物模板、掉落与任务模板、条件表、阶段化、外形映射、数据化 AI 等），裁剪为单机、单玩家、无网络的 2.5D 形态。架构本身不预设引擎、语言、存储格式，也不预设任何具体游戏的口味决定（技能数量、目标选择方式、是否有公共冷却、是否有消耗品、是否能跳跃等一律是可配置项或可替换策略）。表现形态由游戏层选择：默认 2D 精灵，可选 3D 模型；逻辑均为二维平面，场景默认 2D 地面图（详见 02、04、09 与 ADR-0012）。

## 2. 阅读顺序

建议按编号顺序通读一遍，之后按需查阅：

1. `00_架构总则.md` — 先建立定位、目标/非目标、裁剪原则、设计原则与名词表这些共识，是后面所有文档的前提。
2. `01_分层与依赖.md` — 建立七层骨架、依赖规则与模块清单，是查找"某个能力归哪一层/哪个模块"的地图。
3. `02_引擎适配层.md` — 运行时对引擎的唯一依赖面，决定"换引擎要改什么"。
4. `03_运行时骨架.md` — 生命周期、主循环、tick 顺序、场景路由，是理解"程序怎么跑起来"的主线。
5. `04` 之后按需查阅对应主题（数据管线、对象模型、规则层、载体层、玩法层、表现层、存档、工程规范、扩展流程、新游戏接入、资产规格）；数值设计相关文档在 `数值设计/` 目录，做数值设计或配平前先读 `数值设计/00_数值总纲.md`。
6. `adr/` 在需要理解"某条拍板决策为什么这样定"时查阅，索引见 `adr/README.md`。

## 3. 强制约束一览

以下约束贯穿全部文档，任何后续设计与后续文档都不得违反：

1. 架构与任何具体游戏解耦，不承载任何一款游戏的专属设定。
2. 架构与具体技术无关，不出现任何引擎、语言、框架、工具的名字。文档中的 `interface` 写法是中立的接口描述记法，不是代码，记法说明见 00 第 4.1 节。
3. 运行时逻辑不依赖引擎对象，引擎能力一律经引擎适配层接口进入。
4. 逻辑与表现彻底分离：逻辑不知道画面，表现层只读、只订阅事件。
5. 依赖只允许从上层调用下层，同层之间只经契约接口与事件总线通信。
6. 核心模拟按固定步长驱动，同种子同输入产生同结果（在同一平台与同一运行时二进制下逐位一致；跨平台只承诺逻辑等价、不承诺逐位一致），可脱离引擎独立测试。
7. 所有内容是结构化数据表，新增内容只加数据、不改代码。
8. 新增原语（效果/光环/事件/物件/任务目标/对话动作等类型）必须先出 ADR、再改注册表、再写代码、再补校验器与测试。
9. 全架构只用一种条件表达式语言表达一切条件与判定逻辑。
10. 游戏口味决定的内容（技能数量、目标选择、公共冷却、消耗品、跳跃等）一律做成可配置项或可替换策略，不写死。
11. 存档是唯一持久化方式，且带版本与迁移函数链。
12. 引擎选型是独立研究课题，架构本身不预设候选或结论。

## 5. 如何提变更

任何对本文档集的修改（新增一层、新增模块、改动某条拍板决策、新增原语）都必须走 `12_扩展与变更流程.md` 规定的流程：先判断变更类型（内容级 / 结构级 / 原语级），内容级直接改数据表说明，结构级与原语级必须先写一份 ADR 说明动机与影响，经设计层确认后才落到对应文档并更新版本号。不接受跳过 ADR 直接改本目录下文档的行为。
