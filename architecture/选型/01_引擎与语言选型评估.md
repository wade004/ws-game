# 引擎与语言选型评估 v1

> 目的：按 [`../02_引擎适配层.md`](../02_引擎适配层.md) 第 3 节评估框架，给出本项目当前采用的核心逻辑语言与第一个引擎适配层实现的具体选型结论与打分依据。
> 日期：2026-09-04
> 状态：已拍板（2026-09-04 用户确认）
> 上游文档：[`../02_引擎适配层.md`](../02_引擎适配层.md)

## 1. 问题拆分

选型拆成两个独立问题，按顺序回答：

1. **核心逻辑语言**——`core/` 全部纯逻辑模块用什么语言实现。
2. **第一个引擎适配层实现**——`adapters/` 下第一套正式（非桩）实现选哪个引擎。

约束：核心逻辑语言必须被选定的引擎原生承载（不引入跨语言绑定层增加维护面），因此问题 1 的候选范围直接受问题 2 的候选引擎生态制约，两个问题一起评估。

## 2. 约束输入

- 目标平台：Windows 单机，不考虑其它平台发行。
- 表现形态：2D 精灵固定镜头路线（对应 ADR-0012 的默认 `sprite` 路线），不需要评估三维渲染管线的成熟度作为否决项，但保留相关维度供后续可能启用 `model` 型外形时参考。
- 架构约束：核心逻辑零引擎依赖，须可用标准测试框架独立测试（见 `../11_工程规范与测试.md`）。
- 团队形态：一人开发，高度依赖 AI 代理写代码，因此"AI 辅助编码准确度"是本次新增的补充评估维度。
- 美术管线：本地出图（见 [`02_美术与工具选型.md`](02_美术与工具选型.md)），对引擎侧无特殊导入格式硬性要求。
- 时间模型：双时间模型（ADR-0013，即时与回合制同规则层）对引擎选型无特殊要求，两种模式均只依赖引擎提供固定步长回调与离散步驱动，不影响本次评估结论。

## 3. 语言候选与结论

| 候选 | 结论 | 理由 |
|---|---|---|
| C# | **入选** | 静态类型、测试框架成熟（xUnit/NUnit）、被 Unity、Godot 4 的 .NET 绑定、MonoGame 三个引擎候选原生承载，且在当前 AI 代理生成代码的准确度评估中表现最高 |
| GDScript | 不选 | 绑死 Godot 引擎，无法作为独立类库跨引擎复用；静态类型能力弱于 C#；只能在引擎无头模式下测试，脱离引擎独立测试的能力弱于 C# 方案 |
| Lua | 不选 | 无静态类型，大型项目下的重构安全性与 AI 生成代码的可验证性不足 |
| Rust | 不选 | 游戏开发生态与编辑器工具链尚不成熟，一人开发场景下工具链摩擦成本过高 |
| C++ | 不选 | 内存管理与编译工具链负担对一人开发过重，与"AI 代理高强度写代码"的团队形态不匹配 |

**结论**：核心逻辑用 C# 做成一个独立的 .NET 类库，目标框架定为 .NET Standard 2.1（以兼容 Unity 运行时），用 xUnit 或 NUnit 编写模块单测，测试时用桩适配层实现全部 L-1 接口（见 `../11_工程规范与测试.md` 测试分层）。

## 5. 结论

**核心逻辑用 C# 独立类库，第一个引擎适配层实现选定 Unity 6 LTS，走 2D 精灵路线**：

- Sprite Renderer + Transparency Sort Axis、Sorting Group 承担纸娃娃分层合成；
- Shader Graph 实现闪白、溶解等表现参数化效果；
- Particle System 承担粒子特效；
- URP 2D Renderer 作为渲染管线；
- 2D 寻路自研网格 A*（`INavigation2D` 的 Unity 实现不引入 NavMeshPlus/A* Pathfinding Project 等第三方寻路包——Unity 内置 NavMesh 面向三维导航网格，与本架构"逻辑层永远是二维平面坐标"的定位不完全贴合，直接手写二维网格 A* 更贴合接口语义；勘误 2026-09-06，此前记录的"依赖第三方包"设想未被采纳，见 `adapters/unity/Packages/com.gamefoundation.adapter.unity/Runtime/EngineAdapter/UnityNavigation2D.cs` 头注释）；
- Input System 包承担 `IInput`；
- TextMeshPro 加一款开源可商用中文字体（如思源黑体）承担 `IUISurface` 的文本渲染。

**明确否决**"3D 场景 + URP + 固定 45 度相机"路线：该路线与 ADR-0012 确立的默认路线（`sprite` 型外形、2D 地面图 + 2D 精灵为默认场景做法）相冲突，`model` 型外形与全 3D 场景在 ADR-0012 中被保留为可选路线而非默认路线，本次选型不预先押注默认之外的路线。

备选：Godot 4 .NET（同一套核心 C# 类库理论上可原样迁移，只需重新实现引擎适配层）。决定性因素是"补充：AI 辅助编码准确度"与"社区与工具链"（资源商店成熟度）两项，Unity 在这两项上领先幅度是总分差距的主要来源。

## 6. 配套技术选型

- 数据表格式：JSON，每张表一个文件。
- 跨游戏工具链语言：Python 3。
- 条件表达式语言（对应 ADR-0005"一个条件语言"）的求值器：自行实现，不引入第三方表达式引擎。
- 测试框架：xUnit 或 NUnit，配合桩适配层（`adapters/stub/`）跑模块单测与集成测试。
- 版本控制：本地 git 仓库先建立，暂不接入远程托管。

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| Unity 授权条款未来变动 | 核心逻辑不依赖 Unity 的任何符号，风险发生时可按 `../02_引擎适配层.md` 第 4 节"迁移引擎的步骤清单"迁移到 Godot 4 .NET，`core/` 与游戏层理论上不改动 |
| 域重载（domain reload）拖慢编辑器迭代速度 | 在编辑器设置里关闭进入播放模式时的域重载选项；核心逻辑的绝大多数验证在独立类库的单测里完成，不依赖频繁进入播放模式 |
| 自研网格 A* 寻路的能力/性能边界（不采用第三方寻路包后，导航能力的成熟度由自身实现兜底，见第 5 节勘误） | `INavigation2D` 接口把寻路能力隔离在引擎适配层内部，自研实现只被该适配层引用，不泄漏到 `core/` 与游戏层；若自研实现的能力边界（如超大地图网格膨胀、复杂地形）无法满足后续需要，可在契约不变的前提下改为接入第三方寻路包或替换算法实现 |
| 核心类库目标框架版本与 Unity 运行时版本对齐 | 当前固定为 .NET Standard 2.1，待 Unity 后续升级运行时版本后再评估是否跟随调整 |

## 9. 可逆性声明与重新评估触发条件

本次选型是可逆决策，不是架构级拍板：核心逻辑作为独立 .NET 类库存在本身就是为可逆性设计的（见第 5、7 节）。出现以下任一情况时，应重新走一遍第 4 节的打分流程：

- Unity 的授权条款变动到实际影响本项目的收入门槛或分发方式；
- 目标平台从"Windows 单机"扩展到需要 Unity 不擅长或 Godot/MonoGame 明显更优的平台；
- AI 代理在 Godot 4 .NET 或其它候选上的生成准确度出现显著提升，缩小或反超当前的分差；
- 项目需要大规模启用 `model` 型外形（ADR-0012 可选路线），且当前引擎在 3D 骨骼动画与换装、2D/3D 混合排序两项上的表现不足以支撑。

## 11. 发布形态验证（工程收尾 K，2026-09-06）

判断记录（为什么要做这项验证）：`core/` 的核心逻辑类库从第 5 节拍板起就选定 C#（.NET Standard
2.1），选型时已经把"AI 辅助编码准确度""headless 测试能力"等维度打了分，但发布形态一直只验证过
Unity 默认的 Mono（JIT）脚本后端；`core/foundation/common/json` 下自写的零依赖 JSON 读写器
当初的设计初衷之一就是"避免依赖反射，兼容 AOT 编译环境"，但这条设计意图在本次之前从未在真正的
AOT（IL2CPP）后端下实测过。本节记录第一次实测结果。

### 实测环境

- Unity 6000.3.23f1（Personal 授权），本机已安装 IL2CPP 模块
  （`Editor/Data/PlaybackEngines/windowsstandalonesupport/Variations/win64_player_*_il2cpp`）。
- 构建入口：`adapters/unity/Assets/Editor/Il2CppPlayerBuilder.cs`
  （`Adapter.Unity.EditorTools.Il2CppPlayerBuilder.BuildWindows64PlayerIl2cpp`），由
  `check.ps1 -Il2cpp` 驱动，见 `adapters/unity/README.md`"IL2CPP 发布路径验证"一节。

### 实测数据

| 项目 | Mono（默认独立版构建步骤，同一次门禁内，Library 缓存已预热） | IL2CPP（`-Il2cpp`，同一次门禁内，本机首次针对该脚本后端构建） |
|---|---|---|
| 构建 + `-gf-smoke` 冒烟总耗时 | 14.8s | 构建失败，见下（总耗时 614s，见下方"耗时构成"） |
| `-gf-smoke-discrete` 冒烟耗时（复用同一份产物） | 3.3s | 未生成产物，未跑（FAIL，0s） |
| 构建结果 | 成功 | **失败**：`Unity.IL2CPP.Bee.BuildLogic.ToolchainNotFoundException` |

**IL2CPP 失败的确切原因**（`build_il2cpp.log` 原文，机器可查证，非猜测）：

```
error: Could not set up a toolchain for Architecture x64. Make sure you have the right build
tools installed for il2cpp builds. Details:
IL2CPP C++ code builder is unable to build C++ code. In order to build C++ code for Windows
Desktop, you must have one of these installed:
 * Visual Studio 2022 or newer with C++ compilers and Windows SDK (version 10.0.19041.0 or newer)
 * Visual Studio 2019 with C++ compilers and Windows SDK (version 10.0.19041.0 or newer)
Unable to detect any compatible Visual Studio installation!
Windows SDK (version 10.0.19041.0 or newer) is not installed.
```

即本机装了 Unity 的 IL2CPP 模块本身（C# → C++ 转换器与运行时），但没有装 IL2CPP 编译 C++ 产物
还需要的独立原生工具链（Visual Studio 2019/2022 的 C++ 组件 + Windows 10 SDK ≥ 10.0.19041.0）
——这两者是操作系统级别的通用开发工具，不属于"Unity 模块"范畴（Unity Hub 的模块管理器不提供
它们），按任务约束"不安装任何 Unity 模块"之外的更保守判断，本次不代为安装，如实记录这一结论：
**IL2CPP 发布路径在"脚本后端切换 + 构建管线触发 + 失败诊断"这条机制链路上验证通过**（构建正确
按 IL2CPP 后端触发、失败时给出的诊断信息准确、`finally` 里的脚本后端还原按预期执行，
`ProjectSettings.asset` 没有真正被永久切到 IL2CPP，见下方"判断记录（还原的准确语义）"），但
**"核心类库在真正的 AOT 运行时下可运行"这一结论本机未能实测验证**，需要一台装有 Visual Studio
C++ 工具链的机器重跑 `check.ps1 -Il2cpp` 才能补齐。

**耗时构成**（614s 里真正的构建失败判定只发生在最后约 14s，见 `[Il2CppPlayerBuilder] result=
Failed ... totalTime=00:00:14.5309438`）：绝大部分时间花在 Unity 针对"这个脚本后端在本工程
Library 缓存里第一次出现"所做的一次性导入/脚本编译/着色器变体编译（`bee_backend.exe` 跑
`ScriptAssembliesAndTypeDB`，加上 `Hidden/Core/FallbackError`、`Hidden/Universal Render
Pipeline/FallbackError` 等着色器编译），而不是 IL2CPP 的 C++ 编译阶段本身——C++ 编译阶段甚至
没有真正开始（在"设置工具链"这一步就失败退出）。

**判断记录（还原的准确语义）**：构建过程中曾观察到 `adapters/unity/ProjectSettings/
ProjectSettings.asset` 在门禁运行期间被 Unity 从 `scriptingBackend: {}`（隐式默认值）改写为
`scriptingBackend: {Standalone: 0}`（显式声明为 Mono2x，即 `0`）——两者语义完全等价（`{}` 本来就
是"取隐式默认值 Mono2x"），不是"永久切到 IL2CPP"，但确实证伪了 `Il2CppPlayerBuilder.cs` 最初的
判断记录"不调用 `AssetDatabase.SaveAssets()` 就不会落盘"——实测 Unity 在 `-quit` 退出编辑器域时，
只要本次会话跑过至少一次 `BuildPipeline.BuildPlayer`，就会把 `PlayerSettings` 落盘一次，与是否
显式调用 `SaveAssets()` 无关。`finally` 块里的显式还原（把值改回构建前读到的原始值）因此不是
"防御性写法"而是必需步骤，该文件头注释已同步修正这一判断记录；本次实测后手工核对
`git diff adapters/unity/ProjectSettings/ProjectSettings.asset` 确认最终内容与构建前一致
（已还原）。

### 结论

- IL2CPP 独立版构建的命令行/API 路径本身正确，可用；具体到本机环境，缺 Visual Studio C++
  工具链，构建在到达 C++ 编译阶段之前就以清晰诊断失败——这是环境缺口，不是本次改动引入的代码
  或流程缺陷。
- `check.ps1 -Il2cpp` 保持默认关闭（可选门槛，见 `../11_工程规范与测试.md` 第 8 节新增的勘误
  条目），不阻塞日常提交门槛；具备 Visual Studio C++ 工具链的机器可随时补跑一次完整验证。
- 本次验证之外新增的风险登记：`core/` 声称的"AOT 友好"设计意图，在拿到一台具备完整 IL2CPP
  工具链的机器之前，仍停留在"设计目标"而非"已验证事实"这一状态，建议列入下一次真正启用发布
  形态构建时的前置检查项。
