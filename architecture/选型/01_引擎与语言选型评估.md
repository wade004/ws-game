# 引擎与语言选型评估 v1

> 目的：按 [`../02_引擎适配层.md`](../02_引擎适配层.md) 第 3 节评估框架，给出本项目当前采用的核心逻辑语言与第一个引擎适配层实现的具体选型结论与打分依据。
> 日期：2026-09-04
> 状态：已拍板（2026-09-04 用户确认）
> 上游文档：[`../02_引擎适配层.md`](../02_引擎适配层.md)

## 1. 问题拆分

选型拆成两个独立问题，按顺序回答：

1. **核心逻辑语言**——`core/` 全部纯逻辑模块用什么语言实现。
2. **第一个引擎适配层实现**——`adapters/` 下第一套正式（非桩）实现选哪个引擎。

约束：核心逻辑语言必须被选定的引擎原生承载（不引入跨语言绑定层增加维护面），因此问题 1 的候选范围直接受问题 2 的候选引擎生态制约，两个问题一起评估。

## 2. 约束输入

- 目标平台：Windows 单机，不考虑其它平台发行。
- 表现形态：2D 精灵固定镜头路线（对应 ADR-0012 的默认 `sprite` 路线），不需要评估三维渲染管线的成熟度作为否决项，但保留相关维度供后续可能启用 `model` 型外形时参考。
- 架构约束：核心逻辑零引擎依赖，须可用标准测试框架独立测试（见 `../11_工程规范与测试.md`）。
- 团队形态：一人开发，高度依赖 AI 代理写代码，因此"AI 辅助编码准确度"是本次新增的补充评估维度。
- 美术管线：本地出图（见 [`02_美术与工具选型.md`](02_美术与工具选型.md)），对引擎侧无特殊导入格式硬性要求。
- 时间模型：双时间模型（ADR-0013，即时与回合制同规则层）对引擎选型无特殊要求，两种模式均只依赖引擎提供固定步长回调与离散步驱动，不影响本次评估结论。

## 3. 语言候选与结论

| 候选 | 结论 | 理由 |
|---|---|---|
| C# | **入选** | 静态类型、测试框架成熟（xUnit/NUnit）、被 Unity、Godot 4 的 .NET 绑定、MonoGame 三个引擎候选原生承载，且在当前 AI 代理生成代码的准确度评估中表现最高 |
| GDScript | 不选 | 绑死 Godot 引擎，无法作为独立类库跨引擎复用；静态类型能力弱于 C#；只能在引擎无头模式下测试，脱离引擎独立测试的能力弱于 C# 方案 |
| Lua | 不选 | 无静态类型，大型项目下的重构安全性与 AI 生成代码的可验证性不足 |
| Rust | 不选 | 游戏开发生态与编辑器工具链尚不成熟，一人开发场景下工具链摩擦成本过高 |
| C++ | 不选 | 内存管理与编译工具链负担对一人开发过重，与"AI 代理高强度写代码"的团队形态不匹配 |

**结论**：核心逻辑用 C# 做成一个独立的 .NET 类库，目标框架定为 .NET Standard 2.1（以兼容 Unity 运行时），用 xUnit 或 NUnit 编写模块单测，测试时用桩适配层实现全部 L-1 接口（见 `../11_工程规范与测试.md` 测试分层）。

## 4. 引擎打分表

评估维度取自 [`../02_引擎适配层.md`](../02_引擎适配层.md) 第 3.1 节的 15 个维度，并新增两个补充维度（AI 辅助编码准确度、启动与迭代速度）；权重为本次评估依据项目优先级自行填定的具体取值（1～3，权重越大越优先），得分为 1～5 分制：

| 维度 | 权重 | Unity 6 LTS | Godot 4（.NET） | Godot 4（GDScript） | MonoGame |
|---|---|---|---|---|---|
| 2D/2.5D 渲染能力 | 3 | 5 | 5 | 5 | 3 |
| Y 排序与分层 | 3 | 5（Transparency Sort Axis + Sorting Group） | 5（y_sort_enabled + z_index） | 5 | 2 |
| 粒子与着色器 | 2 | 5（Particle System + Shader Graph） | 4 | 4 | 2 |
| 导航能力 | 2 | 3（内置偏 3D，2D 需第三方包） | 4（NavigationServer2D） | 4 | 1 |
| UI 能力 | 2 | 4（UGUI / UI Toolkit） | 4（Control） | 4 | 1 |
| 脚本语言与静态类型 | 3 | 5 | 5 | 3 | 5 |
| headless 测试能力 | 3 | 5 | 5 | 3 | 5 |
| Windows 导出 | 2 | 5 | 4 | 5 | 4 |
| 许可证与成本 | 2 | 3（闭源；个人版收入门槛内免费；条款曾变动） | 5（MIT） | 5 | 5 |
| 社区与工具链 | 2 | 5（资源商店最丰富） | 3 | 4 | 2 |
| 美术管线兼容 | 2 | 5 | 5 | 5 | 4 |
| 3D 骨骼动画与换装（可选路线） | 1 | 5 | 3 | 3 | 1 |

## 5. 结论

**核心逻辑用 C# 独立类库，第一个引擎适配层实现选定 Unity 6 LTS，走 2D 精灵路线**：

- Sprite Renderer + Transparency Sort Axis、Sorting Group 承担纸娃娃分层合成；
- Shader Graph 实现闪白、溶解等表现参数化效果；
- Particle System 承担粒子特效；
- URP 2D Renderer 作为渲染管线；
- 2D 寻路依赖第三方包（如 NavMeshPlus 或 A* Pathfinding Project）承担 `INavigation2D`；
- Input System 包承担 `IInput`；
- TextMeshPro 加一款开源可商用中文字体（如思源黑体）承担 `IUISurface` 的文本渲染。

**明确否决**"3D 场景 + URP + 固定 45 度相机"路线：该路线与 ADR-0012 确立的默认路线（`sprite` 型外形、2D 地面图 + 2D 精灵为默认场景做法）相冲突，`model` 型外形与全 3D 场景在 ADR-0012 中被保留为可选路线而非默认路线，本次选型不预先押注默认之外的路线。

备选：Godot 4 .NET（同一套核心 C# 类库理论上可原样迁移，只需重新实现引擎适配层）。决定性因素是"补充：AI 辅助编码准确度"与"社区与工具链"（资源商店成熟度）两项，Unity 在这两项上领先幅度是总分差距的主要来源。

## 6. 配套技术选型

- 数据表格式：JSON，每张表一个文件。
- 跨游戏工具链语言：Python 3。
- 条件表达式语言（对应 ADR-0005"一个条件语言"）的求值器：自行实现，不引入第三方表达式引擎。
- 测试框架：xUnit 或 NUnit，配合桩适配层（`adapters/stub/`）跑模块单测与集成测试。
- 版本控制：本地 git 仓库先建立，暂不接入远程托管。

## 7. 仓库落地映射

对应 `../11_工程规范与测试.md` 第 1 节的目录约定，具体落地为：

```
core/                       一个 .NET 解决方案下按层拆分的类库项目：
  Core.Foundation             对应 core/foundation/
  Core.Numbers                对应 core/numbers/
  Core.Rules                  对应 core/rules/
  Core.Carriers                对应 core/carriers/
  Core.Gameplay                对应 core/gameplay/
  Presentation.Common          对应 presentation/ 引擎无关部分
adapters/
  unity/                     Unity 工程，通过 asmdef 引用核心库的编译产物
                             （DLL 放 Assets/Plugins，或以 UPM 本地包形式引入）
  stub/                      纯 .NET 桩实现，供 xUnit/NUnit 测试与 CI 使用
其余目录（games/、data/、assets/、toolchain/、build/）与 ../11_工程规范与测试.md 第 1 节一致
```

## 8. 风险与缓解

| 风险 | 缓解 |
|---|---|
| Unity 授权条款未来变动 | 核心逻辑不依赖 Unity 的任何符号，风险发生时可按 `../02_引擎适配层.md` 第 4 节"迁移引擎的步骤清单"迁移到 Godot 4 .NET，`core/` 与游戏层理论上不改动 |
| 域重载（domain reload）拖慢编辑器迭代速度 | 在编辑器设置里关闭进入播放模式时的域重载选项；核心逻辑的绝大多数验证在独立类库的单测里完成，不依赖频繁进入播放模式 |
| 2D 寻路能力依赖第三方包 | `INavigation2D` 接口把寻路能力隔离在引擎适配层内部，第三方包只被适配层实现引用，不泄漏到 `core/` 与游戏层 |
| 核心类库目标框架版本与 Unity 运行时版本对齐 | 当前固定为 .NET Standard 2.1，待 Unity 后续升级运行时版本后再评估是否跟随调整 |

## 9. 可逆性声明与重新评估触发条件

本次选型是可逆决策，不是架构级拍板：核心逻辑作为独立 .NET 类库存在本身就是为可逆性设计的（见第 5、7 节）。出现以下任一情况时，应重新走一遍第 4 节的打分流程：

- Unity 的授权条款变动到实际影响本项目的收入门槛或分发方式；
- 目标平台从"Windows 单机"扩展到需要 Unity 不擅长或 Godot/MonoGame 明显更优的平台；
- AI 代理在 Godot 4 .NET 或其它候选上的生成准确度出现显著提升，缩小或反超当前的分差；
- 项目需要大规模启用 `model` 型外形（ADR-0012 可选路线），且当前引擎在 3D 骨骼动画与换装、2D/3D 混合排序两项上的表现不足以支撑。

1. 给定第 4 节打分表与权重，任何人按同一套分值都能复算出与第 4 节一致的加权总分与排序。
2. 第 5 节结论与第 4 节打分表排序结果一致，且明确否决了与 ADR-0012 默认路线冲突的候选路线。
3. 第 8 节风险清单中的每一条都能在 `../02_引擎适配层.md` 或 `../11_工程规范与测试.md` 中找到对应的架构级保障机制（如迁移引擎步骤清单、引擎适配层隔离原则）。
4. 第 9 节的重新评估触发条件具体、可判断，不是模糊的"如有需要"。
