## 1. 仓库与目录约定

本架构不规定具体引擎/语言，但约定顶层目录职责划分，供每次新游戏立项（见 [13_新游戏接入指南.md](13_新游戏接入指南.md)）统一放置：

```
architecture/          本文档集：设计层拍板的架构规范，不随具体游戏变化
core/                  L0~L4 纯逻辑模块的实现，零引擎依赖，按层分目录
  foundation/<module>/   L0，每个模块一个目录，见第 2 节模块范式
  numbers/<module>/      L1
  rules/<module>/        L2
  carriers/<module>/     L3
  gameplay/<module>/     L4
presentation/<module>/ L5，引擎无关部分（FeedbackBinder 规则引擎、View 绑定、UI 数据绑定、SpriteRig 逻辑、通用 UI 套件的引擎无关部分）
adapters/
  <engine_name>/        每种引擎一套引擎适配层（L-1）实现
  stub/                 桩适配层实现，专供测试与 CI 使用，不对外发布
games/
  _template/            新游戏模板：复制改名后即为具体游戏的游戏层代码骨架（组装配置、策略配置）+ 最小数据集（`data/game/`，见下）
  <game_name>/           具体游戏复制模板改名后的游戏层代码、组装配置、策略配置（本框架仓库不含任何具体游戏，实际接入见各游戏自己的仓库）
data/
  _framework/            框架级数据表（表的行被框架代码引用/生成，见 `data/README.md`"两类目录"一节），随分发包 `dist/<version>/data/_framework/` 一起发给游戏
  _sample/               示例数据，仅供本框架仓库自身冒烟测试与校验器自测使用，不代表任何真实游戏内容
  <game_name>/           具体游戏的数据表（放各自游戏仓库自己的 `data/<game_name>/` 下，与 `data/_framework/` 并列加载，见 04 第 4 节"多根加载与合并规则"；本框架仓库不含，`games/_template/data/game/` 只是模板复制起点，不是本框架仓库自己的游戏数据）
assets/
  <game_name>/           具体游戏的表现资源（精灵、特效、音效等原始素材，本框架仓库不含）
  _placeholder/          含 assets/_placeholder/ 通用占位资产包（色块角色、方块怪、简易特效、占位音效、开源可商用字体），任何新游戏第一天可用
toolchain/              校验工具、构建脚本等跨游戏复用的工程工具；含资产导入工具（出图产物→资产目录→外形表行→校验，见 `toolchain/import_assets.py`）、事件常量/占位资产生成器（`--check` 模式供门禁校验）、数据校验器（`validate_data.py` + `validator/`）与其自身测试（`toolchain/tests`）
dist/                   构建产物输出目录（按版本号分子目录，如 `dist/<version>/`），不入版本库正文（仅记录构建产物版本约定，见第 7 节、根目录门禁脚本）
```

- `core/` 下的模块不得出现任何 `adapters/` 或 `games/` 的引用，依赖方向只能反过来。
- `data/` 与 `assets/` 按游戏隔离，允许存在跨游戏共享的公共数据/资源子目录，但共享内容需要走内容管线的引用完整性校验（见 [04_数据与内容管线.md](04_数据与内容管线.md)）。

（建议）具体目录名的大小写与分隔符风格（下划线/短横线）建议在新游戏立项时随选定的引擎/工具链约定一次并写入该游戏的接入记录，本文档只固定层级含义，不固定大小写风格。

## 2. 模块范式

L0~L4 每个模块遵循统一的内部目录结构，保证"可以脱离引擎独立测试""可以整体拆走复用"两条架构目标（见 00）落到工程实践；模块的完整路径是 `core/<层>/<module>/`（L5 表现层模块为 `presentation/<module>/`，见第 1 节）：

```
core/<层>/<module>/    （L5 为 presentation/<module>/）
  README.md      模块职责、依赖哪些层/哪些契约、不负责什么
  contracts/     对外暴露的接口签名（本模块提供给别人调用的契约）
  core/          纯逻辑实现，不依赖任何引擎符号
  schema/        本模块拥有的数据表字段说明（与 04 的全表清单对应的分片文档）
  tests/         模块单测，脱离引擎运行
```

- **纯逻辑、零引擎依赖**：`core/` 内的代码不得引入任何 L-1 引擎适配层的具体实现符号，只允许依赖 `contracts/` 里声明的接口类型（例如 `SkillHost` 这类宿主契约，其运行时实现由更上层注入，模块本身不知道注入的是谁）。
- **不跨模块直接引用**：模块 A 需要模块 B 的能力时，只能经 B 的 `contracts/` 或经事件总线，不允许直接 import/引用 B 的 `core/` 内部实现细节；这保证任一模块可以被替换实现而不牵连其他模块。
- **只经契约与事件**：跨层、跨模块的所有交互方式收敛为两种——同步的契约调用（问答式，如"查询当前位置"）与异步的事件通知（广播式，如"某单位死亡了"），不存在第三种私有旁路。

## 2.1 框架级美术与 UI 交付物

以下三样是框架级交付物，随核心逻辑一起排进落地计划，不属于某一款游戏各自完成的工作（决策依据见 [ADR-0014](adr/0014-资产契约导入工具与UI套件是框架交付物.md)）：

- **资产规格书**：框架级模板，内容覆盖每类资产的尺寸、锚点约定、方向数与镜像、纸娃娃层清单与叠放顺序、序列帧图集切法、特效贴图格式、图标尺寸与构图规则、音效格式与响度、命名规则；归属 `architecture/` 文档集本身（随文档版本规则版本化，见 [12_扩展与变更流程.md](12_扩展与变更流程.md) 第 4 节），每款游戏在其上填具体值落到该游戏的接入记录；由设计层维护模板、游戏层维护具体取值。
- **资产导入工具**：把出图产物做抠图、切片、图集、锚点写入，落到第 1 节约定的 `assets/<game>/` 目录，自动生成外形表行，并校验缺锚点、尺寸不符、引用不存在的文件；引擎无关部分归属 `toolchain/`，与具体引擎资源格式相关的部分归属对应 `adapters/<engine_name>/`；由跨游戏的工具维护者维护，具体游戏只按约定调用。
- **通用 UI 套件与占位资产包**：UI 套件的数据绑定与界面单元定义归属 `presentation/<module>/`（引擎无关），带默认朴素皮肤的界面实现归属 `adapters/<engine_name>/`；占位资产包归属 `assets/_placeholder/`；三者均由框架维护者维护，任何新游戏立项第一天即可用它们跑通框架级验收，无需等待真实美术资源。

## 3. 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 逻辑 id（数据行 id） | `<domain>.<name>`，全小写，点分（拍板决策 4） | `skill.fireball`、`item.iron_sword`、`quest.find_the_missing_child` |
| 类型/接口名 | 语义清晰的名词/名词短语，跨文档保持与本架构已用词一致（如 `SkillHost`、`StatBlock`），不同义重复造词 | `SkillHost`、`WorldState` |
| 事件 key | `<system>.<verb_past_or_state>`，风格沿用魔兽 Combat Log（见拍板决策 7） | `combat.damage_dealt`、`aura.applied`、`quest.completed` |
| 常量/枚举值 | 全小写，下划线分隔，语义自解释 | `flat`、`pct`、`mult`（StatMod 运算类型） |
| 文件与目录（架构文档层面） | 已在第 5 节文档目录固定，具体游戏内目录风格由该游戏统一约定并记录 | 见第 1 节 |

- 同一逻辑概念在全部文档中必须使用同一术语（见 [00_架构总则.md](00_架构总则.md) 名词表），禁止在不同文档里对同一事物使用不同命名。

## 4. 错误处理与断言

| 场景 | 处理方式 |
|---|---|
| 数据引用不存在（如技能引用了不存在的效果 id） | DataRegistry 加载期校验拦截，不允许进入运行时（见 04 校验器），运行时不做静默降级 |
| 运行时契约调用参数非法（如查询越界坐标） | 契约实现方返回明确的 `Optional`/错误结果，调用方必须处理该分支，不允许调用方假设"总是成功" |
| 不可恢复的内部一致性错误（如同一 tick 内世界状态出现相互矛盾的标志） | 触发断言中止当前 tick 的调试构建行为；发布构建降级为记录诊断日志并尝试保留上一个一致状态，不允许整进程崩溃影响玩家存档完整性 |
| 表现层异常 | 表现层异常不得影响 WorldSim 的 tick 推进（呼应 09 表现层铁律），只影响画面呈现 |

（建议）断言与日志的具体输出通道由引擎适配层的平台服务接口提供，本文档只约定"发布构建里断言失败不能崩溃到丢存档"这条底线。

## 5. 性能约定

| 约定 | 说明 |
|---|---|
| 对象池 | 高频创建销毁的对象（弹道、特效实例、伤害数字浮字、临时查询结果集合）一律走对象池，不逐帧新建销毁（呼应 09 VFX/SFX 对象池、[06_规则层_属性技能战斗AI.md](06_规则层_属性技能战斗AI.md) 的效果结算） |
| 避免每帧分配 | 固定步长 tick 内的高频路径（属性聚合、目标查询、条件求值）避免每 tick 产生大量临时分配，优先复用缓冲区/结果结构 |
| 事件批处理 | 同一 tick 内产生的同类事件（如群体技能命中多个目标）允许在事件总线层面批量投递，订阅方按批处理，减少订阅回调的调用开销 |
| 空间查询性能约定 | 目标查询/范围查询（`findUnits` 一类契约）由引擎适配层的空间查询接口提供加速结构，逻辑层不自行实现暴力遍历以外的优化，也不假设查询是 O(1) 的，写法上避免不必要的重复查询 |

## 6. 测试分层

| 层级 | 覆盖内容 | 运行方式 |
|---|---|---|
| 模块单测（脱离引擎） | `core/<层>/<模块>/tests`，验证纯逻辑正确性 | 不启动任何引擎，用桩实现契约接口（如桩 `SkillHost`）直接调用 `core/` 逻辑 |
| 集成测试 | 多个模块经真实契约与事件总线组合后的行为 | 用桩适配层（实现 L-1 接口但不做真实渲染/音频/输入的最小实现）驱动 WorldSim 跑若干 tick，断言事件流与状态 |
| 数据校验 | 全部数据表的引用完整性、schema 版本、字段约束 | DataRegistry 启动时的校验器全量跑一遍所有数据（见 04），作为独立可执行的校验步骤 |
| 性能基线 | 关键路径（一次 tick 的耗时、大规模目标查询耗时）的基准测试 | 固定场景/固定单位规模下采样耗时，与历史基线比较，超出阈值即失败 |
| 回放回归 | 用固定输入录像 + 固定种子重放，比对战斗日志事件流与既往基线是否一致 | 复用 [10_存档与持久化.md](10_存档与持久化.md) 的 ReplayPlayer，属于确定性保证的回归验证手段 |
| 资产校验 | 锚点、尺寸、引用完整性 | 资产导入工具的校验步骤（见第 2.1 节），与数据校验同级，作为提交门槛之一 |

- 模块单测与集成测试都不依赖真实引擎运行，这是"每个模块可脱离引擎独立测试"（架构目标 4）的直接落地方式。
- 桩适配层（Stub Adapter）作为 `adapters/stub/` 长期维护，专供测试与 CI 使用，不对外发布。
- 契约一致性测试套件对桩与各引擎实现共用：同一份场景源码（按引擎适配层每个接口的语义/性能约定逐条编写，与具体测试框架无关）分别驱动桩适配层与每个真实引擎实现各跑一遍，验证"这份具体实现是否满足契约"，而不只是各自实现内部逻辑自洽；某条场景在具体实现上确因平台限制无法确定性验证时，场景可声明跳过并记录原因，不得放宽断言本身。

## 6.1 消费方演练（见第 8 节提交门槛清单）

新游戏接入本架构后，需要一份独立于框架源码树、只以分发产物为输入的端到端演练，验证"一个从未接触过框架源码的新工程，照着接入文档操作能否真正跑起来"——从零搭建最小消费方工程、只引用分发包、走完包解析、编译、集成测试、独立构建产物这条完整链路，作为工作台内部测试（可以直接引用框架源码）之外的独立交叉验证。该演练是第 8 节提交门槛清单"提交门槛"之一的自动化形式，具体产物由各团队自行实现，不规定具体工具形态。

## 7. 构建产物与版本号约定

| 约定 | 说明 |
|---|---|
| 构建产物版本号 | 与存档 `save_version`（见 10）分离，构建产物版本号标识"这一份运行时代码+数据"的整体版本，用于问题追踪与灰度发布 |
| 数据 schema 版本 | 每张数据表独立的 `schema_version`（见 04），与构建产物版本号不是一一对应关系，一次构建产物里可以包含多张不同 schema 版本历史遗留的数据（迁移后统一） |
| 产物内容 | 构建产物 = 引擎适配层实现 + foundation 模块 + 具体游戏层代码 + 数据 + 资源的一次打包快照，具体打包方式由引擎/工具链决定，本架构只约定"版本号必须可追溯到对应的架构文档版本与数据 schema 版本组合" |

## 8. 提交门槛清单

任何改动在合入前必须满足（以仓库根门禁脚本一键跑通以下各项为准，逐项人工核对仅作为门禁脚本暂不可用时的兜底）：

- [ ] 数据校验器全量通过（引用完整性、schema 版本、必填字段）
- [ ] 受影响模块的单测通过
- [ ] 若改动涉及事件 key、契约签名、数据表结构等"新增原语"范畴（见拍板决策 10），已完成对应审批流程（见 [12_扩展与变更流程.md](12_扩展与变更流程.md)）
- [ ] 若改动可能影响确定性（新增非确定性调用、绕开分流随机源等），已跑回放回归确认战斗日志事件流未产生非预期偏差
- [ ] 表现层改动未引入对逻辑数据的写回（人工核对铁律 P1~P4，见 09）
- [ ] 新增资产已经过导入工具并通过资产校验，外形表行由工具生成而非手填
- [ ] 文档同步：若改动使某份架构文档描述与实现不一致，已按 [12_扩展与变更流程.md](12_扩展与变更流程.md) 的"文档与实现不一致处理规则"处理

## 基础架构提供 / 游戏层提供

| 能力 | 基础架构提供 | 游戏层提供 |
|---|---|---|
| 目录约定与模块范式 | 是 | 具体游戏内代码的组织细节遵循该范式 |
| 命名规范 | 是 | 具体 id/事件 key 的取名需遵循规范 |
| 错误处理原则 | 是 | 具体错误提示文案与恢复流程 |
| 性能约定原则 | 是 | 具体性能预算数值（如目标帧率、单位数量上限）按游戏体量确定 |
| 测试分层方法论与桩适配层机制 | 是 | 具体测试用例、具体性能基线数值 |
| 提交门槛清单 | 是 | 具体门槛的执行工具（校验工具、构建脚本等）实现 |

## 验收标准

1. 给任意一个 `core/` 下的模块，能不启动引擎、只用桩契约实现，跑通其单测。
2. 给定一次修改，能对照第 8 节清单逐项判断是否满足提交门槛，无歧义项。
3. 新成员仅阅读本文档与 [00_架构总则.md](00_架构总则.md)，能正确判断一段新代码应该放进 `core/`、`presentation/`、`adapters/` 还是 `games/`。
4. 一次刻意引入的数据引用错误（如技能引用不存在的效果 id）能被数据校验步骤拦截，不进入运行时。
