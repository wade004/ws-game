# ADR-0058 技能宿主契约纳入光环查询与效果落地出口

状态：已拍板 2026-09-21

## 背景

消费方反馈（第三批第 3 条，2026-09-21）：技能宿主契约（`ISkillHost`）缺 `AuraQuery`/`EffectSink`
两个只读入口。技能宿主组合根的生产实现已经以公开属性的形式暴露这两个能力（均已是接口类型）：

```
public IEffectSink EffectSink => _effectDispatcher;
public IAuraQuery AuraQuery => _auraHost;
```

`IAuraQuery`/`IEffectSink` 两个接口本身早已存在、且被框架自身多处消费（如组合根构造函数装配
战斗宿主、光环句柄账本等）。但技能宿主契约接口没有声明这两个成员——只持有契约接口引用的调用方
拿不到这两个已经接口化的只读查询/写入口，必须向下转型或直接持有具体实现类型。

消费方场景：一个"被动技能与其常驻光环"之间做只读核对（`HasAura`/`TryGetInstanceRef`）与施加/
移除（`ApplyAura`/`RemoveAura`）的会话对象，此前必须以具体实现类型为构造函数参数类型才能拿到
`AuraQuery`/`EffectSink`，导致另一个转发同一实例的会话对象也被迫继续依赖具体类型——消费方曾
尝试把后者改造为只依赖契约接口（`Knows`/`LearnFromBook` 已经可以，见 ADR-0050），但这一步因为
拿不到 `AuraQuery`/`EffectSink` 而回退。

这与 ADR-0050《技能宿主契约纳入技能簿查询与学习成员》是同一类缺口的延续：契约接口的成员集合
落后于具体实现类实际已经提供的公开能力，本次收口的是其中的光环查询/效果落地这两个出口。

## 决策

1. **把 `AuraQuery`/`EffectSink` 两个只读属性补进技能宿主契约接口**，签名与具体实现类既有的
   同名公开属性逐字一致，类型分别为 `IAuraQuery?`/`IEffectSink?`（可空——见决策 2）。ABI 只能
   新增：用**带默认实现的接口成员**（同 ADR-0050 决策 1 同一惯例）新增这两个成员，不要求任何
   既有实现类型连带改动即可继续编译通过。

2. **默认实现统一降级为 `null`，不套用 ADR-0050"只读查询/写路径两分"里写路径那一档口径**：
   - 这两个成员本身都是**属性 getter**——只回答"能不能拿到这个出口引用"，getter 本身不产生
     任何副作用、不推进任何状态、不修改任何账本，是纯只读查询，允许一个明确的保守默认值
     （同 `Knows`/`GetKnownSkills`/`GetSkillNameKey` 既有的"查询类默认实现允许显式降级"惯例）。
   - `IEffectSink` 自身确实持有写方法（`ApplyEffect`/`ApplyAura`/`RemoveAura`），但那是
     `IEffectSink` 接口自身的职责边界，不是 `ISkillHost.EffectSink` 这个属性 getter 的职责——
     getter 只负责"给不给你这根引用"，调用方拿到非 `null` 引用之后发起的写操作，语义由
     `IEffectSink` 实现自身承担，与本决策无关。因此不属于 ADR-0050 决策 2 里"写路径默认实现
     不能悄悄假成功、必须抛异常"要防的那类陷阱——那条规则针对的是"调用即产生状态变化的方法"
     本身默认降级成静默 no-op；本决策的两个成员默认降级成 `null` 之后，调用方要么在判空处直接
     感知到"这个宿主不支持"（编译期强制处理 `null`，运行期不会有任何假动作被静默执行），要么
     根本不会尝试对 `null` 引用发起写操作（对 `null` 调用方法会抛 `NullReferenceException`，
     不存在"看起来成功、实际上什么也没发生"的中间态）。
   - 组合/包装出的契约实现（若持有并转发内层真实实现）必须显式转发这两个新成员，不能依赖默认
     实现的隐式兜底——同 ADR-0050 决策 2 第三点，纳入既有 `InterfaceDefaultMemberForwardingTests`
     门禁的检测范围；技能宿主组合装配（`core/rules/assembly.RulesAssembly`）内部的延迟绑定代理
     同样补上显式转发。

3. **既有实现类的两个同名公开属性原地保留、物理签名逐字节不变，改用显式接口实现转发**，与
   ADR-0050 决策 3 完全同一理由：若让这两个既有公开属性直接隐式满足新增的契约成员，编译器会把
   它们的物理二进制属性从"普通实例属性访问器"改写成"虚方法+密封"，被本仓库按物理签名比对的
   ABI 探针判定为两处破坏性变更，即便实际运行完全兼容也不例外（已用 `toolchain/abi_probe.ps1`
   的旧编译 consumer 换新 DLL 不重新编译实测验证正常，`breaks=0`）。改用显式接口实现后，原属性
   的二进制表现与本次改动之前逐字节相同，新增的转发属性本身在二进制里是不参与"公开表面"统计的
   形态，探针不再误报。

## 后果

### 正面

- 消费方今后可以只持有技能宿主契约接口引用，完成"取光环查询出口 → 只读核对光环 → 取效果落地
  出口 → 施加/移除光环"这条链路，不再需要下沉到具体实现类型；此前因这一缺口而回退的接口化改造
  （消费方另一个转发同一技能宿主实例的会话对象）具备了继续推进的前提条件。
- 与 `IAuraQuery`/`IEffectSink` 本身已经是稳定契约接口的既有事实一致——本次只是把"取得这两个
  接口引用的入口"也纳入 `ISkillHost` 契约，不新增任何新概念。
- 默认接口成员是纯新增，不要求任何现存实现类型（含各模块测试替身）连带修改即可继续编译通过。

### 负面

- 默认降级为 `null` 意味着调用方对任意 `ISkillHost` 引用调用 `.AuraQuery`/`.EffectSink` 后必须
  自行判空，不能假设总能拿到非空引用——这是刻意的（与 ADR-0050 的"查询类默认实现允许显式降级"
  惯例一致），但确实要求调用方对"这个具体宿主实现是否提供这两个出口"有基本认知。

## 与 ADR-0050 的关系

本次是 ADR-0050 建立的同一套模式（契约成员落后于具体实现类既有公开能力 → 用带默认实现的接口
成员补齐 → 既有同名公开成员改显式接口实现转发，不动物理签名）在另外两个成员上的直接复用，不
另起一套：

- 默认降级档位不同：ADR-0050 的四个成员按"只读查询/写路径"两分（写路径抛异常）；本次两个成员
  都归入"只读查询"一档（默认返回 `null`），理由见决策 2——它们是属性 getter，不是会产生状态
  变化的方法。
- 显式接口实现的理由完全相同（决策 3 与 ADR-0050 决策 3 逐句对应）。
- 组合/包装实现必须显式转发的门禁要求完全相同，纳入同一套 `InterfaceDefaultMemberForwardingTests`
  门禁与 `core/rules/assembly.RulesAssembly` 内部代理的显式转发惯例。

## 备选方案与为什么不选

- **写路径口径统一，`EffectSink` 默认实现也抛异常而不是返回 `null`**：与 ADR-0050 的
  `LearnSkill`/`LearnFromBook` 用同一套"写路径不允许静默降级"逻辑，表面上看起来更严格一致。
  但 `EffectSink` 属性本身不是写路径——它是"给不给引用"的只读问题，抛异常反而会阻止调用方
  用一个简单的判空分支优雅处理"这个宿主不支持"的情形（改成必须 try/catch），且与
  `AuraQuery`/`GetSkillNameKey` 等同样返回引用/值类型的其它只读查询成员的降级口径不一致，
  故不选。
- **不使用带默认实现的接口成员，而是把这两个出口单独抽成一个新的窄接口**：与 ADR-0050 备选
  方案第三点同一理由被否决——不解决"这两个能力理应属于同一个技能宿主契约"的根本问题，且契约
  本身已经两次验证"用默认接口成员新增能力、不破坏 ABI"是可行路线，不再叠加新接口。
