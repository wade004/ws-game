# ADR-0063 装备宿主契约补模板 id 查询

状态：已拍板 2026-09-21

## 背景

消费方反馈（游戏接入方第五批第 2 条，基于冻结发布提交核实）：装备面板要显示"槽位名 + 已装备物品
名"，需要已装备物品的模板 id——但载体层装备契约 `IEquipmentHost` 的 `Equip`/`Unequip`/
`GetEquipped`/`GetAllEquipped` 四个既有成员全部只返回一个不透明的物品实例引用（只携带实例 id，
见该引用类型顶部判断记录"不暴露物品实例内部状态"），拿不到模板 id。路径层 `player.equipment.
<slot>`（供表现层用路径小语法拉取运行期数据）同样只解析出裸实例 id。消费方因此只能向下转型到具体
实现类 `Core.Carriers.Item.EquipmentHost`，调用一个不在契约上的公开方法
`GetAllEquippedInstances`，才能拿到模板 id——面向接口编程做不到，与背包侧已经具备的对称能力
（`player.inventory[i].template`，契约层 `IInventoryHost.ListItems` 本就返回携带模板 id 的完整
物品条目）不一致。

独立核实：`Core.Carriers.Item.EquipmentHost` 确实以公开方法形式提供了 `GetAllEquippedInstances`
（返回槽位 id → 完整 `ItemInstance`，含模板 id），但这是内部实现细节层的补充方法（供
`EquipmentPersistable.Save` 序列化用），从未提升到 `IEquipmentHost` 契约接口。这是框架内部独立
观察到的同一个缺口，不只是消费方单方面反馈。

## 决策

1. **`IEquipmentHost` 新增两个只读成员**：`GetEquippedTemplateId(unitId, slot)`（某单位某槽位
   已装备物品的模板 id，语义与 `GetEquipped` 的"槽位未装备返回 null"完全对应）、
   `GetAllEquippedIdentities(unitId)`（该单位当前全部已装备槽位到"实例 id + 模板 id"的映射，形态
   对应既有 `GetAllEquipped`，供纸娃娃/装备面板一次性同步全部槽位而不必逐槽调用前者）。新增元素
   类型 `EquippedItemIdentity`（`readonly struct`，携带 `InstanceId`/`TemplateId` 两个字段）——不
   复用既有 `EquippedWeaponSummary`（该类型只有模板/品质/词缀三个身份字段、没有实例 id，回答的是
   "这个槽位挂的是什么"而不是"是哪一件具体实例"，定位不同，见该类型对照判断记录）。ABI 只能
   新增：用"带默认实现的接口成员"（既有契约同类扩展先例，见 ADR-0050《技能宿主契约纳入技能簿
   查询与学习成员》、ADR-0058《技能宿主契约纳入光环查询与效果落地出口》）新增这两个成员，不要求
   任何既有实现类型连带改动即可继续编译通过。`ItemInstanceRef` 与既有四个方法签名一字不动。

2. **默认实现按"只读查询"口径，恒返回保守默认值（`null`/空字典）**：与 `Core.Rules.Common.
   ISkillHost` 既有的 `Knows`/`GetSkillNameKey`/`AuraQuery` 等只读查询默认成员同一惯例——这类
   查询允许一个明确、保守的降级默认值，语义是"该宿主实现不提供这项查询"，不属于"运行时写路径不
   允许静默降级"这条硬性约束管辖的范围（该约束只管"会产生副作用、被误当作成功"的写路径，`Equip`/
   `Unequip` 两个既有写方法不受影响）。组合/包装出的 `IEquipmentHost` 实现（若存在）必须显式转发
   这两个新成员，不能依赖默认实现的隐式兜底——本仓库框架内 `InterfaceDefaultMemberForwardingTests`
   门禁专门检测这类"新增默认成员被组合层悄悄吃掉"的遗漏，本次新增的两个成员同样纳入该门禁的检测
   范围。

3. **生产实现 `Core.Carriers.Item.EquipmentHost` 用显式接口实现落地这两个新成员**，取数据源与既有
   `GetAllEquippedInstances`（未改动）同一份内部账本。不新增同名公开方法、改用显式接口实现，理由
   同 ADR-0050 决策 3——若让一个新的同名公开方法直接满足契约成员，不产生 ABI 破坏（这两个成员本身
   是全新签名，没有已发布的同名公开方法需要保护物理签名），但本次仍统一走显式接口实现，是为了与
   同一类型上其它按 `ISkillHost` 惯例落地的默认接口成员（如 `GetWeaponAttackIntervalSeconds`/
   `GetWeaponSchool`，见 ADR-0059）保持同一套"新增契约成员一律显式接口实现"的类型内部约定，减少
   未来审阅者需要记住"哪些成员是隐式、哪些是显式"的心智负担。

4. **路径层新增 `player.equipment.<slot>.template`/`.instance` 子路径**，比照既有
   `player.inventory[i].template|count|instance`；既有裸路径 `player.equipment.<slot>`（返回实例
   id）保持原行为不变。判断记录（末段保留关键字，不新增下标语法）：装备槽 id 允许多段
   （namespaced，如 `equip.main_hand`），与 `inventory[i].<field>` 的按下标定位不同，沿用
   `player.quest.<questId>.state|objective[i]`/`player.skill.<id>.cooldown` 两条既有子路径同一
   惯例——末段不带下标、字面量恰为 `template`/`instance` 时按子路径解析，其余段拼装槽位 id；其余
   情况落到既有裸查询分支，行为逐字节不变。**不新增 `.count`**：装备类物品 `stack_size == 1`
   （见 07 校验），恒为 1 没有信息量。**不新增 `.name_key`/`.quality`**：这类字段需要另查
   `item.template`/词缀表才能取到，背包侧 `inventory[i].*` 同样不给（名字由游戏拿模板 id 自己查
   表）——两侧口径保持一致，是本次刻意的取舍，不是遗漏（见"备选方案"一节）。空槽/卸下后子路径
   结果为"无"，与背包空格既有口径（`inventory[5].template` 为 `null`）一致。

5. **视图模型**：`presentation/ui` 已有的装备相关视图模型 `InventoryViewModel` 新增只读属性
   `EquippedSlotIdentities`（槽位 id → `EquippedItemIdentity`），比照 `Slots`
   （`InventorySlotSnapshot` 携带模板 id）与既有 `EquippedSlots`（槽位 id → 裸实例 id）。判断记录
   （新增属性而不是改写 `EquippedSlots` 的元素类型）：`EquippedSlots` 是已发布的公开只读属性，
   改写其元素类型会破坏既有调用方编译，ABI 只允许新增，故新增一个并行属性、不动前者；仍需要裸
   实例 id（如比对/去重）的既有消费方继续读 `EquippedSlots`，互不影响。

## 后果

### 正面

- 消费方今后可以只持有 `IEquipmentHost` 接口引用，取得"槽位 → 已装备物品模板 id"，完成装备面板
  "槽位名 + 物品名"这一诉求，不再需要向下转型到具体实现类型调用非契约方法。
- 路径层、视图模型与背包侧的既有取值口径（模板 id 给、品质/名称不给）保持对称，游戏层不需要为
  装备与背包两套数据分别记两套"能拿到什么、拿不到什么"的心智模型。
- 默认接口成员是纯新增，不要求任何现存实现类型（含各模块测试替身）连带修改即可继续编译通过；
  ABI 探针核实 breaks=0。

### 负面

- `player.equipment.<slot>.template`/`.instance` 与 `player.quest`/`player.skill` 共享同一个
  "末段保留关键字"的解析惯例，理论上存在装备槽 id 恰好以字面量 `template`/`instance` 结尾时被
  误判为子路径的边界情况——与既有 quest/skill 两条子路径同一已接受的既有惯例，游戏内容侧只要不用
  这两个字面量给装备槽命名（本就是不常见的命名选择）即不受影响。
- 品质/词缀仍拿不到（刻意口径，见"备选方案"）：消费方若未来需要装备面板显示品质染色/词缀提示，
  需要另一轮反馈单独评估，本次不预先铺路。

## 备选方案与为什么不选

- **路径层/视图模型一并给出品质/词缀**（复用既有 `EquippedWeaponSummary` 三元组）：技术上可行——
  `EquipmentHost` 已经有 `GetEquippedWeaponSummary`/`GetAllEquippedWeaponSummaries` 现成实现。但
  消费方反馈只点名"模板 id"（装备面板"槽位名 + 物品名"本身也只需要模板 id），背包侧
  `inventory[i].*` 同样不给品质/名称；一并给出会让装备侧的查询口径比背包侧更"富"，两条本该对称
  的路径出现不必要的不对称，且没有消费方需求支撑这个额外面。故只给模板 id，需要品质/词缀时按
  真实反馈再评估。
- **直接把 `EquippedWeaponSummary`/`GetEquippedWeaponSummary`/`GetAllEquippedWeaponSummaries`
  提升到 `IEquipmentHost` 契约**（三者均已在具体类上存在，形态与本次新增高度相似）：没有选择这条
  更省事的路径，是因为 `EquippedWeaponSummary` 不携带实例 id——它回答"这个槽位挂的是什么"，不
  回答"是哪一件具体实例"；消费方反馈与装备面板场景都需要"实例 + 模板"二元组（用于与
  `GetAllEquipped` 返回的 `ItemInstanceRef` 对账、或按实例 id 做进一步查询），直接复用会让调用方
  拿到一个缺失实例 id 的结果，需要再单独查一次 `GetEquipped`/`GetAllEquipped` 才能拼齐，体验比
  新增一个专用的"实例+模板"类型更差。`EquippedWeaponSummary` 三个成员本身不受本决策影响，继续
  留在具体类型上，未来若有独立需求可以单独提交契约提升。
- **不新增专用类型 `EquippedItemIdentity`，直接用 `(Id InstanceId, Id TemplateId)` 值元组**：
  减少一个新类型定义，但本仓库既有先例（`ItemInstanceRef`/`EquippedWeaponSummary`）均用具名
  `readonly struct` 表达"物品身份的一个只读快照"，命名字段比元组的 `Item1`/`Item2` 或匿名字段名
  更利于调用方阅读，故沿用既有惯例新增一个具名类型。
- **路径层用下标语法（如 `player.equipment[i].template`）而不是保留关键字末段**：装备槽位天然
  按 id（而不是数组下标）寻址——不存在"第 i 个已装备槽位"这个概念，游戏层需要按具体槽位 id 查询
  （"头盔槽装备了什么"而不是"第 3 个已装备槽位是什么"），下标语法与既有 `player.equipment.<slot>`
  裸路径的寻址方式不一致，故延续 quest/skill 两条子路径已经验证过的"末段保留关键字"惯例，不引入
  第三种路径寻址风格。
