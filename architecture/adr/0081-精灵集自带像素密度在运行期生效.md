# ADR-0081 精灵集自带像素密度在运行期生效

状态：已拍板 2026-09-23

## 背景

消费方反馈第二十三批（`<game>` 接入方，基于 v1.64.0 冻结发布提交核实，改进建议非阻塞）指出：精灵集
自带的 `anchors.json` 里有顶层 `pixels_per_unit` 字段，由 `toolchain/asset_import/sprite_cmd.py`
（占位资产生成器 `toolchain/gen_placeholder_assets.py` 同一字段名）写出，但运行期从未被解析——全仓
源码检索 `anchors.json` 命中 0 处解析代码。已落地的引擎适配层实现里，构造图像类资源（`Image`/
`Effect` 两个种类）时的"像素-单位换算比"实参一律取该实现内部唯一的全局属性（默认 100）。后果：一张
512 画布的精灵永远渲染成 5.12 世界单位高，消费方只能在美术侧把内容在画布内预缩小（牺牲有效分辨率）。

落地期核实结论（任务书要求的"第 0 步核实"，如实记录，不代为掩盖）：`anchors.json` 目前在仓库内实际
有两种并存 schema，均属当前有效、被维护的产物，不是一份已废弃的历史遗留：

- **`toolchain/asset_import/sprite_cmd.py`（消费方实际使用的资产导入工具，落地 `assets/_sample` 等
  真实数据集）产出的 schema** 是"按方向档位分层"：`{"<方向档位>": {"canvas_size": [w, h], "anchors":
  {...}}}`，**顶层不含 `pixels_per_unit` 字段**（`toolchain/asset_import/check_cmd.py` 的对应校验
  逻辑同样不检查任何顶层 `pixels_per_unit`）。
- **`toolchain/gen_placeholder_assets.py`（框架级占位资产生成器，产出 `assets/_placeholder`）产出的
  schema** 是"整集单一顶层"：`{"canvas": {"width", "height"}, "pixels_per_unit": ..., "directions":
  {"<方向档位>": {...锚点...}}, ...}`——顶层确有 `pixels_per_unit`，但 `canvas` 也是顶层单一值（整个
  精灵集一个画布尺寸），不是消费方反馈原文所说的"每方向 `canvas`"。

即：消费方反馈原文描述的字段组合（顶层 `pixels_per_unit` + 每方向 `canvas`）是两种 schema 的语义
混合，任何一种单独的现行 schema 都不完全吻合；且真正被消费方接入流程使用的 `sprite_cmd.py`/
`check_cmd.py`（`_sample` 数据集）产出的 `anchors.json` **目前完全没有 `pixels_per_unit` 字段**。
这一事实与设计层原始决策 1 的措辞（"已声明且 > 0 就用它……缺失……一律回退"）并不冲突——决策 1 本就
预留了"缺失时回退"的分支，只是需要如实记录：按本 ADR 落地后，**只有 `_placeholder` 精灵集（及未来
任何按 `_placeholder` schema 手工/工具补上该字段的精灵集）能立即受益，`_sample`/消费方现有数据集在
`sprite_cmd.py` 同步产出该字段之前不会有任何行为变化（安全回退到全局默认值）**。是否要让
`sprite_cmd.py`/`check_cmd.py` 也为"按方向分层" schema 补一个顶层 `pixels_per_unit`
字段——不在本次任务书授权范围（任务书明确"运行期照它解码"，未提及改动 toolchain 生成/校验
脚本），留给设计层后续裁决，见本文"后果"一节"待设计层确认"。

## 决策

1. **像素密度由资产自己声明，运行期照它解码**：已落地引擎适配层实现解码某个精灵集下的图像资源
   （`ResourceKind.Image`）时，先按该图像资源的资源引用 id 判断它是否属于某个精灵集，是则读该精灵集
   自己的 `anchors.json` 顶层 `pixels_per_unit`；已声明且 `> 0` 就用它作为该图像的像素-单位换算比；
   缺失、非正数、`anchors.json` 文件不存在、JSON 解析失败或顶层不是对象——一律回退到该实现既有的
   全局像素-单位换算比属性（默认 100），**回退路径的行为与改动前逐字节一致，既有资产不受任何
   影响**。
2. **哪些图像资源属于"某个精灵集下的图像"（任务书要求自行判断并写明）**：
   - `"layer."` 类别（身体纸娃娃层与 [ADR-0071](0071-装备纸娃娃层随朝向换图.md) 装备覆盖层，
     两者共用同一套 `sprites/<精灵集名>/<方向>/<层名>.png` 三级目录，见该实现资源路径解析入口
     "U2-1 判断记录"）：精灵集目录段即该资源 id 去掉类别前缀后双下划线分隔三段的第一段。
   - `"sprite."` 类别本身（`sprite_set_id` 直接当 `Image` 资源 id 使用的既有简化，见该实现资源路径
     解析入口"ADR-0038 适配层接线"一节"非 layer/paperdoll 类别的通用回退分支此后只覆盖 sprite 类别
     本身"）：资源 id 本身就是 `sprite_set_id`，经 `AssetRefConventions.SpriteSetDirectory` 直接算出
     目录。
   - **不属于任何精灵集的图像资源，直接回退全局默认值，不做 `anchors.json` 查找**：`"paperdoll."`
     类别（[ADR-0038](0038-资源引用类别前缀唯一决定路径空间.md) 决策 4，扁平单文件，不落在任何
     `sprites/<name>/` 目录下，没有伴生的 `anchors.json`）；`"icon."` 类别（图标，落在独立的
     `icons/<category>/<name>.png`，与精灵集无关）；其余未登记类别同理。
3. **不新增 `display.map` 尺度字段**：消费方给的第二个方向（在 `display.map` 上加一个逐条目尺度
   字段）不采纳，见本文"备选方案"一节。
4. **驳回全局像素-单位换算比属性既有注释里的"不读项目专属配置，避免 L-1 反向依赖游戏内容"顾虑**：
   本次读取的是精灵集自己随身携带的伴生文件（`anchors.json`），不是项目配置、不是任何内容数据表——
   适配层本来就在读该资产目录下的图片，与读取同目录下的 `frames.json`/`atlas.json` 同一性质，不
   构成 L-1"适配层反向依赖游戏内容"。该属性的字段注释已同步更新，不留与实现矛盾的旧表述。
5. **本次只接 `pixels_per_unit`，不接 `canvas`**：`canvas`/`canvas_size` 服务的是锚点像素坐标的
   画布基准，跟像素密度是两件事，接它需要另行拍板锚点坐标换算口径，留待锚点系统细化时另议。
6. **特效图集（`ResourceKind.Effect`）本轮不动**：`frames.json` 没有 `pixels_per_unit` 字段，vfx/
   `sprite_anim` 图集没有"精灵集"这个归属层级（两者的资产根相对目录与精灵集目录是两套独立空间，
   见 `AssetRefConventions`），不在本次范围。
7. **按精灵集目录缓存解析结果，含"未声明"这一结论**：已落地引擎适配层实现新增一份按精灵集相对目录
   索引的实例级缓存，避免同一精灵集下解码多张图反复读盘；生命周期与该实现既有的资源缓存同一套
   口径——随加载器实例存活。该实现当前没有独立的"整体清缓存/重载"入口，按单个资源 id 卸载的既有
   方法与本缓存"按精灵集目录"的粒度不是同一维度，且同一精灵集的 `anchors.json` 内容不会因某个资源
   被卸载而改变，因此不需要跟随单资源卸载联动清理。

## 后果

### 正面

- 精灵集自带的像素密度声明第一次在运行期真正生效，`_placeholder` 精灵集（`placeholder_hero` 等，
  `anchors.json` 顶层已声明 `pixels_per_unit`）立即受益，无需任何数据/工具改动。
- 回退路径与改动前逐字节一致，`_sample` 等现有数据集（`anchors.json` 尚无该字段）行为完全不变，
  零风险。
- 按精灵集目录缓存，多帧/多层同集图像解码不重复读盘。

### 负面

- **`_sample`/消费方现有数据集不会立即受益**：`sprite_cmd.py`/`check_cmd.py` 产出与校验的
  `anchors.json`（"按方向档位分层" schema）目前没有顶层 `pixels_per_unit` 字段，本次任务书范围
  只做运行期解析，未改动 toolchain 生成/校验脚本，消费方若要让自己的精灵集受益，需要手工在
  `anchors.json` 顶层补一个 `pixels_per_unit` 数字字段（与本 ADR 决策 1 的解析规则完全兼容，不需要
  额外代码支持）。
- 两种 `anchors.json` schema 并存（`_placeholder` 顶层单一 `canvas`+`pixels_per_unit`，`_sample`
  按方向分层无 `pixels_per_unit`）这一事实本身不是本次改动引入的新问题，但本次改动让它第一次产生
  可观测的行为差异（`_placeholder` 精灵集能覆盖全局默认值，`_sample` 精灵集不能）。

### 待设计层确认

- 是否要求 `toolchain/asset_import/sprite_cmd.py` 也在其"按方向档位分层"schema 的 `anchors.json`
  顶层写出 `pixels_per_unit`（`--pixels-per-unit` 命令行参数已存在，当前只用于换算 `display.map`
  的 `anchor_points`，未写回 `anchors.json` 本身），并相应扩展 `check_cmd.py` 校验——不在本次任务
  书授权范围，留给设计层裁决是否值得单开一个后续任务。

## 备选方案与为什么不选

- **在 `display.map` 上加一个逐条目尺度字段**：`pixels_per_unit` 描述的是"这张图是按什么密度画
  的"，是资产自身属性；`display.map` 描述的是"这个逻辑对象长什么样"。两处都能表达大小 = 同一件事
  有两种写法，将来必然打架（例如同一精灵集被两个不同 `display.map` 行引用、各自声明不同尺度时，
  "这张图到底多大"就有了两个互相矛盾的答案来源）。故不选，密度只由资产自己的 `anchors.json`
  声明一次，`display.map` 不重复表达。
- **顺带统一两种 `anchors.json` schema（把 `_placeholder` 改成"按方向分层"或把 `_sample` 补成
  "顶层单一"）**：任务书范围明确是"运行期照它解码"，不涉及 toolchain 生成/校验脚本改动；且两种
  schema 统一本身是比"接入一个字段"更大的决策（涉及 `check_cmd.py` 校验规则、`sprite_cmd.py`/
  `gen_placeholder_assets.py` 两个生成器、已落地的 `_sample`/`_placeholder`/消费方数据），不应该
  在一次"改进建议、非阻塞"的任务里顺手做掉。故不选，如实记录现状（见"待设计层确认"），运行期解析
  按两种 schema 各自的实际字段位置分别兼容（对"按方向分层"schema 而言，顶层天然没有
  `pixels_per_unit`，落进"未声明"分支安全回退，不需要额外代码区分两种 schema）。
