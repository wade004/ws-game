# ADR-0156 发布第五步复用全量记录改跑定向门禁、提交钩子合并跳过、下限登记文件单独判级

状态：已拍板 2026-10-05

## 背景

1.99.0 发布实测约 3 小时，其中三段是同一份信息的重复验证：

- 合并前在集成工作树跑过一次含引擎侧的全量门禁（54 分钟，`REGRESSION_LOG.md` 登记为 `full-20261001-42`）；发布脚本第 5 步又在主检出把同一份全量
  原样重跑一遍（再 54 分钟，各项用例数逐项相同）。而第 3b 步的发布守卫此前已经证明"该全量记录之后只改了文档类文件"。
- 只改 `toolchain/gate_floors.json` 的提交，提交钩子跑了约 20 分钟：影响集判定把它记为 T1，但选中的步骤是整个工具链用例套件（约 1600 例）。
  这个文件唯一的消费者只有 `toolchain/tests/test_gate_floors_logic.py` 一个用例文件。
- 把"合并前已全量通过的分支"合并进主干的合并提交，提交钩子又跑了约 20 分钟的快速全量：暂存清单是该分支带来的全部改动，判为 T3；
  而被提交的树与已测过的树逐字节相同。

## 决策

1. **发布第 5 步默认复用已验证的全量记录，改跑定向门禁。** 第 3b 步守卫放行（含引擎侧的全量通过记录就是当前提交，或是其祖先且其后只改文档类文件）、且工作树
   除第 4 步写回的版本文件之外没有任何改动时，第 5 步跑 `check.ps1 -Changed <记录提交> -AbiStrict -FailFast -NoTiming`，宿主与此前相同（Windows 自带的
   脚本宿主 5.1）。判定范围是记录提交以来的全部改动（文档类改动 + 版本号写回），按模块表选步骤。守卫不放行、工作树有别的改动、`-DryRun`、或显式传
   `-FullRegate` 时仍跑全量，行为与此前一致。日志写明复用的是哪条记录（run_id + 提交）与定向门禁的结论行；结论行同时写进门禁通过记录（`-Resume` 的凭据）。
   选择逻辑集中在 `toolchain/_release_regression_guard.ps1` 的 `Get-ReleaseGatePlan`，`build.ps1` 与测试共用。
2. **模块表新增路径规则 `release_version_files`**：`VERSION`、适配层与游戏模板两个 `package.json`、`packages-lock.json` 记 T1，只跑受版本号影响的步骤——
   包清单一致性（打包 + 打包产物检查）、DLL 同步、引擎侧编译、消费方演练、`.meta` 自检；不跑核心类库全量测试、公开面兼容探针、数值仿真基线。此前这四个文件
   "未被任何规则覆盖"，保守判 T3，会让上一条的定向门禁退化成全量。
3. **模块表新增路径规则 `gate_floors_only` 与步骤 `floors_pytest`**：只改 `toolchain/gate_floors.json` 时只跑 `test_gate_floors_logic.py`（校验登记文件
   四个套件齐全、取值符合"实测 90% 向下取整"规则、门禁测试步骤确实接了下限检查）加秒级基础步骤（含文档类检查）；步骤可登记 `triggers_except`，
   使 `toolchain_pytest` 的 `toolchain/**` 触发不再覆盖该文件。与 `toolchain/tests/**` 或其它工具链路径同批改动时，全量用例套件照旧会跑。
4. **提交钩子新增 `MergeSkip` 档**：合并提交（恰有一个第二父提交）且即将提交的树与第二父提交的树逐字节相同、该第二父提交在 `REGRESSION_LOG.md` 有含引擎侧的
   全量记录背书（判定复用发布守卫，目标提交换成第二父提交）时，钩子不再重复跑快速全量。树不同（主线上有第二父提交没有包含的独立改动，或手工改过合并结果）、
   没有记录、章鱼合并、判定出错一律照常跑（宁可多跑，不静默放行）。

## 权衡（明确接受的风险）

- 发布第 5 步不再对"记录之后的树"做全量。放行的前提是：记录提交之后只有文档类改动 + 版本号写回，前者由守卫的路径白名单证明、后者由 `release_version_files`
  规则与定向门禁覆盖；工作树里任何别的改动都会退回全量。残余风险是"版本号写回波及了模块表没登记的步骤"——显式 `-FullRegate` 保留为兜底，且合并后的
  全量与合并前的全量仍按 `AGENTS.md` §1b 照常要求，不受影响。
- `release_version_files` 同时放宽了这四个文件在日常提交里的判级（原 T3）。适配层 `package.json` 的依赖改动因此只跑包清单、DLL 同步、引擎侧编译、消费方演练，
  不再触发核心类库全量测试；这些文件改的是包清单而非代码，且合并前后全量仍会覆盖。
- `-DryRun` 仍跑全量：它不写回版本文件，定向门禁将看不到发布特有的改动，而演练的目的正是验证整条流水线。
- `MergeSkip` 依赖"树相同"这一可机械核对的事实，不依赖提交说明；它只省掉钩子里的重复把关，合并后的全量门禁不受影响。

## 后果

- `build.ps1` 新增开关 `-FullRegate`（仅与 `-Release` 同传，不与 `-Resume` 同传）；`.githooks/pre-commit` 认 `MergeSkip`；
  `toolchain/precommit_tier.ps1` 在 `Full` 档上补判合并跳过。
- `toolchain/change_impact.py` 支持步骤字段 `triggers_except`；`toolchain/module_map.json` 增加上述两条路径规则、一个步骤与一条触发排除。
- 用例：`toolchain/tests/test_release_targeted_gate.py`（第 5 步选择逻辑、端到端接线、合并跳过、下限步骤静态接线）与 `test_change_impact.py` 新增的判级用例。
- `AGENTS.md` §5 与 `toolchain/README.md`"发布"一节记录第 5 步的新行为。
