# ADR-0019 复合字段子结构登记为机器可读 schema（含按 kind 分派的变体）

状态：已拍板 2026-09-09

## 背景

`04_数据与内容管线.md` 第 4 节的 `DataRegistry` 与实现级 `TableSchema`/`FieldSchema`（`core/foundation/data_registry/contracts/`）把每张表的字段登记为 `FieldKind` 之一：`Bool`/`Int`/`Number`/`String`/`Id`/`IdList`/`Reference`/`TextKey`/`Expr`/`Enum`/`Vec2`/`Object`/`Array`。其中 `Object`/`Array` 两种被定义为"结构未知、由上层模块自行解释的 JSON 对象/数组，本模块只做存在且是对象/数组检查"，登记上只有一句自由文本描述，例如 `skill.def.effects` 登记为 `[{kind: String, params: Object}, ...]`，19 种效果原语各自的参数结构只存在于运行时解析代码（`core/rules/skill/core/ParamsX.cs` 等）与 06 号文档的表格里。

现状不够用的地方：

1. 内容最核心的结构恰恰都是复合字段：技能效果列表与每种原语的参数、光环效果列表、触发器、施法修正的 `affects`、掉落分组与条目、任务目标与奖励、对话节点与动作、遭遇单位/波次/阶段、刷新条目、区域触发参数、外形表的 `mirror_pairs`/`anchor_points`/`clips`。任何 Schema 驱动的工具（内容编辑器、文档生成器、表结构差异工具）在这些字段上都无法自动生成表单或做结构校验，只能退化为自由 JSON 编辑。
2. 校验规则对复合字段的结构检查散落在各模块的 `IValidationRule` 与运行时解析代码里，同一结构的"登记描述"与"实际解析"是两套口径，文档（06/07/08）与代码之间的一致性只能靠人工审计维持（历次深度审核已多次发现此类漂移）。
3. "新增内容不改代码"的承诺在复合字段上是打折的：内容作者要知道某种效果原语接受哪些参数、哪些必填、取值范围，只能翻文档或读代码。

## 决策

1. **`FieldSchema` 增加可选的子结构描述**，对 `Object`/`Array` 两种 `FieldKind` 生效；不新增 `FieldKind` 枚举值，既有登记不填子结构时行为不变（向后兼容，属 MINOR 变更）：
   - `Object` 字段可登记 `fields: List<FieldSchema>`（递归，子字段同样可以是 `Object`/`Array`）。
   - `Array` 字段可登记 `item: FieldSchema`（元素结构；元素本身可以是标量、`Reference`、`Object` 等任一 `FieldKind`）。
   - 需要按某个判别字段分派结构的复合字段（效果原语的 `params`、光环效果、锁的 `requirement`、区域触发的 `params`、位移效果的子类型等）登记为**变体**：`variants: {discriminator: String, cases: Map<String, List<FieldSchema>>}`，判别字段的合法取值集合即变体表的键集合，等价于对该判别字段的枚举校验。
2. **登记与校验同源**：`DataRegistry` 的字段级校验按子结构递归检查必填/类型/枚举/引用/Expr 可解析；已登记子结构的复合字段，其结构检查以登记为唯一权威，各模块既有的手写结构校验规则逐步改为只保留"登记表达不了的业务判断"（如预算超标、叠加类别冲突、循环引用）。运行时解析代码可以继续用现有方式读参数，但新增参数必须先登记再使用。
3. **原语注册表与子结构登记合一**：新增一种效果原语/光环效果/物件类型等（ADR-0010 的受控开口）时，在 `12_扩展与变更流程.md` 第 2 节"再改注册表"这一步同时登记其变体子结构，作为该步骤的必做项；校验器新增检查项"变体表键集合与运行时注册的原语集合一致"。
4. **描述字段保留**：`FieldSchema.Description` 继续作为面向人的说明；子结构登记后，04 号文档第 4 节 `DataRegistry` 接口签名不变，只在第 3 节"记录主键约定"之后补一节说明子结构的记法与校验语义。
5. **首批登记范围**（按对编辑器价值排序，分批落地）：`skill.def.effects`（19 种原语变体）、`skill.aura_def.effects`（10 种变体）、`skill.proc_def`/`skill.spell_mod_def` 的复合字段、`loot.table.groups`、`quest.def` 的目标与奖励、`dialog.*` 节点与动作、`encounter.def` 单位/波次/阶段、`spawn.table` 条目、`area.trigger_def.params`、`gobj.lock.requirement`、`display.map`/`display.anim_set` 的复合字段。

## 后果

### 正面
- Schema 驱动的工具（编辑器、文档生成、差异比对）可以对全部内容结构自动生成表单与做结构校验，专项编辑器的卡片式表单有了唯一的数据来源。
- 复合字段的结构在登记、校验、文档三处只有一份来源，减少历次审计反复发现的"文档与实现漂移"。
- 新增原语的审批流程多了一个机器可核对的落点：变体表与运行时注册集合是否一致由校验器保证。

### 负面
- 首批登记范围涉及 L2～L5 多个模块，是一项跨模块的一次性工作量，且要与既有手写校验规则逐条对账，避免登记与旧规则重复报错或口径不一。
- `FieldSchema` 变复杂后，登记本身也可能出错；需要为子结构登记补一层"登记自洽"测试（判别字段存在、变体键不重复、递归深度有限）。
- 运行时解析代码若与登记不一致，短期内会出现"登记说必填、代码有默认值"一类差异，需要在对账时逐条决定以哪边为准并记录判断。

## 备选方案与为什么不选

- **保持现状，编辑器对复合字段只提供 JSON 子编辑，专项编辑器在编辑器项目里各自硬编码参数表单**：编辑器会成为第二份"结构真相"，框架每新增或调整一个原语参数，编辑器都要手工跟改，正是本架构一贯反对的两套口径。
- **用外部的通用 schema 格式描述子结构**（另起一份与 `FieldSchema` 并行的结构文件）：与既有 `TableSchema` 登记机制形成两套来源，校验器还要再实现一套解析；不如在既有 `FieldSchema` 上扩展。
- **只给编辑器暴露运行时解析代码的反射信息**：把实现细节当契约，违反"框架对编辑器只承诺契约"（ADR-0018），且反射信息表达不了必填/枚举/引用语义。

## 魔兽世界的对应做法

魔兽世界的 `spell` 表用固定列（`Effect1..3`、`EffectBasePoints`、`EffectMiscValue` 等）表达效果参数，每种效果类型对各列的解释由客户端与服务端代码约定，工具与文档（如社区维护的 spell effect 说明）各自维护一份解释——正是本决策要避免的"结构真相分散在代码与外部文档"的状态。本架构选择把每种效果类型的参数结构登记进表定义本身，对应关系是"同一份效果类型注册表既驱动运行时解析也驱动工具与校验"。

## 修订记录

- 2026-09-10（第十四轮审核 P3-02 澄清，不改变本 ADR 正文任何决策）：决策 3"变体表键集合与运行时注册的原语集合一致"这一校验项，实际载体是各模块自己的 coverage tests（如 `core/rules/skill/tests/SkillSchemaCoverageTests.cs`、`core/carriers/gobj/tests/GobjSchemaCoverageTests.cs`），比较的是 `FieldSchema` 变体登记表与该模块运行时实际注册的原语/kind 集合是否一致，属于该模块自动化测试套件的覆盖范围。`presentation/assembly/SchemaAudit.cs`（`check.ps1`"元数据门禁：validator --schema-audit"步骤，ADR-0018 决策 3）是另一件不重叠的事——只审计已登记 `TableSchema`/`FieldSchema` 结构声明本身是否自洽（空键、`common`/`discriminator` 冲突、递归结构等），不加载任何数据，也不比较任何运行时注册表。此前"元数据门禁"一类文案在个别位置容易把两者读成同一个机制；本条只澄清叫法边界，两套机制各自的实现与职责范围均不变。
