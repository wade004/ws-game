# ADR-0040 运行期宿主的命令行能力契约

状态：已拍板 2026-09-19

## 背景

该需求由消费方反馈触发（2026-09-19 一批反馈中的两条），核实后确认两处对外命令行能力面存在
真实缺口，不是反馈失实：

1. **无法进入并保持可交互运行状态**：现有全部批处理入口（构建全部场景、独立版冒烟等）均为
   "跑完即退出"语义——启动、跑一段固定流程、退出，进程生命周期不由外部控制。没有一个入口是
   "进入运行期宿主后保持存活、停留在可交互状态，供外部持续观察/操作，直到外部主动结束它"。
   标准批处理运行模式本身也不预设这种"常驻"概念，需要专门的入口设计。
2. **无通用的内容数据同步工具**：现有两个内容同步入口各自绑定在自己的既定流程上：
   - 一个入口服务于"按包依赖解析到本地的框架自带内容 → 该内容包既定的目标子目录"，源不是
     任意目录，而是包解析结果；目标路径也是围绕该包自身用途固定拼接出来的。
   - 另一个入口服务于"框架仓库自己的几类内容（框架自带数据、样例数据、模板自带最小数据集、
     占位资产）→ 框架自己的开发自测工作台工程"，一次调用同步好几组源/目标固定路径对，且带有
     针对框架自身工作台的专属规则（如某一路径排除某类派生文件、离开该路径立即失败自检）。

   两者都不接受"任意源内容目录 → 任意目标运行期工程"这样一对通用参数，导致任何框架自身发布
   流程与私服通道之外的场景（例如某个游戏想把自己独有的内容数据同步进自己独立维护的运行期
   工程），都没有官方入口可用，只能自行重新实现一遍同步逻辑。

**总原则先行拍板**：框架对外提供的应当是**通用、参数化、面向任意外部工具**的命令行能力，
不是面向某一个具体消费方定制的联调协议。理由：
- 仓库既定边界是"内容编辑器随游戏走、不进框架"（[ADR-0018](0018-编辑器随游戏走与框架为此提供的交付物.md)）。
  若把上述两项能力做成面向某个消费方的专属协议，框架里就会出现消费方专属概念，直接踩这条边界。
- 做成通用、参数化的命令行入口后，持续集成脚本、内容作者自己的工具、任何第三方工具都能使用，
  框架层面不需要感知、也不需要区分调用者是谁。
- 这与 [ADR-0025](0025-资源引用标识到资产相对路径的约定纳入公开契约.md)/
  [ADR-0037](0037-资源引用路径推导契约扩展到vfx-sfx-model-anim_set.md) 收口"各消费点各自
  实现→统一公开契约"的模式是同一类问题：与其为发现问题的那一个使用方单独定制，不如把能力本身
  收口成公开契约。

## 决策

1. **总原则**：框架对外暴露的运行期与内容工具类命令行能力，一律设计为通用、参数化、可被任意
   外部工具调用的入口；不为任何具体消费方定制专属协议。这类入口的参数面与输出格式（含退出码
   约定）本身即是公开契约，纳入与框架其余公开契约同等的稳定性管理（变更需评估是否构成破坏性
   变更，参照 [ADR-0039](0039-内容数据schema破坏性变更政策.md) 的分级思路）。

2. **新增长驻可交互运行入口**：

   - **与既有"跑完即退"入口的关系**：并列新增，不取代。"跑完即退"语义本身对自动化门禁场景
     仍是必要的（门禁需要确定性退出码，不能让进程无限期占用）；新入口是运行期宿主的另一种启动
     模式，与既有入口共享同一套运行期装配与内容加载路径，只是对外暴露不同的生命周期承诺。
   - **退出方式**：新入口承诺存在至少一种非强杀的受控退出路径——外部可以通过某种约定信号
     （具体载体留给落地期确定，例如响应标准中断信号，或监听一个约定的外部请求）通知其结束，
     入口收到后可控释放资源并以约定退出码结束，而不是只能被外部进程管理器强行杀死。
   - **内容数据指定**：新入口与既有构建/冒烟入口一样，接受一个"要加载的内容数据根"参数；该
     参数与决策 3 新增同步入口的目标参数面对齐，便于外部工具组合使用（先同步内容、再以该内容
     启动长驻运行）。
   - **成功/失败如何被外部判定**：
     - 新入口需要有一个外部可观察的**就绪信号**，宣告"已进入可交互状态，可以开始外部操作/观察"；
       就绪信号出现之前，外部不应假定其已进入可交互状态。
     - 启动失败（含内容加载失败等阻断态）复用既有批处理入口已有的退出码分级约定（成功为一个
       固定值，失败为非该值），不新造一套独立的退出码语义。
   - **范围声明**：本决策只约束"存在这样一个入口，且这个入口对外承诺就绪信号与受控退出路径"这
     一契约面；就绪信号的具体载体、受控退出的具体信号形式、是否需要额外的健康检查接口等实现
     细节，留给落地期设计与实现。若落地期发现本决策所列某一项契约（如"非强杀退出"）在批处理
     运行期环境下确实做不到，须回到本 ADR 补一版说明或另出 ADR 调整契约，不得在实现中悄悄降级
     后不留记录。

3. **新增参数化内容同步入口**：

   - **参数面**：至少包含——源内容目录（必填，任意路径，不限定于框架自带内容）、目标运行期
     工程（必填，任意路径，不限定于框架自身工作台或某个既定包的目标子目录）、覆盖策略（至少
     区分"以源为准清理目标多余文件"与"只新增/更新、保留目标独有文件"两态）、干跑（只报告将要
     发生的改动，不实际写入）。参数命名与具体标记形式留给落地期，只有参数面的存在性与语义是
     本次拍板内容。
   - **与既有两个同步入口的关系（并列，不取代、不包装）**：核实两个既有入口的实际职责后确认，
     二者都不是"通用同步能力套了一层固定参数"的特例，而是各自承载着与本次通用能力无关的专属
     语义——一个绑定在按包依赖解析出的内容与该包既定用途的目标子目录上，源头不是任意目录；
     另一个一次调用同步好几组框架仓库自身专属的源/目标路径对，并夹带只对框架自身工作台成立的
     专属规则（某类派生文件的处理方式、离开预期状态即失败退出的自检）。两者的现有行为已被各自
     既定流程与已有验证手段依赖：
     - 直接取代任意一个都会破坏向后兼容，且两个入口解决的问题（私服包内容落地、框架自身工作台
       自测同步）在通用入口之外依然需要专门存在，不能被"任意源→任意目标"这一更泛化的抽象
       完全替代（它们各自还承担着与自身场景绑定的专属规则，不是单纯的路径参数差异）。
     - 把通用能力实现成套在其中一个既有入口外面的包装，会让通用入口的参数面继承该入口内部的
       隐藏假设（例如固定的目标子路径拼接规则、专属的多目录树分组语义），违反决策 1"通用、
       参数化、不为具体消费方或具体既定流程定制"的要求。
     - 因此新增第三个、独立的通用入口，与既有两者并列存在，各自服务各自的既定流程；该新入口
       未来是否在内部实现上复用与既有入口相同的底层复制原语（如增量对比、避免重复写入未变更
       文件），是纯粹的实现期内部选择，不影响本决策的对外契约结论，也不要求本 ADR 落地时同步
       改造既有两个入口。
   - **幂等性承诺**：以相同参数重复运行该入口，在源内容本身不变的前提下，不应对目标产生有
     意义的差异（视为幂等）。已知例外：若源内容来自某条已知会引入序列化副作用的产出流水线
     （如重复运行会把整数字面量重写为浮点字面量），该副作用属于该产出流水线自身的缺陷，已
     独立立项跟踪修复，不计入本入口的幂等性承诺范围——本入口只承诺"同步动作本身幂等"，不
     承诺"上游内容产出过程本身幂等"。

4. **不在本 ADR 范围**：本轮反馈中另外四条不需要新的契约面，按各自性质处理，不纳入本 ADR：
   - 分发物是否包含验收用样例数据集：能力已存在（独立的样例数据分发通道），缺口是消费方
     文档指引不足，按补充文档处理。
   - 开发期数据热重载只监视部署副本：底层扩展点已具备，缺口是模板层未把该扩展点接线暴露为
     环境变量/命令行开关，按普通接线改动处理，此前已有 ADR 定过方向。
   - 校验问题结构化文本格式的稳定性：结构化字段与命令行入口的结构化输出已经存在，缺口是
     "非结构化文本格式是否承诺稳定"这一点的文档澄清，按文档勘误处理。
   - 批处理构建入口缺少开发态构建开关：现有批处理入口补一个开关即可，属纯脚本级改动，不
     构成新的契约面。

## 后果

### 正面

- 长驻可交互运行入口给任意外部工具提供了统一、非专属的联调回路，外部工具不再需要各自反向
  工程"如何让运行期宿主停留在可交互状态"。
- 参数化内容同步入口第一次把"任意源目录 → 任意目标运行期工程"的能力从两个各自绑定专属流程的
  入口中解耦出来，往后任何新的消费场景不需要为自己量身定制第三个同步脚本。
- 两项能力的参数面、输出格式与退出码约定被本 ADR 明确列为公开契约，落地期与任意外部消费方
  都有明确、可依赖的稳定性预期，不再各自照抄或反推实现细节。

### 负面

- 长驻运行入口的就绪信号载体、受控退出的具体信号形式等实现细节留给落地期，短期内还不能直接
  使用；若落地期发现契约中某一项在批处理运行期环境下确实做不到，需要回来修订本 ADR，存在
  返工风险。
- 参数化同步入口与既有两个入口并列而不整合，长期存在"同一类操作有三个入口，各自适用场景不同"
  的认知成本，需要在面向消费方的文档中讲清楚三者的选择依据；若未来决定收敛为更少的入口，需要
  新的 ADR 处理。
- 决策 3 的幂等性承诺明确排除了已知的上游序列化副作用，该副作用修复前，个别数据集上"幂等"这
  一承诺在感知上仍会打折扣，需要与该副作用的独立修复项联动才能完全兑现。

## 备选方案与为什么不选

- **直接做成面向该消费方的专属联调协议**（例如专属的进程间通信协议、只服务某一类消费方的
  启动封装）：能更快满足当前唯一已知的诉求来源，但会在框架里引入消费方专属概念，直接违反
  "内容编辑器随游戏走、不进框架"的既定边界（ADR-0018）；且一旦未来出现第二个需要同样能力的
  外部工具，要么被迫复用一个名义上专属、事实上通用的协议（名实不符，边界会被逐渐侵蚀），要么
  框架又要为它单独定制第二份，重蹈"各消费点各自实现、未收口为公开契约"的覆辙（与 ADR-0025/
  0037 背景所述问题模式同构）。故不选。
- **本次只解决长驻运行入口，参数化同步入口留给消费方自行在既有入口基础上包装脚本**：会让
  "通用命令行能力"这一契约面出现明显缺口——长驻运行入口通常需要先用"待加载的内容"启动，若
  这一步没有通用同步入口，长驻运行入口的实际可用范围会退化为"只对框架自身工作台内容可用"，
  与决策 1 总原则冲突。故两项一并处理。
- **把参数化同步入口做成对既有"框架自身构建同步"入口的就地扩展**（在其现有固定源/目标路径对
  基础上，新增一对可选的自定义源/目标参数，复用同一次调用）：改动面看似更小，但该入口内部把
  "多组固定源/目标路径、按内容类型分组同步、仅对框架自身工作台成立的专属自检规则"耦合在一次
  调用里，硬塞进一对可选自定义参数会让该入口从"框架自身工作台专属同步"退化成两用入口——两条
  调用路径共享同一份实现，却分别对应两种完全不同的契约稳定性预期（一个是仓库内部实现细节，
  一个即将成为对任意外部工具开放的公开契约），任一边今后的调整都可能意外影响另一边。故不选，
  改为新增第三个独立入口（决策 3 正文）。
