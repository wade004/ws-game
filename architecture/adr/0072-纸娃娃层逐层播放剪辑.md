# ADR-0072 纸娃娃层逐层播放剪辑

状态：已拍板 2026-09-23

## 背景

消费方反馈第十八批同一批指出的第二个"已知简化"（与 [ADR-0071](0071-装备纸娃娃层随朝向换图.md)
同批，两者共用同一份背景材料，本篇只记录本决策独有的部分）：`display.anim_set.clips.<state>.
resource_ref`（04 第 7.2 节）驱动的是引擎适配层挂接的一份**整身**序列帧播放对象，纸娃娃层
（`IRenderer2D.SetLayers` 落地的逐层渲染对象）在任何状态下都只有静态图；整身序列帧对象的渲染排序
又恒在全部纸娃娃层之上（引擎适配层既有实现），结果是一旦播放真正带多帧美术的状态（待机呼吸、
攻击挥击一类），整身画面会盖住纸娃娃层——接入方要做"角色待机/攻击时装备跟着动"的表现，撞到这一
限制。

`SpriteViewBase`/引擎适配层相关注释此前把"纸娃娃层各自播放独立剪辑"登记为"已知简化，待设计层确认
是否要做逐层剪辑"；[ADR-0037](0037-资源引用路径推导契约扩展到vfx-sfx-model-anim_set.md) 决策 2
的"待设计层确认"事项之一同样涵盖 sprite 型逐层剪辑这一半。本篇即是该待办的裁决落地。

约束（同 ADR-0071 一贯惯例）：不改 04 `display.anim_set` 表的字段结构（`resource_ref` 仍是单个
`Id`，不拆分）；不引入与 `IRenderer2D.SetLayers` 平行的第二套渲染通道——纸娃娃层逐层剪辑必须落地到
`SetLayers` 已经建好的同一批逐层渲染对象，使现有 flash/fade、flipX、height 偏移、阴影一类既有
表现天然继续对逐层动画生效，不需要为"正在播动画的纸娃娃层"另写一套颜色/变换同步逻辑；
`IFrameAnimPlayer`/`FrameAnimPlayer` 只允许新增，不改既有公开签名。

## 决策

1. **sprite 型且声明了 `paperdoll_layers` 的外形，`resource_ref` 语义从"整身唯一剪辑"扩展为
   "逐层剪辑集引用"，按两级顺序逐层探测**：对 `DisplayInfo.Sprite.PaperdollLayers` 里的每一层
   `<layerName>`，依次尝试
   ① `sprite_anim.<去类别前缀的 resource_ref>__<方向裸档位名>__<layerName>`（方向 + 层名，与
   ADR-0071 装备层同一套方向档位换算，取实体挂接时刻的默认朝向）、
   ② `sprite_anim.<去类别前缀的 resource_ref>__<layerName>`（仅层名，不分方向）；
   两级都探测不到时，该层维持它已有的静态图（`SetLayers` 落地的结果），**不隐藏、不清空**——继续
   保持当前可见的纸娃娃层素材，不因为这一状态没给它专属动画美术就消失。没有 `paperdoll_layers`
   的外形（`item`/`gobj`/`projectile`，或 `paperdoll_layers` 为空的 `creature`）和 model 型外形，
   本决策整体不生效，行为与升级前完全一致（挂接流程开头的早退判断）。这套探测逻辑落在引擎适配层
   新增的挂接后置步骤里，接在既有的默认动画剪辑解析步骤之后追加一次调用，不改动该步骤其余行为。
2. **至少一层命中逐层剪辑时，整身序列帧渲染对象隐藏；一层都没命中时，维持既有的整身兜底行为
   （可见、正常播放）**——两种模式互斥，不是叠加显示。落地方式：`IFrameAnimPlayer`/
   `FrameAnimPlayer` 新增一个"当前帧号变化"通知方法（`IFrameAnimPlayer` 契约新增带默认实现的
   方法，向前兼容既有实现者，见"后果"一节 ABI 说明），引擎适配层挂接时订阅一次，回调里按当前播放
   的剪辑查本次状态是否有任何一层命中的逐层剪辑表：命中则把整身渲染对象的可见性关掉，并把命中层
   各自的当前帧贴图直接写进 `SetLayers` 建好的对应逐层渲染对象（引擎适配层新增一个按层下标写入
   渲染对象贴图的方法，不新建任何渲染对象，也不新增 `IRenderer2D` 契约本身的签名）；未命中则把
   整身渲染对象的可见性开回来并直接返回，不触碰任何纸娃娃层——与升级前"只有整身一份画面"完全
   一致。
3. **各层探测按 `PaperdollLayers` 数组顺序严格串行进行，不并发**：对某一层的两级探测（含各自的
   异步加载往返）全部落定（命中或两级都落空）后才开始探测下一层。第一个真正命中逐层剪辑的层，被
   选为这次状态"共享时间轴"的权威来源——它的帧数/帧率直接注册成这次状态本来就对应的那个剪辑 Id
   （与既有整身占位剪辑是同一个 Id，直接覆盖；复用 `FrameAnimPlayer.Update` 已有的"每次推进前
   按剪辑 Id 重新从共享字典取最新版本"热替换机制——剪辑处于播放中时异步覆盖也会在下一次推进自动
   切到新内容，不需要额外的"补注册后重新播放"步骤）。其余命中的层各自登记成一个独立的衍生剪辑
   Id，只提供自己的帧序列供取帧，不参与推进时间轴。
   判断记录（为什么串行探测、不是谁先异步完成谁当权威）：并发探测下"谁是权威来源"由网络/磁盘
   I/O 完成的先后顺序决定，同一份数据在不同机器/不同次运行下可能选出不同的层当权威，帧数/帧率
   因此不确定，运行期回归测试也无法稳定断言；串行探测把"权威来源"钉死为 `PaperdollLayers` 数组
   里第一个真正命中的层，结果只取决于数据本身的层顺序与内容，跨机器/跨次运行一致，也让测试能够
   可靠断言。
4. **共享时间轴的帧号对各命中层各自按自己的帧数取模（不是夹取/截断在最后一帧）**：新增的取帧方法
   用"帧号对该层帧数取模"（负数修正）取帧。判断记录（为什么是取模，不是夹取）：占位样例数据里
   刻意让 `head`（2 帧）与 `hand_main`（3 帧）帧数不同，用于验证这条规则本身；夹取会让帧数少的层
   在权威时间轴播到后半段时长时间停在最后一帧（视觉上"卡住"，比不播放更容易被误判为缺陷），取模
   让帧数不同的层各自以自己的周期循环播放，只是彼此不同步（同一时刻处于自己剪辑的第几帧不同），
   这与"多数 2D 分层渲染方案里纸娃娃层各自独立播放、只是共享同一个驱动节拍"的通用做法一致，也是
   本决策"共享单一时间轴"这一简化本身能够成立的前提——真正要求逐层完全独立帧率/播放进度的场景
   超出了本次消费方反馈的范围，见"备选方案"一节。

## 后果

### 正面

- 纸娃娃层第一次能够在真正播放多帧动画的状态下（待机呼吸、攻击挥击等）随共享时间轴切换素材，
  整身渲染对象不再永远盖住纸娃娃层，接入方"角色播动画时装备跟着动"的需求不再受阻。
- 完全复用既有 `SetLayers` 渲染路径（逐层渲染对象、颜色/排序/镜像既有遍历），没有引入第二套渲染
  通道，flash/fade、height 偏移、阴影等既有表现对参与逐层动画的层继续生效，不需要具体游戏或后续
  维护者记住"这层在播动画时颜色/变换走另一条路"。
- 不是破坏性数据变更（与 ADR-0071 不同）：现有扁平 `sprite_anim.<name>` 资源与既有的"扁平查找→
  找不到降级单帧"逻辑完全不改，逐层剪辑纯粹是新增的、基于磁盘是否存在按约定命名的资源而自动生效
  的附加能力——没有按新约定准备逐层美术的存量数据，行为与升级前逐帧一致（运行期回归覆盖了这一条：
  没有任何一层命中逐层剪辑的状态下，整身渲染对象保持可见、纸娃娃层不被触碰）。
- `IFrameAnimPlayer` 新增的通知方法用带默认实现的接口方法落地，不要求已有的具体实现类型改动即可
  编译通过（ABI 只加法）。

### 负面

- **只在实体挂接时刻按当时朝向探测一次逐层剪辑，运行期朝向改变不会重新探测**（与 ADR-0071 装备层
  "每次重建装备层都按当前朝向重算"不同）：一个四方向以上的游戏若既要逐层动画又要这份动画随朝向
  切换素材，本决策目前只覆盖挂接时的朝向。这是有意的范围收窄，不是遗漏——本轮反馈只要求"装备
  跟着角色播动画"，没有"逐层动画还要随时随地跟着转向换图"这一更复杂的需求；后续若有消费方反馈
  明确提出，按同一套判断记录另开 ADR 处理，不在本决策里超前设计。
- **只覆盖 `DisplayInfo.Sprite.PaperdollLayers` 声明的基础层，不覆盖装备动态新增的层**：一件装备
  给角色新增了一个默认层名列表之外的纸娃娃层（ADR-0071 决策 2 提到的"装备新增的层"）时，这个新增
  层不参与本决策的逐层剪辑探测，始终维持静态图——挂接后置步骤在实体挂接时点运行，这时装备是否已经
  穿戴、穿戴了哪些槽位是运行期后续事件才确定的信息，与"探测只做一次"（见上一条）是同一处范围
  边界，一并记录，不是两个独立缺陷。
- 共享单一时间轴意味着不同帧数的层不会同步播放到同一视觉阶段（见决策 4"取模不是夹取"判断记录）：
  多数 2D 卡通渲染下这个差异不明显，但美术如果要求"所有层必须严格同帧同步"，本决策目前的方案不
  满足，需要美术层面对齐帧数（都做成同一帧数）来规避，不是代码层面可以消除的限制。
- 引擎适配层新增若干个承载"层名查表"/"按层下标写贴图"/"逐层串行探测"职责的私有实现——这一层的
  体量因此又增大了一截，属于预期内的、与决策复杂度相称的代码量增长，不是可以再精简的冗余。

## 备选方案与为什么不选

- **给纸娃娃层各自独立的播放进度（各层自己的计时/帧号变化订阅），不共享单一时间轴**：能让帧数
  不同的层各自以严格正确的节奏播放，互不干扰，但需要给每一层单独起一个播放器实例（当前引擎适配层
  是"一个播放器对应一个整身渲染对象"的既有设计，纸娃娃层复用的是 `SetLayers` 的渲染对象数组，不是
  各自独立的播放器组件），既加大改动面（每层一个播放器意味着每层一份逐帧轮询、一份订阅管理），也
  超出本轮消费方反馈"装备跟着角色播动画"这一具体需求的必要范围。故不选，改为共享单一权威时间轴 +
  各层取模读帧（决策 3/4），代价在"后果"一节如实记录，留作后续消费方明确提出"逐层独立播放进度"
  需求时再按新 ADR 扩展的接口。
- **权威时间轴来源改成夹取到最后一帧、不循环取模**：能让帧数少的层"播完停在最后一帧"看起来像是
  设计好的收尾姿态，但对循环播放的待机一类状态反而更容易造成"卡住不动"的视觉错觉（见决策 4 判断
  记录），且与循环动画"应当持续循环"的直觉预期冲突。故不选，改用取模循环。
- **运行期每次朝向变化都重新探测逐层剪辑**（呼应"后果"一节第一条负面）：能补上"逐层动画随朝向
  换图"这一更完整的能力，但本轮反馈没有提出这一需求，提前做等于超出反馈范围的预先设计，且会让
  探测时机从"挂接时一次性"变成"随朝向持续重复"，需要额外的节流/去重考虑（避免朝向抖动时反复触发
  异步加载）——不在没有真实需求验证的前提下引入这份复杂度。故不选，只做挂接时探测一次，缺口如实
  记录在"后果"一节，等后续反馈明确后再处理。

## 与游戏客户端的对应参考

对应主流 2D 动作/RPG 游戏"角色播放攻击/待机动画时，武器、头饰等纸娃娃层跟随身体一起播放各自的
序列帧"的通用表现手法——装备层与身体层共用同一条节拍，但各自的美术资源相互独立，是纸娃娃换装
系统里"分层渲染 + 共享驱动节拍"这一常见组织形式的具体实现。
