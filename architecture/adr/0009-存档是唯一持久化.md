# ADR-0009 存档是唯一持久化

状态：已拍板 2026-09-04

## 背景

单机无网络场景下不存在账号层、不存在服务端数据库，所有玩家进度的持久化必须落在本机某种文件形式上。如果不明确"存档是唯一权威来源"，容易出现进度数据分散在多处（例如设置文件里混入进度字段、某些模块自行落盘缓存）导致的一致性问题，也不利于统一设计版本迁移、损坏兜底、回放等机制。

## 决策

每个存档槽是一份带版本的结构化文档，包含玩家、世界状态、当前地图与位置、随机种子等全部进度相关数据，配合迁移函数链处理版本升级；设置（画面、音量、按键绑定等偏好）单独存放，不属于存档的一部分。自动存档点是否启用是可配置项。具体模型见 [../10_存档与持久化.md](../10_存档与持久化.md)。

## 后果

### 正面
- 进度数据只有一处权威来源，删除/复制/备份一个存档槽即可完整迁移一局游戏进度，不会遗漏散落在别处的状态。
- 版本迁移、损坏兜底、确定性回放等机制只需要针对"存档"这一种持久化对象设计，不需要为多处持久化各自维护一套机制。
- 设置与存档分离，使得清空/切换存档不会影响玩家的操作习惯与画面偏好设置。

### 负面
- 所有需要跨读档保留状态的模块都必须显式实现 Persistable 契约并接入 SaveSystem 汇总流程（见 [../10_存档与持久化.md](../10_存档与持久化.md)），增加了模块开发时的一项固定工作量。
- 存档体积会随玩家进度（背包、任务状态、世界状态标志等）增长，需要在设计阶段就考虑哪些数据默认不存（见该文档"哪些不存"一节）以控制体积与序列化成本。

## 备选方案与为什么不选

- **多处持久化并存**（如任务进度单独存一个文件、背包单独存一个文件）：可以让不同系统独立迭代自己的存储格式，但会让"一次读档是否完整恢复了游戏状态"失去单一权威判断依据，版本迁移与损坏恢复也需要分别处理多套文件，一致性风险高，不采纳。
- **完全不做版本化，存档格式变更即视为不兼容**（玩家必须开始新游戏）：实现最简单，但对玩家体验损害极大，且不符合"单机游戏应尽量保护玩家投入的时间"的行业惯例，不采纳。

## 魔兽世界的对应做法

魔兽世界的持久化完全在服务端数据库完成，客户端不持有权威存档；单机场景没有服务端，因此需要一个对应的"唯一权威持久化载体"角色，本 ADR 让存档承担这一角色，并借鉴服务端数据库"结构化、可迁移、有版本"的特性，用存档 schema 版本与迁移函数链对应数据库表结构迁移的思路。
