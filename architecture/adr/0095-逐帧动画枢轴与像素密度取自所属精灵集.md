# ADR-0095 逐帧动画枢轴与像素密度取自所属精灵集

状态：已拍板 2026-09-26

## 背景

消费方反馈第四十批（`<game>` 接入方，基于 v1.74.0 冻结发布提交核实，阻塞）：属于某精灵集的逐帧
动画（按方向/层切换的角色动作剪辑）播放时，枢轴仍固定在几何中心、像素密度仍取全局默认值，与同一
精灵集下的静态图像表现不一致——静止时脚底对齐，一进入动画就跳回图中心对齐。

落地期核实结论：[ADR-0091](0091-精灵枢轴取自精灵集脚底锚点.md) 决策 5 曾写明逐帧动画"本质是
同一批图像资源按帧切换，共用同一条解码路径"，因而未单独处理——该判断是错的。已落地引擎适配层里，
精灵集静态图像与精灵集内逐帧动画走的是两条互不相干的解码路径：前者读取 `anchors.json` 脚底锚点
与像素密度；后者只读取动画自带的帧图集与 `frames.json`，从未读取所属精灵集的 `anchors.json`，
枢轴与像素密度均固定为改动前的全局默认值。特效序列帧（不属于精灵集）不受影响，行为不变。

## 决策

1. **加载时机决定信息可得性**：逐帧动画解码入口与精灵集静态图像解码入口是两个独立方法，动画解码
   发生时并不知道调用方要播放的是哪个精灵集；因此在资源加载调用点补一个可选的"所属精灵集"提示，
   随加载请求一并传入解码入口，作为决定枢轴/像素密度取值的依据之一。不改动既有加载接口的原有签名，
   只新增一个携带该提示的重载，未使用该重载的既有调用方行为不变。
2. **枢轴与像素密度的解析优先级**（从高到低）：
   a. 动画自带的 `frames.json` 若显式声明了枢轴/像素密度，直接采用——这是给"画布不规则、不适用
      所属精灵集统一锚点"的个别动画留的逃生舱，声明后本条动画不再看所属精灵集。
   b. 否则，若加载时提供了所属精灵集提示，按 [ADR-0091](0091-精灵枢轴取自精灵集脚底锚点.md)
      决策 1、2 同样的公式与方向回退规则，从该精灵集的 `anchors.json` 取脚底锚点与像素密度
      （复用 ADR-0091/[ADR-0081](0081-精灵集自带像素密度在运行期生效.md) 已接入的同一份解析
      与缓存，不新增磁盘 IO）。
   c. 都没有（未提供精灵集提示，或提示对应的精灵集/锚点不存在）——回退此前固定写死的几何中心与
      全局默认像素密度，逐字节不变；特效序列帧（不属于任何精灵集，加载时不会带精灵集提示）始终
      走这条回退路径，行为不受本 ADR 影响。
3. **同一份帧图集尺寸与所属精灵集画布不一致时**：以动画自身实际帧尺寸为准计算枢轴比例坐标，
   与 ADR-0091 决策 1"取实际解码纹理尺寸、不取声明画布"同一原则，不一致记一条诊断。
4. **已知限制——同一动画资源短时间内被不同精灵集复用时不重新解码**：逐帧动画的解码结果按资源
   标识缓存；同一资源标识若先后携带不同的精灵集提示被请求加载，视为极罕见的资源复用场景，直接
   复用已解码结果并记一条去重诊断（同一资源标识只记一次，不刷屏），不重新解码——若确需按不同
   精灵集重新解出不同枢轴，需先卸载该资源或重启加载器实例（例如场景重新加载）使缓存失效。这是
   为避免"同一份图集在内存中同时存在多份不同枢轴的解码结果"这一更复杂的多态缓存机制而接受的
   已知限制，非本次任务范围内需要收敛的设计缺口。
5. **不改动逐帧动画的帧切换与排序**：枢轴决定的是精灵在世界中的对齐点，帧切换时逐帧替换的是
   贴图内容而非枢轴本身（枢轴随首次解码结果固定在精灵对象上），因此不涉及帧切换逻辑；渲染排序
   公式仍由逻辑坐标本身决定，不需要联动改动。
6. **范围**：只影响属于精灵集的逐帧动画（角色动作剪辑）。特效序列帧图集（打包图集、不组织成
   "精灵集"、不适用"脚底对齐"语义）不受影响，改动前后行为逐字节一致。

## 后果

### 正面

- 逐帧动画与同一精灵集的静态图像枢轴/像素密度表现一致，根治"静止对脚底、一动画跳回图中心"的
  错位问题。
- 复用 ADR-0091/ADR-0081 已接入的解析与缓存，不增加额外磁盘 IO；不改动任何既有公开接口的原有
  签名。

### 负面（行为变更，需在发布说明标注）

- 全部属于精灵集且实际参与本次接线的逐帧动画调用点——播放时会整体相对此前上移（改动前对齐图
  中心，改动后对齐脚底），与 ADR-0091 静态图像那次的视觉变化方向一致。
- 决策 4 的已知限制：同一动画资源被不同精灵集复用的场景下，后到的精灵集提示不会生效，直到该
  资源被卸载或加载器实例重置。

## 备选方案与为什么不选

- **解码入口自己反查资源标识归属哪个精灵集**：逐帧动画的资源标识命名本身不总能唯一反推出精灵集
  （尤其不带方向的简化命名），需要额外维护一张反查表，比"加载时机本就知道、顺手传一个提示"更
  复杂且容易和资源命名规则的后续演化脱节。
- **同一资源标识按精灵集分别缓存多份解码结果**：能彻底解决决策 4 的限制，但需要把现有"按资源
  标识为键"的缓存整体改造成"按(资源标识, 精灵集)复合键"，涉及卸载、内存占用等一连串连带决策，
  超出本次阻塞项的最小修复范围；已作为已知限制记录，交由设计层后续视复用场景是否真实出现再评估。
