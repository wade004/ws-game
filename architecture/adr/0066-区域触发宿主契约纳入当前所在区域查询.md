# ADR-0066 区域触发宿主契约纳入当前所在区域查询

状态：已拍板 2026-09-22

## 背景

消费方反馈（游戏接入方第九批，阻塞，基于冻结发布提交核实）：`<game>` 要在 HUD 常驻显示玩家当前
所在区域的名字，但框架给不出这个数据：

- 区域触发契约（下称"区域触发宿主契约"）的 `evaluate` 只在检测到进入/离开时经事件总线派发一次性
  `进入`/`离开` 事件；"谁在哪个触发范围内"这份状态只存在生产实现内部私有字段里，契约不暴露任何
  只读查询出口。
- 表现层 HUD 视图模型、玩家路径小语法均没有"当前区域"字段/路径。
- 接入方因此只能自己订阅进入/离开事件、自己缓存一份"当前所在区域"状态——这是自建平行状态：既
  重复了宿主已经在维护的事实，又要自己处理重叠区域、陷阱等边界情形，稍有差池就与宿主的真实判定
  脱节。接入方已停工。

区域显示名来自区域触发定义的 `name_key` 字段（经本地化解析，框架不做本地化，只给文本键）。

## 决策

1. **宿主层新增只读查询：某单位当前所在的全部触发区域 id，按进入先后排序**（最早进入的在最前，
   最近进入的在最后）。不在任何区域时返回空集合。含通过动态陷阱登记通道进入的触发体——本成员只
   回答"是否检测到处于范围内"这一件事，不附加任何"是否配置了显示名"的过滤，那是表现层派生"当前
   区域名"定义时才需要的判断，不属于宿主层职责。
   <br>ABI 只能新增：用带默认实现的接口成员新增（既有同类契约扩展的一贯做法），默认实现恒返回
   空集合，不要求任何既有实现类型（含测试替身）连带改动即可继续编译通过。生产实现用显式接口实现
   （不用同名公开方法隐式满足契约成员）转发到内部账本——理由与本仓库其它契约新增成员完全一致：
   隐式实现会把落地方法的物理签名从普通实例方法改写为接口成员的虚方法形态，被静态 ABI 比对工具
   误判为破坏；显式接口实现规避这一问题，新增的公开方法本身物理签名不受影响。
   <br>为了给出"进入先后"这一排序，生产实现内部需要记录每次成功进入的顺序——用确定性的单调计数
   （每次成功进入分配一个递增序号），不用系统时钟：取墙钟时间戳会破坏本框架"运行时路径不依赖
   系统时间"的确定性铁律，单调计数已经足够表达"谁先谁后"这一件事，不需要真实的时间刻度。触发体
   被移除登记（无论是单条移除还是随地图批量卸载）时，对应的"进入中"记录要一并清掉，否则会残留一
   条再也不会被清除的"孤儿"记录，让本查询持续报告一个已经不存在的触发体；两条移除路径（单条/按
   地图批量）保持同一处理口径。

2. **"当前区域"的定义（表现层派生，不进宿主层）**：该单位所在区域中，最近进入且尚未离开、并且
   配置了显示名（`name_key` 非空）的那一个。没有显示名的触发（陷阱、纯任务探索点等）不参与"当前
   区域名"的判定——它们不是给玩家看的地名，只是恰好也落在"该单位当前所在的区域"这个更宽泛的集合
   里。重叠区域场景下离开内层区域时，"当前区域"回落到仍在其中的、次新进入的那个有名区域，不是
   直接变成"无"。
   <br>判别字段选择：区域触发定义已有的 `name_key`（可空的文本键字段）本身就是内容作者"要不要给
   这块区域一个显示名"的显式选择，语义上就是"这是不是一块地名区域"最贴切的信号。四种数据驱动的
   触发类型（地图切换点、任务探索点、遭遇战触发、脚本触发）都不天然对应"这是给玩家看的地名"，
   唯独 `name_key` 是否非空直接回答了这个问题，不需要另外新增一个"是否地名区域"的专用布尔字段或
   按触发类型硬编码判断——按类型判断还会把"某类地图切换点恰好没配名字"或"某个脚本触发恰好配了名字
   用于调试"这类例外情形处理得更别扭。

3. **路径层新增两条 `player.*` 子路径**：区域 id 本身、区域显示名文本键，均在没有当前区域时取
   "无"。装配需要同时依赖区域触发宿主契约与承载区域定义数据的只读数据视图（后者用来按 id 反查
   `name_key`——宿主层查询本身不暴露这个字段，见决策 1）；新增依赖走新增构造重载，不改既有构造
   函数签名。名字的显示文本由具体游戏经本地化解析，路径只给文本键，与任务、技能等既有同类路径
   （标题/名称文本键）口径一致。

4. **表现层视图模型新增两个只读属性**，经上述路径转发，取值类型与"区域 id"/"显示名文本键"两个
   字段各自的既有类型一致（均为可空的引用标识类型）。

5. ABI 只能新增：以上全部改动纯加法，不删改任何既有公开签名、不给既有构造/方法加参数。

## 后果

### 正面

- 消费方今后经区域触发宿主契约的新查询成员，或更省事地直接经路径层/HUD 视图模型两条现成通道，
  就能拿到"当前所在区域 id + 显示名文本键"，不再需要自己订阅事件、自建一份平行状态账本去追踪
  进入/离开与重叠区域的回落规则。
- 新增契约成员是纯新增（带默认实现），不要求任何现存实现类型（含各模块测试替身）连带修改即可
  继续编译通过；ABI 探针核实 `breaks=0`。
- "当前区域"的重叠回落规则收在宿主层权威状态之上做一次性推导，接入方不需要自己重新实现这套
  判定逻辑，也不会因为各自实现细节不同而与宿主真实状态产生分歧。

### 负面

- 表现层"当前区域"的判定需要额外依赖一份只读数据视图（用于反查 `name_key`），路径层构造函数因
  此多一个重载分支——与本框架此前同类改动（技能簿查询、光环查询等新增依赖）面临的取舍完全相同，
  不是本次新引入的问题。
- 宿主层查询返回的"全部所在区域"与表现层"当前区域"是两个不同粒度的概念，调用方需要理解这一层
  区分（不能假设宿主层查询直接就是"当前显示区域"）；本 ADR 决策 1/2 的文字已经明确划出这条边界，
  风险可控。

## 备选方案与为什么不选

- **让宿主层直接给出"当前区域名"这一个最终结果**：技术上能省掉表现层一次判定，但"是否配置了
  显示名"这层过滤依赖的是内容数据（`area.trigger_def` 的 `name_key` 字段），而宿主层运行期账本
  本身并不持有、也不应该持有这份内容数据的反查能力（该数据经数据登记表按需加载，不属于宿主层
  运行期状态的天然组成部分）；把这层过滤放在宿主层会让契约职责边界模糊——宿主层只负责"检测
  进入/离开"，"哪些区域该显示名字"是内容/表现层的判断，与本模块既有"只负责检测进入/离开 + 满足
  条件 + 发事件或调用钩子，不内含具体业务逻辑"的定位冲突，故改为宿主层只给权威的原始状态，"当前
  区域"这一表现层概念的推导逻辑留在表现层。
- **新增一个专门的"是否地名区域"布尔字段**：会给内容数据表新增一个与 `name_key` 高度冗余的字段
  （"有没有名字"与"是不是地名区域"在目前四种触发类型下没有观察到需要区分的场景），增加内容作者
  的填写负担与两个字段可能互相矛盾的校验成本，故直接复用已有的 `name_key` 可空性作判别信号。
- **进入序号用系统时钟时间戳**：更符合直觉的"先后"表达，但违反本框架"运行时路径不依赖系统时间"
  的确定性铁律（回放/测试场景下系统时钟不可控），且本需求只要求"谁先谁后"的相对顺序，不需要真实
  的时间刻度，单调计数已经完全满足，故不采用时间戳。
