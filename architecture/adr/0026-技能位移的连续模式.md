# ADR-0026 技能位移的连续模式

状态：已拍板 2026-09-11

## 背景

消费方反馈（`architecture/落地计划/消费方反馈-2026-09-11-技能位移连续模式.md`，M-C10《投射物与技能位移通用能力反馈》第 1 节，非 bug 的扩展建议）：06 第 3.2 节 `move` 效果原语现有 `charge`/`leap`/`knockback` 三种子类型均由 `EffectDispatcher.ApplyMove` 直接 `SetPosition` 到算出的终点，一次性完成——适合"最终逻辑位置在哪"这类离散结果，但没有连续路径采样、没有碰撞/导航裁决、没有暂停/取消的观测点。已复现最小场景：合法墙前目标 `(1,0)` 使用 static leap `(3,0)`，墙区间 `x=1.5..2`，终点直接跳变且 `walkable=true`——`walkable=true` 只是说落点本身可行走，不代表从起点到落点这条路径没有穿墙。

消费方建议合同：增加可选连续模式，同时保持现有瞬移模式的兼容性；合同明确路径采样、碰撞/导航裁决、阻挡后的停止或回退、暂停与取消事件；验证条件是同一输入分别走现有瞬移和连续模式，逐 tick 比较位置、事件和最终状态，现有三种模式结果保持兼容。

现有可复用的基础设施：`core/carriers/unit` 已经有一套成熟的"移动系统"（`MovementHost`/`MovementTickHandler`/`MovementState`），处理目标类寻路（`INavigation2D.FindPath`）、方向类直接位移（对候选终点做 `Raycast` 判定，受阻则截断/收缩）、控制效果禁止移动（`MovementState.MovementLocked`/`IAuraQuery.GetControlFlags`）、暂停（`SimStep.Dt`）、离散/连续两种时间模型。`move` 效果原语要的"连续位移"在本质上是同一件事——沿一条直线、每步按速度推进、遇阻按策略处理——只是发起方是技能效果而不是玩家/AI 的移动意图，且期间需要与玩家/AI 的常规移动互斥。

## 决策

1. **`move` 效果参数新增可选字段，与既有子类型字段正交**：既有 `mode`（`charge`/`leap`/`knockback`，决定"位移到哪个点"）字段含义不变；新增 `motion`（`instant`，缺省，即现行三种位移的现有语义；`continuous`，转交连续位移）字段决定"怎么位移过去"。判断记录（命名，不复用 `mode`）：若"瞬移/连续"这一维度也叫 `mode` 会与既有取值集合 `{charge,leap,knockback}` 冲突、破坏既有数据对该字段取值范围的假设，两个维度正交、各自独立登记枚举值，改用 `motion` 避免撞名。`motion: continuous` 时追加可选参数：`speed`（每秒位移距离）或 `duration`（总耗时，二选一，`EffectDispatcher` 按 `|target-origin|/duration` 换算等效速度，`speed` 存在时优先于 `duration`）、`blocking`（`stop`/`revert`，缺省 `stop`）、`sample_step`（路径采样步长，缺省取 L3 `MovementOptions.DefaultDisplacementSampleStep`）。五个新字段登记进 `SkillSchemas` 的 `move` 变体（ADR-0019 记法，扁平超集登记，不拆二级 Variants，惯例同该处既有判断记录"避免过度设计"），`speed`/`duration`/`sample_step` 若声明必须 `> 0`（ADR-0021 范围约束同一口径）。

2. **实现落在 L3 `core/carriers/unit`，L2 `EffectDispatcher` 只组装请求并依赖倒置转交**：新增 `core/rules/common/contracts/IControlledDisplacementSink`（依赖倒置接口，惯例同既有 `IProjectileSpawner`）与纯数据 DTO `ControlledDisplacementRequest`（`{unitId, origin, target, speed, blocking, sampleStep}`）。`MovementHost` 直接实现该接口，新增公开入口 `BeginControlledDisplacement(request)`——与既有 `Request`/`Stop` 同一惯例，把请求转译为一条 `Kind == "move_displace"` 的 `Intent` 提交，真正推进由 `MovementTickHandler` 在 `TickPhase.MovementAndNavigation` 消费：
   - 每个模拟步内，把本次可推进的距离（连续模式 `speed × dt`；离散模式取"剩余直线距离 + 一个采样步长"的上界，保证一次性走完，见决策 4）按不超过 `sample_step` 的增量逐段推进；每段推进前用 `INavigation2D.Raycast` 做一次判定（与既有目标/方向移动"射线与路径段同源判定"完全一致的可通行统一规则，见 02 第 1.8 节勘误）。
   - 采样段受阻：`blocking=stop` 停在阻挡前最后可通行采样点（按 `MovementOptions.ArrivalEpsilon` 从入射点回退，回退量相对"本次推进调用开始时的位置"取下界，不会因为采样粒度巧合落在阻挡区域的开区间边界上而回退量被夹成零，见实现判断记录）；`blocking=revert` 回到起点。两种子行为结束后统一触发一次既有 `MovementHost.OnMoveStopped`。
   - 到达终点、单位被控制（`MovementState.MovementLocked` 或 `IAuraQuery.GetControlFlags` 含 `NoMove`）、单位死亡（`Unit.Alive` 变 `false`）、调用方经既有 `MovementHost.Stop` 显式请求停止，四类情形同样结束受控位移，各自触发一次 `OnMoveStopped`（原因见决策 3）。
   - 时间模型暂停（本次推进调用的 `dt <= 0`）时整段推进逻辑短路，不产生任何位移/事件，位移保持进行中——"暂停"因此不需要为受控位移单开一条独立通道，复用连续模式 tick 本身"暂停时不推进"的既有约定即可。
   - 位移期间玩家/AI 的普通移动意图（`Kind == "move"`）被拒绝（不排队）：判定加在 `MovementTickHandler.ApplyIntent` 顶部，检查 `MovementState.Displacement.HasValue`，落地位置与既有"控制期间禁止移动"（`IsLocked`）同一处，是同一层"这个单位本 tick 完全不能按普通方式位移"的语义扩展，不新增独立的互斥机制。`MovementHost.Stop`（`Kind == "move_stop"`）例外——它是"调用方主动取消"的既有出口，延伸到既能取消路径跟随也能取消受控位移（决策 1 提到的"取消"）。

3. **可观测性复用既有事件，不新增事件类型**：受控位移开始时 `MovementState.Mode` 切换为既有的 `Forced`（"被击退/传送等非自主位移强制置入的模式"，语义天然契合），触发既有 `unit.state_changed`；每次推进产生的位置变化复用既有 `unit.moved`（`UnitMovedEvent`）；全部终止路径复用既有 `MovementHost.OnMoveStopped`，新增四个 `MoveStopReason` 枚举成员（`DisplacementArrived`/`DisplacementBlocked`/`DisplacementControlled`/`DisplacementCasterDead`，显式 `Stop` 复用既有 `Requested`）区分终止原因——枚举成员新增不涉及 `gen_event_constants`（那是数据驱动的事件目录登记工具，服务于跨表引用/内容校验；`OnMoveStopped` 是宿主内部的进程内回调事件，不进数据驱动的事件目录，不在该工具范围内，见 `core/foundation/event_bus` 判断记录）。`MovementState` 新增只读属性 `IsControlledDisplacementActive`（等价 `Displacement.HasValue`），供调用方查询"受控位移进行中"标志，不必自行判空内部结构。

4. **兼容性**：`motion` 缺省 `instant`，`EffectDispatcher.ApplyMove` 原有的三分支 `switch`（`charge`/`leap`/`knockback`）代码逐字节未改动，新分支在其之前短路返回——既有数据、既有测试全部不受影响。无阻挡时，连续模式按与瞬移分支完全独立实现、但对同一输入算出的目标点公式相同（`ApplyContinuousMove`/`ApplyMove` 两段代码各自计算，不共享同一份状态），最终落点与瞬移模式一致，由测试锁定。离散模式（回合制）下一次性完成整段位移（不按每回合移动预算拆分）：判断记录——受控位移是"技能效果的一次性结果"，不是玩家点击的持久化路径目标，离散模式下 `MovementTickHandler.Execute` 本身也没有"未收到新意图仍继续推进"的自动续推（那一遍循环只在连续模式生效，见该方法既有判断记录"离散步下只处理当前行动者"），若受控位移也套用这条既有限制、指望下一回合再继续推进，会把"选择离散/连续时间模型"这一策略配置项意外泄漏成"技能位移生效方式不同"这一可观测的游戏规则差异，不符合 05/06 "时间模型对判定结果透明"的既定取舍（同 ADR-0013 决策）；一次性完成使连续/离散两种时间模型下同一次位移的最终落点/是否受阻结论一致，只是"逐 tick 位置序列"这一观测维度在离散模式下退化为一次性给出最终结果（离散步本身没有"tick"概念，符合预期）。

## 后果

### 正面

- 消费方反馈的最小场景（墙前 leap）在连续模式下能正确停在墙前/回退到起点，不再有"合法目标却终点跳变穿墙"的可观测缺口；瞬移模式保持现状，游戏层可按具体技能的表现需要逐条选择。
- 复用既有 `MovementHost`/`MovementTickHandler`/`INavigation2D.Raycast`/`unit.moved`/`unit.state_changed`/`OnMoveStopped` 全套基础设施，不引入第二套位移/事件/裁决机制，维护面不扩大。
- `IControlledDisplacementSink` 依赖倒置接口 + `MovementHost` 直接实现，让 `EffectDispatcher`（L2）新增这一分支时不需要改动任何既有构造函数的物理签名（`EffectDispatcher`/`SkillHost`/`RulesAssembly`/`CarriersAssembly` 均只新增可写属性/新增接口实现，`abi_probe`/`abi_surface` 门禁验证通过），符合"公开 API 只能新增"的硬性约束。

### 负面

- `move` 效果的参数表因此变宽（新增五个字段），内容作者需要理解 `mode`（位移到哪）与 `motion`（怎么位移过去）两个维度正交这一点，短期有一定学习成本；已在 `SkillSchemas.cs` 登记处与 06 文档勘误行落字说明。
- 受控位移与玩家/AI 普通移动互斥、且拒绝（不排队）——若某个游戏希望"位移结束后自动补上被打断的移动意图"，需要在游戏层自行监听 `OnMoveStopped` 后重新提交 `MoveRequest`，框架本身不提供排队缓存（简单确定性优先，同 05/06 既有的"移动系统只做最简单确定性处理，复杂交互留给游戏层"取舍）。
- 离散模式一次性完成意味着"一次位移瞬间跨越很长距离"在回合制游戏里没有"分几个回合走完"的选项；如果某个具体游戏确实需要这种效果，需要在游戏层把一次位移拆成多个技能效果分别触发，框架不在 `move` 原语本身提供跨回合拆分。

## 备选方案与为什么不选

- **消费方自行在游戏层对 `move` 效果做插值/寻路**：否决——阻挡/导航裁决属于框架已经统一维护的通用规则（`INavigation2D`/02 第 1.8 节"可通行统一规则"，`Raycast`/`FindPath`/`IsWalkable` 全仓库共用同一套判定），若交给每个消费方各自实现，必然出现"技能位移用一套阻挡判定、玩家移动用另一套"的不一致（例如某个消费方的插值实现忘记处理"贴边不算受阻"这条既有规则），与"可通行判定是框架统一契约、不允许消费方各自造轮子"的既定取舍（02 第 1.8 节勘误本身即是为了消灭类似不一致而补的）相悖。
- **`move` 原语内部自建一套独立的连续位移状态机，不复用 `MovementHost`/`MovementTickHandler`**：否决——会与既有移动系统各自维护一份"当前是否在移动""位置怎么推进"的状态，容易出现二者互相不知道对方存在、同时移动同一个单位的竞态（例如玩家在受控位移期间同时按住移动键，两套系统各自算出不同的位置）。决策 2 选择"新增一个新的 `Intent.Kind`（`move_displace`）接入既有 tick 处理器"而不是新建平行系统，正是为了让"位移与移动互斥"这条规则有唯一的裁决点。
- **`motion: continuous` 复用既有 `mode` 字段的取值集合，追加 `charge_continuous`/`leap_continuous`/`knockback_continuous` 三个新枚举值**：否决——子类型（位移到哪）×模式（怎么位移）两个维度会变成 `3×2=6` 个平铺枚举值，往后每新增一种"怎么位移"的模式（如未来可能的"抛物线位移"）都要把子类型枚举值再翻一倍；两个正交字段（决策 1）的组合数是加法不是乘法，扩展性更好，也是 06 文档里 `interrupt_flags`/`school_damage` 等多处"字段正交而不是笛卡尔积平铺"的既有登记惯例。
- **阻挡后统一按 `stop` 处理，不提供 `revert` 选项**：否决——消费方反馈原句明确要求"阻挡后的停止或回退"，`revert`（如某些技能设计里"冲锋撞墙后弹回原地"）是常见玩法诉求，且实现成本很低（复用同一次 `Raycast` 结果，只是落点公式不同），没有理由砍掉。
