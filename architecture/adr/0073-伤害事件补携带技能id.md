# ADR-0073 伤害事件补携带技能 id

状态：已拍板 2026-09-23

## 背景

消费方反馈第十九批第 3 条（`<game>` 接入方，基于冻结发布提交核实）：要表达"某个技能命中目标时在目标身上播一个特效"，接入方希望用框架原生的 `feedback.binding` 声明——按技能过滤事件、`attach: target` 把动作挂到命中目标身上。核实结果：框架里不存在任何一个事件同时携带"是哪个技能"和"打中了哪个单一目标"：

1. `combat.damage_dealt`（`CombatDamageDealtEvent`，`core/rules/common/contracts/Events.cs`）字段是 `sourceId`/`targetId`/`school`/`amount`/`isCrit`/`hitResult`/`attackInstanceId`——有单一 `targetId`，但没有 `skillId`。
2. `skill.cast_start` 有 `skillId` 但完全没有目标字段；`skill.cast_success` 有 `skillId` 但只有 `IReadOnlyList<Id> Targets`——技能施放本就允许多目标（如 `target.chain_def.max_targets > 1`），且 `FeedbackBinder.TryGetField`（`Core.Foundation.Expr` 条件系统）显式不覆盖 `targets`：Expr 没有列表类型，无法把"命中了列表里的哪一个"表达成一个可比较的单值字段。
3. `FeedbackBinder.Dispatch` 对声明 `attach: target` 的动作解析是 `ExtractId(evt, "targetId")`——查不到单值 `targetId` 就跳过整个动作并记诊断，`skill.cast_success` 因此天然无法承载 `attach: target`。

消费方核实无误，这是框架侧真缺口。约束：本层对外公开的契约（事件构造签名）只允许新增，不允许修改既有公开签名。

## 决策

1. **给 `combat.damage_dealt`（`CombatDamageDealtEvent`）补一个可空 `SkillId` 属性，不是给 `skill.cast_success` 补单一目标字段**。判断记录（为什么选前者不选后者）：施法（`skill.cast_start`/`skill.cast_success`）与命中结算（`combat.damage_dealt`）是框架里两个不同粒度的既有概念——前者是"这一次施放请求"（可以对应零到多个目标），后者是"这一次效果落地"（恰好一个来源、一个目标）。"某个技能命中了哪个目标"本就是结算这一步才产生的信息，`combat.damage_dealt` 本身已经具备单一 `targetId` 这个结构，缺的只是"这次结算来自哪个技能"这一项；反过来若给 `skill.cast_success` 塞一个"单一命中目标"字段，等于在一个语义上允许一对多的事件里伪造一个不存在的一对一关系（多目标技能该填谁？只填最后一个命中的目标会让消费方看到与 `Targets` 列表不一致的数据），且每个目标各自是否命中/是否被免疫/最终数值都是结算逐次算出来的，`skill.cast_success` 触发时这些信息根本还不完整。故选前者。
2. **取值来源是结算落地那一刻的 `EffectContext.SkillId`，不新引入第二套"当前技能"跟踪机制**：`EffectContext.SkillId` 字段本就存在（`core/rules/common/contracts/EffectContext.cs`），`Resolver.Resolve`（`core/rules/combat/core/Resolver.cs`）唯一的 `combat.damage_dealt` 发布点原样转发这个值即可，不需要新的状态跟踪。
3. **`context.IsPeriodic == true` 时截断为 `null`，不是无条件转发**：`EffectContext.SkillId` 这个字段在光环周期效果路径（`Core.Rules.Skill.AuraHost.FirePeriodic`）被复用来承载光环定义 id（`AuraInstanceState.DefId`），不是技能 id——这是该字段在周期效果上下文里的既有实际用法（供 `SpellMod` 按"学派/技能 id/标签"三维匹配时把光环定义 id 当作过滤维度之一，见 `EffectDispatcher.ApplyDamageOrHeal` 判断记录），不是本次改动引入的新状态。若无条件转发，光环周期伤害的 `combat.damage_dealt.skillId` 会被填成一个不属于 `skill.def` 命名空间、消费方永远匹配不上任何真实技能的光环定义 id，看起来像"这次伤害来自某个技能"，实际是误导。`EffectContext.IsPeriodic` 恰好就是区分"这是不是光环周期性触发"的既有字段（见该属性文档"区别于技能效果的一次性结算"），据此截断为 `null`，语义上是"这次伤害不经技能结算路径产生"，与既有 `AttackInstanceId` 字段"未经 `CastPipeline` 产生的结算为 `null`"是完全同一类可空惯例（周期光环伤害两个字段恒同时为 `null`，不是巧合，是同一条结算路径决定的）。
4. **普通攻击（`Core.Rules.Combat.AutoAttackHost`）命中携带 `AutoAttackHost.NativeSkillId`（保留 id `skill.native_auto_attack`），是有意的，不是缺口**：`AutoAttackHost.Update` 构造 `EffectContext` 时本就固定传入这个保留 id（见 [ADR-0059](0059-普通攻击的框架原生执行机制.md) 决策 3"落地事件与技能击杀完全同构"），它不对应任何真实注册的 `skill.def` 行——这一点在 ADR-0059 落地时已经拍板并写入 `AutoAttackHost.NativeSkillId` 的类型注释。本次改动只是让这个既有取值第一次经由 `combat.damage_dealt.skillId` 对外可观测：消费方可以用它精确匹配"普通攻击命中"这一条件，声明反馈绑定，不需要另外发明一种"是不是技能"的分支判断。
5. **ABI：新增构造函数重载，不改动既有签名**——`CombatDamageDealtEvent` 现有八参数构造（`triggerChainDepth`/`attackInstanceId` 均带默认值）保持原样不动，新增一个九参数构造重载（新增末尾非默认参数 `skillId`，同仓库既定的"新增重载而非新增可选参数"惯例，见 `SkillCastStartEvent` 系列构造先例、`core/rules/combat/README.md` ADR-0070 判断记录），旧重载改为转发调用新重载并传 `skillId: null`。`TryGetField` 新增 `"skillId"` 分支（`SkillId.HasValue` 时才返回，同 `"attackInstanceId"` 既有写法）。
6. **`feedback.binding` 消费侧不需要额外接线**：`FeedbackBinder.FromDisplaySource.Skill => ExtractId(evt, "skillId", "auraDefId")`（`from_display: skill`）与 `RulesExprHostFactory.Host.QueryEvent`（`event.<field>` 条件表达式，含 snake_case→camelCase 的既有字段名映射）都是按字段名字符串通过 `IExprReadableEvent.TryGetField` 通用转发，不针对具体事件类型或字段名单独硬编码——新增的 `"skillId"` 分支落地后，`event.skill_id` 条件过滤与 `from_display: skill` 在 `combat.damage_dealt` 上自动可用，不需要在 `FeedbackBinder`/`RulesExprHostFactory` 里再加任何代码。

## 后果

### 正面

- 消费方现在有且只有一条路径能表达"某个技能命中目标时的表现反馈"：`event: combat.damage_dealt` + `condition: event.skill_id == "..."` + `attach: target`，不需要绕道拼凑 `skill.cast_success` 的多目标列表。
- 普通攻击命中第一次成为可按 id 精确声明反馈绑定的对象，与技能命中共用同一套过滤机制，消费方不需要为"是不是普通攻击"另写分支。
- 新增字段零接线成本：`from_display: skill` 与 `event.<field>` 条件过滤均经既有通用字段名转发机制自动生效。

### 负面

- `CombatDamageDealtEvent` 再多一个 ABI 重载，选择哪个重载的维护面随每次纯加法新增持续增长——与既有 ADR-0059/0070 已经接受的同一类代价一致，不是本决策独有的新增负担。
- 光环周期伤害的 `skillId` 恒为 `null`，消费方若想对"某个光环的周期伤害"做类似的按 id 过滤反馈，仍需另行用 `auraDefId` 一类字段（本次改动范围之外，光环周期伤害当前的 `combat.damage_dealt` 并不携带 `auraDefId`，是否补齐留给后续独立评审）。

## 备选方案与为什么不选

- **给 `skill.cast_success` 补一个"最后一个/首个命中目标" `targetId` 字段**：见决策 1 判断记录，会在一个语义上允许一对多的事件里伪造一对一关系，且触发时机早于逐目标结算完成，数值/命中信息不完整。故不选。
- **光环周期伤害的 `skillId` 无条件转发 `EffectContext.SkillId`（即光环定义 id）**：见决策 3，会让消费方看到一个看似"来自某技能"实则不属于 `skill.def` 命名空间的 id，是误导而不是补齐信息。故不选，改为按 `IsPeriodic` 截断为 `null`。
- **新增一个独立的 `combat.skill_hit` 事件，与 `combat.damage_dealt` 并存**：能避免改动既有事件类型，但会制造两份"这次是否命中/命中了谁"的并行数据源，且未命中/被免疫等既有由 `combat.damage_dealt` 单独表达的分支需要在新事件里重新对齐一遍，维护成本更高，收益（不改动既有事件类型）在 ABI 只新增不修改的前提下并不成立（新增字段本就不破坏既有消费方）。故不选。

## 与游戏客户端的对应参考

对应主流 MMORPG 客户端"技能命中特效挂在结算这一步，而不是施法开始/成功这一步"的通用表现惯例（多目标技能的每个命中各自播放独立的命中特效，不是施法一次性触发一份"通用命中特效"），本篇只补齐框架侧承载"这次结算来自哪个技能"的数据字段，不涉及具体特效资源/挂点的呈现细节（呈现细节归游戏，见 13 第 5 节"框架只给状态，呈现归游戏"）。
