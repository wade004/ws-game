# ADR-0006 逻辑id到DisplayInfo映射

状态：已拍板 2026-09-04

## 背景

逻辑层（技能、生物、物品、光环等）需要有具体的画面表现（精灵、动画、特效、音效），但如果逻辑数据直接携带资源路径或美术细节字段，会造成两个问题：一是逻辑层被迫感知表现层概念，违反逻辑与表现分离的架构目标；二是换皮肤、换美术风格、甚至换引擎时都需要改动逻辑数据本身。需要一层间接映射，把"逻辑上是什么"与"看起来是什么样"彻底分开。

## 决策

外形注册表 DisplayInfo（归属 L0 基础层，见 [../01_分层与依赖.md](../01_分层与依赖.md)）把生物、物品、物件、技能、光环等的逻辑 id 映射到具体表现资源：精灵集、纸娃娃层、锚点、方向数、图标、vfx id、sfx id。逻辑表本身只存这些对象的逻辑 id（例如技能表只记录该技能属于哪种效果类型、数值多少），不存任何资源路径；新增一种外形只需要新增一行 DisplayInfo 映射记录，不改动任何逻辑数据或代码。具体字段与体系见 [../09_表现层.md](../09_表现层.md)。

## 后果

### 正面
- 逻辑数据与表现资源可以完全独立迭代：策划改数值不触碰美术资源，美术换风格不触碰逻辑数值，两者的变更互不干扰、互不需要对方重新校验。
- 换皮肤、多美术风格共用同一套逻辑规则（如同一场战斗系统配不同游戏的不同美术）成为可能，直接支撑"骨架承载所有游戏"的架构目标。
- 表现层铁律"只读逻辑状态、不写回"（见 [../09_表现层.md](../09_表现层.md)）因为有这层映射而更容易落实：表现层永远是从逻辑 id 查表得到表现细节，不存在从表现层反向影响逻辑数据的通路。

### 负面
- 每新增一个逻辑对象都需要配套至少一条 DisplayInfo 映射记录，否则该对象没有可见表现，增加了内容制作的步骤数（相比"逻辑数据里直接写资源路径"的一步到位）。
- 映射表本身的字段设计需要覆盖足够多的表现维度（层、锚点、方向、特效、音效等），设计不当会导致后续频繁修改映射表结构。

## 备选方案与为什么不选

- **逻辑数据直接内嵌资源路径字段**：实现简单直接，早期原型阶段效率更高，但一旦项目规模变大，逻辑与美术的耦合会导致任何一方的变更都牵连另一方，且完全无法支持"同一套逻辑配不同美术"的复用场景，不采纳。
- **表现层运行时按命名约定自动推导资源路径（无独立映射表）**：省去维护映射表的工作量，但命名约定难以覆盖复杂的纸娃娃分层、方向档位、特效变体等场景，且校验工具无法对"约定是否遵守"做结构化检查，容错性差，不采纳。

## 魔兽世界的对应做法

魔兽世界的 CreatureDisplayInfo、ItemDisplayInfo、SpellVisual/SpellVisualKit 正是这一设计的原型：creature_template 只存 `DisplayID` 引用，具体模型、贴图、缩放由 CreatureDisplayInfo 表决定；item_template 的外观同理由 ItemDisplayInfo 决定；法术的视觉表现由 SpellVisual 关联的 Kit 决定，而非写在 Spell 本身的效果定义里。本 ADR 是对这套"逻辑 id 到外形表的间接映射"体系在单机 2.5D 场景下的直接移植，具体对照见 [../09_表现层.md](../09_表现层.md) 第 10 节。
