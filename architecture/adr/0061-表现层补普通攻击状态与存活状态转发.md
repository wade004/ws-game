# ADR-0061 表现层补普通攻击状态与存活状态转发

状态：已拍板 2026-09-21

## 背景

消费方反馈第四批第 1/2 条（`<game>` 接入方，基于冻结发布提交核实）指出两处表现层缺口：

1. **普通攻击状态**：上一版本已把普通攻击落地为框架原生一等执行路径（新增
   `Core.Rules.Combat.AutoAttackHost`，`IsEnabled`/`GetTarget`/`GetState` 三个查询方法，`GetState`
   给出正交状态快照 `AutoAttackState { Off, NoTarget, Attacking }`），但只停在规则层——表现层没有
   任何路径或视图模型属性能读到这个状态，接入方要画"普通攻击开关/是否正在攻击"这类 HUD 元素，
   只能自己在游戏层重新猜测（例如凭"是否选中目标"反推，猜不出"已开启但暂无目标"这一中间态）。
2. **存活状态**：表现层同样没有任何路径能回答"这个单位（玩家自身/当前目标）是否存活"，接入方要
   画死亡遮罩、判断目标框是否继续显示，只能自己在游戏层直接查血量是否为零——这会绕开框架自身
   判定死亡的权威时点（见决策 3），与规则层实际的死亡语义产生偏差窗口。

约束：本层对外公开的契约只允许新增，不允许修改既有公开签名的参数列表；两处数据均须原样转发规则
层已有的权威查询结果，不在表现层重新推导。

## 决策

1. **两处新增均照搬既有施法条（`casting.*`，ADR-0056）路径与属性命名惯例，不另起一套写法**：
   `PlayerPathProvider`/`TargetPathProvider` 各自新增一个构造函数重载（既有重载原样保留，新重载
   在既有参数列表末尾追加新依赖），`HudViewModel` 各新增只读属性，经 `IUiDataSource.Query` 转发，
   不持有规则层引用。

2. **普通攻击状态在表现层是结构化枚举，不是字符串——枚举跨越路径查询协议边界时转成固定小写
   文本，惯例同 ADR-0060 光环极性字段**：`HudViewModel` 新增只读属性 `AutoAttackState`
   （玩家自身）与 `TargetAutoAttackState`（目标），类型直接是 `Core.Rules.Combat.AutoAttackState`
   （不是字符串）；新增 `Core.Rules.Combat.AutoAttackStateNames` 静态类（`ToText`/`Parse`/
   `TryParse`，惯例同 `AuraPolarityNames`/`EffectKindNames`）负责这一枚举与固定小写文本
   （`off`/`no_target`/`attacking`）之间的双向转换。新增路径 `player.auto_attack.state`/
   `target.auto_attack.state`，经 `AutoAttackHost.GetState(unitId)` 取值后由
   `AutoAttackStateNames.ToText` 转出文本装入 `ExprValue.OfString`；`HudViewModel.Refresh()` 读到
   该路径后再经 `AutoAttackStateNames.Parse` 转回枚举写入属性——协议层文本化只发生在路径查询这一
   层边界，规则层与视图模型两端全程是类型安全的枚举，不会因为要支持这层文本化输出而回退成字符串
   表示。判断记录（三个取值都参与文本化，没有"未声明"哨兵值）：与
   `AuraPolarity.Undeclared` 不同，`AutoAttackState` 的三个取值（`Off`/`NoTarget`/`Attacking`）
   均是合法的、互斥的运行时状态本身，不存在"内容作者未声明"这一维度（这是查询驱动的运行时状态，
   不是登记表里的可选字段），因此 `AutoAttackStateNames.ToText` 对三个取值全部给出固定文本，不
   需要第四个"未声明"分支。

3. **存活状态的权威来源是 `IUnitAccess.Exists`×`IsAlive`，不是表现层自行判断血量是否为零**：
   新增路径 `player.alive`/`target.alive`（`ExprValue.OfBool`），经 `IUnitAccess.Exists(unitId)`
   （单位当前是否仍在世界模拟中）与 `IUnitAccess.IsAlive(unitId)`（是否存活，由
   `Core.Rules.Combat.Resolver` 在结算致死伤害的时刻调用 `SetAlive(false)` 写入，与
   `AutoAttackHost.Update` 自身判定"目标是否已死亡需要清空"用的同一个查询）共同得出。选择这一
   对查询而不是"读取生命值资源池、判断是否 `<= 0`"，理由有二：其一，`IsAlive` 是规则层对"死亡"
   这件事唯一的权威判定出口，`Resolver` 写入它的时点（结算管线落地环节）与生命值资源池被扣到 0
   的时点不保证同一拍完全同步（例如伤害吸收/护盾在同一次结算内部的中间态），表现层另起一套
   "生命值 `<= 0`"的判断会与规则层自己的死亡语义产生偏差窗口；其二，`IUnitAccess.Exists` 与
   `IsAlive` 已经是 `TargetPathProvider` 既有 `faction`/`name` 子路径判定"目标是否还在世界模拟中"
   的既定查询（见 ADR-0048 对应判断记录），本决策只是把同一对查询再转发一层给存活状态，不新增
   查询面。`HudViewModel` 新增只读属性 `PlayerAlive`（`bool`，玩家单位恒存在于世界模拟，不需要
   区分"不存在"）与 `TargetAlive`（`bool?`）。

4. **`TargetAlive` 的"无目标"语义与既有 `TargetId` 完全一致，不新造一套判定**：无当前目标时
   `target.alive` 路径求值结果为"无"，`HudViewModel.TargetAlive` 为 `null`（不是 `false`）——与
   `TargetId`/`TargetName`/`TargetFaction` 既有"无目标时为 `null`，不是某个具体默认值"的口径
   逐字一致（见 ADR-0048 对应判断记录），接入方按同一套"先判空、非空才读值"的既有代码路径即可
   处理三者，不需要为存活状态单独学一套约定。

5. **数据来源：新增依赖直接来自 `AutoAttackHost`/`IUnitAccess`，不在表现层重新计算**：
   `PlayerPathProvider` 新增十二参数构造函数重载（既有十参数重载原样保留，追加
   `IUnitAccess unitAccess, AutoAttackHost autoAttackHost`）；`TargetPathProvider` 新增八参数
   构造函数重载（既有七参数重载原样保留，追加 `AutoAttackHost autoAttackHost`——`IUnitAccess` 该
   Provider 已持有，`alive` 子路径复用既有字段，不新增依赖）。`PresentationAssembly` 新增局部
   变量 `autoAttackHost = gameplay.Carriers.Rules.AutoAttack`（`RulesAssembly` 已有的公开只读
   属性，见 ADR-0059，不新增依赖边界），两个 Provider 均改走新增的重载传入。ABI：两个 Provider
   各新增一个构造函数重载，`HudViewModel` 新增四个只读属性，`Core.Rules.Combat` 新增
   `AutoAttackStateNames` 一个新类型；全部既有公开签名不改动。

## 后果

### 正面

- 接入方第一次能仅凭框架交付的数据画出普通攻击开关/攻击中状态与存活遮罩，不必再自行猜测中间态
  或绕开框架的死亡判定时点自建一套血量阈值判断。
- 两处新增均是对已有规则层权威查询（`AutoAttackHost.GetState`/`IUnitAccess.Exists`/`IsAlive`）
  的原样转发，不引入任何新的判定逻辑，未来这两个查询本身的语义演进会自动透传到表现层，不需要
  在两处重复维护。
- 存活状态与既有 `TargetId` 系列属性共用同一套"无目标即 `null`"约定，接入方不需要为这次新增学习
  新的判空规则。

### 负面

- `AutoAttackState` 跨越路径查询协议边界时经历"枚举 → 文本 → 枚举"两次转换（同 `AuraPolarity`），
  比直接暴露枚举类型多一层间接——这是路径查询协议本身"取值只覆盖五种通用形状，不为具体枚举类型
  开判别分支"的既定代价，不是本决策专属的额外负担。
- `PlayerPathProvider`/`TargetPathProvider` 又各多一个构造函数重载，`PresentationAssembly` 是
  目前唯一的生产装配入口，多重载之间的选择只在这一处发生，尚未出现需要同时维护多套装配路径的
  场景；但重载数量本身随每次纯加法新增持续增长，是这套 ABI 纪律的已知、可接受的维护面。

## 备选方案与为什么不选

- **存活状态按生命值资源池是否 `<= 0` 在表现层判断**：能省去新增 `player.alive`/`target.alive`
  路径与两个 Provider 构造依赖，直接复用既有 `power` 子路径查询即可；但如决策 3 所述，生命值降到
  0 与规则层真正判定死亡（`IsAlive` 被置为 `false`）不保证同一拍同步，表现层另起一套阈值判断会
  与框架自身的死亡语义产生偏差窗口，且要求接入方知道"哪个资源池是生命值"这一游戏专属信息（框架
  本身不硬编码某个资源池类型代表生命值）。故不选。
- **普通攻击状态直接以字符串形式暴露在 `HudViewModel` 公开属性上（不做枚举转换）**：能省去
  `AutoAttackStateNames`/`AutoAttackState` 属性类型上的一次转换，但字符串比较不受类型系统约束，
  接入方拼错字面量编译期不会报错，只会在运行时悄悄判断失败——与 ADR-0060 光环极性字段否决同一
  方案的理由完全一致。故不选，`HudViewModel` 层保持枚举类型，只在路径查询协议这一层做文本转换。

## 魔兽世界的对应做法

对应魔兽世界客户端普通攻击按钮的"未开启/已开启待索敌/已开启攻击中"三态图标与目标框死亡时切换
灰度遮罩的通用展示惯例，本篇只补齐数据出口，不涉及具体图标/遮罩呈现细节（呈现细节归游戏，见 13
第 5 节"框架只给状态，呈现归游戏"）。
