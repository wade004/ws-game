# ADR-0044 gobj 对话打开回调新增交互者身份透传路径

状态：已拍板 2026-09-20

## 背景

消费方反馈（复审报告"反馈 6"，`ws-game-wow` 2026-09-20）指出：载体层 gobj 模块把交互分发到对话
系统的回调契约，签名只有"交互发起者 id + 对话动作引用 id"两个参数，不携带触发本次交互的物件
实例自身身份。玩法层对话系统打开会话（gossip）时需要三元组"发起者 id、交互对象 id、菜单 id"，
其中"交互对象 id"在后续会话动作里会被下游当作一个真实、稳定的身份使用——例如"打开商店"这类
动作在未显式指定商店引用时，约定按"当前交互对象自身"推断该由哪个商店接待。

现有装配根实现拿不到这个身份，只能用"对话动作引用 id"（本质是菜单的 id，可能被多个不同的物件
实例共用同一份菜单）顶替。这一权宜做法本身已经在框架自己的装配代码判断记录里被明确记录为"契约
缺口"，不是外部误判：该权宜实现会让"按当前交互对象推断"这一下游能力实际拿到错误的推断依据（
拿到的是菜单 id，不是真正被交互的那个物件）。补一条 creature 原生交互路径（另案讨论，暂不在本
决策范围）不能替代本决策——即便未来提供了原生路径，"把非生物物件包装成可对话交互对象"这条现有
路径仍会长期或过渡期存在，其契约缺口需要独立修复。

约束：本层对外公开的委托契约只允许新增，不允许修改既有公开签名的参数列表（既有签名的调用方
遍布装配根与既有测试，破坏性变更会波及全部既有集成点且违反本仓库"公开契约只增不减"的既定
基线）。

## 决策

1. **新增一个携带交互对象身份的委托类型，与既有委托并存，不修改既有委托签名**：既有委托
   （"发起者 id、对话动作引用 id"两参数）签名原样保留，继续可用。新增一个委托类型，在既有两个
   参数之外追加第三个参数——触发本次交互的物件实例自身 id；载体层的口味配置对象新增一个可选
   属性持有这个新委托的实例，与既有委托属性并列，互不冲突。

2. **物件宿主优先调用新回调，未设置时退回旧回调，两者都未设置时行为不变**：分发点在两个属性都
   非空时只调用新回调（不重复调用旧回调），只设置了旧回调时调用旧回调，两者都未设置时保持此前
   既有的"记一条诊断、交互本身判定为无动作"的降级语义——本决策不改变任何未升级调用方的可观测
   行为。

3. **装配根改接新回调，交互对象身份改传物件实例自身 id，不再用对话动作引用 id 顶替**：真正的
   生产装配入口（框架自带的组合根参考实现）改为设置新回调，把"当前交互对象"参数传物件实例自身
   的稳定 id，而不是此前顶替用的对话动作引用 id。装配代码里此前明确写着"契约缺口"的判断记录
   随之更新为指向本决策，说明缺口已根治、不再是待办。

4. **旧委托的语义边界收窄为"调用方明确不需要/无法提供交互者身份"**：本决策不废弃旧委托（仍是
   合法的公开契约），但其适用场景从"唯一路径"收窄为"调用方确实不需要身份透传"这一较窄场景（如
   最小化测试替身、身份对下游确实无意义的场合）。这一语义边界写入对应模块的判断记录，不只是
   代码注释里的一句话，避免今后有新调用方误把旧委托当成默认推荐路径。

## 后果

### 正面

- 消费方指出的下游能力（如"打开商店"类动作按当前交互对象推断具体商店）从此能拿到真实、稳定的
  交互对象身份，不再受"多个物件实例共用同一份菜单时互相顶替出错误结果"的影响。
- 新旧委托并存、优先级明确、降级语义不变，公开契约只做加法，不需要改动任何既有调用方即可保持
  行为完全一致；已升级到新回调的调用方与未升级的调用方可以并存于同一个版本。
- 契约缺口从"代码注释里的自我承认"变成"有对应决策记录、已在装配根根治"的已关闭状态，减少同一
  缺口被外部反馈重复发现的概率。

### 负面

- 载体层的对话打开回调从此存在两个委托类型，调用方（尤其是新接入的具体游戏）需要知道优先用
  哪一个、旧的什么时候还有意义，短期增加一点认知成本；已在相关模块判断记录里写清语义边界与
  优先级规则，缓解该成本。
- 若未来同一层还有其它回调契约暴露出类似"发起者身份够用、被交互对象身份不够用"的缺口（本决策
  只根治了对话打开这一个回调），需要重复走一遍"新增委托类型 + 新增可选属性 + 优先级"这套模式，
  本决策不引入一个通用的、一次性解决"所有回调都补身份参数"的机制——评估后认为为一个目前只有
  一处实例的问题预先设计通用机制，收益不确定但复杂度是确定的，故按需逐个根治更合适。

## 备选方案与为什么不选

- **直接在既有委托签名上追加第三个参数**：技术上最直接，但会破坏既有公开委托的签名，波及全部
  既有装配代码与测试里对该委托类型的赋值/调用写法，且违反本仓库"公开契约只增不减"的硬性约束
  （既有签名的参数列表不允许变化）。故不选。
- **用一个携带默认行为的上下文对象类型替换现有的两个独立委托参数**：能一次性容纳未来可能追加的
  更多上下文字段，但本次要补的只是一个额外的身份字段，引入一个新的上下文类型意味着要同时改造
  委托本身的参数形状与全部既有调用点的写法，改动面明显大于"直接新增一个携带该字段的委托类型"，
  收益（面向假设中的未来扩展）不确定，成本（本次改动面）确定更高。故不选，把"是否需要一个通用
  上下文对象"这一判断留到确实出现第二处同类需求时再评估。
- **不改契约，装配根内部另开一张"当前正在处理哪个物件实例"的旁路查找表，交互分发前先查表**：
  物件宿主与装配根之间目前没有稳定的"当前调用属于哪一次交互"的跨调用状态可以依附，人为造一张
  这样的表是更脆弱的隐式耦合（容易在重入、异常路径下产生脏数据），不如让契约显式携带这个身份、
  由调用栈天然保证正确性。故不选。
- **只在文档里说明"交互对象身份目前不可靠"，不改代码**：否决——消费方已经指出这会让"按当前
  交互对象推断"这一下游能力实际不可用，属于框架自己承认的契约缺口，具备明确、低成本、不破坏
  兼容性的修复路径，没有理由只记录不修复。

## 魔兽世界的对应做法

无直接对应（这是本框架载体层与玩法层之间的一处内部契约扩展，修复的是框架自身装配代码里的一处
权宜实现，不对应魔兽世界的任何具体游戏系统设计）。
