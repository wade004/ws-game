# ADR-0024 字段登记表纳入动态键映射形态

状态：已拍板 2026-09-10

## 背景

消费方内容编辑器项目在数据驱动扫描全部登记表后（第三批反馈第 21 条），列出 18 个仍未按 ADR-0019 登记子结构、停留在元数据门禁白名单里的 `Object`/`Array` 字段，要求逐一确定结构、能登记的登记、确属不透明的写清理由。

复核这 18 个字段（及白名单原有条目）逐个核对运行时解析代码后，发现其中相当一部分（职业模板的基础属性 `arch.class.base_stats`、种族模板的属性修正 `arch.race.stat_mods`、生物模板的基础属性 `creature.template.base_stats`、等级曲线条目的成长量 `prog.level_curve.entries[].growth`、外形表的锚点定义 `display.map.anchor_points`/换装槽位默认网格 `display.map.default_slot_meshes`/材质参数 `display.map.material_params`、动画集合的剪辑映射 `display.anim_set.clips`、武器风格表的施法动作覆盖 `display.weapon_style.cast_anim_override`/命中特效覆盖 `display.weapon_style.impact_vfx_override`、遭遇阶段的循环覆盖 `encounter.def.phases[].ai_rotation_override`、AI 行为外壳的转移条件覆盖 `ai.behavior_profile.transitions`）共有的真实结构是同一种模式：**键本身不是固定清单，由内容动态给出；但每个键对应的值种类是固定的**——例如"属性 id → 数值"这样的映射，属性 id 集合随内容变化，但值恒为数值。

ADR-0019 给复合字段引入的子结构登记（`fields`/`item`/`variants`）都要求键在登记时已知：`fields` 是固定子字段清单，`variants` 是按判别字段分派到有限几种已知取值。这类"动态键映射"字段不属于以上任何一种，此前只能退回"存在且是对象"这一档最弱校验，停留在元数据门禁的白名单里，附带理由"Map 型对象，现有 `FieldSchema` 没有对应登记形态"。这不是这些字段本身不该有结构化登记的价值——恰恰相反，它们大多是内容作者常改字段（属性表、动作覆盖表尤其如此），编辑器如果能对键做补全、对值做校验，价值明显；缺口纯粹是登记记法表达力不够。

## 决策

1. **`FieldSchema` 对 `Object` 种类新增第四种可选子结构登记 `Map`**，与既有 `Fields`/`Variants` 互斥（一个 `Object` 字段的子结构登记在"固定键清单""按判别字段分派的变体""动态键映射"三者中至多选一），不新增字段种类，不改动既有构造函数（新增能力通过登记后追加的 `WithMap` 承载，同 `WithRange`/`WithGroup`/`WithUnit` 既有惯例，既有登记不调用 `WithMap` 时行为与登记前完全一致，属向后兼容的增量能力）：
   - 键约束三选一：引用某张已登记表的既有记录（等价于标量 `Reference` 字段的键版本）；引用某个域名（等价于标量 `Reference` 字段按域引用的键版本）；自由字符串（键不做任何存在性/格式检查，登记时须写明理由——同 `IdList` 字段 `WithFreeIds` 的既有惯例）。三者由值级不变量在构造入口即保证"恰好其一"，不像 `IdList` 的 `ReferenceTable`/`ReferenceDomain`/`FreeIds` 三个独立属性那样允许"都不设"这一非法中间态残留到事后检查才发现——这是相对 `IdList` 既有模式的一处有意简化，见后文"备选方案"。
   - 值登记：一条完整的字段登记（与既有子字段完全同构，可以是标量、引用，也可以再递归嵌套 `Object`/`Array`/`Map`），描述每个键对应值的种类、范围、子结构。
2. **登记与校验同源，加载期统一处理**：已登记 `Map` 的字段，`DataRegistry` 在字段级校验阶段对该字段的每个已出现的键与值递归检查——键按登记的键约束并入"引用完整性"检查项（与既有标量 `Reference`/`IdList` 字段共用同一套判定逻辑，只是检查主体从"字段值"换成"字段的每个键"，不新增平行的检查实现）；值按登记的值结构递归复用既有检查项（必填、类型、枚举、引用、范围、表达式可解析等）。问题定位复用 ADR-0019 已有的路径记法并扩展一种新写法：`字段路径[键]`（如 `base_stats[stat.strength]`），键本身校验失败同样用这个路径定位；`Map` 字段没有"已知键清单"，不做 ADR-0019 的"多余子字段"检查，凡满足键约束的键都是合法键。
3. **元数据门禁新增自洽检查**：`Map` 只能登记在 `Object` 字段上（登记在其它字段种类上判定为登记自洽问题）；`Map` 不得与 `Fields`/`Variants` 同时登记在同一字段上。两项检查均刻意不在登记（`WithMap`）挂载时做运行期检查，而是留给元数据门禁事后批量枚举——同 ADR-0021 `WithRange` 判断记录"让登记在错误种类字段上的错误停留在可枚举的软失败，而不是启动路径上的一次性异常"这条既有风格。
4. **导出给内容工具**：已登记 `Map` 的顶层字段，随其它字段元信息一并批量导出键约束（引用哪张表/哪个域/或自由字符串及理由）与值的种类，供内容编辑器为这类字段提供键补全与值校验，不必退化为不透明的 JSON 子编辑。
5. **第二批登记范围**：对第三批反馈第 21 条列出的 18 个字段逐一核对运行时解析代码后分流——`arch.class.base_stats`/`arch.race.stat_mods`/`creature.template.base_stats`/`prog.level_curve.entries[].growth`（键均引用属性定义表、值为数值）、`display.map.anchor_points`/`display.map.default_slot_meshes`/`display.map.material_params`、`display.anim_set.clips`、`display.weapon_style.cast_anim_override`/`display.weapon_style.impact_vfx_override`、`encounter.def.phases[].ai_rotation_override`、`ai.behavior_profile.transitions` 共 12 个字段改用 `Map` 登记；另有一个字段（事件词汇登记表的携带字段名清单 `found.event_catalog.fields`）核实后发现其真实形状是"数组元素类型固定为字符串"，与"动态键映射"无关，直接用既有 `Array.Item` 登记即可，不需要 `Map`；其余 5 个字段（天赋树节点的效果授予 `arch.talent_tree.nodes[].grants`、物件模板的触发范围 `gobj.template.type_data.trigger_shape`、世界状态标志的合法取值 `world.flag_schema.allowed_values`、对话动作参数的联合类型取值 `dialog.gossip_menu.options[].actions[]{kind=set_flag}.params`、UI 布局定义的引擎相关参数 `ui_layout_definition.fields`）复核后确认仍不属于"动态键映射"——分别是无解析代码可依据的透传字段、元素类型随判别字段动态变化的联合类型、单键值为标量联合类型、刻意保持引擎无关的自由扩展位，`Map` 形态解决不了这几类缺口，维持元数据门禁白名单并更新理由说明与 `Map` 扩展的关系。元数据门禁白名单条目数由 20 条降至 7 条。

## 后果

### 正面
- 内容作者常改的一批"属性表""动作覆盖表"字段第一次获得加载期的键/值校验，键填错（如属性 id 拼写错误）、值类型不对能在加载期被拦下，不再退化为运行期静默忽略或不易察觉的行为异常。
- 内容编辑器可为这类字段提供键补全（按登记的键约束枚举候选）与值输入校验，不必再退化为不透明的 JSON 子编辑。
- 元数据门禁白名单从 20 条收敛到 7 条，剩余条目都是真正意义上"当前登记记法表达不了"或"刻意保持不透明"的字段，白名单的信号价值更高。

### 负面
- `Map` 与 `Fields`/`Variants` 是三个刻意设计为互斥的可选子结构，登记时选错形态（如把本该是固定键清单的字段误登记成 `Map`）不会被构造函数拒绝，需要依赖元数据门禁与逐字段核对运行时解析代码这两道既有防线，与 ADR-0019/0021 已知的同类风险一致，不是本决策独有的新增风险面，但仍是需要持续注意的一点。
- 第二批登记涉及多个模块，是一次性的跨模块工作量，且要与运行时解析代码逐字段核对（键的格式要求、值是否允许省略等），核对遗漏的风险与 ADR-0019 首批登记时相同，已按同一纪律（以运行时解析代码为唯一依据）逐字段核对并补充/更新各模块的 coverage 测试。
- 已有内容数据里，若 `Map` 字段的键此前从未受任何存在性检查（如引用键约束下键本该存在但内容里写错了），会从"能加载"变成"加载期阻断"——已核对现有示例数据与游戏模板数据集，不受影响；后续内容若出现类似问题，改法是修数据而不是放宽登记。

## 备选方案与为什么不选

- **保持现状，`Map` 型字段维持"存在且是对象"，全部留在白名单**：正是本决策要解决的问题本身——这些字段大多是内容作者常改字段，长期停留在"退化为 JSON 子编辑"的状态，与 ADR-0019 决策"复合字段的结构在登记、校验、文档三处只有一份来源"的既有方向相悖。
- **给 `IdList` 一样，`Map` 的键约束也做成三个各自独立的可设属性（`KeyReferenceTable`/`KeyReferenceDomain`/`FreeKeys`），允许"都不设"再靠元数据门禁补一道遗漏检查**：`IdList` 保留这个历史形态是因为它比 `Map` 更早引入、且改动它的独立设置方式属于另一件事（不在本决策范围）；`Map` 是全新登记形态，没有历史包袱，选择在值级构造入口就保证"三选一"，比"允许非法中间态、靠另一道检查事后发现"更简单、也少一条门禁检查项，是本决策认为更优的起点设计，不代表既有 `IdList` 形态是错的。
- **`Map` 的值也允许是"任意标量联合类型"，一并解决第三批反馈里提到的另一处联合类型缺口（一个对话动作参数字段）**：调研后确认这是两个不相关的缺口——动态键映射解决的是"键的形状"问题，联合类型解决的是"单个固定键的值可以是几种不同标量类型之一"问题，两者的登记形态设计目标不同，硬凑到一起会让 `Map` 的语义变复杂（"值可以是联合类型"这件事与"键是否动态"完全正交）。该缺口继续留在白名单，作为独立缺口留给未来评估是否单独扩展一种"标量联合类型"登记形态。
- **改成给 `Object`/`Array` 都换成通用的外部 schema 描述格式，一次性覆盖 `Map`、联合类型等所有已知缺口**：与 ADR-0019 否决"用外部通用 schema 格式"的理由相同——会与既有登记表机制形成两套来源，校验器要再实现一套解析，不如在既有登记结构上做最小必要扩展。

## 魔兽世界的对应做法

魔兽世界客户端/服务端的 `SpellEffectN`/`SpellEffectMiscValueN` 一类固定列表达效果参数，遇到"键值对数量不固定"的场景（如天赋加成对多个技能生效）通常靠额外的关联表或运行时按命名约定枚举一批固定列（`EffectN` 系列列到某个上限为止）绕过，本质仍是"用固定列模拟动态映射"，工具与文档只能各自维护一份"这批列实际上表达的是一个映射"的约定，容易与实现出现单边漂移。本架构选择在登记表层面直接表达"这是一个动态键映射"这一结构事实本身，让校验器与内容工具从登记里得到权威结构信息，不需要靠命名约定或额外文档猜测。
