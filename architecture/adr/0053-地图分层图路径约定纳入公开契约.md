# ADR-0053 地图分层图路径约定纳入公开契约

状态：已拍板 2026-09-21

## 背景

消费方反馈（内容编辑器项目，第 75 条）：`资源引用标识 → 资产相对路径`这一类约定，[ADR-0025](0025-资源引用标识到资产相对路径的约定纳入公开契约.md)、[ADR-0037](0037-资源引用路径推导契约扩展到vfx-sfx-model-anim_set.md)、[ADR-0038](0038-资源引用类别前缀唯一决定路径空间.md) 三份 ADR 已陆续把 `sprite`/`icon`/`vfx`/`sfx`/`sprite_anim`/`paperdoll`/`anim`/`model` 八个类别前缀收口为公开静态方法（框架契约面一处、内容导入工具链一处，两侧各自独立实现、靠同一组样例互相对照），唯独地图分层图（`world.map` 表引用的 `ground`/`overlay`/`decal`/`nav_hint` 四层贴图）这一类不在其中——它的相对路径格式（形如 `maps/<map>/<layer>.png`）目前唯一的出处是内容导入工具地图子命令自身的一段说明性文字，从未以可调用的公开函数形式暴露。框架契约面完全没有与之对应的方法；消费方（内容编辑器）只能照抄这段说明性文字自行拼接路径。

这与 ADR-0025 背景一节指出的问题是同一根因的又一处表现：约定散落在说明性文字里而不是可调用的契约面，规则一旦调整（目录层级、扩展名、分隔符），消费方从公开契约的变更信号（新增/废弃方法、编译期报错）里得不到任何提示，只能等运行期路径对不上再排查。地图分层图这一类此前遗漏，不是设计上刻意排除——ADR-0036 收口了这组分层图的坐标换算约定（像素/世界坐标、`image_transform` 字段），但没有一并收口它们的路径约定本身；ADR-0037/0038 收口范围逐一列出的是 vfx/sfx/model/anim_set 几类引用字段，同样没有覆盖地图分层图，属于收口序列里的一个遗留缺口。

核实现行实现（内容导入工具地图子命令）后确认：地图分层图目录路径由"资产根目录 + 数据集段 + `maps` + 地图名"四段拼接而成，各层文件再在此目录下按固定文件名（`ground.png`/`overlay.png`/`decal.png`/`nav_hint.png`）落地；地图名即 `world.map` 行 `id` 字段去掉 `world.` 类别前缀后的剩余部分（与 ADR-0025 确立的"去掉类别前缀、点号换下划线"规则同构，只是此前从未以这一规则的名义表达出来）。这条格式与既有八个类别前缀方法所在的路径空间完全同构（资产根相对、可与 `assets/<dataset>/` 拼接后做文件系统存在性检查），只是此前从未纳入同一套公开契约。

## 决策

1. **新增地图分层图路径约定的公开方法，收口进既有资源引用路径推导契约面**：新增 `MapDirectory`（地图目录）与 `MapGroundFile`/`MapOverlayFile`/`MapDecalFile`/`MapNavHintFile`（四个固定层各自的文件路径）共五个方法，与 ADR-0025/ADR-0037/ADR-0038 已收口的八个类别前缀方法同一路径空间、同一推导规则（去掉类别前缀、点号换下划线）、同一形态（签名风格、参数类型、返回值语义、非法输入处理口径均与既有方法一致，不另起一套）。四个层名是一组固定取值，用四个独立方法各自表达，不由调用方传裸字符串拼接层名——与既有契约面"每类资源引用对应一个专属方法"的既有惯例一致，不新增枚举或额外的分派参数。

2. **地图目录/文件路径的推导对象是 `world.map` 行的 `id`（形如 `world.<map>`），不是地图名裸字符串**：与 `SpriteSetDirectory`/`IconFile` 等既有方法一致，均以登记表行的资源引用标识（带类别前缀）为输入，而不是已经拆出来的裸名称——保持契约面输入形状统一，消费方不需要为地图分层图单独记一套"这里要传拆过前缀的名字"的例外规则。

3. **内容导入工具链同步提供独立实现的等价函数，工具本身改为调用它，不再自行拼接**：地图子命令与既有 vfx/sfx/sprite 等子命令一样，改为调用同一条规则的独立语言实现（两种运行环境之间不共享同一份源码，只能各自实现、互相对照，沿用 ADR-0025 决策 3 确立的既有做法）；地图子命令模块自身的说明性文字不再重复给出具体路径格式字符串，只指向这组共享函数，避免格式字符串本身与权威实现出现第二处、可能漂移的拷贝。

4. **规则本身不变，只是收口来源**：本次不改变任何已产出地图资产的相对路径——新方法的输出与内容导入工具地图子命令改动前的输出逐字节一致（改动前后对照测试覆盖，见下方"验收标准"），不需要重新生成/迁移任何已有地图资产或数据行。

5. **变更约定须走 ADR**：往后如需调整地图分层图路径格式本身（不是新增第五个并存的层，是修改既有四层或目录的推导规则），须新增 ADR 说明变更理由与迁移影响，不得在具体实现里私自调整——与 ADR-0025 决策 4 同一约束，理由相同：唯一实现一旦被绕开就回到本 ADR 要解决的漂移问题。

6. **不扩大收口范围**：`world.map` 行的 `scene_ref`/`nav_ref` 两个字段（分别固定为 `scene.<map>`/`nav.<map>`）对应的是引擎适配层内部逻辑资源路径空间（同 ADR-0038 决策 5 的 `EngineLogicalPath` 分类），本工具不生成、不落地这两类资源本身（导航与碰撞由引擎适配层侧手工绘制），其推导规则是否需要收口为公开方法留待出现真实消费方需求时另行评估，本次不预先处理。

## 后果

### 正面

- 地图分层图与既有八个类别前缀补齐为一套统一收口的资源引用路径契约面，消费方（内容编辑器）第一次拥有一个权威的公开来源，不再需要照抄工具自身的说明性文字反推路径格式。
- 内容导入工具地图子命令与其它资源类别子命令处理方式对齐（改为调用共享函数），格式字符串不再以说明性文字的形式散落在文档字符串里，规则调整会体现为契约面的方法签名/行为变化，能被两侧各自的测试与消费方的集成过程捕获。
- 为往后识别、处理同类"资源引用路径约定遗留在收口序列之外"的缺口提供了同一处理范式（对照 ADR-0025/0037/0038 已确立的模式）。

### 负面

- 新方法的推导对象是登记表行 id（带类别前缀），若地图名本身包含点号（当前不存在这类数据，也不是任何工具会产出的形状），推导结果与内容导入工具改动前"直接拼接地图名原始字符串"的行为会出现差异——已在实现的判断记录里显式记录这一已知边界，不影响任何现有数据。
- 公开这组方法后，往后调整地图分层图路径格式（即使只是很小的调整）都成为契约变更，需要按决策 5 走 ADR，多了一道流程成本。

## 备选方案与为什么不选

- **维持现状，只把地图子命令自身的说明性文字写得更精确**：治标不治本——消费方仍然只能照抄文字反推，规则调整时文字与实现仍需两处同步修改，不能提供可被编译期/集成过程捕获的契约信号，与 ADR-0025 背景一节否决同类方案的理由相同。
- **地图分层图路径方法直接接收裸地图名字符串，不要求传登记表行 id**：这会让地图分层图这一类的契约输入形状与既有八个类别前缀方法（均接收带类别前缀的资源引用标识）不一致，消费方需要为地图分层图单独记住一条"这里不用整行 id、要先自己拆前缀"的例外规则，增加认知负担；本 ADR 决策 2 选择保持形状统一。
- **四个层名合并为一个方法、层名作为字符串或枚举参数传入**：既有八类前缀均是"一个类别一个专属方法"，没有先例用字符串/枚举参数在方法内部再分派；引入这一新形态只对地图这一类适用，反而制造了两套不同的契约表达习惯，不如四个层各自一个方法与既有惯例保持一致。
