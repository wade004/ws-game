# ADR-0029 迁移链串接与整表迁移纳入公开契约

状态：已拍板 2026-09-13

## 背景

消费方反馈（内容编辑器项目，2026-09-13，见 `architecture/落地计划/消费方反馈-2026-09-13-编辑器-第40条.md` 第 40 条）：数据注册表加载一张 `schema_version` 落后的表时，内部把"从旧版本串出迁移链"这一步实现为一个私有方法，只服务于加载期的内存态构造——迁移结果不写回磁盘、不写信封 `migrated_from`，框架没有提供任何公开的"迁移链串接"或"批量迁移一批行并落盘"入口。核实框架全部已登记表当时迁移链均为空、示例数据集也没有任何一张表的 `schema_version` 真的落后过一版——这两个事实合在一起意味着"迁移链串接"这条逻辑从未被真实数据练习过，只有加载期那一条内部调用路径覆盖到。

这与 ADR-0020（表达式词法器纳入公开契约）面对的是同一类问题：内容工具（编辑器"执行迁移并写回磁盘"这一功能）需要的能力，框架内部已经有唯一实现，只是没有对外暴露——消费方被迫照着 3 节"schema 版本与迁移"的文字描述与框架源码自行复刻"取第一条 `FromVersion` 等于当前版本的环节、直到精确到达目标版本"这条链选取语义，且因为没有真实迁移用例可以拿来做端到端比对，复刻实现是否与框架行为一致只能靠人工读源码验证——框架未来若调整这条算法细节（链选取策略、版本比较边界），复刻实现不会自动感知，只能在两边逐渐漂移到产生实际问题时才被发现。"整表迁移并写回磁盘"这一步（内容工具改信封 `schema_version`、生成/更新 `migrated_from`）框架此前完全没有对应实现——DataRegistry 从不写文件，这段逻辑此前只存在于消费方自己的实现里，没有框架权威实现可比对。

## 决策

1. **迁移链串接纳入公开契约**：数据注册表内部原本私有的"从起始版本串到目标版本"实现，改为一个公开、单一来源的静态入口——语义与原私有实现逐字一致：从起始版本起，每一步取该表登记的迁移环节集合中第一条"起点等于当前版本"的环节，直到精确到达目标版本；途中缺少衔接某个版本的环节、或某一步越过目标版本，均判定为"缺少迁移环节"；起始版本等于目标版本时是空链，不是"缺少迁移环节"。数据注册表加载期的既有调用点改为委托这个公开入口，不再维护第二份实现，报错文案与既有行为不变。
2. **单行迁移纳入公开契约**：按迁移链顺序对单条记录依次应用迁移这一步，同样收口为公开入口，与加载期行内循环逐字一致。
3. **新增整表迁移的权威实现**：框架新增一个"信封级"入口——输入符合 04 号文档"文件顶层信封"约定的完整表内容（表名、信封版本号、记录数组），若信封版本号已是当前版本则原样放行，否则调用决策 1/2 的迁移链与单行迁移，产出一份新的信封内容：版本号改为当前版本，`migrated_from` 写入"最早的原始版本号"（若输入信封已带合法 `migrated_from`，说明此前迁移过一次，保留那个更早的值，不用本次迁移前的版本号覆盖——否则连续多次增量迁移会逐次丢失最早的原始版本，"记录原始版本号，便于排查"这一目的落空），信封其余键与记录内容按决策 2 迁移，输入本身不被修改。这是内容工具"执行迁移并写回磁盘"应当调用的唯一入口，不自行拼装决策 1/2 再手写信封改写逻辑。
4. **`migrated_from` 澄清为信封级（表级统一）可选键**：04 号文档 3 节字段表列出的 `migrated_from` 与 `schema_version` 同级，不是逐行字段——与 `schema_version` 本身"表级统一版本号"这条既有结论对齐（同一张表内全部记录共享同一个版本号，`migrated_from` 同理）。数据注册表加载期新增对这个可选信封键的形状校验：若出现，必须是小于当前信封版本号的正整数，否则判定为阻断错误；合法时加载期不据此做任何额外判断（不参与迁移触发条件，触发迁移只看版本号是否落后），只是放行一个此前从未被显式承认、也未被拒绝过的信封键。
5. **示例数据集新增一张迁移链演示表**：框架此前全部登记表的迁移链均为空，示例数据也没有任何"真实经历过迁移"的用例——消费方只能自己合成一张测试专用表结构来验证复刻实现。框架新增一张没有任何运行时消费方、专门用于演示迁移链的登记表（1→2 一步迁移，把某个字段改名），配一份版本号故意落后一版的示例数据文件，供内容工具用真实数据端到端验证"迁移链串接 + 整表迁移"复刻实现是否与框架行为一致，不必再自行合成。

## 后果

### 正面
- 内容工具/编辑器获得一个权威、与数据注册表加载期逐字同源的迁移链构造与整表迁移实现，不再需要照着文字描述与源码另写一套容易漂移的复刻逻辑；框架未来调整链选取算法细节时，消费方通过调用同一份实现自动感知，不会静默漂移到产生实际问题才被发现。
- "整表迁移并写回磁盘"第一次有了框架权威实现，内容工具不必自己设计"如何正确处理已带 `migrated_from` 的信封"这类此前没有先例可循的细节（如多次增量迁移时应保留最早原始版本、不是覆盖为上一次迁移前的版本）。
- 示例数据集第一次有了真实的"迁移链生效"用例，内容工具/编辑器可以用它做端到端验证，不必自行合成测试专用表结构。

### 负面
- 迁移链串接、单行迁移、整表迁移三个入口一旦公开，即成为公开契约的一部分，后续对链选取算法本身的任何调整都需要按语义化版本规则评估是否构成破坏性变更；此前这份自由度完全在框架内部，没有外部约束。
- 加载期新增对信封 `migrated_from` 键的形状校验，是一条新的阻断条件——此前任何写了非法 `migrated_from`（如字符串、超出范围的整数）的数据文件都会被静默接受，现在会报错；核实当前框架全部已登记表的示例/框架数据文件均不含这个键，不受影响，这条新校验只影响未来新写入该键的文件。
- 新增的迁移链演示表没有任何运行时消费方，纯粹是一张文档/工具验证用的表——需要在 schema 注释、`data/README.md`、04 号文档总索引里都明确标注"仅供迁移链演示，无运行时消费方"，避免被误当作真实游戏内容的一部分去消费或扩展。

## 备选方案与为什么不选

- **维持现状，内容工具自行复刻迁移链串接逻辑**：与决策面对的问题本身矛盾——本 ADR 存在的理由就是消费方反馈已经证明这条路径会导致复刻实现与框架行为逐渐漂移，且没有真实数据可以验证复刻是否正确。
- **只公开迁移链构造，不提供整表迁移入口**：迁移链构造只解决"这张表的迁移环节是否齐全、按什么顺序应用"这一半问题，"改写信封版本号、正确处理 `migrated_from`（尤其是多次增量迁移时保留最早原始版本这条细节）"这另一半此前完全没有框架实现可参考，消费方反馈明确点出这一段逻辑也是编辑器自行实现、没有权威实现可比对——只解决一半问题不能根治反馈里描述的困境。
- **`migrated_from` 改为逐行字段（每条记录各自记录是否迁移过）**：与 `schema_version` 本身"表级统一版本号"这条已拍板结论不一致（04 号文档 3 节开篇即"每张表携带 `schema_version`...同一张表内全部记录共享同一个版本号"），迁移是整表一次性发生的操作，不存在"同一个文件里一部分记录迁移过、一部分没有"这种中间态，逐行记录只会引入不必要的冗余与不一致的可能性。
- **迁移链演示表放进框架级数据目录（随分发包发给游戏）而不是示例数据目录**：这张表没有任何运行时消费方，不满足"该表的行由框架代码引用或生成"这条框架级数据表判定规则（见 `data/README.md`"两类目录"一节），放进框架级目录会让游戏侧收到一张自己用不上、也不该使用的表，示例数据目录（不随主分发包发布，只随可选的样例包）是更准确的归属。
