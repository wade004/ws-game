# ADR-0001 万物皆法术

状态：已拍板 2026-09-04

## 背景

一款持续运营多年的游戏，其"让世界发生变化"的动作类型会不断膨胀：装备特效、天赋、坐骑、开门开箱、采集、传送、Boss 机制……如果每一类都各自实现一套专用代码，代码库会迅速分裂成大量互不复用的特殊情况，新增一类新动作就需要新增一套子系统，架构目标"新内容不改代码"无法达成。需要一个统一的抽象，把"世界如何被改变"这件事收拢成同一种数据结构。

## 决策

任何"让世界发生变化"的动作都建模为 Skill（效果 Effect + 光环 Aura + 触发 Proc/SpellMod 的组合），不为单个内容写专用代码：

- 装备特效 = 授予一个技能 + 挂一个被动光环。
- 天赋 = 被动光环内部携带的 SpellMod（对其他技能的参数进行覆盖/加成）。
- 坐骑 = 一个提供移动速度加成的光环 + 一套外形层（DisplayInfo，见 ADR-0006）。
- 开门、开箱、采集、传送等物件交互 = GameObject 的 `on_use` 指向一个 Skill 或一个对话动作。
- Boss 机制 = 遭遇（Encounter）阶段配合触发器（Trigger）与 Skill 的组合。

具体结构定义见 [../06_规则层_属性技能战斗AI.md](../06_规则层_属性技能战斗AI.md)（Skill 系统全结构）与 [../07_载体层_物品生物物件.md](../07_载体层_物品生物物件.md)（GameObject on_use）。

## 后果

### 正面
- 内容团队新增几乎任何"世界变化类"内容都只需要填数据，不需要新增代码路径，直接支撑架构目标"新内容 = 加数据不改运行时"。
- 效果结算、光环叠加、触发链路只需要实现和测试一套通用管线，而不是 N 套专用逻辑各自维护。
- 战斗日志、反馈绑定（见 [../09_表现层.md](../09_表现层.md)）可以统一挂在 Skill 结算事件上，不必为每类内容单独对接表现。

### 负面
- 抽象层级更高，编写新数据的人需要理解"效果+光环+触发"的组合方式才能表达意图，学习成本高于直接写专用代码。
- 某些天然不像"施法"的交互（如纯粹的场景摆件开关）被迫套进 Skill/GameObject.on_use 的框架，描述上略显绕弯，但换来的是审批与代码复用的一致性。
- 若某类内容确实无法用现有 Skill 原语表达（效果类型不够用），需要走新增原语审批（ADR-0010），不能绕过去写专用代码，短期内可能造成排期压力。

## 备选方案与为什么不选

- **每类内容各自实现专用系统**（如单独的"坐骑系统""天赋系统""机关系统"）：短期实现简单直接，但长期导致系统数量随内容类型线性增长，且各系统各自处理光环叠加、事件广播、存档等重复逻辑，维护成本高，与"骨架承载所有游戏"的目标冲突。
- **只用事件脚本、不引入 Skill 抽象**：把一切都写成"触发条件 + 任意脚本"，灵活度最高，但脚本内容不受数据校验约束，无法做引用完整性检查，也难以做统一的战斗日志与反馈绑定，牺牲了可测试性与可审计性。

## 魔兽世界的对应做法

魔兽世界的绝大多数游戏内容确实都以 Spell 为最终落点：装备的"使用效果"和"套装效果"是挂 Aura 的 Spell；天赋是修改其他 Spell 参数的 SpellMod；载具/坐骑是携带光环与模型替换的 Spell；几乎所有交互式 GameObject（宝箱、传送门、任务物件）的 `data` 字段最终也指向 Spell 或脚本触发一次 CastSpell。本 ADR 是对这一设计哲学的直接借鉴与固化。
