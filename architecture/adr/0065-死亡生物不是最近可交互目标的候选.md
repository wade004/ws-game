# ADR-0065 死亡生物不是最近可交互目标的候选

状态：已拍板 2026-09-22

## 背景

消费方反馈（游戏接入方第七批第 1 条，基于冻结发布提交核实）：ADR-0062 新增的"最近可交互目标"
查询——`IInteractionTargetRegistry.TryFindNearest` 的默认实现只按运行期实体的类别标识
（场景物件/生物/地面掉落物三个既有的字符串常量）分类候选，不看生物类实体当前是否存活。框架在
单位死亡时不会自动销毁其运行期实体（死亡是逻辑状态，不是生命周期状态——尸体继续以
`alive = false` 的形态存在于世界模拟中，直到刷新表/复活策略另行处理），而生物死亡结算生成的
地面掉落物又固定生成在死亡位置——尸体与它自己的战利品因此同坐标、等距，等距候选取运行期实体
标识序数最小者，生物类前缀恒小于掉落物类前缀，查询因此恒返回尸体。接入方的实际表现是：每次
击杀后按交互键都打在尸体上，捡不到战利品；尸体比场景中其它存活单位更近时，还会连带挡住那些
本该被命中的单位。这是真实玩法路径不可用，不是测试环境的偶发问题。

独立核实候选生物类实体的原生"交互"分流（生物原生交互路径，见既有决策）现状：该分流（意图
分发 → 交互宿主）在派发交互请求前只核对交互发起者是否存在、交互目标是否已登记为生物运行期
实例、距离是否在交互范围内，不核对目标是否存活——只要死亡生物的运行期实体还留在世界模拟中
（未被销毁），直接对它发起交互请求仍会被受理并按既有规则处理（有对话配置则打开对话、无配置则
判定为"无可交互内容"）。这与本次要治理的"候选发现"是两层不同的问题：候选发现回答"附近有什么
可以按键互动"，分流回答"已知目标 id、发起交互请求会不会成功"。现有代码没有任何迹象表明分流对
死亡生物的宽松处理是有意为将来的尸体交互（例如拾荒/检查尸体）预留的口子——它单纯是从未考虑过
"目标已死亡"这一分支。但分流行为本身不在本次反馈复现的缺陷范围内（反馈复现的路径全部经"按键
交互最近目标"，从未直接对着一个已知死亡生物 id 发起交互），改动它没有对应的失败用例支撑，按
任务边界不在本次改动，留待需要真正处理死亡目标交互时再评估（见下"备选方案"倒数第二条）。

## 决策

1. **生物仅存活且有可交互内容时为候选（见 [ADR-0069](0069-最近可交互目标候选生物需有可交互内容.md)）**：
   `IInteractionTargetRegistry.TryFindNearest` 默认实现（`Core.Carriers.Assembly.InteractionTargetRegistry`）
   对生物类候选新增一条存活核对——只有当规则层权威口径判定该生物"存在且存活"时才进候选，与场景
   物件/地面掉落物同层但不接入这条判定（它们不是"单位"概念的实例，没有存活状态）。存活判定复用
   表现层补普通攻击状态与存活状态转发（`player.alive`/`target.alive`）同一权威口径——单位状态
   门面的"是否存在"×"是否存活"两个只读查询的合取，不读生命值资源池是否 `<= 0`；理由同该决策：
   资源池归零与规则层真正判定死亡（写入存活状态那一刻）不保证同一拍同步，另起一套阈值判断会
   制造与规则层结果不一致的时序窗口。

2. **不新增可选参数，不在候选结果类型上补存活标志**：候选的含义是"现在按交互键能成功交互的
   东西"，死亡生物按决策 1 不满足这个定义，就不应该出现在候选集合里——这不是"要不要展示存活
   信息"的展示层选择，是候选本身的定义收窄。给调用方开一个"是否排除死亡目标"的开关，只会让每
   个接入方都要记得主动打开它才能拿到正确行为，默认值不安全；不开则每个新接入方都要重新踩一遍
   本次反馈同样的坑。未来若有游戏确实需要"对准尸体做另一类交互"（例如拾荒、检查尸体），那是一
   个语义完全不同的新交互类别（交互对象是"死亡后留下的可处理内容"，不是"仍然存在的生物"），
   应该独立设计一条新的候选/分流，不应该通过给本查询"开洞"来兼容，见"备选方案"。

3. **候选判定所需的存活信息，走本层已经持有的依赖，不新增契约**：`InteractionTargetRegistry`
   所在的装配层级构造时已经接收单位状态门面（决策 1 提到的同一个只读契约）作为依赖——它原本就
   需要这个依赖来解析查询发起者自身的位置与存在性，只是此前从未把它用在候选筛选上。因此本次
   改动不新增任何构造参数、不新增依赖注入点、不产生新的公开签名——加固候选判定这件事发生在装配
   层级内部已有的依赖范围之内，不需要装配层级向更上层（玩法内容层）反向依赖来换取这份信息。

4. **表现层的"附近最近可交互目标"取值路径不需要单独改动**：它读的是同一个候选查询的结果，
   查询本身收窄之后自动生效，不需要表现层再单独核对一次目标是否存活。

## 后果

### 正面

- 接入方按交互键不再被尸体挡住——存活单位、地面掉落物都能被正确发现为候选，掉落物拾取这一最
  基础的击杀后交互路径第一次真正可用。
- 尸体比其它存活单位更近时不再遮挡后者，交互目标发现的结果与玩家实际能感知到的"这附近谁还活
  着、有什么能捡"保持一致。
- 改动完全落在候选筛选这一处已有实现内部，不新增契约、不新增可选参数、不产生任何公开签名变化，
  没有旧调用方需要跟着改。

### 负面

- 本决策只治理"候选发现"这一层。生物原生交互分流本身对已知目标 id、请求是否会被受理这一层的
  存活核对由 [ADR-0067](0067-生物原生交互分流拒绝死亡目标与死亡发起者.md) 补齐，不在本决策
  范围内。
- 死亡生物的交互能力就此完全从"最近目标发现"路径中消失，如果后续需要支持"对尸体做点什么"，
  需要另起一条新的候选/分流（见"备选方案"），不能通过放宽本次收窄的判定来实现——这是有意的
  设计取舍，不是遗留缺口。

## 备选方案与为什么不选

- **给 `TryFindNearest` 加一个"是否包含死亡生物"的可选参数，默认排除、可选纳入**：能不动
  "候选"这个概念的既有含义，但会把"死亡生物算不算候选"这个判断从框架转嫁给每一处调用点——
  绝大多数调用点（"附近能按键做什么"）根本不关心这个开关，加了也不会用；真正想要"尸体交互"
  的极少数场景，语义上根本不是"最近可交互目标里放宽一格"，而是完全不同的一类交互，用同一个
  参数表达不出"这具尸体能不能被拾荒"这种更丰富的判定（比如是否已经被拾荒过、拾荒是否需要特定
  身份）。故不选。
- **在 `InteractionTarget` 上补一个只读的存活标志，交给调用方自己决定要不要用它过滤**：这会让
  "候选"这个结果类型承担两种互相冲突的语义——一部分调用方拿它当"已经过滤好的可交互列表"直接
  用，另一部分调用方还要自己再判断一次是否要因为存活标志跳过——每个接入方各自实现一遍同样的
  过滤逻辑，恰恰是"最近可交互目标查询"这个统一入口最初想消灭的重复劳动。故不选。
- **顺带把生物原生交互分流也改成拒绝死亡目标**：能让"候选发现"与"分流受理"两层行为完全对齐，
  逻辑上更干净。但本次反馈复现的失败路径全程经"按键交互最近目标"，从未直接构造一个死亡生物 id
  发给分流，改动分流本身超出本次任务边界，故不在本决策内处理；见 ADR-0067（后续反馈提供了绕过
  候选查询、直连分流的真实路径后单独立项补齐）。
- **单独给尸体开一类"可拾荒/可检查"的交互候选，随本决策一并设计**：目前没有任何具体游戏提出
  这个需求，提前设计一套没有真实场景支撑的尸体交互模型（谁能拾荒、拾荒一次还是多次、与"最近
  可交互目标"是并列候选还是需要玩家先切换"交互模式"）大概率与后续真正出现该需求时的实际形状
  不符，届时还要再改一轮。故不选，留给真正有此需求的游戏接入时另行设计。

## 魔兽世界的对应做法

无直接对应（这是本框架"最近可交互目标"查询与生物死亡后运行期实体保留机制两者组合出的一处结构
性缺口修复，不对应魔兽世界任何具体游戏系统设计）。
