# ADR-0080 地图分层图接入运行期渲染

状态：已拍板 2026-09-23

## 背景

消费方反馈第二十一批（改进建议，非阻塞）：要把场景地面接进来时发现，基础架构没有任何"声明式铺地面"的
办法，只能自己在游戏侧手写图元、手算坐标/旋转/平铺比例才能把一张地图背景图摆到场景里。

核实结论：地图分层图这条契约链其实早就定好了，只是从未接上运行期，这一刀是接线，不是造新契约。

- 每张地图四层分层图（`ground`/`overlay`/`decal`/`nav_hint`）的磁盘路径推导规则已纳入公开契约
  （见对应 ADR），框架契约面与内容导入工具链两侧各自独立实现、互相对照，入参是地图行 id，四层文件名
  固定。这一条本次不改，也不在本次收口范围内。
- 四层的语义已定死：`ground`（地面层，必需）、`overlay`（前景遮挡层，必需，遮挡单位的近景建筑/树冠）、
  `decal`（装饰层，可选，不遮挡单位的贴花/痕迹）、`nav_hint`（导航标注参考图，供内容作者手绘导航数据
  时参考，不是可见内容本身）。
- 地图背景图片像素坐标 ↔ 世界坐标的换算参数（`world.map.image_transform`，可选字段）已经收口——`每
  世界单位对应的像素数`、`世界原点在图片中的像素坐标`、`图片宽高像素`（可选，声明后可算出世界坐标包围
  盒）均已有契约类型给出换算与包围盒计算。
- 表现层的层结构表（地面层/装饰层/前景遮挡层三个离散图层号常量）早已声明，但全仓库零引用——坑位预留
  着，从未有任何内容真正填进去过。
- 现状后果：样例地图产出的分层图只是孤儿资产，除一个存在性校验之外没有任何运行期加载/渲染路径消费
  它们；表现层的"地图/场景数据"这类资源种类此前也没有任何真正的消费方。

## 决策

1. **范围：`ground`/`overlay`/`decal` 三层接入渲染，分别落到表现层已声明的地面层/装饰层/前景遮挡层
   三个离散图层号**。`nav_hint` 不渲染——它是内容作者手绘导航数据的参考图，不是可见内容。

2. **摆放位置：世界矩形唯一由地图行已有的 `image_transform` 决定，不新增任何坐标/缩放/平铺/旋转字段，
   不给地图登记表加任何 schema 字段**。同一张地图的三层分层图像素对齐、共用同一个世界矩形，唯一真相
   源是 `image_transform` 既有的换算（含包围盒计算），不另写第二套算法。
   - 地图行没有声明 `image_transform`（该字段本就是可选字段）时：不渲染任何分层图，记一条诊断，不
     抛异常。
   - `image_transform` 声明了但未声明图片宽高像素（该子字段也是可选的）时：无法算出世界坐标包围盒，
     同样不渲染任何分层图、记一条诊断、不抛异常——与"未声明 `image_transform`"归入同一种"缺关键
     入参，无法界定要摆多大，索性不摆"的处理口径，不臆造第二套"只知道换算比例、不知道图多大时"的
     降级方案。

3. **契约扩展，纯加法**：
   - 资源加载入口的资源种类枚举新增一项，按地图行 id 整套加载该地图 `ground`/`overlay`/`decal` 三张
     分层图——不是"一层一个资源 id"：路径推导的入参本就是地图行 id，四层是固定文件名，不存在逐层的
     资源引用 id，不为此发明新的类别前缀。加载是否完成以地图行 id 本身为准。
   - 2D 渲染接口新增一对"地图分层图"能力：建一层（入参含地图 id、层别、世界矩形、离散图层号）与销毁
     一层，句柄采用与既有精灵/粒子句柄同一惯例的不透明只读结构体。两个新成员均为**默认接口方法**，
     默认实现不画任何东西、`createMapLayerInstance` 返回一个约定的"无效句柄"——ABI 只加法，既有的
     `IRenderer2D` 实现方（含测试替身）不改一行仍能编译、行为不变。层别用新增的枚举表达，只覆盖参与
     渲染的三层（不含 `nav_hint`）。
   - 遵守既有铁律：渲染实现只消费已加载完成的资源，遇到未加载/缺失的层用实现内建的可见占位并记诊断，
     不得隐式触发加载、不得抛异常——先发起加载、再等加载完成、再建层的顺序由表现层驱动方负责，渲染
     实现本身不越权触发加载。

4. **驱动方：表现层新增一个宿主组件，接入表现层组装根**。场景加载完成时（进入场景就绪状态那一刻）为
   当前地图建这三层，场景卸载/切图前销毁——不能出现"切走再切回，场景里堆出两套分层图"这种泄漏。表现
   层既有铁律不破：只读逻辑状态、不写回、不新增任何事件、只经引擎适配层接口绘制。

5. **明确不做**：
   - 不做按格拼贴、不做平铺重复、不做逐区域拼图、不做旋转——地图分层图这条既有约定就是"一张地图一套
     分层图"，本次只把它接上运行期，不扩大契约本身的形状。将来真需要按格图块，另开 ADR。
   - **不新增任何地形语义**（可通行性、移动消耗、地表类型一类判定）：可通行性归导航数据与导航系统，
     给分层图叠加第二个"这块地能不能走"的真相源必然与导航数据打架。分层图纯粹是可见内容，不参与任何
     游戏规则判定。
   - 不改动引擎场景资源这条既有的引擎自身场景资产加载通路，不改地图分层图路径推导规则本身，不改既有
     存在性校验工具的行为，不新增资源引用类别前缀。
   - 不接入 `nav_hint`。

6. **样例数据与降级**：样例地图现有 `ground`/`overlay`/`nav_hint` 三张图，没有 `decal`（`decal` 本就
   是可选层）。这正好是"可选层缺失要优雅降级"的现成用例：缺 `decal` 时只建两层、记诊断、不报错、不画
   占位——不为了凑齐三层而给样例补一张 `decal` 图。

## 后果

### 正面

- 场景地面第一次有了框架原生的声明式接入方式：内容侧只需要产出分层图 + 声明 `image_transform`，不再
  需要在游戏层手写图元、手算坐标/缩放。
- 表现层已声明多年的三个离散图层号第一次有了真正的消费方，验证了层结构表本身是可落地的，不是纸面
  声明。
- 世界矩形只有一个真相源（`image_transform`），不引入第二套坐标/缩放表达，避免未来出现"到底以哪个
  为准"的分歧。
- 可选层（`decal`）缺失的优雅降级路径有真实样例数据覆盖，不是纸面约定。

### 负面

- 地图分层图目前仍是"一整张图铺满一个矩形"的最简形态，不支持大世界场景常见的分块流式加载/按格拼贴——
  地图很大时单张背景图的内存与导入体积会成为瓶颈，这是本次决策 5 明确划出的范围外项，需要时另开 ADR
  处理。
- 只有声明了 `image_transform`（含图片宽高像素）的地图才能受益，未声明的既有地图数据不会自动获得可见
  地面，需要内容侧补声明才能用上本次接入的渲染能力。

## 备选方案与为什么不选

- **给地图登记表新增独立的坐标/缩放/平铺字段，不复用 `image_transform`**：会制造两个"这张图到底多大、
  摆在哪"的真相源，且与 `image_transform` 已经承担的语义完全重叠，将来两者取值不一致时无法判断以哪个
  为准。故不选，世界矩形唯一由 `image_transform` 决定。
- **为地图分层图的每一层单独发明一个资源引用类别前缀（如逐层各自一个资源 id）**：地图分层图的路径推导
  规则入参本就是地图行 id、四层是固定文件名，从未存在过"逐层各自一个资源引用 id"这种形状；单独发明
  一套只为了套进现有的"资源种类 + 资源 id"加载模型，会让加载入口与既有的地图路径约定产生第二套、互相
  冲突的资源标识方式。故不选，加载入口新增的资源种类直接以地图行 id 为准，一次性加载整套分层图。
- **未加载/缺失时一律用可见占位（含可选层）**：可选层缺失是"这张地图确实没有这一层"的合法状态，不是
  资源缺失/加载失败——用占位方块渲染一个内容作者从未打算提供的图层，画面观感比"干脆不画"更糟，也会让
  "占位方块"这个本该只在真正的数据缺陷时出现的信号失去意义。故不选，必需层缺失才用占位并记诊断，可选
  层缺失只是不建这一层、记诊断。
- **在场景加载完成之前（加载期）就建层**：既有的资源首次引用责任归属铁律要求"先发起加载、等加载完成、
  再建实例"，场景加载流程本身并不感知地图分层图这一类新增资源，提前建层会破坏"只消费已加载完成的资源"
  这条底线。故不选，驱动方在场景加载完成后自行发起分层图加载，加载完成回调里才建层。
