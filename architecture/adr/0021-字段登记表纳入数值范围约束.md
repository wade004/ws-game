# ADR-0021 字段登记表纳入数值范围约束

状态：已拍板 2026-09-10

## 背景

`04_数据与内容管线.md` 第 4 节的字段登记（实现级 `FieldSchema`）把 `Number`/`Int` 两种标量字段种类的校验限定为"存在且类型匹配"（检查项 `field_type`），取值本身不受任何约束。ADR-0019 已经给复合字段（`Object`/`Array`）补上了机器可读的子结构登记，但那次决策没有覆盖标量字段自身的取值范围——这条缺口在实践中被一个消费方游戏项目的问题报告具体暴露出来：

一个周期性效果的间隔参数（含义是"每隔 N 个时间单位结算一次"）与一个持续时间覆盖参数（含义是"覆盖光环的默认持续时间，省略则沿用默认值"）均登记为 `Number`。当内容里把间隔填成 `0` 或负数、把持续时间覆盖填成负数时：

- 加载期校验器（0 error）判定为合法内容——`Number` 种类只检查"是不是一个数"，不检查"这个数有没有意义"。
- 运行时逻辑对这类取值早已有防御性处理（间隔 `<= 0` 时直接跳过本次周期结算），但这段处理此前是**纯静默**的——不产生任何日志或诊断，外部表现就是"这个效果看起来完全不生效"，内容作者需要自己排查半天才能定位到是哪个字段的哪个取值出的问题。
- 与之对比，如果同一个字段填成字符串而不是数字，`field_type` 检查项会在加载期就报错阻断——**类型错误能被拦下，取值范围错误却不能**，这条不一致本身就是问题所在：两者都是"内容作者填错了一个字段"，理应得到同等强度的加载期反馈。

这不是某一个字段的孤立问题：全架构的字段登记里，`Number`/`Int` 种类被广泛用来表达"必须为正的周期/时长"、"不能为负的计数/上限"、"必须落在 `[0,1]` 的概率/百分比"这类语义在文档或运行时判断逻辑里其实早已明确、只是从未在登记表层面表达出来的取值约束。

## 决策

1. **字段登记表新增可选的数值范围约束**：`FieldSchema` 对 `Number`/`Int` 两种字段种类支持登记一个可选的范围——下界、上界各自独立可选，是否含端点各自独立可选（例如"大于 0"、"大于等于 0 小于等于 1"、"小于等于某个上限但不设下限"均可表达）。不新增字段种类；未登记范围的字段行为与登记前完全一致，属向后兼容的增量能力（同 ADR-0019 的兼容惯例）。
2. **登记与校验同源，加载期统一阻断**：已登记范围的字段，由数据注册表在字段级校验阶段（与 `field_type`/`required_field` 等既有检查同一时序，且晚于类型检查——类型都不对的取值不会再额外报范围问题）统一检查实际取值是否落在登记的范围内，新增检查项"数值范围合法"，问题定位到记录主键与完整字段路径（含子结构/变体内部的字段），说明期望的范围与实际取值。这条检查递归适用于 ADR-0019 登记的子结构内部字段，复用同一套递归校验实现，不新增平行的检查逻辑。
3. **元数据门禁新增自洽检查**：范围只能登记在 `Number`/`Int` 字段上，登记在其它字段种类上判定为一条登记自洽问题，由"元数据门禁"（ADR-0018 决策 3 的静态审计工具）报告——这类登记错误属于"字段登记本身有没有自洽"，与"某条具体内容数据是否合法"是两件事，不混在同一条检查通道里（惯例同该工具已有的其它自洽检查项）。范围声明自身的合法性（下界/上界至少给一个、下界不大于上界、端点选择不产生空区间）在登记时即校验，不合法的声明无法完成登记，这条不留给元数据门禁，因为它是纯粹的值级不变量，与挂在哪个字段上无关。
4. **导出给内容工具**：已登记的范围与其它字段元信息（种类、必填、枚举取值等）一样，可从登记表批量导出，供内容校验命令行工具与编辑器基础套件消费——编辑器可据此在内容作者输入时就地做范围校验，不必等到一次完整的加载校验才发现越界。
5. **登记范围要求有依据**：不是每一个 `Number`/`Int` 字段都要机械补一个范围——只登记有明确依据的范围（文档已写明的取值区间，或运行时逻辑已经对越界值做出特殊处理、隐含了一条取值约束），每处登记在实现里注明依据出处。没有依据的字段维持现状（只检查类型），避免登记层替代内容设计做主观判断。

## 后果

### 正面
- 修复背景里描述的具体缺口：语义上不可能成立的数值内容能在加载期就被拦下，不再需要跑到运行期靠"效果看起来不生效"这种间接方式才能发现，且反馈强度与类型错误一致（同样是加载期阻断，同样报告完整字段路径）。
- 把此前散落在各模块"手写校验规则"里的一部分单字段数值下界/上界判断，收敛成登记表本身能表达的通用能力——这部分手写规则不必删除（部分规则还承担跨字段/跨记录的判断，登记表达不了），但登记本身先在更早的阶段拦一道，两者并存不冲突。
- 内容工具（编辑器）获得范围信息后，能在作者输入的当下就提示越界，而不是等到提交后跑一次完整校验才发现。

### 负面
- 范围登记本身也可能出错（登记的范围与实际业务意图不符），需要"元数据门禁"与登记时注明依据两条机制共同防御，不能完全消除人为疏漏。
- 首批登记范围之外的字段暂不受益，需要按依据逐步补齐，是一项持续性的、非一次性完成的工作。
- 已有内容数据若恰好落在新登记范围之外，会从"能加载"变成"加载期阻断"，登记新范围前必须核对现有内容/示例数据不受影响（数据错就改数据，范围定错就改范围）。

## 备选方案与为什么不选

- **只在运行时逻辑里加日志/诊断，不改动登记表**：能缓解"完全静默"，但内容错误仍然要跑到运行期才暴露，且诊断信息分散在各模块的运行时代码里，不同模块的处理方式容易不一致；不如在加载期统一拦截，与既有 `field_type` 检查同一强度、同一时机。
- **把范围检查做成又一条通用的 `IValidationRule`（业务规则），不进登记表本身**：范围是字段自身的静态属性，与登记表里已有的必填、枚举、引用等字段元信息性质相同，理应挂在同一处；单独做成规则会导致同一个字段的约束分散在"登记表"与"规则列表"两处，且规则天然拿不到"这是哪个字段"的结构化信息，没法像 3 号决策那样做登记自洽检查，也没法像 4 号决策那样批量导出给内容工具。
- **一次性给所有 `Number`/`Int` 字段机械补一个宽松范围（如"非负"）**：没有依据的机械补齐会产生大量与业务意图无关的登记，一旦某个字段的真实语义允许负值（如冷却增量），机械补的范围反而会误伤合法内容；坚持"只登记有依据的范围"。

## 魔兽世界的对应做法

魔兽世界的 `spell` 表用固定列表达效果参数（`EffectBasePoints`、`EffectAmplitude` 等），取值范围没有任何声明式约束，服务端/客户端代码里对间隔为 0、持续时间为负一类取值各自有零散的防御性处理（有的直接忽略、有的按默认值处理、有的干脆没处理而在特定组合下产生可复现的异常行为），是否存在这类隐患完全依赖代码审查或运行时踩坑发现——正是本决策要避免的"约束散落在运行时代码、且各处处理不一致"的状态。本架构选择把有依据的取值约束提升到登记表层面统一表达，让加载期校验器成为发现这类内容错误的唯一权威出口。
