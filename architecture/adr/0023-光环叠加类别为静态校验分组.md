# ADR-0023 光环叠加类别为静态校验分组

状态：已拍板 2026-09-10

## 背景

`06_规则层_属性技能战斗AI.md` 第 3.3 节把 `skill.aura_def.stack_category` 描述为"用于叠加冲突检测（见 04 校验器）"，第 3.8 节"叠加与刷新规则"表格进一步写"同 `stack_category` 的光环叠加数超过 `max_stacks`……忽略新实例的叠加请求，或按策略替换为最新参数"。这两处表述放在一起容易被读成：`stack_category` 是一个**跨光环定义共享的运行时叠加槽位维度**——同一类别下不同 `aura_def` 会互相竞争同一份叠加计数与溢出处理。

实际实现分两层，且此前已被两轮外部审计各自独立发现同一条落差：

- `core/rules/skill/schema/SkillValidationRules.cs` 的 `StackCategoryConflictRule` 只在**加载期**把 `stack_category` 当作内容分组使用：同一类别下若同时存在 `max_stacks > 1`（声明"可叠加"）与 `max_stacks == 1`（声明"不可叠加，仅可刷新"）两种记录，判定为叠加形态混用冲突并报错；类别相同、叠加形态一致（如都 `max_stacks == 1`）的多个定义完全允许通过。
- `core/rules/skill/core/AuraHost.cs` 的运行时槽位键是 `(target, defId, sourceKey)`（`_slots` 字典，见该文件第 76 行），`stack_category` 完全不参与这把键；`SkillOptions.StackOverflowPolicy` 的三种取值（`Ignore`/`RefreshOnly`/`Replace`）只作用于**同一 `aura_def`、同一来源槽位**的重复应用（`ReapplyExisting`），不同 `aura_def` 之间不发生任何叠加计数聚合或溢出互相影响，即使二者 `stack_category` 相同。

历史审计 `architecture/落地计划/audit-b3b91ee-20260907/doc-code-matrix.md` 第 49 行已经记录了这条文档措辞与实现的落差，并建议"06/skill README 改为'同定义叠加已支持；类别级语义待实现'，补 ADR/代码或收窄文档"，但当时未继续跟进拍板。

本次由消费方游戏项目提交只读复核报告 `ws-game-wow/docs/框架反馈/光环叠加类别契约一致性核对.md`，用真实 `RulesAssembly` 装配的 Runtime 报告复现：把两个显式相同 `stack_category` 且 `max_stacks=1` 的定义依次施加到同一目标，两者均产生成功的 `AuraAppliedEvent`，各自可查询到，`AuraInstanceRef` 不同，层数各自为 1——即"同类别、不同定义可并存"。消费方明确不把这一现象定性为 `AuraHost` 算法缺陷，也不要求框架实现跨定义互斥，只请求把契约在文档层面写明确，与历史审计的建议方向一致，本次借此机会一并拍板收口。

## 决策

1. **`stack_category` 是跨定义的静态内容校验分组**，作用范围限定在加载期校验器——用于发现"同一类别下混用了不同叠加形态（可叠加 vs 不可叠加）的定义"这类内容登记问题，不是运行时的任何数据结构维度。
2. **运行时叠加与溢出严格按 `(target, aura_def, sourceKey)` 槽位处理**，`stack_category` 不参与槽位键的构成。`StackOverflowPolicy` 的 `Ignore`/`RefreshOnly`/`Replace` 三种策略只作用于同一光环定义与同一来源槽位的重复应用；不同 `aura_def` 即使 `stack_category` 相同也各自独立维护叠加状态，彼此并存、互不影响、互不触发对方的溢出策略。
3. **`sourceKey` 的默认语义**：`SkillOptions.AllowMultiSourceTiming`（默认 `false`）为假时，槽位键的 `sourceKey` 恒为 `null`——同一目标身上同一 `aura_def`，无论施加来源是谁，都命中同一个槽位（不按来源分别计时）；仅当该项开启（`true`）时，`sourceKey` 才取实际来源 id，槽位键变为按 `(defId, sourceId)` 分别维护独立实例。这条语义此前只存在于代码与配置项注释里，06 文档正文未提及，本次一并写清楚，避免被误读为"总是按来源分别计时"。
4. **跨定义共享叠加槽位（即"同 `stack_category` 的不同 `aura_def` 相互竞争同一份叠加计数/溢出处理"）是当前未提供的能力**，列入 `architecture/落地计划/落地方案与分阶段计划.md`"能力边界与未默认接入能力索引"表"未提供"分类；若未来确有具体游戏需要这类语义，需要另立 ADR 明确：被顶掉的一方如何选择（替换目标）、层数与效果归属如何在跨定义场景下计算与叠加、三种溢出策略如何映射到"跨定义"这一新维度、未登记 `stack_category` 的定义之间是否算同一类别（缺省类别语义）——这些都不是"照搬现有单定义语义"能直接回答的问题，需要独立拍板。

## 后果

### 正面

- 校验器（`StackCategoryConflictRule` 及其问题消息）、架构文档（06 第 3.3/3.8 节、04 第 5 节）、运行时诊断/代码注释（`AuraHost.cs`、`SkillOptions.cs`）三方对"同类别不同定义可并存"与"同定义同来源槽位溢出"使用同一套措辞，消除此前"文档暗示跨定义槽位、实现按定义分槽"的表述落差，避免下一个消费方重复同样的误读成本（历史审计已发现过一次，本次是第二次独立复现）。
- 消费方的 Runtime 验收报告成为本决策的既有回归证据；本次新增的验收测试固化同一组场景，防止未来改动无意间改变这条既有语义。
- 明确把"跨定义互斥槽位"列为未提供能力而非缺陷，划清"契约不清楚"与"功能未实现"两件事的边界，后续若有具体游戏提出需求，走该未提供能力标注指向的 ADR 流程即可，不需要重新调查一遍现状。

### 负面

- 若未来确有游戏需要跨定义共享叠加槽位（如"多个不同来源的减益技能共享一个减益槽位，只保留最强一条"这类设计），本决策不提供现成能力，需要额外的设计与实现工作，不能通过调整现有 `stack_category` 字段的解释来免费获得。
- 本决策收紧了 `stack_category` 的字面含义（"用于叠加冲突检测"这一表述本身没变，但明确限定在静态校验范围），依赖旧表述做出"跨定义共享槽位"设计假设的游戏内容需要重新核对。

## 备选方案与为什么不选

- **跨定义共享类别槽位**（把 `stack_category` 提升为运行时槽位键的一部分，替代现有的 `defId` 维度或与其并列）：需要先回答决策 4 列出的四个问题（替换目标、层数与效果归属、策略作用范围、缺省类别语义），任何一个回答不同都会产生不同的运行时行为；且这会改变 `AuraHost` 自 1.0.0 起、跨越 1.15.0 等多个已发布版本的既有叠加/移除时机与事件序列，属于破坏性变更。当前没有任何消费方提出这一具体需求——本次反馈明确只要求文档说清楚现状，不要求实现变更——贸然改动运行时行为没有依据，也违反"不改运行时算法"的既定处理边界。本决策把该方向记为"未提供能力"，留待有具体需求时再走独立 ADR。
- **保持文档现状不变，只让消费方自行在其内容/文档中注明理解差异**：不采纳。这条落差已被两轮独立的外部审计（`audit-b3b91ee-20260907`）与消费方复核各自发现一次，说明现有措辞确实容易造成误读，属于文档本身的责任而非消费方一次性的个例问题；继续不处理会让后续消费方反复承担同样的核验成本。

## 魔兽世界的对应做法

魔兽世界存在"光环组"（`SpellGroup`）机制，部分增益/减益法术（如多种"狂暴"类光环）显式登记为同一组，客户端/服务端在施加时按组内优先级互相替换，只保留符合条件的一条——这是一种真正的跨法术共享槽位语义。本架构的 `stack_category` 字段命名借用了类似的直觉，但当前范围明显更窄：只提供加载期"叠加形态一致性"分组校验，不提供魔兽光环组那样的运行时跨定义槽位共享与替换。若未来需要落地类似魔兽光环组的完整语义，按本 ADR 决策 4 另立 ADR，不在本次决策范围内。
