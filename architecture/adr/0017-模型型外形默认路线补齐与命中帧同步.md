# ADR-0017 模型型外形默认路线补齐与命中帧同步

状态：已拍板 2026-09-08

## 背景

[09_表现层.md](../09_表现层.md) 第 3.3.2、4 节与 [02_引擎适配层.md](../02_引擎适配层.md) 第 1.12 节已经把 `model` 型外形的契约（`IRenderer3D`、`ICharacterRig`、槽位/挂点、命中帧同步策略）定义完整，但落地程度与 `sprite` 型外形不对称，具体表现为：

1. **`ICharacterRig` 的 `model` 型实现只是占位**：`ModelCharacterRig` 此前对层管理、锚点/挂点查询三个方法一律抛 `NotSupportedException`，只有"与外形类型无关"的状态记账/程序动画序列推进两项职责可用；同一逻辑单位选用 `model` 型外形后，除了播放骨骼动画剪辑之外几乎没有其它可用能力，与 `SpriteCharacterRig` 已有的完整层/锚点/程序动画落地不对称。
2. **`IResourceLoader` 的资源种类枚举没有模型类别**：`ResourceKind` 枚举（见 [ADR-0016](0016-引擎适配层契约阶段4联调补齐.md) 决策 5）覆盖图片、音频、字体、数据表、场景、导航网格、特效七类，唯独没有 `display.map`（`kind: model`）的 `model_ref` 与 `display.equip_visual` 的 `model_ref` 所指向的模型/骨骼动画资产类别，模型资源的首次加载责任无法用统一枚举表达。
3. **命中帧从关键帧数据到实际反馈之间没有接通**：`display.anim_set.clips[*].events`（04 第 7.1.1 节）已经登记了 `{name, time_pct}` 关键帧事件，`sprite` 型的 `FrameAnimClip.Keyframes`/`SpriteCharacterRig.HitFrameReached` 也已落地，但 `HitFrameReached` 只存在于 `SpriteCharacterRig` 一侧（未提升进 `ICharacterRig` 契约），`FeedbackBinder` 没有任何订阅方消费它——`RenderOptions.HitFrameSync = AnimKeyframeDriven` 这一口味配置项因此没有可观察的实际效果，无论选它还是 `LogicDriven` 表现层的播放时机都完全一样。
4. **武器风格没有"实体当前用的是哪一套"这一段查询**：`IWeaponStyleResolver`（09 第 4.4 节）已知 `weaponStyleRef` 之后能查到覆盖表，但"给定一个实体，它现在算哪一个 `weaponStyleRef`"这一前置查询没有任何契约或实现——装备变化事件（`item.equipped`/`item.unequipped`）已存在，但没有消费方把它与 `weaponStyleRef` 关联起来。
5. **`AnimStateMachine.StateChanged` 不携带触发技能 id**：09 第 4.4 节 `cast_anim_override` 要求按技能 id 覆盖施法动作剪辑，但状态机的切换事件只有 `(entityId, from, to)` 三元组，消费方（"持有 `WeaponStyleResolver` 的组装层代码"）拿不到是哪个技能触发了这次 `cast` 切换，无法实现按技能覆盖。

以上五项均是"契约已经说清楚该有什么，实现没跟上"的情形，其中第 2 项（资源种类枚举）与第 5 项（状态机载荷）涉及已定稿的契约签名变更，按 [12_扩展与变更流程.md](../12_扩展与变更流程.md) 第 5 节需要 ADR 说明变更理由；其余三项虽然是新增实现/新增字段而非改写既有签名，但彼此关联、共同构成"model 型外形默认路线"与"命中帧同步"这两条完整链路，一并在本 ADR 决策，便于对照。

## 决策

1. **`ResourceKind` 新增 `Model`**：加载责任沿用 [ADR-0016](0016-引擎适配层契约阶段4联调补齐.md) 决策 6——谁首次引用一个模型资源 id（`display.map.model_ref`、`display.equip_visual.model_ref`）谁负责调用 `loadAsync`，`IRenderer3D` 只消费已加载完成的资源，未加载时使用实现内建占位并记诊断，不隐式触发加载、不抛异常。
2. **model 型外形的默认路线是框架职责**：表现层（`presentation/render`）提供真实的 `ModelCharacterRig`（不再是占位实现），归并 09 第 4.1 节 CharacterRig 四项职责的 `model` 型落地；引擎适配层选用 `model` 型外形时必须提供 `IRenderer3D` 的真实实现（真正的三维渲染与骨骼动画管线），只有游戏全程只使用 `sprite` 型外形时才允许声明降级、不提供 `IRenderer3D` 真实实现——这一条把 09 第 3 节验收标准 5 此前"model 型是否提供真实三维渲染管线是游戏层可选投入，不是本架构验收范围"的表述收紧为"选了 model 型就必须有真实实现，可选的只是'要不要选 model 型'这个上一层决策"。
3. **动画事件到命中帧统一为 `ICharacterRig.HitFrameReached`**：`sprite` 型经序列帧剪辑关键帧（`FrameAnimClip.HitFrameMarker`）触发，`model` 型经 `IRenderer3D.onAnimEvent` 命中固定事件 id（`ModelCharacterRig.HitFrameEventId`，取值 `anim_event.hit_frame`）触发；`HitFrameReached` 从 `SpriteCharacterRig` 的专属成员提升进 `ICharacterRig` 契约本身，两种外形类型的消费方（如反馈绑定）不必关心具体是哪种外形。
4. **命中帧同步（`HitFrameSync = AnimKeyframeDriven` 时生效）**：反馈规则新增字段 `sync: "hit_frame"`（`feedback.binding.sync`，默认对 `combat.damage_dealt` 类命中反馈开启，其余事件默认不开启），标记为命中同步的规则，其全部动作延迟到攻击方 `ICharacterRig` 的命中帧事件到达后才一并播放；带超时兜底，默认 0.5 秒，超时即照常播放并记一条诊断。命中帧同步只影响反馈动作的呈现时机，伤害/状态结算仍然只由规则层按固定步长结算一次，不受呈现时机延迟影响（09 第 4.3 节"逻辑判定结果与时机永远由规则层决定"的延续）。
5. **武器风格来源新增"实体 → 武器风格引用"查询**：新增表现层契约 `IWeaponStyleSource.GetWeaponStyleRef(entityId): Optional<Id>`，默认实现按装备变化事件（`item.equipped`/`item.unequipped`）失效缓存，取该实体主手武器的物品模板 id，经既有的 `display.map.weapon_style_ref` 关联链路（09 第 4.4 节"关联方式"——物品模板对应的 `display.map` 行 `logical_id` 就是该模板 id 本身）解析出 `weaponStyleRef`；不新增任何数据表字段——`display.map.weapon_style_ref` 已经足以承载这条关联，"实体现在用哪个模板"是本决策新增的唯一缺口。
6. **`AnimStateMachine` 状态切换事件携带触发技能 id**：新增 `StateChangedWithSkill: (entityId, from, to, triggerSkillId: Optional<Id>)` 事件，与既有 `StateChanged: (entityId, from, to)` 同一次切换背靠背触发；`triggerSkillId` 只在由 `skill.cast_start` 驱动的切换（进入 `attack`/`cast`）时非空。既有 `StateChanged` 事件签名不变，保证既有订阅方不必修改代码即可继续编译通过。

## 后果

### 正面

- 选用 `model` 型外形的游戏在表现层不再遇到"层/挂点管理直接抛异常"的硬性阻断，装备外观（槽位换装/挂点挂接）、程序动画八原语、命中帧同步在引擎无关层面已经是完整可用的实现，接入具体引擎适配层（下一阶段）只需要补齐 `IRenderer3D` 真实实现本身，不需要再补一层表现层胶水代码。
- `RenderOptions.HitFrameSync = AnimKeyframeDriven` 第一次有可观察的实际效果——命中反馈动作确实会等到动画剪辑播到命中帧才播放，不再是"设了也白设"的口味配置项。
- 武器风格查询链路补齐"实体 → weaponStyleRef"这一段后，`cast_anim_override`/`impact_vfx_override` 才具备被真正接线消费的完整前提条件。
- `ResourceKind.Model` 落地后，模型资源的首次加载责任与其它六类资源遵循同一套契约，不需要引擎适配层为模型资源另开一条特殊加载通路。

### 负面

- `ICharacterRig` 契约新增 `HitFrameReached` 事件成员、`ModelCharacterRig` 构造函数签名发生实质变化（不再是无参占位构造），已经存在的（未来的）具体引擎适配层实现若直接实现了 `ICharacterRig` 或构造过旧签名的 `ModelCharacterRig`，需要跟着调整；本次落地范围内尚无任何引擎适配层代码依赖这两处（占位实现从未被实际构造使用过），无迁移成本，但记录在案供后续接入方注意。
- `AnimStateMachine` 新增一个额外事件（而非直接扩展 `StateChanged` 签名）是"新增重载"的折中，长期看两个事件并存增加了状态机对外暴露的接口面；一旦确认所有消费方都已经迁移到新事件，可以考虑在未来的破坏性版本里合并为一个事件并删除旧事件（不属于本 ADR 决策范围）。
- "选了 model 型就必须提供真实 `IRenderer3D` 实现"收紧了游戏层的选择空间——此前允许"选 model 型但暂不接三维渲染管线"的过渡态在决策 2 之后不再是合规状态，需要相应更新验收标准的措辞（见文档同步清单）。

## 备选方案与为什么不选

1. **保持 `ModelCharacterRig` 占位、把真实实现完全留给具体游戏各自实现**：好处是本轮改动量最小。否决理由——09 第 4.1 节职责表已经把"层/槽位管理、锚点/挂点查询"列为 CharacterRig（框架职责）而非游戏层职责，`sprite` 型这两项职责已由框架给出完整实现，`model` 型继续占位会让两种外形类型在"基础架构提供"这一维度上不对称，且每款选用 `model` 型的游戏都要重新实现一遍同样的槽位/挂点/程序动画映射逻辑，与"基础架构提供 CharacterRig 与程序动画原语的行为定义"这一条产品定位矛盾。
2. **命中帧统一事件不提升进 `ICharacterRig`，只在 `SpriteCharacterRig`/`ModelCharacterRig` 各自暴露、由消费方按外形类型分别处理**：好处是不改动既有接口。否决理由——`FeedbackBinder`/`IHitFrameSource` 一类消费方按实体 id 订阅命中帧，不应该也不需要知道该实体是哪种外形，分别处理会让每一处消费代码都重复一遍"先判断外形类型再取事件"的样板代码，与两种外形类型对上层"看起来是同一个 rig"的既有设计目标（`ICharacterRig` 本就是为了统一两种外形类型的操作面）相悖。
3. **武器风格来源直接在 `item.template` 新增 `weapon_style_ref` 字段，绕开 `display.map`**：好处是查询路径少一跳（不必先查 `display.map`）。否决理由——09 第 4.4 节已经明确拍板"武器表现档案是 DisplayInfo 体系的一部分"，关联方式是 `item.template.display_ref → display.map.weapon_style_ref`，`item.template` 本身属于载体层（数值/规则），在其中新增一个纯表现属性字段会打破"数值侧与表现侧互不干扰"这条既有分工（09 第 4.4 节"武器的数值侧与表现侧互不干扰"原文），且现有 `display.map.logical_id` 已经可以直接承担"物品模板 id → 该模板的 DisplayInfo"这条查询，不存在必须新增字段才能打通的真实缺口。
4. **命中帧同步不做超时兜底，命中帧事件永远不来就永远不播放**：好处是实现更简单。否决理由——命中帧事件依赖具体引擎适配层的动画事件回调是否可靠触发（如剪辑被中途打断、资源加载失败导致剪辑根本没有播放过），若无兜底，一次异常会导致对应的命中反馈永久丢失且没有任何诊断信息，与 09 第 1 节表现层一贯"缺表现资源不阻断游戏、只降级"的宽容策略相悖。

## 魔兽世界的对应做法

魔兽世界客户端的角色模型（骨骼动画、装备槽位网格替换、武器挂点）与序列帧类精灵是完全不同的两套底层资产管线，但对上层战斗系统而言二者都统一表现为"这个单位现在应该播放哪个动作、挂了什么装备"，客户端不需要按资产类型分别写战斗表现逻辑；武器的攻击特效、命中特效随装备变化实时切换，命中判定的逻辑时机与动作剪辑的视觉命中帧由客户端独立的时间轴对齐系统协调，而不是让战斗结算直接依赖动画播放进度。本 ADR 的 `ICharacterRig` 统一命中帧事件、"实体 → 武器风格引用"查询、命中帧同步的超时兜底三项决策，分别对应这三点在单机 2.5D 场景下的最小实现。
