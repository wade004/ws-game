# ADR-0076 event 分组静态类型改为未知而非谎称 Bool

状态：已拍板 2026-09-23

## 背景

消费方（游戏）第二十批第 3 条（阻塞项）：`event.<key>` 引用的具体字段类型随触发本次求值的事件
类型动态变化，这是 04 第 6.2 节 `event` 分组当初设计成"宽松"（未登记 key 不当错误）的初衷——静态
期本就无法穷举每一种事件携带的每一个字段。但落地时"宽松"被实现成了"给 `event` 分组下任意未登记
的 `key` 固定返回一份签名：零参数、返回类型恒为 Bool"，而不是"承认这个类型在静态期未知"。

两者的差别不是措辞，是校验结论会不会算错：内容里写 `event.<某字段> == "<字符串字面量>"`（或与
Id 字面量比较）这类条件时，静态校验按"这个引用的类型是 Bool"去核对比较两侧类型是否一致，与右侧
的 String/Id 字面量比较判定"两侧类型不一致"、报 Error；而运行期真正求值这个引用时，走的是各事件
类型自己的字段表（如某个表示命中结果的字段，运行期实际返回字符串"Hit"/"Miss"/…），与静态期认定
的 Bool 完全对不上——静态期给出的是一个运行期根本不存在的类型冲突，不是数据真的有问题。内容作者
按事件真实字段类型写的条件，加载期直接被拒绝，涉及该条件所在表整体加载失败。

## 决策

**`event` 分组下未登记的 `key`，静态类型推断阶段一律视为"类型未知"，不再返回任何固定的已知
签名（含此前的"返回 Bool"）。**

具体做法：负责合并 `quest`/`player`/`world`/`event` 四个分组的引用登记表实现，此前对 `event`
分组的查询恒注入一份固定签名（参数未知、返回类型固定为 Bool），改为对 `event` 分组不做任何特殊
拦截，未登记的 `event.<key>` 如实报告"未登记"。

这个改动之所以只用一处如实返回"未登记"就足够、不需要新增任何分支逻辑，是因为下游两处本就已经有
对应的正确处理路径，问题只出在"没能被正常触发到"：

- 解析期（点分标识符归类为引用还是 Id 字面量）本就有一条独立于登记表查询结果之外的判断——
  `event` 分组下未登记的 key 恒解析为引用节点，不会退化为 Id 字面量（这条判断早于本次改动就
  存在，理由是 event 不是内容域名，退化为字面量会让"查询触发事件字段"的语义整体错误）。这条路径
  不依赖登记表对 `event` 分组回答"已登记"，因此本次改动不影响解析期行为。
- 静态类型推断期（比较两侧类型是否一致、逻辑操作数是否为 Bool）本就有"某一侧类型未知就跳过这项
  类型检查而不是报错"的既有分支——这条分支服务的正是"这个引用来自一个当前无法在静态期确定类型的
  合法用法"这一场景，本次改动之前从未被 `event` 分组触发到，只是因为登记表一直谎称"类型已知"。
  如实报告"未登记"之后，这条既有分支自然接管，不需要新写代码。

运行期的表达式求值路径（按事件真实携带的字段名与字段值取值）完全不受影响——本决策只改变的是静态
期"这个引用大概率是什么类型"这一推断结论，不改变运行期任何一行查询/取值逻辑。

## 后果

### 正面

- `event.<key> == <字符串/Id/数值/布尔字面量>` 这类按事件真实字段类型书写的条件，静态校验不再
  因为一份编造的类型而误报，内容加载不再被这类合法写法无差别拒绝。
- 未登记的 `event.<key>` 仍然解析为引用节点（不退化为字面量）、`语法错误`/`未知分组`/`参数个数
  不对` 这类真实错误仍然照常在静态校验阶段报出——本决策只是让"类型未知"如实呈现为"未知"，不是把
  `event` 分组的校验整体放行成"恒不报错"。
- 运行期表达式求值路径一行未改，行为逐字节不变。

### 负面

- `event.<key>` 参与比较/逻辑运算时，静态期不再能够对其做任何类型层面的把关（如误把一个数值字段
  当布尔用、误把参数个数写错）——这是"承认类型在静态期确实未知"必然要付出的代价，此前"能报错"
  只是因为那份类型是编出来的，报错本身并不可靠（见"背景"一节，运行期真实类型经常与之不符）。这类
  笔误只能留给运行期诊断（按事件字段名查不到会记一条警告并退化为该类型的默认值）与人工测试发现。

### 与不采纳的方案

未采纳"开放一个按 key 精确注册 `event` 分组签名的入口，让消费方按自己关心的事件字段逐条登记"：
这个方案理论上能同时保留类型检查与消歧准确性，但要求消费方为每一个用到的事件字段单独登记一次，且
框架内部装配根（表现层与内容校验共用的组合登记表）实际使用的仍然是框架自带的那一份登记表，消费方
另行 compose 出的更精确版本只能让"内容校验期"通过，覆盖不了框架内部用于运行期装配的这一份——会
造成"校验期用一份、运行期解析用另一份"的不一致，治标不治本，且把本该框架内部解决的缺口转嫁成了
消费方每接入一个新事件字段就要多做一步登记的负担。

真正能在不牺牲消歧准确性的前提下补上这部分类型检查的路径，是等事件目录本身开始登记"某个事件类型
携带哪些字段、各自什么类型"（当前事件目录只登记事件 key 本身，不登记字段形状），届时可以按事件
类型精确推导 `event.<key>` 的类型，而不是像本决策这样整体退让为"未知"。这是留给将来的演进方向，
不在本次决策范围内实现。

## 与游戏客户端的对应参考

对应主流数据驱动型游戏引擎里"事件负载（payload）的具体字段随事件种类而变、只有拿到具体事件实例
才能确定某个字段的真实类型"这一常见设计——静态配置阶段引用这类字段时，工具链通常也只能做到"语法/
存在性层面的把关"，无法在不知道具体事件形状登记的前提下做精确类型检查，这是同类系统里的常见取舍，
不是本项目独有的简化。
