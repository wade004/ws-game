# ADR-0042 框架内诊断契约必须有到达宿主控制台的通路，并采用统一转发机制

状态：已拍板 2026-09-19

## 背景

框架内大量模块（表现层与核心层均有）遵循同一套惯例：定义一个模块自用的最小诊断出口契约
（形如"记一条警告""记一条错误，可选带触发它的异常"两个方法），默认实现只把消息收集到内存
列表，不依赖任何具体日志/呈现方式，由调用方决定如何进一步呈现。这一惯例本身是合理的分层
设计——诊断契约所在的层级不应该被迫依赖某种具体的呈现方式。

但此前的装配实践把"契约本身不依赖具体呈现方式"逐渐做成了"没有任何装配根真正把它接到宿主
控制台"：诊断契约的默认实现只被构造，构造它的宿主对象在多数情况下不对外暴露这份实例的引用
（诊断参数是可选构造参数，调用方不传时内部各自新建一份默认实现，外部拿不到），三个生产装配
入口因此从未有机会把这些消息转发出去。后果是：数据缺失、未注入可选回调、未知引用键等大量
本该在开发期被立刻看到的问题，在真实运行环境下完全静默——只在受影响的具体功能表现异常时才
会被间接发现，且难以定位根因。

表现层的一套诊断契约（覆盖运行期特效、音效、反馈、视图绑定等六条链路）已经分三批各自手工
接上了转发链路，每一批都在"这次终于接完了"之后又发现遗漏点（构造函数未对外暴露诊断实例、
遗漏某条并行链路、遗漏某个独立契约）。这种"发现一个接一个"的修复节奏本身暴露了更深的问题：
框架里到底还有多少个同惯例的诊断契约从未被接过，此前从未做过一次完整的普查；而且即使普查
出来，按"每个契约各写一套装饰器/转发器"的既有做法去逐个接入，成本会随契约数量线性增长，
且新增诊断契约时容易被遗忘（既有机制没有强制任何"新契约必须接入"的约束）。

## 决策

1. **架构结论：框架内所有诊断契约产生的信息，都必须存在一条能到达宿主控制台的通路**——
   "诊断契约默认只记内存"是允许的实现细节，但"完全没有任何装配路径能把它转发出去"不再是
   可接受的终态。新增诊断契约时，装配根必须在合理的时间点（构造完成后、或该诊断来源开始
   产生消息之前）把它接入统一转发机制（决策 2），或者在该契约所在模块的判断记录里写明"为
   什么这条不需要接入"的具体理由（例如决策 3 描述的结构性排除情形）。不接入且不说明理由，
   视为遗漏。

2. **统一转发机制：一个与具体诊断契约解耦的注册制轮询集线器**，取代"每套契约各写一个专属
   转发器/装饰器"的既有做法。核心设计：
   - 集线器本身只认识"一个来源名 + 一份只增不减的消息列表引用"，不需要任何诊断契约实现某个
     公共接口——契约之间消息列表的具体类型不统一（有的直接是字符串列表，有的是"消息+可选
     异常"的记录列表），要求它们都实现同一个新接口意味着要么改造全部契约的对外返回类型，
     要么新接口只能承诺最小公共能力、事实上还是要包一层。改为在装配根登记时用一个轻量投影
     把消息列表整理成统一形状，集线器本身的实现完全不需要新增代码来认识新契约。
   - 每帧轮询一次，只处理每个来源自上次轮询以来新增的那一段消息，不重复处理、不需要为每个
     来源单独维护事件订阅。
   - 复用既有转发链路已经验证过的去重（按转发文本去重）、容量上限淘汰（超过上限时淘汰最久
     未被再次命中的一条）、可运行期开关三项能力，不另起一套语义；错误级消息与警告级消息
     统一映射为宿主控制台的同一种严重级别（决策 4），转发文本额外携带来源名前缀，避免不同
     模块凑巧产生完全相同文案时被去重逻辑误判为同一条。
   - 新增诊断契约接入的完整成本：契约所在的宿主类型补一个只读属性对外暴露其诊断实例的引用
     （若此前没有对外暴露），装配根在构造完成处补一行登记调用——不需要修改集线器本身的
     任何代码。

3. **本轮已完成一次全仓普查，并把普查发现的、符合接入条件的诊断契约全部接入统一机制**：
   普查覆盖全部以"最小诊断出口，只记警告/错误到内存"为惯例的契约，逐个确认其宿主是否在
   三个生产装配入口的可达范围内。可达且尚未接入的，本轮全部接入；不接入的，逐一说明结构性
   理由（决策 3）。普查结果与逐项状态记录在本仓库的判断记录与提交历史中，不在本 ADR 正文
   重复列出——本 ADR 只固定"必须做过普查、必须有完整清单、清单要能被追溯"这一流程要求，
   具体清单内容不属于架构层面的拍板对象，会随框架演进持续变化。

4. **错误级诊断消息到达控制台时的严重级别，统一按较低的严重级别处理，不映射为"错误"级别**：
   宿主运行环境的自动化测试框架会把未预期的"错误"级别输出直接判定为测试失败；框架内多个
   诊断契约的错误分支覆盖的是预期内的、不应中断流程的异常路径（如某处资源缺失、某个可选
   回调未注入），并不构成"测试本身失败"的信号。统一转发机制因此把全部诊断消息（无论契约
   自身区分警告还是错误两级）都转发为宿主控制台的同一种较低严重级别，只在转发文本里额外
   携带一个标记，保留"这条消息在契约层面原本是错误级"的可辨识信息，不实际影响控制台的
   严重级别判定。

5. **不要求所有诊断契约都必须立即接入**：某些诊断契约的实例生命周期与统一机制要求的"消息
   列表随时间只增不减、可跨帧持续读取同一个引用"这一前提结构性不兼容——例如契约的默认实现
   是在单次调用过程中临时构造、调用结束即随之丢弃，从未有任何变量在跨帧的时间尺度上持有它。
   这类契约不适用轮询式转发，需要另一种机制（如在异常/非预期分支处直接同步转发一次，而不是
   攒起来轮询），留待后续单独立项；本轮不为了凑齐接入数量而牵强处理这类契约，转发覆盖面
   宁可如实呈现为"结构性排除"，也不能用不适用的机制勉强接入、制造"看起来已经接好了"的
   假象。

## 后果

### 正面

- 框架内原本大量完全静默的诊断信息，第一次有了到达宿主控制台的默认通路，显著缩短"某个
  功能表现异常"到"定位到具体根因"之间的距离。
- 新增诊断契约接入统一机制的成本被压到最低（一个只读属性 + 一行登记调用），降低了未来
  重复本轮"发现一个接一个"这种修复节奏的概率。
- 统一机制与具体诊断契约解耦，新增契约不需要修改机制本身的任何代码，符合"新增内容不改
  代码"的一贯取向。

### 负面

- 决策 5 描述的结构性排除意味着覆盖面本身不是、也不能宣称是 100%——仍有一部分诊断信息
  （生命周期为单次调用、跨帧不持久的那一类）在本轮之后依然只能通过阅读代码或专门的调试
  手段发现，需要在后续独立立项解决，不能误认为"诊断契约的静默问题已经全部解决"。
- 决策 4 的严重级别降级处理是自动化测试框架约束下的权宜安排，牺牲了"错误级诊断在控制台上
  应当比警告级更醒目"这一直觉——需要依赖转发文本里的标记辨认，不如原生的不同严重级别直观。
- 统一转发机制引入了一层新的间接（登记 + 轮询），相比"契约直接持有一个具体呈现方式的引用、
  产生消息时立即呈现"的写法多了一帧的延迟与一次遍历开销，对绝大多数诊断场景（非高频路径）
  可忽略，但确实不是零成本。

## 备选方案与为什么不选

- **继续沿用"每套契约各写一个专属转发器/装饰器"的做法，只是把它应用到全部契约上**：这正是
  本轮之前实际发生的模式，已经证明了其成本随契约数量线性增长、且容易遗漏——决策的动机之一
  正是要终结这种模式，故不选。
- **要求全部诊断契约的默认实现统一实现同一个新的公共接口**：能让统一机制的实现更简单（不需要
  登记时投影），但代价是要么改造大量既有契约的对外返回类型（消息列表的具体元素类型不统一，
  统一到公共接口要求的最小形状会丢失部分契约已经暴露的细节，如触发异常本身），要么破坏这些
  契约已发布的公开签名。相比之下，让装配根在登记时按需投影，把这层适配成本放在装配根、不
  波及契约本身，成本分配更合理。故不选。
- **为决策 5 的结构性排除类型也强行接入统一机制**（如在每次调用点手动构造一次转发）：技术上
  可行，但会让"契约已接入统一机制"这句话失去准确含义——真正需要的是"异常/非预期分支处直接
  同步转发"这一不同的机制，混进轮询式的统一机制里只会让两种机制的职责边界变得模糊，增加
  后续维护成本。故本轮不做，留待专门机制单独解决。
- **把诊断消息的错误级别原样映射到控制台的错误级别，另外调整自动化测试框架使其容忍这些
  预期内的错误输出**：改动测试框架本身识别"预期内错误"的方式涉及更大范围的既有测试基线
  调整，且需要对全部现有错误级诊断消息逐一确认"是否真的属于预期内"，风险与工作量都显著
  高于统一降级处理；转发文本携带标记的降级方案已经能满足"保留可辨识性"这一实际需求。
  故不选。
