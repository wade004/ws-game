# ADR-0050 技能宿主契约纳入技能簿查询与学习成员

状态：已拍板 2026-09-20

## 背景

消费方反馈：技能宿主契约缺 `GetKnownSkills`/`LearnSkill`/`LearnFromBook`/`Knows` 四个方法——这些
能力此前只在具体实现类（`core/rules/skill` 模块的技能宿主组合根）上，面向接口编程做不到，消费方
只能拿到具体类才能查询"某单位已知哪些技能"或驱动"学习/技能书"，正在绕行（持有具体类型引用，
放弃了原本应有的接口解耦）。

框架自己也已经承认这个缺口：`core/carriers/item/contracts/SkillGranter.cs`（装备联动"授予/撤销
主动技能"的具名委托）改动前的注释原文写道——技能宿主契约"没有 `LearnSkill`/`ForgetSkill` 一类
方法……该能力目前只在具体实现里，未提升到共享契约……本模块用委托绕过"。这是框架内部独立观察到的
同一个缺口，不只是消费方单方面反馈。

独立核实：技能宿主组合根确实以公开方法的形式提供了 `Knows(unitId, skillId)`、
`GetKnownSkills(unitId)`、`LearnSkill(unitId, skillId)`（另有带来源/带永久标记的重载）、
`LearnFromBook(unitId, bookId, level)`，但技能宿主契约接口只声明了施法、目标查找、冷却、
读条/打断、只读就绪查询等战斗相关成员，确实不含以上四个。

## 决策

1. **把 `Knows`/`GetKnownSkills`/`LearnSkill`/`LearnFromBook` 四个成员补进技能宿主契约接口**，
   签名与具体实现类既有的同名公开方法逐字一致（`LearnSkill` 取双参数、不带来源/永久标记的那个
   重载——契约缺口反馈点名的是这一个，带来源/带永久标记的重载不在本次范围，见"备选方案"一节）。
   ABI 只能新增：用"带默认实现的接口成员"（既有契约同类扩展先例，见地面坐标施法请求相关决策）
   新增这四个成员，不要求任何既有实现类型连带改动即可继续编译通过。

2. **默认实现的语义按"只读查询"与"写路径"两分，不搞一刀切**：
   - `Knows`/`GetKnownSkills`（只读查询）默认分别返回"否"/空列表，语义是"这个宿主实现不维护
     已知技能账本"。这类只读查询允许一个明确、保守的降级默认值，与契约里已有的另一处降级默认
     （施法就绪只读快照的默认实现）是同一惯例。
   - `LearnSkill`/`LearnFromBook`（写路径，要求宿主真正记住状态变化）默认实现不能悄悄"什么也不
     做但看起来成功"——运行时写路径不允许静默降级是本仓库的既有硬性约束，只有只读分析类查询才
     允许显式降级；写路径默认 no-op 会让调用方误以为"已经学会"，但随后查询不到，是一种更隐蔽的
     错误。因此这两个默认实现改为抛出一个含义明确的异常，直接告知调用方"这个宿主实现没有技能簿
     能力"，不伪装成功。
   - 组合/包装出的契约实现（若持有并转发内层真实实现）必须显式转发这四个新成员，不能依赖默认
     实现的隐式兜底——本仓库已有一套反射门禁专门检测这类"新增默认成员被组合层悄悄吃掉"的遗漏，
     本次新增的四个成员同样纳入该门禁的检测范围。

3. **既有实现类的四个同名公开方法原地保留、物理签名逐字节不变，改用显式接口实现转发**，而不是
   让它们直接满足新增的契约成员。这不是随意选择——独立核实过程中发现：若让这四个既有公开方法
   直接满足新增的契约成员，编译器会把它们的物理二进制属性从"普通实例方法"改写成"虚方法+密封"
   （这是让既有方法满足契约的必然结果，与契约成员是否带默认实现无关），这个二进制属性变化会被
   本仓库按物理签名比对的 ABI 探针判定为四处破坏性变更——即便任何调用点的编译产物本就不区分这
   两种物理形态、实际运行完全兼容（已用探针"旧编译消费方换新版本二进制、不重新编译"这条实测
   验证过），静态签名比对仍然只看物理属性、不看运行时行为，会误报。改用显式接口实现（只新增
   四个转发方法，不改动原方法本身的任何字节）后，原方法的二进制表现与本次改动之前逐字节相同，
   新增的转发方法本身在二进制里是不参与"公开表面"统计的形态，探针不再误报，也确实不构成任何
   破坏——这才是这四个能力对外一路只有新增、没有变更的真实结果。

4. **顺带把一处面向具体类型的绕行改为面向接口**：表现层一个只读技能书查询的适配器此前的构造函数
   只接受具体实现类型（当时契约上确实没有它需要的查询成员，别无选择）；现在该成员已提升到契约，
   给这个适配器新增一个接受契约接口类型的构造函数重载（保留原有具体类型重载不删，纯新增，不破坏
   ABI），今后的装配代码可以只持有接口引用。

## 后果

### 正面

- 消费方今后可以只持有技能宿主契约接口引用，完成"学技能 → 查询已知 → 从技能书学"这整条链路，
  不再需要下沉到具体实现类型。
- 框架自己代码里"自认契约缺口"的那段注释所描述的状况成为历史，注释已同步更新指向本决策。
- 默认接口成员是纯新增，不要求任何现存实现类型（含各模块测试替身）连带修改即可继续编译通过。

### 负面

- 带来源、区分永久/临时的学习/遗忘重载（装备联动用来做按来源引用计数）仍未提升到契约，装备联动
  模块内部的具名委托绕行仍然保留一部分——这部分未被消费方点名，本次不在范围内（见备选方案）。
- 写路径的默认实现选择"抛异常"而不是"静默且安全的空实现"，意味着任何新写的、不打算支持技能簿的
  契约实现，一旦被调用到这两个新成员就会在运行期而不是编译期暴露"不支持"——这是刻意的（避免
  写路径静默降级），但确实要求调用方对"这个具体宿主实现是否支持技能簿"有基本认知，不能盲目对
  任意契约引用调用这两个成员。

## 备选方案与为什么不选

- **一并把带来源/带永久标记的学习与遗忘重载也提升到契约**：这些重载是装备联动模块按"来源"做
  引用计数的内部机制（同一技能可能被多个来源同时授予，卸下一个来源不应该影响其它来源仍在授予的
  技能），消费方反馈与框架自身注释都只点名了最基础的四个成员，没有证据表明消费方需要按来源的
  细粒度控制。范围外的契约扩张会引入不必要的默认实现设计负担（"来源"这个概念对大多数不做装备
  联动的宿主实现没有意义），故本次只收口消费方点名的四个，其余留待真的出现相应需求时再评估。
- **写路径的默认实现选择"静默空实现"而不是抛异常**：与只读查询统一用同一套"安全降级"逻辑，
  代码看起来更整齐。但这违反运行时写路径不允许静默降级的既有约束——调用方看不到任何信号就以为
  操作成功，之后靠查询才发现落空，是比"当场报错"更差的开发体验，故不选。
- **让既有四个公开方法直接满足新增契约成员，不额外写转发方法**：这是最直白的做法，代码量最少，
  最初也确实这样落地过——但如"决策 3"所述，独立核实发现这会改写既有方法的物理二进制属性，被
  按物理签名比对的 ABI 探针判定为破坏性变更，与本决策"ABI 只新增"的前提直接冲突。改为新增四个
  纯转发方法后，两难被同时满足：契约新增成员有了着落，原方法一个字节都没变。多出的四个转发方法
  是极小的重复样板代码，换来的是探针能够如实反映"这确实是一次纯新增"，权衡后选择后者。
- **不使用带默认实现的接口成员，而是把这四个方法单独抽成一个新的窄接口**（类似表现层那个只读
  查询窄接口的思路，供需要这四个能力的调用方额外持有一个引用）：这不需要动既有契约接口，风险更
  低，但没有解决"这四个能力理应属于同一个技能宿主契约"这个根本问题——调用方仍然需要同时持有两个
  接口引用才能拼出完整能力，且下一次再出现类似缺口又要重复"开一个新窄接口"这套流程。契约本身
  已经有先例证明"用默认接口成员新增能力、不破坏 ABI"是可行路线，故选择直接扩充既有契约，不再
  叠加一个新接口。
