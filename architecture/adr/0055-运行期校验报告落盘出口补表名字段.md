# ADR-0055 运行期校验报告落盘出口补表名字段：日志文本不是契约，同一口径的补齐

状态：已拍板 2026-09-21

## 背景

[ADR-0047](0047-运行期校验报告落盘出口.md) 落地了运行期校验报告的跨进程落盘出口：外部进程（如随
游戏走的独立工具）不再需要解析宿主日志文本，可以直接读取一份原子落盘的 JSON 文档，拿到本次校验的
完整逐条问题集合，外层再包一层轻量信封（单调递增序号、触发来源、时间戳）。

消费方反馈：开发期数据热重载确认/失败时，该信封缺一个关键信息——"这次校验确切针对哪一张表"。热重载
入口本身持有确切的表名（这次改动只重新加载了一张表），却只把这个值用于宿主控制台的日志文本插值，从
未传给落盘出口。信封顶层原有的四个字段（`sequence`/`source`/`timestamp_utc`/`issues`）里，`source`
只是"这是启动校验还是热重载校验"两个固定枚举值之一，不含"哪一张表"；逐条问题元素虽然各自带一个
`table` 字段，但那是"这一条问题出在哪张表"，热重载校验干净（本次改动没有触发任何问题、`issues` 为
空数组）时逐条问题集合完全是空的，从中拿不到"刚才重载的是哪张表"这个信息。独立进程消费方于是只能
退回去解析宿主日志里 `[DataHotReload] 热重载 "<表名>" 成功/失败 ...` 这一行人类可读文本——这与
ADR-0047 落地时同一份类型的判断记录明确写着的"不逼消费方解析任何日志文本，与 ADR-0046 决策 1『日志
文本永远不是契约』同样约束本次落地"直接矛盾：本该被这条通道覆盖的场景，恰好在这一个字段上被漏掉了。

本单是同一口径的补齐，不是新的架构决策：ADR-0046/0047 已经把"消费方不该被要求解析呈现层文本"这条
立场定下来，本单只是把信封字段补全到覆盖这条立场原本就该覆盖的场景。

## 决策

1. **信封顶层新增可选字段 `table`，语义是"这次校验确切针对哪一张表"**：与逐条问题元素已有的
   `table` 字段（"这一条问题出在哪张表"）是两个不同层级、不同语义的字段，不能互相替代——热重载
   校验干净时逐条问题集合为空，仍需要从信封级 `table` 知道刚才重载的是哪张表；启动全量校验下每条
   问题的 `table` 字段依然各自有值，但信封级 `table` 与"这次触发校验的是哪一张表"这个问题本身
   不适用（见决策 2）。新增字段是纯加法：不改动、不重命名、不调整既有四个字段的类型或含义。
2. **热重载来源（`source: "hot_reload"`）下，`table` 是被重载的那张表的确切名字；启动全量校验
   来源（`source: "startup"`）下，`table` 固定输出 JSON `null`，不输出空字符串，也不输出 `"all"`
   一类占位值**：启动全量校验校验的是当前已注册的全部表，不是某一张单一确定的表，"这次校验针对
   哪一张表"这个问题在这个场景下本身没有一个有意义的答案——不该为了让字段"看起来总有值"而编造一个
   缺省即缺省的场景中并不存在的答案。空字符串在很多消费方的字符串处理惯例里会被当作"合法但为空"
   与"缺失"两种含义混用，`"all"` 更是直接可能被字面理解成某张真实存在、名字恰好叫 `all` 的表——
   两者都比"结构化的缺失标记"更容易被消费方误读。`null` 是本文档信封与逐条问题字段集合里已经在用
   的"这个字段本场景不适用"的既有记法（`record_key`/`field`/`group`/`note`/`rule_id` 均如此：未填
   也输出 `null`，不整体省略字段），消费方按可选字段处理即可，不需要为这一个新字段学一套新的缺失
   约定。
3. **两条通道共用同一份序列化实现（`ValidationIssueJsonWriter`）这条既有分工不变，本次新增字段
   不进入该共享实现，只加在落盘出口自己的信封组装代码里**：ADR-0047 决策 2 已经定下"落盘内容的
   逐条问题字段形状与命令行结构化出口（`toolchain/validator --json`）完全一致，两条通道共用同一份
   `ValidationIssueJsonWriter.AppendIssueJson` 实现，不允许分叉"——这条约束覆盖的是"逐条问题"这一
   层，本次新增的 `table` 字段属于"信封"这一层，不属于逐条问题，因此不修改
   `ValidationIssueJsonWriter`，两条通道在逐条问题字段形状上继续保持不分叉。命令行结构化出口本身
   不需要新增这个字段：`toolchain/validator --json` 的输出信封天生覆盖的是"命令行本次传入的全部
   数据根、全部已注册表"一次性校验的结果（信封字段是 `tables`/`fields`/`errors`/`warnings`/
   `blocking`/`table_names`/`issues` 一类"这一批"的统计量，`table_names` 本身就是一个数组，天然
   对应"多张表"），结构上不存在与运行期"某一次触发确切针对哪一张表"对应的单一值——命令行出口没有
   与运行期热重载等价的"单表触发"场景，也就没有这个字段的必要性。
4. **ABI 只新增：新增一组带 `table` 形参的重载，既有重载保留并委托给新重载（`table` 缺省传
   `null`），不修改任何既有公开方法的形参列表**：`ValidationReportFileOutlet.WriteIfConfigured`/
   `Write`/`BuildJson` 三个方法各自新增一个多一个 `string? table` 形参的重载，既有不带 `table` 的
   重载原样保留、方法体改为委托给新重载并显式传 `table: null`，返回值与副作用与本次改动前逐位
   一致。三处启动全量校验调用点（游戏模板的启动流程一处、引擎适配层两个独立的宿主组合根各一处）
   不需要改动，继续调用既有的不带 `table` 重载，等价于显式传 `null`；唯一改动的调用点是开发期数据
   热重载标准实现里的重载单张表方法，把已持有的表名局部变量一并传给新重载。

## 后果

### 正面

- 独立进程消费方第一次能在不解析任何宿主日志文本的前提下，知道"这次热重载确认/失败对应哪一张
  表"，补齐了 ADR-0047 落地时本该覆盖、却在这一个字段上留白的场景，消除了与该类型自身判断记录
  "日志文本永远不是契约"相矛盾的既有状态。
- 纯加法：既有四个信封字段与全部逐条问题字段一个不改，未设置落盘路径时依然不产生任何文件，三处
  启动全量校验调用点不需要任何改动，只有热重载这一个调用点需要补一个已有的局部变量。

### 负面

- 信封字段集合从三个必需字段（`sequence`/`source`/`timestamp_utc`，`issues` 视为第四个必需字段）
  变成"四个必需 + 一个可选（可能为 `null`）"，消费方读取该字段前需要判断是否为 `null`——这是任何
  新增可选字段都无法避免的额外心智负担，本单认为收益（消除对日志文本的依赖）大于这一点点读取端的
  额外判断。

## 备选方案与为什么不选

- **启动全量校验下 `table` 输出空字符串 `""`**：决策 2 已详述——空字符串在很多消费方的字符串处理
  习惯里会被当作"合法但为空的值"而不是"这个字段不适用"，容易被误判为"这次校验的表名恰好是空
  字符串"这种不存在的场景。故不选。
- **启动全量校验下 `table` 输出占位字符串 `"all"` 或 `"*"`**：比空字符串更危险——`"all"`/`"*"`
  完全可能与未来某张真实存在的表同名（表名本身没有保留字机制禁止这类字面量），消费方按字符串比对
  表名时会把"这不是针对单一表的校验"误判成"这次校验针对一张真的叫这个名字的表"。故不选。
- **把 `table` 字段直接加进 `ValidationIssueJsonWriter.AppendIssueJson`（逐条问题层）而不是信封
  层**：逐条问题本来就已经有自己的 `table` 字段（"这一条问题出在哪张表"），语义已经被占用，重复
  或覆盖这个字段只会制造混淆；且"热重载校验干净、`issues` 为空数组"这一常见场景下逐条问题集合
  里根本没有任何元素可以携带这个信息，只有信封层能承载"这次触发确切针对哪张表"，故信封层是唯一
  能覆盖全部场景的位置。
- **`toolchain/validator --json` 的信封同步补一个等价字段**：决策 3 已详述——命令行出口的信封
  天生是"一批表"的统计量，结构上没有与运行期"单次触发确切针对哪一张表"对应的单一值，勉强补一个
  多数时候只能是 `null` 的字段没有实际消费场景，故不选，两条通道继续只在"逐条问题"这一层共用
  同一份实现，不在"信封"这一层强行对齐。

## 与 ADR-0046/0047 的关系

本单不改变 ADR-0046 决策 1"日志文本永远不是契约"、ADR-0046/ADR-0047 已确立的"结构化转发/落盘是
唯一应该被依赖的契约"这条立场，也不改变 ADR-0047 决策 2"两条通道共用同一份逐条问题序列化实现，
不允许分叉"这条约束（本单新增字段刻意避开该共享实现，只加在信封组装代码里，理由见决策 3）。本单
是 ADR-0047 落地时遗漏的一个字段的补齐：ADR-0047 决策 4 已经解决了"消费方如何区分最新结果/结果是
否通过"，本单进一步解决"消费方如何在不解析日志文本的前提下知道这次结果对应哪一张表"，两者是同一条
立场（跨进程消费方不应该被逼着解析呈现层文本）在信封字段集合上的两次独立补齐，不冲突、不重复。

## 魔兽世界的对应做法

无直接对应（本决策是框架自身运行期校验可观测性基础设施的字段补全，服务的是内容工具链的跨进程协作
场景，不对应魔兽世界任何具体游戏系统设计，同 [ADR-0046](0046-运行期校验报告结构化转发出口.md)/
[ADR-0047](0047-运行期校验报告落盘出口.md) 判断记录同一立场）。
