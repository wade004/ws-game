# ADR-0086 创建期异常隔离与诊断信息不丢失

状态：已拍板 2026-09-25

## 背景

消费方反馈（第三十二批，阻塞项，ADR-0085 同批复核遗留）：跨图读档后，`ViewBinder.TryGetView`
对全部存活生物返回 false，实体本身正常。框架侧用生产装配复现不出来（见 ADR-0085"背景"一节的
复核结论），但复核过程中确认了三处会放大同一类故障的缺口，均已在消费方日志里留下痕迹：

1. 消费方日志里，"订阅者处理 `entity.created`/`save.loaded` 时抛出异常"这条诊断几乎每次运行都
   出现，但排查不出是谁抛的、抛的什么——诊断消息只有事件 key 一项，没有订阅者标识、异常类型、
   异常消息。
2. 引擎适配层把诊断转发到宿主控制台时，只转发消息文字，异常对象整个被丢弃（类型、堆栈全部
   丢失）；且转发去重只按消息文字做键，两个类型不同但文字凑巧相同的异常会被误判成同一条，重复
   出现的异常在去重后彻底不留痕迹。
3. `ViewBinder.OnSaveLoaded` 的补建/装备外观对账是循环——为全部未绑定/存活实体依次调用
   `OnEntityCreated`（或调用 View 的销毁/外观重置方法）。循环里任何一个实体的视图工厂/View 方法
   抛出异常，会中断整个循环：该实体之后排队的全部实体都拿不到处理机会。异常本身又被事件总线的
   订阅者异常保护吞掉（见 1），外部只剩一条看不出内容的诊断——这足以单独产生"无一幸免"的症状
   形态，且与消费方所报现象吻合。
4. ADR-0085"后果"一节已经指出但当时未处理的负面项：`GameplayAssembly.AttachSceneRouter`
   隐含"传入的场景路由构造时用的钩子注册表与 `GameplayAssembly.Hooks` 是同一实例"这一装配惯例，
   没有任何防呆——不同实例时 `ScenePostLoad` 钩子（跨图读档完成通知的补发点）永远不会触发，
   读档一直挂起且没有任何异常/诊断，只能在实际卡死时才被发现。

## 决策

四处都是"运行时故障被放大或被隐藏"类缺口，不改变任何成功路径的行为，只改失败路径的可观测性与
隔离性。

1. **`ViewBinder` 逐实体隔离。** `OnEntityCreated` 把"建 View（视图工厂创建 + 绑定）"包一层
   捕获：失败时不写入绑定表、记一条带实体 id/kind/displayId/异常类型/异常消息/堆栈的诊断，正常
   返回，不再向上抛异常。`OnSaveLoaded` 内部三段遍历多个实体的循环（销毁陈旧 View、装备外观
   对账；补建这一段直接复用已经隔离的 `OnEntityCreated`）同样逐条捕获——单个实体失败只记一条
   诊断，不影响循环处理其余实体。
2. **事件总线订阅者异常诊断带上订阅者标识与异常类型/消息。** 订阅登记时（在原始处理函数被包进
   内部调用壳之前）取一次"声明类型.方法名"作为订阅者标识；捕获异常时，诊断消息文本本身拼上
   事件 key、订阅者标识、异常类型全名、异常消息；完整异常对象（含堆栈）仍按原有参数位传递，不
   丢失。
3. **诊断转发到宿主控制台不丢异常信息，重复出现不静默丢弃。** 全仓"消息 + 可选异常"形状的错误
   记录契约中，已经携带异常对象的几处（事件总线、钩子注册表、应用生命周期、存档系统、场景路由
   ——即背景第 1 条链路实际流经的那一段）不再只转发消息文字：转发文本带上异常类型全名与堆栈，
   去重键额外纳入异常类型全名与堆栈最顶一帧（不再只按消息文字），两个类型不同、文字相同的异常
   因此不会被误判成同一条。同一去重键重复出现时，不再彻底吞掉：仍然转发一条精简提示，带累计
   出现次数，只是不重复整段堆栈刷屏。诊断契约本身只做加法（新增读取方式），不改任何既有成员
   签名。
4. **`AttachSceneRouter` 钩子注册表同实例防护。** 传入的场景路由若能判断其构造时使用的钩子
   注册表（生产装配与全部既有测试夹具构造场景路由用的具体类型可以判断），且与本类型的钩子
   注册表不是同一实例，立即抛异常，消息写清楚原因（哪个钩子、为什么不同实例会导致读档挂起）。
   拿不到可比较的引用（传入的是其它场景路由实现）时不做判断，不强行拦截未知情形。

### 明确不做的事

- **不把场景路由与钩子注册表的耦合换成事件订阅。** ADR-0085"后果"一节提出的替代方案——改为
  订阅总线上的场景加载完成事件，不再依赖钩子注册表是否同一实例——是更彻底的结构性修正，涉及
  生产装配入口改动，本次只做运行时防呆，不做这一步。
- **不扩大诊断契约携带异常对象的覆盖面。** 全仓还有相当一部分模块的错误诊断契约从一开始就只
  是纯字符串（从未捕获过异常对象），本单不逐个给它们的 `Error` 调用点补上异常参数——那是另一个
  独立的、覆盖面大得多的收口，只在背景第 1 条实际流经的链路上做了修复。
- **不改变事件总线"单个订阅者异常不影响其它订阅者"的既有隔离粒度。** 本单新增的是"循环内部
  逐实体隔离"，不改动事件总线本身按订阅者逐个捕获异常的既有行为。
- **不新增诊断契约的 Error 级读取通道。** `ViewBinder` 一类只暴露 Warn 一级的诊断契约仍然只有
  Warn；本单不给它们新增 Error 级方法，异常详情按既有惯例拼进 Warn 的消息文本。

## 后果

### 正面

- 单个实体的显示资源缺失/损坏不再能连累同一次对账循环里排在它后面的全部实体。
- 排查"某订阅者处理某事件时抛异常"不再需要额外复现——诊断本身就带够定位所需的信息。
- 两个不同异常不会因为消息文字相同而在宿主控制台上互相覆盖，重复出现的异常也不会无声消失。
- 场景路由与钩子注册表实例不一致这一装配错误，从"读档卡死才发现"变成"装配时立即报错"。

### 负面

- 诊断转发文本变长（带类型全名与堆栈），宿主控制台单条日志的字节数增加。
- `ViewBinder` 补建循环里一个持续失败的实体，每次全量对账都会重新尝试并重新记一条诊断——不做
  失败实体的短期免疫处理；这与既有"周期性重试而非熔断"的取舍一致（见 ADR-0085"备选方案"一节
  对类似取舍的说明），不在本单改变。

## 备选方案与为什么不选

- **给 `ViewBinder` 的对账循环加"失败即整体跳过"的熔断**：会把"一个实体的局部问题"重新放大成
  "整批实体都不处理"，与本单要解决的问题方向相反。未采纳。
- **诊断转发保留纯字符串去重键，只在消息文本里追加异常类型**：类型文字凑巧相同仍可能与其它
  消息哈希碰撞导致误判，且不解决"重复出现即消失"的问题。未采纳，改为去重键本身纳入类型与堆栈
  顶帧。
