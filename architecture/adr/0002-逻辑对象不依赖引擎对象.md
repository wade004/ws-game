# ADR-0002 逻辑对象不依赖引擎对象

状态：已拍板 2026-09-04

## 背景

如果世界模拟的核心对象（单位、物件、弹道等）直接继承或组合引擎提供的节点/组件类型，逻辑代码就会天然被锁死在某一种引擎之上：换引擎意味着重写整个对象模型，脱离引擎单独测试逻辑也无从谈起。架构目标要求"引擎可替换"且"每个模块可脱离引擎独立测试"，这两条目标都要求逻辑对象与引擎对象在类型层面彻底解耦。

## 决策

世界模拟 WorldSim 由纯逻辑对象构成，对象继承关系固定为：

```
Entity
 └─ Unit
     ├─ PlayerUnit
     └─ CreatureUnit
 └─ GameObject
 └─ Projectile
 └─ AreaTrigger
 └─ DroppedLoot
```

这些类型不继承任何引擎节点/组件基类，只依赖 [../02_引擎适配层.md](../02_引擎适配层.md) 声明的窄契约接口（如空间查询、导航）。每个逻辑对象在需要被看见时，由表现层为其创建一个 View 绑定（见 [../09_表现层.md](../09_表现层.md) View 绑定协议），View 只读该逻辑对象的状态、只订阅其事件，不反向持有或修改逻辑对象。

## 后果

### 正面
- WorldSim 可以在完全不启动引擎、不创建任何 View 的情况下独立 tick、独立测试（见 [../11_工程规范与测试.md](../11_工程规范与测试.md) 模块单测/集成测试）。
- 更换引擎时，只需要重新实现引擎适配层与 View 的具体渲染细节，WorldSim 与全部规则层/玩法层代码不受影响。
- 逻辑对象的字段与行为完全由数据与规则决定，避免"引擎组件的生命周期钩子"与"游戏逻辑的状态机"两套生命周期互相纠缠导致的隐性耦合。

### 负面
- 需要额外维护一层 View 绑定协议与同步机制（位置、朝向、事件转发），比"逻辑直接就是引擎节点"多一层间接开销与实现工作量。
- 对不熟悉这种分层方式的开发者，初期需要适应"逻辑对象看不见、摸不着引擎世界"的心智模型。

## 备选方案与为什么不选

- **逻辑对象直接继承引擎节点**（常见的"脚本挂在场景节点上"模式）：实现门槛低、上手快，是多数引擎的默认推荐做法，但会导致逻辑与引擎强绑定，直接违反"引擎可替换"与"零引擎依赖可独立测试"两条架构目标，且规则层单测必须启动引擎环境，测试成本高、速度慢。
- **逻辑对象与引擎对象一一双向绑定（逻辑可反查引擎对象）**：折中方案，看似灵活，但一旦逻辑代码可以拿到引擎对象引用，边界形同虚设，长期会被滥用为逻辑直接操作渲染细节的后门，因此不采纳，改为单向的 View 只读绑定。

## 魔兽世界的对应做法

魔兽世界服务端的对象模型（Object/Unit/Player/Creature/GameObject/DynamicObject/Corpse/Item 等）本身就是纯服务端数据结构，完全不知道客户端渲染细节，客户端只是根据服务端广播的状态与事件去驱动模型/动画表现。本 ADR 把这种"服务端权威、客户端只读投影"的解耦关系，在单机场景下改造为"逻辑层权威、表现层只读 View"的对应关系，解耦思想一致，只是不再涉及网络同步。
