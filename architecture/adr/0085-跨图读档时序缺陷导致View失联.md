# ADR-0085 跨图读档时序缺陷导致 View 失联

状态：已拍板 2026-09-25

## 背景

消费方反馈（第三十二批，阻塞项，基于冻结发布提交核实）：跨图读档（地图 A 存档 → 传送到地图
B → 从 B 读档切回 A）之后，`Presentation.ViewBinding.ViewBinder.TryGetView` 对全部当前存活
生物实体返回 false——既包含读档快照里原本就有的实体（如玩家自身），也包含读档完成之后剧情
继续推进时才全新生成的实体。实体本身在逻辑层是存活、可查询、AI 正常运作的，只是表现层的 View
绑定缺失。

消费方给出的因果推断：`GameplayAssembly.RestoreFromSlot` 的执行顺序是先
`SaveSystem.Load(slotId)`、再（目标地图与当前地图不同时）`ISceneRouter.LoadScene(...)`；
`SaveSystem.Load` 尾部同步 `PublishImmediate(SaveLoadedEvent)`，早于 `LoadScene` 触发的
`IWorldSim.ClearAll()`——`ViewBinder` 订阅 `save.loaded` 做的一次性对账因而针对一个必然被
`ClearAll` 整体推翻的中间态，且此后没有第二次对账。复核确认这条推断方向正确、但只解释了一半：
它没能解释"读档完成之后才全新生成的实体"为什么也没有 View——这些实体走的是与读档快照完全无关
的正常 `entity.created` 路径，`ViewBinder` 对该事件的订阅本身没有任何缺陷。

用真实 `GameplayAssembly` + `Core.Foundation.SceneRouter.SceneRouter` + `ViewBinder` + 真实
`Core.Foundation.SaveSystem.SaveSystem`（`presentation/view_binding/tests/
CrossMapRestoreViewRebindTests.cs`）复现，定位到两个独立根因。

## 决策

### 根因 1：`save.loaded` 在跨图读档分支里发得太早

`Core.Foundation.SaveSystem.SaveSystem.Load`（改动前，行为等价于本次改动后
`deferLoadedNotification: false` 分支）逐段恢复完成后立即
`PublishImmediate(new SaveLoadedEvent(slotId))`——这在同图读档/普通存档场景下是对的（读档
这一刻确实就是"世界最终态"），但 `GameplayAssembly.RestoreFromSlot`（改动前 1374 行起）的跨图
分支要在这之后才发起 `ISceneRouter.LoadScene`，而 `LoadScene` 内部的 `ClearAll` 会把
`ViewBinder.OnSaveLoaded`（`presentation/view_binding/core/ViewBinder.cs:320`）刚对账出来的
View 全部当垃圾销毁。"读档完成"这个通知在跨图分支里被过早地在一个必然被推翻的中间态上发出，
之后再没有第二次对账机会。

### 根因 2：`SceneRouter.FinishLoading` 从不在 post_load 钩子之后补发 `DispatchPending`

`Core.Foundation.SceneRouter.SceneRouter.FinishLoading`（`core/foundation/scene_router/core/
SceneRouter.cs:273`）只在 `ClearAll` 之后调用过一次 `_bus.DispatchPending()`
（289 行，冲刷销毁事件），随后调用 `WellKnownHooks.ScenePostLoad` 钩子（301 行，生产装配的
`GameplayAssembly.EnterMap` 在此钩子内运行，`Loot.ReattachToWorld`/`Spawn.ApplyForMap`/玩家
重新 `AddEntity` 等步骤都在这里发生），但此后再没有任何一次 `DispatchPending`。
`IWorldSim.AddEntity` 对 `entity.created` 走的是 `Enqueue`（入队，非立即派发），这批实体的
`entity.created` 因此要等某个不确定的未来 `world.Tick()`（其内部阶段管线自带
`DispatchPending`）才会被送达 `ViewBinder`。这条根因与存档/读档完全无关：**普通进图（第一次
`LoadScene`）、同图读档、跨图读档**三条路径下，`EnterMap` 新增的实体全部受影响，也同等地解释
了"读档完成后才全新生成的实体也没有 View"这半个现象——它们与读档快照里的实体走的是同一条
`IWorldSim.AddEntity` → `entity.created`（Enqueue）路径，缺的不是订阅或语义，是一次迟迟不来
的 `DispatchPending`。

### 修复：把"读档完成"的语义钉死在"世界最终态"那一刻，而不是让下游各自猜

设计层判断：`save.loaded` 的语义应当是"读档已经完全落定"；跨图分支里它在场景切换前触发，这
本身就是时序缺陷，应当从时序源头修——把"读档完成"的通知挪到世界真正达到最终态之后再发，而不
是让每个订阅者各自猜测"这次是不是还要再等一次场景切换"。**不采用"无条件把 `save.loaded` 重新
派发一次"的方案**：`ISaveSystem` 目前只有一个实现，事件总线也没有去重机制，无条件二次派发会让
全部订阅者收到两次通知，即使当前这批订阅者事后审计（见下节）确认都是幂等的，这仍然是把"意外的
重复副作用"作为既定行为固化进契约，本 ADR 不接受这个代价。

具体改动（均为新增成员，不改动任何既有公开签名）：

1. `ISaveSystem` 新增两个带默认实现的接口成员（`core/foundation/save_system/contracts/
   ISaveSystem.cs`）：`LoadResult Load(Id slotId, bool deferLoadedNotification)`（默认退化为
   `Load(slotId)`，即默认不延迟）与 `void NotifyLoaded(Id slotId, int? migratedFromVersion)`
   （默认空实现）。`Core.Foundation.SaveSystem.SaveSystem`
   （`core/foundation/save_system/core/SaveSystem.cs:251`/`260`/`506`）实现真正的延迟逻辑：
   `deferLoadedNotification: true` 时跳过尾部的 `SaveMigratedEvent`/`SaveLoadedEvent` 派发，
   调用方必须自行在认定的"世界最终态"时刻调用 `NotifyLoaded` 补发。
2. `GameplayAssembly.RestoreFromSlot`（`core/gameplay/assembly/GameplayAssembly.cs:1374`）
   跨图分支改用 `deferLoadedNotification: true`，把待补发的 `(slotId, migratedFromVersion)`
   记入新增私有字段 `_pendingRestoreNotification`；同图分支/无场景路由/`LoadScene` 直接抛出
   异常的分支保持原语义，立即调用 `NotifyLoaded`。
3. `GameplayAssembly.AttachSceneRouter`（同文件 1609 行）新增一次性注册：经共享的
   `Hooks`（与传给 `SceneRouter` 构造函数的是同一个 `IHookRegistry` 实例）以 `order: 1000`
   （远大于 `ISceneRouter.RegisterPostLoadHook` 固定使用的 `0`）注册
   `OnScenePostLoadFlushAndNotify`（1659 行）——保证在生产 post_load 钩子（`EnterMap` 等）都
   跑完之后才执行：先无条件 `_bus.DispatchPending()`（对普通进图/同图读档/跨图读档三条路径
   一视同仁，修复根因 2），再检查 `_pendingRestoreNotification`，非空则消费并调用
   `SaveSystem.NotifyLoaded`（修复根因 1，此时世界已是 `EnterMap` 跑完之后的最终态）。
4. 兜底：`GameplayAssembly` 构造函数新增对 `AppEventKeys.StateChanged` 的订阅
   （`OnAppStateChangedForPendingRestoreNotificationFallback`，1691 行）——若跨图读档发起的
   `LoadScene` 因资源失败被 `SceneRouter` 取消（`HandleLoadFailure` 把应用状态转回
   `AppState.MainMenu`，且不会触发 post_load 钩子），`_pendingRestoreNotification` 会靠这个
   兜底在状态转回 `MainMenu` 时补发，不会永久卡住、不会让"读档本身仍然算成功"这条既有承诺落空。

### `save.loaded` 全部订阅者审计结论

逐一复核仓库内 `SaveEventKeys.SaveLoaded` 的全部生产订阅者（不含测试与历史审计快照）：

| 订阅者 | 处理逻辑 | 时机变化是否安全 |
|---|---|---|
| `presentation/view_binding/core/ViewBinder.cs:133` | `OnSaveLoaded()`：对当前快照做销毁/创建/重置对账，本身就是本次修复要修的那个订阅者 | 安全，且是本次修复直接受益者 |
| `presentation/shell/core/ShellViewModel.cs:45` | `OnRelevantEvent(evt) => Refresh()` | 安全，纯重渲染，幂等 |
| `presentation/ui/core/ViewModels/ActionBarViewModel.cs:212` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/CharacterStatsViewModel.cs:62` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/DialogViewModel.cs:69` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/HudViewModel.cs:290` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/InventoryViewModel.cs:83` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/QuestLogViewModel.cs:70` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/SaveSlotsViewModel.cs:32` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/ShopViewModel.cs:77` | 同上模式 | 安全 |
| `presentation/ui/core/ViewModels/SkillBookViewModel.cs:52` | 同上模式 | 安全 |

结论：全部 12 个订阅者要么是本次修复的目标本身（`ViewBinder`），要么是"收到事件就整体
重渲染/清缓存"的幂等处理，不存在"只能在场景切换前收到才对"的隐含时序假设。三条路径（普通
进图不涉及 `save.loaded`；同图读档走立即派发，时机完全不变；跨图读档从"逐段 Load 刚完成"
延后到"EnterMap 也跑完"）里，只有跨图读档一条路径的派发时机发生了可观察的变化，且变化方向
是"更晚、更接近直觉上的完成时刻"，不改变事件本身的字段与语义。

### 明确不做的事

- 不改变同图读档、无场景路由、`LoadScene` 直接抛异常这三种既有分支的 `save.loaded` 派发时机
  ——它们本就发生在世界最终态之后，不受本次修复影响。
- 不给 `SceneRouter.FinishLoading` 本身加无条件的"post_load 之后再补一次 DispatchPending"
  ——修复钉在 `GameplayAssembly.AttachSceneRouter` 新注册的钩子里，而不是改
  `Core.Foundation.SceneRouter.SceneRouter` 的内部实现；`SceneRouter` 对外的
  `RegisterPostLoadHook` 契约（固定 `order: 0`）保持不变，这次新增的高 `order` 钩子走的是
  `IHookRegistry` 已有的公开排序机制，不是新契约。
- 不处理"跨图读档过程中应用状态从 `Pause` 发起"这类更冷门的边缘状态转移组合——`
  AppStateMachineConfig.Default()` 未登记 `Pause → Loading`，本次没有证据表明消费方场景涉及
  这条路径，留作后续如有反馈再单独处理，不在本次范围内。
- 不改动 `core/gameplay/spawn/core/SpawnHost.cs` 的既有"存活实体"重建逻辑——复核确认它从不
  持久化原始 `EntityId`，跨图读档后 `OnMapEnter` 策略的生物本就会经 `EnterMap` 正常重新生成，
  不是本次两个根因之外的第三个问题。

## 后果

### 正面

- "存活实体 ⟺ 已建 View" 这条不变量现在在普通进图、同图读档、跨图读档三条替换世界内容的路径
  上都成立，读档完成之后继续生成的新实体也不再受影响。
- 修复不改动任何既有公开成员签名，全部通过带默认实现的接口成员新增；`ISaveSystem` 仓库内唯一
  实现 `SaveSystem` 覆盖了真正的延迟逻辑，其余假设的实现者不做任何改动也能继续编译通过。

### 负面

- `GameplayAssembly` 现在依赖"`Hooks` 与传给 `SceneRouter` 构造函数的是同一个 `IHookRegistry`
  实例"这一装配惯例；若未来某个装配路径改为传入两个不同实例，`OnScenePostLoadFlushAndNotify`
  钩子不会被 `SceneRouter` 触发，`_pendingRestoreNotification` 会一直靠 `AppEventKeys.
  StateChanged` 兜底或永久挂起直到下一次进入 `MainMenu`——这是本次修复引入的一个隐性耦合，
  未在代码层面加断言防呆，留意后续若拆分装配路径需要同步处理。

## 备选方案与为什么不选

- **无条件把 `SaveLoadedEvent` 在 `LoadScene` 完成后再重新 `PublishImmediate` 一次**：改动
  最小，但会让全部订阅者在跨图读档时收到两次通知；即使本次审计确认当前 12 个订阅者都幂等，
  这仍是把"重复派发"固化为契约的一部分，且不修复根因 2（新生成实体仍然没有 View）。未采纳。
- **在 `SceneRouter.FinishLoading` 内部无条件加一次 `DispatchPending`**：能同时修复根因 2，
  但把"游戏层 post_load 钩子里做了什么"这个假设编进了基础架构的场景路由模块内部实现，且需要
  改动 `Core.Foundation.SceneRouter.SceneRouter` 本身（消费方对框架仓库只读冻结发布提交，
  改动面越小越有利于后续独立验证）；改在 `GameplayAssembly.AttachSceneRouter` 用已有的
  `IHookRegistry` 排序机制同样能达到效果，且不触碰 `SceneRouter` 内部实现。未采纳。
- **让 `ViewBinder` 自己订阅场景路由的 `SceneLoadFinishedEvent` 做二次对账，而不改
  `save.loaded` 的派发时机**：只修复了根因 1 里 `ViewBinder` 自己这一个订阅者，其余 11 个
  订阅者（尤其是需要感知"存档确实已经落定"的 `SaveSlotsViewModel` 等）依旧可能在一个不完整
  的世界状态上收到通知；根因 2（新生成实体缺 View）也完全没有被覆盖到，因为它与 `save.loaded`
  的派发时机无关。未采纳。

## 魔兽世界的对应做法

无直接对应——本条是本架构自身事件时序编排的缺陷修复，不涉及具体游戏机制设计。
