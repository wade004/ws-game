# ADR-0134 实验室引擎宿主：同一运行入口加扩展钩子，逻辑指纹跨宿主逐字节一致

状态：已拍板 2026-10-03（对 [ADR-0120](0120-手感实验室为框架交付物.md) 决定 1"一个内核、两个宿主"中引擎宿主的落地决定；手感落地 M4-H 引入，M4-W4 补原生相机相对控制空间、帧时间源接入与 GPU 帧耗时）

## 背景

ADR-0120 规定实验室是"一个内核、两个宿主、一份数据集"，无头宿主此前已落地并承担日常回归，引擎宿主一直未提供。无头宿主用桩适配层与假视图，证明得了"逻辑指令发对了"，证明不了"适配器把逻辑指令画对了"：命中帧与动画关键帧是否同刻、镜头冲击曲线、顿帧期间角色与粒子是否真的冻住、真实资源加载出来的图标与逐层剪辑、帧耗时。这些必须在真实适配器上观测。

引擎宿主的风险是第二套循环：如果它自己推进模拟、自己组装世界，就会与无头宿主出现两份"同一场景"，指纹比对失去意义，实验室的核心承诺（同一输入脚本在任何宿主上逻辑结果相同）也就无从保证。

## 决策

1. **同一运行入口加扩展钩子，不是第二套循环**：引擎宿主就是无头宿主用的同一个运行入口，外加一个扩展接口。扩展的挂接点固定为：挂接、包装视图工厂、反馈分流、就绪、相机朝向查询与控制空间覆盖、脚本轴输入观测、每个固定步末尾、每个表现帧、收尾；多个扩展可叠加。扩展只能在内核已有的时序上观测与分流，**不得改变逻辑**。

2. **逻辑指纹逐字节一致**：同一脚本、同一格子，引擎宿主与无头宿主产出的逻辑组指纹必须逐字节相同。这是新增的跨宿主不变量，在引擎侧自动化测试里对全部手感场景脚本逐字节比较；它是"引擎侧只画、不改判定"的机器证据。

3. **引擎侧失败隔离到记录里**：引擎侧装配与驱动中的任何异常都被吞进录制里的"引擎错误"列表（成为度量），引擎视图创建失败时该实体退回内核的假视图；失败不得传播、不得改变逻辑。

4. **引擎侧度量是条件组，不污染无头基线**：引擎度量组只在引擎宿主的度量注册表里存在，缺省注册表不含它，所以无头运行与既有基线、不变量逐字不变。组内度量：命中帧对齐（样本数、缺失数、误差）、镜头冲量曲线（与线性衰减的偏差、单调、残余）、顿帧期间角色与粒子的推进量（冻结目标应为零，旁观与对照单位应大于零）、CPU 帧耗时分布、GPU 帧耗时分布、相机相对输入误差、换装图层核对、引擎失败数。真实时钟类度量归"实时类"，只做量级上限检查，不逐字节比较。

5. **GPU 帧耗时只在存在图形设备的环境取得**：取不到时（无图形设备的批处理、不支持异步回读、渲染或回读出错）度量照样在场，状态度量标为"不可用"，数值取哨兵值（不超过任何倍率上限，基线比较不误报），原因写进记录；整次运行要么全有数、要么全标不可用，不留一半有数一半没数的分位数。"不可用"是被记下来的状态，不是缺失。

6. **模拟时间驱动表现**：宿主关闭引擎组件自己的逐帧更新，由舞台按模拟时间推进帧动画、特效序列、动画器与相机，因此快放、慢放、批处理下结果可复现。推进经 [ADR-0136](0136-可注入帧时间源.md) 的公开时间源入口完成。

7. **渲染隔离**：舞台物体放在专用图层，舞台相机只渲染该图层，场内其它相机在舞台存续期间剔除该图层，销毁后恢复且不留物体；依赖像素或相机取景的测试不得受别的用例残留影响。

8. **覆盖存储与 A/B**：覆盖集 = 名字 + 若干"手感字段 + 操作（set/multiply/add/remove）+ 值 + 作用单位（空为全局）"的写入，本地文件存储，经手感装配的运行期调试覆盖层生效，**源数据与档案文件一字不动**；写入按字段登记校验（字段未登记、不允许该操作、值种类不对都拒绝并返回问题清单，不碰存储）。A/B 对同一脚本同一格子的两组覆盖逐度量求差（B − A），实时类由调用方过滤。编辑器面板的全部状态与逻辑放在纯逻辑的面板模型里（无引擎即可测试），窗口只绘制。

9. **输入噪声模型与回放**：脚本层可注入延迟、抖动与丢事件（种子化），噪声结果被记录、可逐字节回放；纯延迟噪声使逻辑响应恰好晚延迟的 tick 数。

10. **落地形态**：引擎宿主是引擎适配包里的可选组件，独立程序集，不被默认引用、不进玩家构建；实验室内核与它依赖的核心库由构建同步为引擎侧的预编译库（构建产物，不入库）。放在适配包内是为了就近驱动适配器的内部推进入口，并与适配器同版本发布，而不是另起一个独立包。

11. **真机手测的范围边界**：真人在真实设备上的试玩评分判断的是"某个游戏的数值与手感取舍是否达标"，不是框架能自动替代的。框架提供可复现的场景脚本、覆盖存储与 A/B、输入噪声模型、CPU 与 GPU 帧耗时，以及一份给游戏团队用的验收清单（见实验室模块说明）；清单的执行记录与结论存进**游戏自己的仓库**，不进框架仓库。

## 后果

### 正面

- 实验室的核心承诺落到机器上：同一脚本在无头与引擎两个宿主上逻辑相同，引擎侧另有"画对了没有"的度量。
- 没有第二套循环，也就没有第二份"同一场景"的维护成本。
- 引擎侧失败不会让逻辑漂移，也不会让整个运行中断，而是变成可比对的度量。
- 覆盖存储与 A/B 让调参结果在写回数据之前就能被基线比较，源数据不被污染。

### 负面

- 引擎宿主的验证依赖引擎侧自动化测试环境，不在无头门禁里；合并前后需要在有引擎的环境里补跑。
- GPU 帧耗时在无图形设备的批处理里取不到，门禁里的引擎侧测试只能看到"不可用"状态，GPU 数值要在带图形设备的环境里采。
- 命中帧对齐度量如实反映姿势集数据与技能时间线的偏移，数据没对齐时度量会如实报差，宿主本身不修这个差。

## 备选方案与为什么不选

- **引擎宿主自带一套运行循环与装配**：两份"同一场景"，指纹比对失去意义；否决。
- **让扩展可以改逻辑（例如按引擎时钟推进模拟）**：逻辑指纹不再跨宿主一致，实验室承诺落空；否决，扩展只观测与分流。
- **引擎侧失败直接抛出**：一次渲染异常就让整段回归中断，且无法与基线比较；否决，吞进记录并成为度量。
- **把引擎度量并进基础度量组**：无头基线全部要重烘；否决，条件组。
- **覆盖直接改源数据文件**：调参实验污染数据、难以回退；否决，覆盖层加独立存储。
- **把真机手测做成框架自动化**：评分对象是游戏自己的取舍，框架没有判据；否决，只提供清单与可复现工具。

## 魔兽世界的对应做法

无直接对应：魔兽的客户端与服务端各自独立，没有"同一输入在两种宿主上逐字节一致"的验证需求；本 ADR 是实验室自身的工程决定。
