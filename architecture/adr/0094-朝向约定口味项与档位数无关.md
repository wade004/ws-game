# ADR-0094 朝向约定口味项与档位数无关

状态：已拍板 2026-09-26

## 背景

消费方第三十九批反馈：朝向约定（05 第 3.1 节，逻辑朝向角度 0 表示正前方、以下述参照系为准，
量化到方向档位数 N 档）里，"角度 0 对应的屏幕朝向"和"角度增长方向是否与镜头左右手一致"这两件事
在不同具体游戏的镜头/摄像机取向下并不总是与框架默认约定吻合，此前唯一的应对办法是各游戏自己在
声明档位数或量化规则上做整体变通，等价于让"朝向口味差异"这件与档位数无关的事情去污染"该用几档
朝向"这件配置。`<game>` 内容示例：某镜头的"正前方"在框架默认约定下量化出来的档位实际是屏幕上的
背影，需要为此把 8 档改成看似无关的另一套数字才能绕过去。

## 决策

1. **新增两个朝向口味配置项，在量化之前对逻辑朝向角度做一次统一的"先镜像、再偏移"变换**：先按
   镜像开关决定要不要把角度取负（用于处理角度增长方向与镜头左右手相反的情况），再叠加一个弧度
   偏移量（用于处理"角度 0"对应的屏幕朝向整体旋转了一个固定角度的情况），变换后的角度才进入既有
   的量化到方向档位这一步，量化本身不做任何改动。两项均为可选配置，默认值下（不镜像、偏移量 0）
   变换前后角度逐字节相同，不影响任何未配置该口味项的既有游戏。
2. **口味项作用在"量化之前的原始朝向角度"这一层，而非按具体档位数重新配一张映射表**：事先核实
   过，负责把逻辑朝向换算成方向档位的绑定环节在调用量化之前手上就有未量化的原始弧度角，因此可以
   直接在这一层做统一变换；据此选择"变换原始角度"这个方案，而不是另一个曾设想的"按档位数各配一张
   索引重映射表"方案（见"备选方案"一节）——原始角度层面的变换与档位数无关，配一次就对任意档位数
   生效，索引重映射表则要求每种档位数各自配一份，且改档位数时要跟着重新配。
3. **既有的按索引重映射的配置项，长度与档位数不一致时新增一次性诊断**：该配置项长度必须等于方向
   档位数才会生效，之前长度不一致时是纯静默按不重映射处理；本次改为在同一进程内按（档位数, 表
   长度）这一组合去重记一条一次性告警级诊断（未接诊断出口时仍然纯静默，不引入新依赖），处理结果
   本身不变（仍是按不重映射处理，不抛异常、不中断），只是让"配置数目对不上"这件事不再无声无息。

## 后果

### 正面

- 具体游戏遇到镜头朝向与框架默认约定不一致时，配两个与档位数无关的角度口味项即可解决，不必再把
  "口味差异"和"该用几档朝向"这两件不相关的事情揉在一起变通。
- 默认值下逐字节不变，早于本次改动的既有游戏接入不需要跟着改配置。
- 索引重映射表长度配错时不再是纯静默的隐性问题，能在启用了诊断出口的环境里被看到。

### 负面（已知限制）

- 两个口味项与既有的按索引重映射配置项是两套独立机制，同时配置时先做角度层面的镜像/偏移、量化后
  再做索引重映射，顺序固定不可调；如果具体游戏的诉求恰好需要反过来的顺序，本决策不覆盖，需另行
  提出需求。
- 一次性诊断只去重到（档位数, 表长度）这个粒度，不区分是哪个具体实体触发的；重开进程后会再记一次。

## 备选方案与为什么不选

- **按档位数各配一张索引重映射表（不新增角度层面的口味项）**：不需要新概念，复用既有机制即可；
  但事先核实过绑定环节在量化前拿得到原始角度，能在角度层面一次性解决、与档位数无关，改档位数不用
  跟着重配，故不选这条路线，只把它保留作为"档位数固定、临时只想调个别索引"这种更细粒度场景的既有
  退路，两者并存不冲突。
- **索引重映射表长度不一致时直接抛异常**：能第一时间暴露配置错误，但会把原本可以继续运行（按不
  重映射处理）的既有行为变成中断性变更，对已经这样配置多年、从未注意到这条限制的既有游戏是破坏性
  的；改为一次性诊断，既暴露问题又不改变既有可用性。
