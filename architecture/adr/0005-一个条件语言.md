# ADR-0005 一个条件语言

状态：已拍板 2026-09-04

## 背景

触发条件、优先级表、掉落条件、任务前置、对话显隐、遭遇阶段、成就 criteria、刷新条件……几乎每个玩法系统都需要表达"在什么条件下发生什么"。如果每个系统各自发明一套条件描述方式（各自的字段组合、各自的求值规则），会导致：内容制作者需要分别学习 N 套条件语法；校验工具需要为每套语法单独实现解析与检查；条件语义在不同系统间可能出现不一致的隐性差异。需要一个统一的条件表达式语言贯穿全部系统。

## 决策

Expr 是全架构唯一的条件表达式语言，触发条件、优先级表、掉落条件、任务前置、对话显隐、遭遇阶段、成就 criteria、刷新条件全部使用它书写。Expr 通过统一的宿主查询接口 `query(key, args)` 获取具体上下文数据（如"当前生命值百分比""是否处于战斗中""某世界状态标志是否为真"），不同系统只需要向 Expr 暴露自己的可查询 key 集合，不需要重新实现条件求值逻辑本身。具体语法与宿主引用方式见 [../04_数据与内容管线.md](../04_数据与内容管线.md)。

## 后果

### 正面
- 内容制作者只需要学习一套条件语法，即可在任务前置、掉落条件、遭遇阶段等所有场景复用。
- 校验工具（语法校验、引用完整性校验）只需要维护一套实现，覆盖全部使用场景。
- 新系统接入条件判断时，只需要声明自己的 `query` 可用 key，不需要重新设计一套条件描述格式，降低了新系统的接入成本，也天然符合"新增内容不改代码"的原则（新条件组合是数据，不是代码）。

### 负面
- Expr 语言本身的表达能力需要覆盖所有系统的多样化需求，设计与维护这门通用语言的复杂度集中在一处，一旦发现表达能力不足，影响面是全架构级别的。
- 部分系统的特殊条件需求（如非常规的复杂判定）可能被迫拆解为多个 Expr 组合或通过额外的 query key 变通表达，而不是直接用该系统的"原生"描述方式，短期内可能不如专用条件格式直观。

## 备选方案与为什么不选

- **每个系统各自实现条件描述**（如任务前置用一种格式、掉落条件用另一种格式）：实现门槛低、各自可以贴合自身语义设计，但长期导致条件语言碎片化，维护与学习成本随系统数量线性增长，与架构"骨架统一、模块可复用"的目标冲突，不采纳。
- **不提供通用条件语言，改为对每种条件类型开放代码回调**：灵活度理论上最高，但代码回调无法被数据校验工具静态检查、无法脱离引擎测试、也违反"新增内容不改代码"的原则，不采纳。

## 魔兽世界的对应做法

魔兽世界服务端有一套通用的 Conditions（`conditions` 表）系统，广泛用于任务判定、脚本触发、法术学习限制、副本显隐等场景，通过统一的条件类型枚举 + 参数组合表达各种判断逻辑，避免每个子系统各写一套条件代码。Expr 是对这一"统一条件系统"设计理念的延续，只是改用表达式而非固定枚举参数组合的形式，以获得更灵活的组合能力。
