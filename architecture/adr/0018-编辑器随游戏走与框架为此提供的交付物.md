# ADR-0018 编辑器随游戏走：基础套件按版本消费框架，无头适配层与校验装配入口列为框架交付物

状态：已拍板 2026-09-09

## 背景

框架已定稿"数据即内容"（ADR-0004）：一款游戏的全部内容是 60 余张结构化数据表里的行，运行时只认 id 与字段。内容作者需要一个图形化的内容编辑器来编辑这些表，编辑器的产品方案已成文（`editor/docs/编辑器产品文档.md`）。方案成文后出现了一个归属问题：编辑器代码放在哪里、随谁的版本发布。

现状不够用的地方：

1. 产品文档 v1.1 把编辑器写成随框架同号发布、放在框架仓库 `editor/` 目录、纳入框架门禁。但用户已明确：编辑器是"一个游戏一个编辑器"，跟随具体游戏走，不跟随框架走。框架仓库若承载编辑器可执行程序，与 `落地方案与分阶段计划.md` 第 3.5 节"框架仓库是被依赖方，任何消费方不进入框架仓库"的原则冲突，也会让编辑器的发布节奏被框架发布节奏绑死。
2. 若反过来每款游戏各自从零写编辑器，编辑器 80% 以上的能力（Schema 驱动的通用编辑、字段控件、引用图、校验集成、Expr 编辑器、本地化矩阵、框架表的专项编辑器、沙盘、工具链调用）完全由框架的 `TableSchema` 与核心类库决定，与具体游戏无关，会在每款游戏里重复一遍，并在框架每次升级时各自跟改。
3. 编辑器的数值沙盘需要脱离引擎跑确定性模拟（ADR-0003），依赖桩适配层 `adapters/stub`；该程序集目前明确"专供测试与 CI，不对外发布"，分发包与私服三个包里都没有，消费方拿不到。
4. 编辑器要做到"编辑器里看到的红线 = 门禁会报的错"，必须与 `toolchain/validator` 装配完全相同的校验规则集合（含 04 第 5.1 节列出的需显式接线的可选规则与 `FailOnUnknownTable`/`Strictness` 选项）。这段装配逻辑目前写在 `toolchain/validator/Program.cs` 里，不是核心库内可被第二个消费方调用的入口。

## 决策

沿用框架对"游戏"的既有模式（新游戏 = 引擎适配层 + 薄游戏层 + 数据），把编辑器拆成同构的三层，并明确各层归属：

1. **编辑器基础套件与编辑器模板是一个独立于框架仓库的消费方项目**（下称"编辑器项目"）：有自己的仓库与语义化版本，按版本号经既有通道（`toolchain/get_framework.ps1` zip 通道或私服通道）锁定框架版本，只引用框架的发布产物，不引用框架源码；兼容性按框架 MAJOR 段声明。框架仓库不承载编辑器代码，`editor/` 目录只保留产品文档与本决策记录。
2. **每款游戏的编辑器实例放在该游戏自己的仓库**（如 `<game>/editor/`）：复制编辑器模板改名，与该游戏的工程共用同一份 `ws-game.lock`（因此编辑器实例与游戏运行时使用的框架版本由构造保证一致，不需要运行期动态加载不同版本的框架程序集），另锁定编辑器项目的版本；随游戏版本发布。游戏专属的编辑面板、校验规则接入、沙盘预设、配置均只放在这一层。
3. **框架为此新增两项交付物**，随 `build.ps1 -Dist`/`-Release` 进入 zip 快照与私服包，并纳入 `check.ps1` 的包清单一致性检查：
   - **无头适配层**：把 `adapters/stub`（`Adapters.Stub`）由"仅测试用"改为正式交付物，放入引擎适配层包 `Runtime/Plugins/Core/` 同级目录（或独立包 `com.gamefoundation.adapter.headless`，具体落点在实现阶段按 `build.ps1` 现有组装方式决定），契约签名与 `02_引擎适配层.md` 一致，行为保持"确定性、无渲染、无输入"。
   - **校验装配入口**：把 `toolchain/validator/Program.cs` 中"调用汇总注册目录 + 可选规则接线参数 + 装配选项"这一段抽为核心库内的单一公开入口（落在 `presentation/assembly` 或等价的最外层装配目录），`toolchain/validator` 与编辑器基础套件都只调用这个入口；可选规则（如 `SpawnSummonOnlyCreatureRule`、`DisplayMapCoverageRule`）的接线参数由入口显式暴露，未提供时入口返回"未启用规则清单"供调用方展示，而不是静默跳过。
4. **框架对编辑器只承诺契约，不承诺实现**：编辑器依赖的框架面固定为——`TableSchema`/`FieldSchema`（含 ADR-0019 提议的复合字段子结构）、schema 迁移链、`DataRegistry` 的加载/校验/重载接口、Expr 解析器、校验装配入口、无头适配层、`toolchain` 命令行工具。这些面上的变更在 `CHANGELOG.md` 里单独标注"编辑器相关契约"，破坏兼容时升 MAJOR。
5. **`13_新游戏接入指南.md` 补一步**："复制编辑器模板到游戏仓库"，与"复制 `games/_template`"并列，作为立项步骤的可选项（不强制每款游戏立项当天就建编辑器）。

## 后果

### 正面
- 编辑器归属与框架既有的消费方模型完全同构，"框架仓库是被依赖方"的原则不被打破；编辑器项目与各游戏编辑器实例都可以按自己的节奏发布。
- 通用能力只在编辑器项目里维护一份，各游戏只写真正游戏专属的薄层；框架 MINOR 升级时新表新字段经 `TableSchema` 自动出现在通用编辑器，各游戏不需要改编辑器代码。
- 编辑器实例与游戏运行时共用同一份锁文件，"编辑器看到的表结构与校验规则就是该游戏在用的那一份"由构造保证，不需要多版本并存的运行期加载机制。
- 沙盘结算与框架测试用的是同一个无头适配层，结果一致性不需要编辑器另写一份桩来保证。

### 负面
- 框架多维护两项交付物（无头适配层的发布形态、校验装配入口），并要为"编辑器相关契约"额外承担兼容性标注义务。
- 三层结构意味着三处版本号（框架、编辑器项目、游戏）与两个锁文件（`ws-game.lock`、编辑器项目的锁定记录）需要在游戏仓库里保持一致，升级流程比"一个整体产品"多一步核对。
- 编辑器项目在框架补齐 ADR-0019 的子结构登记之前，对 `Object`/`Array` 字段只能提供 JSON 子编辑，专项编辑器的卡片式表单要等框架侧先做。

## 备选方案与为什么不选

- **编辑器放在框架仓库、随框架同号发布**（产品文档 v1.1 的写法）：与"任何消费方不进入框架仓库"冲突；编辑器发布被框架发布节奏绑死；也不符合用户"编辑器跟游戏走"的明确要求。
- **一个通用编辑器独立产品、运行期按所打开游戏的锁文件动态加载对应版本的框架程序集**：能解决多游戏锁不同版本的问题，但需要编辑器只依赖稳定契约并自行处理多版本程序集隔离，复杂度高；而"编辑器实例随游戏走、与游戏共用锁文件"让这个问题根本不出现。
- **每款游戏各自从零写编辑器，框架不提供任何套件**：通用能力在每款游戏重复实现，框架升级时各自跟改，与 ADR-0014"UI 套件是框架交付物"的同一逻辑相悖。
- **编辑器自己实现一套无头适配层而不发布 `Adapters.Stub`**：不需要改框架，但十几个桩类型会在编辑器项目里复制一份，沙盘结果与框架测试用桩的一致性无人担保。

## 魔兽世界的对应做法

魔兽世界的内容不是由一个随客户端发布的通用编辑器维护，而是由内部工具直接编辑 DBC/服务端模板表（`creature_template`、`item_template`、`spell` 等），工具与具体项目的数据版本绑定，这与"编辑器实例随游戏走"对应。其数据表结构由客户端与服务端共用的表定义驱动，工具按表定义生成编辑界面，对应本架构"编辑器由 `TableSchema` 驱动、框架只承诺契约"的取舍。
