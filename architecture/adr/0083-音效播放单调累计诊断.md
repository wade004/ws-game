# ADR-0083 音效播放单调累计诊断

状态：已拍板 2026-09-24

## 背景

消费方第二十五/二十六批反馈：真实发出 `ui.action_invoked` 后，`play_sfx` 绑定确认已经派发
（事件侧计数为真），但在一个约 0.4 秒的窗口里轮询播放状态，从未观测到两个具体音效
（对应本框架占位素材里两个极短的 UI 音效）播放。框架侧此前两轮复现（确定性用例、真实引擎
适配层运行期用例）均是绿的，因为这些用例断言的是"播放调用发生了且恰好一次"这一计数式结论，
消费方判定的是"轮询播放状态能不能抓到"这一瞬时状态——两者是不同维度的观测方式，绿灯不能
直接说明消费方那一侧也一定能观测到。

本轮定位新增的线索：占位音效本身的可播放时长极短（换算到帧数只有个位数），"是否正在播放"这一
引擎侧瞬时状态天然就只能被观测这么短的一段时间；用轮询去抓一段几帧长的瞬态，本来就存在"抓不到"
的结构性风险，与是否真的发生过播放是两件事。

## 决策

1. **本轮定位结论（通读派发到真实播放这条路径的代码 + 补一条实测计时用例后得出，逐条列出）**：
   - 冷资源（此前从未加载过的音效）从播放请求派发到真正调用底层播放接口之间的墙钟延迟，实测
     （复刻资源加载器"后台线程读取字节 + 排队 + 按帧轮询消费"这套既有架构模式，用与占位音效
     等字节量的临时文件做真实磁盘读取，不是纯内存估算）单次运行为 19.08 毫秒（1 次轮询即完成），
     量级远小于消费方观测到的 0.4 秒窗口——这套加载架构模式本身不会系统性地把开始播放的时刻
     推迟到超出该窗口之外。
   - 播放真正开始之后，"正在播放"这一状态可被观测的时长就等于音效本身的播放时长——底层播放
     实现按"播放中的对象是否已经自然播完"来判定回收时机，不存在额外的提前结束；而占位音效
     本身极短（几十毫秒量级，换算到常见帧率下只有个位数帧），可观测窗口天然就只有这么长。
   - 冷加载完成之后，框架是**补播放**，不是丢弃：加载成功的回调路径里恰好调用一次真正播放，
     由确定性用例钉死"资源就绪前不播放、就绪后恰好补播放一次"这一行为；只有加载失败或首次
     加载超时两种结局才会丢弃且不重试。
   - 逐处检查这条路径后，**没有发现任何静默吞掉播放请求、不留诊断记录的分支**：资源未登记、
     加载失败、加载超时三条丢弃路径均已各自记一条诊断文本。发现一处相邻但不同的既有行为——
     同一播放分组容量已满时会抢占停止一个较低优先级的、已经成功开始播放的实例，这个分支本身
     不记诊断；它属于"提前结束一次已经成功播放的音效"，不是"从未播放"，不在本次结论范围内，
     如实记录、留待后续视情况处理，本次不改动。
   - **综合结论**：现有证据更支持"确实播放了，只是轮询窗口太短、或轮询节奏本身抓不到这么短的
     瞬态"，不支持"播放压根没有发生"（后者已被框架侧确定性用例与两轮真实引擎适配层运行期复现
     共同排除）。"冷加载本身把开始播放的时刻推迟到消费方轮询窗口之外"这一可能性，在本轮实测
     的延迟量级下不成立；但不能排除消费方真实工程里存在本轮未接触到的额外延迟来源（不同硬件、
     不同负载、不同版本的资源加载实现细节等）——**证据不足以完全排除这后一种可能，如实记录为
     未能完全定论，不编造一个看似更完整但缺乏实测支持的结论**。
2. **新增一套与既有文本诊断契约平行、形状不同的单调累计诊断契约**：既有的表现层诊断契约是
   "只增不减的文本消息列表"，供统一的轮询转发机制向宿主控制台转发；本次新增的契约不是文本
   消息，而是四个只读成员——播放请求次数、真正开始播放次数、因资源缺失/加载失败/超时而未能
   播放的次数（三条既有丢弃路径统一计入同一个桶，均已各自伴随一条既有文本诊断，本契约只是
   同一批事件的数值化镜像，不新增判定逻辑），以及最近一次成功播放的记录（播放的资源引用 +
   一个随成功播放次数单调递增的序号，不单独维护一份重复计数）。这套计数错过某一帧不会丢失
   信息——只要在任意时刻读取，就能看到"这些事情曾经发生过"，天然不受"抓瞬态"这一结构性限制
   影响，直接解决背景里描述的"轮询抓不到≠没播放"这一根本性观测偏差。
3. **播放路径的宿主类型新增一个只读出口暴露这份计数，表现层装配根新增一个转发属性把它接到
   消费方够得到的位置**：与既有文本诊断契约的既有转发惯例一致（宿主类型的构造期无条件自建
   一份计数记录并通过只读属性暴露，装配根构造完成后原样转发），不新增可选构造参数、不改变
   任何既有公开方法的签名或行为，纯加法。
4. **新增契约不接入既有的诊断消息统一轮询转发机制**：该转发机制的设计前提是"一份只增不减的
   消息列表，逐帧比较长度、转发新增的一段文本"；本次新增的四个成员是独立计数器与一条可覆写
   的最近记录，不是消息列表，没有"新增的一段文本"可供该机制逐帧比较转发，结构性不兼容——按
   既有决策，这类不适用轮询式转发的诊断契约允许不接入，只需要在其所在模块留痕说明理由，不
   牵强接入制造"看起来已经接好了"的假象。消费方需要时直接读取装配根的转发属性。

## 后果

### 正面

- 消费方不再需要靠抓取一个可能只持续几帧的瞬时播放状态来确认"框架是否真的按预期播放了音效"，
  改为读取一组只增不减的计数与一条最近播放记录，任意时刻读取都能得到确定性结论。
- 定位过程本身用实测数字排除了"这条加载架构会系统性拖慢到超出观测窗口"这一假设，缩小了后续
  排查范围；同时如实标注了尚未能排除的部分，不制造虚假的问题已完全解决的印象。
- 纯加法改动，不改变任何既有播放语义与既有公开方法签名的行为，既有确定性用例与既有运行期用例
  不受影响。

### 负面

- 新增计数不能替代"消费方到底听没听到声音"这类主观听感验证，只能证明"播放调用确实发生过"，
  不能证明"扬声器确实发出了声音"（后者依赖具体设备/静音状态等，不属于本契约范围）。
- 抢占停止一个已经成功播放的实例这条既有分支目前不记入本次新增的任何计数，也不产生诊断文本，
  如实记录为已知边界，不在本次一并处理。
- 本次定位结论里"证据不足以完全排除的部分"没有被解决，只是被诚实地标注出来；如果消费方那一侧
  确实存在额外延迟来源，仍需要消费方后续配合提供更具体的复现信息才能继续缩小范围。

## 备选方案与为什么不选

- **把新的计数语义塞进既有的文本消息诊断契约里，复用同一套转发机制**：既有契约里已经有多个
  持有者共享同一份"只有一个记录方法"的最小契约，硬加计数语义会让其余持有者也带上一套对它们
  毫无意义的成员；且既有转发机制按"消息列表逐帧比较长度"设计，计数器不是这个形状，勉强凑进去
  要么改造转发机制本身的核心假设，要么在契约里塞一层适配，两者都比另起一个独立的小契约更复杂。
  故不选。
- **不新增契约，只是把既有文本诊断里补一条"播放开始"的信息文本**：文本消息是一次性追加的日志
  性质，不是"任意时刻读取都能得到确定量"的计数——消费方仍然需要在合适的时机去翻这份日志、
  自己数有没有出现某条文本，与直接读一个数值相比更繁琐、更容易因为翻阅时机不对而漏看，没有
  真正解决"错过瞬态就等于错过信息"这个根本问题。故不选。
- **不追加实测用例，凭经验直接判断这套加载架构不会拖慢到 0.4 秒以上**：任务要求给出真实测量
  值而不是估算；框架侧此前已经有过"31 步全 PASS 不等于三份基线零差异"这类"凭经验判断比实际
  更松"的教训，本次坚持补一条能出数字的用例，即便实测结果符合预期，也留下了可复核的证据，而
  不是又一次未经验证的经验判断。故不选。
