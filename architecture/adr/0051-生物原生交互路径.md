# ADR-0051 生物原生交互路径

状态：已拍板 2026-09-20

## 背景

消费方反馈第 2 条（`<game>` 接入方，基于冻结发布提交核实）指出：载体层"交互"意图的唯一消费者
只认识场景物件（gobj）这一种目标类型，参数形状固定为"场景物件实例 id"。生物（非玩家单位/NPC）
要被玩家直接交互（走到面前按键打开对话/商店/训练师），框架没有提供对应的原生路径——接入方唯一
能用的办法是先把该生物包装成一个场景物件模板，让它顶替一个本来不属于它的实体类型，才能借用既有
的交互分发链路。

接入方由此自建了一套完全独立于框架"交互"意图的平行实现，绕开框架路径直接持有生物实体引用。这
不是接入方一次性的误用，而是框架侧确实缺一条原生路径——07 层的补充信息表历来把"生物"与"场景
物件"列为两类并列的载体层实体，唯独"交互"这一个能力只覆盖了后者。

框架此前已经在另一处决策（ADR-0044）里把"交互分发到对话系统"的回调补齐为携带触发交互的实例
自身身份，而不是让下游拿对话菜单引用顶替。该决策的适用范围限定在场景物件，生物路径当时明确留白
（"另案讨论，暂不在本决策范围"）。本决策就是那条留白的后续。

约束：本层对外公开的契约（接口、委托类型、装配根构造签名）只允许新增，不允许修改既有公开签名的
参数列表；新增的可选数据字段必须缺省可选、不改变既有数据行在缺省该字段时的行为。

## 决策

1. **新增一个独立的"生物交互"契约，与既有的"场景物件交互"契约并列，不合并成一个通用交互
   接口**：两者当前分发结果的形状不同（生物只有"分发到对话"一种原生结果，场景物件还有"分发到
   技能""开锁"等更多分支），并列声明避免为了共用一个接口而给生物侧塞入几个恒定用不到的成员。
   交互结果的枚举类型复用既有的那一个（其"分发到对话/无动作/未知目标"三个取值已完整覆盖生物侧
   全部情形），不新建一套平行的结果类型。

2. **新增一个生物模板字段，指向对话菜单，语义与场景物件的"交互分发到对话"分支对齐，但不复用
   同一个判别式结构**：生物模板新增一个可选字段，登记该生物原生交互时打开哪一份对话菜单；缺省
   （未登记）表示该生物当前没有原生可交互内容。不复用场景物件那个"技能或对话二选一"的判别式
   字段结构——生物侧当前只有对话这一种原生交互结果，硬套一个恒定单分支的判别式只会引入多余的
   抽象层，不是"预留未来扩展"的正当理由；确有第二种生物原生交互结果时，再评估是否需要判别式。

3. **交互结果回调透传交互者身份与被交互者（生物）实例身份两个标识，命名如实反映"生物实例"而
   非场景物件实例**：与 ADR-0044 的做法保持同一个思路（回调不能只给下游一个标识、让调用方去猜
   另一个），但新回调的参数命名明确写"生物实例"，不套用场景物件那个回调的参数名——两者是两个
   独立的委托类型，命名各自如实反映自己的被交互者类型，不因为形状相似就共用同一个类型或误导性
   命名。

4. **"交互"意图仍是同一个输入层意图种类，按参数形状分流给两个独立的消费者，不新增一个绑定
   实体类型的意图种类**：消费方反馈原文即指出"交互是输入层的意图，不应该绑定到某一种场景实体
   类型"——本决策不为生物另开一个新的意图种类名（那等于走回"意图绑定实体类型"的老路），而是让
   同一个"交互"意图的参数按"这次要交互的是哪一类目标"携带不同的标识字段，两个消费者各自只认
   自己的字段、对不认识的形状静默放行给另一个消费者处理，两者都不认识时才是真正的格式错误，需要
   给出诊断。既有调用方（从未携带生物侧字段）的行为不受任何影响。

5. **运行时不允许静默降级**：生物没有配置原生可交互内容、已配置但对应的对话打开回调未注入、
   交互目标 id 未登记为已知生物实例，这几种情形都必须留下诊断信息或以异常方式暴露，不允许直接
   返回一个从调用方视角"看起来正常"的结果——沿用本层既有的模块级诊断出口写法（内存收集 +
   面向宿主控制台的统一转发机制，见 ADR-0042），不新造一套诊断机制。交互距离不足这一纯粹的
   游玩节奏场景（玩家正在走近途中）不算"降级"，维持与既有场景物件交互同样的静默处理，避免逐帧
   交互尝试刷屏。

## 后果

### 正面

- 接入方不再需要为"跟 NPC 对话"这类最基础的需求把生物伪装成场景物件，也不再需要维护一套完全
  绕开框架意图系统的平行实现；框架自己的意图消费链路第一次同时覆盖两类主要的可交互实体。
- 生物交互结果的回调携带真实、稳定的生物实例身份，下游（对话系统一类的按"当前交互对象"做推断
  的能力）从一开始就不会被"多个生物共用同一份对话菜单"这类情形污染，不需要像场景物件那样先经历
  一轮契约缺口再补救。
- 新增内容全部是新增契约/新增可选字段，既有装配、既有数据、既有测试的行为逐位不变，不需要任何
  已有调用方跟着改动才能继续通过。

### 负面

- 载体层从此有两个并列的"交互"契约（场景物件、生物），装配根需要同时接线两套回调，短期增加一点
  认知与接线成本；两者结构高度对称（都是"目标身份 + 可选内容引用 + L4 回调注入点"），实际接线
  代码可以直接照抄既有场景物件那一套的写法。
- 生物侧当前只支持"分发到对话"一种原生交互结果，晚于场景物件支持的"分发到技能"能力；若后续需要
  生物原生支持技能类交互（如"对着雕像使用技能触发机关"一类生物专属玩法），需要再走一轮新增决策，
  本次不预先设计尚无需求支撑的分支。

## 备选方案与为什么不选

- **把生物交互塞进既有的场景物件交互接口，生物实例伪装成一种新的"物件种类"**：这正是接入方此前
  被迫采用、且本决策要根治的绕行方式本身，继续在框架内部沿用同一种思路只是把绕行从游戏侧搬进
  框架侧，没有解决"生物与场景物件是两类不同的实体，交互目标类型不应该被强行统一成一种"这一根本
  问题。故不选。
- **新增一个专门表达"要交互的目标可以是生物也可以是场景物件"的联合类型，替换掉两个独立的意图
  参数形状**：能让"交互"意图的参数形状看起来更统一，但会同时改变场景物件侧已经发布、被既有
  调用方依赖的参数形状，属于破坏性变更；即使只新增、不改动旧形状，联合类型本身也需要调用方先
  判断"这次是哪一种"再取值，与直接按字段是否存在分流相比没有实质简化，徒增一层包装。故不选。
- **给生物交互也套用场景物件那个"技能或对话二选一"的判别式字段结构，为将来可能出现的生物技能
  交互预留位置**：本决策的第 2 条已经说明——当前生物侧只有对话一种结果，判别式在只有恒定单分支
  时是纯粹的多余抽象，预留一个尚无具体设计支撑的扩展位不如等真正出现第二个分支时再决定用什么
  形状表达，避免过早绑定一个后来发现不合适的结构。故不选。
- **只在文档里说明"生物交互目前不是框架原生能力，游戏侧自行实现"，不新增代码**：否决——消费方
  已经指出这是最基础的 NPC 交互场景，接入方也已经证明自建的平行实现是完全可行且低成本的绕行，
  但绕行本身脱离了框架统一的意图系统、诊断出口与回放机制，长期由每个接入方各自重复实现同一个
  框架级能力缺口没有正当理由。故不选。

## 魔兽世界的对应做法

无直接对应（这是本框架载体层输入意图消费范围的一处扩展，修复的是框架自身"交互能力只覆盖一种
实体类型"的结构性缺口，不对应魔兽世界的任何具体游戏系统设计）。
