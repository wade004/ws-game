# ADR-0004 数据即内容

状态：已拍板 2026-09-04

## 背景

"新内容不改代码"是本架构的核心承诺，其前提是内容必须以数据形式存在并能被统一加载、统一校验，而不是散落在代码里的字面量或专用初始化逻辑。需要确立数据作为内容唯一载体的地位，并配套一套加载与校验机制，否则每个内容制作者都可能各自发明一套数据组织方式，长期演变成事实上的多套并存格式。

## 决策

- 所有内容一律以结构化文本表形式存在（具体存储格式待选型，见 [../02_引擎适配层.md](../02_引擎适配层.md) 引擎选型评估），不写入代码字面量。
- 每张表携带 `schema_version`，供迁移与兼容判断（机制与存档迁移类似，见 [../10_存档与持久化.md](../10_存档与持久化.md)，但数据 schema 版本与存档版本是两条独立的版本线）。
- 全部逻辑 id 统一采用 `<domain>.<segment>(.<segment>)*` 小写点分格式（如 `skill.fireball`，多级形式如 `skill.aura.burning`）。
- DataRegistry（见 [../04_数据与内容管线.md](../04_数据与内容管线.md)）在启动时全量加载所有数据表并执行引用完整性校验；校验器是提交门槛（见 [../11_工程规范与测试.md](../11_工程规范与测试.md)），未通过校验的数据不允许进入运行时。
- 每个模块自带字段说明（模块目录下的 `schema/`，见 [../11_工程规范与测试.md](../11_工程规范与测试.md) 模块范式）。

## 后果

### 正面
- 内容制作与代码开发彻底解耦，内容团队可以独立于程序迭代节奏产出新内容。
- 统一的引用完整性校验能在开发阶段而非运行时发现"技能引用了不存在的效果"这类错误，避免线上/试玩阶段才暴露问题。
- 统一 id 规范使跨模块引用（技能引用效果、物品引用技能、任务引用物品等）具备一致的可读性与可检索性。

### 负面
- 相比"直接改代码里的数值"，数据驱动增加了一层间接性，简单的一次性调参也需要走数据编辑与校验流程，短期效率略低于硬编码。
- 需要额外投入维护 DataRegistry、校验器、schema 版本迁移机制本身的工程成本。

## 备选方案与为什么不选

- **内容与代码混写（部分数值写数据表、部分逻辑写代码字面量）**：短期灵活，但边界模糊后会逐渐蔓延为"改内容需要改代码"，与架构目标直接冲突，且难以做统一校验，不采纳。
- **不做启动期全量校验，运行时按需校验或不校验**：可以减少启动耗时，但会把数据错误的暴露时机推迟到玩家实际触发相关内容时，排查成本远高于启动期一次性全量校验，不采纳。

## 魔兽世界的对应做法

魔兽世界的内容高度数据化，体现在庞大的 DBC/DB2 数据表体系（spell.dbc、item_template、creature_template、quest_template 等）与服务端数据库表的组合：绝大多数内容通过配表实现，代码只提供通用执行引擎与少数特殊脚本钩子。本 ADR 延续这一思想，把"表体系 + 校验 + id 规范"确立为单机架构下的对应机制。
