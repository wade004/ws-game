# ADR-0036 地图图片像素与世界坐标换算约定

状态：已拍板 2026-09-18

## 背景

消费方反馈第 59 条（2026-09-18，`docs/上游反馈-待转发-2026-09-18.md` 第 26～41 行）：实体世界坐标只声明为 `Vec2(x, y)`（05 第 3.1 节），从未写明 Y 轴方向——唯一线索是引擎适配层参考实现相机构造参数的间接推断，不是文档的直接结论；`world.map`（05 第 4.1 节）/资产规格书模板（14 第 2.2 节 `pixels_per_unit` 一行）也从未给出"地图背景图片像素坐标 ↔ 世界坐标"的换算比例或图片像素行方向与世界 Y 轴的关系，`pixels_per_unit` 长期留空待填；地图导入工具（`toolchain/asset_import/map_cmd.py`）只搬运分层图文件，不涉及任何比例尺/方向参数。

消费方想在背景地图图片上精确摆放内容坐标（出生点、传送点、区域触发等）时，拿不到官方换算依据，只能自行约定或要求用户手工校准；一旦自行猜测的默认值与框架实际行为不一致（尤其 Y 轴方向猜反），会产出背景图与世界坐标对不齐甚至整体镜像的隐蔽内容缺陷，且这类缺陷在静态校验里完全不可见（坐标数值本身合法，只是摆放位置的视觉呈现错了）。

## 决策

1. **世界坐标 Y 轴正方向向上**（屏幕/地图的"北"）：05 第 3.1 节"世界坐标是二维平面坐标 `Vec2(x, y)`"补一句集中声明——`+Y` 朝上，与常见地图"上北下南"的直觉一致；本条只是把此前从未明文的方向补齐为文档结论，不改变任何既有字段的类型或既有内容数据的坐标数值本身（既有数据里的 `x`/`y` 数值不需要因本条重新解释或改写——此前没有声明并不等于此前隐含了另一种方向，运行时从未按坐标方向做过任何区分左右/上下的逻辑判定）。
2. **地图背景图片像素坐标**：以左上角为原点、列向右为正、行向下为正——这是绝大多数图片编辑器、图片文件格式（含本架构采用的位图图片格式）与主流 2D 引擎加载贴图时的默认像素坐标约定，采用同一约定使换算公式不需要额外坐标系翻转说明。
3. **换算公式**（`pixels_per_unit` 简写 `ppu`，`origin_px` 为世界原点 `(0,0)` 在图片中的像素坐标）：
   - 像素 → 世界：`world.x = (px.x - origin_px.x) / ppu`；`world.y = (origin_px.y - px.y) / ppu`。
   - 世界 → 像素（逆变换）：`px.x = world.x * ppu + origin_px.x`；`px.y = origin_px.y - world.y * ppu`。
   - `world.y` 与 `px.y` 符号相反，是"世界 Y 向上、图片行向下"两条约定共同的直接推论，公式本身不是新增自由度。
4. **`world.map` 新增可选字段 `image_transform`**：`{pixels_per_unit: Number, origin_px: Vec2, image_size_px?: Vec2}`。地图不声明本字段时，框架不隐含套用任何默认换算——消费方（含编辑器）显式读取字段缺失，须自行决定兜底策略，不得静默假设 `pixels_per_unit = 32`/`origin_px = (0,0)` 一类猜测值当成地图确实声明过的换算参数。框架仅在契约层提供一个显式命名的默认值供选用（`MapImageTransform.Default`，ppu = 32、原点在图片左上角），调用方需要主动选择使用它，而不是遇到缺省自动落到它。
5. **`pixels_per_unit` 项目级默认值收口为 32**：14 第 2.2 节游戏填写项的 `pixels_per_unit` 行由 `<待填>` 改为"框架默认 32；每张地图可在 `world.map.image_transform` 覆盖"，解决反馈原文"资产规格书模板的 `pixels_per_unit` 行留空待填"这一具体症状；"框架默认"只是内容工具在缺省场景下可以选用的建议值，不是决策 4 所述"不隐含套用"的例外。
6. **新增校验规则 `world_map_point_outside_image`（Warning）**：地图声明了 `image_transform.image_size_px` 时，`spawn_points`/`teleport_points` 的世界坐标若落在按本条公式换算出的图片包围盒之外，报一条不可提升的警告（内容仍可以摆在图片外——如设计上确实需要一块画布外的逻辑区域——本规则只是提示"这个点画不到背景图上，检查是不是摆错了"，不是硬性拒绝）。

## 后果

### 正面

- 消费方（尤其编辑器）第一次拿到官方、结构化、机器可读的换算依据，能把"背景图对齐"纳入自动化/编辑期校验，不必再靠猜测或手工校准。
- 换算参数挂在具体地图行上（而不是全局唯一一套），天然支持不同地图使用不同分辨率/比例尺的背景图。
- `image_transform` 是可选字段，未声明的既有地图数据不受影响，不需要为存量内容补数据才能通过校验；新增校验是 Warning 且不可提升，不阻断既有 `--strict` 门禁。

### 负面

- 多了一份需要人工维持一致的参数（`origin_px`/`pixels_per_unit` 必须与实际出图工具产出的图片吻合）；声明错误不会被静态校验直接抓出（`world_map_point_outside_image` 只能发现"点落在图片包围盒外"这一类问题，发现不了"声明的 ppu 本身就与实际比例尺不符但恰好所有点都落在包围盒内"的情形）。
- `image_size_px` 缺省时新增校验规则完全跳过（无法界定包围盒），实际收益依赖消费方愿意在声明 `image_transform` 时一并提供图片尺寸。

## 备选方案与为什么不选

- **世界 Y 轴正方向向下，与图片像素行方向一致**：否决——与主流 2D 引擎（含本架构技术选型采用的引擎）的世界坐标系默认方向相反，选它会让逻辑层与表现层之间处处需要做一次 Y 翻转才能对齐渲染，且与既有"世界模拟不依赖引擎对象"（ADR-0002）的取舍相悖——本该在一处声明清楚的坐标约定，会因为选了与引擎相反的方向而被迫在引擎适配层的每一次坐标搬运代码里重复翻转，翻转逻辑本身还容易被遗漏在个别调用点造成隐蔽镜像缺陷，恰好是本条反馈想要根治的那类问题。
- **不在框架层声明，由各游戏自行约定换算比例与方向**：否决——这正是本条反馈指出的现状与痛点：换算关系分散在游戏各自的实现或消费方的口头约定里，没有单一权威来源，编辑器一类跨游戏内容工具无法给出通用的"背景图对齐"功能，只能针对单个游戏各写一套；与 ADR-0014/ADR-0018"机制归框架、内容归游戏"的既有分工原则相悖——像素↔世界坐标换算是与具体游戏内容无关的通用机制，理应由框架给出结构化声明位。
- **只声明 Y 轴方向的文字结论，不新增 `image_transform` 结构化字段（换算比例继续靠约定俗成）**：否决——反馈原文"影响"一节明确指出问题不止 Y 轴方向一项，还包括像素↔世界单位的换算比例本身无处声明；只补文字结论解决不了"编辑器需要机器可读的换算参数才能做自动对齐/校验"这一具体诉求。

## 魔兽世界的对应做法

魔兽世界客户端的地图坐标系是历史遗留的多层换算（ADT 地形格子 → 归一化 0～100 坐标 → 小地图/世界地图各自独立的图片映射表，且世界坐标 Z 轴才是"上"，X/Y 才是水平面），本身高度耦合具体地形格式与客户端渲染管线，并非一份可直接照搬的通用换算契约；本 ADR 的"单张地图声明一套线性换算参数"是本架构 2.5D 单机场景下的简化设计，无直接对应。
