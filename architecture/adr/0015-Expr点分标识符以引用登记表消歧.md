# ADR-0015 Expr 点分标识符以引用登记表消歧

状态：已拍板 2026-09-04

## 背景

Expr 条件表达式语言（见 [04_数据与内容管线.md](../04_数据与内容管线.md) 第 6 节，源于 [ADR-0005](0005-一个条件语言.md)"一个条件语言"）的语法定义中，字面量产生式为 `<literal> ::= <number> | <string> | "true" | "false"`，引用产生式为 `<reference> ::= <group> "." <key> ( "(" <arg_list> ")" )?`，其中 `<group>` 取自九个固定分组（`self`/`target`/`event`/`world`/`quest`/`player`/`combat`/`enemies`/`time`）。BNF 里没有"内容 id 字面量"这一产生式，但第 6.2 节给出的大量合法示例把内容 id 当作参数或比较对象直接写进表达式，例如 `self.has_aura(skill.aura.burning)`、`target.faction == fac.wildlife`、`world.get(world.bridge.repaired)`、`quest.is_active(quest.deliver_letter)`、`player.has_item(item.town_key)`。

问题在于：`world`、`quest`、`target`、`combat` 这四个分组名同时也是 id 规范（见 04 第 2.2 节）里登记的内容域名。当解析器读到形如 `quest.deliver_letter` 这样一个点分标识符时，仅从语法形式上无法判断它是"`quest` 分组下名为 `deliver_letter` 的引用"，还是"域名为 `quest` 的一个内容 id 字面量"——两者的产生式外观完全相同，BNF 与既有文字说明都未定义消歧规则。这不是实现细节层面的疏漏，而是语法定义本身存在的歧义，若不澄清，不同实现（校验器与运行时宿主）可能对同一段表达式文本给出不一致的解析结果，违反"同一份内容在校验期与运行期含义一致"的隐含前提。

## 决策

**点分标识符的归类以宿主引用登记表为准**：解析一个形如 `<第一段>.<其余段>` 的点分标识符时，若该组合在当前宿主的引用登记表中有登记（即第 6.3 节所说"登记的 `group.key` 组合"——每个 `key` 都附带返回类型与参数类型签名的登记项），则解析为 `<reference>`；否则整体解析为一个内容 id 字面量，且必须满足第 2 节的 id 格式要求。

配套规则如下：

1. **BNF 扩展**：`<literal>` 增加一条分支：
   ```
   <literal> ::= <number> | <string> | "true" | "false" | <id_literal>
   ```
   并加注：`<reference>` 与 `<id_literal>` 在语法形式上完全相同，实际归类由引用登记表在解析时消歧，不由 BNF 本身区分。
2. **校验器新增一条警告**：当一个被解析为 id 字面量的标识符，其域名段恰好与九个分组之一同名，但对应的 `group.key` 组合并未在引用登记表中登记时，报"疑似引用拼写错误"（警告级别，不阻断内容合入）。此规则用于捕获诸如把 `self.hp_pct` 误写成 `self.hp_pctt` 这类打字错误——错误发生后表达式仍能按"id 字面量"合法解析，若不加这条警告将悄悄放行。
3. **登记表是解析的输入之一**：内容校验期（校验器）与运行期（宿主注册引用时）必须使用同一份引用登记表作为解析输入，以保证同一段表达式文本在两个阶段的解析结果一致；登记表本身的登记、增删走各宿主既有的引用登记机制，不在本决策范围内另行定义。

## 后果

### 正面
- 消除了 BNF 与既有示例之间的矛盾，`quest.deliver_letter`、`world.bridge.repaired` 这类写法从"语法未定义行为"变为"有明确消歧规则的合法字面量"，第 6.2 节现有示例无需改写。
- 内容作者的书写方式完全不变：不引入任何新增前缀符号或书写约束，现有全部表达式文本保持字面兼容。
- 疑似拼写错误警告在"引用误写成看似合法的字面量"这类原本会被静默放行的错误场景下提供了一层校验期提示。

### 负面
- 解析器的签名从"只依赖表达式文本"变为"依赖表达式文本 + 引用登记表"，任何需要解析 Expr 的位置（校验器、运行时宿主、未来可能出现的工具，如内容编辑辅助）都必须先能拿到登记表才能正确解析，增加了接入方的前置依赖。
- 若某个宿主在登记引用时遗漏了 `key`，原本应报"未知引用"错误的笔误会退化为"合法的 id 字面量"，只能靠上述警告或后续的类型检查（比较、参数类型不匹配）间接发现，不再是解析期硬错误。
- 校验期与运行期若使用了不同版本或不同来源的登记表（例如两边各自维护了一份而未保持同步），会导致同一段文本解析结果不一致，因此"同一份登记表"这一前提本身变成需要各实现方遵守的约束，而不是语法层面能自动保证的性质。

## 备选方案与为什么不选

以下按顺序逐一列出考虑过的四个方案，第一个是本决策采纳的方案，其余三个均被否决：

1. **登记表消歧（本决策采纳）**：如"决策"一节所述，按第一段与其余段组合是否在引用登记表中登记来判断是引用还是 id 字面量。优点是不改变任何既有书写方式、不引入新符号；代价是解析器需要依赖登记表这一外部输入，已在"后果"一节说明。
2. **给 id 字面量加前缀记法**（如 `@skill.fireball` 或反引号包裹 `` `skill.fireball` ``）：解析时凭前缀即可无歧义区分，不依赖任何外部登记表，规则本身最简单。否决理由：这会改变全部内容作者现有的书写习惯，且会使第 6.2 节现有全部把 id 当参数/比较对象的示例失效，需要逐条改写；引入歧义解决方案的代价大于歧义本身造成的问题。
3. **位置规则**（约定"出现在引用调用参数位置或比较运算符右侧的点分标识符一律视为 id 字面量，不可能是引用"）：不需要登记表，规则形式上简单。否决理由：这条规则无法表达"参数位置上写的确实是引用"这一合法且已在用的写法，例如 `enemies.count_in_range(self.range)` 中 `self.range` 出现在参数位置但明确是引用而非 id；该方案会直接禁止这类合法表达式，表达能力倒退。
4. **段数规则**（约定"点分标识符的段数达到某个阈值即视为引用，否则视为 id 字面量"，或反之）：不需要登记表。否决理由：`quest.deliver_letter`（id 字面量）与 `quest.is_active`（引用）段数完全相同，段数本身不携带任何可用于区分二者的信息，该规则在语法层面就不成立，无法自洽。

## 魔兽世界的对应做法

无直接对应。魔兽世界的法术脚本/条件系统（如 SmartAI 的条件表、法术特效的条件判断）不存在"表达式文本里的点分标识符可能是变量引用也可能是内容编号字面量"这类歧义——它的条件系统通常用独立的枚举参数字段表达"引用哪类对象的哪个属性"，与本决策要解决的"同一段文本形式需要靠外部登记表消歧"这一问题不属同一形态，故不作对应关系比附。
