# ADR-0062 地面掉落物原生交互与统一最近可交互目标查询

状态：已拍板 2026-09-21

## 背景

消费方反馈第五批第 1 条（`<game>` 接入方，基于冻结发布提交核实）指出：载体层"交互"意图此前已经
有两条并列的原生分流——场景物件（见既有决策）与生物（ADR-0051）——唯独地面掉落物没有对应的原生
分流，只提供裸的"放下"与"拾取"两个方法。接入方要做"玩家走到掉落物旁按键拾取"这一最基础的需求，
唯一能用的办法是自己遍历掉落物模块暴露的"当前存活掉落物 id 列表"、自行算最近距离，再直接调用拾取
方法——这条链路完全绕开了框架统一的"交互"意图系统与诊断出口，是接入方逐个接入自己重复实现一遍的
框架级能力缺口，而不是这一个接入方的一次性误用。

反馈原文还提到期望能有一个"按最近距离找可交互目标（生物或物件）"的统一查询类型。核对（基于冻结
发布提交，不读工作树）后确认：这个类型此前从未在本仓库任何一层真正存在过——不是"生物、物件已经有
这类查询，唯独掉落物没有覆盖"，而是三类可交互目标此前都没有这样一条统一的查询入口，表现层同样
没有对应的"附近是否有可交互目标"取值路径。反馈原文里出现的类型名，据此按反馈原文的命名意图补上，
不是"扩展一个已存在的登记表"。

约束：本层对外公开的契约（接口、委托类型、装配根构造签名）只允许新增，不允许修改既有公开签名的
参数列表；新增的可选数据字段/构造重载必须缺省可选，不改变既有调用方在缺省该参数时的行为。

## 决策

1. **新增第三条"交互"意图原生分流，与场景物件、生物两条既有分流并列，结构完全对称**：交互发起
   方在同一个"交互"输入意图上携带一个掉落物实例标识字段（命名与既有两条分流的"场景物件实例标识"
   /"生物实例标识"字段同一构词法），本分流只认自己的字段形状，对不认识的形状静默放行给另外两条
   分流处理，三条分流都不认识时才是真正的格式错误。分流内部依次做存在性核对、距离核对（复用掉落
   模块已有的拾取距离配置项，不新开一份平行的距离配置）、拾取许可判定（见决策 2），成功后直接调用
   掉落模块既有的"拾取"方法完成实际拾取，不重复实现一遍拾取逻辑（不产生第二套背包写入/掉落物销毁
   路径）。

2. **拾取许可判定：不新建归属系统，复用"L4 回调注入点、未注入时默认放行"这一贯穿本层的既有惯例**：
   核对掉落物数据结构与既有拾取方法后确认，掉落物身上原本就带的"归属提示"字段明确不承载任何强制
   语义（本架构面向单机场景，该字段仅为兼容掉落生成管线的数据结构而保留）；既有拾取方法从未检查
   过它。再核对场景物件的交互方法同一处"是否要判断归属"的位置，同样只有一套数据驱动的"锁"准入
   门槛，语义是"是否已解锁"而不是"归属于谁"——本层目前没有任何一条交互分流真正实现过身份/阵营
   归属判定。据此没有旧概念可复用，也不为此另造一套归属系统；改用本层贯穿多个模块的既有惯例：新增
   一个可选回调注入点，缺省（未注入）时默认放行，是否允许拾取完全交给具体游戏在组装期注入判断逻辑，
   回调携带"归属提示"字段的原始值供游戏自行解释，框架自身不赋予它任何强制含义，与该字段一贯的口径
   保持一致。

3. **新增一个统一的"最近可交互目标"查询类型，覆盖场景物件、生物、地面掉落物三类目标，不是只服务
   掉落物一类的孤立查询**：该类型放在载体层的公共契约目录（只定义类型与接口、不含业务逻辑），因为
   目标分类只需要依据运行期实体自身携带的类别标识（场景物件/生物/掉落物三个既有的字符串常量），
   不需要引用任何一个具体载体模块或掉落模块自身的类型——接口与其默认实现因此可以完全留在不依赖
   玩法层的那一层，不违反"载体层不依赖玩法层"的既有边界，同时在玩法层的掉落模块实际构造出掉落物
   实例后依然能透明地覆盖到它（因为查询是在调用时对运行期世界状态现场求值，不是在构造期收集一份
   固定列表）。
4. **该查询不另开一份登记表，直接对运行期世界状态现场求值**：三类目标的生成、消失（拾取/过期/
   销毁）此前都已经在通过既有的实体生命周期管理机制维护自己在运行期世界里的存在性；本查询的默认
   实现每次调用都直接读这份运行期状态的现场结果，不另外维护一份需要手动登记/注销、可能与运行期
   世界状态脱节的登记表——不会出现"目标已经消失，仍被最近目标查询命中"的悬挂引用，也不需要三个
   载体模块各自改动来配合一份新登记表的生命周期。
5. **表现层新增一条统一的"附近最近可交互目标"取值路径，覆盖三类目标，不是只给掉落物开一条孤立
   路径**：核对现状发现表现层对场景物件、生物此前也从未提供过"附近是否有可交互目标"这一类取值——
   不是"另外两类已经有、唯独掉落物没有"，而是三类都没有。既然要新开一条路径，直接设计成三类通用：
   该路径的取值携带目标身份、目标类别、目标距离三项；游戏侧判断"附近是否有可拾取的掉落物"只需要
   读类别字段是否等于掉落物这一个既有的类别标识，不需要框架为"附近是否有可拾取掉落物"这一件事单独
   开一条只覆盖掉落物的路径。验收经生产装配入口贯通到该取值路径，覆盖"装配根按标准接线方式构造
   出完整运行期对象图后，取值路径能否读到正确结果"这一层，不停在中间某一层装配代码上。
6. **运行时不允许静默降级**：拾取目标不存在、拾取许可回调拒绝，这两种情形必须留下诊断信息（沿用
   本层既有的模块级诊断出口写法：内存收集 + 面向宿主控制台的统一转发机制），不允许直接返回一个
   从调用方视角"看起来正常"的结果。交互距离不足这一纯粹的游玩节奏场景（玩家正在走近途中）不算
   "降级"，与既有场景物件、生物两条分流对"距离过远"的既有处理保持一致——维持静默，不记诊断，
   避免玩家逐帧尝试交互时刷屏。

## 后果

### 正面

- 接入方不再需要为"走到掉落物旁按键拾取"这一最基础的需求自己遍历掉落物列表、算最近距离、绕开
  框架意图系统直接调用拾取方法；框架自己的"交互"意图分发链路第一次同时覆盖场景物件、生物、地面
  掉落物三类主要的可交互实体。
- 新增的统一"最近可交互目标"查询与表现层取值路径一次性补齐了此前对三类目标都缺失的能力，接入方
  今后新增任何一类需要"附近有什么可交互"的界面提示，都只需要读同一条路径，不需要分别为每一类目标
  各自实现一遍"扫描 + 算最近距离"。
- 拾取许可判定新增了一个明确的、默认放行的回调注入点：不需要归属判定的游戏不受任何影响（缺省行为
  与此前完全一致）；需要归属判定的游戏可以在组装期注入自己的判断逻辑，不需要绕开框架的拾取入口。
- 新增内容全部是新增契约/新增可选字段/新增构造重载，既有装配、既有数据、既有测试的行为逐位不变，
  不需要任何已有调用方跟着改动才能继续通过。

### 负面

- 载体层从此有三个结构对称的"交互"契约（场景物件、生物、掉落物），装配根需要多接一套查询与分流的
  构造与注册，短期增加一点接线成本；三者结构高度一致（目标身份 + 距离核对 + 可选的 L4 回调注入点），
  实际接线代码可以直接照抄既有两套的写法。
- 统一的"最近可交互目标"查询目前只回答"最近的一个是谁"，不支持"按类别只查某一类"或"返回距离内
  全部候选"；接入方如果需要更复杂的筛选（例如"只提示掉落物，忽略生物"），需要自己在拿到目标类别
  后再过滤，或者后续视需求再评估是否新增筛选参数——本次不预先设计尚无需求支撑的筛选能力。

## 备选方案与为什么不选

- **把掉落物交互塞进既有的场景物件交互契约，掉落物实例伪装成一种新的"物件种类"**：这正是场景物件
  交互决策、生物交互决策（ADR-0051）此前已经论证并否决过的绕行思路本身，继续沿用只是把"一种实体
  类型伪装成另一种"的绕行从游戏侧搬进框架侧，没有解决"掉落物是一类独立的可交互实体，不应该被强行
  统一成物件"这一根本问题。故不选。
- **给拾取许可判定发明一套独立的阵营/身份归属系统**：核对后确认本层现存任何一条交互分流都没有真正
  实现过归属判定，也没有需求明确要求这样一套系统应该长什么形状；提前设计一套没有具体使用场景支撑
  的归属模型，大概率与后续真正出现归属需求时的实际形状不符，届时还要再改一轮。改用本层既有的"默认
  放行的回调注入点"惯例，把设计权完全交给真正有归属需求的具体游戏。故不选。
- **只给掉落物单独开一条"附近是否有可拾取掉落物"的表现层取值路径，不做成三类统一**：能更快满足
  反馈原文字面提到的掉落物场景，但会让表现层同时存在"只覆盖掉落物的孤立路径"与"未来某天可能补上
  的场景物件/生物版本"两套形状不一致的路径，之后接入方每多要一类就再多问一次框架"这类有没有对应
  的查询"。核实现状后确认三类目标其实都还没有这条能力，不存在"复用已有的两类、单独给掉落物补"这
  个更省事的选项，直接一次性设计成统一路径没有增加实质成本。故不选。
- **保留"接入方自行遍历掉落物列表算最近距离"作为官方认可的用法，只补文档说明**：否决——消费方已
  经证明这是最基础的拾取交互场景，接入方也已经证明自建的绕行实现完全可行但重复劳动，且绕行本身
  脱离了框架统一的意图系统与诊断出口，长期由每个接入方各自重复实现同一个框架级能力缺口没有正当
  理由。故不选。

## 魔兽世界的对应做法

无直接对应（这是本框架载体层"交互"能力覆盖范围与"最近可交互目标"查询能力的一处结构性补全，修复
的是框架自身此前对地面掉落物这一类可交互实体缺原生路径、以及三类可交互目标都缺统一查询入口的
结构性缺口，不对应魔兽世界任何具体游戏系统设计）。
