# ADR-0043 gossip 菜单新增可选开场白/正文字段

状态：已拍板 2026-09-20

## 背景

消费方反馈第 3a/3b 条（`ws-game-wow` 2026-09-20 反馈文档《交互/gossip/任务日志/NpcFlag/持久化/
掉落RNG 七项核实》）核实成立：

- **3a**：gossip 菜单内容表只登记了"id"与"选项列表"两个字段，从设计之初就没有规划"开场白/正文"
  概念——对照同一模块内的剧情节点结构，剧情节点一直都有自己的正文文本字段，二者本应是同一层级
  的概念，却只有一个落了地。
- **3b**：参考 UI 的对话框正文区因此没有字段可查，只能硬编码一句占位文案顶着，且这句占位文案与
  真正经本地化查询得到的剧情正文文案（同一对话框、剧情分支下走的是正经查询路径）处理方式明显
  不一致——3b 是 3a 的下游症状，没有 3a 就没有字段可给 3b 查，两者必须合并为同一个改动单。

这一空白如果不补，参考 UI 会一直显示一句与内容无关的通用占位文案，内容作者也没有任何登记入口
可以为 gossip 菜单配置一句开场白，只能通过"新增一个专门的脚本钩子在打开菜单时另外演出一段文字"
这类绕行方式变通实现，成本和一致性都不如直接给内容表补一个字段。

## 决策

1. **gossip 菜单内容表新增一个可选的开场白/正文文本引用字段**：字段值是指向本地化文本条目的
   引用键，缺省（内容作者未提供）合法，代表"该菜单不配置开场白"。这是纯新增字段，不改变任何
   既有字段的名字、类型或语义，属于内容数据 schema 的兼容变更（既有的《内容数据 schema 破坏性
   变更政策》把"新增可选字段"明确归为兼容变更一类，不适用该政策为破坏性变更设定的材料清单与
   披露流程），已有数据不需要做任何迁移即保持合法。

2. **字段命名跟随本模块既有的"文本引用字段"命名惯例，不采用消费方反馈原文的建议名**：本模块内
   已有两种文本引用字段命名方式并存——
   - 一种是"某个语义名 + `_key` 后缀"（如任务标题、任务描述各自的文本引用字段），用在"这个字段
     只是宿主对象众多属性之一"的场景；
   - 另一种是裸的"文本键"字段名，用在"这个结构体自身的全部意义就是一段文本"的场景（如菜单里的
     每一个选项、剧情里的每一个节点/分支，它们各自的核心内容就是一段要显示的文字）。

   gossip 菜单本身是"一份菜单"，不是"一段文本"——它的开场白只是它众多属性之一（旁边还有选项
   列表），因此按第一种惯例命名为"`greeting_key`"（语义名"开场白" + `_key` 后缀），不沿用第二种
   惯例裸称"文本键"（会与菜单内部"选项自己的文本键"这一既有字段同名但语义不同，造成混淆），也
   不采用消费方反馈原文建议的"`_text_key`"三段式命名（`_key` 后缀本身已经隐含"这是一个文本引用
   字段"，重复"text"没有带来额外区分度，反而与本模块统一惯例不一致）。

3. **字段缺省时，展示方不渲染正文区，不回落到任何占位文案**：这是本次改动同时要拍板的展示取舍
   ——3b 修好之后，字段缺省的菜单应该表现为"对话框里没有正文这一块"，而不是显示一句通用套话。
   理由：占位文案是框架自己编的一句话，与内容作者的创作意图无关，一旦真的显示给玩家，玩家会
   把这句话当成游戏内容的一部分来理解，这是比"干脆不显示"更严重的误导；而"这个菜单本来就没有
   配置开场白"与"外壳不知道该说什么随手写了一句"是两种完全不同的内容状态，缺省时选择不渲染，
   能让这两种状态在展示层面保持可区分，往后如果内容作者确实想要一句通用兜底文案，可以显式在
   数据里配一条，而不是让展示层帮所有人做了这个决定。

4. **契约扩展只用新增重载，不修改任何既有公开签名**：本次涉及的两个既有公开类型（菜单的内存态
   表示、以及只读查询返回的视图对象）都需要携带这个新字段，两者均按"新增一个多一个参数的构造
   重载，原有构造函数保留不变、新参数在其内部取缺省值"的方式扩展，不touch 原有构造函数的参数
   列表——任何已经按旧签名构造这两个类型实例的既有调用方（包括测试代码）不需要做任何改动。

## 后果

### 正面

- 内容作者从此有了直接给 gossip 菜单配置开场白的登记入口，不需要再借助脚本钩子这类更重的机制
  变通实现一句开场白。
- 参考 UI 对话框的正文区处理方式在 gossip 与剧情两条分支之间统一（都经本地化查询得到真实文案，
  不再有一条分支是硬编码占位文案的特殊情形）。
- 缺省不渲染而非回落占位文案的取舍，避免了"框架编的话被当成游戏内容"这一更隐蔽的误导，长期看
  减少了内容审查阶段需要额外排查"这句话是不是不小心漏配了"的负担（不渲染本身就是最直观的信号）。
- 全部按新增处理（新字段可选、新构造重载），已有内容与已有调用方代码不需要做任何改动即保持合法。

### 负面

- 参考 UI 从"总有一句正文可看"变成"可能完全没有正文区"，如果内容作者错误地以为这个字段是必填
  的、漏配了却没有察觉，玩家看到的是一个不完整的对话框而不是一条明显的报错提示——这是"缺省不
  渲染"取舍本身带来的、可以接受的代价（比误导性占位文案更好，但确实不是零成本，留给内容校验
  流程按需评估要不要为"存在选项但没有开场白"这类情形单独加一条非阻断提示）。
- 本模块内"两种文本引用字段命名惯例并存"的既有格局没有借这次机会统一，本次新增字段只是按既有
  惯例分类挑了其中相符的一种，不是本 ADR 的决策范围。

## 备选方案与为什么不选

- **不新增字段，只在展示层换一句更通用的占位文案**：能让 3b 的症状看起来不那么突兀，但完全没有
  解决 3a 的根因——内容作者依然没有任何登记入口配置真正的开场白，下一次遇到同类反馈只是换一句
  新的占位文案继续硬编码。故不选。
- **采用消费方反馈原文建议的字段名（三段式，语义名 + "text" + "key"）**：技术上完全可行，字段
  本身的行为不受名字影响，但会与本模块内其余"语义名 + `_key`"的既有字段命名方式不一致，制造
  一个新的例外，故改用与既有惯例对齐的两段式命名。
- **字段缺省时回落到与此前相同的占位文案，只是把它从硬编码改成配置项**：能保留"总有正文可看"
  的界面观感，但没有解决占位文案本身"框架编的话被当成游戏内容"这一更根本的问题，只是把它从
  代码里搬到了配置里，故不选，改为缺省不渲染。
- **把开场白做成菜单选项列表的第零个特殊选项，而不是新增一个独立字段**：能复用选项结构已有的
  文本引用字段，不需要新增字段，但"开场白"在语义上不是一个可以被选择的选项（它没有可执行的
  动作、也不应该出现在"可见选项"的过滤与序号体系里），勉强套进选项结构会让选项列表的语义变得
  不纯粹，调用方还需要额外分支处理"第零项其实是正文不是选项"，故不选，改为在菜单层级新增一个
  独立字段，与选项列表并列。

## 魔兽世界的对应做法

魔兽世界的 gossip 交互窗口本身就在选项列表上方展示一段 NPC 问候文本，本决策补齐的正是这层此前
缺失的对应关系——此前的字段集合里没有承载这段文本的位置。与魔兽世界的差异在于展示取舍：魔兽
世界的 gossip 窗口里这段问候文本事实上是必然存在的（内容制作流程本身保证），本架构选择把它做
成可选字段并让缺省情形"不渲染"，是因为本架构面向的内容作者群体与生产约束不同，不能假设每一份
gossip 菜单内容在制作阶段都会补全这段文本，需要一个明确、不误导的缺省行为。
