# ADR-0071 装备纸娃娃层随朝向换图

状态：已拍板 2026-09-23

## 背景

消费方反馈第十八批（`<game>` 接入方，基于冻结发布提交核实）指出：接入方要实现"装备穿戴后人物外观
改变、三向层图"（四方向游戏的纸娃娃层美术按 front/side/back 三向分别绘制），撞到框架自身在类型
注释里早已标注过的"已知简化"——`presentation/render/core/SpriteViewBase.HandleItemEquipped` 把
`EquipVisualDef.MeshRef`（对应 04 第 7.1.2 节 `display.equip_visual.mesh_ref`）直接当成该纸娃娃层
的最终资源 Id 存进 `_equipOverridesBySlot`，`RebuildEquippedLayers` 命中覆盖的层直接采用这个值，
**跳过**了未被覆盖的层都会经过的 `ResolveLayerResourceId` 方向档位换算。结果是一件装备只能提供
一张图，无论角色朝向哪个方向，装备层永远显示同一张素材，四方向/八方向游戏要的"随朝向换图"做不到。

`EquipVisualDef.MeshRef` 字段注释、`SpriteViewBase.OnEvent` 类型注释均把这一点登记为"已知简化"；
[ADR-0037](0037-资源引用路径推导契约扩展到vfx-sfx-model-anim_set.md) 决策 2 进一步把"sprite 型
`mesh_ref` 是否要提升为与 model 型平级的正式契约"列为留给消费方反馈第 66 条回复文档的"待设计层
确认"事项，未裁决。本篇即是该待办的裁决落地。

约束（同既有 ADR 惯例）：不改 04 `display.equip_visual` 表的字段结构（`mesh_ref` 仍是单个可选
`Id`，不拆成按方向分的子字段）；`SpriteViewBase` 对外公开签名只允许新增，不修改
`ResolveLayerResourceId` 既有签名；不引入新的渲染路径，装备层解析结果仍经既有
`IRenderer2D.SetLayers` 落地。

## 决策

1. **`mesh_ref` 的 sprite 型语义变更：从"该层最终资源 Id"改为"装备层资源集引用"，与身体层
   `display.map.sprite_set_id` 处在同一位置，经与身体层完全同一套方向档位公式换算**。不新增
   schema 字段——04 不动。运行期新增
   `protected virtual Id ResolveEquipLayerResourceId(SpriteLayerPlacement placement, Id
   equipLayerSetRef)`（`SpriteViewBase` 新增方法，ABI 只加法，不改
   `ResolveLayerResourceId(SpriteLayerPlacement)` 既有签名），默认实现与 `ResolveLayerResourceId`
   共用同一个私有静态 `ComposeLayerResourceId(string layerSetName, SpriteLayerPlacement placement)`：
   `"layer.<layerSetName>__<方向裸档位名>__<层名>"`（14 第 1.2 节命名模板，方向裸档位名经
   `Presentation.Common.DirectionSlots.StripPrefix` 还原，`flipX` 同身体层一样不编码进资源 Id——
   同一份 `_r` 原图配合精灵实例整体 `flipX` 足够表达镜像档位）。两者唯一差异是 `layerSetName`
   的来源：身体层取 `DisplayInfo.Sprite.SpriteSetId`，装备层取 `equipLayerSetRef.Value`（即
   `EquipVisualDef.MeshRef` 原值，经 `StripCategoryPrefix` 去掉类别前缀）。
2. **`_equipOverridesBySlot` 存的从"最终资源 Id"改为"装备层资源集引用"，`RebuildEquippedLayers`
   改走统一的合成流程**：先把 `DisplayInfo.Sprite.PaperdollLayers` 默认层名与装备新增的、不在
   默认集合里的层名（按槽位 Id 升序排列，见既有判断记录）合并成一份完整层名列表，对这份列表统一
   调一次 `IRenderConventionHost.ComposeSpriteLayers` 按当前朝向解析方向槽位；再逐层按是否命中
   `_equipOverridesBySlot` 覆盖分派到 `ResolveEquipLayerResourceId`/`ResolveLayerResourceId`。
   装备新增的层（此前直接使用覆盖值，不经任何方向解析）现在与默认层共用同一次方向解析，行为更
   一致——装备新增一层同样会随朝向换图，不再是覆盖表里的层与默认层各自一套规则。
3. **占位资产与校验工具同步落地三向层图，使升级后的样例数据真实可加载**：
   `data/_sample/display/display.equip_visual.json` 现有两行 sprite 型样例（`mesh_ref` 值本身
   不改，仍是 `paperdoll.item.sample_hero_hat_test`/`paperdoll.item.sample_hero_hat_wiring_test`
   ——旧值恰好符合新语义对"资源集引用"的格式要求，不需要改动）；`toolchain/import_sample_assets.py`
   改为生成三个方向档位（`front`/`side_r`/`back`，见下）的层文件，落在与身体纸娃娃层同一套
   `sprites/<mesh_ref 去掉类别前缀>/<方向>/<slot_id 推导出的层名>.png` 三级目录（新增
   `toolchain/asset_import/ref_conventions.py` 的 `paperdoll_equip_layer_file`/
   `EQUIP_LAYER_CHECK_DIRECTIONS`）；`toolchain/asset_import/check_cmd.py` 的
   `display.equip_visual.mesh_ref` 校验相应改为对这三个方向档位各自核对层文件存在性（新增检查名
   `display_anim_equip_layer_file_missing`），不再校验此前的单个扁平文件。
   判断记录（为什么是 front/side_r/back 三向，不是当前 `creature.sample_hero` 实际声明的
   `direction_count=8` 对应的五个 canonical 档位）：接入方原始需求明确是"四方向游戏、三向层图"，
   14 第 2.1 节 canonical 半圈里 `front`/`side_r`/`back` 是跨 4/8/16 方向均合法、覆盖跨度最大的
   三档；`EQUIP_LAYER_CHECK_DIRECTIONS` 只是占位资产生成器/校验工具约定的最小落地子集，不是运行期
   方向档位换算规则本身的枚举上限——8/16 方向游戏若要装备层的过渡档位（`front_side_r` 等）也有
   独立美术，照常按同一套 `ResolveEquipLayerResourceId` 公式补对应方向的文件即可，不需要代码改动。

## 后果

### 正面

- 装备纸娃娃层第一次能够随角色朝向切换素材，接入方"装备穿戴后外观随朝向改变"的需求不再受阻。
- 装备层与身体层共用同一套方向档位换算公式（`ComposeLayerResourceId`），不会出现"身体层换了命名
  算法、装备层没跟着换"的分叉；装备新增的层与默认层现在共用同一次方向解析，此前的不一致一并根治。
- `ResolveLayerResourceId`/`ResolveEquipLayerResourceId` 均为 `protected virtual`，具体游戏可各自
  独立覆盖身体层与装备层的命名规则，互不影响。
- ADR-0037 决策 2 登记的"sprite 型 `mesh_ref` 是否提升为正式契约"待裁决事项就此裁决完毕。

### 负面

- **破坏性数据变更**：升级前把 `mesh_ref` 当"最终资源 Id"直接使用的存量数据（若其取值本身不满足
  "去掉类别前缀后能对应一套三级目录"这一新约定），升级后会解析到不存在的资源——`_equipOverridesBySlot`
  记录加载失败时按既有"资源加载失败保留占位方块，记诊断，不抛异常"的既有降级策略处理（不是新增
  行为，见 `SpriteCharacterRig.HandleResourceLoadCompleted` 判断记录），但视觉上装备层会显示占位
  方块而不是任何一张真实图。消费方需要把该字段值当装备层的"资源集名字前缀"重新准备一套三向（或
  更多方向）美术并按 `sprites/<name>/<方向>/<层名>.png` 落地，不能沿用升级前的单张扁平图。答复稿
  由主会话另行转给消费方，本 ADR 只记录事实与升级路径。
- `SpriteViewBase` 再新增一个可覆盖方法，具体游戏子类若已经重写过 `ResolveLayerResourceId` 想让
  装备层沿用完全相同的自定义命名规则，需要同时重写 `ResolveEquipLayerResourceId`（两者不再天然
  共享同一份自定义逻辑，除非调用方自己在两个重写里都调用同一个私有辅助方法）——与身体层/装备层
  两个独立覆盖点的设计意图一致（见决策 1），不是缺陷，只是多一处需要留意的重写面。

## 备选方案与为什么不选

- **给 04 `display.equip_visual.mesh_ref` 加按方向拆分的子结构（如 `{front: Id, side_r: Id, back:
  Id}`）**：能让方向映射在数据层显式可见，但破坏"04 只登记单个 `Id` 字段"的既有 schema 形状，且
  与身体层 `sprite_set_id`（同样是单个字符串引用、按约定推导出多方向文件）的既有惯例不一致——
  装备层与身体层理应遵循同一套"一个引用 id + 运行期按约定推导出多个方向文件"的心智模型，不需要
  为装备层单独发明一套数据结构。故不选，改用与身体层完全对称的"资源集引用 + 运行期方向档位换算"
  方案（决策 1）。
- **把 `ResolveEquipLayerResourceId` 做成 `ResolveLayerResourceId` 的一个可选参数重载**（如
  `ResolveLayerResourceId(SpriteLayerPlacement, Id? equipLayerSetRef = null)`）：能少一个方法名，
  但会让"给基类新增可选参数"这条本身就存在争议的 ABI 变更方式（新增可选参数不破坏调用点，但会让
  已经重写该方法的具体游戏子类的重写签名与基类不再匹配，`override` 编译报错）成为必须——与
  AGENTS.md"不删改既有公开签名、不给既有构造/方法加参数"的既定底线冲突。故不选，改为新增一个独立
  方法（决策 1），两者共用私有静态辅助方法避免重复实现。
- **保持 `mesh_ref` 语义不变，改为在 04 新增一个独立字段承载"是否按方向拆分"的布尔开关**：能保留
  向后兼容（旧数据不必改），但会让同一个字段在运行期有两种互斥的解释方式，增加数据编写者与代码
  两侧的心智负担，且"随朝向换图"是四方向/八方向游戏纸娃娃层美术的默认合理预期（同身体层一样默认
  按方向拆分），不应该需要显式开关才能得到符合直觉的行为。故不选，直接改语义（决策 1），破坏性
  变更的影响面在"负面"一节如实记录。

## 与游戏客户端的对应参考

对应主流 2D MMORPG（如魔兽世界的二维前身、暗黑破坏神系列的纸娃娃换装表现）"装备贴图随角色朝向
切换"的通用惯例——装备层美术资源与身体基础层同一套方向档位组织形式，不是单独一套规则。
