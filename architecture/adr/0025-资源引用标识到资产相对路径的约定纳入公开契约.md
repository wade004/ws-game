# ADR-0025 资源引用标识到资产相对路径的约定纳入公开契约

状态：已拍板 2026-09-11

## 背景

消费方反馈（内容编辑器项目，2026-09-11，见消费方反馈第 32 条，`architecture/落地计划/消费方反馈-2026-09-11-编辑器-第30-32-33-34条.md`）：04 第 7.1 节把 `display.map` 的 `sprite_set_id`/`icon_id` 两个字段定义为"由引擎适配层解析的不透明字符串"，架构文档层面确实没有给出、也不打算给出一个"标识 → 磁盘路径"的公开函数（04 第 7.1 节判断记录"任务书显式拍板……只做格式校验，不做跨表存在性检查"本就只关心加载期校验，不涉及路径解析）；但这条标识 → 相对路径的具体换算规则实际上已经存在，且不止一处——已落地的引擎适配层实现里有一份，内容导入工具链里另有一份，14 号文档第 1.2 节"命名规则"一节给出的是"文件名模板"这一份说明性文字，三处对同一条规则的表达方式并不完全统一，编辑器等内容工具没有任何单一权威来源可以调用，只能对照 `data/_sample` 下的具体样例反推（如 `sprite.item.sample_blade` → `sprites/item_sample_blade/`、`icon.creature.sample_beast` → `icons/creature/sample_beast.png`），既容易反推错、也无法在规则调整时自动感知。

核实现行实现（见回复文档"现行约定原文"一节，逐处引用源码判断记录）后确认：

1. **`sprite_set_id`（形如 `sprite.<category>.<name>`）→ 相对目录路径 `sprites/<category>_<name>`**：去掉第一个点分段（类别前缀）、剩余点号换成下划线，三处独立实现（已落地引擎适配层实现的资源加载入口、框架表现层"纸娃娃层资源标识"编码入口、内容导入工具链的精灵集导入子命令）互相字节级一致，但各自维护、没有任何机制保证不漂移。
2. **`icon_id`（形如 `icon.<category>.<name>`）→ 相对文件路径 `icons/<category>/<name>.png`**：类别前缀去掉后不flatten，`category` 段保留为独立子目录——这条规则只存在于内容导入工具链（图标/精灵集导入两个子命令）里，已落地的引擎适配层实现从未实现对 `icon_id` 的加载路径解析（该标识目前只作为元数据随 `display.map` 记录读出，尚无运行期消费方把它解析为具体图片资源并加载），即这条规则此前完全没有公开、也没有对照实现互相印证——编辑器反推示例 `icon.creature.sample_beast → icons/creature/sample_beast.png` 命中的正是这条唯一实现，只是编辑器不知道它来自哪里、是否权威。

两条规则彼此不同（一个 flatten 到底、一个保留一层子目录），且分散在多处独立实现里，与本架构一贯的"约定只应该有一处权威实现"取舍（同 [ADR-0020](0020-表达式词法器纳入公开契约.md) 决策 3"不允许派生出第二套"的同一理由）相悖。

## 决策

1. **`sprite_set_id`/`icon_id` 两个字段的"标识 → 相对路径"规则收口为公开契约**：新增公开静态入口（`SpriteSetDirectory`/`IconFile` 两个函数，另配 `TryParseSpriteSetId`/`TryParseIconId` 两个反向解析函数），放在框架契约面里全部消费方都能引用到的一个公共位置；此前分散在已落地引擎适配层实现、框架表现层内部的相互独立实现，全部改为转发到这一处，不再各自持有独立副本。
2. **规则本身不变，只是收口来源**：`sprite_set_id` 沿用"去掉类别前缀、点号全部换下划线"（flatten 到底），`icon_id` 沿用"去掉类别前缀后，第一段作为子目录、其余部分再 flatten 为文件名"（保留一层结构）——两条规则均取现行已在真实内容数据集上验证过的实现（见背景第 1/2 点），不改变任何既有资产的相对路径，不需要重新生成/迁移任何已产出的资产。
3. **内容工具链必须经由同一份规则，不得独立实现**：内容侧的资产导入工具（精灵集/图标两类导入命令）由各自内联计算路径改为调用同一条规则的独立语言实现（两种运行环境之间不共享同一份源码，只能各自实现、互相对照）；两侧各自的自动化测试对同一组真实样例（取自既有内容样例数据集）断言同一个期望路径字符串，任一侧改动规则而另一侧未同步，会在各自的测试里独立暴露。
4. **变更约定须走 ADR**：往后如需调整这两条路径规则本身（不是新增第三条并存的规则，是修改现有两条），须新增 ADR 说明变更理由与迁移影响（同 [12_扩展与变更流程.md](../12_扩展与变更流程.md) 第 5 节"结论性决策变化"的既有流程），不得在具体实现里私自调整——否则唯一实现被绕开，回到本 ADR 要解决的漂移问题。
5. **不扩大覆盖范围**：14 第 1.2 节"通用扁平文件名模板"覆盖的资源引用标识集合比 `sprite_set_id`/`icon_id` 更广（还包括模型资源标识、通用资源标识等），这些字段目前各自只有一处实现、彼此独立、不构成消费方反馈第 32 条指出的"重复实现导致漂移"问题，本次不纳入收口范围；后续若发现同类重复实现问题，按同一模式（新增 ADR + 收口为公开契约）逐个处理，不必一次性预先收口全部资源引用标识。

## 后果

### 正面

- 编辑器等内容工具获得一个权威来源，不再需要照抄样例数据反推路径规则，且规则调整时能立即感知（公开契约面变更本身会被消费方的集成/编译过程捕获）。
- 已落地引擎适配层实现与框架表现层内部此前两份相互独立、字节级相同的私有实现合并为一处，往后规则调整只需要改一个地方。
- `icon_id` 的路径规则第一次成为公开、有专门测试覆盖的契约，不再是"只存在于内容导入工具链里、没人正式承认过"的隐性约定；即使运行期加载路径尚未接入图标资源，编辑器等工具已经可以安全依赖这条规则做预览/校验。
- 两侧内容工具链现在共用同一条公开规则、各自独立实现互相对照测试，为往后同类"同一约定多处实现"问题提供了可复用的处理范式。

### 负面

- 新增的反向解析函数（`TryParseSpriteSetId`/`TryParseIconId`）是有损逆运算——`sprite_set_id` 的类别段与名称段之间的分隔符在正向编码时已经和名称内部可能出现的分隔符字符混同，反向解析依赖"类别取值范围是一个有限枚举集合，且枚举值本身不含该分隔符"这一假设；若未来新增的类别取值恰好破坏这一假设，反向解析会给出错误结果而不是报错——已在实现的判断记录里显式记录这一边界，消费方需要知悉反向解析不是无损的严格逆函数。
- 公开这两条规则后，往后调整它们（即使只是修一个边界情形的 bug）都成为契约变更，需要按决策 4 走 ADR，不能再像此前那样在某一处实现里静默修掉——多了一道流程成本，换来的是不再有第二处实现悄悄地留着同一个 bug 未修。

## 备选方案与为什么不选

- **维持现状，只在 14 号文档里把"命名规则"一节写得更精确，不新增代码契约**：文档精确化本身治标不治本——已落地引擎适配层实现与框架表现层内部两份独立实现已经存在，光把文档写准不会让它们合并成一份，规则调整时仍然要记得同步改两处代码，文档再精确也不能替代"只有一处权威实现"这一根本取舍（同 ADR-0020 背景一节的同一论证）。
- **只公开 `icon_id` 的规则（`sprite_set_id` 已经通过既有实现"够用"就不动）**：`sprite_set_id` 的重复实现问题（背景第 1 点）与 `icon_id` 完全没有公开实现的问题（背景第 2 点）是同一根因（约定散落各处、没有单一来源）的两个具体表现，只解决其中一个仍然留下另一处漂移风险，不如一并收口。
- **反向解析函数不提供，只提供正向"标识 → 路径"，编辑器需要反向查找时自行按目录扫描或维护索引**：编辑器等内容工具的典型场景之一是"看到一个磁盘文件，想知道它对应哪条内容记录"（如资产管线扫描出的孤儿文件排查），没有反向解析入口时只能重新发明一套猜测逻辑，与本 ADR 的初衷（消灭"猜规则"）矛盾；即使反向解析存在有损边界（见"后果·负面"），提供一个带明确边界说明的官方实现也好过完全没有、逼消费方自己写一个同样有损但没有说明的版本。
