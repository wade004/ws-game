# ADR-0020 表达式词法器纳入公开契约

状态：已拍板 2026-09-10

## 背景

消费方反馈（内容编辑器项目，2026-09-10，见 `architecture/落地计划/消费方反馈-2026-09-10-编辑器.md` E5）：表达式解析器的词法切分实现（词法 token 种类、切分逻辑）此前只是解析器内部的实现细节，不对外暴露——编辑器等工具想在文本框里对表达式语言做语法高亮（关键字/字符串/数字/引用标识符分色）、或做"光标所在 token 是什么"这类 token 级诊断时，拿不到任何官方提供的词法信息，只能照着 04 号文档第 6.1 节 BNF 与表达式解析器源码自己另写一套词法规则。

这与本架构一贯的契约边界原则相悖：ADR-0018 已拍板"框架对编辑器只承诺契约，编辑器不得读取框架内部实现"；反过来，框架同样不应该逼迫编辑器为了一个本就已经存在、且是唯一实现的词法规则去平行造一套轮子——两套词法规则一旦存在，语言本身任何一次演进（关键字集合变化、转义规则调整、点分标识符边界调整等）都需要两处同步修改，历史上没有任何机制强制保证这一点，必然逐渐漂移，且漂移只会在编辑器高亮显示与实际解析结果不一致时才被使用者发现。

表达式解析器（`core/foundation/expr/core/ExprParser.cs`）内部已经有一个独立的词法切分步骤（`core/foundation/expr/core/ExprLexer.cs` 的 `ExprLexer.Tokenize`），只是被声明为 `internal`，且切分出的 `ExprToken` 只记录了 `Position`（起始偏移）没有记录长度，不足以让调用方定位一个 token 在源文本里的完整区间。

## 决策

1. **词法切分入口纳入 `core/foundation/expr` 的公开契约面**：`ExprLexer`、`ExprToken`、`ExprTokenKind` 三个类型从 `internal` 改为 `public`；`ExprLexer.Tokenize(string text)` 作为公开的词法切分入口，签名不变，返回值类型收紧为 `IReadOnlyList<ExprToken>`（只读序列，调用方不应该、也不需要修改这份 token 列表）。
2. **`ExprToken` 补齐 `Length` 字段**：原有的 `Position` 属性更名为 `Start`（与 `ExprParseException.Position` 同一套"源文本字符偏移"坐标系，命名上与"区间起点"的语义对齐），新增 `Length` 属性表示该 token 在源文本里占用的原始字符数。`Start`/`Length` 构成半开区间 `[Start, Start+Length)`，是编辑器做高亮/悬浮提示定位的依据。`Text` 属性保持"解码后的值"语义不变——多数 token 种类下 `Text.Length == Length`，但字符串字面量例外（源文本的引号与转义序列在 `Text` 里已被解码/去除），两者不保证相等，调用方需要哪个信息用哪个属性，不能互相替代。
3. **与解析器共用同一份实现，不允许派生出第二套**：`ExprParser.Parse` 内部继续直接调用 `ExprLexer.Tokenize` 拿到 token 序列再做语法分析——本次改动只是放宽这两个类型的可见性与给 `ExprToken` 补一个字段，不复制、不重写词法逻辑本身。编辑器等工具做语法高亮/token 级诊断时必须调用这个公开入口，不得另写一套独立的词法规则；非法字符、未闭合字符串等词法错误抛出的 `ExprParseException`，其位置字段与 `ExprParser.Parse` 对同一段非法输入报出的位置逐位一致（因为是同一份实现，不可能不一致）。
4. **不改变语言本身**：本决策只涉及"是否公开已有实现细节"与"给 token 结构补一个字段"，不改变 04 号文档第 6.1 节 BNF、词法规则（关键字集合、转义规则、点分标识符边界等）、类型与求值规则的任何一条既有结论，按 `12_扩展与变更流程.md` 第 5 节归类为"变化仅是细节勘误"，04 号文档不递增版本号，只在第 6.1 节补一句说明并引用本 ADR（见文档内该处判断记录）。

## 后果

### 正面
- 编辑器等工具获得一个权威、与解析器逐字节同源的词法信息来源，语法高亮/token 级诊断不再需要照抄 BNF 另写一套容易漂移的词法规则。
- `ExprToken` 补齐 `Length` 字段后，调用方可以精确定位每个 token 在源文本里的字符区间，不需要自己用 `Text.Length` 反推（对字符串字面量这类做法本就是错的，见决策 2）。
- 词法层面的错误位置（`ExprParseException.Position`）与解析器报错位置天然一致，编辑器可以把词法错误与语法错误用同一套"跳转到源文本位置"的 UI 逻辑处理，不需要区分来源。

### 负面
- `ExprToken`/`ExprTokenKind`/`ExprLexer` 一旦公开，后续对词法规则的任何调整（新增关键字、调整转义规则等）都成为公开契约变更，需要按语义化版本规则评估是否构成破坏性变更（新增 `ExprTokenKind` 枚举值本身即为潜在破坏性变更——调用方若对该枚举做穷尽 `switch` 会因新增分支编译警告或运行期落入 `default`，需要在落地时明确告知消费方）；此前这份自由度完全在框架内部，没有外部约束。
- `ExprToken.Position` 更名为 `Start` 是一次二进制/源码不兼容的重命名——本仓库内唯一的调用方 `ExprParser.cs` 已同步改名，无其它消费方（编辑器项目尚未接入本入口，接入本身晚于本次改动），不构成对外发布产物的破坏性变更；但若本次改动落在已发布版本号之后，需要按语义化版本规则（`README.md`"版本与发布"一节）评估是否需要 MAJOR 递增——本次改动落地即随当前开发中版本一并发布，不单独评估。

## 备选方案与为什么不选

- **维持现状，编辑器自行实现一套词法高亮规则（只覆盖高亮不追求语义精确）**：语法高亮工具的常见做法，但与本架构"框架/编辑器不得各自维护一份本该只有一处的真相"的一贯取舍（同 ADR-0019 决策 2"登记与校验同源"的理由）相悖；点分标识符、转义字符串等细节一旦不一致，编辑器展示的高亮会在边界情况下与实际解析结果对不上，误导内容作者。
- **只公开一个"高亮片段"结果（如返回一组 `(start, length, cssClass)`），不公开 token 结构本身**：把"token 种类到高亮样式"的映射逻辑放进框架，编辑器的展示主题/配色方案就必须反过来依赖框架决定，职责倒挂（框架不应该关心编辑器如何着色）；公开 `ExprTokenKind` 本身，由编辑器自行决定每种 token 种类如何展示，边界更清晰。
- **新增一个独立的 `Core.Foundation.Expr.Tooling` 命名空间/程序集，包装一层"公开友好"的 API，不直接公开内部类型**：会制造第二份需要与内部实现同步的结构（哪怕是包装层，字段增减也要两处改），与决策 3"不允许派生出第二套"的取舍矛盾；`ExprLexer`/`ExprToken`/`ExprTokenKind` 本身结构已经足够简单（一个静态方法 + 一个只读结构体 + 一个枚举），直接放宽可见性即可，不需要额外包装层。
