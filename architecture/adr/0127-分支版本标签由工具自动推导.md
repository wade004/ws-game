# ADR-0127 分支版本标签由工具自动推导

状态：已拍板 2026-10-01

## 背景

`AGENTS.md` §1b 规定了分支上的版本号格式：分支为 `<主干版本号>_<分支名去掉 feature/ 或 bugfix/ 前缀>`，合并回主干后按主干升级、
格式 `<版本号>_release`。直接把这种带下划线后缀的字符串写进 `VERSION` 行不通：

- 包管理器（通用包注册表与引擎包管理器）的版本字段只接受语义化版本，下划线后缀会让包清单校验与发布失败；
- 改用 `-xxx` 预发布后缀（语义化版本允许）会让该版本的排序**低于**同号正式版，依赖解析与"严格大于当前版本"的发布校验因此出错；
- 分支各自改 `VERSION` 会让每次合并都在这一个文件上冲突。

## 决策

1. **包版本、引擎包清单、发布标签、发布包名、变更日志版本标题、公开面兼容探针基线全部继续用纯语义化版本 `X.Y.Z`**；
   `VERSION` 内容与版本一致性门禁、`build.ps1` 版本校验逻辑一律不变。
2. **用户规定的格式实现为"版本标签"，由工具按当前分支自动推导，不手写进任何文件**：
   - `feature/<名>`、`bugfix/<名>` 分支：`<VERSION 内容>_<名>`，例 `1.92.0_gate-timing-autolog_20261001`；
   - 主干：`<VERSION 内容>_release`；发布后 `VERSION` 升级，标签随之变成新版本号加 `_release`，合并时 `VERSION` 不会冲突；
   - 其它分支（发布维护分支等）：`<VERSION 内容>_<分支名，/ 换成 ->`；游离 HEAD：`<VERSION 内容>_detached-<短提交号>`；
   - 不变量：任何分支名下，标签都以 `VERSION` 内容开头且其后紧跟 `_`。
3. **标签的落点**：
   - 门禁脚本开头与汇总末尾各打印一行"版本标签：…"；
   - 构建时写入程序集的信息版本（文件属性里的产品版本）：门禁与构建脚本推导标签后经构建属性传入，未传入时回退为 `VERSION` 内容。
     只动信息版本，程序集版本与文件版本不动，公开面兼容性不变；
   - 发布脚本生成的发布说明首行写 `<新版本>_release`，其后接变更日志该版本条目正文；本次发布构建的信息版本同样是 `<新版本>_release`。
   仓库没有运行期对外暴露框架版本号的公开接口（现有的"版本"成员都是存档/数据表版本），因此不新增接口。
4. **分支名规范成为门禁步骤"分支名规范"**：只对 `feature/`、`bugfix/` 前缀的分支判定，要求 `<前缀>/<小写英文数字连字符的名称>_<八位有效年月日>`；
   不合规范（含中文等非 ASCII、大写、空格、缺日期、日期无效）判失败。标签对不合规范的名字仍照常推导，失败信息单独报出。
   主干、发布维护分支与游离 HEAD 不判定（主干上的合并后全量门禁因此不会被本步骤挡住）。

## 权衡（明确接受的风险）

- 程序集信息版本随分支变化，同一份源码在不同分支上构建出的二进制内容不同（仅该元数据字段）。发布永远在主干构建，
  产物里的标签是 `<新版本>_release`，不受影响；分支上的构建产物只用于分支内验证。
- 标签推导依赖版本管理命令与脚本运行环境；推导失败时门禁只提示、构建退回 `VERSION` 内容，由"分支名规范"步骤单独把关。
- 非 ASCII 分支名经环境变量传递时可能受控制台代码页影响，但这种名字本来就会被门禁判失败。

## 后果

- `AGENTS.md` §1b 删除"带后缀格式要等适配切片落地"的说明，改为现状一句话：`VERSION` 与包版本保持语义化版本，标签由工具推导。
- 推导与检查逻辑集中在 `toolchain/version_label.py`，用例覆盖各类分支的期望标签与"标签以版本内容加下划线开头""不合规名必然失败"两条不变量。
