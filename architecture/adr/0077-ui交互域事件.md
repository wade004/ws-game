# ADR-0077 UI 交互域事件

状态：已拍板 2026-09-23

## 背景

消费方反馈第二十批第 1 条（`<game>` 接入方，基于冻结发布提交核实）指出：`presentation/ui/**` 目前只有订阅（视图模型订阅逻辑层事件刷新自己），从未发出过任何事件——`feedback.binding` 这套"事件 → 呈现动作"的通用绑定机制（见 06 第 8 节、09 表现层）完全无法挂在任何 UI 交互上：打开一个面板、关闭一个面板、点一次技能栏按钮，都没有对应的事件可订阅，接入方只能绕开框架自己的事件总线另建一套 UI 侧通知机制才能给这些交互配音效/特效，与框架"呈现动作统一经 `feedback.binding` 声明式挂接"的既定口径不一致。

约束：

- 本层对外公开的契约只允许新增，不允许修改既有公开签名的参数列表。
- 不引入"buttonId"概念——`presentation/ui` 核心层是引擎无关、皮肤无关的层，不知道、也不该知道具体游戏用什么控件（按钮、快捷键、手柄输入）触发了一次交互；新事件只能挂在框架自己已经拥有的、与具体控件无关的概念上。
- 事件只陈述"哪个面板发生了什么交互"这一事实，不携带任何呈现意图字段（见决策 3）。

## 决策

1. **新增三个 UI 交互域事件：`ui.panel_opened { panelId }`、`ui.panel_closed { panelId }`、`ui.action_invoked { panelId, actionName }`**（`domain=ui`）。`panelId` 即 `ui_layout_definition.id`（面板注册用的定义 id，与"面板分类"`panel` 枚举字段是两个不同的东西，前者才是每条定义各自的唯一 id，后者是有限枚举——`ui.panel_opened`/`ui.panel_closed`/`ui.action_invoked` 三者共用同一套 `panelId` id 空间，便于同一条 `feedback.binding` 规则按需要用 `panelId` 关联"同一个面板"发生的多种交互）。`actionName` 取框架自身既有的 UI 意图方法名语义（即 `Presentation.Ui.UiIntents` 各公开方法自身承载的动词，如 `cast_skill`/`use_item`/`equip`/`unequip`/`buy`/`sell` 等——这套词汇表框架早已存在并长期维护，本决策只是把它同时作为事件字段值复用，不新建第二套词汇表），不是任何具体游戏的按钮/快捷键标识。
2. **发布点落在引擎无关的 UI 核心层，不落在某个具体皮肤/adapter**：
   - `Presentation.Ui.UiPanelRegistry.Open`/`Close`——面板打开/关闭的唯一权威登记点（已打开再次 `Open`、已关闭再次 `Close` 均不重复触发，与该类型既有幂等语义一致）——在登记状态真正发生变化时分别广播 `ui.panel_opened`/`ui.panel_closed`。
   - `Presentation.Ui.UiIntents`——UI 意图的唯一入口——新增一批带前导 `Id panelId` 参数的方法重载（与不带 `panelId` 的既有重载按参数**个数**区分，避免可选参数导致的重载歧义；`Move`/`OpenMenu`/`CloseMenu` 不提供 `panelId` 重载，因为它们不对应任何面板内交互），调用其中任一重载即广播一次 `ui.action_invoked`，`actionName` 由该方法自身固定给出（调用方不能自定义字符串），`panelId` 由调用方传入（只有调用方——不论是原生 UI 视图模型还是某个引擎适配层的皮肤代码——知道自己所在的面板是哪一条 `ui_layout_definition`，`UiIntents` 是单例、无状态，不持有"当前面板"上下文，不能反过来替调用方猜）。
   这两个类型都在同一个引擎无关的 `presentation/ui/core` 内，原生 UI 视图模型与任何引擎适配层皮肤面板只要经它们完成登记/发起意图，都自动获得这三个事件，不需要各自重复接线。
3. **事件只陈述事实，不携带呈现意图，框架不预设默认呈现绑定**：三个事件的字段仅有 `panelId`/`actionName`（`ui.panel_opened`/`ui.panel_closed` 只有 `panelId`），不新增诸如"该不该出声""是不是确认类操作"这类呈现判断字段——这类判断属于具体游戏的呈现设计，框架发事件只负责"发生了什么"，"该怎么表现"完全交给 `feedback.binding`/游戏侧代码决定（13 第 5 节"框架只给状态，呈现归游戏"的直接推论）。相应地，框架不为任何 UI 交互登记默认音效/特效绑定；`data/_sample/feedback/feedback.binding.json` 里挂在这三个事件上的样例行仅作为"怎么用"的示范，使用样例资源，不构成推荐配置。
4. **09 表现层第 1 节 P2 铁律措辞收窄修订**：既有措辞"表现层只允许订阅事件，不允许发出事件（唯一例外：`presentation.playback_finished`）"改为"表现层被允许发出的事件限定在一个明确枚举的小集合内（目前含 `presentation.playback_finished`、本篇新增的 `ui.panel_opened`/`ui.panel_closed`/`ui.action_invoked`，以及 [ADR-0078](0078-单位步幅位移事件.md) 新增的 `unit.stride_completed`），集合外的表现层代码仍然只能订阅"——收窄而非删除 P2 的约束意图：新增的每个例外都不携带任何"逻辑判定"数据、不写回任何逻辑状态、也不影响仿真基线，与 `presentation.playback_finished` 原有的豁免理由（09 第 1 节既有措辞）同一性质，不是放开表现层可以随意发事件。

## 后果

### 正面

- `feedback.binding` 第一次能挂在真实的 UI 交互上，接入方不需要另建一套 UI 通知机制。
- 不引入 buttonId 或任何游戏专属标识，`actionName` 复用框架已有词汇表，事件词汇表不因具体游戏的皮肤设计膨胀。
- 发布点在引擎无关核心层，原生视图模型与任意引擎适配层皮肤自动获得同一套事件，不需要各自重复接线。

### 负面

- `UiIntents` 新增一批 `panelId` 重载，公开方法数量明显增加，是纯加法 ABI 演进的既有代价（同 ADR-0059/0061/0070 已接受的同一类代价）。
- 09 第 1 节 P2 铁律的例外集合从 1 条增至 4 条，需要长期维护"这条例外为什么不违反 P2 精神"的判断记录，避免未来被误当作"表现层可以随意发事件"的先例扩大解释。

## 备选方案与为什么不选

- **引入 buttonId，让事件直接携带具体控件标识**：能让接入方不用改造已有的皮肤按钮点击回调，但会让引擎无关的 UI 核心层知道"按钮"这个具体皮肤概念，与 01/09 已经确立的"L-1 引擎适配层与其上各层解耦"边界冲突，且不同游戏的控件命名各不相同，框架事件词汇表会被迫收纳游戏专属词汇。故不选。
- **在 `UiActionInvokedEvent` 上追加"是否需要确认音"之类的呈现提示字段**：能省去游戏侧自己按 `actionName` 归类哪些动作该配音效，但这类归类本质是呈现设计判断，框架没有能力、也不该替所有游戏做这个判断（不同游戏对"买卖是否该有确认音"的设计答案完全不同）。故不选，归 `feedback.binding` 的 `condition`/`actions` 自行按 `actionName` 挑选。
- **`panelId` 由 `UiIntents` 自己维护"当前面板"栈、调用方不必传**：能省一个参数，但 `UiIntents` 是单例、可能同时服务多个并发展开的面板（如快捷栏与背包同时可见），维护一个全局"当前面板"栈本身就不可靠，且需要额外的"进入/离开面板"生命周期接线，比直接让唯一知道答案的调用方传参更复杂。故不选。

## 落地缺陷与修复（2026-09-23）

消费方第二十五批反馈基于 1.65.0 真实场景实测报告两个现象：(1) 真实发出一次 `ui.panel_opened` 之后，同一次冒烟会话内一条此前正常工作的 `item.equipped -> floating_text` 绑定不再触发；(2) `ui.action_invoked -> play_sfx` 确认真实派发到位（消费方自建订阅者确认 `actionName` 命中），但从未观测到音效真实播放。消费方已排除绑定写法本身（与其它正常工作的条目一致，无 `condition`、无 `attach`）与资源文件缺失/损坏两种可能。

**排查方式**：不凭推理下结论，先在核心层 + 表现层（真实 `IEventBus`、真实 `FeedbackBinder`、真实装配根）构造红色用例，而非直接假定某个原因成立。

**结论（与最初假设不同，如实记录）**：

- 现象 1（跨事件 key 的污染）：经真实事件总线 + 真实装配根反复复现，包含消费方描述的隔离步骤（零命中规则的 `ui.panel_opened` 发布、触发/不触发 `MenuOverlay` 子状态两种变体），以及直接针对事件总线本身的重入发布测试，均未能复现。确认不同事件 key 之间的派发本就相互隔离（一个 key 的订阅回调抛异常不影响另一个 key），`PublishImmediate` 从订阅回调内部重入发布（同 key 或不同 key）也已经能完整投递到两次发布各自的全部订阅者，不丢单、不因重入损坏正在进行中的派发。本次未能在核心层 + 表现层代码中找到任何路径能让一次真实的 `ui.panel_opened` 发布影响一个不相关的后续事件的绑定执行。
- 现象 2（确认已派发但从未观测到播放）：沿 `play_sfx` 动作的整条派发路径通读代码并经真实装配根验证——字面量 `sfx_id`、无 `attach`、无 `condition` 的绑定形态下，这条路径不存在任何依赖实体解析的分支（不会因为 UI 事件不带实体而抛出或跳过）；"首次引用、此前从未加载过某音效资源"这一关键变量（消费方现象里的核心条件）经真实装配根验证，冷加载排队、去重、真实异步资源加载完成回调（模拟真实引擎"不在调用当下同步回调"的时序）到最终播放的整条链路均按预期工作。核心层 + 表现层代码中未发现可归因的缺陷；本现象判断为可能与承载音频真实播放这件事的具体运行环境相关，留待在能够运行该环境的场景下单独排查。
- 排查中确认存在的一个真实缺陷（与现象 1/2 的字面描述不完全一致，但同属"UI 事件不携带实体"这一设计决策暴露出的一类风险，值得一并修复）：`FeedbackBinder.OnEvent` 处理同一个事件命中的多条规则时，一条规则的 `action` 派发（例如给一个不携带实体的 UI 事件配了从战斗规则模板照抄来的、隐含依赖实体解析的动作写法）一旦抛异常，会连带中止同一次调用里排在后面的其它规则/其它动作——不影响不同事件之间（已验证隔离），但会让"同一事件命中的其它绑定被误跳过"。这条缺陷目前只能通过故障注入的测试替身复现（通读当前真实接线的全部具体呈现组件，实体解析均已是查不到就返回空的防御式写法，现状下不会真的抛出），不是现象 1/2 本身的成因，但属于同一类"呈现动作对实体解析的隐藏假设"风险的一个真实、已修复实例。修复与详细判断记录见 `presentation/feedback_binder/README.md` 判断记录 18（属于 `feedback.binding` 的通用派发健壮性问题，不限于 UI 域事件，故未并入本篇正文决策）。

**为什么原验收没有覆盖到这条路径**：原 ADR-0077 验收复用的样例数据与既有测试绑定形态本身干净（无 `condition`、无 `attach`），只验证了"正常路径"（真实发布、真实命中、真实派发、全程不抛异常）。当时没有构造"绑定命中但派发过程抛异常"这条路径——这本是"UI 事件不携带实体"这一决策的直接推论（内容作者一旦对 UI 事件配了隐含依赖实体解析的动作写法就会命中），但决策拍板时未连带补一条对应的健壮性验收用例。

**是否需要修改本篇决策**：不需要。排查未发现立即派发（`PublishImmediate`）语义本身与两个现象或已确认的缺陷有关，第 3 节"事件只陈述事实，不携带呈现意图"的决策不受影响——`presentation/feedback_binder/README.md` 判断记录 18 的修复落在动作派发的异常隔离上，不涉及在事件里补充实体/呈现意图字段。
