# ADR-0110 导航契约新增"最近可走点"

状态：已拍板 2026-09-29

## 背景

消费方第六十批反馈（阻塞项，复现路径只读复核成立）：点地移动的目标点落在阻挡格内时，寻路端点契约
（起终点任一不可走即返回"无路径"）使建路直接失败，移动系统按既有口径报"无路径"失败、请求被丢弃，
单位原地不动。桌面类游戏的惯例是"点到墙上也走到离该点最近的可走位置"。消费方明确不在游戏侧自建
"最近可走点"算法（会复制一份导航层的可走判定，网格尺寸或剪枝规则一变就静默失效），要求框架原生
提供。

## 决策

1. **导航契约新增两个默认接口成员**：`TryFindNearestWalkable(mapId, point, maxRadius, preferNear,
   out walkable)` 与 `FindNearestWalkableCandidates(mapId, point, maxRadius, preferNear, maxCount,
   results)`（后者取按同一排序规则的前 `maxCount` 个候选，第一个即前者的结果）。两者都是纯新增的默认
   接口成员，既有实现源码/二进制兼容。
2. **排序规则写死，只有一份实现**：范围 = 以 `point` 为圆心、`maxRadius` 为半径的圆。**主键** = 候选到
   `point` 的距离按导航格宽量化（`floor(距离 / 格宽)`，同一量化档并列）；**次键** = 候选到 `preferNear`
   的距离（小者优先）；仍并列按坐标字典序（先 X 后 Y）。`point` 本身可走时原样返回它，排第一位。范围内
   没有可走点返回失败。返回的候选点取格心（或点本身），保证作为寻路终点不会因"贴边/落在格边界"被判不可走。
3. **格几何与排序集中在契约层的共享工具里**：网格布局（阻挡包围盒外扩边距、缺省格宽、单轴格数上限）与
   排序搜索各只有一份实现，默认接口实现、测试桩、真实网格实现都只是把各自的"格子是否可走"交给它，
   因此两个实现对同一张阻挡图给出**相同**的最近可走点。真实网格实现构建自己的寻路网格时同样用这份
   布局公式（不再各抄一份）。默认接口实现（给不知道网格的第三方实现者）只用可走判定做同心环采样
   （步长 0.25 世界单位，环 k 半径 `k × 0.25`，每环 `max(8, ceil(2πr / 0.25))` 个方向），主键（环号）精确、
   环上两个采样点之间的可走点可能漏掉，是近似。
4. **移动选项**（默认值下 1.87.0 行为逐字节不变）：`UnwalkableTargetPolicy`（`Reject` 默认 /
   `SnapToNearestWalkable`）、`UnwalkableTargetSnapRadius`（默认 8.0 世界单位）、
   `UnwalkableTargetCandidates`（默认 8，含最近点本身的候选总数上限）。
5. **生效范围**：只对点目标移动请求生效（`ToTarget` 一族；召唤物跟随等以同一种移动意图提交目标点的调用方，
   移动系统看到的意图与 `ToTarget` 无法区分，一并生效）。追击（`ToUnit`，见 ADR-0102）、方向移动、
   受控位移不变。点目标的**所有**建路点走同一套解析：首次建路、阻挡变化后的重规划——重规划从**原始请求
   目标**重新解析（移动状态新增只读属性记录原始目标），原始点后来变可走了就直接去原始点。
6. **建路顺序**：先取最近可走点建路；失败（落在不可达孤岛上）时按同一排序规则依次尝试后续候选，至多
   `UnwalkableTargetCandidates` 个；全部失败才按既有口径报"无路径"。
7. **对外可观测性**：失败通知携带的目标始终是**原始请求目标**；新增"目标被调整"通知
   （`MovementHost.OnMoveTargetAdjusted`：单位 id、原始请求目标、解析后的目标），只在解析结果与原始点
   不同且据此建路成功时触发，每次解析触发一次；到达判定与到达通知按解析后的目标走。
8. **离散（回合）步**：`Reject` 时完全不变；`SnapToNearestWalkable` 时先解析最近可走点、再走既有的格子
   吸附流程。

## 后果

### 正面

- 点墙/点阻挡外框带走到离该点最近的可走位置，消费方不必在游戏侧复制可走判定。
- 排序规则与网格几何只有一份，两个导航实现的结果一致由构造保证，并有一致性场景用同一组输入在两个
  实现上跑。
- 纯新增 ABI；默认 `Reject` 下既有行为逐字节不变。

### 负面（已知限制）

- "可走"不等于"可达"：候选回退只有 `UnwalkableTargetCandidates` 个，最近点与其后若干候选都在同一块
  不可达区域内时（区域大于候选数覆盖的范围），仍报"无路径"。
- 最近可走点精度为一格（取格心），不是阻挡边界上的精确点。
- 导航对网格范围之外的点一律判可走（只有登记的阻挡矩形不可走），因此地图范围外、又不在任何阻挡内的点
  本身"可走"，原样返回、不被夹取到范围内；若该点被阻挡外框隔开不可达，仍按"无路径"处理（候选回退
  也只在其附近找）。落在阻挡外框带内的点会被吸附回框内。
- `SnapToNearestWalkable` 对全部以点目标意图提交的调用方生效，不区分调用方（含召唤物跟随）；只想对
  玩家点击生效的游戏需在游戏层按调用方切换选项。
- 阻挡变化策略为 `Revalidate` 且旧路径仍畅通、或 `Ignore`/`Stop` 时不重新解析（只有实际发生重规划才从
  原始目标重新解析）。
- 单位自身站在不可走点上时，所有候选寻路必然失败（端点契约），仍报"无路径"，与 `Reject` 一致。
- 默认接口实现是采样近似（见决策 3），需要精确结果的实现应覆盖为按自身网格搜索。

## 备选方案与为什么不选

- **只在移动系统内按格宽自行搜索**：会在移动系统里复制一份导航网格几何，网格规则变化时静默失效——
  与消费方明确拒绝的"平行机制"同类，不选。
- **只提供"部分路径"（路径终点取最接近目标的可达点）**：终点由寻路内部决定，调用方与通知面拿不到"调整后
  的目标"，且各实现语义不一；不选。
- **对范围外的点夹取到网格范围内再搜**：导航对范围外的点判可走且可直达，夹取会让开阔地图上的远处点击被
  截断或超半径失败；不选。
