# ADR-0110 导航契约新增"最近可走点"与"可达最近点"

状态：已拍板 2026-09-29

## 背景

消费方第六十批反馈（阻塞项，复现路径只读复核成立）：点地移动的目标点落在阻挡格内时，寻路端点契约
（起终点任一不可走即返回"无路径"）使建路直接失败，移动系统按既有口径报"无路径"失败、请求被丢弃，
单位原地不动。桌面类游戏的惯例是"点到墙上也走到离该点最近的可走位置"。消费方明确不在游戏侧自建
"最近可走点"算法（会复制一份导航层的可走判定，网格尺寸或剪枝规则一变就静默失效），要求框架原生
提供。

首版只按几何取"最近可走点"再试少量后续候选，仍漏掉一整类点击：点击点**可走但不可达**——地图外围
一圈阻挡外框的外侧、围栏另一侧、封闭院落里。这些点离它最近的一批可走点全在同一块不可达区域内，
按到点击点的距离取几个候选逐个寻路必然全部失败，结果仍是"无路径"。用消费方真实的阻挡矩形集实测
（外框外侧 3 个单位处的点击）确认了这一点。"可走"与"从单位处可达"是两回事，吸附结果必须以
**与单位当前位置连通**为准。

## 决策

1. **导航契约新增三个默认接口成员**（纯新增，既有实现源码/二进制兼容）：
   - `TryFindNearestWalkable(mapId, point, maxRadius, preferNear, out walkable)` 与
     `FindNearestWalkableCandidates(mapId, point, maxRadius, preferNear, maxCount, results)`：纯几何查询，
     只看"可走"，后者取按同一排序规则的前 `maxCount` 个候选，第一个即前者的结果。
   - `TryFindNearestReachable(mapId, from, point, maxRadius, out reachable)`：在以 `point` 为圆心、
     `maxRadius` 为半径的范围内找**与 `from` 连通**的可走点。连通规则与该实现的 `FindPath` 完全一致
     （含"不许切角"等邻接规则），返回 `true` 时对返回点调用 `FindPath(from, reachable)` 必定成功；
     `point` 本身可走且与 `from` 连通时原样返回它；`from` 自身不可走或范围内没有这样的点返回失败。
2. **排序规则写死，只有一份实现**：范围 = 以 `point` 为圆心、`maxRadius` 为半径的圆。**主键** = 候选到
   `point` 的距离按导航格宽量化（`floor(距离 / 格宽)`，同一量化档并列）；**次键** = 候选到偏好点的
   距离（小者优先；`TryFindNearestWalkable` 的偏好点由调用方给，`TryFindNearestReachable` 固定取 `from`）；
   仍并列按坐标字典序（先 X 后 Y）。`point` 本身满足条件时原样返回，排第一位。返回的候选点取格心
   （或点本身），保证作为寻路终点不会因"贴边/落在格边界"被判不可走。三个成员共用这一份排序，
   区别只在候选的限定条件（可走 / 可走且与 `from` 连通）。
3. **内置实现都做精确实现**：
   - 网格实现（引擎适配层）：按阻挡版本缓存主网格的**连通分量标号**（4 邻域洪泛；寻路的 8 邻域"对角
     移动要求两个正交邻居都可走"使对角边从不连接原本不连通的格子，两者分量相同）。标号随寻路网格
     一起在阻挡变化（登记/清空/重建）时丢弃，下一次查询才惰性重算一次，平时查询只比较标号。查询 =
     标号预筛出与 `from` 同分量的候选，按排序取第一名，再对它调用一次 `FindPath` 确认（确认失败的候选
     排除后取下一名，至多 16 次）。`from` 位于网格范围外时寻路退化为直线检查，此时不用标号，逐候选
     `FindPath`。标号只算主网格（寻路的第一道），不把网格范围外的开阔区域并入分量——`FindPath` 本身不经
     网格外绕行，标号必须与它一致。
   - 测试桩：桩的寻路只有直线，"连通"就是"两端可走且线段不受阻"，它依赖 `from` 的位置、不是等价类关系，
     没有可缓存的分量标号；逐候选直接用与 `FindPath` 同一个判定，谓词只在候选能刷新当前最优时才调用。
   - 默认接口实现（不知道网格的第三方实现者）是近似：取几何候选的前 64 个按序逐个 `FindPath` 试探，
     返回第一个成功者；前 64 个都不可达时返回失败，即使更远处有可达点。
4. **格几何与排序集中在契约层的共享工具里，且是公开类型**：`NavGridLayout`（网格布局：阻挡包围盒外扩
   边距、缺省格宽、单轴格数上限）与 `NearestWalkableSearch`（`CollectOnGrid` 按格精确搜索、`CollectSampled`
   环采样）各只有一份实现，默认接口实现、测试桩、网格实现都只是把各自的"格子是否满足条件"交给它，
   同一张阻挡图上各实现结果一致。它们**必须公开**：接口注释要求网格实现覆盖候选枚举并调用
   `CollectOnGrid`，游戏自己写的导航实现同样需要；改成内部类型加友元程序集要求核心程序集逐个登记下游
   程序集名，第三方无从使用。对外契约成员：`NavGridLayout`（`Compute`、`CellCenter`、`Origin`/`CellSize`/
   `Width`/`Height`、三个常量）、`NearestWalkableSearch`（`CollectOnGrid`、`CollectSampled`、`SampledStep`、
   `MinSampledDirections`、`MaxSampledRings`）；排序比较、候选结构、区间夹取、可达试探个数上限都是私有/
   内部细节，不承诺稳定。
5. **移动选项**（默认值下 1.87.0 行为逐字节不变）：`UnwalkableTargetPolicy`（`Reject` 默认 /
   `SnapToNearestWalkable`）、`UnwalkableTargetSnapRadius`（默认 8.0 世界单位）、
   `UnwalkableTargetCandidates`（默认 8，只在 `TryFindNearestReachable` 给出的点仍然 `FindPath` 失败——
   第三方近似实现所致——时使用，含已试过的那个的候选总数上限）。
6. **生效范围**：只对点目标移动请求生效（`ToTarget` 一族；召唤物跟随等以同一种移动意图提交目标点的调用方，
   移动系统看到的意图与 `ToTarget` 无法区分，一并生效）。追击（`ToUnit`，见 ADR-0102）、AI 的自有寻路
   调用、方向移动、受控位移不变。点目标的**所有**建路点走同一套解析：首次建路、阻挡变化后的重规划——
   重规划从**原始请求目标**重新解析（移动状态新增只读属性记录原始目标），原始点后来变可走或变可达了
   就直接去原始点。
7. **建路顺序**：先经 `TryFindNearestReachable(单位位置, 原始目标, 半径)` 取与单位连通的最近点，再对它
   `FindPath`（内置实现保证一次成功）；只有 `FindPath` 仍失败（第三方近似实现）时才按几何排序依次尝试
   `UnwalkableTargetCandidates` 个后续候选；全部失败或半径内没有可达点才按既有口径报"无路径"。
   "点本身可走但不可达"（围栏另一侧、封闭院落里、边界阻挡带外侧的点）同样走这条路径。
8. **对外可观测性**：失败通知携带的目标始终是**原始请求目标**；新增"目标被调整"通知
   （`MovementHost.OnMoveTargetAdjusted`：单位 id、原始请求目标、解析后的目标），只在解析结果与原始点
   不同且据此建路成功时触发，每次解析触发一次；到达判定与到达通知按解析后的目标走。
9. **离散（回合）步**：`Reject` 时完全不变；`SnapToNearestWalkable` 时先解析、再走既有的格子吸附流程。

## 后果

### 正面

- 点墙、点阻挡外框带、点外框外侧、点围栏另一侧都走到离该点最近的**走得到**的位置，消费方不必在游戏侧
  复制可走判定或连通判定。
- 排序规则与网格几何只有一份；网格实现的连通标号按阻挡版本缓存，重算是一次 O(格子数) 洪泛（消费方真实
  阻挡图上不到 1 毫秒），每次点击只多一次与移动系统随后那次同量级的寻路。
- 纯新增 ABI；默认 `Reject` 下既有行为逐字节不变。

### 负面（仍然成立的限制）

- 最近点精度为一格（取格心），点本身可走且可达时才是原始点。
- 搜索半径默认 8.0 世界单位：点击点离最近的可达区域比半径还远时（例如外围阻挡外框很厚、点击点又落在外框
  外侧）仍报"无路径"；需要更大范围的游戏调大 `UnwalkableTargetSnapRadius`。
- 网格实现的标号只算主网格，与寻路的第一道一致：比格子更薄的阻挡使"主网格连通但 `FindPath` 不认"的
  候选由确认步排除；反过来，主网格判为不连通、却只靠寻路的细网格/直线兜底才走得通的窄通道（窄于格子）
  不会被识别为可达，结果偏保守。
- 网格范围之外的点：导航对它们判可走（只有登记的阻挡矩形不可走），点本身可走且直线可达时原样返回，
  不夹取到范围内；起点在网格范围外时不用标号，只能逐候选 `FindPath`。
- 测试桩没有绕障（直线导航），"连通"即直线不受阻，桩上的可达结果因此比网格实现更保守（绕过墙才能到的点
  在桩上算不可达）。
- `SnapToNearestWalkable` 对全部以点目标意图提交的调用方生效，不区分调用方（含召唤物跟随）；只想对
  玩家点击生效的游戏需在游戏层按调用方切换选项。
- 阻挡变化策略为 `Revalidate` 且旧路径仍畅通、或 `Ignore`/`Stop` 时不重新解析（只有实际发生重规划才从
  原始目标重新解析）。
- 单位自身站在不可走点上时，所有候选寻路必然失败（端点契约），仍报"无路径"，与 `Reject` 一致。
- 默认接口实现是近似（决策 3），需要精确结果的实现应覆盖 `TryFindNearestReachable`（并把候选枚举覆盖为
  按自身格子的 `CollectOnGrid`）。

## 备选方案与为什么不选

- **只在移动系统内按格宽自行搜索**：会在移动系统里复制一份导航网格几何，网格规则变化时静默失效——
  与消费方明确拒绝的"平行机制"同类，不选。
- **只提供"部分路径"（路径终点取最接近目标的可达点）**：终点由寻路内部决定，调用方与通知面拿不到"调整后
  的目标"，且各实现语义不一；不选。
- **对范围外的点夹取到网格范围内再搜**：导航对范围外的点判可走且可直达，夹取会让开阔地图上的远处点击被
  截断或超半径失败；不选。
- **首版做法：按几何取最近可走点，失败再按同一排序试少量后续候选**：点击点可走但不可达时，最近一批候选
  全在不可达一侧，候选数再大也是碰运气；不选，改由导航按连通性直接挑出可达的那一个。
- **给网格外围补一圈"图外"可走格并入连通分量**：寻路本身不经网格外绕行，把图外区域并入标号会让"标号
  连通而 `FindPath` 失败"，违背"连通规则必须与 `FindPath` 完全一致"；不选。
