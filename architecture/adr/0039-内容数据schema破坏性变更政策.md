# ADR-0039 内容数据 schema 破坏性变更政策

状态：已拍板 2026-09-18

## 背景

勘察确认仓库目前**没有**一份成文的、专门针对"内容数据 schema 破坏性变更"的政策：

- `architecture/12_扩展与变更流程.md` 第 1、2、5 节覆盖的是"新增内容要不要走 ADR"（第 1 节）、
  "新增原语要不要走审批"（第 2 节）、"文档与实现分歧如何处理"（第 5 节）三类问题，均不回答"改
  一个既有字段/表的语义算不算破坏性变更、破坏性变更本身该如何管理节奏"这一问题。
- `AGENTS.md` 第 3 节"代码规则"里的"ABI 只新增"约束，明确针对的是**代码公开签名**（重载、类型、
  接口成员、构造/方法参数），不覆盖数据 schema 层面的表结构、字段语义、资源引用取值约定。
- 已确认的唯一先例：1.43.0 新增的 `equip_visual_mode_field_group` 规则（`EquipVisualModeFieldGroupRule`）
  是一条新增的、无条件注册的 Error 级校验规则——它上线后，此前满足旧规则但不满足新规则的既有数据
  会首次报错，这本质上是一种破坏性变更（数据不变，规则变了，结果从"通过"变成"报错"），但当时是
  按 CHANGELOG 显著标注处理的，没有对照任何成文政策，只是"恰好做对了"。
- [ADR-0038](0038-资源引用类别前缀唯一决定路径空间.md) 决策 2/3/4 要求把 sprite 型动画资源引用
  的类别前缀从 `anim` 改为新增的 `sprite_anim`，属于典型的"改资源引用取值约定"，同样撞上了这一
  政策空白——本 ADR 与 ADR-0038 同批拍板，用于补齐 ADR-0038 落地时应当遵循的破坏性变更流程依据。

这一空白如果不补，往后每次遇到"要不要允许一次性破坏性改、改了要不要给迁移期"这类问题，只能临时
现场讨论，容易出现口径不一致（如同一类"新增无条件 Error 级规则"，下次可能被当作"不算破坏性变更"
处理）。

## 决策

1. **适用范围**：本政策适用于**内容数据 schema**——数据表结构、字段、字段语义、资源引用取值
   约定。**代码 ABI 不在本 ADR 范围**，代码 ABI 已有 `AGENTS.md` 第 3 节的独立约束，两者是两套
   分开的规则，互不替代。

2. **分级**：
   - **兼容变更**：新增可选字段。
   - **破坏性变更**：新增必填字段、改字段名、改字段语义、改资源引用取值约定、删字段。
   - **新增无条件 Error 级校验规则视同破坏性变更**：即使不改任何表结构/字段本身，只要新规则
     会让此前合法的既有数据首次报错，就按破坏性变更对待，不因为"没有改 schema 定义本身"而免于
     本政策约束。

3. **当前期政策（尚无下游正式游戏内容接入）**：破坏性变更允许在一个 minor 版本内一次性完成，但
   必须同时齐备以下材料，缺一不可：
   - 一份 ADR，说明变更理由、影响范围与迁移方式；
   - CHANGELOG 显著标注为破坏性变更（不能混在普通条目里不加区分）；
   - 逐字段的 before/after 迁移说明（旧取值/旧结构 → 新取值/新结构，覆盖每一个受影响字段）；
   - 仓库内全部数据根（当前实际持有数据的是 `data/_sample`；`data/_framework`、
     `games/_template/data/game`、`core/sim/tests/data` 若持有受影响字段也需同步迁移）同步完成
     迁移，不允许只改一部分数据根；
   - 通过消费方反馈回复文档通知消费方（同现行"消费方反馈-YYYY-MM-DD-…"系列文档的既有渠道）。

4. **下游正式游戏内容接入之后的政策**：一旦有下游正式游戏内容接入（区别于本仓库自身的
   `data/_sample` 自测数据），当前期"一次性完成"的做法停止适用，改为**至少保留一个 minor 版本
   的弃用期**：弃用期内新旧两种形态都必须能被正确读取（旧形态读取时发出警告，不阻断），弃用期
   结束后再移除对旧形态的兼容读取。本条款只设定"至少一个 minor"的下限与"弃用期内兼容读取 + 发
   警告"的最低要求，具体某次破坏性变更的弃用期长度、警告文案等落地细节留给该次变更自己的 ADR
   决定。

5. **补记先例**：1.43.0 的 `equip_visual_mode_field_group` 新增规则，按本政策第 2 条分级属于
   "新增无条件 Error 级校验规则"一类，当时按 CHANGELOG 显著标注处理，做法与本政策第 3 条当前期
   政策一致（虽然当时没有对照任何成文政策）；本条不要求补做 ADR 或补做其它材料，只作为先例记录，
   确认本政策与已发生的实际做法不冲突。

6. **与 12 号文档的关系**：`architecture/12_扩展与变更流程.md` 第 5 节"文档与实现不一致的处理
   规则"处理的是另一个问题（文档描述与实现不一致时怎么办），与本政策（数据 schema 本身要不要变、
   变了怎么管理节奏）并列、不重叠；在该文档中新增一处指向本 ADR 的引用，帮助读者从"变更流程"文档
   找到"破坏性变更政策"这条相关但分开的规则。

## 后果

### 正面

- 往后每次遇到"这算不算破坏性变更""破坏性变更要不要给兼容期"，有一份成文政策可以直接对照，不再
  需要每次临时讨论，减少口径不一致的风险。
- "新增无条件 Error 级规则视同破坏性变更"这一条把此前容易被忽略的一类变更（不改 schema 定义本身，
  只改校验严格度）明确纳入管理，避免以后出现"这次只是加了个规则，不算破坏性变更"的误判。
- 为 [ADR-0038](0038-资源引用类别前缀唯一决定路径空间.md) 落地期的迁移工作（sprite 型动画资源
  引用类别前缀迁移）提供了明确的材料清单（ADR、CHANGELOG 标注、逐字段迁移说明、全数据根同步、
  消费方通知），落地期不需要另外现场决定"要不要通知消费方"这类问题。

### 负面

- "当前期允许一次性完成"这一宽松政策是有时效性的——一旦有下游正式游戏内容接入，就必须切换到"至少
  一个 minor 弃用期"的更严格流程，届时受影响的变更实现成本会上升（需要同时维护新旧两种读取路径），
  这一成本是本政策决策 4 主动接受的、为了保护下游正式内容不被无预警破坏的必要代价。
- 决策 3 要求"仓库内全部数据根同步迁移"，即使某个数据根当前没有受影响字段的实际数据（如
  `data/_framework` 当前 `display/` 目录为空），也需要在流程上确认这一点而不是假设，增加了每次
  破坏性变更的核对工作量。

## 备选方案与为什么不选

- **不设"当前期/下游接入后"两阶段区分，一律要求弃用期**：当前仓库唯一持有数据的是自测用途的
  `data/_sample`，不存在任何下游正式游戏内容会被破坏，强制要求弃用期只会拖慢框架自身仍在快速
  迭代阶段的设计收敛速度，对当前实际风险不成比例。故不选，改为按"是否已有下游正式内容接入"分级。
- **只要求 CHANGELOG 标注，不强制要求 ADR 与逐字段迁移说明**：现行先例
  （`equip_visual_mode_field_group`）已经证明"只有 CHANGELOG 标注"在事后追溯时不够——CHANGELOG
  条目通常只有一两句话，读者需要另外去翻实现代码才能搞清楚具体哪些取值受影响、该怎么改；本政策
  要求的 ADR + 逐字段迁移说明是为了让破坏性变更的决策理由与具体迁移步骤都有专门、完整的记录位置，
  不依赖事后翻代码反推。故不选，仍要求材料齐备。
