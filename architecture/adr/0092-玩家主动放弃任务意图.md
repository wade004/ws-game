# ADR-0092 玩家主动放弃任务意图

状态：已拍板 2026-09-26

## 背景

消费方反馈第三十八批（`<game>` 接入方，基于 v1.74.0 冻结发布提交核实，阻塞）：`UiIntents` 只有
`AcceptQuest`/`TurnInQuest` 两个任务相关意图，没有任何入口能表达"玩家主动放弃一条已接取的任务"
——这是任务系统的常见交互（WoW 等参照系里"放弃任务"是任务日志面板的标配按钮），当前只能绕开框架
自行实现一套平行状态管理才能落地。

消费方已排除 `IQuestHost.Fail` 作为替代方案：`Fail` 的既有语义是"规则判定的失败结局"（escort 类
目标失败、事件类目标超时等策略层面的失败判定，需要 `AllowFail` 策略开关放行），会在任务日志里留下
一条永久的 `Failed` 记录（见"决策 3"对该记录实际副作用的核实）；玩家主动放弃与"规则判定失败"是两个
不同的语义来源，用 `Fail` 冒充"玩家放弃"会让任务日志把两类完全不同性质的事情混在同一个终态里
呈现给玩家，且 `Failed` 状态一旦进入没有回到"可再次接取"的路径（见决策 3），与"放弃后应当能够重新
接取"的预期直接冲突。

## 决策

1. **新增契约成员 `IQuestHost.Abandon(unitId, questId)`，返回 `bool`**（与 `Accept`/`Fail` 同一
   结果形状惯例）。作为默认接口成员加入既有公开接口（ABI 只加法约束下，给已存在的公开接口
   新增必须实现的抽象成员会让全部既有实现方编译失败，只能新增带默认体的成员）：默认体恒抛
   `NotSupportedException`——与既有查询类默认成员（如 `GetQuestTitleKey` 默认返回 `null`）刻意不同：
   放弃是一次会改变运行期状态、会发事件的写操作，静默降级为"什么都不做但返回 false"会让调用方
   （UI）误以为放弃已经生效，因此不适用查询类默认成员的静默降级惯例，未升级的宿主实现应当让调用方
   明确得知这个能力不可用。宿主的生产实现提供真正落地。

2. **语义**：只允许对当前状态为"已接取、未交付"（含目标已全部达标但尚未交付，WoW 同类交互里可以
   放弃一条待交付任务）的任务放弃。放弃成功后，该任务的运行期进度记录整体移除——效果等价于"这个
   单位从未接取过这条任务"：状态查询落回按前置条件实时求值的可用/不可用两态；任务日志查询不再
   包含它；目标计数归零；不写入任何"失败"记录。成功发布新事件 `quest.abandoned`（字段对齐
   `quest.failed`/`quest.turned_in` 既有惯例：`unitId` + `questId`，不带原因字段——放弃不需要
   "为什么"）。任务从未接取过、已经交付完成、已经处于失败终态、或任务本身未登记（含从未存在、或
   已被内容重新加载删除）——均返回失败结果，不抛异常、不发事件：这是一个供 UI 一键调用的玩家意图，
   调用方不需要先查询状态再决定是否可以调用。

3. **`Fail` 与 `Abandon` 的语义差异（核实 `Fail` 的实际副作用，非猜测）**：`Fail` 把状态置为
   `Failed` 并发 `quest.failed`，这条记录会被任务日志查询长期返回、随存档持久化；核实运行期状态机
   代码确认 `Failed` 是一个真正的终态——状态查询命中 `Failed` 时恒定返回 `Failed` 本身，不像"已交付
   的可重复任务"那样存在"下一日/下一次立即回落到可用"的分支，也就是说框架代码本身不提供任何从
   `Failed` 回到"可再次接取"的路径（是否允许重新挑战完全取决于游戏层是否自行提供额外机制，框架
   没有内建）。`Abandon` 则完全不产生这类终态记录：整条记录被移除，任务当次即可通过前置条件重新
   判定是否可再次接取，与游戏层是否额外处理无关。两者面向的场景不同：`Fail` 是规则对任务结局的
   裁决（策略开关控制是否允许发生），`Abandon` 是玩家自己的意愿表达（框架不设开关限制，只要处于
   可放弃的状态就允许）。

4. **表现层落地**：`UiIntents` 新增 `AbandonQuest(questId)`/`AbandonQuest(panelId, questId)`
   两个重载，形状与错误处理完全比照既有 `TurnInQuest` 一对重载（带 `panelId` 的重载先发布
   `ui.action_invoked { panelId, actionName: "abandon_quest" }` 再转发）。任务日志视图模型对
   `quest.abandoned` 的刷新方式与 `quest.failed` 一致——两者都是"该任务从日志里消失/状态整体变化"
   一类事件，视图模型早已对 `quest.failed` 做整体重建订阅，直接补一条同类订阅即可，不需要新的刷新
   逻辑分支。

5. **存档**：不新增任何字段。运行期进度整体移除后，"未接取"这一状态天然不出现在存档快照里（存档
   段本就只序列化"当前有记录"的任务），读档恢复的行为与"这个任务从未在这局游戏里被接取过"完全
   一致，不需要区分"从未接取"与"接取后又放弃"两种历史。

6. **不做**：不新增诸如"该任务是否允许放弃"一类的数据字段——本次没有出现这类需求，任务定义本身
   也没有等价于"能否放弃"的现成策略位；确有需要（例如剧情关键任务不允许中途放弃）再另开决策，不
   在本次预先铺一个没有消费方的可选项。不改动 `Fail` 的任何既有行为与签名。

## 后果

### 正面

- 任务日志第一次拥有"玩家主动放弃"这一原生能力，不需要消费方绕开框架自建平行状态管理。
- 与 `Fail` 保持清晰的语义边界：一个是规则判定的结局（可能永久、需要策略开关放行），一个是玩家
  意愿的即时生效（无开关限制、必然可逆回到"未接取"）——不会因为复用同一个方法而让任务日志把两类
  性质不同的终态混淆展示。
- 全部改动走加法：新增契约成员（默认接口成员）、新增事件、新增表现层意图方法重载，既有实现方与
  调用方不需要改一行代码即可继续编译、运行。

### 负面（已知限制）

- **会连带丢失可重复任务的历史交付记录**：运行期进度记录里同时保存着"历史累计交付次数"与"最近一次
  交付发生的时间"（供可重复任务的"当日是否已交付过"等判定使用）。放弃动作把整条记录移除，若该
  任务是可重复任务且此前已经通过正常流程交付过若干次，玩家在某一轮重新接取后又中途放弃，会连带
  丢失这些历史交付信息——依赖"该任务是否曾经完成过"这一查询的下游（例如把它设为另一条任务的前置
  条件）会因此从"曾经完成过"变回"从未完成"。这是"放弃即完全等价于从未接取过"这一设计决策的直接
  推论，本次不单独处理，见下"备选方案"为何不选。

## 备选方案与为什么不选

- **复用 `Fail` 表达玩家主动放弃**：能省一个契约成员，但 `Fail` 是策略开关控制的规则判定结局、
  没有回到"可再次接取"的框架内建路径，与"放弃后应当能立即重新接取"这一核心预期直接冲突；把两种
  不同性质的终态混进同一个方法与同一个事件，会让任务日志的历史记录失去"这条任务到底是被判定失败
  了，还是玩家自己不想做了"这一区分，对内容作者与玩家都是有意义的信息，不应该被抹平。故不选。
- **放弃后保留一条"已放弃"的历史记录（新增第七个状态），而不是整条移除**：能保留"这个任务曾经被
  放弃过"这一历史事实，但需要给状态机新增一个新的终态分支、状态查询/存档/任务日志三处都要为这个
  新分支各自补一套处理，且"是否应该像 `Failed` 一样长期占据任务日志的一条展示位"这一呈现设计没有
  消费方需求支撑；本次反馈的诉求就是"玩家能一键放弃并重新接取"，选择"整体移除、等价于从未接取"是
  能满足该诉求的最小改动，多出来的历史记录能力留待真有需求时再评估。故不选，已知限制见上。
- **新增数据字段控制某些任务不允许放弃**：本次反馈的任务定义都不需要这个限制，预先加一个没有
  消费方的可选项只会增加内容作者需要理解的表面积；真有"剧情关键任务不允许放弃"这类诉求时再开
  独立决策裁决具体口径（例如复用现有某个策略位，还是新增专门字段）。故不选。
