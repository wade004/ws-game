# ADR-0054 资产/数据根目录与目录内固定文件名纳入公开契约

状态：已拍板 2026-09-21

## 背景

消费方反馈（内容编辑器项目，第 76、77 条）：[ADR-0053](0053-地图分层图路径约定纳入公开契约.md) 刚把"地图分层图相对路径"这一处遗留缺口收口进公开契约，同一份反馈里还指出同一病灶的另外两处，均在 ADR-0053 决策收口之外：

1. **根目录本身的推导规则没有公开契约**：`资源引用标识 → 资产相对路径` 这条约定（ADR-0025/0037/0038/0053 已逐步收口）描述的是"资产根目录之下"的相对路径，但"资产根目录/数据根目录本身在哪"——省略 `--assets-root`/`--data-root` 时默认落在仓库根下的哪个固定段名、传相对路径按什么基准解析、传绝对路径是否原样使用——这条规则只写在内容导入工具通用模块一个内部函数与各子命令的文档字符串里，框架契约面完全没有对应的公开方法。ADR-0053 决策 2 的答复文档里也提到"调用方自行拼接资产根目录与数据集段前缀"这一步，同样从未纳入公开契约。消费方任何要"不显式传根目录参数也能算出同一默认路径"的功能（资产根探测、命令行组装预览）都只能照抄这两个默认段名字面量。

2. **资源目录内的固定产物文件名，以及其中一类文件的内部结构，同样没有公开契约**：`vfx`/`sprite_anim`/`sprite_set` 三类目录型资源引用（ADR-0037/0038 已收口的 `VfxResourceDir`/`SpriteAnimDir`/`SpriteSetDirectory` 三个方法）解析出的是"目录"这一层，目录下固定产出的文件名（图集 `atlas.png`，以及 `vfx`/`sprite_anim` 两类额外产出的序列帧数据 `frames.json`）此前只写在内容导入工具模块文档字符串与方法 XML 注释的说明性文字里，从未提升为可编译期引用的方法。其中 `frames.json` 的**内部结构**（`frame_w`/`frame_h`/`fps`/`frame_duration`/`loop`/`frames:[{index,x,y,w,h,duration}]`）缺口更深一层——此前唯一的解码实现是引擎适配层内部一个私有方法，非该引擎的消费方（如随游戏走的内容编辑器）要显示"帧数/帧尺寸/首帧裁剪区"这类信息，只能自行按字段名解析 JSON，属于自行实现框架格式。

这两处与 ADR-0025/0053 背景一节指出的根因完全相同：约定散落在说明性文字或私有实现里而不是可调用的契约面，规则一旦调整，消费方从公开契约的变更信号（新增/废弃方法、编译期报错）里得不到任何提示。核实现行实现后确认：

- 根目录推导规则（内容导入工具通用模块的一个函数）：省略时默认 `<仓库根>/assets`（或 `data`）；传相对路径按仓库根解析；传绝对路径原样使用。六个内容导入子命令一致调用这一条规则，是内容导入工具链内部已经统一的单一实现，只是没有对应的框架契约面方法，也没有在内容导入工具链一侧独立收口为可单独测试的公开函数（此前是通用模块的一个内部实现细节，嵌在参数解析流程里）。
- 目录内固定文件名：`vfx`/`sprite_anim` 两类共用同一套打包实现，产出 `atlas.png` + `frames.json` 两个文件；`sprite_set` 类共用同一套打包实现，但产出的是 `atlas.png` + `atlas.json`（按方向档位/层名分帧的索引文件，结构与 `frames.json` 不同，且只被内容工具自身的存在性校验消费，运行时精灵渲染走同目录下按方向档位/层名展开的独立扁平文件，不经 `atlas.png`/`atlas.json`）——因此本次只补 `sprite_set` 的 `atlas.png` 文件名一项，不臆造对应的 `frames.json`/结构化解析契约。
- `frames.json` 结构：`vfx`/`sprite_anim` 两类在运行时经同一个资源种类、同一段解码逻辑消费，字段与缺省值规则（`loop` 缺省 `false`、`fps` 缺省 `12`、顶层 `frame_duration` 缺省时按 `fps` 推算、单帧 `duration` 缺省时退回顶层值）完全相同。

## 决策

1. **新增资产/数据根目录推导的公开方法，与资源引用路径推导契约面并列、不并入同一类型**：新增 `ResolveAssetsRoot`/`ResolveDataRoot`（省略/相对/绝对三种取值的推导规则）与 `DatasetAssetsDirectory`/`DatasetDataDirectory`（根目录 + 数据集名 → 数据集目录）共四个方法。这组方法与 ADR-0025/0037/0038/0053 已收口的资源引用路径方法接受的输入形状不同——本组方法接受"仓库根路径 + 数据集名/根目录覆盖值"，不接受资源引用标识，回答的是"资产根/数据根目录本身在哪"；既有方法接受资源引用标识，回答的是"给定一个资源引用标识，它在资产根目录下的哪个相对路径"。两者是消费方定位到最终磁盘文件过程中依次经过的两个不同维度，形状不同、不共享方法签名，因此单独归为一组，不并入既有类型。

2. **新增 vfx/sprite_anim/sprite_set 三类目录型资源的固定文件名方法，并入既有资源引用路径推导契约面**：新增 `VfxAtlasFile`/`VfxFramesFile`/`SpriteAnimAtlasFile`/`SpriteAnimFramesFile`/`SpriteSetAtlasFile` 五个方法，与既有 `VfxResourceDir`/`SpriteAnimDir`/`SpriteSetDirectory`（同样接受资源引用标识、返回资产根相对路径）同一形态、同一契约面，只是从"目录"细化到"目录内固定文件"这一层——与 ADR-0053 决策 1 新增地图分层文件方法（`MapGroundFile` 等）时"目录 + 固定文件名各一个专属方法"是同一惯例。**不新增 `sprite_set` 类的 `frames.json`/`atlas.json` 对应方法**：`sprite_set` 目录内与 `atlas.png` 配套的索引文件是 `atlas.json`（按方向档位/层名分帧，字段形状与 `frames.json` 完全不同），且目前只被内容工具自身消费、不在运行时资源加载路径上，本次反馈原文与现有代码都未要求为它新增契约，不借机扩大收口范围、不发明消费方没有提出的需求。

3. **`frames.json` 结构新增独立于具体运行环境的只读解析契约，原有私有实现改为复用它**：新增结构化只读类型（含解析入口），字段与缺省值规则与此前引擎适配层内部私有实现逐字节一致（结构体不解析时机与运行环境相关的信息——例如单帧裁剪宽高缺省时的兜底值依赖已解码图集的实际尺寸，属于运行环境相关的收尾步骤，留给调用方在拿到图像尺寸后自行处理，不在本契约职责范围内）。原来内嵌在引擎适配层里的解析逻辑，改为调用这一契约取得结构化数据后只做本地环境特有的收尾（按裁剪矩形切图），不再自行解析 JSON、不留两份解析实现。

4. **内容导入工具链同步提供独立实现的等价函数，通用模块原有实现改为调用它，不再自行维护一份拷贝**：与 ADR-0053 决策 3 同一手法——两种运行环境之间不共享同一份源码，只能各自实现、互相对照；通用模块原有的根目录推导实现改为对两个已知取值委托给新增的独立函数，不引入新的行为分支。

5. **全仓排查同一病灶的其它重复实现，发现即一并收口**：核实确认内容导入工具链之外，存在第二处独立维护同一条根目录推导规则、但行为有细微差异的实现（相对路径覆盖值按"当前工作目录"而非"仓库根"解析）——已改为调用新增的共享函数收敛为统一行为，行为差异属于本次一并修正的既有分歧，不是意外改动（见对应改动点的判断记录）。除此之外全仓未发现同一条根目录推导规则、或本 ADR 收口的固定文件名规则的其它重复实现。

6. **规则本身不变，只是收口来源**：新方法的输出与内容导入工具改动前的输出逐字节一致（改动前后对照测试覆盖，见"验收标准"），不需要重新生成/迁移任何已有资产或数据行。

7. **变更约定须走 ADR**：往后如需调整根目录默认段名、数据集目录拼接规则、或本次新增的固定文件名/`frames.json` 结构本身，须新增 ADR 说明变更理由与迁移影响——与 ADR-0025 决策 4、ADR-0053 决策 5 同一约束，理由相同。

8. **与 ADR-0053 的关系**：本 ADR 是 ADR-0053"资源引用路径约定必须由公开契约充当权威出处"这一原则在另外两个维度上的延伸，不是对 ADR-0053 任何决策的修改——ADR-0053 收口的是"资源引用标识 → 资产根相对路径"，本 ADR 收口的是该相对路径两端的另外两截："资产根目录本身在哪"（决策 1）与"资产根相对路径这一层目录之下，固定产出的文件叫什么、其中一个文件里面装的是什么结构"（决策 2、3）。三者合起来，消费方从"游戏仓库根 + 数据集名 + 资源引用标识"到磁盘上一份可读的文件内容，每一步都有对应的公开契约方法，不再有任何一段依赖照抄说明性文字或私有实现。

## 后果

### 正面

- 消费方从"游戏仓库根 + 数据集名 + 资源引用标识"到磁盘文件的全过程第一次拥有端到端的公开契约，不再需要在任何一段照抄工具自身的说明性文字或私有实现反推格式。
- `frames.json` 结构第一次有了不依赖特定运行环境的读取入口，非该运行环境的消费方（如内容编辑器）可以直接复用同一份解析逻辑，不需要自行实现一份格式相同、可能与权威实现漂移的拷贝。
- 顺带发现并收敛了一处此前独立维护、行为有细微差异的根目录推导实现，减少了潜在的行为分歧来源。

### 负面

- 公开这组方法后，往后调整根目录推导规则、固定文件名、`frames.json` 结构均成为契约变更，需要按决策 7 走 ADR，多了一道流程成本——与 ADR-0053 决策 5 的负面后果同理。
- 收敛第二处根目录推导实现的行为差异（相对路径覆盖值的解析基准从"当前工作目录"改为"仓库根"）对该实现现有的调用方式是一次可观察的行为变化，虽然核实后判定属于修正既有分歧、且该入口是内部工具脚本，仍在此明确记录，供往后排查异常时参考。

## 备选方案与为什么不选

- **把根目录推导方法并入既有资源引用路径推导契约面同一类型**：会让该类型同时承载两种不同输入形状的方法（资源引用标识 vs. 仓库根+数据集名），增加消费方理解契约面时的认知负担；本 ADR 决策 1 选择单独归组，与 ADR-0053 决策 3 备选方案一节"不引入两套契约表达习惯"的理由一致，只是这次的分界线是输入形状而不是方法命名风格。
- **也为 `sprite_set` 类新增一个仿 `frames.json` 的结构化解析契约，把 `atlas.json` 一并收口**：`atlas.json` 的字段形状（按方向档位/层名分帧的字典）与 `frames.json`（按序列帧顺序排列、含播放时序字段）不同，且消费方反馈原文与现有代码均未提出这一需求；强行收口属于代为设计消费方没有提出的功能，不是"如实收口现有约定"，故不做。
- **`frames.json` 结构解析契约里也把单帧裁剪宽高缺省时的兜底值（依赖已解码图集尺寸）一并解析出来**：这一步依赖运行环境完成图像解码后才能拿到的信息，不是纯 JSON 解析阶段能确定的；如果契约内部替调用方猜测一个默认尺寸，等于代为决定了一个运行环境相关的行为，且与原实现"用已解码纹理整宽/整高兜底"的语义脱钩，故本 ADR 只解析 JSON 里显式写出的值，缺省时明确留空，由调用方按自己能拿到的信息决定。
