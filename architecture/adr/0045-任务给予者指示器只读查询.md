# ADR-0045 任务给予者指示器只读查询：框架只给状态，呈现归游戏

状态：已拍板 2026-09-20

## 背景

消费方反馈第 4 条（2026-09-20，见
`architecture/落地计划/消费方反馈-2026-09-20-任务指示器只读查询.md`）：消费方需要在 NPC 头顶（或
任意等价挂载点）呈现"这个 NPC 身上是否有可接/进行中/可交付的任务"这一常见 RPG 交互提示，但框架
未规划任何对应的聚合查询能力——独立核实结论：全仓库对 `GiverStatus`/`QuestBanner`/`questPOI`/
`quest_available`/`available_quest`/`GetGiverStatus` 等关键词做大小写不敏感搜索零命中，
`IQuestHost` 内确认无任何"某个给予者身上是否有可接任务"的聚合方法。

这是一处纯粹的**能力空白**，不是数据缺口：既有任务状态机（`IQuestHost.GetState`，见
`core/gameplay/quest` README）已经能完整回答"给定单位、给定任务，当前处于哪一态"，只是从未有人把
"给予者身上可能同时关联多条任务，聚合成一个用于呈现提示的单一状态"这层逻辑单独抽出来做成公开
查询。

## 决策

1. **新增一个只读聚合查询能力**：给定"任务给予者关联的任务 id 集合"与"玩家任务状态来源"，返回一个
   任务给予者指示器状态枚举，覆盖四态——**无可交互任务／有可接任务／有进行中但未完成的任务／有可
   交付的已完成任务**。完全基于既有状态查询逐条求值聚合，不引入任何新的持久化状态，不改动内容
   schema。

2. **给予者身份用现有单位/NPC 身份表示，不新造 id 体系**：框架的任务定义 schema 从未登记"这个任务
   由哪个 NPC 给出"（对话菜单的"接取任务"/"交付任务"动作只携带任务引用，NPC → 任务集合的映射完全
   是内容/游戏侧的编排产物），框架也没有可读的"给予者拥有哪些任务"登记表可供反查。因此本查询把
   "给予者关联哪些任务"作为调用方输入，不再单独设计一个"给予者 id"参数——调用方在拿到某个 NPC 的
   单位身份时，自行决定这个 NPC 关联哪些任务并传入本查询，框架只负责这些任务在当前玩家状态下的
   聚合与优先级裁决。这正是"用现有单位身份表示给予者"的直接落地：给予者是谁这件事，由"哪个单位在
   问"（调用方上下文）+"它关联哪些任务"（调用方给出的集合）共同表达，不需要框架另建一套身份系统。

3. **状态优先级固定、确定性、写死为：可交付 &gt; 可接 &gt; 进行中 &gt; 无**。同一给予者同时关联的
   多条任务可能同时命中多种状态时，只返回优先级最高的一个，理由：
   - **可交付优先于可接**：可交付意味着"回去交任务"是当前最紧迫的下一步（通常伴随立即的奖励结算），
     其呈现优先级高于"还有新任务可接"这一相对不紧迫的提示。
   - **可接优先于进行中**：进行中的任务通常已经有其它追踪手段（任务日志、既有的"当前激活目标位置
     查询"能力），指示器在"进行中"这一态上的边际提醒价值低于"有新的交互可做"（可接是一次性的、错过
     容易被遗忘的提示，进行中不会被遗忘，玩家可以随时在任务日志里查看）。
   - 优先级顺序本身不依赖具体呈现方式（图标形状/颜色由游戏侧决定），只是"给定多态时选哪一个作为
     查询结果"的确定性规则，任何两次相同输入的调用必须返回相同结果。

4. **明确边界：不覆盖"等级不足预览"等中间态，不为此新造判定语义**。任务前置条件是任意布尔表达式，
   可能混合任务链引用、玩家属性、世界状态等多个维度；框架现有的只读前置预演能力明确只解析"这个
   任务点名了哪些其它任务"这一层任务链结构，不对整条前置表达式做真正的布尔求值，因此无法在不引入
   一套新的表达式子集求值/参数反解语义的前提下，低成本区分"完全不可接"与"只差某个具体条件（如
   等级）"这类中间态。本次任务边界是"复用既有状态查询，不新增能力"，做这类中间态判定需要的是一套
   新的表达式语义分析能力，超出本次范围，本次不做。指示器的"无可交互任务"因此不区分"前置完全不
   满足"与"只差一点点"，两者对调用方而言都是"当前不可接"；调用方如需要更细粒度的预演，需自行在
   游戏侧对前置表达式做语义解读。

5. **框架只给状态判定，具体呈现一律归游戏侧**：本查询的返回值只是一个状态枚举，头顶图标的形状/
   颜色/动画/贴图切换等任何视觉表现细节，框架不内置、不假设、不提供默认实现——同框架一贯的"提供
   机制与查询、不替游戏做美术/呈现决策"取向（参见既有多处"游戏责任"类判断记录）。这不是本次臨時
   决定，而是本次能力设计的前提：如果框架尝试连带内置呈现规则，会立刻绑定到某一类具体游戏的美术
   风格假设，与"技术无关、游戏无关，面向后续所有游戏"的框架定位冲突。

## 后果

### 正面

- 消费方反馈第 4 条指出的能力空白得到填补，游戏侧不再需要自行重新实现"遍历给予者关联任务、查
  状态、按某种顺序裁决"这套逻辑（否则大概率每个游戏各写一份、裁决优先级不一致）。
- 新增能力完全基于既有状态查询，零新增持久化状态、零 schema 改动，实现成本与回归风险都很低。
- 呈现边界写清后，未来任何游戏在挂具体视觉表现时，不需要等框架先做视觉层的决策。

### 负面

- "无可交互任务"这一态不区分"完全不可接"与"只差一点点"，游戏侧若确实需要这类更细粒度的预告
  提示（如"等级不足，还差 2 级"），仍需自行解读前置表达式或等待后续专门立项，本次不解决。
- 给予者关联的任务集合完全由调用方提供，框架不做任何"这个集合是否正确/完整"的校验——如果游戏侧
  的给予者-任务映射本身编排有误（如遗漏了某条任务），指示器只会如实反映"给定集合"的聚合结果，
  不会主动发现遗漏，这属于内容编排正确性的范畴，不是本查询的职责。

## 备选方案与为什么不选

- **让框架直接反查"哪些任务的接取方式与这个 NPC 相关"，不要求调用方显式传入任务集合**：需要框架
  的任务定义或对话菜单登记"由哪个 NPC 给出"这一新字段，是一次 schema 变更（哪怕是新增可选字段），
  且不同游戏对"给予者-任务"关系的编排方式差异很大（有的游戏可能一个 NPC 关联的任务集合是动态
  计算出来的，不是静态登记）。相比之下，把这一层完全留给调用方、框架只负责聚合裁决，兼容面更广，
  也符合"不新增数据表、不改 schema"的任务边界。故不选。
- **把本查询做成 `IQuestHost` 的新成员方法**：`IQuestHost` 在测试与表现层各自有独立的假实现
  （直接实现该接口的类型），新增接口成员会破坏这些既有实现的 ABI 兼容（除非全部补齐新成员，
  但那些假实现分处不同模块，属于跨模块的强耦合改动，且下一次再新增类似查询又要重复一遍）。改为
  独立静态查询类，只依赖 `IQuestHost` 已有的只读方法，是纯新增类型，不触碰任何既有类型的成员
  列表，符合 ABI 只增不减的约束，也与框架内既有的同类"预演/聚合查询不进宿主接口"先例（任务前置
  链预演、对话剧情预演）保持一致。故选独立静态类，不选接口新成员。
- **一并实现"等级不足预览"等中间态判定**：需要新增一套表达式子集求值/参数反解语义（识别并单独
  求值前置表达式里"等级比较"这一类子表达式），是明显超出"复用既有状态查询"这一任务边界的新能力，
  且没有一个足够通用、不同游戏都适用的"中间态"定义（不同游戏的前置条件构成差异很大，等级只是其中
  一种）。故本次不做，留待有具体需求时单独评估。
- **让框架内置一套默认的头顶图标/颜色呈现规则**（哪怕只是"提供一个可选的默认实现，不用也可以"）：
  即便标注为"可选"，一旦框架给出具体视觉呈现，就会被后续游戏当作事实标准参照，实质上开始承担
  框架定位之外的美术决策职责，且任何具体呈现风格都无法适配"面向后续所有游戏"这一定位。故不提供
  任何默认呈现，只给状态枚举。

## 魔兽世界的对应做法

任务给予者头顶的感叹号/问号图标（含灰色感叹号表示"等级不足预览"）是魔兽世界任务系统的经典呈现
惯例，本决策提供的只读查询能力是这一呈现效果背后需要的状态判定逻辑的框架侧支持面；"灰色感叹号"
对应的"等级不足预览"中间态本决策明确不做（决策 4），游戏侧如需要还原这一具体呈现细节，需自行在
游戏层解读前置条件或等待后续专门能力。图标本身的美术形态、颜色、动画不属于框架职责（决策 5），
不对应魔兽世界客户端具体的图标资源与渲染实现。
