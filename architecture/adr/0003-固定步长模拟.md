# ADR-0003 固定步长模拟

状态：已拍板 2026-09-04

## 背景

若世界模拟直接跟随渲染帧率推进（每帧的 tick 时长随实际帧耗时浮动），同样的输入在不同帧率下会产生不同的模拟结果：这既破坏了"同种子同输入同结果"的可测试性目标，也让暂停、慢动作、回放等功能难以精确实现。需要把"模拟时间"与"渲染时间"解耦。

## 决策

核心模拟按固定步长（默认 60Hz，可配置）tick，每个 tick 内的输入、随机数消耗、结算顺序完全确定；渲染层在两个 tick 之间对表现状态做插值，不改变模拟结果本身：

- 暂停 = 停止推进 tick（不消耗模拟时间），但渲染仍可继续刷新静止画面。
- 慢动作 = 一个时间累积器的缩放系数调整，只影响"多久推进一次 tick"，不影响每个 tick 内部的计算逻辑，也不影响 UI 时钟等不应被慢动作影响的部分。

具体的主循环结构与 tick 顺序见 [../03_运行时骨架.md](../03_运行时骨架.md)。

## 后果

### 正面
- 同种子、同输入序列，无论渲染帧率如何波动，模拟结果完全一致（在同一平台与同一运行时二进制下逐位一致；跨平台只承诺逻辑等价、不承诺逐位一致，见文末"范围澄清"一节），直接支撑架构目标"可测试可确定"与 [../10_存档与持久化.md](../10_存档与持久化.md) 的确定性回放能力。
- 暂停、慢动作等单机常见需求可以用统一机制实现，不需要为每个功能单独处理时间语义。
- 性能基线测试（见 [../11_工程规范与测试.md](../11_工程规范与测试.md)）可以针对"每 tick 耗时"这一稳定指标衡量，不受渲染帧率抖动干扰。

### 负面
- 渲染插值增加了表现层的实现复杂度（需要在两个逻辑状态之间平滑过渡，而不是直接展示最新逻辑状态）。
- 极端情况下（长时间卡顿）需要"追赶 tick"策略（一帧内补跑多个 tick），若不加限制可能导致单帧计算量暴涨，需要设置追赶上限（具体策略见 [../03_运行时骨架.md](../03_运行时骨架.md)）。

## 备选方案与为什么不选

- **可变步长模拟（每帧 tick 一次，步长等于帧耗时）**：实现最简单，多数入门项目默认如此，但直接放弃了确定性——同样操作在不同机器/不同帧率下结果不同，无法支撑回放与确定性回归测试，与架构目标 4 冲突，不采纳。
- **固定步长但不做渲染插值（渲染直接贴合最新 tick 结果）**：实现更简单，但在低 tick 率（如为了性能降到较低频率）下画面会有明显的卡顿感，牺牲了表现流畅度；插值成本可控且是行业常见做法，因此仍选择插值方案。

## 魔兽世界的对应做法

魔兽世界服务端本身按固定的心跳间隔更新世界状态（服务端 tick），客户端渲染独立于服务端心跳做插值与预测，这与本 ADR 的"固定步长模拟 + 渲染插值"思路一致，区别在于魔兽世界的固定步长是为了服务端多人权威同步，本架构的固定步长是为了单机场景下的确定性、可测试性与暂停/慢动作能力。

## 范围澄清（2026-09-06）

本澄清不改变本 ADR 的决策，只界定"同种子同输入产生同结果"这一承诺的适用范围，不影响本 ADR 状态：

模拟路径中存在若干依赖平台数学库实现的浮点超越函数运算（例如三角函数、开方），这类运算在不同平台/处理器架构上可能产出末位不同的结果。因此本 ADR"模拟结果完全一致"的承诺实际限定为：**同一平台、同一运行时二进制**下逐位一致；跨平台或跨运行时二进制运行同一份种子与输入序列，只承诺**逻辑等价**（同样的判定分支、同样的事件序列），不承诺数值逐位一致。

若未来需要跨平台逐位一致（例如支持"跨平台回放校验"或"跨平台联机对拍"一类需求），需要另立 ADR 引入定点数学（把模拟路径的浮点超越函数运算替换为定点数运算或查表实现），本 ADR 与本次澄清均不预设该决策。
