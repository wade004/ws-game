# ADR-0007 窄契约加事件总线

状态：已拍板 2026-09-04

## 背景

多个模块（数值、规则、载体、玩法、表现）需要互相协作，但如果允许模块之间随意直接引用彼此的内部实现，模块边界会迅速瓦解，导致"模块可拆走复用"这一架构目标无法实现，也会让单元测试必须拉起一大堆无关模块才能跑通。需要明确规定模块间交互只能经过两种受控通道。

## 决策

模块之间只经两种方式交互，不存在第三种私有旁路：

1. **窄契约（Narrow Contract）**：同步的问答式调用，接口只暴露调用方真正需要的最小方法集合（如 `SkillHost`、`EffectSink`、`CombatHost`、`AiHost`，具体签名见 [../06_规则层_属性技能战斗AI.md](../06_规则层_属性技能战斗AI.md)），不暴露被调用方的内部数据结构。
2. **事件总线（Event Bus）**：异步的广播式通知，事件词汇沿用魔兽世界 Combat Log 风格并统一登记（如 `combat.hit`、`aura.applied`），发布方不知道谁在订阅，订阅方只依赖事件 key 与携带的数据字段，不依赖发布方的内部实现。

模块内部（`core/`）的实现细节对外不可见，模块只通过 `contracts/` 目录暴露上述两类接口（见 [../11_工程规范与测试.md](../11_工程规范与测试.md) 模块范式）。

## 后果

### 正面
- 任一模块可以被替换实现（例如替换目标选择策略的具体算法）而不影响调用方，只要契约签名不变。
- 模块单测可以用桩实现契约接口，完全隔离被测模块与其依赖，测试速度快、覆盖精确。
- 事件总线让"谁需要知道某件事发生了"与"这件事是谁触发的"解耦，新增一个订阅方（例如表现层新增一种反馈规则）不需要改动事件发布方的代码。

### 负面
- 相比直接引用，窄契约与事件总线都增加了一层间接调用的心智成本与少量运行时开销（事件分发、接口调用）。
- 事件词汇与契约签名一旦被多处依赖，后续修改的影响面会更广，需要更谨慎地设计初始接口（部分场景可能因此归入新增原语审批范畴，见 ADR-0010）。

## 备选方案与为什么不选

- **模块间直接引用具体实现（无契约层）**：短期开发速度最快，是很多中小型项目的默认做法，但会让模块边界名存实亡，任何一个模块的内部重构都可能波及大量调用方，与"模块可拆走复用""可脱离引擎独立测试"两条架构目标直接冲突，不采纳。
- **只用事件总线、不设窄契约（一切交互都异步化）**：对于需要立即得到结果的查询场景（如"当前是否处于战斗中"）用纯异步事件表达会非常别扭，需要额外的状态缓存与时序处理，不如直接提供同步查询契约简洁可靠，因此保留两种通道并存。

## 魔兽世界的对应做法

魔兽世界服务端内部模块（法术系统、战斗系统、AI 系统等）之间既有直接的函数调用契约（如 SpellEffect 处理函数、Aura 处理器），也有广播式的事件/钩子机制（如脚本钩子 OnSpellCast、OnDamage 等），Combat Log 更是面向客户端的标准化事件流格式，本身就是"统一事件词汇"的现实范例。本 ADR 把这种"契约调用 + 事件广播"并存的模式确立为全架构统一的模块交互方式，并要求事件命名风格向 Combat Log 靠拢以获得更好的可读性与可扩展性。
