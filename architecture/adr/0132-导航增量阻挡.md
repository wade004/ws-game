# ADR-0132 导航契约的增量阻挡成员

状态：已拍板 2026-10-03（对 [ADR-0016](0016-引擎适配层契约阶段4联调补齐.md) 决策 7 所定导航阻挡登记方式的追加决定：只加成员，不改既有成员语义；手感落地 M4-L 引入）

## 背景

导航契约登记阻挡的方式只有整批替换：调用方每次都把全部阻挡矩形重新交一遍。静态地形没问题，但动态阻挡（可破坏障碍被打碎后让路、运行期出现的墙）每变一块就要重发全部矩形，开销随阻挡总数线性增长，调用方还得自己长期保存一份"当前全部矩形"。实验室的可破坏障碍已经遇到这个问题（早期只能用"被打死后整批替换去掉"的近似），障碍多了就不成立。

需要一条增量登记的路，同时不能破坏既有契约：导航契约有第三方实现，既有的"阻挡版本号"又是路径校验与重规划的触发条件。

## 决策

1. **导航契约追加三个默认接口成员**（只加不改，既有实现源码兼容、二进制兼容）：
   ```
   interface INavigation2D {
     addBlocking(mapId: Id, rect: Rect)                 // 追加一块动态阻挡
     removeBlocking(mapId: Id, rect: Rect): Bool        // 按矩形值移除登记顺序里第一份匹配项，返回是否真移除了
     getBlocking(mapId: Id): List<Rect>?                // 当前登记快照；null 表示实现不暴露（默认）
   }
   ```
   阻挡按多重集合处理：重复登记同一矩形各算一份，每次移除只移掉第一份。

2. **版本语义不变**：每次有效的增或删让该地图的阻挡版本号**恰好**递增一次（等价于一次整批替换）；移除不存在的矩形返回 false 且版本号不变。整批替换、清空、重建网格的语义一字不动。路径校验与重规划因此仍只看版本号变化。

3. **默认实现**：经 `getBlocking` 取当前集合，追加或移除之后整批替换。实现若连 `getBlocking` 也不暴露（返回 null），默认实现抛"不支持"，**不静默退化成"只剩这一块"**——那会悄悄丢掉其余阻挡。需要真增量的实现覆盖三个成员。

4. **随附实现与一致性**：测试桩与引擎适配层的导航实现覆盖为真增量（引擎适配层同时重置该地图的网格缓存）；适配器一致性场景新增一条，在引擎侧自动化测试里才运行。

5. **首个消费者**：实验室的可破坏障碍——出场时逐块追加，被打死后按值移除，阻挡版本号逐次递增，路径随之失效重规划。

## 后果

### 正面

- 动态阻挡的单次变更是常数级而不是随阻挡总数线性增长，调用方不必自己保存全量矩形。
- 全部是加法：既有实现与既有调用方不受影响；版本号语义不变，路径校验的触发条件不变。
- 不暴露快照的第三方实现得到明确的失败而不是静默丢阻挡。

### 负面

- 没有网格实现的第三方导航若既不暴露快照也不覆盖三个成员，在调用增量成员时会抛异常，接入方需要二选一补齐。
- 按矩形值匹配（而不是按句柄）意味着调用方要自己保证"移除的就是当初追加的那一块"；重复矩形下移除的是登记顺序里最早的那份。

## 备选方案与为什么不选

- **把整批替换改成增量语义**：破坏既有契约，所有既有调用方行为改变；否决。
- **追加带句柄的阻挡（返回句柄、按句柄移除）**：要新增句柄类型与生命周期规则，并与整批替换并存时定义句柄何时失效；否决，按矩形值匹配对当前用途足够，且不引入新类型。
- **默认实现在无快照时退化成"只剩这一块"**：静默丢掉其余阻挡，错误离配置处越远越难查；否决，显式抛出。
- **每次增删让版本号递增不止一次或不递增**：路径校验的触发条件会漂移；否决，恰好一次，与一次整批替换等价。

## 魔兽世界的对应做法

无直接对应：魔兽的导航网格由服务端预烘焙，动态阻挡由游戏对象的碰撞承担，不暴露"增量登记阻挡矩形"这类接口。
