# ADR-0075 停止特效反馈动作

状态：已拍板 2026-09-23

## 背景

消费方反馈第十九批第 2 条：`feedback.binding` 的固定动作集合只有"播放"一侧（`play_vfx`），没有对应
的"停止"动作——光环/持续状态一类需要"施加时起播、移除时停播"的循环特效（如持续吟唱光圈、灼烧
持续特效），只能靠特效自身的 `lifetime` 到期自然回收，表现层完全没有出口在光环提前被驱散/覆盖时
主动掐断正在播的特效，导致光环已经没了、绑在角色身上的特效还在继续播的观感错误。

## 决策

1. **`FeedbackActionKind` 固定枚举新增第七项 `StopVfx`**：`feedback.binding` 新增可声明的
   `stop_vfx` 动作，字段形状镜像 `play_vfx`——同样支持 `vfx_id`（显式指定）与 `from_display`
   （从触发事件所在的 `display.map` 行取值）二选一定位要停止的特效逻辑 id，同样带 `attach`
   （source/target）表达"停哪个实体身上的实例"。与 `play_vfx` 的唯一形状差异：`attach` 不接受
   `world`——`stop_vfx` 靠 `(特效逻辑 id, 附着实体)` 这一对键定位在播实例（见决策 3），world 没有
   实体可作为键的一部分，构造函数直接拒绝，不留一个必然找不到目标的取值。
2. **不改 `IFeedbackSink.PlayVfx` 签名、不让它返回句柄**：`feedback.binding` 是声明式数据，规则
   之间没有"上一条动作的返回值"这种概念可以承接一个句柄；即便 `PlayVfx` 改成返回句柄，框架侧仍然
   必须自己建一张 `(特效逻辑 id, 附着实体) -> 句柄` 的表才能在另一条独立规则的 `stop_vfx` 动作触发
   时查到该停哪个实例——两条路线最终都要落到这张表，不如干脆用这张表本身做查找依据，不给
   `PlayVfx` 强加一个数据层用不上的返回值。`IFeedbackSink` 改为新增一个 `StopVfx(vfxId, attach)`
   方法，带默认实现（接口自带一份空方法体、什么都不做的默认实现）——未显式实现该方法的
   既有 `IFeedbackSink` 实现方，`stop_vfx` 动作分派到默认实现即静默无操作，不需要跟着改一行代码
   即可继续编译、运行（ABI 只加法）。
3. **同一 `(特效逻辑 id, 附着实体)` 有多个在播实例时，停最近一个（覆盖式单句柄，不是列表）**：
   框架侧维护一张 `(vfx_id, entityId) -> 最近一次 Play 返回的句柄` 的表，每次同一键的 `PlayVfx`
   调用直接覆盖旧句柄（不追加），`StopVfx` 查到即停、查不到静默返回。选择"停最近一个"而不是
   "停全部"：光环/持续状态类特效（本决策的驱动场景）本质是"每个实体身上同一种光环特效同一时刻只有
   一份"，重复施加同一光环通常表现为"重新起播、覆盖旧实例"而不是"叠加出多份"；用覆盖式单句柄而不是
   增长的列表，内存占用有界（键的数量上限是"当前活跃实体数 × 特效逻辑 id 数"，不随重复播放次数
   增长），实现也更简单。
4. **查不到在播实例时静默返回，不打任何诊断**：`stop_vfx` 触发时目标特效已经自然到期回收、或从未
   播放过，是完全正常的时序（光环移除事件到达时，特效可能早已自己放完），不是数据或调用错误，不该
   产生警告噪音。

## 后果

### 正面

- 光环一类"持续到移除才停"的特效，现在有了数据驱动的正规出口在移除时刻主动停播，不再依赖
  `lifetime` 到期这一种终止路径，观感上不会再出现"光环没了、特效还在"的错位。
- `IFeedbackSink` 新方法走带默认实现的接口成员，ABI 只加法，既有实现方不需要跟着改动。
- "停最近一个"的判定规则内存占用有界，且与光环类特效"同一实体同一时刻只有一份"的真实使用场景
  完全对应，不需要为一个当前不存在的"同一光环允许多份叠加特效"场景预留列表结构。

### 负面

- 如果确有内容需要"同一光环在同一实体身上允许多份独立特效实例、drop 掉的是最旧的那份"这类更复杂
  的语义，当前"覆盖式单句柄"实现不支持——真出现这类真实需求时需另开 ADR 扩展为按需保留列表，当前
  没有这类真实驱动场景，不提前做。
- `stop_vfx` 依赖 `PlayVfx` 侧已经把 `(vfx_id, entityId)` 记入同一张表；如果消费方自定义了
  `IFeedbackSink` 实现且只覆盖了 `PlayVfx` 不覆盖 `StopVfx`（合法，DIM 默认允许这样），`stop_vfx`
  动作对这类实现方是无操作——这是默认实现刻意的行为（决策 2），不是遗漏。

## 备选方案与为什么不选

- **让 `PlayVfx` 返回一个不透明句柄，`feedback.binding` 或调用方保存后传给 `stop_vfx`**：
  `feedback.binding` 是纯声明式数据（一条条独立的"事件 → 动作"规则），规则本身没有变量/中间结果
  的概念，没有地方存这个返回的句柄——真要接住它，框架侧还是得自己建一张查找表，且现在多了一层
  "谁负责保存这个句柄"的额外契约（内存生命周期归谁管、规则重载后旧句柄是否失效）。不如让框架直接
  按 `(vfx_id, 附着实体)` 这个对声明式规则天然可表达的键自建查找表，`PlayVfx` 保持无返回值，接口
  形状更简单，两条独立的声明式规则（一条 play 一条 stop）各自只需要知道"特效逻辑 id + 附着到哪个
  实体"，不需要在两条规则之间传递任何运行期产物。故不选。
- **`stop_vfx` 停全部匹配 `(vfx_id, entityId)` 的在播实例（维护列表而不是单句柄）**：更通用，但
  当前没有真实场景需要"同一光环在同一实体身上允许多份叠加实例"，维护一个会持续增长（直至逐个
  natural-timeout 或被显式停止）的列表比维护一个覆盖式单句柄多一层内存增长与遍历开销，且"停全部"
  语义在"光环被重新施加、旧实例其实应该被新实例取代"这一真实场景下反而是错的（会把刚起播的新实例
  也一并停掉）。故不选"停全部"，选"覆盖式单句柄、停最近一个"。
- **查不到在播实例时记一条 Warning 级诊断**：会把"光环特效已自然放完、恰好这时移除事件才到达"这一
  完全正常的时序噪音当成异常上报，消费方控制台会被大量无意义警告淹没。故不选，选择静默返回。

## 与游戏客户端的对应参考

对应主流游戏客户端里"状态/光环特效随状态终止而主动摘除"的常见处理——持续类视觉效果（持续吟唱
光圈、灼烧粒子、护盾光罩等）普遍在状态施加时挂载、状态被驱散/覆盖/正常结束时主动摘除，而不是仅靠
特效自身预设的存活时长到期，这是表现层与状态系统联动的常规做法，本决策把这条联动路径补进声明式
反馈规则里。
