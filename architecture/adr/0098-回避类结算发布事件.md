# ADR-0098 回避类结算发布事件

状态：已拍板 2026-09-26

## 背景

消费方第四十三批反馈2（`<game>` 接入方，基于 v1.77.0 冻结发布提交核实，阻塞）：结算管线对
未命中（miss）/闪避（dodge）/招架（parry）三个判定分支只调用既有的仇恨/进战簿记与
`CombatOptions.ResolveTrace`（只读诊断出口，不是事件），完全不经过事件总线；免疫吸收判定为
免疫时同样只记一句诊断日志（"不落地、不发事件"）。全仓核实：不存在任何 `combat.(miss|dodge|
parry|immune|avoid)` 一类事件，`combat.damage_dealt`/`combat.heal_done` 只在真正落地时发布。
消费方需要用事件驱动"未命中"飘字、"招架"专属音效等回避类战斗反馈，只能反过来用"这一拍没有收到
`combat.damage_dealt`"这种不可靠的沉默推断——这与"这一拍根本没有发生任何结算"完全无法区分。

## 决策

1. **新增事件 `combat.attack_avoided`**，强类型 `CombatAttackAvoidedEvent`（放
   `core/rules/common/contracts/Events.cs`，与 `CombatDamageDealtEvent`/`CombatHealDoneEvent`
   同文件同风格——三者同属"结算管线落地/回避各自结局"的同一组事件，`CombatDamageDealtEvent`
   实际登记位置本就是本文件而非单独的 combat 契约目录，本次不新开先例）。字段：`SourceId`、
   `TargetId`、`School`、`HitResult`（只会是 `Miss`/`Dodge`/`Parry`/`Immune` 之一）、可空
   `SkillId`、可空 `AttackInstanceId`、`TriggerChainDepth`。`TryGetField` 暴露
   `sourceId`/`targetId`/`school`/`hitResult`/`skillId` 五个字段（`attackInstanceId` 不经 Expr
   暴露，同 `CombatDamageDealtEvent` 既有惯例）。
2. **`HitResult` 新增 `Immune` 成员**（追加到枚举末尾，ABI 只加法，不改变既有成员数值；全仓核实
   既有代码只按具名成员比较，不受影响）——免疫吸收（步骤 7）与命中表六分支（步骤 1）是两个不同
   管线阶段各自的结局，此前只有 `ResolveResult.Immune` 这一布尔字段能表达，本次让事件的
   `HitResult` 字段也能报告同一语义。
3. **发布点两处，`Resolver.Resolve` 内**：① `Miss`/`Dodge`/`Parry` 既有终止分支（步骤 1
   判定出结果后提前 return），与既有 `NotifyCombatEvent` 调用同一位置；治疗分支不会进入这三个
   分支（`DetermineHit` 对 `isHeal` 恒不掷回避判定）。② 步骤 7 免疫判定为 `true` 的既有分支，
   伤害/治疗两个语境均可能免疫、均发布，仍然不落地 `IPowerHost`、不发
   `combat.damage_dealt`/`combat.heal_done`（两者与本事件在同一次结算里互斥，不会同时出现）。
   已死亡目标的既有早退路径（只记诊断、不触碰任何数值/事件）保持不变，不追加发布。
4. **不改动 `combat.damage_dealt`/`combat.heal_done`**：不以 `amount=0` 冒充回避——两者现有
   订阅方（仇恨/进战计数、任务目标计数、`feedback.binding` 命中特效）的既有假设是"收到即发生了
   一次真实数值结算"，混用会制造需要额外分支澄清的歧义。四类回避结局合用同一个新事件类型、靠
   `HitResult` 字段区分，与 `combat.damage_dealt` 自身"命中/偏斜/格挡/暴击共用一个事件类型"同一
   惯例，不新开先例。
5. **实现 `ITriggerChainEvent`**（`TriggerChainDepth` 原样戳入产生本次结算的
   `EffectContext.TriggerChainDepth`，不经 Expr 暴露）：回避类结局同样可能被声明为某个
   `skill.proc_def.trigger_event`（如"每次被闪避时触发一个被动技能"）。若不实现该接口，
   `EventCorrelation.GetTriggerChainDepth` 会对本事件恒取默认值 0（视为根事件），重现 N04 收边
   补齐（外部审计 68c9bed）此前在 `AuraRemovedEvent` 上修复过的同一类"事件驱动 Proc 自循环预算
   旁路"缺口——新增事件类型时一并接好，不留给下一次审计重新发现。此项超出消费方反馈的字面诉求，
   属本次顺带处理的一致性修正，ABI 只加法（新增属性 + 接口实现），不影响任何既有调用方。
6. **表现层不改动**：`presentation/feedback_binder`（`FeedbackBinder`）按 `feedback.binding`
   声明的事件 key 泛化订阅，不是硬编码白名单；`FeedbackRuleValidator` 按 `EventKeys.All` 校验
   `event` 字段（软引用 `found.event_catalog`），新事件登记后自动可用，不需要代码改动。不预置
   任何默认文案/绑定——具体反馈由 `<game>` 自己的 `feedback.binding` 配置。

## 后果

### 正面

- 消费方首次能用事件驱动"未命中/闪避/招架/免疫"四类回避反馈，不需要靠沉默推断。
- 与 `combat.damage_dealt`/`combat.heal_done` 严格解耦：既有订阅方零影响，不需要改一行代码。
- 顺带补齐 `ITriggerChainEvent`，避免新事件类型重蹈已知的 Proc 自循环预算旁路缺口。

### 负面

- **多一次事件总线 `Enqueue`**：三个终止分支与免疫分支各多一次 `Enqueue` 调用，战斗热路径上的
  开销可忽略（与既有 `combat.damage_dealt`/`combat.heal_done` 同量级），不构成实际负担。
- `HitResult` 新增 `Immune` 成员后，该枚举不再只对应命中表六分支——阅读代码时需要留意
  `Immune` 只会出现在事件的 `HitResult` 字段上，不会出现在 `HitTableConfig`/`ResolveResult.Hit`
  的既有语境里（`ResolveResult.Hit` 报告的仍是步骤 1 判定结果，不受本次改动影响）。

## 已知限制

- `TryGetField` 不暴露 `attackInstanceId`——需要按攻击实例关联回避事件的 Expr 条件过滤场景（如
  `feedback.binding` 按批次去重）本次不支持，需要时经强类型属性读取（`Presentation.FeedbackBinder`
  等宿主代码可以，纯 Expr 条件配置不行）。

## 备选方案与为什么不选

- **给 `CombatDamageDealtEvent` 补 `amount=0` 表示回避**：省一个事件类型，但会让既有订阅方需要
  额外分支区分"真实造成 0 点伤害"与"根本没有结算"，语义混淆，故不选（见决策 4）。
- **未命中/闪避/招架/免疫各开一个专用事件**：四者携带字段完全相同，差异只在结果标签，与
  `combat.damage_dealt` 自身按 `HitResult` 区分命中/偏斜/格挡/暴击的既有惯例不一致，徒增事件
  类型数量，故不选。
