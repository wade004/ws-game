# ADR-0064 任务宿主契约补标题与目标描述文本键查询

状态：已拍板 2026-09-22

## 背景

消费方反馈（游戏接入方第六批，基于冻结发布提交核实）：任务追踪 HUD 要显示"任务名 + 目标描述 +
进度 + 可交付状态"，但表现层拿不到前两项。内容数据侧字段早已存在（任务定义的标题文本键、单条
目标的描述文本键），任务宿主契约与对应视图模型均未转发：

- 任务宿主契约（`<game>` 层的只读查询接口，下称"任务宿主契约"）已有的状态查询/转移方法集里，
  没有任何一条能按任务 id 取到标题文本键，也没有任何一条能按任务 id + 目标下标取到该条目标的
  描述文本键——两个字段本身在任务定义的内存态表示里都已经存在，只是没有对外的查询出口。
- 表现层的任务日志视图模型只转发"该单位全部有记录任务的进度快照"与"当前全部激活目标三元组"，
  同样不带标题/描述文本键。
- 消费方因此只能让表现层自己反查内容数据表拼出任务名/目标描述，违反本框架"视图不得自己拼宿主
  数据"的既定铁律（09 表现层文档，只读查询铁律）——视图只应转发宿主已经算好的结果，不应该另开
  一条路径绕过宿主直接读内容数据。

这与此前多批消费方反馈（技能名称显示键、装备模板 id 查询等）是同一类缺口的延续：契约接口的
只读查询集合落后于内容数据实际已经登记的字段，本次收口的是任务标题/目标描述这两个文本键。

## 决策

1. **任务宿主契约新增两个只读成员**：按任务 id 取标题文本键；按任务 id + 目标下标取该条目标的
   描述文本键。两者返回类型与任务定义/目标定义现有的标题键、描述键字段类型一致（均为可空的引用
   标识类型）。ABI 只能新增：用**带默认实现的接口成员**（既有契约同类扩展先例）新增这两个成员，
   不要求任何既有实现类型（含测试替身）连带改动即可继续编译通过。既有的状态查询/转移方法集、
   进度快照结构、激活目标三元组结构一字不动。

2. **默认实现按"只读查询"口径，恒返回"无"（保守默认值）**：与既有同类只读查询默认成员同一惯例——
   这两个成员本身不产生任何副作用、不推进任何状态、不修改任何账本，允许一个明确、保守的降级
   默认值，语义是"该宿主实现不提供这项查询"。未知任务、目标下标越界、或该任务/该条目标未登记
   对应文本键，三种情形调用方（任务追踪 UI）都按"这条暂时没有文案可显示"处理，不需要相互区分，
   均降级为"无"，不抛异常、不编造占位文案。生产实现用显式接口实现落地这两个新成员，不用新增的
   同名公开方法隐式满足契约成员——理由同既有同类改动的一贯判断记录：隐式实现会把该公开方法的
   物理签名从普通实例方法改写为契约成员的虚方法形态，被静态 ABI 比对工具误判为破坏；显式接口
   实现规避这一问题，公开方法本身的物理签名/行为不受影响。组合/包装出的实现（若存在）必须显式
   转发这两个新成员，不能依赖默认实现的隐式兜底——本仓库框架内的默认成员转发门禁专门检测这类
   遗漏，本次新增的两个成员同样纳入该门禁的检测范围。

3. **表现层视图模型新增两个并行的按 id 转发方法**，不改写既有的进度快照类型与激活目标三元组的
   元素形状——前者是已发布的公开类型，后者是值元组，往里塞文本键要么破坏 ABI、要么需要一次不
   兼容的类型替换；新增两个纯只读转发方法（不新增订阅、不缓存快照，文本键来自内容定义，不随
   运行期事件变化）与既有同类扩展（如"目标需求数量"查询）同一处理口径，不是遗漏。

4. **路径小语法（供表现层用点分路径拉取运行期数据）新增两条任务相关子路径**：一条对应"标题
   文本键"（末段保留关键字，不带下标，转发新增的标题键查询成员）；一条对应"目标描述文本键"
   （末段保留关键字，带下标，转发新增的目标描述键查询成员，下标与既有目标进度子路径对齐同一份
   目标数组）。两者比照既有任务子路径（状态、单条目标进度）同一套"末段保留关键字"解析惯例，
   不引入新的路径寻址风格；未知任务/越界下标/数据未填三种情形与既有目标进度子路径越界即"无"
   同一口径。

5. **框架自带的参考 UI 面板（任务日志面板）顺手改为有标题文本键时优先显示标题**：不给面板已发布
   的构造方法加必填参数（消费方已在用这个签名，加参数会导致下一次升级直接编译不过）；改用与本
   框架同类改动一贯的做法——新增一个携带本地化查询能力的加性重载，提供了才会优先经本地化查询
   渲染任务真名，未提供时（既有签名）退化显示文本键本身（键串本身有信息量，不是编造的占位
   文案），完全没有标题文本键时回退显示任务 id，保持该字段落地前的行为。

## 后果

### 正面

- 消费方今后可以只经任务宿主契约与任务日志视图模型两层只读查询，拿到"任务名 + 目标描述"，完成
  任务追踪 HUD 的展示诉求，不再需要表现层自己反查内容数据表拼数据，不再违反"视图不得自己拼宿主
  数据"的铁律。
- 新增契约成员是纯新增（带默认实现），不要求任何现存实现类型（含各模块测试替身）连带修改即可
  继续编译通过；ABI 探针核实无破坏。
- 路径小语法两条新子路径与既有任务子路径同一套解析惯例，游戏层不需要为标题/描述文本键单独学习
  一套新的路径语法。

### 负面

- 参考面板新增的"携带本地化查询能力"构造重载与既有签名并存，调用方需要知道该用哪一个——与本
  框架此前同类改动（如动作条面板）面临的取舍完全相同，不是本次新引入的问题。
- 路径小语法的"末段保留关键字"惯例存在理论边界情况（任务 id 恰好以关键字字面量结尾时被误判为
  子路径），与既有任务/技能两条子路径共享同一已接受的既有惯例，不因本次新增而扩大风险面。

## 备选方案与为什么不选

- **直接往进度快照类型/激活目标三元组里塞标题/描述键字段**：技术上能让调用方少一次方法调用，
  但进度快照是已发布的公开类型，改写其字段语义或往值元组里加元素都会破坏既有调用方的编译——
  ABI 只能新增，不能改动已发布类型的既有形状，故选择新增并行查询方法而不是改写既有结构。
- **参考面板直接给已发布的构造方法加一个必填参数**：会导致消费方下一次升级直接编译不过——
  与"任务追踪 HUD 展示优化"这个诉求本身矛盾（不能为了改善一个展示细节，先破坏消费方现有代码
  能不能编译通过这个更基本的前提），故改用加性重载。
- **不做参考面板改动，只收口契约与视图模型两层**：技术上也能满足消费方反馈（消费方接入的是自己
  的 UI，不依赖框架参考面板），但参考面板此前只显示裸 id 这一行为本身也是一处可以顺手改善的
  展示缺口，改动风险可控（加性重载，不影响既有调用方），故一并收口，不留一个"文本键已经能查到、
  框架自己的参考实现却继续显示裸 id"的不一致状态。
