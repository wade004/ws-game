# ADR-0088 仇恨表跟随运行期阵营变化清理

状态：已拍板 2026-09-25

## 背景

消费方反馈（第三十三批，阻塞项2）：目标运行期改判为友方（框架此前不提供入口，消费方只能直接
写实体的阵营字段）后，仇恨表没有被清理，`AiHost.HandleCombat` 也直接取威胁表最高值当目标、不
检查是否仍敌对——AI 持续"追"这个已转友方的目标，施法因目标不合法失败（实测 69 次），旁边真正
敌对、距离仅 3 米的单位完全得不到处理。核实后确认两处真缺口：框架没有运行期改阵营的入口；
`IThreatTable` 没有"按来源移除一条"的方法（`PruneDead` 只清理已死亡的来源）。

## 决策

1. **新增运行期改阵营的框架入口**：`WorldUnitAccess.SetFaction(unitId, newFactionId)`——
   与 `SetLevel`/`Revive` 等既有"改单位状态"入口同层，只加在具体实现类型上，不上升为只读查询
   契约 `IUnitAccess` 的成员。新旧阵营相同时直接返回；不同则写入后用同步派发的方式发布
   `unit.faction_changed`（`unitId`/`oldFactionId`/`newFactionId`），登记进事件目录并过生成器
   一致性检查。
2. **`IThreatTable` 新增 `RemoveSource(unitId, sourceId)`**：只删 `unitId` 自己表里的一条；默认
   接口实现抛不支持异常（收边新增能力，不强制其它既有测试替身支持），`ThreatTable` 提供真实
   删除。
3. **`ThreatTable` 订阅 `unit.faction_changed`，双向清理**：变更方自己的仇恨表里不再敌对的来源；
   全部被追踪单位的仇恨表里，把变更方当作来源、但已不再敌对的条目。敌对性现场判定，不缓存。
   仅生产装配路径（`CombatHost`）具备这条订阅；测试替身不受影响。
4. **护栏（与决策 3 独立存在）**：`AiHost.HandleCombat` 选目标时不再无条件信任威胁表最高值，
   跳过已不敌对/已死亡的来源，继续取下一个仍敌对的；全部非敌对则不选目标，回落到既有脱战判定。
   即便某条路径遗留了一条非敌对的仇恨条目，AI 也不会选它当目标。

## 验收

- 复现：A 的仇恨顶端是 B；运行期把 B 改判为 A 的同阵营——A 的仇恨表不再含 B，目标切到下一个
  仍敌对的单位。
- 不变量：仇恨表里只剩非敌对来源时，`HandleCombat` 不选任何目标，回落到既有脱战逻辑。

## 明确不做的事

- 不提供"批量/按地图"改阵营的入口，只做单个单位这一颗粒度。
- 不给阵营关系判定本身加缓存——现场查询即可，尚无性能证据支持缓存的必要性。
- 不处理"感知范围内发现新目标"相关的转移逻辑——那是 ADR-0087 的范围。
