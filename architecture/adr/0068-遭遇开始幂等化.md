# ADR-0068 遭遇开始幂等化：同一地图同一遭遇已有进行中实例时不再新建

状态：已拍板 2026-09-22

## 背景

消费方反馈（游戏接入方第十一批）：遭遇宿主的开始接口不检查同一遭遇是否已有进行中实例，每次调用
都新建一个实例、重新生成初始参战单位、重新发出"遭遇开始"事件。区域触发把"进入即开始遭遇"这一
触发类型设为"非一次性"（为了让玩家死亡后可以重新挑战同一遭遇）时，玩家在战斗过程中来回穿越触发
范围的边缘，每次进入都会再调用一次开始接口，同一遭遇因此出现多个并存的进行中实例——订阅"遭遇
开始"事件、据此做一次性初始化的表现层逻辑被反复重置，症状是间歇性的、与玩家在触发范围边缘的
移动路径强相关，极难定位。消费方目前在自己的装配层用可覆盖的开始请求委托挡住这个问题（先查有没有
已在进行中的实例，命中就不再转发到开始接口），本质是在框架契约缺口上打了一层不属于自己该管的
外部补丁。

## 决策

1. **同一地图上同一遭遇定义已有进行中实例时，开始接口不再新建**：不重新生成参战单位、不重新
   发出"遭遇开始"事件，直接返回那个已在进行中的实例 id（幂等）。"进行中"用遭遇宿主既有的活跃
   状态查询口径——已结束（胜利/失败/被强制中止）的实例不算，不会挡住重新开始。不同地图上的同一
   遭遇定义互不影响，各自独立判定。

2. **判定与创建逻辑只写一份，开始接口内部直接复用**：不允许新旧两条路径各自维护一份"是否已有
   进行中实例"的判断，避免后续改动只改一处、另一处悄悄留在旧行为。

3. **签名不变**：开始接口现有签名保持不变——调用方拿到的仍然只是一个实例 id，从返回值本身看不出
   "这次是真的新建了，还是命中了已有实例"。

4. **新增一个显式区分两种结果的入口**：遭遇宿主契约新增一个默认接口成员，返回一个枚举结果（新建
   / 命中已有进行中实例），内部走与既有开始接口完全相同的判定，不是另一套独立实现。默认接口成员
   本身只能委托给既有开始接口并恒报告"新建"——它欠缺的只是"识别出命中了已有实例"这层判定能力
   （需要访问具体实现方的内部实例账本，接口层面拿不到），因此老的实现方（未升级的自定义实现、
   旧版本编译产物）保持升级前完全一致的行为，不会因为契约新增一个成员就跟着改变既有行为。生产
   实现用显式接口实现覆盖，转发到与开始接口共用的同一份判定逻辑，真正区分两种结果——不让这个新
   落地方法隐式满足接口同名成员，理由同本仓库既有一系列默认接口成员的落地惯例（隐式实现会把方法
   物理签名从普通实例方法改写为接口成员的虚方法形态，被 ABI 探针静态签名比对误判为破坏；显式
   接口实现是 IL 私有方法，不计入公开表面，规避这一问题）。

5. **"已在进行中"属于正常情况，不写诊断**：玩家在触发范围边缘来回走动是正常游玩操作（不是内容
   配置错误），命中已有实例时不产生任何诊断输出，与既有"距离/边界类瞬时状态不写诊断"同一口径。

6. **不改区域触发默认的开始请求委托本身**：区域触发模块对"进入即开始遭遇"这一触发类型的默认
   转发逻辑，此前就是直接转调遭遇宿主的开始接口，本次改动落地后自动获得幂等保护，不需要任何
   改动——这正是本决策选在遭遇宿主这一层根治、而不是在区域触发层打补丁的原因（见"备选方案"）。

## 后果

### 正面

- "进入即开始遭遇"类型的触发区域配成"非一次性"（用于支持死亡后重新挑战）不再是危险组合——玩家
  来回穿越触发范围不会制造多个并存的进行中实例，表现层的一次性初始化逻辑不会被反复重置。
- 根治点在遭遇宿主本身，区域触发默认转发逻辑自动受益，消费方此前在自己装配层打的外部补丁可以
  拆除，改用框架原生行为。
- 契约签名不变，只新增一个默认接口成员，纯加法；需要区分"新建/命中已有实例"的调用方可选用新
  入口，不需要的调用方（如区域触发默认转发）不必感知这一变化。

### 负面

- 这是一次行为变更：本决策落地前，同一地图同一遭遇允许同时存在多个进行中实例（每次调用开始接口
  都真的新建一个）；落地后同一地图同一遭遇任意时刻至多一个进行中实例，后续调用命中时原样复用。
  框架内经排查没有依赖"同一遭遇可并存多个进行中实例"这一行为的既有测试或流程（见"影响既有文档"
  排查结论）。
- 需要真正做到"每次都强制重开"（而不是"没有就开、有就复用"）的场景，不能再依赖反复调用开始接口
  达成——如果后续出现这类需求，需要新增一个显式的"强制重开"入口，不能通过放宽本次收紧的判定来
  实现（同批同类型 ADR 的一贯取舍：默认安全的行为不为极少数场景开洞）。

## 备选方案与为什么不选

- **在区域触发层打补丁（消费方当前的临时做法）**：只解决"进入即开始遭遇"这一条触发路径，任何
  其它直接调用遭遇宿主开始接口的调用方（当前没有，但契约层面不排除未来出现）仍然暴露同一问题；
  且需要每个调用方自己维护一份"查询是否已有进行中实例"的逻辑，本质是把契约缺口转嫁给每个消费方
  重复实现。故不选，改在遭遇宿主本层根治。
- **让开始接口签名本身携带"是否新建"这一额外信息（如改返回一个结构体）**：属于破坏性变更，会
  波及全部既有调用点（表现层、消费方装配代码）。故不选，改为签名不变 + 新增一个默认接口成员
  这一纯加法方案，需要区分结果的调用方按需迁移到新入口，不需要的调用方不受影响。
- **默认接口成员的默认实现也尝试判定"是否已有进行中实例"**：接口层面没有任何可用的只读查询能
  回答这个问题（现有的"全部活跃实例"查询能拿到 id 列表，但拿不到每个实例对应的地图与遭遇定义，
  引入这些信息意味着要么扩大接口的最小面、要么在默认实现里做一次比对不同实现方内部账本的暗箱
  假设，两者都不合适）。默认实现恒报告"新建"、老实现方保持原行为，是唯一不引入额外接口面、
  不对未知实现方做假设的选择。

## 影响既有文档

- `core/gameplay/encounter/README.md`"判断记录"新增一条，记录本决策的落地要点与判断记录 1（胜负
  条件求值绑定发起玩家）等既有条目的关系（互不影响）。
- `core/gameplay/area_trigger/README.md` 新增一条判断记录，说明"进入即开始遭遇"类型触发配成
  "非一次性"这一组合此前是已知的危险组合，本决策落地后已经安全，本模块自身无需任何改动。

## 魔兽世界的对应做法

无直接对应（魔兽世界的副本/遭遇进入由独立的地下城实例系统统一管理，一个角色同一时刻只能身处
一个具体的实例化副本，不存在"同一张普通地图上同一遭遇可能被多次开始请求命中"这一问题形态；本
决策是本框架"遭遇不强制走独立实例化地图、可以直接绑定在共享地图上"这一裁剪设计下才会出现的
结构性缺口修复，不对应魔兽世界任何具体系统设计）。
