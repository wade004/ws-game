## 1. StatBlock（属性聚合）

本节定义的是 L1 模块 StatBlock 的契约，规则层只消费。`StatBlock` 挂在每个 `Unit` 上（见 05），属性定义本身属于 L1 数值层的 `stat.definition` 表（见 04），本节定义其如何聚合与修改。

### 1.1 三段式聚合

```
最终值 = ( 基础值 + Σ flat修正 ) × ( 1 + Σ pct修正 ) × Π ( 1 + 独立乘区_i )
```

| 阶段 | 运算 | 典型来源 |
|---|---|---|
| 基础值 + 固定修正（flat） | 加法叠加 | 等级成长、装备固定属性、光环固定加成 |
| 百分比修正（pct） | 各项相加后统一相乘 | 装备百分比属性、光环百分比加成 |
| 独立乘区（mult） | 各来源分别相乘，互不合并 | 不同类别的增益效果（如"易伤"和"部位增伤"分属不同乘区，避免相加抵消设计意图） |

评级换算（属性评级 → 百分比效果的曲线换算，如魔兽的急速评级/命中评级）作为可选策略：`stat.rating_conversion` 表存在且启用时，某些属性在参与三段式聚合前先过一层评级曲线（曲线断点以单位等级为自变量）；未启用时评级属性本身即最终百分比值。是否启用是策略配置项。

勘误补充（2026-09-07，外部审计 R08）：评级换算结果按等级缓存，只有单位等级真正发生变化时才需要重算——"等级变化"覆盖两条来源：正常升级（`progression.level_up`）与读档恢复等级（对应 10 `player.progression` 段的读档路径，读档不经过正常升级流程，不发 `progression.level_up`，需要一条独立的通知路径触发同一次重算）；两条来源都必须驱动评级缓存失效，遗漏读档这一条会导致读档后评级换算结果停留在读档前的等级。

勘误补充（2026-09-11，消费方反馈第 36 条）：第 51-53 行表格"等级成长"这一"固定修正（flat）"典型来源，只有唯一一条写入路径（来源 id 固定为 `prog.growth`）：正常升级、读档恢复、以及 07 第 2.1 节"生物出生等级 > 1"（经 `stat_growth_ref` 一次性补写"2 级到出生等级"的累计段）三条触发时机共用同一套聚合逻辑——"当前等级对应的整段累计成长量"，不是按触发时机分别各自累加一次。基础值本身（07 第 2.1 节 `base_stats`）不叠加任何等级成长，成长量只经本节这一层 flat 修正生效，避免与基础值各计一次同一段成长。

### 1.2 StatModifier

```
struct StatModifier {
  stat: StatKey
  op: flat | pct | mult
  value: Number
  sourceId: Id
  multGroup: Optional<String>   // 仅 op = mult 时有意义，独立乘区分组名，缺省归入默认分组
}
```

- `sourceId` 标记修正的来源（某条光环实例 id、某件装备实例 id），移除来源时按 `sourceId` 整体撤销其名下全部修正，不需要逐条匹配数值（对应魔兽装备穿脱、光环消失时的属性回退方式）。
- `multGroup` 承载第 1.3 节策略配置项"独立乘区的分类粒度"：同一分组内的多条 `mult` 修正先相加，各分组之间再相乘（见第 1.1 节 `Π (1 + 独立乘区_i)`）；未指定时全部落入同一个默认分组。

### 1.3 契约

```
interface StatHost {
  getStat(unitId: Id, stat: StatKey): Number
  addModifier(unitId: Id, modifier: StatModifier): void
  removeModifiersBySource(unitId: Id, sourceId: Id): void
}
```

- 目录名：`core/numbers/stat_block`（L1 数值层，见 01）
- 数据表：`stat.definition`（见 04，L1 登记，本模块只读引用）
- 事件：发出 `stat.changed { unitId, stat, oldValue, newValue }`
- 依赖层：L0（Expr、EventBus）、L1（`stat.definition`）
- 策略配置项：评级换算是否启用；独立乘区的分类粒度（默认按"效果来源类别"分区，游戏层可细化）
- 测试方式：脱离引擎对 `StatHost` 灌入一组 `StatModifier`，断言三段式聚合结果与手算一致；`removeModifiersBySource` 后断言属性回退到移除前状态

## 2. PowerSet（资源池）

本节定义的是 L1 模块 PowerSet 的契约，规则层只消费。资源类型数量与种类完全由数据定义（拍板范围：资源类型可配置数量），架构不预设"只有法力"或"必须双资源"。

### 2.1 数据

引用一组资源类型定义（登记为 `arch.power_type` 表，见 04 第 1.1 节）；每种资源类型声明：上限来源（固定值或引用属性）、回复规则（随时间线性回复、随战斗行为产出、脱战自动回满等，策略配置项）、衰减规则（可选，如脱战后归零）、消耗与产出的触发点（施法时扣减、命中时产出等，由 Effect 原语 `energize` 驱动，见第 4 节）。

### 2.2 契约

```
interface PowerHost {
  getPower(unitId: Id, powerType: Id): Number
  getPowerMax(unitId: Id, powerType: Id): Number
  modifyPower(unitId: Id, powerType: Id, delta: Number, sourceId: Id): void

```

- 目录名：`core/numbers/power_set`（与 StatBlock 同层，二者同属 L1 数值消费的运行期状态，共用测试脚手架）
- 事件：`power.changed { unitId, powerType, oldValue, newValue }`；资源值降至下限（0 或数据声明的
  `min`）的那一次额外发 `power.depleted { unitId, powerType }`（连续多次扣到下限只发一次）
- 依赖层：L0、L1
- 策略配置项：资源类型集合、回复/衰减规则、是否允许资源溢出
- 测试方式：脱离引擎构造若干资源类型定义，驱动时间前进，断言回复/衰减曲线与配置一致

### 3.3 AuraDef 与 AuraEffect

`skill.aura_def` 字段：`id`、`duration`（`Optional<Number>`，空表示永久直到被移除）、`max_stacks`、`stack_category`（跨定义的静态叠加校验分组，仅供加载期内容校验使用，见 04 校验器与 [ADR-0023](adr/0023-光环叠加类别为静态校验分组.md)）、`dispel_type`（供 `dispel` 效果按类别筛选）、`effects: List<AuraEffect>`。`duration`、`periodic_damage`/`periodic_heal`（见下表）`params.interval` 均以时间单位计，施加/触发当下按当前生效模式折算原始数据值——`AuraHost` 内部持有与 `CooldownTracker`（3.1 节 `cooldown_duration` 行）同一套语义的系数，`ApplyAura` 写入剩余持续时间、`Update` 读取周期间隔时都先乘上该系数；模式切换时既有实例的剩余持续时间与周期累加器同步按同一系数换算，保持"累加器/interval 还差多久触发下一跳"这一比例关系在切换前后连续（勘误：2026-09-07，外部审计 5e779c6 相邻缺口根治，见变更记录）。

结论明确（2026-09-10，消费方复核，[ADR-0023](adr/0023-光环叠加类别为静态校验分组.md)，见变更记录）：`stack_category` 不是运行时叠加槽位维度——`AuraHost` 的运行时槽位键是 `(target, aura_def, sourceKey)`（见 3.8 节），`stack_category` 只被 04 第 5 节"叠加类别冲突"校验项在加载期使用，检查同一类别下是否混用了不同的叠加形态（`max_stacks>1` 与 `max_stacks==1`）。不同 `aura_def` 即使 `stack_category` 相同，运行时也各自独立维护叠加状态、互不影响，这不是算法缺陷，是本字段的既定范围；跨定义共享叠加槽位是当前未提供的能力（见落地方案"能力边界与未默认接入能力索引"表）。

| AuraEffect 类型 | 语义 |
|---|---|
| `mod_stat` | 持续期间提供一条 `StatModifier` |
| `periodic_damage` | 按周期造成伤害（走结算管线，来源标记为该光环） |
| `periodic_heal` | 按周期恢复生命 |
| `absorb` | 提供一个吸收池，结算管线中先扣吸收池再扣生命（见第 5 节） |
| `immunity` | 对指定学派/效果类型免疫 |
| `proc_trigger` | 绑定一个 `skill.proc_def`，光环存在期间监听触发条件；同一光环可登记多个本类型条目，各自独立生效（见下方勘误） |
| `spell_mod` | 绑定一个 `skill.spell_mod_def`，修改施法管线中的某个维度（见 3.6） |
| `override_skill` | 用另一个 `SkillDef` 替换某个技能的表现或效果（天赋/装备改变技能形态的实现位） |
| `control` | 施加控制状态（禁止移动/禁止施法/禁止普通攻击等标志位组合） |
| `flag` | 单纯的标志位光环，供 Expr 的 `self.has_aura(...)` 判断使用，不产生其它效果 |

勘误补充（2026-09-10，消费方前置核验复现，见变更记录）：`immunity` 按 (学派, 效果原语类型) 泛化定义，对第 3.2 节登记的全部效果原语一体适用（`interrupt`/`dispel`/`energize`/`teleport`/`move` 等同样生效，不限定于 `school_damage`/`heal`）——07 第 2.1 节 `CreatureUnit.Immunities` 的静态写法 `effect.<kind>` 同一语义。第 4.1 节结算管线"免疫吸收"步骤只是"伤害/治疗恰好都要经过该管线，因此在那里落地"的实现位置，不代表免疫判定本身只对这两类效果生效。例外：`apply_aura` 不纳入——对"施加一个光环实例"这个操作本身的免疫是另一层语义（免疫的是"获得光环"这件事，不是光环生效后内部某个子效果），本文档未就此拍板；`apply_aura` 的控制类光环免疫仍按既有实现逐条判定（见 07 `control_immune`）。

勘误（2026-09-10，消费方反馈"同一光环多个 Proc 触发器静默忽略问题"，见 `architecture/落地计划/消费方反馈-2026-09-10-多Proc触发器.md`、变更记录）：`proc_trigger` 行内容错误——`effects` 列表里允许登记多个 `proc_trigger` 条目，各自独立经 `ProcHost` 挂载、独立结算条件/命中率/内部冷却，光环整体移除（到期、驱散、显式移除、叠加溢出被替换等一切摘除路径）时全部一并注销，不残留孤儿订阅；同一光环内多条 `proc_trigger` 引用同一个 `proc_ref`（同一个 `skill.proc_def`）没有可区分的运行时语义，在加载期即被拒绝（04 第 5 节新增检查项 `aura_proc_trigger_duplicate`，定位到 `effects[index].params.proc_ref`）。修复前实现把"多个 `proc_trigger` 条目"按单值字段处理，加载校验通过但运行期只有最后登记的一个真正生效，是实现缺陷，不是本节此前的既定语义——本条只是把契约写清楚并同步代码，不改变已定稿的其余判定条件与结构。

### 3.5 SpellMod

```
struct SpellModDef {
  id: Id
  targetDimension: cast_time | cost | cooldown | crit_chance | effect_value | charges
  op: flat | pct
  value: Number
  affects: SkillFilter   // 按学派/标签/具体技能id过滤影响范围
}
```

SpellMod 是天赋、装备特效修改技能表现的唯一手段（拍板决策 1），通过 `apply_aura` 附带 `spell_mod` 类型的 `AuraEffect` 生效，不允许技能定义之间互相硬编码修改。

勘误补充（2026-09-11，消费方反馈"只读就绪查询影响后续充能状态"，见 `architecture/落地计划/消费方反馈-2026-09-11-充能查询副作用.md`）：**充能只读查询不得产生状态、`charges` 维度上限变化的守恒规则**——第 7 节 `getSkillReadiness` 与本节 `charges` 维度 SpellMod 共同暴露的一处缺口：查询当前充能数/下次恢复剩余这类只读接口，此前的实现会在调用时按"当下"的有效充能上限惰性创建账本状态；若这次查询发生在一次充能上限调整（如施加/移除带 `charges` 维度 SpellMod 的光环）**之前**，创建的账本会记下旧上限，此后上限变化不会追认到已创建的账本——同一场景"查没查询过一次"这一操作本身，会改变后续原生施法能连续成功的次数，是与只读查询契约相反的可观测副作用。本条明确两点：

1. **查询纯化**：任何只读查询（当前充能数、距下次充能恢复剩余、修饰后有效充能上限/单次恢复时间、技能是否就绪等）不得创建或修改充能账本，也不得推进任何计时器；尚未产生账本的技能，查询按当前有效上限计算一个只读默认快照（当前充能=有效上限、距下次恢复剩余=0）即可，不需要为此创建状态——账本的创建与生命周期完全由原生写路径（结算消耗一次充能、进入冷却、直接增加充能等）决定。
2. **充能上限变化的守恒规则**：已存在账本的技能，若其有效充能上限发生变化（`charges` 维度 SpellMod 因光环施加/移除/刷新而改变结果），当前充能数按差值 Δ 跟随调整，不是简单地清零或按新上限重新计算——上限**提高** Δ 时，当前充能数同步 `+= Δ`（新增的充能格立即可用，正在进行中的恢复窗口不受影响、不重置）；上限**降低**时，当前充能数夹取到不超过新上限，若因此恰好达到新上限（满充能）则清零"距下次恢复剩余"（没有正在进行的恢复窗口）。该对账在任何触达账本的时点（原生写路径，或——为保证只读查询看到的数字与紧接着的一次原生写路径结果一致——只读查询自身的快照计算）都按同一口径进行，不写回账本时（只读路径）只是"算出来给调用方看"，不产生状态变化。

两条规则合起来保证：查询本身永远不改变后续原生施法的实际行为，而"有效上限变化时当前充能数不跟着守恒"这一独立语义缺陷（即便完全不经过任何只读查询，仅靠原生写路径的惰性创建时机不同，同样会触发）也一并根治。详见 `core/rules/skill/core/CooldownTracker.cs` 类型判断记录与 `core/rules/skill/README.md` 判断记录、消费方反馈回复文档。

### 3.6 施法管线

固定检查顺序（每一步失败即中止并返回对应失败原因码）：

| 步骤 | 检查内容 | 失败原因码示例 |
|---|---|---|
| 1 存活与状态 | 施法者存活、未被 `control` 类光环禁止施法 | `SILENCED` / `STUNNED` / `DEAD` |
| 2 学派锁定 | 是否被 `interrupt` 效果锁定对应学派 | `SCHOOL_LOCKED` |
| 3 冷却 | 技能自身冷却与所属分类冷却是否就绪；充能是否 > 0 | `ON_COOLDOWN` |
| 4 公共冷却 | 若 `respects_gcd` 且公共冷却开关开启，检查公共冷却是否就绪（策略配置项，见下） | `GCD_ACTIVE` |
| 5 资源 | `cost` 是否够；离散模式下另检查 `action_cost` 行动点是否够（见 3.1 节 `action_cost`） | `INSUFFICIENT_POWER` / `INSUFFICIENT_ACTION_POINTS`（仅离散模式） |
| 6 目标合法性 | 按 `target_shape_ref` 解析目标，结合目标选择链（第 5 节）与阵营/存活等过滤，目标数量是否满足最小要求 | `NO_VALID_TARGET` |
| 7 距离与视线 | 是否在射程内、（若配置要求）是否有视线 | `OUT_OF_RANGE` / `LINE_OF_SIGHT` |
| 8 读条/引导 | 进入读条或引导状态，期间监听 `interrupt_flags` 指定的打断条件 | `INTERRUPTED` |
| 9 结算触发 | 读条/引导完成后，扣除资源、进入冷却/公共冷却、依次执行 `effects` | 无（正常完成） |

- **法术队列**：读条即将结束前的一小段窗口内可预先提交下一个施法请求，读条结束后立即顺序执行，避免因逐帧轮询输入产生的操作丢失；队列窗口长度是策略配置项。
- **公共冷却开关**：是否存在跨技能的统一冷却（GCD）、其时长，均为策略配置项；关闭时步骤 4 恒通过。
- **打断与学派锁定**：`interrupt` 效果命中读条/引导中的技能时立即中止步骤 8 并按 `interrupt_flags`/效果参数决定是否锁定对应学派一段时间。
- **离散模式下的解释**：本节固定检查顺序不变，规则层只改"解释"不改结构——`cast_time` 在离散模式下解释为"延迟 N 个己方回合生效的动作"（步骤 8 变为跨回合等待）；`channel_time` 解释为"每个己方回合重复一次直到结束"；公共冷却在离散模式下恒关闭（步骤 4 恒通过），因为离散模式下每回合只行动一次，公共冷却语义不适用；法术队列在离散模式下即"下一动作"——本回合已提交但尚未结算的意图。

勘误补充（2026-09-11，消费方反馈"读条完成当帧新冷却被提前推进问题"，见 `architecture/落地计划/消费方反馈-2026-09-10-施法时序与实例标识.md`、变更记录）：**新创建计时状态的起算时刻规则**——步骤 9"进入冷却/公共冷却"与本节相邻的计时状态（公共冷却、充能恢复窗口、3.8 节光环持续时间/周期累加器）共用同一套"以数据集声明的时间单位计、每次推进调用扣减一段 `dt`"的记账方式。本条明确：一次推进调用（连续模式一次 `Update(dt)`；离散模式一次 `AdvanceRoundTimers`/`AdvanceCastForActor`）内，若步骤 9 的结算触发是这次调用自己造成的（读条/引导恰好在本次 `dt` 内耗尽剩余时间），那么由结算触发新创建的冷却/公共冷却/充能恢复窗口/光环实例，起算于"这次推进调用结束之后"，不被这次调用自己的 `dt` 再扣减一遍——换言之，同一个完成时刻，不论调用方把总时长拆成一次推进还是拆成多次连续的小步推进，结果都必须一致（`cast_time=0.5`、`cooldown_duration=1` 的技能读条完成瞬间，新冷却剩余应恒为 `1`，不因为"单步 `Update(0.5)`"还是"两步 `[0.25,0.25]`"而分别得到 `0.5`/`0.75`）。此前实现（连续模式 `SkillHost.Update`）把"推进读条/引导（可能触发步骤 9 结算）"排在"推进既有冷却/公共冷却/充能/光环/Proc 内部冷却"之前，本次调用新创建的计时状态因此被同一个 `dt` 立即多扣一次；已改为先推进既有计时状态、再处理读条/引导，使新创建的状态自然落在下一次推进调用才第一次被推进，属于对步骤 9 既定语义（"进入冷却"就是"这次冷却満额可用，从现在开始计时"）的时序修复，不改变已定稿的判定条件与公式。相邻计时状态排查结论：GCD（步骤 4 公共冷却）、充能恢复窗口（步骤 3/3.1 节 `charges`）与冷却共用同一条推进路径，同类缺口一并修复；3.8 节光环持续时间/周期累加器（读条/引导完成时经 `effects` 里的 `apply_aura` 落地的新实例）同类缺口一并修复；Proc 内部冷却（3.4 节）只在事件总线批处理派发触发事件时才写入，不与"读条/引导是否恰好在本次调用内完成"这一时序竞争同一个 `dt`，不受影响。离散模式（[ADR-0013](adr/0013-时间模型可替换即时与回合制同一规则层.md)）下推进步长恒为整数轮（不可再分），不存在"同一完成时刻因拆分方式不同产生不同结果"这一可观测症状，本条不改变离散模式现状行为。

勘误补充（2026-09-11，消费方反馈"施法生命周期事件缺少实例关联标识建议"，见同一份反馈文档、变更记录）：**施法实例身份规则**——`SkillHost.castSkill` 返回的 `CastResult` 携带一个稳定的施法实例 id（"这一次施法请求"的标识）。它与效果结算批次共用的"攻击实例 id"（`EffectContext.attackInstanceId`，每次结算——一批目标同时应用同一组 `effects`——各分配一个全新值，见第 3.4/8 节 Proc/触发链相关说明）是两个不同层面的标识：前者贯穿"这一次施法请求"从排队/开始到成功/失败/打断的整个生命周期，后者只标记"这一批目标这一次结算"，读条/引导期间的多次周期跳（各自是独立的一次结算）与瞬发的一次结算各自拿到不同的攻击实例 id，即使它们都属于同一个施法实例；两者不互相冒用。分配时机：步骤 1～7 全部校验通过、真正进入步骤 8（立即开始读条/引导/瞬发）或进入法术队列时分配；步骤 1～7 任一步校验失败不分配（对应 `skill.cast_failed` 事件不携带该 id）。第 8 节四个施法生命周期事件（`skill.cast_start`/`skill.cast_success`/`skill.cast_failed`/`skill.cast_interrupted`）补充携带同一个 id：真正开始读条/引导/瞬发时发出的 `skill.cast_start` 与随后的 `skill.cast_success`/`skill.cast_interrupted`（若发生）携带同一个值；法术队列内的身份规则——排队接受本身即分配 id 并随 `CastResult` 返回，若该队列槽位在真正轮到它之前被新的排队请求覆盖、或被其所依附的当前读条/引导打断而清空，均发出一条携带"被清空的那个排队请求自己 id"的 `skill.cast_failed`（不是覆盖它的新请求、也不是被打断的当前施法各自的 id），使消费方能确认"排的这个队最终没有被执行"，不会永远等不到任何结果通知。`trigger_spell`/Proc 直接执行效果（3.4 节）不经过步骤 1～9 的施法管线，不发本节四个主动施法生命周期事件，也不携带/冒用施法实例 id；它们各自的效果结算仍然会分配上一段说明的"攻击实例 id"，与本条的施法实例 id 是两层不同的标识，不要互相替代。

勘误补充（2026-09-11，外部审计 audit-d6fda65-20260911 CORE-118-CAST 根治）：**施法终结事件保证**——步骤 8 读条/引导一旦进入生效状态，直到它正常完成（进入步骤 9）为止，只要中途被从"生效中"摘除（打断、施法者死亡/销毁、或实现内部的任何防御性重验），就必须恰好发一次以它自己的施法实例 id 标识的 `skill.cast_interrupted`；若它当时还挂着一个已排队的请求，该请求也必须恰好发一次以排队请求自己的施法实例 id 标识、携带 `QUEUE_CLEARED` 的 `skill.cast_failed`——两者互不替代、各自只发一次，不允许"摘除但不通知"的静默丢弃，也不允许同一次施法/排队请求收到两次终结事件。这一保证与施法者死亡/销毁事件本身何时真正派发到订阅方无关：施法者失效（存活/存在状态）与对应事件的实际派发时机可能不在同一次推进调用内完成（事件总线"入队 + 批处理派发"，见 `core/foundation/event_bus` README），不论哪一侧先发生，消费方最终必须且只能收到一组终结事件。此前实现在"施法者失效已生效、但死亡/销毁事件要等本次推进调用之后的批处理派发才送达"这一时序下未能满足本条——防御性重验分支只摘除内部状态、不发任何事件，等死亡/销毁事件真正派发到打断路径时状态已被摘除、无从补发，当前施法与排队请求都收不到终结通知，是实现缺陷，不是"调用者不应在此时查询"的合同异常（这一旧判断记录的前提不成立，已随代码改动一并勘误）。

勘误补充（2026-09-11，消费方反馈"冷却充能与公共冷却缺少统一只读查询接口"，见 `architecture/落地计划/消费方反馈-2026-09-11-冷却充能只读查询.md`）：步骤 3（冷却）、步骤 4（公共冷却）补充只读查询出口 `getSkillReadiness(unitId, skillId): SkillReadiness`（第 7 节）——只读取宿主现有冷却/充能/公共冷却账本，不推进时间、不创建第二套计时器、不修改任何状态，查询前后再次查询或再次 `getCooldown` 得到的值不变；其 `isReady`/阻塞来源与随后一次 `castSkill` 在同一状态下经这两步会得到的裁决结论一致，但不覆盖步骤 1/2/5/6/7 等其它拒绝原因，`isReady` 为真不等价于此刻 `castSkill` 一定成功。

勘误补充（2026-09-11，消费方反馈"动态地面坐标施法请求"，[ADR-0027](adr/0027-地面坐标施法请求.md)，见 `architecture/落地计划/消费方反馈-2026-09-11-地面坐标施法.md`）：**地面坐标施法请求**——本节固定检查顺序描述的是以单位为目标的 `castSkill` 入口；另有一条独立入口 `castSkillAtGround(casterId, skillId, request: GroundCastRequest): CastResult`（第 7 节），以显式世界坐标点（而非选中的单位列表）为落点，与 `castSkill` 结构性互斥（签名不含单位目标列表，不存在被静默替代的可能）。裁决口径共用步骤 1～5（存活/控制、学派锁定、冷却/充能、公共冷却、资源），换成地面坐标专属校验取代步骤 6/7：技能未在 `skill.def` 声明 `ground_target: true` 一律拒绝；射程（`range > 0` 时，从施法者到落点）超出复用 `OUT_OF_RANGE`；视线受阻返回 `GROUND_TARGET_NO_LINE_OF_SIGHT`（与单位目标的 `LINE_OF_SIGHT` 拆成独立原因码）；落点不可行走（依赖可选的导航查询，未注入时跳过本项）返回 `GROUND_TARGET_UNREACHABLE`；技能未声明允许地面目标返回 `GROUND_TARGET_UNSUPPORTED`。请求携带一份坐标快照策略（请求时固定 / 效果落地那一刻重新采样，默认前者），读条/引导期间的效果落地在应用前用与请求时相同的校验逻辑再校验一次，未通过则跳过该次效果落地（不影响施法本身的读条/引导正常收尾）。施法实例身份规则、`skill.cast_start`/`skill.cast_success` 等生命周期事件与单位目标路径完全一致，事件额外携带落点坐标；不支持法术队列（读条/引导中收到新的地面坐标请求一律 `BUSY`）。

### 3.7 目标解析形状

技能的目标解析 = `target_shape_ref` 指向的目标选择链（第 5 节 `target.chain_def`，链内 `shape`/`filters`/`sortBy` 字段组合候选范围与过滤排序，`shape` 按需引用 05 第 3.5 节的 `Shape`）；技能定义本身不直接写死"选最近的敌人"，而是引用一条已登记的选择链，便于同一条链被多个技能复用、被 AI 与玩家辅助施法共用。

勘误补充（2026-09-11，[ADR-0027](adr/0027-地面坐标施法请求.md)）：链的 `shape` 字段默认以施法者当前坐标/朝向为锚点重新锚定（见第 5 节）；`castSkillAtGround`（3.6 节）解析同一条链时改以地面坐标点为锚点、朝向固定为世界 +X 轴（一个地面坐标点没有"朝向"概念）。方向性形状（`cone`/`line`/`rect`）的链若被同一条 `target_shape_ref` 在单位目标与地面坐标两条入口间复用，其在地面坐标入口下的朝向不随施法者面向改变；需要按施法者朝向变化的地面坐标场景应改用不依赖朝向的形状（`circle`），或为两条入口分别登记不同的链。

### 3.8 叠加与刷新规则

| 规则 | 语义 |
|---|---|
| 同一 `aura_def` 与来源槽位（`(target, aura_def, sourceKey)`，见下行 `sourceKey` 语义）叠加数超过 `max_stacks` | 忽略新实例的叠加请求，或按策略替换为最新参数（策略配置项：`ignore\|refresh_only\|replace`）。仅作用于同一 `aura_def` 与同一来源槽位的重复应用；`stack_category` 不参与该槽位键，不同 `aura_def` 即使类别相同也各自独立叠加、互不影响（见 3.3 节结论说明、[ADR-0023](adr/0023-光环叠加类别为静态校验分组.md)） |
| 同来源同光环再次施加 | 默认刷新持续时间并按叠加规则处理层数（拍板沿用魔兽常见语义），是否允许多来源分别计时是（建议）扩展位，默认关闭以简化状态管理 |

结论明确（2026-09-10，消费方复核，[ADR-0023](adr/0023-光环叠加类别为静态校验分组.md)，见变更记录）：`sourceKey` 在默认的共享计时模式（`SkillOptions.AllowMultiSourceTiming = false`，默认值）下恒为 `null`——同一目标身上同一 `aura_def`，无论施加来源是谁，都命中同一个槽位，不按来源区分；只有显式开启独立来源计时（`AllowMultiSourceTiming = true`）时，槽位键才按 `(aura_def, sourceId)` 分别维护独立实例。不要把本节"同来源同光环再次施加"这一行默认语义误读成"总是按来源分别计时"。

勘误补充：`periodic_damage`/`periodic_heal` 携带一个可选的缩放属性（按来源属性 × 系数叠加到基础值上，见第 3.2 节 `school_damage`/`heal` 的"基础值、系数"语义在光环周期效果上的复用）时，若来源单位在光环仍生效期间已被销毁（`Despawn`，见 05 第 5.3 节 `SpawnHost.notifyDespawn`），光环本身不因来源销毁而失效（05/06 均未规定"来源销毁应连带移除已施加到其他目标身上的光环"这一行为，只有目标自身销毁才会摘除其名下光环）——周期效果继续按既定间隔结算，缩放属性部分因来源已不存在、无从查起，按 0 处理（只保留基础值部分），不中断周期结算、不视为异常。

勘误补充（2026-09-07，外部审计 R07）：一次时间推进（`dt`）大于某个光环剩余持续时间时（主循环追帧/大步长一次推进跨越了到期点），周期效果只按"到期前那一段时长"结算，不把到期之后本不该存在的时间余量也计入周期计时——即到期前应发生的周期次数 = `floor(min(dt, 剩余持续时间) / interval)`，不是 `floor(dt / interval)`。永久光环（`duration` 为空）没有到期点，不受本条限制，仍按完整 `dt` 结算。

### 3.9 控制递减

控制效果的递减机制（同类控制连续命中效果减半直至免疫）在魔兽用于 PvP 平衡，本架构裁剪为可选策略，默认关闭；关闭时改用"Boss/精英级免疫标志"（`creature.template.immunities`，见 07）覆盖需要豁免控制的场景。

## 4. Combat（战斗系统）

目录名：`core/rules/combat`（规则层，见 01）。

### 4.1 结算管线（固定步骤）

结算管线与时间模型无关：无论调用方处于连续模式还是离散模式，结算管线本身的固定步骤、输入输出与确定性要求完全一致，时间模型只影响"结算在哪个模拟步被触发"，不影响"结算怎么算"。

```
判定(命中/闪避/招架/格挡...可配置项)
  → 基础值(效果原语给出的基础数值)
  → 暴击(是否暴击、暴击倍率)
  → 施法者乘区(施法者自身增伤类修正)
  → 减免(护甲/抗性/百分比减伤)
  → 目标乘区(目标自身承伤类修正，如易伤/减伤)
  → 免疫吸收(免疫判定优先，其次扣减absorb光环的吸收池)
  → 落地(实际改变生命值/资源值)
  → 后置(触发Proc、写入仇恨表、发出结算事件)
```

每一步只依赖上一步的输出与只读的 `StatHost`/`PowerHost` 查询，不允许跨步骤回填修改，保证同种子同输入同结果（拍板决策 3 的确定性要求在结算管线上的体现）。

勘误（DOC-118-09，codex 第十八轮，audit-d6fda65-20260911）：本节未规定偏斜/格挡与暴击是否必须互斥——"判定"步骤决出偏斜/格挡/暴击各自是否触发（各自独立掷骰），随后"基础值"步骤应用偏斜系数/格挡固定减免、"暴击"步骤应用暴击倍率，两步依次对同一笔数值相乘，参考实现（`core/rules/combat`）默认按此叠加，不做互斥限制。是否需要互斥（例如某款游戏希望"偏斜的攻击不可能同时暴击"）属消费方战斗结算策略/口味配置，由该游戏自行决定并实现，不是本节固定步骤本身的约束，也不需要改动这条固定管线的顺序。

勘误（消费方反馈"结算中间步骤经真实施法路径不可观测"，编辑器第 31 条，见 `architecture/落地计划/消费方反馈-2026-09-11-编辑器-第31条.md`）：结算管线可选接入一个**结算追踪回调**（`CombatOptions.resolveTrace`）——仅供内容工具/诊断消费，不改变本节固定步骤本身：接入后，管线每一次返回前（含判定步骤即终止的短路分支）都会把本次的输入（`EffectContext`）与完整输出（`ResolveResult`，含各步骤中间值 `Steps`）交给该回调恰好一次；未接入时零开销，管线行为、事件与判定结果不受影响。

| `crit`（暴击） | 开启 | 暴击率与暴击倍率均为属性驱动 |

### 4.3 护甲与抗性公式

护甲/抗性到减免百分比的换算走 `combat.resist_curve` 曲线表（04 已登记），公式形态为参数化曲线（如"护甲值 / (护甲值 + 系数 × 等级差修正)"这一类饱和曲线），具体系数由数据配置，架构只固定"输入护甲/抗性值、输出 0~1 的减免百分比"这一契约，不固定具体数学式，留给游戏层按需求调参。

### 4.4 仇恨表（Threat）

- 单机场景仇恨表的唯一用途是驱动 AI 选择目标（拍板范围声明），不涉及多人抢怪等设计目的。
- 规则：造成伤害按数值增加对应目标的仇恨值；治疗按（可配置系数的）数值增加仇恨值（治疗友方单位时，仇恨记在被治疗方所在阵营的仇恨表里，供敌对 AI 选目标）；专门的嘲讽类效果（`apply_aura` 搭配 `control` 或专用标志）可直接设置/强制置顶仇恨值；脱离战斗时清空仇恨表。

```
interface ThreatTable {
  addThreat(unitId: Id, sourceId: Id, amount: Number): void
  getTopThreat(unitId: Id): Optional<Id>
  clear(unitId: Id): void
  getThreat(unitId: Id, sourceId: Id): Number                    // 读取某来源当前仇恨值，未记录返回 0
  setThreat(unitId: Id, sourceId: Id, amount: Number): void       // 直接设置某来源仇恨值，供"强制置顶"实现
  getAll(unitId: Id): List<{source: Id, amount: Number}>          // 只读列出该单位仇恨表全部条目，供调试/测试与召唤模块"共享仇恨表"策略读取双方条目
}
```

### 4.5 进出战斗规则

- 进入战斗：造成/受到伤害、被仇恨表记录、主动使用带 `combat`-only 限制的技能，任一条件满足即置位 `combatState = in`。
- 脱离战斗：一段时间内（可配置）未产生新的战斗事件、且周边无存活的敌对仇恨来源，置位 `combatState = out`，并触发仇恨表清空、资源回复规则切换（如脱战自动回满）。
- 进入战斗事件（`combat.entered`）同时触发时间模型切换：若该场景的 `combat_time_model` 与当前时间模型不同，主循环按 03 第 3.3 节流程切换到对应模式并完成时间单位换算；`combat.left` 时按同一流程切回。
- 脱战判定时长同属第 3.1 节（04）"以数据集声明的时间单位计"的时间字段：离散模式下按 `seconds_per_turn` 换算为等效轮数（向上取整，保证不早于连续模式下的原定时长触发），每轮结束（`sim.round_ended`）时累加一次；判定条件本身（一段时间内未产生新战斗事件、且周边无存活的敌对仇恨来源）不因时间模型而改变。
- 勘误补充：进战判定的双方任一方若已经从世界中被销毁（`Despawn`，见 05 第 5.3 节）——例如一条来源已销毁的周期效果仍在继续结算（见 3.8 节勘误补充），结算过程仍会尝试对结算双方各判定一次是否需要置位 `combatState = in`——对"已不存在于世界中的一方"静默跳过这次进战判定（不置位、不发 `combat.entered`），既不是当作错误处理，也不做其它兜底；已存在的一方判定不受影响，正常按上一条规则置位。
- 勘误补充（2026-09-11，消费方反馈第 C11 项）：`combatState` 的唯一来源是本节描述的战斗模块自身（不是资源池等下游同步对象），读档恢复时须先清空该运行期状态再用存档值恢复、由本模块把结果同步给下游，见 [10_存档与持久化.md](10_存档与持久化.md) 第 3 节"恢复顺序与一致性契约"。

### 4.6 死亡与复活

死亡与复活策略是可配置项（拍板裁剪原则：死亡改复活点或读档）：

| 策略 | 语义 |
|---|---|
| `respawn_point` | 死亡后在最近/指定复活点满状态复活 |
| `reload_save` | 死亡后回退到最近一次自动/手动存档 |
| `permadeath`（建议） | 死亡即结束当前存档周期，供硬核难度使用，默认不启用 |

勘误补充（2026-09-11，消费方反馈第 C11 项）：`respawn_point` 策略延迟到期后才执行的复活队列须在读档、目标单位销毁、世界清空、执行主体自身释放等时机全部失效并在执行前校验目标单位仍存在，避免用一条读档前遗留的旧复活记录覆盖读档恢复好的状态，或对已不存在的单位执行复活，见 [10_存档与持久化.md](10_存档与持久化.md) 第 3 节"恢复顺序与一致性契约"。

## 5. Targeting（目标选择）

目录名：`core/rules/targeting`（规则层，见 01）。

`target.chain_def` 定义一条有序的"候选来源 + 过滤 + 排序"组合：

```
struct TargetChainDef {
  id: Id
  source: current_target | nearest_in_shape | self | party_lowest_hp_pct | ...
  shape: Optional<Shape>      // 候选范围（05 第 3.5 节 Shape），未声明时由来源策略自带范围（如 self/current_target 不需要范围）
  filters: List<FilterExpr>   // 存活、阵营关系、免疫标志等
  sortBy: Optional<{key, direction}>
  maxTargets: Optional<Int>   // 候选数量上限，缺省 1；0 表示不限
  fallback: Optional<Id>      // 找不到候选时退化到另一条链
}
```

链式规则完全可配置（拍板范围声明：口味决定的目标选择链不写死），架构固定的是"来源枚举 + 过滤 + 排序 + 回退"这一组合结构，具体某个技能用哪条链、链里包含哪些过滤条件由数据决定。

- 契约：`TargetHost.resolve(chainId: Id, casterId: Id) -> List<UnitRef>`
- 事件：目标选择默认不发事件；实现可提供开关，开启时发出 `targeting.resolved`（携带施法者、链 id、目标列表）供调试与表现层订阅；结果作为施法管线步骤 6 的输入

勘误补充（2026-09-11，[ADR-0027](adr/0027-地面坐标施法请求.md)）：补充只读解析出口 `resolveAtPoint(chainId: Id, casterId: Id, point: Vec2) -> List<UnitRef>`——与 `resolve` 复用同一条候选收集/过滤/排序/截断/回退管线，唯一差异是形状查询/排序距离基准的锚点从"施法者当前坐标/朝向"换成显式传入的 `point`（朝向固定为世界 +X 轴，见 3.7 节勘误），`currentTarget` 恒视为未提供。供 3.6 节 `castSkillAtGround` 复用同一条 `target.chain_def` 定义解析地面坐标施法命中的单位集合；不发布 `targeting.resolved`（该事件以"施法者+链"为主键，调用频率与既有 `resolve` 不同）。
- 依赖层：L0（Expr）、L1（Faction）、依赖 05 的 `ISpatialQuery`
- 策略配置项：链的具体组合（等价于游戏口味中的"目标怎么选"）
- 测试方式：脱离引擎构造一组假想单位坐标与阵营，驱动 `resolve`，断言返回顺序与手算一致

## 6. AI

目录名：`core/rules/ai`（规则层，见 01）。

### 6.1 行为外壳状态机

```
idle → patrol → chase → combat → return → flee
                                └→ dead（任意状态可进入）
```

| 状态 | 语义 | 典型转移条件（Expr，`enemies`/`self`/`time` 分组） |
|---|---|---|
| `idle` | 原地待命 | 感知到敌对单位进入感知半径 → `chase`；无巡逻路径时的默认态 |
| `patrol` | 沿路径巡逻 | 同上转移到 `chase`；到达路径终点循环或折返 |
| `chase` | 追击目标直至进入攻击范围 | 进入攻击范围 → `combat`；追出脱战范围或目标消失 → `return` |
| `combat` | 执行优先级表（Rotation） | 目标脱离仇恨表且无新目标 → `return`；自身血量低于阈值且策略允许 → `flee`（可选） |
| `return` | 返回出生点/巡逻起点 | 到达后 → `idle` 或 `patrol` |
| `flee` | 逃离战斗 | 脱离追击范围 → `return`；被追上继续战斗则回 `combat`（策略配置） |
| `dead` | 死亡 | 见第 4.6 节死亡策略 |

`ai.behavior_profile` 字段：`id`、`perception_radius`、`patrol_path_ref`（可选）、`leash_range`（脱战追击上限距离）、`flee_hp_pct_threshold`（可选）、`combat_return_policy`、`rotation_ref`（`combat` 态执行的优先级表引用，第 6.4 节"Boss 阶段 = 换 Rotation"实际替换的正是本字段指向的表）、`decision_interval`（可选，`combat` 态求值优先级表的节奏，以模拟时间单位计）、`transitions`（可选，覆盖默认转移条件：键为转移名，值为 Expr 文本，未列出的转移名沿用第 6.1 节状态表给出的默认判定）。

离散模式下，`chase`/`return` 两个状态按每回合移动预算（见 04 `found.time_model.movement_budget_rule`）执行位移，一次状态求值内可能消耗完本回合全部移动预算而不改变状态；连续模式下二者按连续速度积分位移，行为外壳状态机的状态集合与转移条件本身不因时间模型而分叉。

### 6.2 优先级表（Rotation）

玩家辅助施法（如"智能循环"类体验）与敌方 AI 使用同一种数据格式，只是挂载宿主不同（拍板范围声明）：

```
struct RotationEntry {
  priority: Int
  condition: Expr          // self/target/combat/enemies 分组
  skillId: Id
}
```

`ai.rotation` 是这些条目的有序列表；执行时按 `priority` 从高到低依次判断 `condition`，第一个满足且施法管线检查通过的条目被执行。

离散模式下，AI 在自己的回合求值一次 `ai.rotation`，可连续执行多个满足条件的条目直到本回合行动点/移动预算耗尽或再无可用条目，然后调用 `TurnScheduler.endTurn`（见 03 第 3.2 节）；连续模式下 AI 按 tick 频率持续求值，不存在"回合内连续行动"的概念。两种模式复用同一份 `RotationEntry` 结构与同一张 `ai.rotation` 表，不产生第二套优先级表格式。

勘误（拍板 2，见 12 §5）："连续行动直到预算耗尽"这一语义只在先攻策略为 `action_points` 时成立（该策略下回合的边界确实等价于"行动点耗尽"）；先攻策略为 `initiative_stat`/`fixed_order` 时，每个行动者一回合固定只执行 `ai.rotation` 中第一个满足条件的一个条目就结束回合——这两种策略下不存在"行动点预算"这一概念，回合边界由 `TurnScheduler` 的先攻顺序本身决定，不是"预算耗尽"触发的。

### 6.3 感知半径与巡逻路径

- 感知半径：`ISpatialQuery` 按 `perception_radius` 周期性（或事件驱动）查询范围内的敌对单位，命中即触发状态转移。
- 巡逻路径：登记在 `ai.patrol_path`（见 04），结构固定为"有序 Vec2 列表 + `loop`\|`pingpong` 模式"，属于地图数据的一部分，格式与刷新表同级登记。

### 6.4 Boss 阶段

Boss 阶段 = 换 Rotation：遭遇系统（见 08）在阶段切换时，不引入新的 AI 状态类型，只是把该 `CreatureUnit` 当前引用的 `ai.rotation` 替换为另一张表，行为外壳状态机与执行机制完全复用。

### 6.5 契约

```
interface AiHost {
  evaluate(unitId: Id): Optional<SkillCastRequest>
  getBehaviorState(unitId: Id): BehaviorState
  forceState(unitId: Id, state: BehaviorState): void   // 供遭遇脚本强制切换阶段/状态
}
```

- 数据表：`ai.rotation`、`ai.behavior_profile`
- 事件：`ai.state_changed { unitId, oldState, newState }`
- 依赖层：L0、L1、L2 内依赖 Skill（发出施法请求）、Targeting、依赖 05 的 `ISpatialQuery`/`INavigation2D`
- 策略配置项：行为外壳各状态的转移阈值、是否启用 `flee`、Rotation 的具体内容
- 调用时机：连续模式下 `evaluate` 按 tick 频率被主循环调用；离散模式下 `evaluate` 只在 `TurnScheduler` 把当前离散步的 `actorId` 指向该单位时被调用一次，返回结果决定本次行动，随后是否再次调用取决于 6.2 节"连续行动直到预算耗尽"的规则
- 测试方式：脱离引擎构造固定场景（单位位置、血量、Rotation 表），逐 tick 推进，断言状态转移序列与技能选择序列符合预期

| `sim.time_model_rescaled` | sim | factor | 连续/离散模式切换时触发（`Core.Gameplay.Assembly.TimeModelSwitch`），携带同一次换算用的系数（语义同 `SimTimers.RescaleAll` 的 `factor`：新单位下 1 个单位对应旧单位下 `factor` 个单位）；`CooldownTracker`/`AuraHost`/`CastPipeline`/`ProcHost`（见 3.6/3.8 节）订阅本事件换算技能冷却/公共冷却/充能恢复进度（含耗尽充能恢复后紧接着开始的下一个恢复窗口）/光环剩余时间/施法读条与引导剩余时间/施法学派锁定剩余时间/proc 内部冷却，是它们从"以数据集声明的时间单位计"跟上模式切换的唯一驱动来源（外部审计 5e779c6 R05 收口 + audit-5c444f1-20260908 CR130-03 收口，`PublishImmediate` 同步发出，不经队列延迟） |

## 验收标准

1. 任给一个"技能改变世界"的场景（造成伤害、施加增益、开门、传送、召唤宠物），都能用第 3.2 节的 Effect 原语组合表达，无需新增专用代码路径。
2. 结算管线固定步骤顺序在文档中唯一定义一次，07/08 引用战斗结算时不重复定义、只引用本节。
3. 命中表六项、死亡复活三种策略、控制递减开关均明确标注默认值与是否可关闭/可选。
4. 玩家辅助施法与敌方 AI 复用同一个 `RotationEntry` 结构，文档中未出现两套并行的优先级表格式。
5. 事件词汇表中的每个事件都能在 07、08、09 文档的订阅方描述中找到至少一个使用场景，或明确标注为预留位。
6. 每个模块（StatBlock/PowerSet、Skill、Combat、Targeting、AI）都给出了目录名、契约、数据表、事件、依赖层、策略配置项、测试方式七项齐全的描述。
