## 1. 表现层铁律

表现层（L5）是全架构中唯一"看得见"的一层，也是唯一被允许直接依赖引擎适配层（L-1）渲染/音频/UI 接口的上层模块集合。为保证逻辑与表现彻底分离（架构目标 2），表现层必须遵守以下铁律，任何实现违反即视为架构缺陷：

| 编号 | 铁律 | 说明 |
|---|---|---|
| P1 | 只读逻辑状态 | 表现层只能读取 WorldSim 暴露的只读快照/查询接口，不持有、不缓存会被误认为权威的逻辑字段 |
| P2 | 只订阅事件 | 表现层对世界的感知一律经事件总线订阅（见 06 第 8 节事件词汇表），不得反向轮询内部结构代替订阅；`presentation.playback_finished`（见 6.4 节）是表现层唯一允许发出、并被 L0 消费的事件，它不改变任何逻辑状态，只解除 03 第 3.2 节所述的节奏门（`PacingPolicy` 的 `wait_for_playback` 等待），不构成对 P2"表现层只订阅"原则的例外 |
| P3 | 不写回 | 表现层任何输入（点击、按键、UI 操作）都必须转换为"意图请求"经窄契约提交给规则层/玩法层裁决，表现层自身不修改任何逻辑数据 |
| P4 | 只经引擎适配层的 2D、3D、镜头接口绘制 | 表现层不得绕过 L-1 接口直接调用引擎底层能力；一律经 `IRenderer2D`、`IRenderer3D`、`ICamera` 等 L-1 接口完成绘制；新增的绘制/播放能力先在 L-1 补接口 |

推论：
- 表现层可以延迟、插值、就近取整、做视觉容错（例如网络延迟类的口味在单机场景通常不需要，但插值仍用于固定步长模拟与渲染帧率解耦，见 [03_运行时骨架.md](03_运行时骨架.md)）。
- 表现层挂掉或被整体替换（换皮肤、换引擎）不影响模拟结果的可重放性（见 [10_存档与持久化.md](10_存档与持久化.md) 确定性与回放一节）。
- 表现层里唯一允许保存的"状态"是纯表现状态（当前播放的动画帧、特效对象池占用、镜头位置等），且这些状态不参与存档（除非游戏层显式声明为可选恢复项）。

## 2. View 绑定协议（表现侧）

每个逻辑对象（Entity 及其子类，见 [05_对象模型与世界.md](05_对象模型与世界.md)）在进入可见范围时，由表现层创建一个与之绑定的 View；View 销毁时机由世界事件（对象销毁/离开场景）驱动，不由表现层自行判断生命周期。

```
interface View {
  bind(entityRef: Id): void
  onEvent(evt: Event): void
  syncPose(pos: Vec2, facing: Direction, height: Number): void
  destroy(): void
}

interface ViewFactory {
  createView(kind: ViewKind, displayId: Id, entityRef: Id): View
}
```

- `entityRef` 是本 View 应绑定的实体 id，供引擎侧实现在创建阶段预知绑定目标；调用方仍需在拿到 View 后显式调用一次 `bind`。

- 创建/绑定/首次同步的顺序契约：`createView` 实现如果需要在返回 View 之前做任何依赖"这个 View 已经绑定到哪个实体"的内部处理（例如按该实体当前已有状态重放一次初始表现），必须先对本次创建的 View 完成一次身份绑定才能开始这类处理——不能假设"创建阶段"与"调用方显式 `bind`"之间存在一段身份未就绪的空档可以先处理别的事。调用方随后仍会按上一条协议再显式调用一次 `bind`，只要两次调用的 `entityRef` 相同，`bind` 必须是幂等的（可以安全被调用多次而不抛异常、不产生额外副作用），不构成对"调用方仍需在拿到 View 后显式调用一次 bind"这一条款的违反。`syncPose` 只在 View 已完成绑定后才可调用。

- `bind` 只建立只读引用（Id），不持有逻辑对象指针/引用本体。
- `syncPose` 由主循环在插值阶段调用（见 [03_运行时骨架.md](03_运行时骨架.md) 的 tick 顺序），View 内部据此驱动渲染变换，不自行外推物理。
- `onEvent` 是 View 接收战斗日志风格事件（见 06、08）并驱动反馈的唯一入口。
- View 的具体渲染节点结构（精灵树、粒子挂点等）完全由引擎适配层实现细节决定，本文档不约束。

- **读档场景的装备外观对账**（2026-09-10 勘误，第十四轮审核 P2-08 根治）：同图内读档（存档 A→B 期间实体身份不变、View 未被销毁重建）不止要求"该有 View 的有、不该有的没有"，选用了可选装备外观表现能力的具体 View，还要求其装备相关外观按读档后的真实装备快照对账——先清空当前已应用的全部外观，再按新快照重新应用；目标快照为空（读到无装备存档）时同样要清零，不能保留读档前残留的外观。这一步只处理"身份不变、继续存活"的既有 View；因本次读档新创建的 View 按既有协议在创建阶段重放一次当前装备即可，不需要重复处理。未选用装备外观能力（未装配对应可选查询/目录）的 View 不受约束。

（建议）ViewKind 的枚举值建议至少覆盖：`unit`、`gobj`、`projectile`、`areaTrigger`、`droppedLoot`，与 05 中的逻辑对象分类一一对应；具体枚举以 04 的 DataRegistry 注册表为准。

## 3. 混合渲染约定

架构目标要求"逻辑只用平面距离与方向，换成纯俯视 2D 不改运行时"；2D 与 3D 的混合渲染完全在表现层完成，逻辑层（L0~L4）不感知"深度""高度"这类渲染概念，只感知平面坐标 `Vec2` 与一个可选的逻辑高度值（用于跳跃、飞行类效果的判定，见 05）。表现形态由游戏层在 `sprite`（2D 精灵）与 `model`（3D 模型）两种外形类型间选择，默认路线是 2D 地面图 + 2D 精灵；"2D 地面图 + 前景遮挡层 + 3D 角色"的混合渲染与全 3D 场景均为可选路线，本节给出的层结构与排序规则对三者一体适用（见 ADR-0012）。

### 3.1 层结构与统一 sortY 排序

| 层 | 内容 | 排序方式 |
|---|---|---|
| 地面层 | 2D 地面图，经 `IRenderer2D` 绘制 | 固定在最底层，不参与 `sortY` 排序 |
| 装饰层 | 2D 地面装饰物（不遮挡单位的贴花、痕迹等） | 固定在地面层之上、单位层之下 |
| 单位层 | 玩家/生物/物件等可见对象，按外形类型二选一：`sprite` 型经 `IRenderer2D` 绘制，`model` 型经 `IRenderer3D` 绘制 | 按统一 `sortY` 排序键合成，`sprite` 与 `model` 混合排序由引擎适配层保证（见 02 第 2 节） |
| 前景遮挡层 | 2D 前景遮挡物（近景建筑、树冠等，遮挡处于其后的单位） | 固定在单位层之上 |
| 特效层 | VFX（见第 5 节），可为 2D 面片或 3D 粒子 | 按挂点或世界坐标随所属对象参与 `sortY` 排序，屏幕空间特效独立于 `sortY` 固定叠加 |
| UI 层 | 见第 7 节 UI 框架 | 固定叠加在最上层，不参与 `sortY` 排序 |

- 统一排序键 `sortY` = 逻辑位置的纵轴分量（对应 05 的 `layerDepth`）+ 每个可见对象的排序偏移（`display.map` 的 `sort_offset` 字段，见 04），`sprite` 与 `model` 型对象共用同一套排序键，具体合成算法由引擎适配层实现，上层不关心细节。
- 排序键相同时的平局规则（建议）：按对象稳定 id 排序，避免同帧抖动闪烁。
- 高度（跳跃、抛物线弹道）只影响绘制时的纵向像素偏移，不参与排序键计算，避免"跳起来穿到墙后面"的错觉需要额外遮挡处理时，由 `sort_offset` 覆盖。

### 3.2 方向量化与镜像（仅 sprite 型）

- 逻辑朝向是连续角度（或单位向量）；仅 `sprite` 型外形在表现层将其量化为固定档位的方向枚举，用于选择对应方向的精灵资源；`model` 型外形直接使用连续朝向驱动骨骼与挂点，不做方向分桶（见 05 第 3.2 节）。
- 档位数量是可配置项（策略配置项，见 [13_新游戏接入指南.md](13_新游戏接入指南.md) 口味配置清单），常见取值 4/8；档位数量由 DisplayInfo 的资源集决定，同一逻辑对象不要求所有方向都有独立美术，缺失方向档位时按镜像规则回退（例如只做半侧美术，另一半靠水平镜像得到）。
- （建议）具体游戏的镜头朝向/世界坐标轴习惯与本架构默认的量化索引约定（见 05 第 3.1 节）不一致时，可在按量化索引解析方向档位前先经一张表驱动的重映射（量化索引 → 量化索引），这是新游戏接入阶段的口味配置项，不改变 `direction_slot`/`mirror_of`/`flip_x` 三个固定档位机制本身。
- 镜像规则表（仅 `sprite` 型）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| direction_slot | Id | 是 | 方向档位标识，如 `front`/`front_side`/`side`/`back_side`/`back` |
| mirror_of | Optional<Id> | 否 | 若本档位由另一档位镜像得到，填被镜像档位 id |
| flip_x | Bool | 否 | 是否水平翻转 |

### 3.3 sprite 型：纸娃娃层与锚点；model 型：槽位与挂点

#### 3.3.1 sprite 型：纸娃娃层顺序与深度、锚点

- 纸娃娃（见第 4 节）内部各层有自己的绘制顺序（层内 z 序），与场景级 `sortY` 排序是两套独立机制：场景级排序决定"这个单位画在那个单位前面还是后面"，层内顺序决定"这个单位身上披风画在铠甲前面还是后面"。
- 每层声明一个锚点，用于挂接子层（武器挂点、头饰挂点、特效挂点等）。

锚点表：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| anchor_id | Id | 是 | 锚点标识，如 `hand_main`、`hand_off`、`head`、`chest`、`root` |
| parent_layer | Id | 是 | 所属层 id |
| offset | Vec2 | 是 | 相对父层原点的偏移（随方向档位可有多组，见下） |
| offset_by_direction | Map<Id, Vec2> | 否 | 按方向档位覆盖偏移，缺省用 offset |

- 锚点运行期查询经 `IAnchorQuery.getAnchorWorldPosition(entityId: Id, anchorId: Id): Optional<Vec2>` 承担，由表现层实现，供特效挂接（`attach_mode: anchor`，见第 5.1 节）等消费方使用。

#### 3.3.2 model 型：槽位与挂点

- 槽位（Slot）承载装备换装：`display.map` 的 `slots` 声明该模型可换装的部位，`display.equip_visual`（见 04 第 7.1.2 节）把具体装备映射到槽位网格，经 `IRenderer3D.setSlotMesh` 应用。
- 挂点（Socket）承载子模型挂接：`display.map` 的 `sockets` 声明该模型的命名挂点，`display.equip_visual` 的 `socket_attach` 模式把独立模型（武器、特效载体等）挂接到挂点，经 `IRenderer3D.attachToSocket`/`detach` 应用。

槽位表：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| slot_id | Id | 是 | 槽位标识，对应 `display.map` 的 `slots` 元素 |
| default_mesh_ref | Optional<Id> | 否 | 默认网格资源引用，对应 `display.map` 的 `default_slot_meshes` |

挂点表：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| socket_id | Id | 是 | 挂点标识，对应 `display.map` 的 `sockets` 元素 |
| attach_ref | Optional<Id> | 否 | 默认挂接的子模型资源引用，可由 `display.equip_visual` 覆盖 |

- model 型 View 需实现可选能力接口 `IModelHandleProvider.tryGetModelHandle(): Optional<ModelHandle>`，向特效/挂点系统暴露自身持有的模型句柄，供 `attach_mode: socket` 的实际挂接使用（见第 5.1 节）。

### 3.4 影子与高度偏移

- 每个可见单位默认携带一个地面投影影子，影子锚定在逻辑平面坐标（不随高度位移）；呈现模式由 `display.map` 的 `shadow` 字段声明为 `blob`（贴地简化影子，大小/透明度可配置）或 `projected`（投影阴影），`none` 表示不渲染影子；`sprite` 型经 `IRenderer2D` 应用，`model` 型经 `IRenderer3D.setShadow` 应用。
- 高度偏移（跳跃、击飞、悬浮类效果）只平移精灵/模型的纵向绘制位置，不平移影子；影子与角色纵向距离越大，直觉上离地越高，此为 2.5D 常用的廉价高度表达手段。高度偏移经正式接口参数传递：`sprite` 型经 `IRenderer2D.setTransform` 的 `height` 参数，`model` 型经 `IRenderer3D.setPlacement` 的 `height` 参数（见 02 第 1.3、1.12 节），不借用 `setShaderParam`/`setMaterialParam` 等材质参数通道传递。

### 3.5 镜头：固定俯角、跟随与缩放

- 镜头是表现层对象，不是逻辑对象；镜头固定俯角与朝向，只做跟随与在配置范围内的缩放，不支持自由旋转，全部操作经 `ICamera` 接口完成（见 02 第 1.13 节）：`configure` 设定俯角/朝向/缩放范围，`follow` 跟随目标（通常是玩家 PlayerUnit 的 View 位置），`setZoom` 在范围内缩放，`worldToScreen`/`screenToWorld` 承担世界平面与屏幕坐标的相互投影，`shake` 承担震屏。
- 镜头对逻辑层只读（用于视锥剔除查询等性能优化），不得反向影响任何模拟结果（例如"离开镜头的单位降低 AI 频率"这类优化如需存在，必须经窄契约由规则层/玩法层主动实现，不能由镜头单方面暂停模拟）。

### 3.6 画布分辨率与拉伸策略

- 参考分辨率、拉伸/信箱/裁剪策略、UI 安全区均为可配置项，具体数值不在本架构拍板，留待新游戏立项时在 [13_新游戏接入指南.md](13_新游戏接入指南.md) 的口味配置清单中填写。

## 4. 纸娃娃与程序动画

### 4.1 CharacterRig 职责

CharacterRig（原 SpriteRig）是表现层里负责"把一个逻辑单位画成一个可动的角色"的组件，按外形类型分派到 `sprite` 或 `model` 两套实现，职责边界：

| 职责 | 说明 |
|---|---|
| 层/槽位管理 | 按外形类型二选一：`sprite` 型持有当前应绘制的纸娃娃层集合（身体、发型、护甲各槽位、武器、坐骑等，随装备/外形变化事件更新，见 3.3.1）；`model` 型持有当前应装配的槽位网格集合（见 3.3.2）；来源均见第 7 节 DisplayInfo 映射 |
| 锚点/挂点查询 | 提供 3.3 节锚点（`sprite` 型）或挂点（`model` 型）的运行时查询，供特效/武器挂接使用 |
| 动画状态机驱动 | 驱动 4.2 节的动画状态机：`sprite` 型驱动序列帧动画（见 4.5）或程序动画原语，`model` 型驱动骨骼动画剪辑（经 `IRenderer3D.playAnim`，见 02） |
| 程序动画原语 | 提供一组不依赖具体美术资源的动画能力，供反馈绑定与动画状态机调用；最终落到各自的变换/材质参数接口：`sprite` 型作用于精灵变换（`IRenderer2D.setTransform`/`setShaderParam`），`model` 型作用于模型变换与材质参数（`IRenderer3D.setPlacement`/`setMaterialParam`） |

程序动画原语清单（拍板，命名固定，两种外形类型均适用，参数留白由具体引擎适配层解释）：

| 原语 | 说明 |
|---|---|
| move | 平移（跟随逻辑位置插值，非独立触发） |
| rotate | 旋转（用于倾倒、翻滚等） |
| scale | 缩放（用于命中缩放反馈、召唤特效等） |
| flash | 闪白（受击/无敌帧反馈） |
| trail | 拖尾（快速位移的视觉延迟） |
| stagger | 后仰（受击打断施法的短促位移反馈） |
| topple | 倾倒（死亡/眩晕倒地） |
| fade | 淡出（消失、隐身切换） |

（建议）原语的具体数值（时长、幅度、缓动曲线）建议做成 DisplayInfo 或 FeedbackBinder 动作参数里的可调项，不写死在代码里，便于同一原语在不同游戏呈现不同"手感"。

勘误补充两点实现级判断记录：① `sprite` 型外形如需复用 `display.anim_set`（04 第 7.1.1 节）的剪辑目录，不经 `display.map.anim_set_ref` 间接查找——该字段严格是 `model` 型专属，`sprite` 型记录填写会被数据校验判为错误；改由引擎适配层的装配代码构造一份"实体 id → 剪辑查表"的解析委托直接注入 CharacterRig，`display.anim_set` 本身仍是被消费的同一张表，只是引用路径与 `model` 型不同（不经 DisplayInfo 字段）。② CharacterRig 的"动画状态机驱动"/"程序动画原语"两项职责里，程序动画原语的时间轴推进（`update(dt)`）由表现帧驱动代码（引擎侧的渲染帧回调，通常与 3.3 节视图同步同一节奏）每帧调用一次；View 绑定协议本身（第 2 节）不承担这一步。

勘误（2026-09-08，[ADR-0017](adr/0017-模型型外形默认路线补齐与命中帧同步.md) 决策 b）：`model` 型 CharacterRig 已从"层/槽位管理、锚点/挂点查询抛不支持"的占位收口为真实实现——层/槽位管理经 `display.equip_visual`（04 第 7.1.2 节）应用：`slot_mesh` 模式经 `IRenderer3D.setSlotMesh` 替换槽位网格，`socket_attach` 模式创建子模型实例并经 `attachToSocket` 挂接；锚点/挂点查询按 `ModelInfo.Sockets` 是否声明该挂点返回声明性结果（声明存在返回零偏移占位、不存在返回未查到，真实的挂点世界坐标由具体 `IRenderer3D` 实现的骨骼系统决定，不是本接口能给出的精确值）；八项程序动画原语中，move/rotate/scale/stagger/topple 五项映射到 `IRenderer3D.setPlacement`（在最近一次基准姿态上叠加），flash/trail/fade 三项映射到 `IRenderer3D.setMaterialParam` 的固定参数名（`flash_intensity`/`trail_intensity`/`fade_alpha`）。可选接口 `IHitFrameEmitter` 提供 `HitFrameReached: Event<Id>` 事件成员（详见 4.3 节勘误；2026-09-08 二次勘误：不是 `ICharacterRig` 本身的强制成员，见 [ADR-0017](adr/0017-模型型外形默认路线补齐与命中帧同步.md)"修订记录"），`sprite`/`model` 两套实现均已提供。选用 `model` 型外形因此不再是"只能播放骨骼动画剪辑、其余能力抛异常"的半成品状态，引擎适配层只需要提供真实的 `IRenderer3D` 实现（决策 2）即可获得与 `sprite` 型对等的完整表现能力。

勘误（2026-09-08，游戏侧复核发现：model 路线动画状态机永久卡死）：`sprite` 型经 `IFrameAnimPlayer` 的"播放完成"回调把非循环剪辑（`attack`/`hit` 等瞬态状态）自然播完的信号接回 4.2 节动画状态机的回落机制；`model` 型此前没有对等通道，Attack/Hit/Cast 等瞬态状态播完后永不回落——本次收口补齐：`IRenderer3D` 追加义务条款（见 02 第 1.12 节勘误）"非循环剪辑自然播放完成时必须经 `onAnimEvent` 额外发出一次完成事件"，`model` 型 CharacterRig 的装配代码把这条完成事件接回动画状态机，与 `sprite` 型走的是同一套回落机制，只是事件来源不同。

### 4.2 动画状态

动画状态机的状态集合是拍板的最小可扩展集合，具体游戏可以在审批流程（见 [12_扩展与变更流程.md](12_扩展与变更流程.md)）下新增状态：

```
enum AnimState { idle, move, attack, cast, hit, death, jump }
```

- 状态切换由表现层依据订阅到的事件与只读运动状态自行决定，不由逻辑层直接下发"播放哪个动画"指令（逻辑层只知道"发生了施法/受击/死亡"，不知道播放第几号动画）。
- `attack` 与 `cast` 的具体动作剪辑由武器表现档案（见 4.4）决定，同一个 `cast` 状态在装备双手剑和装备法杖时可以播放完全不同的美术。
- 回落时机（2026-09-07 勘误）：`cast`（读条/引导）的视觉时长本就等于逻辑层的读条/引导时长，施法收尾（成功/失败/被打断）事件到达时该状态天然已经播完，由该事件直接驱动回落；`attack`（覆盖普攻与瞬发技能）不同——瞬发时"进入 attack"与"逻辑施法收尾"这两个事件在同一次逻辑派发批次内背靠背发出，若也靠收尾事件驱动回落，会让 `attack` 在同一帧内被切回待机/移动，对应的动作播放形态根本没有机会真正播出（违反 1. 表现层铁律"动画时长与逻辑结算独立"）；`attack` 因此改由动画播放完成的回调驱动回落，保证至少完整播放一遍。
- 重触发语义（2026-09-08 勘误，游戏侧复核发现：同一瞬态状态连续两次触发不重播）：瞬态状态（`attack`/`cast`/`hit`/`jump`）的"开始"类事件（再次进入攻击、再次受击等）若到达时状态数值与当前已相同（例如上一次 `attack` 播放尚未完成，第二次普攻又触发一次 `attack`"开始"事件），此前会被状态机当成"无变化"直接丢弃、不重播——对瞬态状态而言这是错误的：游戏行为确实又发生了一次，理应重播一遍完整剪辑（连击类玩法尤其依赖这一点）。动画状态机因此新增一类独立信号"重触发"，与真正的状态切换分开触发，消费方（动画剪辑解析/播放层）对两者调用同一套"解析剪辑并播放"逻辑——播放器对"再次播放同一剪辑"的既有语义就是从头重新播放，不需要额外机制。`idle`/`move` 等持续状态不适用本条，同状态重入保持幂等（移动方向不变不需要每帧重播一遍待机/移动剪辑）；`death` 终态同样不适用（进入终态后不再接受任何切换/重触发）。

### 4.3 命中帧同步规则

- Skill 的效果结算时机由规则层（见 [06_规则层_属性技能战斗AI.md](06_规则层_属性技能战斗AI.md)）按固定步长驱动，与表现层播放的动画剪辑时长天然不对齐；命中帧同步规则用于把"逻辑判定时刻"与"动画视觉命中时刻"对齐，避免"打击特效比动作快/慢半拍"。

同步策略（二选一，按武器表现档案/技能配置声明，建议默认值见括号）：

| 策略 | 说明 |
|---|---|
| logic_driven（建议默认） | 逻辑层在效果结算 tick 广播命中事件，表现层收到即播放命中反馈，动画剪辑本身不产出判定，只做视觉伴随；优点是逻辑确定性不受美术资源时长影响 |
| anim_keyframe_driven | 动画剪辑内标记一个"命中关键帧"：`model` 型经 `display.anim_set`（见 04 第 7.1.1 节）登记的关键帧事件、由 `IRenderer3D.onAnimEvent` 回调触发；`sprite` 型经序列帧剪辑的等效关键帧标记触发（见 4.5）。表现层在到达该帧时才触发命中反馈的播放（但不改变逻辑判定已经发生的事实，只影响视觉呈现的时间点，用于需要强"打击感"贴合的近战武器） |

无论哪种策略，**逻辑判定结果与时机永远由规则层按固定步长决定**，表现层的关键帧只调节反馈动作播放的呈现时刻，不得回退去改变已经结算的战斗结果。

勘误（2026-09-08，[ADR-0017](adr/0017-模型型外形默认路线补齐与命中帧同步.md) 决策 c、d）：`anim_keyframe_driven` 策略现已实际接通，不再是没有可观察效果的口味配置项。`sprite`/`model` 两种外形类型的动画事件统一为可选接口 `IHitFrameEmitter.HitFrameReached: Event<Id>`（2026-09-08 二次勘误：不是 `ICharacterRig` 本身的强制成员，见 [ADR-0017](adr/0017-模型型外形默认路线补齐与命中帧同步.md)"修订记录"；`model` 型经 `IRenderer3D.onAnimEvent` 命中固定的命中帧事件 id 触发）；反馈绑定（第 6 节）在该策略下消费本事件——`feedback.binding` 新增字段 `sync: "hit_frame"`（未提供该字段时，`event` 为 `combat.damage_dealt` 默认视为 `hit_frame`，其余事件默认不开启），声明为命中同步的规则，其全部动作延迟到攻击方的 `HitFrameReached` 事件到达后才一并播放，带超时兜底（默认 0.5 秒，超时即照常播放并记诊断，不无限期悬挂）。同一个逻辑事件命中多条命中同步规则时，全部规则的动作合并为一个批次、随同一次命中帧一起释放（不按规则各自拆开等待）；不同来源（如范围攻击命中的不同目标各自触发的事件）各自形成独立批次，按各自入队顺序逐批释放，不互相串扰。攻击方当前没有绑定 `ICharacterRig`（如无表现的战斗模拟）时立即播放，不等待。伤害/状态结算仍然只在事件到达那一刻由规则层结算一次，命中帧同步只延后反馈动作的播放时刻，不重复结算、不回退已结算的结果。

勘误（2026-09-08，第九方审核 `architecture/落地计划/audit-85f1f4f-20260908/` 动画剪辑事件登记契约差异根治）：`model` 型 `anim_keyframe_driven` 依赖的关键帧事件由具体消费方把 `display.anim_set.clips[*].events`（04 第 7.1.1 节）数据驱动地登记进对应剪辑资产（见 02 第 1.7 节 `animation_clip` 种类勘误）——该登记动作必须与剪辑资产已有（美术自带）的关键帧事件合并，不得整体覆盖丢弃；若同一份剪辑资产（同一 `resource_ref`）被声明了不同事件配置的多个 `display.anim_set` 共同引用，登记时必须按各自的 `display.anim_set` 隔离生效范围，不允许其中一个 anim_set 的事件配置覆盖、决定其它 anim_set 实际看到的关键帧事件——这是 `anim_keyframe_driven` 策略"命中帧经关键帧事件触发"这一既有语义天然要求的合并/隔离细节补充说明，不是新增字段或新增策略。

### 4.4 武器表现档案决定普攻动作与技能特效变体

- 武器表现档案登记在 `display.weapon_style`（见 04），是 DisplayInfo 体系的一部分（见第 7 节），把"逻辑上的一次普攻/一次施法"映射到"具体应该播放哪一套动作剪辑与挂点特效"；它与 07 `item.template.weapon_profile`（伤害、攻速、学派等数值定义）是两张分开的表——武器的数值侧与表现侧互不干扰。
- 关联方式：`item.template` 经其 `display_ref` 指向的 `display.map` 行携带 `weapon_style_ref: Optional<Id>` 字段（见 04 第 7.1 节），指向具体的 `display.weapon_style` 行；换装备只改 `display.map`/`display.weapon_style` 的数据行，不改任何逻辑数据。
- 字段表：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| id | Id | 是 | 武器表现档案 id |
| auto_attack_anim | Id | 是 | 普攻动作剪辑引用 |
| cast_anim_override | Map<Id, Id> | 否 | 按技能 id 覆盖施法动作剪辑 |
| swing_vfx | Optional<Id> | 否 | 挥舞轨迹特效 |
| impact_vfx_override | Map<Id, Id> | 否 | 按技能 id 覆盖命中特效 |

- 逻辑层的 Skill 定义（06）只声明"这是一个近战/远程/法术类技能"，具体动作与特效变体查表得到，换装备不改任何逻辑数据。
- `model` 型外形下，`impact_vfx_override` 指定的命中特效挂到相应挂点（`display.map` 的 `sockets`，经 `IRenderer3D.attachToSocket`），而非纸娃娃锚点。

勘误（2026-09-08，[ADR-0017](adr/0017-模型型外形默认路线补齐与命中帧同步.md) 决策 e、f）：新增表现层契约"实体 → 武器风格引用"查询 `IWeaponStyleSource.getWeaponStyleRef(entityId): Optional<Id>`，补齐"给定一个实体，它现在算哪一个 `weaponStyleRef`"这一前置查询——默认实现按装备变化事件（`item.equipped`/`item.unequipped`）失效缓存，取该实体主手武器的物品模板 id 后经上文"关联方式"同一条链路（物品模板对应的 `display.map` 行 `logical_id` 就是该模板 id 本身）解析出 `weaponStyleRef`；未新增任何数据表字段，`display.map.weapon_style_ref` 已足以承载这条关联。此外，`AnimStateMachine` 的状态切换事件新增 `StateChangedWithSkill: (entityId, from, to, triggerSkillId: Optional<Id>)`，与既有三元组事件同一次切换背靠背触发，`triggerSkillId` 只在由施法开始事件驱动的切换（进入 `attack`/`cast`）时非空，支持按技能 id 查 `cast_anim_override`；既有三元组事件签名不变。

勘误（第十二轮审核 ac3b622，2026-09-09，`architecture/落地计划/audit-ac3b622-20260909/`
PRES-110-01 根治）：上一条勘误"默认实现按装备变化事件（`item.equipped`/`item.unequipped`）失效
缓存"未覆盖读档场景——存档系统的"读档不是业务事件"抑制作用域会丢弃读档期间重放装备联动时正常
派发的这两个事件，缓存因此收不到失效通知；补一句：默认实现同时订阅存档系统"读档完成"事件
（该事件在抑制作用域外正常派发），收到后整表清空缓存，保证同图读档后下一次查询按当前真实装备
状态重新解析，不复用读档前的旧值。不改变 `IWeaponStyleSource` 接口本身的签名，只是补全默认实现
的失效时机描述。

### 4.5 序列帧动画预留接口（sprite 型专用）

为兼容未来可能引入的逐帧美术资源（区别于程序动画驱动的骨骼/层动画），预留最小接口，不在本架构展开实现；本接口仅用于 `sprite` 型外形，`model` 型的骨骼动画播放经 `IRenderer3D.playAnim`（见 02 第 1.12 节）：

```
interface FrameAnimPlayer {
  play(clipId: Id, loop: Bool, speed: Number): void
  stop(): void
  onComplete(callback: Handle): void
  onAnimEvent(callback: Handle): void        // 勘误新增：与 model 型 IRenderer3D.onAnimEvent 对称，
                                               // 服务 4.3 节 anim_keyframe_driven 命中帧同步策略
}
```

序列帧资源同样经 DisplayInfo 映射得到 clipId，不在逻辑表里出现资源路径；序列帧剪辑的关键帧标记
（命中帧等，见 4.3 节）是运行期值对象字段，04 未给序列帧资源定义独立数据表 schema，不经
`DataRegistry` 落地，由具体游戏的表现层装配代码构造后注入。

| attach_mode | `world｜anchor｜socket｜screen` | 是 | 世界坐标播放 / 挂接到 sprite 型锚点跟随 / 挂接到 model 型挂点跟随 / 屏幕空间播放 |
| lifetime | Number | 否 | 预期存活时长，用于对象池回收兜底 |
| resource_ref | Id | 是 | 指向具体引擎资源的间接引用，由适配层解释；粒子呈现为 2D 面片还是 3D 粒子由适配层依据目标外形类型与美术资源决定，本表不区分 |

- **跟随的实现现状**（2026-09-10 勘误，第十四轮审核根治）：`socket` 挂接目标提供真实模型句柄时，播放器经引擎适配层做真正的父子挂接（子实例的引擎侧变换随父挂点持续变化），天然持续跟随，不需要播放器每帧介入。`anchor` 挂接、以及 `socket` 挂接目标没有可用模型句柄时按既有约定降级为 world 播放——这两种情形下播放器需要每帧重新解析一次挂接目标当前位置并把已发射的粒子实例移动过去，才能做到"跟随"；这一步依赖引擎适配层按需提供的可选能力（"重新定位一个已发射的粒子实例"），未提供该能力时退化为生成那一刻定位一次、此后静止，是允许的能力降级，不是本表契约的缺口。

### 5.2 sfx 表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| sfx_id | Id | 是 | 音效逻辑 id |
| layer | String | 是 | 分层音效轨道（如 战斗/环境/UI/语音，供混音分组） |
| priority | Int | 否 | 同轨道抢占优先级 |
| variants | List<Id> | 否 | 多个随机变体资源引用，播放时随机挑一个避免重复感 |
| resource_ref | Id | 是 | 指向具体引擎资源的间接引用 |

### 5.3 播放器接口

```
interface VfxPlayer {
  spawn(vfxId: Id, at: Vec2 | AnchorRef, params: Map<String, Number>): Handle
  stop(handle: Handle): void
  update(dt: Number): void            // 推进对象池，到达 lifetime 的播放实例自动回收（见第 5.4 节）
}

interface SfxPlayer {
  play(sfxId: Id, at: Optional<Vec2>): Handle
  stop(handle: Handle): void
  setLayerVolume(layer: String, volume: Number): void
  setLayerMuted(layer: String, muted: Bool): void   // 静音/取消静音某条分层轨道（见第 5.5 节）
  update(dt: Number): void            // 推进冷资源首次加载的挂起播放请求，超时后自动丢弃（勘误见下）
}

interface AudioLayerVolumeHost {                      // 分层音量宿主（见第 5.5 节）：设置面板读写各层音量的统一归口
  layers: List<String>                                // 可调层清单：sfx 表 layer 去重 + "music"，顺序稳定
  getVolume(layer: String): Number                    // 未知层返回 1.0（默认满音量，不报错）
  setVolume(layer: String, volume: Number): void      // "music" 经 IAudio.setBusVolume 应用，其余层经 SfxPlayer.setLayerVolume 应用；随后持久化为设置项 audio.volume.<layer>
}
```

- `SfxPlayer.play` 的 `at` 参数经 `IAudio.playSfx` 的 `position: Optional<Vec2>` 参数传递到引擎适配层（见 02 第 1.4 节），为空时按无空间衰减方式播放。

勘误（2026-09-11，第十八轮审核 PRES118-SFX，12 §5 细节勘误，结论不变）：`SfxPlayer.update(dt)` 此前未列入本节接口伪代码，但实现层一直需要它——冷资源首次引用未加载完成时排队等待（见第 5.1 节资源引用），若此后没有新的 `play` 调用触发惰性超时扫描，挂起请求会永久卡住；`VfxPlayer.update`/`SfxPlayer.update` 与 `FeedbackBinder` 队列推进三者同属"每帧必须驱动、不受当前是否处于游戏内状态门槛限制"的一组维护步骤，装配根应当把三者收敛为一处统一调用（例如装配层暴露的单一"逐帧维护"入口），而不是各个生产装配入口各自罗列这份清单——由多处分别罗列的做法已实测出现过遗漏其中一项的情形。

### 5.4 对象池

- VFX/SFX 播放实例一律经对象池复用，避免每帧分配（呼应 [11_工程规范与测试.md](11_工程规范与测试.md) 性能约定）；池的容量、回收策略（按 lifetime 超时回收/按 category 分池）由引擎适配层实现，接口对上层透明。

### 5.5 分层音效

- 音效按 `layer` 分组，每层可独立调节音量、独立静音（用于设置面板"音效/音乐/语音"分别调节）。
- 设置面板不直接调用 `SfxPlayer.setLayerVolume`/`IAudio.setBusVolume`，而是经 `AudioLayerVolumeHost`（第 5.3 节）读写各层音量；该宿主负责把写入持久化为设置项 `audio.volume.<layer>`（落盘经 [10_存档与持久化.md](10_存档与持久化.md) 第 7 节的设置文件），下次构造时自动恢复，使"音量从哪来、写到哪去、重启后能否恢复"只有一个归口。
- 同层音效遵守 `priority` 抢占规则，避免同一时刻大量音效叠加导致爆音（口味相关的抢占阈值为可配置项）。
- "设置"面板（见第 7.1、9 节）展示的音量分层清单、读音量与持久化，经一个收敛了"层清单 + 读 + 写"
  的音量宿主契约提供（层清单 = 全部 `sfx.def.layer` 去重后再加一条音乐总线；写入按分层 key 持久化
  到设置存储；除音乐总线经 `IAudio` 的总线音量接口外，其余分层写入即落到本节 `SfxPlayer.setLayerVolume`/
  `setLayerMuted`），UI 侧不需要各自维护一份平行的层清单或构造期回调。

### 5.6 经 DisplayInfo 映射

- 逻辑层触发"播放某效果的命中反馈"时，只携带逻辑 id（技能 id、光环 id、物品 id 等），不携带任何 vfx_id/sfx_id；表现层经 DisplayInfo（第 7 节）查表得到具体 vfx_id/sfx_id 后再调用播放器接口，从而保证换皮肤/换美术资源不触碰逻辑表。

## 6. 反馈绑定 FeedbackBinder

FeedbackBinder 是表现层里把"逻辑事件"翻译为"一组具体表现动作"的规则引擎，是 09 与 04（Expr）、06（事件词汇表）三者的交汇点。

### 6.1 规则格式

```
FeedbackRule {
  event: EventKey            // 订阅的事件类型，如 combat.damage_dealt, combat.missed, aura.applied
  condition: Expr            // 使用全架构唯一条件语言（见 04），可查询事件携带的数据
  actions: List<FeedbackAction>
}

FeedbackAction =
    FloatingText(styleId: Id, textSource: TextSource)
  | PlayVfx(vfxId: Id, attach: AttachSpec)
  | PlaySfx(sfxId: Id)
  | Freeze(durationMs: Number)          // 顿帧
  | ShakeCamera(profileId: Id)          // 震屏
  | Flash(profileId: Id, target: source|target)   // 闪白（勘误补 target，无 world 选项）
```

- 一条规则可以绑定多个动作（例如一次暴击命中 = 飘字 + 命中特效 + 音效 + 轻微顿帧）。
- `condition` 让同一个事件类型可以按数据分支出不同表现（例如 `combat.damage_dealt` 事件按 `event.is_crit`、`event.school` 等字段分流到不同飘字样式/特效变体）。
- `ShakeCamera(profileId: Id)` 引用的震屏预设携带强度、时长、频率三项字段，一一对应 `ICamera.shake(intensity, durationSeconds, frequency)` 的三个参数（见 02 第 1.13 节）。

### 6.2 飘字样式表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| style_id | Id | 是 | 样式 id |
| color_ref | Id | 是 | 颜色引用（正常伤害/暴击/治疗/闪避文案各自配色，具体色值由表现资源管理，不在本表写死颜色值） |
| size_scale | Number | 否 | 相对基础字号的缩放 |
| motion_profile | Id | 否 | 飘字运动曲线引用（上浮/抖动/聚合等） |

### 6.3 合并规则

- 短时间窗口内同源同类型的多条飘字（如多段伤害的技能在同一 tick 内命中多个目标，或一次多跳伤害）按合并策略聚合展示，避免刷屏；合并窗口时长、合并展示形式（求和后单条 / 简单折叠为"xN"）为可配置项。
- 合并只影响表现层展示，不影响战斗结算与战斗日志事件本身的独立记录（见 06、10 的回放需求，事件流必须保持原始粒度）。

### 6.4 离散模式下的动作回放

离散模式下（见 03 第 3.2 节），一个离散步在 `WorldSim.tick` 内可能瞬间产生多条事件（动作、飘字、特效等）；表现层按事件顺序把这些事件放入一个本地播放队列，逐条顺序回放（依次触发对应的 `FeedbackAction`），不并行播放、不打乱事件间的因果顺序。

- **加速与跳过**：队列的播放速度（加速倍率）与是否允许整体跳过是表现层本地设置，不改变已经结算的战斗结果，也不改变事件流的记录粒度（呼应 6.3 节）。
- **回放完毕**：队列清空、且没有任何表现动作（特效/音效等）仍在等待首次异步加载完成（2026-09-07
  勘误：原表述只提到"队列清空"，未覆盖表现资源首次异步加载仍在进行中的情形——`play_vfx`/
  `play_sfx` 引用尚未加载完成的资源时立即返回、不阻塞队列，若只看队列是否清空会把仍在加载中的
  特效/音效误判为"已经播完"）后，表现层发出 `presentation.playback_finished` 事件；若当前
  `PacingPolicy.mode()` 为 `wait_for_playback`，主循环收到该事件后调用
  `PacingPolicy.onPlaybackFinished()`（见 03 第 9 节）解除 `playing_back` 子态（见 03 第 2 节），
  推进下一离散步；若为 `immediate`，主循环不等待此事件也会继续推进，播放队列在后台按自己的节奏
  播完——播放队列本地设置为"不排队、逐条立即执行"时同样不主动发出本事件（呼应"表现层只订阅"），
  但命中仍在异步加载中的资源时仍应在该资源加载完成的那一刻补发一次本事件，避免曾经因为等待
  加载而关闭的节奏门永远等不到解除信号。
- 该事件不携带、也不允许携带任何会被 L0 解释为"逻辑判定"的数据，只作为节奏门的解除信号，符合表现层铁律 P2、P3。

## 7. UI 框架

### 7.1 组成

UI 框架覆盖以下界面单元，具体游戏可以裁剪不用（例如没有目标框机制的游戏可以不接入目标框模块），但接口形状统一：

HUD、动作条、状态栏、目标框、背包与装备、任务日志、对话框、商店、菜单、设置、按键绑定面板、回合顺序条（仅离散模式）、行动点显示（仅离散模式且启用 `action_points` 先攻策略）、"结束回合"意图按钮（仅离散模式，提交给 `TurnScheduler.endTurn`，见 03 第 3.2 节）。

### 7.2 数据来源与绑定方式

- 所有 UI 面板只依赖两类输入：对 WorldSim 的只读查询（呼应铁律 P1）与事件订阅（呼应铁律 P2）；UI 不持有可写的游戏状态副本。
- 数据绑定方式采用"查询 + 订阅刷新"模型：

```
interface UiDataSource {
  query(path: String): Any                 // 只读快照查询，如 "player.power.mana.current"
  subscribe(eventKey: EventKey, handler: Handle): SubscriptionId
  unsubscribe(id: SubscriptionId): void
}
```

- **读档场景的补充规则**（2026-09-09 勘误，与第 4.4 节 `IWeaponStyleSource` 缓存失效时机同一判断记录）：存档系统"读档不是业务事件"的抑制作用域（见 [10_存档与持久化.md](10_存档与持久化.md)）会连带丢弃读档期间各业务系统正常触发的增量事件本身的派发；只按业务事件订阅刷新的 UI 面板，在同图读档场景下会因此收不到任何刷新信号，停留在读档前的旧快照上（与已经是读档后新状态的 `UiDataSource.query` 结果不一致）。任何维护派生展示状态（不是每次都重新 `query`，而是订阅事件后增量更新一份本地缓存/快照）的 UI 面板，除已有的业务事件外，都必须额外订阅存档系统"读档完成"事件（该事件在抑制作用域外正常派发），收到后做一次整体重建，保证同图读档后无需调用方手动干预即与查询到的当前真实状态一致；重复收到"读档完成"事件（如迁移紧接读档两次派发）只是多刷新一次，应保持幂等、不重复订阅。

- UI 控件对用户输入的响应，一律封装为"意图请求"经窄契约提交（例如背包面板的"使用物品"点击，提交 `UseItemIntent(itemInstanceId)` 给玩法层，不直接改变背包数据），呼应铁律 P3。

### 7.3 主题与字体、本地化接入

- 主题（配色、控件皮肤）与字体是表现资源，经引擎适配层的 UI 承载面接口装载，本架构不规定具体主题方案。
- 文案一律经本地化表（见 [04_数据与内容管线.md](04_数据与内容管线.md) 本地化一节）用 key 间接引用，UI 层不硬编码任何面向玩家的文本字符串。

## 8. 镜头

镜头职责与配置项已在 3.5 节说明，全部操作经引擎适配层的 `ICamera` 接口完成（见 02 第 1.13 节）；本节补充镜头与 UI/输入的关系：镜头切换（如对话演出时的过场镜头、锁定 Boss 的战斗镜头）由玩法层通过事件/钩子触发并调用 `ICamera.configure`/`follow`/`setZoom`，表现层负责具体运镜表现，镜头系统本身不产生玩法判定（例如"镜头能否看到目标"不用于战斗合法性判断，合法性判断只用逻辑层的视线查询，见 05）。

勘误（2026-09-11，第十八轮审核 PRES118-CAMERA，12 §5 细节勘误，结论不变）：场景加载完成后是否重置跟随目标、重置后跟随谁，都是可替换策略（见第 3.5 节"跟随策略、边界规则"配置项），但"策略可替换"不等于"默认不接线"——装配根默认启用镜头自动配置（构造期即 configure+follow 玩家单位）时，理应在场景加载完成后同样默认重新建立跟随目标，不能让镜头在切图/读档后静止不动、需要每个具体游戏自己重新接一遍这条默认链路；场景路由的"加载完成回调"与"加载完成事件"两个时机可能不一致（例如加载完成事件在回调之后才派发），装配根若要在回调里提前重新指定跟随目标，必须确保这一步不会被随后到达的加载完成事件的默认重置覆盖掉——可靠做法是把"重置后立即重新指定"收在镜头系统自己响应该事件的同一次处理内完成，不依赖调用方猜测两个时机的先后顺序。

| FeedbackBinder 规则引擎 | 是 | 具体反馈规则数据、飘字样式 |
| UI 框架接口与数据绑定方式 | 是 | 具体界面视觉、主题、布局 |
| Shell 流程骨架 | 是 | 具体菜单内容与美术 |

## 验收标准

1. 表现层任意模块的实现可以指出其满足 P1~P4 中的哪一条、如何满足，且没有反例（无直接改写逻辑数据的代码路径）。
2. 给定一份 DisplayInfo 数据与一份反馈规则数据，能够不改任何代码，让同一套逻辑技能在不同游戏里呈现完全不同的动作、特效与音效。
3. 关闭表现层（不创建任何 View）后，WorldSim 仍可独立 tick 并产出与开启表现层时一致的战斗日志事件序列。
4. 新增一个动画状态或一个程序动画原语，能在文档中定位到"是否需要走审批流程"的判断依据（见 [12_扩展与变更流程.md](12_扩展与变更流程.md)）。
5. 同一逻辑单位可在 `sprite` 型与 `model` 型外形间切换而不改逻辑数据，只改 `display.map` 与相关表现资源行（`ICharacterRig`/`DisplayInfo.Kind` 两套实现并存、按数据驱动选择分派）。勘误（2026-09-08，[ADR-0017](adr/0017-模型型外形默认路线补齐与命中帧同步.md) 决策 b，收紧此前措辞）：`model` 型 `CharacterRig`（表现层引擎无关部分）与"选用 model 型外形"两件事本身不再是可选投入——表现层已提供真实实现；只有"要不要选 model 型外形"这一层选择是游戏层决策，一旦选择 model 型，引擎适配层就必须提供 `IRenderer3D` 的真实实现（网格与骨骼动画资源），只有游戏全程只使用 `sprite` 型外形时才允许不提供 `IRenderer3D` 真实实现。
