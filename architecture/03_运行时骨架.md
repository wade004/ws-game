## 1. 应用生命周期

应用级状态机由 L0 基础层的应用生命周期模块（`core/foundation/app_lifecycle`）驱动：

```
Boot → MainMenu → Loading → InWorld ⇄ Pause
                     ↑           │
                     └───────────┘（场景切换时经 Loading 中转）
```

`InWorld` 内部还有一组子状态，由玩法层与输入共同驱动，彼此互斥（同一时刻只处于其中之一）：

```
Explore ⇄ Combat
   │  ⇄ Dialog
   │  ⇄ MenuOverlay
   └─ ⇄ Cutscene
```

## 2. 状态机表

| 状态 | 进入条件 | 允许转移到 | 谁驱动 |
|---|---|---|---|
| Boot | 应用进程启动 | MainMenu | L0 应用生命周期：完成基础系统初始化（数据注册表加载、引擎适配层就绪）后自动转移 |
| MainMenu | Boot 完成，或从 InWorld/Pause 选择"返回主菜单" | Loading（新游戏/读档）、退出应用 | L5 游戏外壳 Shell 响应玩家在菜单上的选择 |
| Loading | MainMenu 发起新游戏/读档，或 InWorld 内发起场景切换 | InWorld、MainMenu（加载失败时） | L0 场景路由 SceneRouter：加载完成后自动转移；加载失败由场景路由驱动回退 |
| InWorld | Loading 完成 | Pause、MainMenu（读档/退出到主菜单）、Loading（切换场景） | 默认由 SceneRouter 转入；退出由输入或存档流程驱动 |
| Pause | InWorld 内触发"暂停"动作，或窗口失焦（是否自动暂停为可配置项） | InWorld（取消暂停）、MainMenu（确认退出当前存档） | L0 应用生命周期响应输入映射产生的暂停动作 |
| Explore（InWorld 子状态） | InWorld 默认子状态，或其余子状态结束后回落 | Combat、Dialog、MenuOverlay、Cutscene | 由触发对应子状态的模块事件驱动（见下方） |
| Combat（InWorld 子状态） | 战斗系统发出 `combat.entered` | Explore（`combat.left` 时） | L2 战斗系统 Combat |
| awaiting_input（Combat 内子态，仅离散模式） | 离散模式下轮到玩家行动，`TurnScheduler.nextStep()` 暂无步产出 | Combat 正常推进（玩家提交意图或"结束回合"意图后） | L0 回合调度器 TurnScheduler，见 3.2 |
| playing_back（Combat 内子态，仅离散模式） | 一个离散步产生的事件序列正在由表现层排队回放，`PacingPolicy.mode() == wait_for_playback` | Combat 正常推进（收到 `presentation.playback_finished` 后） | L0 节奏策略 PacingPolicy，见 3.2 |
| Dialog（InWorld 子状态） | 对话系统发出 `dialog.gossip_opened` 或 `dialog.story_node_entered` | Explore（`dialog.ended` 时） | L4 对话系统 Dialog |
| MenuOverlay（InWorld 子状态） | 玩家触发"打开菜单"动作 | 回落到触发前的子状态（Explore 或 Combat） | 输入映射 + UI 框架 |
| Cutscene（InWorld 子状态） | 剧情节点或遭遇阶段触发过场演出 | Explore（过场结束时） | L4 对话/遭遇模块 |

子状态之间允许有限的叠加（例如 Combat 中打开 MenuOverlay），具体叠加规则由游戏层通过 `core/foundation/app_lifecycle` 提供的状态栈机制配置，本文档只规定互斥的默认关系。`awaiting_input`、`playing_back` 是 Combat 内部按时间模型产生的附加子态，只在战斗时间模型为离散时出现，连续模式下 Combat 不进入这两个子态。

## 3. 主循环与时间模型

核心模拟由 L0 的 `core/foundation/sim_loop` 驱动，`WorldSim.tick` 的唯一输入是一个模拟步 `SimStep`；时间模型决定这个模拟步如何产生，是 L0 的可替换策略：**连续模式**（`SimStep` 携带固定的经过秒数，是探索与战斗的默认模式）与**离散模式**（`SimStep` 携带当前行动者与阶段，由回合调度器按先攻规则产生）。两种模式共享 4.2 节规定的同一套 tick 顺序，保证同种子同输入产生同结果。

### 3.1 连续模式

连续模式采用**累积器模式**：

1. 每次 `IClock.onFrame` 触发，取得本次真实经过时间 `realDeltaSeconds`。
2. 若处于慢动作，先将 `realDeltaSeconds` 乘以时间缩放系数；若处于暂停，则本步跳过第 3~4 步（不产生任何模拟推进），但仍处理界面动画等真实时间驱动的表现。
3. 将（可能已缩放的）时间累加进累积器 `accumulator`。
4. 当 `accumulator >= stepSeconds` 时，循环调用一次 `WorldSim.tick(Continuous{dt: stepSeconds})` 并从累积器中扣减 `stepSeconds`，直到 `accumulator < stepSeconds`；为避免长时间卡顿后追赶步数过多导致的"死亡螺旋"，单帧最多执行 `maxCatchUpSteps` 次 tick，超出部分的时间直接丢弃而不追赶。
5. 循环结束后，`accumulator / stepSeconds` 得到插值系数 `alpha`（范围 0~1），交给表现层的视图绑定用于在"上一 tick 状态"与"本 tick 状态"之间做位置等插值渲染，从而在固定步长模拟与可变帧率渲染之间获得平滑画面。

要点：

- **暂停** = 不调用 `WorldSim.tick`，累积器也不再增长；真实时间驱动的 UI 动画、菜单交互不受影响。
- **慢动作** = 对进入累积器之前的 `realDeltaSeconds` 做缩放，只影响模拟推进速度，不影响 `IClock.now()` 返回的真实时间。
- **步长可配置**：`stepSeconds` 与 `maxCatchUpSteps` 都是 `core/foundation/sim_loop` 暴露的配置项，默认步长对应每秒 60 次模拟，具体数值由游戏层按需调整。

### 3.2 离散模式

离散模式下模拟不再按真实时间累积推进，而是由**回合调度器 TurnScheduler**（`core/foundation/sim_loop` 内的子组件）按先攻规则维护本回合的行动顺序，逐个产生离散步：

1. `TurnScheduler.beginCombat(participants)` 在进入离散模式时按先攻策略（`initiative_stat`、`action_points`、`fixed_order`，预留 `atb` 作为后续扩展位不展开）计算并维护本轮行动顺序。
2. 主循环每次询问 `TurnScheduler.nextStep()`：若当前行动者是非玩家（AI 或环境行动），返回一个 `Discrete{actorId, phase}` 步供 `WorldSim.tick` 处理；若轮到玩家行动，调度器不产出步、应用状态机进入 `awaiting_input` 子态（见第 2 节），主循环照常驱动表现与 UI，但不推进模拟。
3. 玩家经窄契约调用 `TurnScheduler.submitIntent(actorId, intent)` 提交本次行动意图（或调用 `endTurn` 提交"结束回合"意图）后，`awaiting_input` 解除，调度器据此产生对应的离散步。
4. 一个离散步在 `WorldSim.tick` 内可能瞬间产生多条事件（动作、飘字、特效等）；节奏策略 **PacingPolicy** 决定调度器是否等待表现层回放完毕再推进下一离散步：`immediate`（不等待，是连续模式的默认节奏，离散模式也可选用）或 `wait_for_playback`（离散模式默认，应用状态机进入 `playing_back` 子态，直到表现层发出 `presentation.playback_finished` 才推进）。
5. 一名行动者的行动结束（主动 `endTurn`，或按先攻策略判定的回合结束条件——如 `action_points` 策略下行动点耗尽）后，`TurnScheduler` 切到顺序中的下一行动者；一轮全部行动者结束后发出 `sim.round_ended`，并按先攻策略决定是否重排下一轮顺序。
6. 回放 = 意图序列：无论连续还是离散模式，存档与重放只记录意图，`awaiting_input` 与 `wait_for_playback` 只影响推进节奏，不改变确定性。

### 3.3 模式切换流程

探索与战斗各自声明时间模型（`exploration_time_model`、`combat_time_model`，见 04 `found.time_model`），三种合法组合：即时/即时（默认）、即时/回合、回合/回合。

1. `combat.entered` 事件发出时，若 `combat_time_model` 为 `discrete` 且当前是连续模式，主循环切换到离散模式：暂停累积器推进，调用 `TurnScheduler.beginCombat(participants)`，此后模拟推进改由 3.2 节描述的离散步序列驱动；若 `combat_time_model` 与 `exploration_time_model` 相同，则不发生模式切换。
2. 切换时刻做一次时间单位换算：进入回合制时，正在生效的光环等以秒计的剩余时长按 `seconds_per_turn`（见 04）折算为剩余回合数；反之，退出回合制、切回连续模式时按同一系数把剩余回合数折算回秒。
3. `combat.left` 事件发出时，若当前处于离散模式，调用 `TurnScheduler.endCombat()`，主循环切回连续模式的累积器推进；遭遇定义也可通过 `combat_mode_override`（见 08）覆盖默认的 `combat_time_model`。
4. 模式切换只改变"模拟步如何产生"，不改变 4.2 节的 tick 顺序、不引入第二套战斗系统；规则层对切换本身无感知，只感知"经过了多少时间单位"。

## 4. WorldSim 结构与 tick 顺序

### 4.1 WorldSim 包含的集合

| 集合 | 说明 |
|---|---|
| Units（`PlayerUnit` / `CreatureUnit`） | 玩家单位与生物单位，具备属性、资源池、可施法/被施法能力 |
| GameObjects | 场景中的可交互物件（箱子、门、机关等） |
| Projectiles | 有独立弹道与生命周期的抛射物逻辑对象 |
| AreaTriggers | 绑定在空间区域上的触发器逻辑对象 |
| DroppedLoot | 已生成但尚未被拾取的掉落物 |
| WorldState 标志字典 | 命名空间化的世界状态标志，见 `05_对象模型与世界.md` 第 8 节 |
| 空间索引 | 供 `ISpatialQuery` 使用的内部索引结构，随集合变化增量更新 |

### 4.2 每个 tick 的处理顺序

每次 `WorldSim.tick` 的输入是一个 `SimStep`（`Continuous{dt}` 或 `Discrete{actorId, phase}`，见第 3 节）；下方八步顺序在两种模式下完全一致，差异只集中在两步：步骤 1"输入意图收集"在离散步下只收集当前行动者 `actorId` 的意图，其余单位不产生意图；步骤 4"移动与导航"在离散步下按该行动者的每回合移动预算（距离或行动点，见 06）结算位移，而非按连续时间的速度积分。

```
输入意图收集 → AI 决策 → 技能管线 → 移动与导航 → 战斗结算 → 触发评估 → 事件派发 → 生命周期清理
```

| 步骤 | 内容 |
|---|---|
| 1. 输入意图收集 | 把上一帧经 `InputMap` 转译出的玩家动作，整理为本 tick 的"意图"列表（移动意图、施法意图、交互意图等），与 AI 产生的意图使用同一种意图数据结构 |
| 2. AI 决策 | L2 的 AI 模块基于行为外壳状态机与优先级表，为非玩家单位（以及可选的玩家辅助施法策略）生成本 tick 的意图，追加进意图列表 |
| 3. 技能管线 | 对本 tick 全部施法类意图执行 `CastPipeline`：校验、消耗资源、读条推进、结算效果与光环变化，产出的伤害/治疗等结果先记录、暂不即时应用 |
| 4. 移动与导航 | 处理位移类意图，结合 `INavigation2D` 与碰撞判定更新单位位置 |
| 5. 战斗结算 | 对步骤 3 产出的效果结果执行 `Resolver`：命中判定、护甲减免、吸收免疫、最终生命值/资源变化，并更新仇恨表 |
| 6. 触发评估 | 用 `Expr` 求值区域触发器进入/离开条件、遭遇阶段推进条件、任务目标更新条件、成就 criteria 等；交互意图（`kind = "interact"`，`args` 含目标物件实例 id，见第 1 步）在本步由载体层的物件宿主（`GameObjectHost`，见 07 第 3.6 节）消费——按 `on_use` 类型分发前先用 `Expr` 校验 `gobj.lock` 的开锁条件（world 标志/持有物品/属性数值三种 `requirement` 之一），与本步其余条目同属"读取当前状态、求值条件、决定是否触发"的模式；处理结果（对象状态变化、掉落生成等）经事件派发（见第 7 步） |
| 7. 事件派发 | 把本 tick 累积的全部事件通过 `EventBus` 统一派发给订阅者，包括表现层的 `FeedbackBinder`、`ViewBinder` 等 |
| 8. 生命周期清理 | 处理本 tick 中被标记为待销毁的实体（死亡单位、过期抛射物、已拾取掉落物等），真正从集合中移除并发出 `entity.destroyed` |

固定顺序的意义：保证同一 tick 内"意图 → 效果 → 结算 → 触发 → 事件 → 清理"的因果链清晰可追溯，也是"同种子同输入同结果"确定性要求的基础。

## 5. 逻辑对象与 View 的绑定协议

- **创建**：`WorldSim` 在把一个新逻辑对象加入集合时发出 `entity.created` 事件，携带实体 id、实体类型与用于查询外形的逻辑 id；L5 的 `ViewBinder` 订阅该事件，经 `DisplayInfo` 取得表现资源引用，创建对应的 View 实例并维护"实体 id → View"的映射表。
- **同步**：View 只在事件派发阶段通过订阅的事件（例如 `unit.moved`、`unit.state_changed`、`aura.applied`）更新自身可视状态；View 允许在渲染帧之间调用只读查询接口（例如取当前逻辑位置用于第 3 节的插值渲染），但不得调用任何会改变逻辑状态的方法——这是"L5 对其余层只读、只订阅事件"规则在运行时骨架层面的具体落实。
- **销毁**：`WorldSim` 在生命周期清理阶段真正移除某实体前发出 `entity.destroyed` 事件；`ViewBinder` 订阅后销毁对应 View（可以先播放死亡/消失动画再真正释放表现资源，动画时长由 View 自行管理，不阻塞逻辑层已经完成的实体移除）。

## 6. 场景路由

地图/场景切换的标准流程：

1. 触发方（Shell 的"新游戏/读档"或 InWorld 内的传送/地图边界）调用 `SceneRouter.loadScene(sceneId)`。
2. 应用状态机转入 `Loading`。
3. `SceneRouter` 依据 `world.map` 确定本场景需要的数据表与资源引用，经 `IResourceLoader` 异步加载。
4. 若是从一个已存在的 `InWorld` 场景切换而来，先触发 `pre_unload` 钩子（存档系统若配置为"切换场景时自动存档"，在此处完成持久化），再卸载旧场景的 `WorldSim` 集合与全部 View。
5. 依据新场景的 `Spawn` 刷新规则与当前 `WorldState` 构建新场景的 `WorldSim` 初始状态。
6. 加载与初始化完成后，应用状态机转入 `InWorld`，触发 `post_load` 钩子，并派发 `scene.load_finished` 事件（镜头、UI、View 绑定据此各自完成初始化）。

`pre_unload`/`post_load` 是 `SceneRouter` 暴露给 `HookRegistry` 的挂载点，存档系统、游戏层自定义逻辑都可以在这两个时机注册回调；加载画面的具体呈现方式由游戏层通过 `presentation/shell` 提供，架构只保证加载流程本身的时序正确。

## 7. 输入映射

动作集（要映射哪些游戏动作）由游戏层通过数据表 `found.input_action` 声明；架构（`core/foundation/input_map`）提供的通用能力包括：绑定解析（把物理输入事件转译为动作事件）、重绑定（运行时修改某动作的物理绑定）、冲突检测（同一物理输入被多个动作占用时给出提示或阻止绑定）、存储（重绑定结果持久化到设置，与存档槽分离）。

以下动作集**仅为说明数据格式的示例，不构成任何具体游戏的操作方式或技能数量的定论**，实际动作集完全由游戏层数据决定：

| 动作名（示例） | 类型 | 说明（示例） |
|---|---|---|
| Move | 轴（二维） | 平面移动方向意图 |
| Confirm | 按下 | 通用确认/交互意图 |
| Cancel | 按下 | 通用取消/返回意图 |
| Interact | 按下 | 与最近可交互物件互动 |
| OpenMenu | 按下 | 打开菜单叠加界面 |
| Pause | 按下 | 触发暂停状态 |
| CameraAdjust | 轴（一维，可选） | 镜头缩放或视角微调 |

## 8. 时间与计时器约定

- **模拟时间与真实时间分离**：模拟时间只在 `WorldSim.tick` 中前进，受暂停与慢动作影响；真实时间来自 `IClock.now()`，不受影响，供菜单动画、加载进度条等界面表现使用。
- **模拟时间轴的单位由时间模型决定**：连续模式下模拟时间轴以秒为单位前进；离散模式下模拟时间轴以回合为单位前进，一次 `Discrete` 步推进一个行动者的一次行动，不产生秒数增量。同一份存档在探索与战斗之间切换时间模型，对应第 3.3 节的换算规则。
- **通用计时器原语**：架构在 L0 提供一个挂在模拟时间轴上的通用计时器能力，供冷却、光环持续时间等一切"经过若干模拟时间后触发"的需求统一使用，由 `WorldSim` 在 tick 中统一推进，调用方只需创建/查询计时器，不必各自维护累加逻辑；计时器原语以数据集声明的时间单位计（秒或回合，见 04 "时间字段语义"），不关心当前处于哪种时间模型。
- **存档中的时间**：存档记录的是模拟时间轴上的绝对量（例如累计 tick 数或模拟秒数），不记录真实世界时间戳；若游戏层需要"已游玩时长"一类统计，属于游戏层自定义数据，不属于架构层面的时间约定。

## 9. 核心类接口签名

```
type SimStep =
    Continuous{ dt: Number }                                        // 连续模式：经过的秒数
  | Discrete{ actorId: Id, phase: turn_start|act|turn_end|round_end } // 离散模式：当前行动者与阶段

interface SimClockHost {
  configureStep(stepSeconds: Number, maxCatchUpSteps: Int): void
  advance(realDeltaSeconds: Number): Number   // 连续模式：产生 Continuous 步并返回本次推进得到的插值系数 alpha（0~1）；离散模式：改由 TurnScheduler.nextStep 产生步，本方法只驱动表现插值，不产生模拟步
  setPaused(paused: Bool): void
  setTimeScale(scale: Number): void
}

interface WorldSim {
  tick(step: SimStep): void
  getEntity(id: Id): Optional<EntityRef>
  queryEntities(filter: EntityFilter): List<EntityRef>
  markForDestruction(id: Id): void
}

interface TurnScheduler {
  configure(policy: initiative_stat|action_points|fixed_order, params: Map<String, Any>): void
  beginCombat(participants: List<Id>): void
  endCombat(): void
  nextStep(): Optional<SimStep>          // 返回空表示进入 awaiting_input 或 playing_back，主循环本步不推进模拟
  submitIntent(actorId: Id, intent: Intent): void
  endTurn(actorId: Id): void
  getOrder(): List<Id>
  getCurrentActor(): Optional<Id>
}

interface PacingPolicy {
  mode(): immediate|wait_for_playback
  onPlaybackFinished(): void            // 表现层发出 presentation.playback_finished 后由主循环调用，解除 playing_back 节奏门
}
```

- `SimStep` 是 `WorldSim.tick` 的唯一输入类型，见第 3 节；`Continuous` 由 `SimClockHost.advance` 在连续模式下产生，`Discrete` 由 `TurnScheduler.nextStep` 在离散模式下产生。
- `TurnScheduler` 是 L0 `core/foundation/sim_loop` 内的子组件，按第 3.2 节规则维护回合顺序、产生离散步序列、管理等待输入与回合/轮次边界。
- `PacingPolicy` 决定离散模式下调度器是否等待表现层回放完毕再推进下一离散步，见第 3.2 节；`immediate` 是连续模式的默认节奏，`wait_for_playback` 是离散模式的默认节奏。
- `TurnScheduler.submitIntent` 的 `intent` 参数结构为 `struct Intent { actorId: Id, kind: String, args: Map<String, Any> }`，玩家与 AI 意图共用；回放录像记录的即此结构（见第 4.2 节步骤 1）。

interface ViewBinder {
  onEntityCreated(id: Id, kind: String, displayId: Id): void
  onEntityDestroyed(id: Id): void
  getInterpolatedPosition(id: Id, alpha: Number): Vec2
}

interface SceneRouter {
  loadScene(sceneId: Id): void
  getCurrentScene(): Optional<Id>
  registerPreUnloadHook(callback: Callback): SubscriptionHandle
  registerPostLoadHook(callback: Callback): SubscriptionHandle

`SceneRouter.registerPreUnloadHook`/`registerPostLoadHook` 返回 `SubscriptionHandle`，与下方 `AppStateHost.onStateChanged` 一致，供调用方按需取消订阅。

以下 L0 契约签名与第 1、2 节所述的应用状态机、第 8 节所述的分流随机源、脚本钩子、本地化、外形注册表一一对应：

```
interface AppStateHost {
  getState(): AppState
  requestTransition(target: AppState): Bool
  pushSubState(sub: InWorldSubState): Bool
  popSubState(): Bool
  onStateChanged(callback: Callback): SubscriptionHandle
  onSubStateChanged(callback: Callback): SubscriptionHandle
  requestExit(): Bool
}
```

驱动第 1、2 节的应用级状态机：`getState`/`requestTransition` 处理主状态间的迁移（迁移是否合法见第 2 节状态机表）；`pushSubState`/`popSubState` 管理 InWorld 内部子状态栈（如对话、菜单叠加于世界内），二者与 `requestTransition` 一样返回 `Bool`：非法转移（如目标子状态与当前互斥关系冲突、栈已空时 `popSubState`）返回 `false`，不修改状态栈；`onStateChanged` 供表现层等订阅主状态变化，`onSubStateChanged` 单独订阅子状态栈变化（二者回调分开，调用方可只关心其中一种）；`requestExit` 请求退出应用（如外壳"退出游戏"按钮），非法时机（如已在退出流程中）返回 `false`。

```
interface RngHost {
  next(stream: Id): Number            // [0,1)
  nextInt(stream: Id, min: Int, max: Int): Int
  getStreamState(stream: Id): RngStreamState
  setStreamState(stream: Id, state: RngStreamState): void
  reset(masterSeed: UInt64): void
}
```

按 `stream` 分流生成随机数以保证可复现：不同用途（掉落、AI、技能）各自持有独立流，互不干扰；`getStreamState`/`setStreamState` 供存档系统持久化与恢复某条流的内部状态；`reset` 按主种子重新派生全部流的初始状态，用于新开局/回放起点等需要整体复位的场景。

```
interface HookRegistry {
  declareHookPoint(hookId: Id, signature: String): void
  register(hookId: Id, callback: Callback, order: Int): SubscriptionHandle
  invoke(hookId: Id, args: Map<String, Any>): void
}
```

供游戏层注册自定义回调的挂载点集合：`declareHookPoint` 登记一个挂载点及其参数签名（供校验与文档化）；`register` 挂载回调并指定同一挂载点上多个回调的执行顺序；`invoke` 由基础架构在对应时机触发，逐一调用已注册回调。

```
interface L10nHost {
  text(key: Id, vars: Map<String, String>): String
  setLocale(locale: Id): void
  getLocale(): Id
}
```

文本与资源的语言切换：`text` 按当前语言取文案并做变量插值，缺失时按策略回退；`setLocale`/`getLocale` 切换与查询当前语言。

```
interface DisplayInfoRegistry {
  lookup(logicalId: Id): Optional<DisplayInfo>
  lookupByCategory(category: skill|aura|item|creature|gobj|projectile): List<DisplayInfo>
}
```

把逻辑 id 映射到表现资源引用：`lookup` 按单个逻辑 id 取其外形信息（精灵集、锚点、特效/音效 id 等）；`lookupByCategory` 按类别批量取用，供表现层预加载或编辑器工具枚举使用。

## 10. 基础架构提供 / 游戏层提供

| 基础架构提供 | 游戏层提供 |
|---|---|
| 应用状态机与 InWorld 子状态机的定义与转移规则 | 需要叠加的自定义子状态（经状态栈机制扩展） |
| 固定步长主循环、累积器、插值、暂停、慢动作的实现机制 | 具体步长、最大补偿步数等数值配置 |
| WorldSim 的集合结构与固定 tick 顺序 | 各步骤具体处理的内容数据（技能定义、AI 优先级表等） |
| 逻辑对象与 View 的绑定协议 | 具体 View 的表现实现（经 `DisplayInfo` 与表现层文档） |
| 场景路由的标准流程与钩子挂载点 | 具体场景清单、加载画面呈现、钩子回调实现 |
| 输入映射的绑定/重绑/冲突检测/存储机制 | 具体动作集内容与默认绑定 |
| 通用计时器原语与时间约定 | 使用计时器的具体游戏内容（冷却时长等数值） |
| 连续/离散两种时间模型的机制、回合调度器与节奏策略 | 探索/战斗各自选用哪种时间模型、先攻策略与节奏策略的具体配置 |

## 11. 验收标准

- 应用生命周期的五个主状态与 InWorld 的五个子状态均已定义，且状态机表给出进入条件、允许转移、驱动方三项；`awaiting_input`、`playing_back` 两个仅离散模式使用的子态已明确标注触发与解除条件。
- 固定步长主循环给出累积器、渲染插值、暂停、慢动作、步长可配置五项机制的具体说明；离散模式给出回合调度器、等待输入、节奏策略、模式切换换算规则的具体说明，且两种模式共享同一套 tick 顺序。
- WorldSim 结构列出全部逻辑对象集合，tick 顺序与第 4.2 节规定的八步顺序完全一致，不可调整；`SimStep` 是 tick 的唯一输入类型，连续步与离散步的差异只集中在意图收集与移动两步。
- 逻辑对象与 View 的绑定协议覆盖创建、同步、销毁三个阶段，且明确 View 只读。
- 场景路由给出完整的地图切换流程，包含加载画面与存档钩子的挂载时机。
- 输入映射说明动作集由游戏层声明、架构提供绑定/重绑/冲突检测/存储，并给出一个明确标注为示例的动作集。
- 核心类接口使用统一的中立伪代码记法给出签名，未出现任何引擎、语言或框架名字；`TurnScheduler`、`PacingPolicy` 的签名与调用时机均可在第 3、9 节找到定义。
