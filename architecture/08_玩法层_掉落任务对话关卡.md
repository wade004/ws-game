## 1. Loot（掉落）

目录名：`core/gameplay/loot`（玩法层，见 01）。

### 1.1 `loot.table` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `loot.<name>` |
| `groups` | List<LootGroup> | 是 | 分组列表，见下 |
| `guaranteed_min` | Optional<Int> | 否 | 保底计数：本表整体至少掉落的条目数 |

```
struct LootGroup {
  rollMode: chance_each | weighted_pick_one
  entries: List<LootEntry>
  pickCount: Optional<Int>   // weighted_pick_one 时可选多次抽取（不放回）
}

struct LootEntry {
  ref: Id                    // item.template 或另一个 loot.table（支持嵌套引用）
  weightOrChance: Number
  condition: Optional<Expr>  // 例如任务相关掉落只在任务激活时可能出现
  countRange: {min: Int, max: Int}
}
```

- `chance_each`：组内每一条独立按自身概率判定是否掉落，互不影响。
- `weighted_pick_one`：组内按权重抽取，抽中一条（或 `pickCount` 条不放回）。
- 支持引用其它 `loot.table`（嵌套），用于"通用材料表"被多个生物掉落表复用；此时 `countRange` 表示把被引用的整张表再整体抽取该次数（而非把嵌套表的抽取结果重复该次数）。
- 伪随机：（建议）对稀有条目引入"未掉落次数累积、逐次提升实际概率直至保底触发"的伪随机分布机制，用以降低连续不掉落的挫败感，是否启用与具体曲线为策略配置项，架构只登记 `guaranteed_min` 作为保底计数的挂载点。

### 1.2 DroppedLoot 与拾取规则

- 结算完成后生成 `DroppedLoot` 实体（见 05），携带具体抽取结果 `List<ItemStack>`。
- 单机场景只有单人拾取，`DroppedLoot.ownerHint` 字段（见 05）在本架构中无实际分配意义，仅为兼容掉落生成管线数据结构而保留；拾取动作直接调用 07 的 `InventoryHost.addItem`，背包已满时的处理策略（拒绝拾取/部分拾取/掉在地上等待）为策略配置项。

### 1.3 与魔兽 `loot_template` 对照

| 魔兽概念 | 本架构对应 | 裁剪说明 |
|---|---|---|
| `loot_template` 按 `Reference` 字段嵌套引用其它掉落表 | `LootEntry.ref` 支持引用 `loot.table` | 保留嵌套复用思想 |
| `Chance` 为负数表示分组内互斥抽取 | `rollMode: weighted_pick_one` | 用显式枚举替代"负数表示特殊语义"的隐式约定，提升可读性 |
| `groupid` 分组 | `groups` 列表 | 直接对应 |
| 拾取分配方式（需求、贪婪、拉霸等） | 直接裁剪，不予保留（拍板裁剪原则） | 单机无多人分配问题 |

## 2. Quest（任务）

目录名：`core/gameplay/quest`（玩法层，见 01）。

### 2.1 `quest.def` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `quest.<name>` |
| `title_key` | Id | 是 | 标题文本键 |
| `description_key` | Optional<Id> | 否 | 描述文本键 |
| `objectives` | List<QuestObjective> | 是 | 目标数组，见下 |
| `prerequisite` | Optional<Expr> | 否 | 前置条件（等级、已完成任务、世界标志等） |
| `exclusive_group` | Optional<Id> | 否 | 互斥组：同组任务同时只能激活/完成一个 |
| `start_method` | `npc_gossip\|item_use\|area_trigger\|auto` | 是 | 起始方式 |
| `turn_in_method` | `npc_gossip\|auto` | 是 | 交付方式 |
| `rewards` | `{items: List<{itemId, count}>, xp: Number, currency: List<{currencyId, amount}>, skills: List<Id>, world_flags: List<{flagKey, value}>, talent_points: Int}` | 否 | 奖励类型；`world_flags` 交付时写入的世界状态标志，`talent_points` 交付时发放的天赋点数 |
| `repeatable` | `none\|daily\|unlimited` | 是 | 可重复性 |

```
struct QuestObjective {
  type: kill | collect | interact | explore | escort | event | cast | talk
  targetRef: Id            // 依 type 指向 creature.template / item.template / gobj.template / area.trigger_def / dialog 节点 等
  count: Int
  descriptionKey: Optional<Id>   // 该条目标自身的描述文本键
  param: Optional<Map<String, Value>>   // 各类型的额外参数，见下
}
```

| `type` | `targetRef` 指向 | `count` 含义 | `param` 要点 |
|---|---|---|---|
| `kill` | `creature.template` | 需击杀数量 | 无 |
| `collect` | `item.template` | 需持有数量 | `consume_on_progress: Bool`（进度是否消耗物品） |
| `interact` | `gobj.template` | 需交互次数 | 无 |
| `explore` | `area.trigger_def`（`quest_explore` 类型） | 恒为 1 | 无 |
| `escort` | `creature.template`（被护送对象） | 恒为 1 | `escort_route_ref`（路径引用） |
| `event` | 任意事件类型（06 第 8 节词汇表中的事件） | 视事件语义 | `eventFilter: Expr` |
| `cast` | `skill.def` | 需施放次数 | 无 |
| `talk` | `dialog.gossip_menu` 或 `dialog.story_tree` 节点 | 恒为 1 | 无 |

### 2.2 任务日志状态机

```
unavailable → available → active → objectives_complete → turned_in
                                 └→ failed（escort/event 类可能失败，策略配置是否允许失败）
```

- `unavailable → available`：`prerequisite` 满足。
- `available → active`：按 `start_method` 被接取。
- `active → objectives_complete`：全部 `objectives` 的 `count` 达标。
- `objectives_complete → turned_in`：按 `turn_in_method` 交付，结算 `rewards`。
- 状态变化持久化在 `PlayerUnit.questLog`（见 05），随存档写入。

### 2.3 任务标记与追踪

- 每个激活任务的每个未完成目标，可关联一个地图标记（供表现层在小地图/主视图渲染，见 09），标记来源是 `targetRef` 对应实体的位置或 `area.trigger_def` 的形状中心，逻辑层只暴露"当前激活目标的位置查询接口"，不涉及具体渲染。
- 追踪：（建议）允许玩家从多个激活任务中"追踪"一个子集，决定哪些目标显示在常驻界面，纯表现层状态，不影响任务判定逻辑，作为可选 UI 特性留给游戏层决定是否启用。

### 2.4 与魔兽 `quest_template` 对照

| 魔兽字段 | 本架构对应 | 裁剪说明 |
|---|---|---|
| `RequiredNpcOrGo` / `RequiredItemId` 等按目标槽位硬编码的字段 | `QuestObjective.type` + `targetRef` 的统一结构 | 用一种通用结构替代魔兽按目标类型分散在多个字段槽位的做法，便于扩展新目标类型（走审批） |
| `PrevQuestId` / `ExclusiveGroup` | `prerequisite`（用 Expr 表达前置任务完成状态）、`exclusive_group` | 前置逻辑改用 Expr 统一表达，比多个专用字段更灵活 |
| `RewardChoiceItemId` 多选一奖励 | （建议）`rewards.items` 扩展为支持"多选一"的分组结构，本版先给出固定奖励结构，多选一作为后续 ADR 增量 | 简化初版范围 |
| `QuestSortID` / 任务分类显示 | 属于表现层/UI 归类，不在本表定义 | 职责边界收在表现层 |

## 3. Dialog（对话与剧情）

目录名：`core/gameplay/dialog`（玩法层，见 01）。

### 3.1 gossip 菜单

`dialog.gossip_menu` 字段：`id`、`options: List<GossipOption>`。

```
struct GossipOption {
  textKey: Id
  visibleIf: Optional<Expr>
  actions: List<GossipAction>
}
```

| Action 类型 | 语义 |
|---|---|
| `vendor` | 打开该 NPC 的 `econ.vendor` 界面（经表现层 UI，逻辑侧只发出"打开商店"请求） |
| `quest_accept` | 接取指定 `quest.def` |
| `quest_turn_in` | 交付指定 `quest.def` |
| `teleport` | 传送到指定传送点（见 05） |
| `save` | 触发存档（见 10） |
| `set_flag` | 写 `WorldState` |
| `start_encounter` | 启动指定 `encounter.def` |
| `cast_skill` | 以该 NPC 为施法者释放指定技能（复用 06 施法管线，例如训练师"传授技能"实为释放一个 `learn_skill` 效果技能） |
| `start_story` | 打开指定的 `dialog.story_tree` |
| `script` | 调用脚本钩子，兜底自定义演出 |

### 3.2 剧情对话树

`dialog.story_tree` 字段：`id`、`nodes: List<StoryNode>`。

```
struct StoryNode {
  id: Id
  textKey: Id
  speakerRef: Optional<Id>       // creature.template 或占位角色 id，供表现层选头像/立绘
  branches: List<{textKey, condition: Optional<Expr>, nextNodeId: Optional<Id>}>
  performanceHookRef: Optional<Id>   // 进入该节点时调用的 found.hook，用于过场/运镜等演出
}
```

- 起始节点固定为 `nodes` 数组第一个元素。
- 分支为空时该节点是终止节点，剧情树结束。
- `performanceHookRef` 是逻辑层与表现层之间关于"演出时机"的唯一约定接口：逻辑层只在进入节点时调用钩子，具体钩子做什么（切镜头、播放过场、静音 BGM）完全是表现层订阅实现，逻辑不感知。

### 3.3 显隐条件

`GossipOption.visibleIf` 与 `StoryNode.branches[].condition` 统一用 Expr 表达，宿主分组复用 04 第 6.2 节（`quest`/`world`/`player` 等），不引入专门的"对话条件语言"。

## 4. Encounter/Level（遭遇与关卡）

目录名：`core/gameplay/encounter`（玩法层，见 01）。

### 4.1 `encounter.def` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `encounter.<name>` |
| `units` | List<{spawnRef 或 creature.template, position}> | 是 | 参战单位 |
| `waves` | Optional<List<Wave>> | 否 | 波次定义 |
| `phases` | Optional<List<Phase>> | 否 | 阶段定义 |
| `arena_rules` | Optional<{boundsShape, resetIfLeave: Bool}> | 否 | 场地规则 |
| `victory_condition` | Expr | 是 | 胜利判定 |
| `defeat_condition` | Expr | 是 | 失败判定 |
| `rewards` | 同 `quest.def.rewards` 结构 | 否 | 奖励 |
| `combat_mode_override` | Optional<`continuous\|discrete`> | 否 | 覆盖场景默认的 `combat_time_model`（见 04 `found.time_model`），仅本遭遇生效 |
| `initiative_override` | Optional<{policy: initiative_stat\|action_points\|fixed_order, params: Map<String, Any>}> | 否 | 覆盖默认先攻策略与参数，仅本遭遇生效，`combat_mode_override` 为 `discrete` 或场景默认已是 `discrete` 时才有意义 |

```
struct Wave {
  triggerCondition: Expr
  spawnRefs: List<Id>
}

struct Phase {
  enterCondition: Expr
  aiRotationOverride: Map<Id, Id>   // unitId(或模板) → 替换后的 ai.rotation 引用，对应06第6.4节"Boss阶段=换Rotation"
  onEnterHook: Optional<Id>
}
```

`combat_mode_override` 未声明（字段缺失）与声明了一个未知取值，两者按同一路径处理——运行期均视为"本遭遇不覆盖"，退回场景默认的时间模型；`initiative_override.policy` 只允许 `initiative_stat`/`action_points`/`fixed_order` 三种取值，未知取值不会退回默认策略，而是在装配/求值期报错（该字段决定先攻调度器的具体策略参数，静默忽略错误取值的风险高于报错）。

### 4.2 关卡

"关卡 = 地图 + 遭遇序列"：`Level`（登记为 `encounter.level`，与 `encounter.def` 同域不同表）字段：`id`、`mapRef`（指向 `world.map`）、`encounterSequence: List<Id>`（有序 `encounter.def` 引用）、`entryDifficultyOptions: List<Id>`（可选难度档位）。关卡本身不引入新的运行时对象类型，只是"地图引用 + 一串遭遇 id + 难度可选项"的编排数据。

### 4.3 与遭遇脚本的边界

- 阶段切换（`phases[].enterCondition` 满足）只做两件事：替换涉及单位的 `ai.rotation` 引用（`aiRotationOverride`）、调用 `onEnterHook`；不直接操作战斗结算（结算永远走 06 定义的管线）。
- 胜负判定（`victory_condition`/`defeat_condition`）是 Expr，通常引用 `enemies.count_in_range`、`self.hp_pct` 等既有宿主分组，不需要新增专门的"遭遇状态"分组。
- 离散模式下遭遇的整轮求值（波次触发、阶段推进、场地规则、胜负判定）改由回合结束/轮结束事件驱动：全部判定在每个 `sim.turn_ended`/`sim.round_ended`（见 06 第 8 节事件表）之后统一求值一次，避免同一行动者的行动过程中途触发波次/切换 `ai.rotation`/改变场地规则/判定胜负；连续模式下仍按 tick 频率求值，行为不变。

## 5. Difficulty（难度）

目录名：`core/gameplay/difficulty`（玩法层，见 01）。

### 5.1 `diff.tier` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `diff.<name>` |
| `name_key` | Id | 是 | 显示名文本键 |
| `sort_weight` | Optional<Int> | 否 | 内容管线展示排序权重，运行期不读取 |
| `modifier_aura_refs` | List<Id> | 否 | 施加给该难度下敌对单位（或全体单位）的修正光环，例如统一提升生物属性 |
| `affix_pool_ref` | Optional<Id> | 否 | 词缀池引用（供 `encounter`/`spawn` 按难度随机附加特殊规则，具体词缀内容为后续扩展，本版只登记挂载点） |
| `loot_multiplier` | Number | 是 | 掉落数量/概率的整体倍率 |

### 5.2 选择时机

难度在"新游戏开始"或"关卡入口"（视 `Level.entryDifficultyOptions` 是否允许中途切换）选择，选择结果写入存档（10）；已进行中的遭遇不因难度切换而重算，只影响后续新生成的内容。是否允许中途切换由难度模块自身的策略开关提供（一个全局布尔配置项），关卡级 `entryDifficultyOptions` 与该开关之间具体如何映射（例如是否允许某些关卡单独覆盖全局开关）由游戏层接线决定，架构本身只提供开关，不提供两者的映射机制。

## 6. Achievement（成就）

目录名：`core/gameplay/achievement`（玩法层，见 01）。

### 6.1 `achv.def` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `achv.<name>` |
| `name_key` | Id | 是 | 显示名文本键 |
| `criteria` | List<Criterion> | 是 | 达成条件 |
| `rewards` | Optional<同 quest 奖励结构> | 否 | 达成奖励 |

```
struct Criterion {
  type: kill_count | collect_count | quest_complete | reach_area | cast_count | custom_event
  observeEvent: Id          // 06/08 事件词汇表中的具体事件类型
  targetRef: Optional<Id>
  count: Int
  filter: Optional<Expr>    // 六种类型均可选携带的补充匹配条件
}
```

- 成就系统只订阅事件总线，累计计数，不主动轮询其它系统状态；`custom_event` 类型对应"以上四类不能覆盖"的情形，由内容作者指定要观察的具体事件类型与匹配条件（Expr）。

| `id` | Id | 是 | `econ.currency.<name>` |
| `name_key` | Id | 是 | 显示名文本键 |
| `cap` | Optional<Int> | 否 | 上限，空表示无上限 |
| `display_ref` | Id | 是 | 图标等外形引用 |

### 7.2 `econ.vendor` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `econ.vendor.<name>` |
| `name_key` | Id | 是 | 显示名文本键 |
| `map_id` | Optional<Id> | 否 | 所在地图，`restockPolicy` 为 `on_map_enter` 时据此判断玩家进入哪张地图触发补货 |
| `sell_items` | List<{itemId, priceCurrencyId, priceAmount, stockLimit: Optional<Int>, restockPolicy: Optional<on_map_enter\|timer>, restockTimer: Optional<Number>}> | 是 | 出售清单，价格与限量刷新；`restockTimer` 为 `restockPolicy: timer` 时的补货周期，该策略下必填 |
| `buy_price_rule` | Optional<Expr 或曲线引用> | 否 | 玩家出售物品给商人时的收购价规则 |

### 7.3 与魔兽 `npc_vendor` 对照

| 魔兽概念 | 本架构对应 | 裁剪说明 |
|---|---|---|
| `npc_vendor` 表（item, maxcount, incrtime, ExtendedCost） | `sell_items` 结构 | 保留限量与刷新周期思想；`ExtendedCost`（多货币/多物品组合支付）作为（建议）扩展位，本版 `priceCurrencyId/priceAmount` 先支持单一货币，组合支付留待后续 ADR |
| 拍卖行/交易 | 直接裁剪 | 非目标（第 2 节非目标声明） |

`restockPolicy: on_map_enter` 的补货判定由组装根的"进入地图"流程在该流程内显式调用触发，不经事件订阅；`restockPolicy: timer` 的补货倒计时只在连续步（tick）推进，离散步不推进——若场景当前处于离散模式，商人补货计时在离散步期间保持不变，直至下一次连续步（或切回连续模式）才继续计时。

## 8. Spawn 归属说明

刷新表（`spawn.table`）的字段与重生策略已在 [05_对象模型与世界](05_对象模型与世界.md#5-刷新与重生) 中完整定义；本层的 `encounter.def.units` 与 `Level` 可以引用刷新表条目作为参战单位的来源（`spawnRef`），也可以直接内联 `creature.template` + 坐标（不经过持久刷新点，遭遇结束即销毁），二者的选择取决于该单位是"常驻于地图的可重复刷新对象"还是"仅本次遭遇临时生成"。掉落（第 1 节）、任务目标（第 2 节 `kill`/`interact` 类）在判定时都不关心目标来源于刷新表还是遭遇内联生成，只按 `creature.template`/`gobj.template` 的模板 id 匹配。

## 验收标准

1. 任给一种任务目标需求（击杀/收集/交互/探索/护送/事件/施法/交谈），能在 `QuestObjective.type` 八种枚举中找到对应项，无需新增字段结构。
2. Boss 机制（阶段切换、波次召唤、场地规则）全部可用 `encounter.def` 的既有字段表达，未引入与 06 战斗结算并行的第二套判定逻辑。
3. 难度差异只体现为"修正光环 + 词缀池 + 掉落倍率"的组合，未在本文档引入额外的难度专属数值系统。
4. 成就系统的实现只依赖订阅事件总线与 Expr 求值，未反向查询其它系统的内部状态。
5. 掉落、任务、对话、遭遇四个高频引用刷新/生物/物品/世界状态的模块，其字段引用均能在 04（数据规范）、05（对象与世界）、07（载体层）中找到对应定义，不出现自造的平行概念。
6. 本文档"各模块契约、事件、依赖、配置、测试汇总"表覆盖 Loot/Quest/Dialog/Encounter/Difficulty/Achievement/Economy 七个模块，逐项齐全。
