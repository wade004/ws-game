## 1. 新增内容 checklist（按类型）

以下每一类"新增内容"都遵循同一个底线：**是否需要写代码 = 否**。全部通过"加数据行 + 配表现资源 + 跑校验测试"完成。表格里的"改哪些表/资源"是概念层面的清单，具体表名以 [04_数据与内容管线.md](04_数据与内容管线.md) 的全表清单为准。

| 内容类型 | 改哪些表 | 加哪些资源 | 跑哪些校验与测试 | 是否需要代码 |
|---|---|---|---|---|
| 新技能 | Skill/Effect/Aura/SpellMod 相关表（见 06） | 技能图标、施法/命中特效、音效、DisplayInfo 映射行（见 09） | 引用完整性校验、Expr 条件语法校验、（如涉及战斗数值）性能基线抽样 | 否 |
| 新被动 | 被动光环表、授予关系（技能/装备/天赋授予被动） | 通常无需新资源，或仅需状态图标 | 引用完整性校验 | 否 |
| 新光环 | Aura 表、Proc/SpellMod 关联字段 | 状态栏图标、可选持续特效 | 引用完整性校验、（如涉及叠加/免疫互斥）互斥规则校验 | 否 |
| 新装备 | Item 模板表、槽位与品质字段、词缀/套装关联（见 07） | 图标、纸娃娃层美术、DisplayInfo 映射行 | 引用完整性校验、物品等级预算校验（若启用） | 否 |
| 新词缀 | 词缀定义表、词缀池归属 | 通常无需新资源 | 引用完整性校验 | 否 |
| 新套装 | 套装定义表、套装效果关联（授予被动光环） | 套装图标（可选） | 引用完整性校验 | 否 |
| 新武器表现档案（见 09） | 武器表现档案表 `display.weapon_style`（见 09） | 普攻/施法动作剪辑、挥舞与命中特效 | 引用完整性校验、DisplayInfo 映射校验 | 否 |
| 新职业 | 职业模板表（Archetype，见 06）、初始技能/属性配置 | 职业图标、专属纸娃娃基础层 | 引用完整性校验 | 否，除非涉及新的施法资源类型（见第 2 节新增原语判断） |
| 新怪 | Creature 模板表、职能标志、AI 引用、掉落引用（见 07） | 生物外形映射、方向精灵集、音效 | 引用完整性校验、AI 行为表校验 | 否 |
| 新 Boss | Creature 模板 + 遭遇/阶段定义（Encounter，见 08） | 专属外形与特效、阶段演出资源 | 引用完整性校验、遭遇阶段条件 Expr 校验、回放回归（机制复杂时建议） | 否，遭遇阶段的触发逻辑用既有触发器原语组合表达 |
| 新地图 | 地图/场景定义表、AreaTrigger、刷新表（见 05） | 地图背景/图块资源、导航数据 | 引用完整性校验、导航数据校验 | 否 |
| 新任务 | Quest 模板表、目标类型引用、前置条件 Expr | 任务图标、对话文本 | 引用完整性校验、任务图（前置/解锁关系）无环校验 | 否，除非用到新的任务目标类型（见第 2 节） |
| 新对话 | Dialog 树表、对话动作引用 | 对话立绘/头像（可选）、语音（可选） | 引用完整性校验、对话树可达性校验 | 否，除非用到新的对话动作类型（见第 2 节） |
| 新物件 | GameObject 模板表、锁与 on_use 引用 | 物件外形、交互特效音效 | 引用完整性校验 | 否，除非用到新的物件类型（见第 2 节） |

## 2. 新增原语审批流程

"原语"特指本架构在拍板决策 10 中列出的、需要修改注册表与代码的最小扩展开口：**新效果类型、新光环类型、新事件、新物件类型、新任务目标类型、新对话动作类型、新 AI 行为状态**。

判断依据：一项需求如果能用"现有原语的新组合 + 新数据行"表达，就属于第 1 节的"新增内容"，不需要审批；只有当现有原语的表达能力确实覆盖不了（例如需要一种全新的效果结算方式，而不是现有效果类型的参数变体）时，才进入本流程。

审批流程（固定顺序，不得跳步）：

```
1. 先写 ADR
   说明背景（为什么现有原语不够用）、决策（新原语的语义与最小接口）、
   后果、备选方案与为什么不选、是否有魔兽世界对应做法。
   ADR 未获通过前不进入后续步骤。
2. 再改注册表
   在对应层的注册表（如效果类型注册表、事件词汇表）登记新原语的 id 与元信息，
   使 DataRegistry 能够识别但尚未提供运行时实现（此时数据引用它会在校验期报"未实现"而非"不存在"）。
3. 再写代码
   在归属层的 core/ 内实现该原语的运行时逻辑，遵循 11 的模块范式，
   不得散落进游戏层代码（原语是基础架构能力，不是某个游戏的专属代码）。
4. 再补校验器
   为新原语补充对应的数据校验规则（如新效果类型的参数合法性校验）。
5. 再补测试
   补充脱离引擎的模块单测，覆盖新原语的核心行为路径。
```

- 任何一步跳过都视为流程违规，即使最终代码能跑通也需要补齐前置文档（ADR 与注册表登记）。
- 审批通过的新原语从此进入"可被第 1 节 checklist 复用"的状态——后续同类内容只需加数据，不再需要重复走审批。

## 3. ADR 格式模板

新增原语审批（以及任何架构层面的关键决策）统一用以下模板产出一份 ADR，存放于 `adr/` 目录，登记进 [adr/README.md](adr/README.md) 索引表：

```
# ADR-NNNN <决策标题>

状态：已拍板 <日期> ｜ 提议中 ｜ 已废弃（若废弃，注明被哪份 ADR 取代）

## 背景
说明面临的问题、为什么现状不够用。

## 决策
说明具体决定了什么，包括新原语/新机制的最小语义定义。

## 后果
### 正面
...
### 负面
...

## 备选方案与为什么不选
逐个列出考虑过的替代方案及否决理由。

## 魔兽世界的对应做法
若有对应的魔兽世界系统设计，说明对应关系与本架构下的取舍；若无对应，注明"无直接对应"。
```

- 编号 `NNNN` 全局递增，不因废弃而回收。
- 一份 ADR 只对应一条决策，不得在一份 ADR 里夹带多条不相关决策。

## 4. 文档版本规则

- 本文档集的每份文档标题携带版本号（如"v1"）；对某份文档做**不改变其结论、只补充细节或勘误**的修改，版本号不变；对某份文档做**改变其结论或拍板内容**的修改，版本号递增，并在文档内追加一条变更记录（变更日期、变更摘要、关联 ADR 编号）。
- 任何导致拍板结论变化的文档修改，必须先有对应 ADR（走第 2、3 节流程或直接的架构级 ADR），文档修改是 ADR 落地的记录，不能反过来先改文档再补 ADR。
- README 的文件清单与目录树（README 第 4 节）是文档集结构的唯一权威列表，新增/删除文档文件必须同步更新 README。

## 5. 文档与实现不一致的处理规则

当发现某份架构文档的描述与实际实现不一致时，按以下顺序处理，不允许放任两者长期分歧：

1. **先判断谁是错的**：实现是否为临时妥协（技术债）还是文档描述已经过时（设计已经在别处被合理调整但文档未同步）。
2. 若是**实现错**：登记为待修复项，明确修复前不得以此实现为基础扩展新内容（避免在错误实现上继续叠加）。
3. 若是**文档错**（设计确实已经变化）：
   - 变化仅是细节勘误 → 直接修订文档，版本号不变，注明勘误。
   - 变化涉及拍板结论 → 先写 ADR 说明变更理由，再修订文档并递增版本号。
4. 任何一次不一致的发现与处理过程，建议在相关模块的 README（见 [11_工程规范与测试.md](11_工程规范与测试.md) 模块范式）中留一条简短记录，便于后续排查同类问题时追溯。
5. 不一致处理**不属于**新增原语审批流程（第 2 节），除非修复过程本身引入了新原语，此时按第 2 节另行走完整流程。

## 基础架构提供 / 游戏层提供

| 能力 | 基础架构提供 | 游戏层提供 |
|---|---|---|
| 按内容类型的新增 checklist | 是 | 具体内容数据本身 |
| 新增原语审批流程 | 是（流程本身） | 具体原语提案的背景与实现 |
| ADR 模板与索引机制 | 是 | 具体 ADR 内容 |
| 文档版本规则 | 是 | 无 |
| 文档与实现不一致处理规则 | 是 | 具体项目按规则执行并记录 |

## 验收标准

1. 给定任意一项"新增 XX"的需求，能在第 1 节表格中定位到对应行，并据此判断"是否需要代码"，结论与拍板决策 1、10 一致。
2. 给定一项确实需要新增原语的需求，能按第 2 节五个步骤逐一对应到具体产出物（ADR 文件、注册表改动、代码、校验器、测试），不存在跳步空间。
3. 抽取任意一份既有 ADR（见 `adr/` 目录），能对照第 3 节模板逐节核对其完整性。
4. 给定一个"文档说 A、实现是 B"的假设场景，能按第 5 节流程判断出处理路径与是否需要 ADR。
