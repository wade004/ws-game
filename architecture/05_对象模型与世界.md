## 1. Entity 继承树

拍板决策 2：世界模拟由纯逻辑对象构成，不继承任何引擎节点或组件；每个逻辑对象由表现层创建一个只读、只订阅事件的 View 与之绑定（绑定协议见 03）。

```
Entity
 ├─ Unit
 │   ├─ PlayerUnit
 │   └─ CreatureUnit
 ├─ GameObject
 ├─ Projectile
 ├─ AreaTrigger
 └─ DroppedLoot
```

### 1.1 Entity（公共基类）

| 字段 | 类型 | 说明 |
|---|---|---|
| `entityId` | Id | 运行期唯一实例 id（区别于内容模板 id） |
| `templateId` | Optional<Id> | 来源的内容模板 id（如 `creature.grey_wolf`），手工放置对象可为空 |
| `position` | Vec2 | 世界平面坐标，见第 3 节 |
| `layerDepth` | Number | 纵轴深度排序键，见第 3 节 |
| `facing` | Number | 朝向角度（弧度或量化方向索引，见第 3 节） |
| `mapId` | Id | 所属地图 |
| `spawnedBy` | Optional<Id> | 刷新表引用，手工放置为空 |
| `worldFlagsScope` | Optional<Id> | 该实体读取世界状态时使用的命名空间前缀（可选，多数继承地图默认） |

生命周期：`created → active → (inactive 可选) → destroyed`；是否进存档由子类决定（见各子类"进存档"列）。

### 1.2 Unit（可战斗、可移动的活体基类）

| 字段 | 类型 | 说明 |
|---|---|---|
| `statBlock` | Ref<StatBlock> | 属性表引用（见 06）；引用性字段，运行期实际由 L1 `StatBlock` 宿主按 `entityId` 索引持有，`Unit` 自身不重复存储一份，本字段只表达"存在这样一个引用关系" |
| `powerSet` | Ref<PowerSet> | 资源池引用（见 06）；引用性字段，持有方式同 `statBlock`，由 L1 `PowerSet` 宿主按 `entityId` 索引持有 |
| `factionId` | Id | 阵营 |
| `auras` | List<AuraInstance> | 当前生效光环实例；引用性字段，运行期由 `core/rules/skill` 的光环宿主按 `entityId` 索引持有 |
| `combatState` | `out\|in` | 进出战斗状态 |
| `threatTable` | Optional<Ref<ThreatTable>> | 仇恨表，仅 `CreatureUnit` 常用，`PlayerUnit` 一般为空；引用性字段，由 `core/rules/combat` 按 `entityId` 索引持有 |
| `movementState` | MovementState | 见第 6 节 |
| `alive` | Bool | 存活状态 |
| `heightOffset` | Number | 高度偏移（跳跃、被击飞、飘浮等视觉抬升），默认 0，仅供表现层渲染读取，不参与平面距离与碰撞计算（详见第 3.3 节） |
| `tags` | List<Id> | 标签集合，供按标签过滤目标等查询使用（装配/内容加载阶段填充） |
| `level` | Int | 当前等级快照，默认 1，由等级成长模块（见 06）写入 |

`statBlock`/`powerSet`/`auras`/`threatTable` 四个字段是"引用性"字段：本文档把它们列在 `Unit` 字段表是为了表达对象模型层面的归属关系，但它们各自的权威存储与读写始终在对应宿主（06 定义的 `StatBlock`/`PowerSet`/光环/仇恨表宿主）里，按 `entityId` 反查，不在 `Unit` 实例本体上重复持有一份可变状态。

勘误补充：`auras` 列出的每一条光环实例还各自记录一个"来源"单位 id（施加这条光环的单位，见 06 第 3.2/3.8 节）——这个来源单位与"持有这条光环的 `Unit`"（本字段所属的这个实体，即光环的目标）是两个可能不同的实体，来源单位的生命周期与光环实例的生命周期没有强制耦合：来源单位被销毁（`Despawn`，见 5.3 节）不会连带移除已经施加在其他目标身上的光环，只有光环自身的目标被销毁才会摘除其名下光环（详见 06 第 3.8 节勘误补充"来源销毁后周期效果的处理"）。

生命周期：`created → active ⇄ (in_combat) → dead → (respawn 或销毁)`。

#### PlayerUnit

- 额外字段：`archetypeId`（职业模板引用）、`talents`（已选天赋）、`questLog`、`inventory`、`equipment`、`skillBook`（已学技能）。`inventory`/`equipment`/`skillBook` 同 `Unit.statBlock` 等字段，是引用性字段——运行期分别由 07 的 `InventoryHost`/`EquipmentHost` 与 06 的技能相关宿主按 `entityId` 索引持有，`PlayerUnit` 不重复存储一份。`questLog` 目前仍是一个未展开结构的占位存储位（未定型的结构化值）；任务状态机（见 08）落地后实际的任务进度权威存储在 08 `QuestHost` 一侧，`questLog` 字段本身尚未被读写，留作已知缺口。
- 进存档：是，是存档的核心内容（详见 10）。
- 全局唯一或按需求支持多个（架构不限制数量，具体游戏决定是否允许多角色）。

#### CreatureUnit

- 额外字段：`aiState`（行为外壳当前状态，见 06）、`lootTableId`、`immunities`、`npcFlags`（职能标志位，见 07）、`ownerId`（`Optional<Id>`，召唤物/宠物用，指向拥有者单位，见 07 第 4 节）。
- 进存档：默认不进存档（由刷新表在读档后按策略重新生成，见第 5 节）；若某只生物承载了任务关键、不可替代的状态（例如已被玩家说服的关键 NPC），该状态经由 `WorldState` 持久化，而不是把 `CreatureUnit` 实例本身写入存档。

### 1.3 GameObject（非活体、可交互的世界对象）

| 字段 | 类型 | 说明 |
|---|---|---|
| `templateId` | Id | 指向 `gobj.template`（见 07） |
| `state` | Map<String, Value> | 运行期可变状态（如箱子是否已开），落地为 `WorldState` 的具名标志（见第 8 节），对象本身不单独持久化 |
| `lockId` | Optional<Id> | 当前锁状态 |

进存档：对象本身不进存档，其可变状态经 `WorldState` 持久化（拍板决策 8、9）。

### 1.4 Projectile（飞行物）

| 字段 | 类型 | 说明 |
|---|---|---|
| `sourceUnitId` | Id | 发射者 |
| `skillContextId` | Id | 关联的技能效果上下文（用于命中后结算） |
| `velocity` | Vec2 | 平面速度矢量 |
| `travelMode` | `straight\|homing\|arc` | 飞行方式（策略配置项） |
| `hitBehavior` | `impact_on_first\|pierce\|impact_on_expiry` | 命中行为 |

进存档：否，飞行物是瞬时对象，不跨存档周期存在。

### 1.5 AreaTrigger（区域触发体）

| 字段 | 类型 | 说明 |
|---|---|---|
| `shape` | Shape（见第 3.5 节） | 触发范围 |
| `triggerType` | `map_transition\|quest_explore\|encounter_start\|script` | 触发类型（见第 7 节） |
| `condition` | Optional<Expr> | 附加触发条件 |
| `oneShot` | Bool | 是否只触发一次 |

进存档：手工放置的固定触发体不进存档（随地图数据加载）；`oneShot` 已触发的状态经 `WorldState` 记录。

运行期簿记（当前在范围内的单位、已触发标记等）由区域触发宿主（第 7.1 节 `AreaTriggerHost`）持有，不在实体本体上。

### 1.6 DroppedLoot（掉落在地面的拾取物）

| 字段 | 类型 | 说明 |
|---|---|---|
| `lootInstanceId` | Id | 运行期实例 id |
| `items` | List<ItemStack> | 掉落物内容 |
| `ownerHint` | Optional<Id> | 单人拾取规则的归属提示（见 08），单机场景通常无实际限制意义，保留字段以兼容掉落生成管线 |
| `expireAt` | Optional<Number> | 过期时间（游戏内时间） |

进存档：（建议）随当前地图状态一并存档，避免读档后地面掉落消失造成体验割裂；具体是否持久化为策略配置项。

## 2. 与魔兽世界对象模型的对照与裁剪

| 魔兽对象 | 本架构对应 | 裁剪/简化理由 |
|---|---|---|
| `Object`（所有可寻址物体的基类，含同步字段） | `Entity` | 去除网络同步相关字段（可见范围、更新掩码等），单机无需按连接分发状态 |
| `Unit`（生物基类） | `Unit` | 保留属性、资源、光环、仇恨、战斗状态等核心概念；去除服务端权威校验字段 |
| `Player` | `PlayerUnit` | 去除账号、公会、好友、聊天、邮件、拍卖行、日历等社交与网络字段；保留职业、天赋、任务日志、背包装备 |
| `Creature` | `CreatureUnit` | 保留模板化、AI 引用、职能标志、掉落引用；去除服务端刷怪范围网格，改用第 5 节刷新表 |
| `GameObject` | `GameObject` | 保留类型枚举、状态、锁、on_use；去除拾取分配方式（单机无多人分配问题） |
| `DynamicObject`（法术产生的临时区域，如法阵） | `AreaTrigger`（`triggerType: script` 或专用效果原语承载） | 合并入 `AreaTrigger`，不单列类型，减少一层几乎重复的概念 |
| `Corpse` | 不单列类型，`CreatureUnit.alive = false` 后按策略保留一段时间再销毁或复活 | 单机无需尸体拾取与复活地点竞争等网络语义，简化为死亡状态与复活策略（见 06 死亡与复活） |
| `AreaTrigger`（服务端范围触发） | `AreaTrigger` | 概念直接保留，语义收窄到单机场景切换、任务探索、遭遇触发、脚本钩子四类 |

## 3. 2.5D 空间约定

### 3.1 坐标与深度排序

- 世界坐标是二维平面坐标 `Vec2 (x, y)`；不存在第三维的运行时坐标。
- 视觉纵深（谁画在谁前面）由 `layerDepth` 单独承载，通常由 `position.y`（或专门的深度基准线）加对象类型偏移计算得出，属于表现层渲染约定（详见 09），逻辑层只需要保证每个 `Entity` 有确定的 `layerDepth` 来源。混合渲染下，`layerDepth` 同时用于 2D 前景层与 3D 模型的排序，二者共享同一套排序键，由引擎适配层保证合成顺序一致（见 02）。
- 所有距离、范围、寻路、视线判定只使用平面坐标；架构要求：把 2.5D 换成纯俯视 2D，运行时逻辑不需要任何改动（拍板范围声明，第 1 节）。

### 3.2 方向量化

逻辑朝向是连续角度；量化只对 `sprite` 型外形在表现层进行（见 04、09），`model` 型外形直接使用连续朝向驱动骨骼与挂点，不做方向分桶。

| 字段 | 说明 |
|---|---|
| `direction_count` | 仅 `sprite` 型外形使用：每个外形映射行（`display.map`，见 04）声明 `4\|8\|16` 三档之一 |
| 量化规则 | 仅 `sprite` 型外形使用：实际朝向角度按 `360 / direction_count` 分桶，取最近桶对应的方向精灵 |
| 镜像 | 仅 `sprite` 型外形使用：声明是否允许左右镜像复用精灵（例如 8 方向只需绘制 5 组精灵，其余 3 组由镜像得到），由 `display.map` 的正式字段 `mirror_pairs` 描述（`direction_slot`/`mirror_of`/`flip_x`，详见 04 第 7.1 节与 09 第 3.2 节） |

### 3.3 朝向与高度偏移

- `facing` 独立于移动方向存在（允许原地转身、边走边射等），逻辑层只存角度值，量化由表现层在渲染时按 `direction_count` 做。
- 高度偏移（跳跃、被击飞、飘浮等视觉抬升）不是坐标系的第三维，而是一个附加在 `Unit`/`Projectile` 上的可选表现参数 `heightOffset`（Number，逻辑层可写，表现层只读渲染，不参与平面距离与碰撞计算），影子渲染以该值驱动影子缩放（详见 09）。

### 3.4 视线

- 视线判定退化为二维遮挡查询：给定两点，查询它们之间是否被"遮挡层"标记的地形/物件阻断，不涉及高度。
- 遮挡信息属于地图导航资源的一部分，经 `INavigation2D`/`ISpatialQuery` 接口查询（见第 6 节），逻辑层不直接读地图资源。

### 3.5 范围形状（Shape）

| 形状 | 参数 | 平面定义 |
|---|---|---|
| `circle` | `center: Vec2, radius: Number` | 以 `center` 为圆心、`radius` 为半径的圆 |
| `cone` | `origin: Vec2, direction: Number, angle: Number, radius: Number` | 以 `origin` 为顶点、朝 `direction` 张开 `angle` 角度、延伸 `radius` 距离的扇形 |
| `line` | `origin: Vec2, direction: Number, length: Number, width: Number` | 以 `origin` 为起点沿 `direction` 方向、长 `length` 宽 `width` 的矩形带 |
| `rect` | `origin: Vec2, halfExtents: Vec2, rotation: Number` | 以 `origin` 为中心、给定半宽高、可旋转的矩形 |

`Shape` 是第 6 节 `SkillHost.findUnits` 等接口的通用入参类型，供技能目标解析、AreaTrigger、AI 感知范围等复用。

### 3.6 碰撞层规划

| 层 | 用途 |
|---|---|
| `terrain_block` | 地形阻挡，影响导航与视线 |
| `unit_block`（可选） | 单位间是否互相阻挡移动，策略配置项（默认关闭，允许单位重叠，简化 2.5D 拥挤场景处理） |
| `trigger_only` | 只参与 AreaTrigger/感知查询，不参与移动阻挡与视线 |

碰撞层是 `ISpatialQuery` 查询时的过滤维度，不是独立的对象类型。

补充（2026-09-06）：三层已按空间查询的标签常量落地——`terrain_block` 由导航层（`INavigation2D`）
承载，空间索引不登记任何地形对象，标签常量本身只用于约定与文档对齐；`unit_block` 由单位登记进空间
索引时携带的标签承载，是否据此阻挡移动是移动策略的一个开关（默认关闭，允许单位重叠，与本节"默认
关闭"结论一致）；`trigger_only` 由区域触发实体登记进空间索引时携带的标签承载，命中判定、视线感知、
移动阻挡一类查询需要排除携带此标签的对象。三层结论本身未变——碰撞层仍然是空间查询的过滤维度，不是
独立的对象类型。

## 4. 地图与场景

### 4.1 `world.map` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `world.<地图名>` |
| `scene_ref` | String | 是 | 场景资源引用（不含路径，由引擎适配层解析加载） |
| `regions` | List<Id> | 否 | 该地图内的子区域划分，供 Expr 中 `world` 分组按区域读取标志 |
| `nav_ref` | String | 是 | 导航资源引用（可行走区域、遮挡层数据），由引擎适配层加载后经 `INavigation2D` 暴露 |
| `spawn_points` | List<{id, position, facing}> | 是 | 玩家出生点/复活点清单 |
| `teleport_points` | List<{id, position}> | 否 | 供传送类效果/AreaTrigger 引用的命名传送目标 |
| `music_ref` | String | 否 | 背景音乐资源引用 |
| `allowed_difficulties` | List<Id> | 否 | 该地图允许应用的难度档位（见 08） |

一张地图 = 一个场景资源 + 一行 `world.map` 数据 + 若干条 `spawn.table` 刷新行；不存在"地图分区块动态加载"之类的网格可见范围机制（拍板裁剪原则：一个场景即一张地图，无需网格可见范围）。

`regions`/`teleport_points`/`music_ref`/`allowed_difficulties` 四个字段已按本节类型/必填性接入表结构校验（勘误：实现级 `TableSchema` 现已登记本表全部八个字段，`core/foundation/scene_router/core/WorldMapSchema.cs`，只做类型校验、不做引用完整性校验）；`teleporter` 类物件（见 07）的传送目标引用 `teleport_target_ref` 按以下规则解析：值恰为两段（等于某条 `world.map` 行 `id`，如 `world.town_square`）时目标是该地图 `spawn_points[0]`；值恰为三段、前两段拼接后等于某条 `world.map` 行 `id`（如 `world.town_square.fountain`）时，第三段与该地图 `teleport_points[]`（先查）/`spawn_points[]`（再查）逐条按点位 `id` 的最后一段匹配，命中则目标是该点位的 `position`；其余情况解析失败，不产生位移（详见 07 第 3.1 节该字段的编码规则说明）。

示例记录：

```
id: world.town_square
scene_ref: scene.town_square
regions: [region.town_square.market, region.town_square.gate]
nav_ref: nav.town_square
spawn_points:
  - id: spawn.town_square.default
    position: {x: 120, y: 80}
    facing: 0
teleport_points:
  - id: tp.town_square.fountain
    position: {x: 200, y: 150}
music_ref: music.town_theme
allowed_difficulties: [diff.story, diff.veteran]
```

## 5. 刷新与重生

### 5.1 `spawn.table` 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | Id | 是 | `spawn.<名字>` |
| `map_id` | Id | 是 | 所属地图 |
| `content_ref` | Id | 是 | 指向 `creature.template` 或 `gobj.template` |
| `position` | Vec2 | 是 | 刷新点坐标 |
| `facing` | Number | 否 | 初始朝向 |
| `condition` | Optional<Expr> | 否 | 刷新条件，引用 `world` 分组读取 `WorldState`（例如某标志未设置才刷新） |
| `respawn_policy` | `on_map_enter\|once\|never\|timer` | 是 | 见下表 |
| `respawn_timer` | Optional<Number> | 视策略而定 | `respawn_policy = timer` 时的重生间隔（游戏内秒） |

### 5.2 重生策略

| 策略 | 语义 |
|---|---|
| `on_map_enter` | 每次玩家进入该地图时，若刷新点当前无存活实例且 `condition` 满足，则生成 |
| `once` | 整个游戏进程只生成一次（是否已生成经 `WorldState` 一个自动分配的标志记录），常用于剧情关键生物/物件 |
| `never` | 数据登记但不自动生成，只能由脚本钩子或对话动作显式触发生成，常用于任务过程中才出现的目标 |
| `timer` | 死亡/清除后计时重生，计时基准为游戏内时间（受暂停与时间缩放影响，见 03） |

刷新是数据行为，不是实体持久化：读档后，`CreatureUnit`/`GameObject` 实例本身不从存档恢复，而是由刷新表按策略结合 `WorldState` 重新计算应该存在哪些实例（拍板裁剪原则：重生改为进图刷新策略）。

### 5.3 契约与事件

```
interface SpawnHost {
  applyForMap(mapId: Id): List<Id>
  notifyDespawn(entityId: Id, reason: String): void
  getSpawnRecord(spawnId: Id): Optional<SpawnRecord>
  spawnNow(spawnId: Id, mapId: Id): List<Id>
  update(dt: Number): void
  triggerNever(spawnId: Id): void
  unloadMap(mapId: Id): void
}
```

`applyForMap` 按 5.2 节的重生策略结合 `WorldState` 计算出某地图当前应存在的刷新点实例并生成，返回生成的实体 id 列表；`notifyDespawn` 在实例死亡或被清除时回调，供 `timer` 策略据此计时重生——`reason` 是自由文本分类（不是固定的 `died|despawned` 二选一枚举），供调用方按需传入更具体的原因说明；`getSpawnRecord` 查询某刷新点当前的记录状态（是否已生成、`once` 策略是否已触发过）；`spawnNow` 立即触发一次指定刷新点的生成（不区分 `respawn_policy`、不检查该策略是否允许"立即触发"，行为等价于跳过重生策略判断直接生成一次），供遭遇战/剧情脚本等需要"此刻立即刷出"的场景调用（勘误：2026-09-05）。生成完成时发出事件 `spawn.executed { spawnId, entityId }`。`update` 推进 `timer` 策略的计时（每次调用按 `dt` 扣减全部计时中刷新点的剩余时间，归零且所属地图仍加载时立即重新生成）；`triggerNever` 显式触发一次 `never` 策略的刷新点生成（见 5.2 节该策略"只能由脚本钩子或对话动作显式触发生成"）；`unloadMap` 在地图卸载时清理本模块对该地图各刷新点持有的运行期实例引用（不销毁实体本身，保留计数与计时状态）。

## 6. 导航与移动

### 6.1 接口

移动与空间查询一律经 L-1 引擎适配层暴露的 `INavigation2D`/`ISpatialQuery` 两个接口，逻辑层不直接接触导航网格等引擎内部结构；两个接口的完整签名与语义以 [02_引擎适配层.md](02_引擎适配层.md) 第 1.8、1.9 节为唯一定义处，本节只说明本层如何使用：

- 移动系统在解析一次 `MoveRequest`（见 6.2）时调用 `findPath(mapId, from, to)` 取得路径点列表；返回空（`Optional` 为空）即寻路失败，按 6.2 节"寻路失败处理"分支处理，端点契约与统一可通行规则以 02 第 1.8 节为唯一定义处。
- 移动前的单点/直线可达性判断调用 `isWalkable(mapId, point)`。
- 第 3.4 节的视线退化查询调用 `raycast(mapId, from, to)`：返回值非空即表示两点间视线被遮挡，返回的 `Vec2` 是第一个遮挡点。
- 技能目标解析、AI 感知等按 05 第 3.5 节 `Shape` 联合类型做范围查询时调用 `ISpatialQuery.queryShape(shape, filter)`；取最近单位调用 `nearest(point, filter)`；`filter`（阵营、单位类型等）由调用方按需构造，`mapId` 由当前已加载场景隐含，无需显式传入。
- 移动系统在建立/重算一条路径时记录当时的 `getBlockingVersion(mapId)` 快照（见 `MovementState.navVersion`），供后续 tick 判断该地图的动态阻挡是否又发生了变化（见第 6.4 节）；`getBlockingVersion` 返回 0 的实现（不支持版本追踪）不影响移动系统的其余行为，只是不参与这一项自动重验。

### 6.2 移动请求与速度

| 字段/概念 | 说明 |
|---|---|
| `MoveRequest` | `{unitId: Id, target: Vec2 \| directionVector, mode: walk\|run\|forced}` |
| `stop` 请求 | 游戏侧通用能力需求：`{unitId: Id}`，取消该单位当前的路径跟随/本 tick 尚未生效的位移意图，语义与生效时机见第 6.4 节 |
| 速度来源 | 来自该 `Unit` 的 `StatBlock` 中的移动速度属性（见 06），而非硬编码常量 |
| 控制效果影响 | 定身、减速、沉默移动等控制效果通过挂在 `Unit` 上的光环修改移动速度属性或直接置位"禁止移动"标志，移动系统只读这些派生状态，不知道具体是哪个光环造成的 |
| 寻路失败处理 | `findPath` 返回空时，移动请求方（AI 行为外壳或玩家输入层）收到失败结果通知；框架侧默认保留旧路径继续（向后兼容），游戏层可切换为"清空路径并停止"，两种口味策略与触发时机见第 6.4 节，不由导航系统自行决定后续行为 |

`MovementState`（挂在 `Unit` 上）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `currentPath` | Optional<List<Vec2>> | 当前寻路结果 |
| `moveMode` | `idle\|walk\|run\|forced` | 当前移动模式 |
| `movementLocked` | Bool | 是否被控制效果禁止移动 |
| `pathIndex` | Int | `currentPath` 中下一个尚未到达的路点索引，供移动推进跨多个 tick/回合持续到达，不必每次重新寻路 |
| `navVersion` | Int | 游戏侧通用能力需求：建立/重算 `currentPath` 时记录的 `getBlockingVersion(mapId)` 快照，供第 6.4 节的动态阻挡重验判断"该地图的动态阻挡是否在建路之后又变化过"，默认 0 |

### 6.3 离散模式下的行动点移动预算

`found.time_model.movement_budget_rule`（见 04 第 3.1 节）为 `action_points` 时，离散模式的每次移动意图额外受行动点预算约束，规则如下：

- 每个离散步（回合）对应一个可配置的等效秒数（策略配置项，供"速度 × 时间"位移公式在离散模式下复用，不为离散模式另写一套位移计算）。
- 移动预算按 `distance`（第 6.2 节既有的"按等效秒数换算可移动距离"）或 `action_points`（本节）两种规则二选一，取值来自 `found.time_model.movement_budget_rule`。
- `action_points` 规则下，每移动单位距离消耗的行动点数、每回合可用的行动点总额度均为策略配置项（对应 04 第 3.1 节 `movement_action_cost_per_unit`/`action_points_per_turn`，经组装根从时间模型表回填）。
- 移动前先按本次预计位移距离折算所需行动点，若当前行动者剩余行动点不足，本次移动意图被拒绝（不产生任何位移），并结束该行动者的当前回合（同 06 第 6.2 节"直到本回合行动点/移动预算耗尽"的既有约定）。
- 未装配离散模式，或该口味配置项未接入时，不做任何行动点检查，行为与连续模式下的既有位移逻辑一致。

### 6.4 停止、失败与阻挡变化策略（游戏侧通用能力需求）

游戏侧在验证移动/导航公共接口后提出的通用能力需求：显式取消一次进行中的移动、区分"目标不可达"与"移动过程中地图动态阻挡发生了变化"这两类失败、以及后者发生时按口味策略自动处理，均不涉及具体游戏内容，落在框架层。

**tick 步骤 4"移动与导航"内部固定顺序**（见 03 第 4.2 节勘误）：

1. 先处理本 tick 的停止请求：清除该单位的 `currentPath`、把 `moveMode` 收回 `idle`（`movementLocked` 不变），并丢弃同一 tick 内在它之前提交的该单位位移意图（之后提交的位移意图照常生效）；不产生任何位移。确有路径或待处理的位移意图被取消时触发一次"移动已停止"通知（原因 `requested`），否则静默（幂等）。
2. 再处理本 tick 存活的位移意图：目标类建立/重算路径（记录当时的 `navVersion` 快照），方向类按方向直接位移；目标与当前位置重合（零长度目标）时不建路径、不产生位移、不触发任何失败/停止通知。一次新的目标类请求整体替换仍在进行中的旧路径时，若旧路径确实存在，触发一次"移动已停止"通知（原因 `replaced`）。
3. 再对本 tick 仍持有路径、且未被前两步处理过的单位：比较该地图当前的 `getBlockingVersion(mapId)` 与该路径建立时记录的 `navVersion`——两者相等（含均为 0，即未装配版本追踪）视为无需处理；不同则按"阻挡变化策略"（见下）处理。
4. 最后才真正推进本 tick 的位移（沿路径跟随或方向位移），与本任务之前的既有逻辑一致。

**寻路失败策略**（口味配置项，默认第一种，保证向后兼容）：

| 取值 | 行为 |
|---|---|
| 保留旧路径 | 不改变任何移动状态，本任务之前唯一的行为——路径请求方仍会收到失败通知，但正在进行中的旧路径（如果有）继续沿用，不受这次失败请求影响 |
| 停止 | 清空路径、把 `moveMode` 收回 `idle`，触发一次"移动已停止"通知（原因 `path_failed`）；若当时并没有正在进行的旧路径，则无事可做，不触发通知（与步骤 1 同样的幂等语义） |

寻路失败时，移动请求方同时收到"失败"通知（不区分原因，本任务之前唯一的通知形式，供既有订阅方继续工作）与携带具体原因的失败通知（原因取值：`no_path`——单纯找不到路径；`blocking_change`——阻挡变化后重算/重验又失败，见下）。允许在失败通知的处理逻辑里同步发起新的停止/移动请求，不会在同一次处理中重复触发失败通知。

**阻挡变化策略**（口味配置项，仅当装配的导航实现支持版本追踪时才会被读取；默认第一种）：

| 取值 | 行为 |
|---|---|
| 重算 | 直接以当前实际位置为起点、原路径最终目标为终点重新整体寻路一次，成功则整体替换路径（不触发"移动已停止"通知，这是系统内部的自动重算，不是第 6.2 节意义上的显式"替换"请求）；失败按"寻路失败策略"处理 |
| 重验 | 先对剩余路段逐段做视线判定，判定均不受阻只更新已验证的版本号快照、路径本身不变（比"重算"更省一次寻路开销）；任意一段受阻则委托"重算"分支处理 |
| 停止 | 直接清空路径、把 `moveMode` 收回 `idle`，触发一次"移动已停止"通知（原因 `blocking_change`），不尝试重算 |
| 忽略 | 不处理版本变化，照常沿既有路径推进（口味调整：游戏层认为不值得为动态阻挡自动重验） |

未装配导航，或导航实现不支持版本追踪（`getBlockingVersion` 恒返回 0）时，本节全部与阻挡变化相关的行为不生效，与本任务之前完全一致。

## 7. AreaTrigger 类型

| 类型 | 语义 | 典型用途 |
|---|---|---|
| `map_transition` | 单位进入触发范围后请求切换地图（经场景路由，见 03） | 地图间的门、路径出口 |
| `quest_explore` | 单位进入触发范围后推进"探索类"任务目标（见 08） | 任务要求"到达某地" |
| `encounter_start` | 单位进入触发范围后启动一个遭遇定义（见 08） | Boss 房入口、伏击点 |
| `script` | 进入/离开触发范围后调用脚本钩子（`found.hook`，见 03） | 无法用前三类覆盖的自定义演出 |

陷阱类物件（07 第 3.1 节 `trap`）复用区域触发的进入检测机制，由物件宿主处理触发效果，不在 `trigger_type` 枚举中另列。

`AreaTrigger` 只负责"检测进入/离开 + 满足条件 + 发事件或调用钩子"，不内含具体业务逻辑；具体业务由订阅方（任务系统、遭遇系统、场景路由）处理。

### 7.1 事件与契约

单位进入/离开触发范围且满足 `condition` 时发出事件 `area.trigger_entered { triggerId, unitId }`、`area.trigger_left { triggerId, unitId }`，由订阅方（任务系统、遭遇系统、场景路由等）据此推进各自逻辑。

```
interface AreaTriggerHost {
  register(def: AreaTriggerDef): Id
  unregister(triggerId: Id): void
  evaluate(unitId: Id, position: Vec2): void
}
```

`register` 登记一个触发定义并返回其 id；`unregister` 移除登记；`evaluate` 由移动系统在单位位置变化后调用，检测该单位与已登记触发范围的进入/离开关系并按需发出上述事件。

## 8. WorldState

### 8.1 定位

WorldState 是带命名空间的标志字典，替代魔兽的 Phasing 机制（拍板决策 8）：不做"同一地点渲染出多套不同世界"的分层叠加，而是用标志控制"这个物件是否存在、这段对话是否可见、这个刷新点是否刷新"等具体表现与规则分支，一律经 Expr 的 `world` 分组读取。

### 8.2 接口

```
interface WorldState {
  get(flagKey: Id): Value
  set(flagKey: Id, value: Value, writerId: Id): void
  has(flagKey: Id): Bool
  onChanged(flagKey: Id, callback: (oldValue, newValue) -> Void): SubscriptionHandle
}
```

- `flagKey` 命名空间格式复用 id 规范中的 `world.<路径>`（可多级，如 `world.bridge.repaired`），供内容作者按剧情结构组织。
- 谁能写：任何持有该模块契约引用的系统都可以写（技能效果 `set_world_flag`、对话动作、任务奖励、脚本钩子、遭遇结算），但每次写入必须带 `writerId`（写入方标识，用于排查与日志），架构不做写权限的强约束，约束靠内容评审与 ADR 流程（新增写入来源不算"新原语"，无需专门审批；但新增一种"写入语义"如批量写需过审批）。
- 事件：每次 `set` 触发 `world.flag_changed` 事件到事件总线，附带 `flagKey`、`oldValue`、`newValue`、`writerId`；`onChanged` 是同一事件的按 key 过滤订阅便利接口。
- 持久化：`WorldState` 整体随存档写入，是拍板决策 9 定义的"存档即世界状态加玩家数据"的"世界状态"部分。
- 类型校验（可选）：`WorldState` 提供一个运行期可选的标志类型校验开关，默认关闭；开启后按 `world.flag_schema`（见 04）登记的命名空间前缀与类型，对 `set`/`get` 的 `flagKey` 与取值做匹配检查，命中未登记前缀或类型不符时报错。是否启用、启用时用哪份登记内容由组装根决定，架构本身不强制开启。

## 基础架构提供 / 游戏层提供

| 能力 | 基础架构提供 | 游戏层提供 |
|---|---|---|
| Entity 继承树与字段定义 | 是 | 否 |
| 具体地图数据、刷新表内容 | 提供表结构与加载校验 | 是，每张地图与每条刷新行 |
| 导航与空间查询接口 | 是（`INavigation2D`/`ISpatialQuery` 签名以 02 为唯一定义处） | 否，具体导航资源生成属于内容/资源制作 |
| 方向量化档位与镜像规则 | 提供机制（4/8/16 三档、镜像声明位） | 具体某个外形选哪一档、是否镜像 |
| WorldState 读写接口与持久化 | 是 | 具体标志命名与含义 |
| AreaTrigger 四种类型的调度 | 是 | 每个触发体挂哪种类型、条件、目标内容 |

## 验收标准

1. 任何逻辑对象都能归入 Entity 继承树的某个叶子类型，且字段表覆盖该类型在 06～08 中被引用到的全部字段。
2. 魔兽对照表中的 8 个对象逐一给出了裁剪或保留理由，无遗漏。
3. 给定"从 2.5D 换成纯俯视 2D"的假设检验：本文档定义的坐标、范围形状、寻路、视线、碰撞层描述中不出现任何三维专属的运行时字段。
4. 一张新地图的接入只需要新增一行 `world.map`、若干 `spawn.table` 行、资源引用，无需修改任何本文档定义的接口签名。
5. WorldState 的读写接口足以表达 08 文档中"任务前置""对话显隐""刷新条件""遭遇阶段"等全部引用场景，无需额外接口。
