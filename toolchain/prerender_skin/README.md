# 标准骨骼蒙皮预渲染为序列帧（`run_prerender_skin.py`）

手感设计/04 第 6.2 节"后续项"的落地（[ADR-0140](../../architecture/adr/0140-标准骨骼蒙皮预渲染为序列帧.md)）：`sprite` 型游戏做**一套蒙皮**
（骨名符合标准骨骼的模型，可带装备层），自动得到全部姿势键 × 全部方向档（× 体量组）的序列帧和 `display.anim_set.<名>` 数据行。
不使用任何 AI 生图；渲染由引擎批处理完成，产物与假人姿势集（`std_dummy_poses`）同形，运行期按现有序列帧路径消费，运行期契约不变。

## 用法

```
python toolchain/run_prerender_skin.py <渲染配置.json> --assets-root <资产根> --data-root <数据根> --dataset <数据集>
    [--unity-project adapters/unity] [--unity-exe <Unity.exe>] [--clips-resources-dir GameFoundation/anim_clips]
    [--clean] [--plan-only] [--chunk-frames 800] [--work-dir <中间文件目录>] [--keep-work] [--no-external-validate]
```

- `--chunk-frames N`：每次引擎批处理渲染的剪辑帧数上限（缺省 800，0 = 不分块）。中间裸帧（未压缩 RGBA）按块产生、按块打包后删除，
  全键全方向全体量时不分块约 6 GB 的中间文件，分块后峰值约几百 MB；产物与不分块逐字节相同（有用例断言）。

- 产物写到 `<资产根>/<数据集>/sprite_anim/` 与 `<数据根>/<数据集>/display/display.anim_set.json`（只替换同 id 的行，别的行原样保留）。
- `--plan-only`：只展开并打印渲染计划（资源清单、帧数），不启动引擎、不要根目录参数。
- 引擎可执行文件：`--unity-exe` > 环境变量 `UNITY_EXE` > Program Files 下 Hub 的固定版本。同一引擎工程同一时刻只能开一个实例：
  渲染前不要有别的引擎进程（编辑器、门禁的 Unity 步骤）占着该工程。**首次在一个新检出里运行会先让引擎导入整个工程，要等一阵**（本工程实测约 11 分钟，
  与资产数量成正比），之后每次启动只要几十秒。
- 退出码：0 通过；1 自检/数据校验/引擎失败；2 配置不合法（未启动引擎）；3 蒙皮被拒绝（缺骨骼等，清单已打印）。
- 样例配置（假人当蒙皮的键子集）：[`sample/dummy_skin_subset.json`](sample/dummy_skin_subset.json)。

## 渲染配置

一份 JSON，未知字段直接拒绝。

| 字段 | 缺省 | 含义 |
|---|---|---|
| `anim_set_id` | 必填 | `display.anim_set.<小写名>`；名字不能以 `std_` 开头（留给框架级姿势集） |
| `skin` | 必填 | 引擎工程内的蒙皮资产路径（预制体或模型文件），如 `Assets/Skins/hero.prefab` |
| `stem_prefix` | `<名>_` | 资源名前缀；资源引用 = `sprite_anim.<前缀>[<体量>_]<键点号换下划线>` |
| `direction_count` | 8 | 方向档数 4/8/16（复用 `asset_import.directions` 的定义；其它值拒绝） |
| `slots` | 该档数全部 canonical 档 | 要渲染的 canonical 右侧档位子集，必须含 `front`；镜像档位（`*_l`）与未知档位拒绝，左侧靠运行期水平翻转 |
| `keys` | `"all"` | 要渲染的键（标准姿势清单里的键，别名键折叠到目标资源）；未知键拒绝；`"all"` 时数据行声明 `pose_standard` |
| `mass_groups` | `[]` | 体量组（`light`/`heavy`，中体量就是主集）；组内每个键用剪辑库里同名的体量变体 |
| `layers` | `{}` | `{层名: [选择器…]}`；选择器是相对蒙皮根的对象路径（如 `hips/spine/upper_arm_r/forearm_r/hand_r`），该对象及其下全部渲染器归入该层；层名不能叫 `body`；一个对象不能属于两个层 |
| `canvas` | `[144,144]` | 输出分辨率（每帧像素） |
| `pixels_per_unit` | 32 | 像素密度（世界单位 → 像素） |
| `pivot_px` | `[72,140]` | 脚点（地面点，蒙皮根原点）落在画布的像素坐标（原点在左上） |
| `camera_pitch_deg` | 0 | 相机俯角（0 = 水平侧视），整套固定 |
| `lighting` | `unlit` | `unlit`：把蒙皮材质换成只保留基础色/基础贴图的不受光材质（确定性、与光照无关）；`lit`：保留蒙皮自己的材质，加一盏平行光（`light_euler_deg`/`light_color`/`ambient_color`） |
| `fps` | 20 | 标定帧率（与假人姿势集同缺省） |
| `position_scale` | 1.0 | 髋位置曲线的缩放（蒙皮身高 / 标准身高 2 世界单位） |
| `pivot_tolerance_px` | 3 | 自检：待机首帧脚点相对 `pivot_px` 的允许漂移 |
| `min_opaque_pixels` | 16 | 自检：整身/身体层一帧的不透明像素数下限 |
| `unity_layer` | 30 | 渲染隔离用的引擎层号（相机剔除遮罩只含该层） |

## 蒙皮输入约定

- **骨名**：蒙皮层级里必须有标准骨骼的全部 17 根骨骼，且名字唯一（`hips`、`spine`、`head`、`upper_arm_r/l`、`forearm_r/l`、`hand_r/l`、
  `socket.main_hand`、`socket.off_hand`、`thigh_r/l`、`shin_r/l`、`foot_r/l`；清单来源 `std_dummy_model_clips.config.BONES`）。缺的、重名的一次列出并拒绝，不写任何产物。
- **按骨名施加动画**：标准剪辑的曲线按"曲线路径末段 = 骨名"施加到蒙皮上，蒙皮的层级路径不必与假人一致（例如骨骼放在 `Armature/` 下也行）。
- **休息姿势**：旋转曲线是相对父骨骼的局部四元数，休息姿势 = 双臂双腿自然下垂、面向 +Z、+X 为主手侧（`std_dummy_model_clips.config.CONVENTION`）。
  蒙皮要按这个约定绑定，否则动作会错位。
- **髋位置**：`hips` 的父链相对蒙皮根必须是单位变换（髋位置曲线按根空间写入，乘 `position_scale`）。蒙皮根原点在脚底。
- **装备层**：用选择器把渲染对象分组；分组不影响动画，只影响层变体的可见性。

## 产物布局

与 `std_dummy_poses` 同形（ADR-0038/0072/0093；`<stem>` = 前缀 + [体量_] + 键点号换下划线）：

```
sprite_anim/<stem>/                    整身默认朝向（= front 的整身合成）；资源引用 sprite_anim.<stem>
sprite_anim/<stem>__<方向>/             整身合成的方向变体
sprite_anim/<stem>__<方向>__body/       身体层逐层剪辑（配置了装备层才出）
sprite_anim/<stem>__<方向>__<层名>/     装备层逐层剪辑（配置了装备层才出）
<资产根>/<数据集>/<名>.prerender.json   规格（配置、每个资源的帧数/取样时刻/事件、键到资源的映射）
```

每个资源目录一张 `atlas.png`（宽 ≤ 2048 的网格）+ `frames.json`；`display.anim_set` 数据行：主集一行，配了体量组时再有中体量空覆盖行与各档覆盖行
（`extends` 主集），与假人姿势集同形。

## 时间与事件

时间轴不另起一份：键清单、相位、每相帧数（`max(1, floor(ms*fps/1000+0.5))`）、帧起点/取样时刻（循环剪辑取帧起点，单次剪辑取帧中点）、帧时长、
命名事件时刻全部调用 `std_dummy_poses`（`phase_frame_plan`、`build.frame_times`、`build.clip_events`），所以帧数、帧时长、事件与假人姿势集逐键逐位一致，
事件落在帧边界上，帧下标换算沿用生产路径的同一取整规则，释放点与命中标记的对齐修复（W5/W6）原样保持。引擎侧标准剪辑的关键帧取在同一批帧边界上，
渲染在同一取样时刻对曲线求值。

## 自检（失败即错误）

1. 结构：键集合、每份资源 × 方向 × 层的 `atlas.png`/`frames.json` 都在；帧数、帧时长、帧率、循环标志、画布与图集尺寸与计划一致；数据行键集合、`resource_ref`、事件与计划一致。
2. 非空：整身与身体层每帧不透明像素 ≥ `min_opaque_pixels`；装备层每帧至少 1 个不透明像素。
3. 画布裁切：任何层任何帧的不透明像素不得贴到画布四边。
4. 枢轴不漂移：主集基础待机键（`idle`）首帧每个方向的轮廓底边、脚区（轮廓底部约 6% 画布高度）水平中心与 `pivot_px` 相差不超过 `pivot_tolerance_px`（没渲染 `idle` 键时记一条提示，该项不适用）。只看脚区和基础待机，是因为举臂持械会带偏整身包围盒，战斗/持械站姿的待机变体步幅与重心本来就不同（全量实跑里战斗站姿的脚区中心偏 4～6 像素，属于姿势而不是漂移）。
5. 层对齐（有装备层时）：逐帧，身体层与各装备层的轮廓并集 == 整身轮廓；没被装备层遮住的身体层像素与整身逐像素同色。
6. 数据校验：生成的数据行过 `validate_data.py --strict` 与 `import_assets.py check`（CLI 默认执行，`--no-external-validate` 关闭）。

## 实测（本机，假人当蒙皮）

- **键子集**（`sample/dummy_skin_subset.json`：6 键 + 轻体量 = 12 份剪辑资源 / 180 帧，2 个方向档，整身 + 身体层 + 1 个装备层 = **1080 张图**）：
  PlayMode 用例"渲染子集两次并比较逐字节一致"整段 **15.2 s**（含两次渲染与全部断言；引擎已导入过工程的前提下，一次渲染约 7 秒）。
- **全键全方向全体量**（8 档方向里的 5 个 canonical 右侧档，中/轻/重三个体量组，整身 + 身体层 + 1 个装备层）：357 份剪辑资源 / 4890 帧 × 5 方向 × 3 层变体 =
  **73350 张图**，分 7 次引擎批处理（`--chunk-frames 800`），渲染 + 组装 **179.6 s**，产出 5712 个资源目录、11425 个文件、约 **49 MB**（纯色块图集压缩得很好；
  蒙皮是带纹理的美术时体积会大得多）；自检 41 s（73350 帧逐帧检查），`validate_data --strict` 与 `import_assets check` 通过；390 个键行，`pose_standard` 检查生效；
  不分块的中间裸帧约 6.1 GB，分块后峰值只有几百 MB。

## 判断记录

1. **为什么命令行驱动器不进 pytest 去启动引擎**：门禁里引擎工程被 Unity 步骤占着工程锁，pytest 再起一个批处理会撞锁。所以 pytest 用桩后端覆盖驱动器，
   真实渲染由 PlayMode 用例覆盖，"驱动器 + 引擎批处理"的端到端在本节末尾记实跑数值，不进门禁。
2. **同一台机器逐字节一致，跨机器只承诺结构与像素容差**：同机同输入同配置两次渲染的裸帧与最终产物逐字节相同（PlayMode 用例与 pytest 各断言一次）。不同图形驱动与硬件的光栅化细节可能让边缘像素不同，
   所以跨机器只保证结构（键集、帧数、帧时长、事件、图集尺寸、目录布局）与像素容差，不比较像素字节，不把预渲染产物纳入指纹基线。默认 `unlit` 光照就是为了把变化面压到最小。
3. **按骨名施加曲线而不用引擎的整段采样**：采样要求曲线路径与实例层级逐段一致，蒙皮就必须长得像假人。按骨名施加后任意层级的蒙皮都能复用同一批标准剪辑。
4. **转蒙皮、不转相机**：相机、光照固定，层变体共用同一相机同一姿势，层间逐像素对齐是构造出来的。偏航 `-yaw` 绕世界竖直轴，0 面向镜头、90 面向画面右、180 背向。
5. **装备层对每个键、每个方向都渲染**：不判断某个装备"在这个键里是否可见"。配置了装备层就每个键都出身体层与各装备层的逐层剪辑，体积随层数线性增长（见下）。
6. **身高与比例**：动画是标准库的动作，比例与标准假人差别很大的蒙皮只靠 `position_scale` 缩放髋位置曲线，肢体长度差异不会被补偿（脚可能离地或陷地）。
7. **事件取样**：循环剪辑在帧起点取样、单次剪辑在帧中点取样，与假人姿势集一致；引擎侧标准剪辑在帧边界上有关键帧、线性插值，所以单次剪辑的中点取样是相邻两个边界姿势的插值。
8. **俯角**：`camera_pitch_deg` > 0 时竖直方向按 cos(俯角) 压缩（正交投影），脚点仍落在 `pivot_px`；待机枢轴自检按压缩后的轮廓判定。

## 已知限制

- 蒙皮的休息姿势必须符合标准骨骼约定；不符合的蒙皮不会被工具检出（工具只校验骨名），动作会错位，要靠自检的枢轴/非空/裁切或肉眼发现。
- `unlit` 模式只保留基础色与基础贴图，透明、自发光、法线贴图在该模式下被忽略；要保留它们用 `lit`（结果依赖光照配置，仍是同机逐字节一致）。
- `lit` 模式是否真的受光取决于引擎工程的渲染管线：框架自己的引擎工程用 URP 2D 渲染器，它不处理三维受光，`lit` 在这个工程里的结果等同按材质基础色平涂（轮廓与 `unlit` 逐像素一致）。受光效果只在使用三维渲染器的工程里有意义，框架工程无法验证，所以 `lit` 的受光行为没有自动化用例（只验证能渲染、轮廓与 `unlit` 一致）。
- 不支持带蒙皮网格的混合形状、布料、粒子等随骨骼之外驱动的外观；只有骨骼变换驱动的渲染器会随姿势变化。
- 跨机器的像素字节不保证相同（见判断记录 2）。
- 装备层按"每个键、每个方向都渲染"处理，没有按键裁剪（见判断记录 5）。
- 命令行驱动器的端到端（驱动器 + 引擎批处理）不进门禁（见判断记录 1）。
